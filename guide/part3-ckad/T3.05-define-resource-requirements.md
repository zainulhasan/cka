## 1. Why this matters

A container with no resource settings can take all the CPU and memory of its node, and the scheduler has no idea how big it is. A container with wrong numbers is worse: a **request** that is too large leaves the Pod `Pending` forever, and a **limit** that is too small makes the app slow (CPU) or kills it again and again (memory, exit code 137). In real life, "random restarts" and "Pods that never start" are very often a resources problem. Setting exact numbers, reading a Pod's QoS class and resizing a running Pod are the skills behind the CKAD competency "Define resource requirements" (CKAD-4.4), so practise them until they are fast: the exam has 15-20 tasks in 2 hours, about 6 minutes per task ([E2](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad), [E3](https://docs.linuxfoundation.org/tc-docs/certification/faq-cka-ckad-cks)). A wrong unit (`m` instead of `Mi`) is accepted by the API and silently ruins the Pod, so you must know the units cold.

## 2. Concepts

### 2.1 Requests and limits: what they are and why there are two

Every container may declare, per resource, two numbers under `resources:`.

| Field | Meaning | Who uses it | What happens at the boundary |
|---|---|---|---|
| `resources.requests` | The amount the container **needs**, reserved for it | The **scheduler** (picks a node), the kubelet (sets `cpu.weight`, computes QoS class and `oom_score_adj`), HPA (CPU % is relative to the request) | Not a boundary at runtime. A container may use more than it requested if the node has spare capacity |
| `resources.limits` | The **ceiling** the container may reach | The **kubelet and container runtime**, via cgroup files (`cpu.max`, `memory.max`) | CPU above the limit: the container is **throttled**. Memory above the limit: the container is **OOM-killed** |

The problem this solves: a cluster shares nodes between many teams' workloads. Without requests, the scheduler stacks Pods on one node until it chokes. Without limits, one leaking Pod starves its neighbours. Requests make **placement** predictable. Limits make **damage** bounded.

**Fields reference** (all live in each container, under `spec.containers[].resources`):

| Field | What it does | Default | Invalid or risky values |
|---|---|---|---|
| `requests.cpu` | CPU reserved for scheduling; becomes `cpu.weight` | none (counts as 0) | Larger than `limits.cpu` is rejected. `0.1m` is invalid (finest unit is `1m`). A request larger than any node's allocatable CPU = Pod `Pending` forever |
| `requests.memory` | Memory reserved for scheduling and QoS | none (counts as 0) | Larger than `limits.memory` is rejected. `128m` is **accepted** and means 0.128 bytes |
| `limits.cpu` | CPU ceiling; becomes `cpu.max` quota | none (unlimited) | Very small limits (`10m`) make most apps crawl |
| `limits.memory` | Memory ceiling; becomes `memory.max` | none (unlimited) | Below the app's real working set = `OOMKilled` loop |
| `requests.ephemeral-storage`, `limits.ephemeral-storage` | Local disk (writable layer, logs, `emptyDir`) | none | Over the limit = the Pod is **evicted** (section 2.8) |
| `<vendor>/<name>` such as `nvidia.com/gpu` | Extended resources (section 2.12) | none | Whole numbers only; no overcommit |

**Defaulting rule.** If you set a `limit` and omit the `request` for the same resource, the API server copies the limit into the request. The reverse does not happen. This is how a "limits only" container ends up Guaranteed (section 2.5).

**Imperative style does not exist for bare Pods.** REAL OUTPUT (kubectl v1.37.1, offline): `kubectl run --help` has no `--requests` or `--limits` flag in v1.37.1 (`grep -i -E "limit|request"` over the help text finds only the `--dry-run` text). For a Pod you generate YAML and add the block; for a Deployment you use `k set resources` (section 2.11).

### 2.2 Units: `m`, `Mi`, `Gi`, `M` vs `Mi`

**CPU** is measured in CPU units. `1` means one vCPU (one core or one hyperthread). `1000m` ("1000 millicores") is the same as `1`. `100m` is a tenth of a CPU. `0.5` is allowed and equals `500m`. The finest precision is `1m`.

**Memory** is measured in bytes. You write a plain integer or a number with a suffix. There are two families of suffixes:

| Suffix | Family | Value | Example | In bytes |
|---|---|---|---|---|
| `k`, `M`, `G`, `T`, `P`, `E` | decimal (powers of 1000) | `M` = 1,000,000 | `128M` | 128,000,000 |
| `Ki`, `Mi`, `Gi`, `Ti`, `Pi`, `Ei` | binary (powers of 1024) | `Mi` = 1,048,576 | `128Mi` | 134,217,728 |
| (none) | plain bytes | | `134217728` | 134,217,728 |
| `m` | **milli** (thousandths) | `m` = 0.001 | `128m` | 0.128 (rounded up to 1 byte) |

REAL OUTPUT (Docker): `docker run --memory=128m` followed by `cat /sys/fs/cgroup/memory.max` printed `134217728`, which is exactly `128Mi`. Docker's `m` means MiB, Kubernetes' `m` does not. Do not carry the habit over.

Three traps:

1. **`M` vs `Mi`.** `128M` is about 4.6% smaller than `128Mi`. Both are valid. The exam text usually says `Mi`; copy it exactly.
2. **`m` on memory.** `memory: 400m` is valid and means 0.4 bytes. The API server does not warn. The container then fails to start or is killed at once. The docs call this out explicitly.
3. **Case matters.** `1gi`, `128mi` and `100M` mean different things or are invalid. The API checks the pattern, not your intent.

REAL OUTPUT (kubectl v1.37.1, offline): a malformed quantity is caught by the client parser.

```console
$ kubectl set resources -f web.yaml --local --limits=cpu=2x -o yaml
error: quantities must match the regular expression '^([+-]?[0-9.]+)([eEinumkKMGTP]*[-+]?[0-9]*)$'
```

Note what that check is: only a pattern for the *shape* of the text. `x` is not in its letter list, so `2x` fails. But `128m` matches the pattern and is a valid quantity, even though it is almost never what you meant for memory. A quantity that parses is not necessarily a sensible one.

### 2.3 Scheduling uses requests only; capacity vs allocatable

The scheduler never looks at live usage. For each node it asks one question per resource:

```
sum of requests of Pods already on the node + request of the new Pod  <=  node allocatable
```

If the answer is "no" for every node, the Pod stays `Pending` with the event `Insufficient cpu` (or `Insufficient memory`). This check is the **NodeResourcesFit** scheduler plugin. Two consequences:

- A Pod with **no requests counts as 0**. The scheduler will put it anywhere, even on a node that is already at 95% real CPU. This is why BestEffort Pods can crowd a node.
- A node can be idle in real usage and still "full" for the scheduler, because requests already add up to its allocatable. Real usage does not matter for placement.

**Capacity vs allocatable.** `status.capacity` is what the machine has. `status.allocatable` is what the scheduler may hand out to Pods:

```
allocatable = capacity - kube-reserved - system-reserved - hard eviction threshold
```

`kube-reserved` and `system-reserved` are kubelet settings that keep room for the kubelet, container runtime and OS daemons. The hard eviction threshold (default `memory.available<100Mi`) keeps a memory cushion. On kind the reservations are usually zero, so allocatable is close to capacity. Always read `allocatable`, not `capacity`.

Commands (these are the ones to type):

```bash
k get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.allocatable.cpu,MEM:.status.allocatable.memory
k describe node lab-worker | grep -A8 'Allocated resources'
```

(The entry's example node name is `w1`, the CKA VM name. On the kind lab cluster use `lab-worker`; in the exam use the node name from `k get nodes`.)

EXPECTED OUTPUT (not captured). The numbers depend on the host machine that runs your kind nodes:

```console
$ k describe node lab-worker | grep -A8 'Allocated resources'
Allocated resources:
  (Total limits may be over 100 percent, i.e., overcommitted.)
  Resource           Requests    Limits
  --------           --------    ------
  cpu                100m (1%)   100m (1%)
  memory             50Mi (0%)   50Mi (0%)
  ephemeral-storage  0 (0%)      0 (0%)
  hugepages-1Gi      0 (0%)      0 (0%)
```

How to read it: the **Requests** column is what the scheduler counts against allocatable; the percentage is relative to allocatable. The **Limits** column can exceed 100%. The line "Total limits may be over 100 percent, i.e., overcommitted" is the official statement that limits are allowed to add up to more than the node has (see the diagram in section 3). Requests can never exceed 100% through the scheduler.

**Under the hood.** The scheduler is not the only gate. After a Pod is bound to a node, the **kubelet** runs its own admission check against the node's allocatable. If the check fails (for example because requests changed since scheduling), the Pod ends in `Failed` with reason `OutOfcpu` or `OutOfmemory`. This is rare; a `Pending` Pod is the common failure.

In kind, the control-plane node carries the taint `node-role.kubernetes.io/control-plane:NoSchedule`, so normal Pods only fit on the two workers. A "not enough CPU" event therefore usually reads `1 node(s) had untolerated taint ..., 2 Insufficient cpu`.

### 2.4 CPU limit means throttling; memory limit means OOMKill

CPU and memory behave differently because of one property: CPU is **compressible** (you can make a process wait for CPU without hurting its correctness) and memory is **incompressible** (you cannot take memory back without killing something).

| | CPU | Memory |
|---|---|---|
| Request becomes | `cpu.weight` (relative share when CPUs are contended) | Nothing in a cgroup by default. Used by scheduler, QoS and `oom_score_adj` |
| Limit becomes | `cpu.max` quota per 100 ms period (CFS bandwidth) | `memory.max` (hard cap) |
| Over the limit | **Throttled**: threads pause until the next period. The process keeps living | Kernel reclaims, then **OOM-kills** a process in the container. Container exit code **137** (128 + SIGKILL 9) |
| What you see | Slow app, latency spikes, no restart, no event | `OOMKilled` / exit 137 / restarts / `CrashLoopBackOff` |
| No limit set | Container may use any idle CPU of the node | Container may grow until the node itself is in trouble |

See [T1.10](../part1-linux/T1.10-linux-namespaces-and-cgroups-v2.md) for the full cgroup tables. The conversions you need here:

| Spec | cgroup v2 file | Example |
|---|---|---|
| `limits.cpu: 200m` | `cpu.max` = `20000 100000` (20 ms of CPU per 100 ms period) | `500m` gives `50000 100000`; `1` gives `100000 100000` |
| `limits.memory: 128Mi` | `memory.max` = `134217728` | |
| `requests.cpu` | `cpu.weight` (relative; the exact number depends on the runtime version, T1.10 section 2.10) | |

REAL OUTPUT (Docker): the kernel files for a container started with `--cpus=0.2 --memory=128m` (Docker writes the same `cpu.max` that the kubelet would write for `limits.cpu: 200m`):

```console
$ docker run --rm --cpus=0.2 --memory=128m busybox:1.36 sh -c 'cat /sys/fs/cgroup/cpu.max /sys/fs/cgroup/memory.max'
20000 100000
134217728
```

**CPU throttling, proven.** REAL OUTPUT (Docker): a busy loop for 3 seconds under a 0.2 CPU limit. `nr_periods` is how many 100 ms periods passed, `nr_throttled` is in how many of them the group ran out of quota, `throttled_usec` is the total time spent paused:

```console
$ docker run --rm --cpus=0.2 busybox:1.36 sh -c 'timeout 3 sh -c "while :; do :; done"; grep -E "nr_periods|nr_throttled|throttled_usec" /sys/fs/cgroup/cpu.stat'
Terminated
nr_periods 32
nr_throttled 31
throttled_usec 2467542
```

31 of 32 periods throttled, about 2.5 s of waiting in 3 s: the loop got the 20% it was allowed. In a Pod you read the same file with `k exec <pod> -- cat /sys/fs/cgroup/cpu.stat`.

**Memory kill, proven.** REAL OUTPUT (Docker): a process that writes 48 MiB into `/dev/shm` (a RAM-backed tmpfs, so it counts against the memory cgroup) under a 32 MiB limit. `exec` makes `dd` the container's main process, so its death is the container's exit:

```console
$ docker run --rm --memory=32m --memory-swap=32m busybox:1.36 sh -c 'exec dd if=/dev/zero of=/dev/shm/x bs=1M count=48'; echo "exit=$?"
exit=137
```

In Kubernetes the same event shows up as `Last State: Terminated, Reason: OOMKilled, Exit Code: 137`. Caveats from T1.10: the label can briefly read `Error` (with exit code 137) before it reads `OOMKilled`, and exit code 137 on its own only means "SIGKILL" (it also appears when a Pod is force-deleted). The proof of an OOM kill is `OOMKilled`, or `oom_kill` greater than 0 in the container's `memory.events`.

**Working set vs `memory.current`.** The kernel reports `memory.current` (all memory charged to the cgroup, including reclaimable page cache). `k top pod` (metrics-server) reports the **working set**, which is `memory.current` minus inactive file cache. The kill decision is made on the cgroup counter, so when you size a limit, look at the peak of `memory.current` (`k exec <pod> -- cat /sys/fs/cgroup/memory.current`) and add a safety margin, not at an average.

**Related but different: no memory limit.** A container with no memory limit has no `memory.max`, so the cgroup OOM killer never triggers for it. It can still die later through node-level OOM or kubelet eviction (section 2.6). "No limit" does not mean "safe".

### 2.5 QoS classes

The **Quality of Service (QoS) class** is a label the API server computes for every Pod at creation and stores in `status.qosClass`. It is read-only and never changes during the Pod's life (even with in-place resize, section 2.10). It decides how the Pod is treated when the node runs short of resources.

| Class | Rule (the whole Pod, **every** container including init containers) | Typical use |
|---|---|---|
| **Guaranteed** | For **both** CPU and memory, every container has a request **and** a limit, and request = limit | Databases, anything that must not be squeezed |
| **Burstable** | Not Guaranteed, and at least one container has a CPU or memory request or limit | Most apps |
| **BestEffort** | **No** container has any CPU or memory request or limit | Throwaway jobs |

Read the Guaranteed rule slowly. One container without a memory limit makes the whole Pod Burstable. `ephemeral-storage` does not take part in the QoS decision.

Examples (container-level `resources:` blocks; each is a complete block you can paste into a container):

```yaml
# BestEffort: no resources block at all (or an empty one)

# Burstable: requests below limits
resources:
  requests: {cpu: 100m, memory: 64Mi}
  limits:   {cpu: 200m, memory: 128Mi}

# Burstable: only a request, no limit
resources:
  requests: {cpu: 100m}

# Guaranteed: requests equal limits for cpu AND memory
resources:
  requests: {cpu: 100m, memory: 64Mi}
  limits:   {cpu: 100m, memory: 64Mi}

# Guaranteed too: limits only (the API server copies them into requests)
resources:
  limits: {cpu: 100m, memory: 64Mi}
```

Quick classification table (practise until instant):

| Pod | Class | Why |
|---|---|---|
| One container, no resources | BestEffort | nothing set |
| One container, `limits` cpu and memory only | Guaranteed | requests default to limits |
| One container, cpu request = cpu limit, no memory settings | Burstable | memory is missing |
| One container, cpu 100m/200m, memory 64Mi/64Mi | Burstable | cpu request is not equal to limit |
| Two containers: one fully equal, one with no resources | Burstable | not every container qualifies |
| App container Guaranteed, init container with no resources | Burstable | init containers count too |
| Two containers, both with cpu and memory request = limit | Guaranteed | every container qualifies |

Read the class with:

```bash
k get pod web -o jsonpath='{.status.qosClass}'
k get pod -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
```

**Under the hood.** The kubelet uses the class to place the Pod's cgroup (a Guaranteed Pod sits directly under the kubepods slice; Burstable and BestEffort Pods sit in `burstable` and `besteffort` slices) and to set `oom_score_adj` on its processes: Guaranteed -997, BestEffort 1000, Burstable between 2 and 999 (a larger memory request gives a lower score). The kernel's node-level OOM killer kills the highest score first. See T1.10 section 2.10 for the REAL kind captures.

### 2.6 Eviction order under node pressure

There are three different "killers". Do not mix them up.

| Killer | Trigger | Who acts | Victim | Visible as |
|---|---|---|---|---|
| **cgroup OOM kill** | One container passes its own `memory.max` | Kernel | A container | `OOMKilled`, exit 137, container restarts |
| **Node OOM kill** | The whole node is out of memory before the kubelet reacts | Kernel, ranked by `oom_score_adj` | A process (BestEffort first, Guaranteed last) | A container restart on the node |
| **Node-pressure eviction** | A node signal crosses a threshold (for example `memory.available<100Mi`, `nodefs.available<10%`, `imagefs.available<15%`, `nodefs.inodesFree<5%` are the Linux defaults for hard thresholds) | **Kubelet** | A whole **Pod** | Pod `Failed`, `kubectl get pod` shows `Evicted` |

For eviction, the kubelet ranks Pods in three steps (from the node-pressure eviction docs):

1. Pods whose usage of the starved resource is **above their request** go first. A Pod using less than it requested goes last.
2. Among those, the lower **Pod priority** goes first.
3. Then the Pod using the most above its request goes first.

This is where QoS shows up, indirectly:

- **BestEffort** Pods have a request of 0, so any usage is "above request": they are evicted first.
- **Burstable** Pods are in the middle: evicted first if they run above their request, and the further above, the earlier.
- **Guaranteed** Pods never run above their request for CPU/memory (request = limit), so they are evicted last. (The kubelet may still evict them if system daemons are starved.)

Eviction side effects you should recognise: the node gets the condition `MemoryPressure=True` (or `DiskPressure`), and a taint such as `node.kubernetes.io/memory-pressure:NoSchedule` stops new Pods without a toleration. The evicted Pod object stays in `Failed` state with reason `Evicted` until you delete it (`k delete pod <name>`); its controller creates a replacement elsewhere.

CPU is never the cause of an eviction. CPU shortage only slows things down.

### 2.7 Init containers and sidecars: the effective request

A Pod runs its containers in phases: init containers run one at a time before the app starts; **sidecar** containers (an init container with `restartPolicy: Always`, stable since v1.33) start in order and then keep running next to the app. The scheduler needs one number per resource for the whole Pod: the **effective request**. The rules:

1. Add up the requests of all **app containers**, plus all **sidecar** containers. Call it `RUN`.
2. For each **regular** init container, take its request **plus** the requests of every sidecar that was started **before** it (sidecars defined above it in `initContainers`). Call each one `INIT_i`.
3. Effective request = `max(RUN, INIT_1, INIT_2, ...)`. The same rule applies to limits.
4. If the Pod's RuntimeClass has `overhead`, add it on top.

Why `max` and not a sum for regular init containers: they finish before the app starts, so they never run at the same time as the app. Why sidecars are added: they stay alive during the app.

Worked numbers (the Pod in section 5, step 4):

| Container | Kind | CPU request | Memory request |
|---|---|---|---|
| `init-db` | regular init (first) | 500m | 64Mi |
| `log-agent` | sidecar (`restartPolicy: Always`) | 100m | 32Mi |
| `init-cfg` | regular init (after the sidecar) | 300m | 16Mi |
| `app` | app container | 200m | 128Mi |

- `RUN` = app + sidecar = 200m + 100m = **300m** CPU; 128Mi + 32Mi = **160Mi** memory.
- `INIT_init-db` = 500m (no sidecar started yet); 64Mi.
- `INIT_init-cfg` = 300m + 100m (sidecar already running) = 400m; 16Mi + 32Mi = 48Mi.
- Effective request = `max(300, 500, 400)` = **500m** CPU and `max(160, 64, 48)` = **160Mi** memory.

So this Pod "costs" 500m on its node even though the app and sidecar only request 300m. A big init container (a migration job, for example) can make a Pod unschedulable even when the app itself is small. QoS also counts init containers: they must be request = limit too for Guaranteed. (Sidecar and init patterns in full: T3.08.)

`k describe node <node>` lists each Pod's CPU/memory request in its "Non-terminated Pods" table using this effective value.

### 2.8 Ephemeral storage

**Ephemeral storage** is the node's local disk used by a Pod: the container's writable layer, container logs, and `emptyDir` volumes (when not memory-backed). It dies with the Pod. You can request and limit it like memory:

- Units are the same as memory: `500Mi`, `2Gi`, `2G`. (A plain number is bytes.)
- The scheduler checks `requests.ephemeral-storage` against the node's allocatable `ephemeral-storage`.
- There is **no cgroup file** for it. The kubelet measures usage periodically and, when a Pod passes its limit, **evicts the Pod** (it is not an OOM kill and there is no exit code 137). `emptyDir.sizeLimit` is a separate cap on one volume and has the same effect.

Complete YAML (the Pod writes 100 MiB into an `emptyDir` with a 50 MiB limit):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: eph
  namespace: lab-t305
spec:
  containers:
  - name: fill
    image: busybox:1.36
    command: ["sh", "-c", "dd if=/dev/zero of=/data/big bs=1M count=100; sleep 3600"]
    resources:
      requests:
        ephemeral-storage: 20Mi     # scheduler reserves this much node disk
      limits:
        ephemeral-storage: 50Mi     # kubelet evicts the Pod above this
    volumeMounts:
    - name: scratch
      mountPath: /data
  volumes:
  - name: scratch
    emptyDir: {}
```

EXPECTED OUTPUT (not captured). The kubelet checks usage on a timer, so the eviction can take from a few seconds to about a minute. Rely on the Pod status `Evicted`; the event wording below is not confirmed (section 11):

### 2.9 Pod-level resources (awareness)

Normally resources are set per container. **Pod-level resources** let you set a budget for the whole Pod in `spec.resources` (CPU, memory, and hugepages), shared by all containers. Useful when containers have bursty, uncorrelated usage and you do not want to size each one.

Feature stage in v1.37: **UNVERIFIED** (the topic entry says beta). The field is `spec.resources.requests` / `spec.resources.limits`. If the feature gate is off on a cluster, the field is not accepted, so check with `k explain pod.spec.resources` first. The docs page is linked in section 10. Behaviour to look up there before relying on it (UNVERIFIED for 1.37, section 11): how container-level values must fit inside the pod-level values, whether containers without their own limits can burst up to the pod-level limit, and how the QoS class is computed from the pod-level values.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pod-level
  namespace: lab-t305
spec:
  resources:                  # budget for the whole Pod
    requests:
      cpu: 500m
      memory: 256Mi
    limits:
      cpu: 500m
      memory: 256Mi
  containers:
  - name: a
    image: busybox:1.36
    command: ["sleep", "3600"]
  - name: b
    image: busybox:1.36
    command: ["sleep", "3600"]
```

This lesson's labs do not use it. For the exam, container-level `resources` is what to type unless the task names pod-level resources.

### 2.10 In-place Pod resize

**The problem.** A Pod's `spec.containers[].resources` used to be immutable. To give a running Pod more CPU you had to delete it (or roll the Deployment), which means a restart and lost state. **In-place resize** (GA in v1.35 per the topic entry; verify on 1.37, section 11) lets you change CPU and memory requests/limits of a **running** Pod through a special `resize` **subresource**. The kubelet then updates the container's cgroup, and, depending on the policy, may or may not restart the container.

**The command.** It needs kubectl v1.32 or newer for `--subresource`:

```bash
k patch pod web --subresource resize --patch \
  '{"spec":{"containers":[{"name":"web","resources":{"requests":{"cpu":"400m"},"limits":{"cpu":"400m"}}}]}}'
```

The patch is a strategic merge, so the container is matched by `name`. The only fields you may change through `resize` are the CPU and memory requests and limits.

**`resizePolicy`** is a per-container field you set when the Pod is created. It tells the kubelet what to do for each resource:

| `resourceName` | `restartPolicy` | Effect when you resize that resource |
|---|---|---|
| `cpu` or `memory` | `NotRequired` (**default** if you do not set `resizePolicy`) | The kubelet changes the cgroup live. Container keeps running; `restartCount` unchanged |
| `cpu` or `memory` | `RestartContainer` | The kubelet **restarts that container** (not the Pod) so it starts with the new value. `restartCount` goes up by 1 |

Use `RestartContainer` for memory when the application reads its memory limit only at start (the JVM sizing its heap is the classic case). CPU is almost always `NotRequired`.

```yaml
resizePolicy:
- resourceName: cpu
  restartPolicy: NotRequired
- resourceName: memory
  restartPolicy: RestartContainer
```

**How to observe a resize.** Three places hold three different things:

| Where | Meaning |
|---|---|
| `spec.containers[].resources` | The **desired** values (what you patched) |
| `status.containerStatuses[].allocatedResources` | What the kubelet has **accepted** for this container |
| `status.containerStatuses[].resources` | What is **actually applied** in the running container |
| `status.conditions` of type `PodResizePending` / `PodResizeInProgress` | Progress and problems |

When desired, allocated and actual all match, the resize is done. In short, the resize is **done when** the three values agree and neither `PodResizePending` nor `PodResizeInProgress` is listed in `status.conditions`. The old `status.resize` field (values `Proposed`, `InProgress`, `Deferred`, `Infeasible`) was removed in v1.33 and replaced by the two conditions below; if a tutorial mentions `status.resize`, it is out of date for 1.37.

| Condition | Reason | Meaning | What to do |
|---|---|---|---|
| `PodResizePending` | `Deferred` | Node cannot fit the new size **now** (other Pods use the room). May succeed later | Free capacity, or wait |
| `PodResizePending` | `Infeasible` | Cannot work on this node at all (bigger than the node, or a rule below is violated) | Revert the patch; recreate the Pod with the new size |
| `PodResizeInProgress` | | The kubelet is applying the change | Wait a few seconds, re-check |

Commands to inspect:

```bash
k get pod web -o jsonpath='{.status.containerStatuses[0].restartCount}{"\n"}'
k get pod web -o jsonpath='{.status.containerStatuses[0].resources}{"\n"}'
k get pod web -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'
k exec web -- cat /sys/fs/cgroup/cpu.max
```

**Rules and limits (check the docs page for the exact list on your version).** Only CPU and memory can be resized. The QoS class must not change, so a Guaranteed Pod must stay request = limit (patch both together). You cannot remove a request or limit that was never set. A Pod must be running. Windows nodes are not covered. Regular (non-sidecar) init containers are not resizable. A memory limit decrease is only accepted if the container's current usage allows it.

**Important for Deployments.** Resizing a Pod changes only that Pod. The Deployment's Pod template is unchanged, so the next rollout or a replacement Pod comes back at the old size. For a lasting change patch the template too (`k set resources deploy ...`, which rolls out new Pods). In-place resize is for "scale this one live Pod now".

| | Edit the Deployment (`k set resources`) | In-place resize (`--subresource resize`) |
|---|---|---|
| Restarts Pods | Yes, rolling replacement | No (for `NotRequired`) |
| Survives next rollout | Yes | No, unless the template is changed too |
| Works on a bare Pod | No: a bare Pod has no template, and the API rejects resource edits on a live Pod | Yes |

### 2.11 `kubectl set resources`, the fast imperative path

For anything with a Pod template (Deployment, ReplicaSet, StatefulSet, DaemonSet, Job):

```bash
k set resources deploy web -c web --requests=cpu=100m,memory=64Mi --limits=cpu=200m,memory=128Mi
```

| Part | Meaning |
|---|---|
| `-c web` / `--containers` | Name of the **container** inside the template. Default is `*` (all containers). It is the container name, not the Deployment name |
| `--requests=cpu=100m,memory=64Mi` | Comma-separated `resource=quantity` pairs |
| `--limits=...` | Same for limits. If you give a limit and no request, the API server defaults the request to the limit |
| `--local -f file.yaml -o yaml` | Edit a local file and print it, no cluster needed |
| `--limits=cpu=0,memory=0` | Does **not** remove the entry. REAL OUTPUT (kubectl v1.37.1, offline): it stores `cpu: "0"` and `memory: "0"` under both `requests` and `limits`. The keys stay, so do not use this to "remove" resources; whether a `"0"` value still gives `BestEffort` is unconfirmed (section 11, item 14). To delete the whole block use a JSON patch (section 4.1) |

It changes the Pod template, so it triggers a rolling update. It does not work on a bare Pod.

**Trap: the container name.** `k create deploy web --image=nginx:1.27` names the container **`nginx`** (taken from the image), not `web`. So `-c web` fails. REAL OUTPUT (kubectl v1.37.1, offline), using a file made by `k create deploy web --image=nginx:1.27 $do`:

```console

```

The same command with the right name works. REAL OUTPUT (kubectl v1.37.1, offline), trimmed:


For a bare Pod: generate YAML, then add the block. `yq` is on the exam hosts ([E9](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)), so you can script the edit:

### 2.12 Extended resources (awareness)

An **extended resource** is any resource name outside the `kubernetes.io` domain, for example `nvidia.com/gpu` (GPU device plugin) or `example.com/dongle`. They are advertised by a node (usually by a **device plugin**) in `status.capacity`, and Pods ask for them under `limits` (and optionally `requests`). Rules:

- Whole numbers only. `nvidia.com/gpu: 1` is valid, `0.5` is not.
- Only in `limits` is enough; if you give both, they must be equal. There is no overcommit.
- The scheduler treats them like CPU: a Pod that needs a resource no node advertises stays `Pending` with `Insufficient <name>`.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-pod
  namespace: lab-t305
spec:
  containers:
  - name: cuda
    image: busybox:1.36
    command: ["sleep", "3600"]
    resources:
      limits:
        nvidia.com/gpu: 1      # Pending forever on kind: no node advertises it
```

You can fake an extended resource on a lab node. EXPECTED OUTPUT (not captured); the command pattern comes from the "Advertise extended resources for a node" task in the docs:

```bash
k proxy &                       # serves the API on 127.0.0.1:8001
curl --header "Content-Type: application/json-patch+json" --request PATCH \
  --data '[{"op":"add","path":"/status/capacity/example.com~1dongle","value":"4"}]' \
  http://localhost:8001/api/v1/nodes/lab-worker/status
k get node lab-worker -o jsonpath='{.status.allocatable.example\.com/dongle}{"\n"}'   # expect: 4
kill %1                         # stop the proxy
```

`~1` stands for `/` inside a JSON-patch path. To remove it: the same call with `[{"op":"remove","path":"/status/capacity/example.com~1dongle"}]`.

### 2.13 Interaction with LimitRange (and ResourceQuota)

Two namespace-level objects change what happens to resources you did or did not write. They get a full lesson in [T3.06 Requests, limits and quotas: ResourceQuota and LimitRange](../part3-ckad/T3.06-requests-limits-and-quotas-resourcequota-and.md). What you need here:

| Object | Effect on a Pod you create |
|---|---|
| **LimitRange** `default` / `defaultRequest` | If a container has **no** limit / request, the admission controller **fills in** the namespace defaults at creation. Your "BestEffort" Pod may therefore come out Burstable or Guaranteed |
| **LimitRange** `min` / `max` | Values outside the range are **rejected** at creation |
| **ResourceQuota** (`requests.cpu`, `limits.memory`, ...) | The sum over the namespace is capped. If a quota covers cpu or memory, every new Pod **must** state that resource (or get it from a LimitRange), otherwise creation fails |

Clue for the exam and for troubleshooting: you did not set resources, but `k get pod -o yaml` shows them. Run `k get limitrange -n <ns>`. Defaults are applied once, at creation; editing the LimitRange later does not change existing Pods.

### 2.14 Related but different

| Often confused | Difference |
|---|---|
| Request vs limit | Request = reserved for placement. Limit = ceiling enforced at runtime |
| `OOMKilled` vs `Evicted` | OOMKilled: kernel killed a container over **its own** limit; Pod object stays, container restarts. Evicted: kubelet removed a **whole Pod** because the **node** was short; Pod ends `Failed` |
| `Pending` vs `OOMKilled` | Pending = never scheduled (look at scheduler events, requests too big). OOMKilled = ran and was killed (limit too small) |
| Resource requests vs ResourceQuota | Requests are per container; quota is a namespace-wide total |
| HPA | HPA's CPU utilisation % = usage divided by the **request**. No request, no percentage, no autoscaling |

## 3. How it works (diagram)

ASCII bar chart for one node, CPU only (1 character = 100m). Three Pods run on it: **A** Guaranteed (request = limit = 1000m), **B** Burstable (request 800m, limit 2000m), **C** Burstable (request 600m, limit 3000m). A fourth Pod **D** is BestEffort (no request, no limit).

```
1 char = 100m         0         10        20        30        40        50        60
                      |---------|---------|---------|---------|---------|---------|---------
capacity   4000m      ########################################
allocatable 3800m     ######################################
requests    2400m     AAAAAAAAAABBBBBBBBCCCCCC..............  <- 1400m free for new Pods
limits      6000m+    AAAAAAAAAABBBBBBBBBBBBBBBBBBBBCCCCCCCCCCCCCCCCCCCCCCCCCCCCCC  D (BestEffort: no limit) ->
                                                            ^ allocatable line: limits may pass it, requests may not

QoS:  A = Guaranteed (last to be evicted)   B, C = Burstable (evicted when above their request)
      D = BestEffort (first to be evicted)
```

Walkthrough:

- `capacity` is the machine; `allocatable` is what is left after reservations. The scheduler's budget is the **allocatable** bar.
- The **requests** bar (2400m) is what the scheduler adds up. It must stay inside allocatable. The dots are 1400m that a new Pod with a request up to 1400m could still use. A Pod requesting 1500m would be `Pending` with `Insufficient cpu`, even if the node is idle right now.
- The **limits** bar (6000m, plus D without any limit) is much longer than allocatable. That is **overcommit**: Kubernetes allows it because Pods rarely peak together. If they do, CPU is shared by `cpu.weight` (proportional to requests) and each Pod is capped by its own `cpu.max`.
- For memory the same picture applies, but the overcommit is dangerous: nothing can be "shared" by waiting. If real memory use passes the node's limit, the kernel or kubelet kills: D first, then B and C if they are above their requests, A last.

### 4.1 Imperative shortcuts

```bash
# Set requests and limits on a Deployment's container (triggers a rollout)
k set resources deploy web -c web --requests=cpu=100m,memory=64Mi --limits=cpu=200m,memory=128Mi

# Why is it Pending?

# Live usage (needs metrics-server)
k top pod -n lab-t305

# Resize a running Pod in place
k patch pod web --subresource resize --patch '{"spec":{"containers":[{"name":"web","resources":{"requests":{"cpu":"400m"},"limits":{"cpu":"400m"}}}]}}'
```

### 4.2 Declarative YAML

A Burstable Pod with every field explained:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web
  namespace: lab-t305
spec:
  containers:
  - name: web                    # container name: use it with -c and in resize patches
    image: nginx:1.27
    resources:
      requests:                  # what the scheduler reserves (placement + cpu.weight + QoS)
        cpu: 100m                # 0.1 CPU. Must be <= limits.cpu
        memory: 64Mi             # 64 MiB. Must be <= limits.memory. "64m" would be 0.064 bytes!
        ephemeral-storage: 100Mi # optional: local disk reserved on the node
      limits:                    # runtime ceiling
        cpu: 200m                # becomes cpu.max = 20000 100000; above it the container is throttled
        memory: 128Mi            # becomes memory.max = 134217728; above it: OOMKilled, exit 137
        ephemeral-storage: 500Mi # above it the Pod is evicted
    resizePolicy:                # optional: what the kubelet does on an in-place resize
    - resourceName: cpu
      restartPolicy: NotRequired        # default; change cgroup live
    - resourceName: memory
      restartPolicy: RestartContainer   # restart this container to apply a memory change
```

A **Guaranteed** Pod (requests equal limits for cpu and memory in every container):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: web-gu
  namespace: lab-t305
spec:
  containers:
  - name: web
    image: nginx:1.27
    resources:
      requests:
        cpu: 200m
        memory: 128Mi
      limits:
        cpu: 200m            # equal to the request
        memory: 128Mi        # equal to the request
```

The resize command for it, keeping request = limit so the QoS class does not change:

```bash
k patch pod web-gu -n lab-t305 --subresource resize --patch \
  '{"spec":{"containers":[{"name":"web","resources":{"requests":{"cpu":"400m"},"limits":{"cpu":"400m"}}}]}}'
```

## 6. Common mistakes and how to fix them

| Symptom | What you will see (exact error/event text) | Cause | Fix (command) |
|---|---|---|---|
| Pod `Pending` forever | `k describe pod`, Events: `Warning  FailedScheduling  ...  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 Insufficient cpu. preemption: ...` (the part after `preemption:` varies; the `Insufficient cpu` / `Insufficient memory` words are the key) | The Pod's (effective) request is larger than the free allocatable CPU or memory of every node | Lower the request: `k set resources deploy NAME --requests=cpu=250m`; or add nodes. Check data with the ladder below |
| Container restarts again and again | `STATUS CrashLoopBackOff`; `Last State: Terminated  Reason: OOMKilled  Exit Code: 137` | `limits.memory` is below the app's working set | Raise the limit: `k set resources deploy NAME --limits=memory=256Mi`; compare with `k exec POD -- cat /sys/fs/cgroup/memory.current` and `k top pod` |
| Apply fails with an unknown field | `Error from server (BadRequest): error when creating "pod.yaml": Pod in version "v1" cannot be handled as a Pod: strict decoding error: unknown field "spec.containers[0].resources.limit"` (EXPECTED; exact wording may differ) | `limit:` written instead of `limits:` (same for `request:`, `resource:`) | Fix the key to `limits` / `requests` / `resources`; re-apply |
| Apply fails on values | `spec.containers[0].resources.requests: Invalid value: "500m": must be less than or equal to cpu limit of 200m` | Request is larger than the limit | Make request <= limit (or equal for Guaranteed) |
| Apply fails on a unit | `error: quantities must match the regular expression '^([+-]?[0-9.]+)([eEinumkKMGTP]*[-+]?[0-9]*)$'` (REAL, from kubectl 1.37.1; the API server prints a similar `Invalid value` message) | Typo in a quantity such as `128MiB` or `2x` | Use `m` for CPU, `Mi`/`Gi` for memory |
| Pod starts but dies at once, or acts as if limit is tiny | Valid YAML, no error. Container fails or is killed immediately | `memory: 128m` (milli) instead of `128Mi` | Write `Mi`; re-create the Pod |
| QoS class is not what you expected | `Burstable` where you wanted `Guaranteed` | One container (or an init container) is missing a CPU or memory request/limit, or a request differs from its limit | `k get pod POD -o jsonpath='{range .spec.containers[*]}{.name}{" "}{.resources}{"\n"}{end}'` and equalise every container |
| `k set resources` fails | `error: unable to find container named web` (REAL, kubectl 1.37.1) | `-c` needs the container name; `k create deploy` names it after the image | `k get deploy web -o jsonpath='{.spec.template.spec.containers[*].name}'` |
| Editing resources on a running bare Pod | `The Pod "web" is invalid: spec: Forbidden: pod updates may not change fields other than ...` | Pod specs are immutable; only the `resize` subresource may change CPU/memory | Use `--subresource resize` (section 2.10) or `k replace --force -f pod.yaml` |
| Pod `Evicted` | `k get pod`: `STATUS Evicted`; event text like `The node was low on resource: memory` or `Pod ephemeral local storage usage exceeds the total limit of containers ...` | Node pressure, or `ephemeral-storage` limit passed | Read the message in `k describe pod`; add requests/limits, free disk, `k delete pod` the Failed Pod |
| App slow, no error, no restarts | Nothing in events. `nr_throttled` is high in `cpu.stat` | CPU limit too low (throttling) | `k set resources deploy NAME --limits=cpu=500m` (or remove the CPU limit) |

**Diagnosis ladder 1: Pod `Pending` with `Insufficient cpu`** (run in this order):

1. `k get pod -n NS` shows `Pending`. Pending has other causes (taints, selectors, unbound PVCs), so go to events next.
2. `k describe pod POD -n NS | grep -A8 Events` (or `k get events -n NS --field-selector reason=FailedScheduling`). The text `Insufficient cpu` or `Insufficient memory` confirms a resource problem. A message about `untolerated taint` or `didn't match Pod's node affinity` is a different problem. A message can list several reasons, one per node group (for example `1 untolerated taint, 2 Insufficient cpu`).
3. `k get pod POD -n NS -o jsonpath='{.spec.containers[*].resources.requests}'`: what the Pod asks for. Remember the **effective** request (section 2.7), so check init containers too.
4. `k get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.allocatable.cpu,MEM:.status.allocatable.memory`: the largest single node. If the request is larger than every node's allocatable, no amount of waiting helps (an unschedulable Pod). If it is smaller than allocatable but still Pending, other Pods use the room.
5. `k describe node NODE | grep -A8 'Allocated resources'`: the Requests column shows how much of allocatable is taken. Free = allocatable minus requests.
6. Fix: lower the request to fit, free capacity (scale something down), or add nodes. Then watch `k get pod -w`.

**Diagnosis ladder 2: restarts with `OOMKilled`**:

1. `k get pod POD` shows `RESTARTS` growing and `CrashLoopBackOff`.
2. `k describe pod POD | grep -A6 'Last State'`: `Reason: OOMKilled` and `Exit Code: 137` mean the memory limit was hit. If it says `Error` with 137, check again a few restarts later (T1.10), or check `oom_kill` in `memory.events`. If the exit code is something else (for example 1), the app crashed for its own reason: read `k logs POD --previous`.
3. `k get pod POD -o jsonpath='{.spec.containers[0].resources.limits.memory}'`: the current limit.
4. `k top pod POD` (metrics-server) and `k exec POD -- cat /sys/fs/cgroup/memory.current` while it is up: how close the app gets to the limit. A steady climb to the limit is a leak; a jump at start-up means the limit is just too low.
5. Fix: `k set resources deploy NAME --limits=memory=256Mi` (also raise the request if it was equal). For a bare Pod, delete and re-create it with the new limit.

**Diagnosis ladder 3: field typo** (`limit:`): the error names the field path (`spec.containers[0].resources.limit`). Open the file, change the key, re-apply. Prevent it by generating the block with `yq` or by copying it from the docs instead of typing it. Without strict validation (`--validate=false`) the unknown field would be dropped silently and the Pod would run with **no** limits, which is why you never turn validation off to "make it work".

### Lab B (Medium): resize a running Pod in place

**Setup**

```bash
k create ns lab-t305
mkdir -p ~/lab/t305
cat <<'EOF' | k apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: resize-demo
  namespace: lab-t305
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
    resizePolicy:
    - resourceName: cpu
      restartPolicy: NotRequired
    - resourceName: memory
      restartPolicy: RestartContainer
    resources:
      requests: {cpu: 200m, memory: 128Mi}
      limits: {cpu: 200m, memory: 128Mi}
EOF
k wait --for=condition=Ready pod/resize-demo -n lab-t305 --timeout=90s
k get pod resize-demo -n lab-t305 -o jsonpath='{.metadata.uid}' > ~/lab/t305/uid.txt   # for the "same Pod" check
```

**Task.** Pod `resize-demo` in `lab-t305` has one container `app`.

1. Raise the CPU request **and** limit of `app` to `400m` without restarting the container. Write the container's `restartCount` after the change to `~/lab/t305/restarts.txt`.
2. Then raise the memory request and limit to `192Mi`. Observe that the container restarts exactly once, and that the Pod object is not re-created (same UID).
3. The QoS class must still be `Guaranteed` at the end.

<details><summary>Hint 1</summary>

Changing `spec.containers[].resources` with `k edit` or a plain `patch` is rejected. The command needs `--subresource resize`.
</details>

<details><summary>Hint 2</summary>

The patch body is `{"spec":{"containers":[{"name":"app","resources":{...}}]}}`. Include both `requests` and `limits`, so the QoS class stays the same.
</details>

<details><summary>Hint 3</summary>

Prove the change inside the container: `k exec resize-demo -n lab-t305 -- cat /sys/fs/cgroup/cpu.max` (the first number is the quota in microseconds per 100000), and `memory.max` in bytes (192Mi = 201326592).
</details>

<details><summary>Solution</summary>

```bash
UID1=$(k get pod resize-demo -n lab-t305 -o jsonpath='{.metadata.uid}')

# 1. CPU, in place (policy NotRequired)
k patch pod resize-demo -n lab-t305 --subresource resize --patch \
  '{"spec":{"containers":[{"name":"app","resources":{"requests":{"cpu":"400m"},"limits":{"cpu":"400m"}}}]}}'
until [ "$(k get pod resize-demo -n lab-t305 -o jsonpath='{.status.containerStatuses[0].resources.limits.cpu}')" = 400m ]; do sleep 2; done
k get pod resize-demo -n lab-t305 -o jsonpath='{.status.containerStatuses[0].restartCount}' > ~/lab/t305/restarts.txt
cat ~/lab/t305/restarts.txt
k exec resize-demo -n lab-t305 -- cat /sys/fs/cgroup/cpu.max

# 2. Memory (policy RestartContainer)
k patch pod resize-demo -n lab-t305 --subresource resize --patch \
  '{"spec":{"containers":[{"name":"app","resources":{"requests":{"memory":"192Mi"},"limits":{"memory":"192Mi"}}}]}}'
until [ "$(k get pod resize-demo -n lab-t305 -o jsonpath='{.status.containerStatuses[0].restartCount}')" = 1 ]; do sleep 2; done
k wait --for=condition=Ready pod/resize-demo -n lab-t305 --timeout=60s
k exec resize-demo -n lab-t305 -- cat /sys/fs/cgroup/memory.max
echo "$UID1 $(k get pod resize-demo -n lab-t305 -o jsonpath='{.metadata.uid}')"
```

Why each step: the `resize` subresource is the only door for editing resources on a live Pod. CPU has policy `NotRequired`, so the kubelet only rewrites `cpu.max` (the container process is untouched, `restartCount` stays 0). Memory has `RestartContainer`, so the kubelet restarts the container to apply `memory.max`; the Pod (same UID) and its IP stay, only the container restarts. Requests and limits are changed together to keep Guaranteed. The `until` loops wait for the kubelet, because the patch returns before the change is applied.

EXPECTED OUTPUT (not captured):

```console
pod/resize-demo patched
0
40000 100000
pod/resize-demo patched
pod/resize-demo condition met
201326592
3f1c... 3f1c...
```
</details>

**Verification**

```bash
test "$(cat ~/lab/t305/restarts.txt)" = 0 \
 && test "$(cat ~/lab/t305/uid.txt)" = "$(k get pod resize-demo -n lab-t305 -o jsonpath='{.metadata.uid}')" \
 && test "$(k get pod resize-demo -n lab-t305 -o jsonpath='{.status.containerStatuses[0].restartCount}')" = 1 \
 && test "$(k get pod resize-demo -n lab-t305 -o jsonpath='{.spec.containers[0].resources.limits.cpu}')" = 400m \
 && test "$(k get pod resize-demo -n lab-t305 -o jsonpath='{.spec.containers[0].resources.limits.memory}')" = 192Mi \
 && test "$(k exec resize-demo -n lab-t305 -- cat /sys/fs/cgroup/cpu.max)" = "40000 100000" \
 && test "$(k exec resize-demo -n lab-t305 -- cat /sys/fs/cgroup/memory.max)" = 201326592 \
 && test "$(k get pod resize-demo -n lab-t305 -o jsonpath='{.status.qosClass}')" = Guaranteed \
 && echo OK
```

## 8. Exam tips

- **Pick the tool by object type.** Deployment (or anything with a template): `k set resources ... -c <container> --requests=... --limits=...`. Bare Pod: `k run ... $do > pod.yaml`, add the `resources:` block (with `yq -i`, which is on the exam hosts, [E9](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)), then apply. Never try to `k edit` resources of a running bare Pod; delete and re-create, or use the resize subresource.
- **Check the container name before `-c`.** `k create deploy` names the container after the image (`nginx`), not the Deployment. When in doubt, omit `-c` (all containers) or print the names with `jsonpath`.
- **Read units twice.** `m` is for CPU (and means milli); memory uses `Mi`/`Gi`. `M` is not `Mi`. After the change, print the result (`k get ... -o jsonpath='{...resources}'`) and read the class with `jsonpath='{.status.qosClass}'`.
- **Pending Pod with resources? Look at events first.** `k describe pod` Events tells you `Insufficient cpu` in one line. Then compare with `k get nodes -o custom-columns=...allocatable...`. Do not guess the numbers.
- **Docs pages to open in the exam** (all inside the allowed docs, [E13](https://docs.linuxfoundation.org/tc-docs/certification/certification-resources-allowed)): 
  - https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/ (units, requests and limits, ephemeral storage, extended resources)
  - https://kubernetes.io/docs/concepts/workloads/pods/pod-qos/ (QoS rules)
  - https://kubernetes.io/docs/tasks/configure-pod-container/resize-container-resources/ (the exact resize command and `resizePolicy`)

## 9. Quick review

1. Which resource numbers does the scheduler use to place a Pod, and which does it ignore?

<details><summary>Answer</summary>

It uses `requests` (summed with the Pods already on the node, compared with node `allocatable`). It ignores `limits` and the real usage.
</details>

2. What does `memory: 400m` mean, and why is it dangerous?

<details><summary>Answer</summary>

`m` means milli, so 400m is 0.4 bytes. The API accepts it. The container then cannot run. Use `Mi` or `Gi`.
</details>

3. A Pod has two containers. One has cpu and memory requests equal to limits. The other has no resources. Which class, and why?

<details><summary>Answer</summary>

Burstable. Guaranteed needs every container to have request = limit for both CPU and memory. BestEffort needs none to have anything; here one does.
</details>

4. Why does exceeding a CPU limit never kill the container, but exceeding a memory limit does?

<details><summary>Answer</summary>

CPU is compressible: the CFS bandwidth controller (`cpu.max`) just pauses threads until the next 100 ms period. Memory is incompressible: after the kernel fails to reclaim, it must kill a process in the cgroup (OOM kill, exit code 137, reason `OOMKilled`).
</details>

5. Write the command that sets requests `cpu=100m,memory=64Mi` and limits `cpu=200m,memory=128Mi` for container `web` of Deployment `web`.

<details><summary>Answer</summary>

`k set resources deploy web -c web --requests=cpu=100m,memory=64Mi --limits=cpu=200m,memory=128Mi`
</details>

6. A Pod has an init container requesting 500m, a sidecar requesting 100m, and an app container requesting 200m. What effective CPU request does the scheduler use?

<details><summary>Answer</summary>

`max(app + sidecar, init) = max(300m, 500m) = 500m` (the init container runs before the app, with no sidecar started yet in this setup; it is not added to the app).
</details>

7. A Deployment's Pods are `Pending` with `Insufficient cpu`. Name the first three checks.

<details><summary>Answer</summary>

(1) `k describe pod` Events to confirm the reason; (2) the Pod's effective request (`jsonpath` on `resources.requests`, init containers included); (3) `k get nodes -o custom-columns=...allocatable...` and `k describe node | grep -A8 'Allocated resources'` to see the largest node and how much is already requested.
</details>

8. What is the command to resize a running Pod's CPU in place, and what decides whether the container restarts?

<details><summary>Answer</summary>

`k patch pod NAME --subresource resize --patch '{"spec":{"containers":[{"name":"C","resources":{"requests":{"cpu":"400m"},"limits":{"cpu":"400m"}}}]}}'`. The container's `resizePolicy` for that resource decides: `NotRequired` (default) means no restart; `RestartContainer` restarts that container.
</details>

9. Which Pods does the kubelet evict first under memory pressure, and why is a Guaranteed Pod the safest?

<details><summary>Answer</summary>

The kubelet ranks Pods by (1) usage above request, (2) priority, (3) how far above request. BestEffort Pods have a request of 0, so they are always above it and go first. A Guaranteed Pod's request equals its limit, so it does not run above its request and is evicted last.
</details>

10. You set no resources, but `k get pod -o yaml` shows requests and limits. Where did they come from?

<details><summary>Answer</summary>

A LimitRange in the namespace with `default` / `defaultRequest` filled them in at creation (T3.06). Check with `k get limitrange -n NS`.
</details>
