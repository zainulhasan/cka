## 1. Why this matters

By default a container process runs as root (UID 0) inside its own namespaces, with 14 Linux capabilities, with a writable root filesystem, and with the right to gain more privileges. If an attacker gets code running in such a container, every one of those defaults helps them: they can write tools to disk, change files, open raw sockets, and try kernel bugs. The `securityContext` is the set of fields in the Pod spec that takes those defaults away. In real clusters this is the first line of defence, and Pod Security Admission (PSA) rejects Pods that do not set it.

In the exam you are asked to set exact values: `runAsUser`, `fsGroup`, a read-only root filesystem, "drop all capabilities and add only X", and to fix a Pod that crashes after you harden it. Putting a field at the wrong level (for example `capabilities` at Pod level) is rejected at once, and a hardened app that cannot write `/tmp` crashes. The exam averages about 6 minutes per task (15-20 tasks in 2 hours; sources: [E2](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad), [E3](https://docs.linuxfoundation.org/tc-docs/certification/faq-cka-ckad-cks)), so the YAML in section 4 must come from your fingers without thinking.

## 2. Concepts

### 2.1 What a securityContext is, and what happens to it

**The problem.** A container is not a small VM. It is a normal Linux process that the kernel has put into namespaces and cgroups (see [T1.10](../part1-linux/T1.10-linux-namespaces-and-cgroups-v2.md)). The kernel still decides what that process may do with its UID, its capabilities, its system calls and its file access. Without settings, the container runtime picks defaults that favour "most images just work": root user, a wide capability set, a writable root filesystem. A `securityContext` lets you pick tighter values per Pod or per container.

**There are two places to put it.**

- `spec.securityContext` is the **Pod-level** context. It applies to every container in the Pod (including init and ephemeral containers) and to the Pod's volumes.
- `spec.containers[].securityContext` is the **container-level** context. It applies to one container and **overrides** the Pod-level value for the same field (section 2.4).

Each level has its own field list. Some fields exist at both levels, some at one level only. You cannot move a field between levels.

**Under the hood.** The path of a field is: you create the Pod, the API server validates the fields and stores them, the scheduler picks a node, and the kubelet on that node translates the `securityContext` into a CRI (container runtime interface) request to the runtime (containerd, then runc). runc does the real work before it starts your process: it sets the UID, GID and supplementary groups, trims the capability sets, sets the `no_new_privs` flag, loads the seccomp filter, mounts the root filesystem read-only if asked, and enters the user namespace if there is one. The kubelet does two jobs of its own: it checks `runAsNonRoot` against the image's user, and for `fsGroup` it changes the group and mode of volume contents. What does the kernel enforce? Everything. What does the Kubernetes API server enforce? Only that the field values are valid.

**What breaks without it.** Without a `securityContext` your container is root with a writable filesystem. With PSA `restricted` on the namespace (see [T3.16](../part3-ckad/T3.16-understand-authentication-authorization-and-admission-control.md)) the Pod is not even created.

### 2.2 Pod-level fields

List captured from the cluster with `k explain pod.spec.securityContext` (field names only):

```text
appArmorProfile  fsGroup  fsGroupChangePolicy  runAsGroup  runAsNonRoot  runAsUser
seLinuxChangePolicy  seLinuxOptions  seccompProfile  supplementalGroups
supplementalGroupsPolicy  sysctls  windowsOptions
```

Note what is **not** in that list: `capabilities`, `privileged`, `allowPrivilegeEscalation`, `readOnlyRootFilesystem`, `procMount`. Those are container-level only.

| Field | What it does | Default | Risky or invalid value |
|---|---|---|---|
| `runAsUser` | UID of the container's first process. Overrides the image `USER`. | The image's `USER`; root (0) if the image sets none. | `0` is root. With `runAsNonRoot: true` it gives `container's runAsUser breaks non-root policy`. Negative numbers are invalid. |
| `runAsGroup` | Primary GID of the first process. | The image's group (usually `0` for root images). | `0` makes root the primary group, which can write many root-group files. |
| `runAsNonRoot` | A **check, not a setting**. If true, the kubelet refuses to start a container that would run as UID 0. | unset (false). | `true` with a root image and no `runAsUser` gives `CreateContainerConfigError` (section 6). It does not choose a user for you. |
| `fsGroup` | A GID that owns the contents of supported volumes. The kubelet sets the group of the volume to it and adds it to the process's supplementary groups. | unset. | Only helps volume types that support ownership change. |
| `fsGroupChangePolicy` | `Always` or `OnRootMismatch`. When the kubelet re-applies `fsGroup` to a volume. | `Always`. | Per `k explain`, it has no effect on `emptyDir`, `secret` and `configMap`. It only matters for big persistent volumes (slow chown on every mount). |
| `supplementalGroups` | Extra GIDs added to the process, besides the primary group and `fsGroup`. | none. | A group GID that owns something sensitive (for example the node's `docker` group on a hostPath) is a privilege grant. |
| `supplementalGroupsPolicy` | `Merge` (also keep the groups the image defines for that user in `/etc/group`) or `Strict` (use only the groups you list). | `Merge`. | Feature status in v1.37: UNVERIFIED. The `k explain` text on this cluster still says "(Alpha) ... requires the SupplementalGroupsPolicy feature gate", and the docs page's feature-state line was not read. `Strict` also needs runtime support. I did not test `Strict`: before you rely on it, run `k explain pod.spec.securityContext.supplementalGroupsPolicy`. See section 11. |
| `seccompProfile` | System-call filter: `type` is `RuntimeDefault`, `Unconfined` or `Localhost` (section 2.6). | `Unconfined` on the kind cluster used here (captured: `Seccomp: 0`). | `Unconfined` turns the filter off. |
| `appArmorProfile` | AppArmor profile (section 2.7). GA since v1.31. | runtime default if AppArmor is on the node. | `Unconfined`. |
| `seLinuxOptions`, `seLinuxChangePolicy` | SELinux label and the relabel strategy (awareness, section 2.7). | node/runtime default. | A different `type`/`level` can break separation between Pods. |
| `sysctls` | Kernel parameters for the Pod's namespaces, as `name`/`value` pairs. | none. | Only "safe" sysctls are allowed by default. An unsafe one is rejected by the kubelet (below). |
| `windowsOptions` | Windows-only settings. Not used for Linux Pods. | none. | Setting it on a Linux Pod. |

**Seen on the cluster: `supplementalGroups` and `sysctls`.** A Pod with `runAsUser: 1000`, `runAsGroup: 3000`, `supplementalGroups: [4000, 5000]`, `fsGroup: 2000` and a safe sysctl `net.ipv4.ip_local_port_range`. The manifest (rebuilt from the settings used in the capture; save it as `groups.yaml` and `k apply -f groups.yaml`):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: groups
  namespace: lab-t317
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 3000
    supplementalGroups: [4000, 5000]   # extra GIDs
    fsGroup: 2000                      # also becomes a supplementary group
    sysctls:
    - name: net.ipv4.ip_local_port_range   # a safe sysctl
      value: "32768 40000"
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
```

Observe with `id` (groups) and by reading the sysctl from `/proc/sys`:

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
$ k -n lab-t317 exec groups -- id
uid=1000 gid=3000 groups=2000,3000,4000,5000
$ k -n lab-t317 exec groups -- cat /proc/sys/net/ipv4/ip_local_port_range
32768	40000
```

So the process's groups are the primary group (3000) plus `fsGroup` (2000) plus the supplemental groups (4000, 5000).

An **unsafe** sysctl (here `kernel.msgmax`) is accepted by the API server but rejected on the node, so the Pod is `Failed` at once. Manifest (name `unsafe`; the value is any number, the kubelet rejects the name before it uses the value):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: unsafe
  namespace: lab-t317
spec:
  securityContext:
    sysctls:
    - name: kernel.msgmax
      value: "16384"
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
```

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
$ k -n lab-t317 get pod unsafe
NAME     READY   STATUS            RESTARTS   AGE
unsafe   0/1     SysctlForbidden   0          5s
$ k -n lab-t317 describe pod unsafe | grep -E 'Reason|Message'
Reason:           SysctlForbidden
Message:          Pod was rejected: forbidden sysctl: "kernel.msgmax" not allowlisted
```

An unsafe sysctl needs the kubelet flag `--allowed-unsafe-sysctls` on the node, which you cannot change in a CKAD task. In a task, use the safe ones. The Pod Security Standards page (section 2.12) lists the safe set that `baseline` allows.

**`fsGroupChangePolicy` in practice.** `fsGroup` makes the kubelet change the group (and the setgid bit) on the volume when it mounts it. With `Always` (the default) the kubelet walks every file in the volume on every mount. With `OnRootMismatch` it looks only at the volume's root directory: if the root already has the right group and permissions, it skips the walk. It changes how often the chown runs, not the end state, and it does nothing for `emptyDir`, `secret` and `configMap` (per `k explain`). So you only see a difference on a large persistent volume whose type supports ownership change. Snippet:

```yaml
spec:
  securityContext:
    fsGroup: 2000
    fsGroupChangePolicy: OnRootMismatch   # default is Always
```

How to observe it (a PersistentVolumeClaim `data-pvc` mounted at `/data` is needed; the volume type must support ownership change, which kind's default local-path storage may not, UNVERIFIED): start a Pod as root with `fsGroup: 2000`, run `chgrp 9999 /data/f` on a file inside, delete the Pod, and start it again with the same spec. With `Always` the file's group is back to `2000` (`ls -ln /data/f`). With `OnRootMismatch` it stays `9999`, because the root directory already matched. This procedure was not run (section 11).

### 2.3 Container-level fields

List captured with `k explain pod.spec.containers.securityContext`:

```text
allowPrivilegeEscalation  appArmorProfile  capabilities  privileged  procMount
readOnlyRootFilesystem  runAsGroup  runAsNonRoot  runAsUser  seLinuxOptions
seccompProfile  windowsOptions
```

| Field | What it does | Default | Risky or invalid value |
|---|---|---|---|
| `allowPrivilegeEscalation` | Sets the kernel `no_new_privs` flag when `false`. A process with that flag cannot gain more rights than its parent through `execve` (setuid binaries, file capabilities). | `true`. | `true` is the default. It is **always** true when the container is `privileged` or has `CAP_SYS_ADMIN` (per `k explain`). |
| `privileged` | `true` gives the container all capabilities, access to all host devices, and no seccomp/AppArmor filter. Almost the same as root on the node. | `false`. | `true`. Combined with `allowPrivilegeEscalation: false` the API server rejects it (below). |
| `capabilities.add` / `capabilities.drop` | Lists of capability names without the `CAP_` prefix, for example `NET_BIND_SERVICE`. `ALL` is allowed in `drop`. | the runtime's default set of 14. | `add: ["SYS_ADMIN"]`, `add: ["NET_ADMIN"]` (section 2.5). Names with the `CAP_` prefix are not the Kubernetes spelling. |
| `readOnlyRootFilesystem` | Mounts the container's root filesystem read-only. Volumes you mount stay writable (if they are not `readOnly`). | `false`. | `true` breaks apps that write to `/tmp`, `/var/run` or their own directory unless you mount an `emptyDir` there (section 2.8). |
| `runAsUser`, `runAsGroup`, `runAsNonRoot` | Same meaning as at Pod level. When set here they win. | unset. | Same as Pod level. |
| `seccompProfile`, `appArmorProfile` | Same as at Pod level, per container. | inherit from the Pod. | `Unconfined`. |
| `seLinuxOptions` | Per container SELinux label. | inherit. | See section 2.7. |
| `procMount` | `Default` or `Unmasked`. `Default` hides some paths under `/proc` from the container. | `Default`. | `Unmasked` is only valid when `hostUsers: false` (captured error below). |
| `windowsOptions` | Windows-only. | none. | On a Linux Pod. |

Two API-server checks captured on the cluster:


### 2.4 Precedence: container overrides Pod

If the same field is set at both levels, the container-level value wins for that container. Containers that do not set it inherit the Pod-level value. A field set only at one level is used as it is.

Manifest (Pod `prec`, rebuilt from the settings used in the capture):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: prec
  namespace: lab-t317
spec:
  securityContext:
    runAsUser: 1000          # Pod level
    runAsGroup: 3000
  containers:
  - name: inherits           # sets nothing: takes UID 1000 and GID 3000
    image: busybox:1.36
    command: ["sleep", "3600"]
  - name: overrides
    image: busybox:1.36
    command: ["sleep", "3600"]
    securityContext:
      runAsUser: 2000        # container level wins for this field only
```

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
# Pod: runAsUser 1000, runAsGroup 3000. Container "overrides" sets runAsUser 2000.
$ k -n lab-t317 exec prec -c inherits  -- id
uid=1000 gid=3000 groups=3000
$ k -n lab-t317 exec prec -c overrides -- id
uid=2000 gid=3000 groups=3000
```

The second container took its UID from its own `securityContext` and its GID from the Pod. Precedence is **per field**, not per block. Only the fields that exist at both levels can conflict: `runAsUser`, `runAsGroup`, `runAsNonRoot`, `seccompProfile`, `appArmorProfile`, `seLinuxOptions`.

### 2.5 Linux capabilities

**The problem.** In old Unix, "root" is one huge power: UID 0 may do anything. Linux splits root's powers into about 40 pieces called **capabilities**, for example "bind a port below 1024" (`CAP_NET_BIND_SERVICE`), "change file owners" (`CAP_CHOWN`), "load kernel modules" (`CAP_SYS_MODULE`). A process holds a set of them. A container needs few. Dropping the rest limits what a compromised process can do, even as UID 0.

**The five sets.** `/proc/<pid>/status` shows five masks, each a hex number where one bit is one capability:

| Line | Name | Meaning |
|---|---|---|
| `CapInh` | inheritable | what may be passed on across `execve` |
| `CapPrm` | permitted | the upper limit of what the process may use |
| `CapEff` | effective | what the kernel checks **right now** when the process does something |
| `CapBnd` | bounding | a hard ceiling. A capability not in it can never be gained |
| `CapAmb` | ambient | kept across `execve` for non-root programs |

**The default set.** A container with no `capabilities` setting gets the runtime's default 14. We read it from a Pod and decoded it with `capsh` in Docker (`capsh` is a tool from the `libcap` package; it is not guaranteed on exam hosts, so treat decoding as something you do on your own VM, and `man capabilities` as the reference):

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
$ k -n lab-t317 exec plain -- grep Cap /proc/1/status
CapInh:	0000000000000000
CapPrm:	00000000a80425fb
CapEff:	00000000a80425fb
CapBnd:	00000000a80425fb
CapAmb:	0000000000000000
```

```text
REAL OUTPUT (Docker)
$ capsh --decode=00000000a80425fb
0x00000000a80425fb=cap_chown,cap_dac_override,cap_fowner,cap_fsetid,cap_kill,cap_setgid,cap_setuid,cap_setpcap,cap_net_bind_service,cap_net_raw,cap_sys_chroot,cap_mknod,cap_audit_write,cap_setfcap
$ capsh --decode=0000000000000400
0x0000000000000400=cap_net_bind_service
```

Fourteen names: that is the default set. `0x400` is bit 10, which is `cap_net_bind_service`.

**Syntax.**

```yaml
securityContext:
  capabilities:
    drop: ["ALL"]               # remove every capability
    add: ["NET_BIND_SERVICE"]   # then add back only what the app needs
```

Order does not matter to you: Kubernetes applies `drop` and `add` so that the result is "default set, minus drop, plus add". With `drop: ["ALL"]` the base is empty and only `add` remains. Capabilities exist **only at container level**. The next lines are the mistake the entry warns about:

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
$ k apply -f e1.yaml        # capabilities placed under spec.securityContext
Error from server (BadRequest): error when creating "e1.yaml": Pod in version "v1" cannot be handled as a Pod: strict decoding error: unknown field "spec.securityContext.capabilities"
```

**What `drop: ALL` does to a root process, and to a non-root process.** For a root container, `drop: ["ALL"]` makes the bounding and effective sets empty. For a non-root container, `CapEff` is already empty after `execve` because non-root processes do not get capabilities from the bounding set by themselves (see `man capabilities`). What does the bounding set do then? It only limits the future. This is why `add: ["NET_BIND_SERVICE"]` does **not** let a non-root process bind port 80. We measured it:

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
# Pod "hard": runAsUser 1000, drop ALL, add NET_BIND_SERVICE, allowPrivilegeEscalation false
$ k -n lab-t317 exec hard -- grep -E 'CapEff|CapBnd' /proc/1/status
CapEff:	0000000000000000
CapBnd:	0000000000000400
```

`CapBnd` has bit `0x400` (the capability is *allowed to exist*), but `CapEff` is zero, so the process **cannot use it**. A non-root process also needs the capability in its ambient set or in a file capability on the binary (`setcap`); Kubernetes sets neither, and `allowPrivilegeEscalation: false` blocks file capabilities. So for a non-root app the right fix to "cannot bind port 80" is one of these: listen on a port above 1023, or set the safe sysctl `net.ipv4.ip_unprivileged_port_start`. `add: ["NET_BIND_SERVICE"]` is useful when the process is root. PSA `restricted` allows exactly that one `add`, which is why it is in the entry's YAML. We will test all four combinations in section 5.

**Dangerous capabilities.**

| Capability | What it allows | Why dangerous |
|---|---|---|
| `SYS_ADMIN` | mount filesystems, change namespaces, many kernel admin calls | Called "the new root". It makes `allowPrivilegeEscalation` always true and enables many container escapes. |
| `NET_ADMIN` | configure interfaces, routes, firewall rules, sniff/spoof | Can reroute or sniff traffic of the Pod's network namespace; with `hostNetwork` that namespace is the node's. |
| `NET_RAW` | open raw sockets, craft packets | It is in the default 14. Dropping it stops ARP/ICMP spoofing from a compromised Pod. |
| `SYS_PTRACE` | attach to other processes | With `hostPID` it reads other containers' memory. |
| `SYS_MODULE` | load kernel modules | Direct kernel code execution on the host. |
| `DAC_OVERRIDE` | ignore file permission checks | It is in the default set; dropping it makes the file mode bits count even for root. |

Demonstration that `NET_ADMIN` is a real extra power (busybox creates a dummy network interface). It uses the Pod `plain` from section 5 step 1 (no `securityContext`) and this Pod `netadmin`, which differs from it only by the added capability:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: netadmin
  namespace: lab-t317
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
    securityContext:
      capabilities:
        add: ["NET_ADMIN"]     # default 14 plus NET_ADMIN
```

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
$ k -n lab-t317 exec plain -- ip link add d0 type dummy          # default 14 capabilities
ip: RTNETLINK answers: Operation not permitted
command terminated with exit code 2
$ k -n lab-t317 exec netadmin -- ip link add d0 type dummy && echo netadmin-created   # capabilities.add: ["NET_ADMIN"]
netadmin-created
$ k -n lab-t317 exec netadmin -- grep CapEff /proc/1/status
CapEff:	00000000a80435fb
```

`a80435fb` is the default `a80425fb` with bit 12 (`NET_ADMIN`) added. The second `ip link add` printed no error, so the interface was created.

### 2.6 seccomp: RuntimeDefault, Unconfined, Localhost

**The problem.** A process asks the kernel for services through about 400 system calls ("syscalls"). Most apps use fewer than 100. Every unused syscall is attack surface for kernel bugs. **seccomp** (secure computing mode) is a kernel filter that lets you block or fail chosen syscalls for a process.

| `seccompProfile.type` | Meaning | Extra field | Observed `Seccomp:` line in `/proc/1/status` |
|---|---|---|---|
| `RuntimeDefault` | The container runtime's default profile (blocks a few dozen risky syscalls). The right choice for almost all apps, and what PSA `restricted` requires (or `Localhost`). | none | `Seccomp: 2`, `Seccomp_filters: 1` |
| `Unconfined` | No filter. | none | `Seccomp: 0`, `Seccomp_filters: 0` |
| `Localhost` | A JSON profile file on the node, path relative to `<kubelet root>/seccomp` (default `/var/lib/kubelet/seccomp`). | `localhostProfile` is **required** | `Seccomp: 2` (a filter is on) |

`Seccomp: 0` means disabled, `1` strict mode, `2` filter mode. Pods that set nothing were `Seccomp: 0` on this kind cluster (captured in section 5), so setting `RuntimeDefault` is a real change.

Examples, each with the way to observe:

```yaml
securityContext:
  seccompProfile:
    type: RuntimeDefault        # observe: grep Seccomp /proc/1/status  -> Seccomp: 2
```

```yaml
securityContext:
  seccompProfile:
    type: Unconfined            # observe: Seccomp: 0
```

```yaml
securityContext:
  seccompProfile:
    type: Localhost
    localhostProfile: profiles/nomkdir.json    # file /var/lib/kubelet/seccomp/profiles/nomkdir.json on the node
```

To test `Localhost`, we created a profile on both worker nodes (a kind node is a Docker container, so `docker cp` works; on a real node you copy the file with `scp` as root):

```json
{
  "defaultAction": "SCMP_ACT_ALLOW",
  "syscalls": [
    { "names": ["mkdir", "mkdirat"], "action": "SCMP_ACT_ERRNO" }
  ]
}
```

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
$ k -n lab-t317 exec sc-local -- mkdir /tmp/d
mkdir: can't create directory '/tmp/d': Operation not permitted
$ k -n lab-t317 exec sc-local -- grep Seccomp /proc/1/status
Seccomp:	2
Seccomp_filters:	1
$ k -n lab-t317 exec plain -- mkdir /tmp/d && echo plain-mkdir-ok
plain-mkdir-ok
```

If the file is missing on the node the container is not created:

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
$ k -n lab-t317 get pod sc-local
NAME       READY   STATUS                 RESTARTS   AGE
sc-local   0/1     CreateContainerError   0          12s
Warning  Failed  kubelet  Error: failed to create containerd container: cannot load seccomp profile "/var/lib/kubelet/seccomp/profiles/missing.json": open /var/lib/kubelet/seccomp/profiles/missing.json: n...
```

(The message was cut at `n...` in the capture; it ends with the operating-system "no such file" text.) The diagnosis path is: `k get pod`, `k describe pod` (events), then read the path in the message and check it on the node.

### 2.7 AppArmor, SELinux and procMount (awareness)

**AppArmor** is a Linux Security Module (LSM) that confines a program by a profile that lists the files, network and capabilities it may use. The field `appArmorProfile` is GA since v1.31 and replaces the old `container.apparmor.security.beta.kubernetes.io/<name>` annotation. It exists at Pod level and container level:

```yaml
securityContext:
  appArmorProfile:
    type: RuntimeDefault        # or Unconfined, or Localhost
    # localhostProfile: k8s-deny-write   # required if and only if type is Localhost; the profile must be loaded on the node
```

| `type` | Meaning |
|---|---|
| `RuntimeDefault` | The runtime's default AppArmor profile. |
| `Unconfined` | No AppArmor enforcement. |
| `Localhost` | A profile already loaded on the node; `localhostProfile` names it. |

**Behaviour on kind, captured.** AppArmor is a kernel feature; kind nodes are containers that use the host's kernel. On the OrbStack host used here, the kernel had no AppArmor, so a Pod that asks for it is not started (even `RuntimeDefault`):

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
# host kernel without AppArmor
$ k -n lab-t317 get pods aa-rd aa-local
NAME       READY   STATUS     RESTARTS   AGE
aa-rd      0/1     AppArmor   0          12s
aa-local   0/1     AppArmor   0          12s
$ k -n lab-t317 describe pod aa-rd | grep AppArmor
  Warning  AppArmor   12s   kubelet            Cannot enforce AppArmor: AppArmor is not enabled on the host
```

So in this environment the field is accepted by the API, and the failure happens at the kubelet, with Pod status `AppArmor`. A `Localhost` profile that is not loaded on the node fails the same way.

**Behaviour on a host with AppArmor, and how to observe it.** On a node whose kernel has AppArmor enabled (for example common Ubuntu hosts), `RuntimeDefault` works. The profile that confines PID 1 of the container is shown in `/proc/1/attr/current`. Manifest (Pod `aa-ok`):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: aa-ok
  namespace: lab-t317
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
    securityContext:
      appArmorProfile:
        type: RuntimeDefault        # swap for Unconfined to compare
```

```bash
k -n lab-t317 exec aa-ok -- cat /proc/1/attr/current
```

```text
EXPECTED OUTPUT (not captured)
cri-containerd.apparmor.d (enforce)
```

With `type: Unconfined` the same command should print `unconfined`. For `Localhost`, the profile named in `localhostProfile` is printed with `(enforce)`; the profile must first be loaded on the node (`apparmor_parser -r <file>` as root). None of this could be captured here because the Docker host kernel has no AppArmor (section 11).

**SELinux** is another LSM, used on Red Hat style hosts. `seLinuxOptions` has `user`, `role`, `type` and `level` fields (MCS label). In practice you set `level` so two Pods cannot read each other's files, or you leave it to the runtime. `seLinuxChangePolicy` (Pod level) controls whether the kubelet relabels a volume recursively or mounts it with the right label. You will not be able to test either on Ubuntu or kind nodes. For the exam: know the field names and that it is a node feature.

**procMount** controls how much of `/proc` the container sees: `Default` masks some paths, `Unmasked` shows them all. Unmasked is for nested-container tools and is only allowed with `hostUsers: false` (captured above). Leave it alone.

### 2.8 readOnlyRootFilesystem and an emptyDir for /tmp

**The problem.** A common attack step is: break in, then download or write a tool, or edit a config file. If the root filesystem is read-only, the write fails. `readOnlyRootFilesystem: true` makes the container's root filesystem layer read-only.

**What it breaks.** Many programs write to `/tmp`, `/var/run`, `/var/cache` or `/run`. These writes now fail. The fix is **not** to turn the setting off. You mount a writable **`emptyDir`** volume at exactly the directories the app writes (see [T3.07](../part3-ckad/T3.07-utilize-persistent-and-ephemeral-volumes.md)). An `emptyDir` is an empty directory created when the Pod starts and deleted with the Pod; it is writable.

Captured with the unprivileged nginx image (`nginxinc/nginx-unprivileged:1.27`, UID 101, listens on 8080):

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
# readOnlyRootFilesystem: true and no volumes
$ k -n lab-t317 get pod n-ro
NAME   READY   STATUS   RESTARTS      AGE
n-ro   0/1     Error    2 (15s ago)   25s
$ k -n lab-t317 logs n-ro | tail -3
/docker-entrypoint.sh: Configuration complete; ready for start up
2026/10/28 05:56:43 [emerg] 1#1: mkdir() "/tmp/proxy_temp" failed (30: Read-only file system)
nginx: [emerg] mkdir() "/tmp/proxy_temp" failed (30: Read-only file system)
```

The log names the exact path (`/tmp/proxy_temp`) to put the `emptyDir` on. After adding `volumeMounts: - {name: tmp, mountPath: /tmp}` with `volumes: - {name: tmp, emptyDir: {}}`:

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
$ k -n lab-t317 exec web -- touch /x
touch: cannot touch '/x': Read-only file system
command terminated with exit code 1
$ k -n lab-t317 exec web -- touch /tmp/x && echo tmp-ok
tmp-ok
$ k -n lab-t317 exec web -- curl -s -o /dev/null -w '%{http_code}\n' localhost:8080
200
```

Also seen in the first log: `10-listen-on-ipv6-by-default.sh: info: can not modify /etc/nginx/conf.d/default.conf (read-only file system?)`. It is an `info` line. The entrypoint script tries to edit its config and carries on. Do not chase info lines when the main process runs.

### 2.9 hostNetwork, hostPID, hostIPC and hostPath: the risk

These are **Pod spec** fields, not `securityContext` fields, but they decide how isolated the container is, so they belong in the same review.

| Field | Where | What it shares with the node | Why it is risky |
|---|---|---|---|
| `hostNetwork: true` | `spec` | the node's network namespace | The Pod sees node interfaces and can reach node-local services (kubelet, metadata endpoints) that bypass NetworkPolicy. |
| `hostPID: true` | `spec` | the node's process list | The Pod sees and can signal every process, and read their `/proc`. |
| `hostIPC: true` | `spec` | the node's SysV IPC and POSIX shared memory | Reads other processes' shared memory. |
| `hostPath` volume | `spec.volumes[]` | a directory (or file or socket) of the node's filesystem | Reading `/` reads the node. Writing to the kubelet or runtime directories gives control of the node. |
| `privileged: true` | container | all capabilities and all devices | The container is almost root on the node. |

**One runnable example per variant.** Pod `hostns` shares three namespaces (no `privileged`, no `hostPath`):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hostns
  namespace: lab-t317
spec:
  hostNetwork: true      # node network namespace
  hostPID: true          # node process list
  hostIPC: true          # node IPC namespace
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
```

How to observe each one:

| Field | Command | What to look for |
|---|---|---|
| `hostNetwork` | `k -n lab-t317 get pod hostns -o jsonpath='{.status.podIP} {.status.hostIP}{"\n"}'` and `k -n lab-t317 exec hostns -- hostname` | the two IPs are equal (a normal Pod gets its own Pod IP) and the hostname is the node's name |
| `hostPID` | `k -n lab-t317 exec hostns -- ps` | the list shows node processes such as `kubelet` and `containerd`, not just `sleep` |
| `hostIPC` | `k -n lab-t317 get pod hostns -o jsonpath='{.spec.hostIPC}'` | prints `true`. The effect (the node's shared memory segments are visible) is not easy to show with busybox, so this lesson checks the field |
| `hostPath` | next Pod, `hostpeek` | the node's files appear under `/host` |

```text
EXPECTED OUTPUT (not captured)
$ k -n lab-t317 get pod hostns -o jsonpath='{.status.podIP} {.status.hostIP}{"\n"}'
172.18.0.3 172.18.0.3
$ k -n lab-t317 exec hostns -- hostname
k-t317-worker
```

(The addresses are examples. The two must match each other, whatever your node IP is.)

Pod `hostpeek` has `hostPID`, `privileged` and a read-only `hostPath: /`:

```yaml

  name: hostpeek
  namespace: lab-t317

  containers:
  - name: app
    image: busybox:1.36

      privileged: true            # all capabilities, all devices
```

### 2.10 User namespaces: hostUsers: false (GA v1.36)

**The problem.** Normally UID 0 in the container is UID 0 on the node. If an attacker breaks out of the container, they arrive as root. A **user namespace** maps IDs: UID 0 inside the Pod is mapped to a high, unprivileged UID on the node. The container still thinks it is root (so apps that insist on root keep working), but the kernel treats it as a normal user on the host. Capabilities held inside the user namespace only apply to resources owned by that namespace, not to the host. See [T1.10](../part1-linux/T1.10-linux-namespaces-and-cgroups-v2.md) for the namespace idea.

**Field.** `spec.hostUsers` (a Pod spec field, not in `securityContext`). Default `true` (share the node's user namespace). Set `false` for a new user namespace per Pod:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: userns
  namespace: lab-t317
spec:
  hostUsers: false          # new user namespace for this Pod
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
```

**Verify by reading the UID map** (`/proc/self/uid_map`: columns are "first ID inside", "first ID outside (on the node)", "how many IDs"):

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
$ k -n lab-t317 exec userns -- id
uid=0(root) gid=0(root) groups=0(root),10(wheel)
$ k -n lab-t317 exec userns -- cat /proc/self/uid_map
         0 2736717824      65536
$ k -n lab-t317 exec plain -- cat /proc/self/uid_map          # a normal Pod
         0          0 4294967295
```

Inside the Pod the user is still `root`, but UID 0 maps to node UID 2736717824 (a range of 65536 IDs). A normal Pod maps 1:1 (`0 0 4294967295`). Note that `CapEff` inside was still the default `a80425fb`: the capabilities are the same, their reach is smaller.

**Requirements.** It worked on this kind setup, with no extra feature-gate flags in the kind config, on kernel `7.2.12-orbstack`, containerd 2.3.4 and runc 1.4.3. User namespaces need kernel and runtime support (including ID-mapped mounts for volumes), so a different host can fail. The "what is required" list is on [the user-namespaces page](https://kubernetes.io/docs/concepts/workloads/pods/user-namespaces/); I did not re-check each requirement on other kernels (section 11). Do not combine `hostUsers: false` with other host sharing fields without reading that page's restrictions.

### 2.11 Verifying inside the container

Every setting above can be proven from inside the container. These are the commands to use after `k exec`:

| You want to prove | Command | Good result |
|---|---|---|
| user and groups | `k exec app -- id` | `uid=1000 gid=3000 groups=2000,3000` |
| capabilities | `k exec app -- grep Cap /proc/1/status` | `CapBnd` has only what you allowed; decode on a VM with `capsh --decode=<hex>` |
| no privilege escalation | `k exec app -- grep NoNewPrivs /proc/1/status` | `NoNewPrivs: 1` |
| seccomp filter on | `k exec app -- grep Seccomp /proc/1/status` | `Seccomp: 2` |
| read-only root filesystem | `k exec app -- touch /x` | `touch: ... Read-only file system` |
| volume group (`fsGroup`) | `k exec app -- ls -ld /data` or `stat -c '%u:%g %a' /data` | group = your `fsGroup`, mode shows `s` (setgid) |
| AppArmor profile | `k exec app -- cat /proc/1/attr/current` | `cri-containerd.apparmor.d (enforce)` for `RuntimeDefault`, `unconfined` for `Unconfined` (EXPECTED, needs an AppArmor host, section 2.7) |
| user namespace | `k exec app -- cat /proc/self/uid_map` | second column is not `0` |
| field names and levels | `k explain pod.spec.containers.securityContext` | list from section 2.3 |

PID 1 (`/proc/1`) is the container's main process, so its status shows the limits that apply to the app. A process you start with `k exec` is a new process in the same container, and it gets the same user and the same capability limits.

### 2.12 Pod Security Standards mapping

PSA checks Pods against three **Pod Security Standards** (see [T3.16](../part3-ckad/T3.16-understand-authentication-authorization-and-admission-control.md) for how to label a namespace). The levels are `privileged` (no limits), `baseline` (blocks known privilege escalations) and `restricted` (current hardening best practice).

Mapping from the fields in this lesson. Rows marked "captured" come from real messages (below). The other cells were read from the [Pod Security Standards page](https://kubernetes.io/docs/concepts/security/pod-security-standards/) while fixing this lesson (the Capabilities, AppArmor, SELinux, Seccomp and Sysctls baseline rows and the restricted rows for volume types, escalation, non-root, seccomp and capabilities). `restricted` includes everything from `baseline`.

| Field | `baseline` | `restricted` |
|---|---|---|
| `privileged: true` | forbidden (captured) | forbidden |
| `hostNetwork`, `hostPID`, `hostIPC` | forbidden (captured) | forbidden |
| `hostPath` volume | forbidden (captured) | forbidden; `restricted` also limits volumes to `configMap`, `csi`, `downwardAPI`, `emptyDir`, `ephemeral`, `persistentVolumeClaim`, `projected` and `secret` (captured message: "restricted volume types") |
| `capabilities.add` | only `AUDIT_WRITE`, `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `FSETID`, `KILL`, `MKNOD`, `NET_BIND_SERVICE`, `SETFCAP`, `SETGID`, `SETPCAP`, `SETUID`, `SYS_CHROOT` | only `NET_BIND_SERVICE` (captured for `NET_ADMIN`) |
| `capabilities.drop` | not required | must include `ALL` (captured) |
| `allowPrivilegeEscalation` | not required | must be `false` (captured) |
| `runAsNonRoot` | not required | must be `true` at Pod or every container (captured); `runAsUser` must not be 0 |
| `seccompProfile.type` | `Unconfined` forbidden; unset is allowed | `RuntimeDefault` or `Localhost`; unset and `Unconfined` are both rejected (captured) |
| `appArmorProfile.type` | unset, `RuntimeDefault` or `Localhost` only | same as baseline |
| `seLinuxOptions` | `type` must be unset or one of `container_t`, `container_init_t`, `container_kvm_t`, `container_engine_t`; `user` and `role` must be unset | same as baseline |
| `sysctls` | only the safe subset (for example `net.ipv4.ip_local_port_range`, `net.ipv4.ip_unprivileged_port_start`; the page has the full list) | same as baseline |
| `readOnlyRootFilesystem` | not required | **not required** (the Pod passes without it) |

The last row is a common trap: read-only root is good practice but PSA does not demand it. Captured messages:


### 2.13 Related but different

- **`securityContext` vs RBAC.** RBAC controls what a *user or ServiceAccount* may do against the Kubernetes API. `securityContext` controls what the *process in the container* may do against the *kernel*. See [T3.15](../part3-ckad/T3.15-understand-serviceaccounts.md).
- **`securityContext` vs PSA.** `securityContext` is the setting; PSA is the gate that checks it. A gate cannot fix your Pod. Setting fields does not require PSA to be on.
- **`securityContext` vs NetworkPolicy.** NetworkPolicy limits network traffic between Pods ([T3.14](../part3-ckad/T3.14-demonstrate-basic-understanding-of-networkpolicies.md)); `NET_ADMIN` and `hostNetwork` can weaken it.
- **`runAsUser` vs `runAsNonRoot`.** `runAsUser` chooses a UID. `runAsNonRoot` only checks that the UID is not 0. Use both: the first makes it work, the second makes a later mistake fail loudly.
- **`privileged: true` vs `capabilities.add: ["ALL"]`.** Privileged also exposes devices and removes seccomp/AppArmor filtering. They are not the same, and neither is acceptable under `restricted`.
- **Image `USER` vs `runAsUser`.** The image `USER` is the default. `runAsUser` overrides it, but files inside the image still have the image's owners. Overriding to a UID that cannot read the app's files can break the app.

## 3. How it works (diagram)

The entry asks for an ASCII table: field, level, effect, how to verify. Fields marked `(spec)` live directly under `spec`, not in a `securityContext`.

```text
FIELD                      LEVEL            EFFECT                                          HOW TO VERIFY
-------------------------  ---------------  ----------------------------------------------  ------------------------------------------------
runAsUser                  Pod, container   UID of first process                            k exec p -- id                -> uid=...
runAsGroup                 Pod, container   primary GID                                     k exec p -- id                -> gid=...
runAsNonRoot               Pod, container   kubelet REFUSES to start a root container       CreateContainerConfigError in k describe pod
fsGroup                    Pod              group of volume files + extra process group     k exec p -- ls -ld /data      -> group, setgid "s"
fsGroupChangePolicy        Pod              when the group is re-applied (Always|OnRootMismatch)   (persistent volumes only; none for emptyDir)
supplementalGroups         Pod              extra GIDs on the process                       k exec p -- id                -> groups=...
supplementalGroupsPolicy   Pod              Merge|Strict handling of image groups           k exec p -- id (not tested here)
sysctls                    Pod              safe kernel params per Pod                      k exec p -- cat /proc/sys/...
seccompProfile             Pod, container   syscall filter RuntimeDefault|Unconfined|Localhost   grep Seccomp /proc/1/status  -> 2 or 0
appArmorProfile            Pod, container   AppArmor profile (GA 1.31)                      cat /proc/1/attr/current ; Pod status "AppArmor" if the node lacks it
seLinuxOptions             Pod, container   SELinux label (node must use SELinux)           ps -Z / ls -Z on the node
allowPrivilegeEscalation   container        false sets no_new_privs                         grep NoNewPrivs /proc/1/status -> 1
readOnlyRootFilesystem     container        root FS read-only                               k exec p -- touch /x          -> Read-only file system
privileged                 container        all caps + all devices                          grep CapEff /proc/1/status    -> 000001ffffffffff
capabilities.drop / .add   container ONLY   edits the capability set                        grep Cap /proc/1/status ; capsh --decode=<hex>
procMount                  container        Default|Unmasked /proc (needs hostUsers:false)  API error if hostUsers is true
hostUsers (spec)           Pod spec         false = separate user namespace                 k exec p -- cat /proc/self/uid_map
hostNetwork/PID/IPC (spec) Pod spec         share node namespaces                           k get pod p -o yaml | grep host
hostPath volume (spec)     Pod spec         mounts a node directory                         k get pod p -o yaml | grep -A2 hostPath
```

**Walkthrough.**

1. Read each row from left to right: the field name, where you may write it, what the kernel does, and one command that proves it. Two rows say "ONLY" or "needs": `capabilities` is container-level only, and `procMount` needs `hostUsers: false`.
2. Row order is the order of the lesson: user and group IDs, then volumes, then kernel filters (seccomp, AppArmor, SELinux), then privilege (escalation, read-only root, privileged, capabilities), then sharing with the node.
3. When a field appears at both levels, the container-level value wins for that container (section 2.4).
4. The two checks done by the kubelet at container creation are `runAsNonRoot` and the seccomp/AppArmor profile load. Their failures show as `CreateContainerConfigError`, `CreateContainerError` or status `AppArmor`, and the reason is in `k describe pod` events.
5. Everything else is set by runc before your process starts, so the proof is always inside the container.

## 4. Commands and YAML you must produce fast

### 4.1 Imperative shortcuts

`kubectl run` has no flags for `securityContext`. The fast pattern is: generate the YAML, then add the block by hand.

```bash
k run app --image=busybox:1.36 $do -- sleep 3600 > pod.yaml      # skeleton in 3 s; edit, then k apply -f pod.yaml
k create deployment web --image=nginxinc/nginx-unprivileged:1.27 --port=8080 $do > web.yaml   # Deployment skeleton
k explain pod.spec.containers.securityContext                    # list the fields and their types
k explain pod.spec.containers.securityContext.capabilities       # drop / add
k exec app -- id                                                 # prove the user
k exec app -- grep Cap /proc/1/status                            # prove the capabilities
k exec app -- touch /x                                           # prove the root filesystem is read-only
k replace --force -f pod.yaml                                    # a Pod's securityContext cannot be edited in place: delete and recreate
k label --dry-run=server --overwrite ns <ns> pod-security.kubernetes.io/enforce=restricted   # what would break?
```

Why `k replace --force`: almost all Pod spec fields are immutable. `k edit pod` on a `securityContext` field is refused. `--force` deletes and recreates the Pod from the file. For a Deployment, edit the template and the rollout replaces Pods for you.

Open the first docs page in section 8; its example YAML can be copied and shortened. Typing from memory is faster if you remember the block below.

### 4.2 The declarative YAML

The YAML from the entry, complete and applyable. Every field is explained in a comment.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hard
  namespace: lab-t317
spec:
  securityContext:                  # POD level: applies to every container and to the volumes
    runAsUser: 1000                 # first process runs as UID 1000 (overrides image USER)
    runAsGroup: 3000                # primary GID 3000
    fsGroup: 2000                   # volume files get group 2000; the process gets group 2000 too
    runAsNonRoot: true              # kubelet refuses to start the container if it would be UID 0
    seccompProfile:
      type: RuntimeDefault          # runtime's default syscall filter
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
    securityContext:                # CONTAINER level: this container only, wins over the Pod level
      allowPrivilegeEscalation: false   # no_new_privs: setuid and file capabilities cannot add rights
      readOnlyRootFilesystem: true      # root FS is read-only; writes must go to mounted volumes
      capabilities:                 # container level ONLY (invalid at Pod level)
        drop: ["ALL"]               # start from an empty capability set
        add: ["NET_BIND_SERVICE"]   # the only capability PSA restricted lets you add
    volumeMounts:
    - name: data
      mountPath: /data              # writable directory, group-owned by fsGroup
  volumes:
  - name: data
    emptyDir: {}                    # scratch volume, removed with the Pod
```

Memory aid for the order you type it: **who** (runAsUser, runAsGroup, runAsNonRoot, fsGroup), **filter** (seccomp), then in the container **no escalation, read-only, drop ALL**. The only thing to remember to add afterwards is an `emptyDir` for each writable path.

## 6. Common mistakes and how to fix them

Each row is followed by the diagnostic path in the order to run the commands. Use the same path every time: `k get pod` (status), `k describe pod` (events), `k logs` (app output), `k get pod -o yaml` (what is actually set).

| Symptom | What you will see (exact error/event text) | Cause | Fix (command) |
|---|---|---|---|
| Pod stuck, never runs | status `CreateContainerConfigError`; event: `Error: container has runAsNonRoot and image will run as root (pod: "nr_lab-t317(<pod uid>)", container: nr)` | `runAsNonRoot: true` but the image's `USER` is root (or unset) and you set no `runAsUser` | add `runAsUser: <non-zero UID>`, or use an image that runs as non-root. `k replace --force -f pod.yaml` |
| Same status with `runAsUser: 0` | `container's runAsUser breaks non-root policy (pod: "r0_lab-t317(<uid>)", container: app)` | `runAsNonRoot: true` and `runAsUser: 0` contradict each other | set `runAsUser` to a non-zero value |
| App crashes after `readOnlyRootFilesystem: true` | status `Error`/`CrashLoopBackOff`; `k logs`: `[emerg] 1#1: mkdir() "/tmp/proxy_temp" failed (30: Read-only file system)` | the app writes under `/tmp` | add `volumeMounts` + `emptyDir` at that path |
| `capabilities` at Pod level | `Error from server (BadRequest): ... strict decoding error: unknown field "spec.securityContext.capabilities"` | capabilities exist only in the container `securityContext` | move the block under `spec.containers[].securityContext` |
| Cannot bind port 80 after `drop: ["ALL"]` | `nc: bind: Permission denied` (nginx prints its own text, not captured; look for `Permission denied` and `:80` in `k logs`) | on nodes where `ip_unprivileged_port_start` is 1024, port 80 needs `CAP_NET_BIND_SERVICE` in the effective set, and a non-root process has none | listen on 8080 (preferred), or run as root with `add: ["NET_BIND_SERVICE"]`, or set the safe sysctl `net.ipv4.ip_unprivileged_port_start` |

**Failure 1 in depth: `container has runAsNonRoot and image will run as root`.**

1. `k get pod nr`. `STATUS` is `CreateContainerConfigError`. The Pod is scheduled and the image is pulled; the container was not created.
2. `k describe pod nr`, read the events at the bottom. This is the real output:

```text
REAL OUTPUT (kind v0.33.0, v1.37.0)
Events:
  Type     Reason     Age               From               Message
  ----     ------     ----              ----               -------
  Normal   Scheduled  36s               default-scheduler  Successfully assigned lab-t317/nr to k-t317-worker2
  Normal   Pulling    35s               kubelet            spec.containers{nr}: Pulling image "nginx:1.27"
  Normal   Pulled     14s               kubelet            spec.containers{nr}: Successfully pulled image "nginx:1.27" in 21.714s ...
  Warning  Failed     1s (x3 over 14s)  kubelet            spec.containers{nr}: Error: container has runAsNonRoot and image will run as root (pod: "nr_lab-t317(3474712c-cfd8-4fa0-8bf9-67031f7f328a)", container: nr)
```

3. The same text is in `k get pod nr -o jsonpath='{.status.containerStatuses[0].state.waiting.message}'`.
4. Find out which user the image uses. One way that works in any cluster: `k run idcheck --image=nginx:1.27 --restart=Never --command -- id`, then `k logs idcheck`. It should print `uid=0(root)`. EXPECTED OUTPUT (not captured). Delete the helper Pod afterwards.
5. Fix: add a non-zero numeric `runAsUser`, or switch to an image built for non-root. Be careful: simply adding `runAsUser: 101` to the official `nginx:1.27` image gets past this check but the app still fails (it wants port 80 and root-owned cache directories). I did not run that variant. That is why section 7 uses the unprivileged image.
6. Because the kubelet can only compare numbers, an image whose `USER` is a *name* (not a number) cannot be proven non-root, so the kubelet refuses it too. The message shape, written from the kubelet source and not captured, is `Error: container has runAsNonRoot and image has non-numeric user (<name>), cannot verify user is non-root (pod: "<pod>_<ns>(<uid>)", container: <container>)`; `<name>` and the other parts are placeholders. If you hit that, set a numeric `runAsUser`. Section 11 lists it as unconfirmed.

**Failure 2 in depth: crash after `readOnlyRootFilesystem`.**

1. `k get pod n-ro` shows `Error`, then `CrashLoopBackOff` after a few restarts.
2. `k logs n-ro` (add `--previous` if the container has restarted) shows the last lines. Read the *last* error, not the first `info` line. Here: `mkdir() "/tmp/proxy_temp" failed (30: Read-only file system)`. Error 30 is `EROFS`, read-only file system.
3. The path in the message is your `mountPath`. Add the `emptyDir` there. If the app writes to several directories (for example `/var/run` and `/var/cache`), each needs its own mount. List them by repeating: run, read the log, add a mount.
4. `k exec` into a running replica to prove the fix: `touch /tmp/x` works, `touch /x` does not.

**Failure 3 in depth: unknown field at apply time.** `strict decoding error` means the API server refused a field name that does not exist at that path. Confirm with `k explain pod.spec.securityContext` (no `capabilities` in the list). The fix is always to move the field to the level where `k explain` lists it.

**Failure 4 in depth: port 80.**

1. Is the process failing to bind? `k logs` shows `Permission denied` and the port.
2. Which user? `k exec p -- id`. If UID is not 0, the capability route does not help (section 2.5). Pick a port above 1023 and update `containerPort`, probes and the Service `targetPort`.
3. If it must be root: `k exec p -- grep Cap /proc/1/status`. `CapEff` must contain `0x400`; decode with `capsh` on a VM, or compare with the value `0x0000000000000400`.
4. Node default: `k exec p -- cat /proc/sys/net/ipv4/ip_unprivileged_port_start`. If it prints `0` (as on kind here), port 80 never needed the capability, so a "bind" error has another cause (for example the port is already used).

**More failures seen while preparing this lesson:**

| Symptom | What you will see | Cause | Fix |
|---|---|---|---|
| Deployment shows `0/2` and no Pods | `k get deploy` `0/2`, `k describe rs` event: `Error creating: pods "web-..." is forbidden: violates PodSecurity "restricted:latest": allowPrivilegeEscalation != false (container "web" must set ...)` | The namespace enforces `restricted` and the Pod template lacks the four fields | set the four fields in the template; read the ReplicaSet events, not the Deployment |
| Pod rejected on `k apply` | `Error from server (Forbidden): ... violates PodSecurity "restricted:latest": ...` | same, for a bare Pod | fix the fields named in the message |
| `SysctlForbidden` | status `SysctlForbidden`, `forbidden sysctl: "kernel.msgmax" not allowlisted` | unsafe sysctl | use a safe sysctl or remove it |
| `privileged` + `allowPrivilegeEscalation: false` | `cannot set allowPrivilegeEscalation to false and privileged to true` | the two contradict | remove `privileged` |
| `procMount: Unmasked` | `hostUsers must be false to use Unmasked` | needs a user namespace | leave `procMount` at `Default` |
| Status `AppArmor` | event `Cannot enforce AppArmor: AppArmor is not enabled on the host` | node kernel has no AppArmor | remove the field or use an AppArmor-enabled node |
| `CreateContainerError` with `cannot load seccomp profile` | see section 2.6 | `Localhost` file missing on the node | copy the JSON file to the node's seccomp directory |

**Task.** In namespace `lab-t317c` the Pod `agent` runs a heartbeat loop that writes the time to `/work/beat` every 2 seconds. Harden it and keep it working. <details><summary>Hints</summary>

</details>

<details><summary>Solution</summary>

Diagnose (before editing, read what the Pod actually has):

```bash

```

Each of those lines is something to remove: `hostNetwork`, `hostPID`, `hostIPC`, `privileged`, and the `hostPath` volume. The `hostPath: /` mount gives the Pod a view of the node's whole filesystem and the app does not use `/host` at all, so it can simply go. The app writes only to `/work`, which today is just a directory in the container's own writable layer. With a read-only root, `/work` needs its own `emptyDir`.

Replace the content of `~/lab/t317/agent.yaml` with:

```yaml

kind: Pod
metadata:
  name: agent
  namespace: lab-t317c
spec:
  securityContext:
    runAsUser: 10001                # not root
    runAsGroup: 10001
    runAsNonRoot: true              # fail loudly if that ever changes
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: agent
    image: busybox:1.36
    command: ["sh", "-c", "mkdir -p /work; while true; do date > /work/beat; sleep 2; done"]

      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
```


`mkdir -p /work` still works under a read-only root, because the directory already exists as the mount point (and `mkdir -p` on an existing directory succeeds). If you only set `readOnlyRootFilesystem: true` and forget the `emptyDir`, `date > /work/beat` fails and the app stops updating the file (the Pod may crash or sit idle depending on the shell; read `k logs agent` to see). Why `emptyDir` is writable for UID 10001: an `emptyDir` is created world-writable, so no `fsGroup` is needed here.

## 9. Quick review

1. What are the two places a `securityContext` can be written, and which one wins for the same field?
<details><summary>Answer</summary>Pod level (`spec.securityContext`) and container level (`spec.containers[].securityContext`). The container value wins for that container, per field. We measured it: Pod `runAsUser: 1000`, container override `2000` gave `uid=2000 gid=3000`.</details>

2. Which command shows whether a field exists at Pod level or container level?
<details><summary>Answer</summary>`k explain pod.spec.securityContext` and `k explain pod.spec.containers.securityContext`. `capabilities` appears only in the second.</details>

3. Why does `runAsNonRoot: true` alone not make a root image work, and what status do you see?
<details><summary>Answer</summary>`runAsNonRoot` is a check, not a setting. The kubelet refuses a container whose user is 0. The Pod shows `CreateContainerConfigError` with `container has runAsNonRoot and image will run as root`. Fix by setting a non-zero numeric `runAsUser` or using a non-root image.</details>

4. Write the container `securityContext` that drops everything and adds back only binding low ports.
<details><summary>Answer</summary>`capabilities: {drop: ["ALL"], add: ["NET_BIND_SERVICE"]}` (container level only).</details>

5. A non-root container has `drop: ["ALL"]`, `add: ["NET_BIND_SERVICE"]` and still cannot bind port 80. Why, and what are two fixes?
<details><summary>Answer</summary>`CapEff` is zero for a non-root process, the capability is only in the bounding set (we saw `CapBnd 0x400`, `CapEff 0`). Fixes: listen on a port above 1023 (and map the Service `targetPort`), or set the safe sysctl `net.ipv4.ip_unprivileged_port_start`.</details>

6. How do you prove inside a Pod that the root filesystem is read-only, and that seccomp is on?
<details><summary>Answer</summary>`k exec p -- touch /x` gives `Read-only file system`. `k exec p -- grep Seccomp /proc/1/status` shows `Seccomp: 2` (and `Seccomp_filters: 1`). `0` means unconfined.</details>

7. The app crashes after `readOnlyRootFilesystem: true`. What do you do?
<details><summary>Answer</summary>Read `k logs` for the path it cannot write, then mount an `emptyDir` at that path (for example `/tmp`). Do not turn the setting off.</details>

8. What do `RuntimeDefault`, `Unconfined` and `Localhost` mean for `seccompProfile`, and what extra field does `Localhost` need?
<details><summary>Answer</summary>The runtime's default filter, no filter, and a JSON profile file on the node. `Localhost` requires `localhostProfile` with the path relative to `/var/lib/kubelet/seccomp`. A missing file gives `CreateContainerError`.</details>

9. Why are `NET_ADMIN` and `SYS_ADMIN` dangerous, and what does PSA `restricted` allow you to add?
<details><summary>Answer</summary>`NET_ADMIN` can reconfigure and sniff networking (the demo created an interface that a default Pod cannot); `SYS_ADMIN` is a catch-all root-like power (mounts, namespaces) and forces `allowPrivilegeEscalation` true. `restricted` allows adding only `NET_BIND_SERVICE` (and requires dropping ALL).</details>

10. What does `hostUsers: false` do, and how do you verify it?
<details><summary>Answer</summary>The Pod gets its own user namespace: UID 0 inside maps to an unprivileged UID on the node. Verify with `k exec p -- cat /proc/self/uid_map`: the second column is not `0` (we saw `0 2736717824 65536`, against `0 0 4294967295` for a normal Pod).</details>

11. Which of these are NOT required by PSA `restricted`: `readOnlyRootFilesystem`, `allowPrivilegeEscalation: false`, `runAsNonRoot: true`, seccomp `RuntimeDefault`, `drop: ["ALL"]`?
<details><summary>Answer</summary>`readOnlyRootFilesystem` is not required. The other four are (the PSA error message lists them). Check with `k label --dry-run=server --overwrite ns <ns> pod-security.kubernetes.io/enforce=restricted`.</details>

**Known limitation.** Most outputs in this lesson are real, captured on a 3-node kind cluster (v0.33.0, node image v1.37.0, kindnet CNI instead of Calico, on an OrbStack Docker host). Two facts the entry asked for depend on the host kernel, and only one kernel was available: user namespaces worked on it; AppArmor is not enabled on it. To meet those fully you need a second environment: the same kind cluster on a Linux host with AppArmor enabled, and the kubeadm VMs of Part 4 (or any Ubuntu node) for `capsh` on a VM. Calico was not installed because nothing here needs NetworkPolicy.
