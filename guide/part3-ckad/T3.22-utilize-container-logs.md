## 1. Why this matters

Logs are the first thing you read when an app misbehaves. A Pod that is `Running` but returns errors, a Pod in `CrashLoopBackOff`, a Job that "did nothing": the reason is almost always one line in a log. If you do not know the flags, you read the wrong container, you miss the crashed instance, or you save ten lines when the task wanted all of them.

Kubernetes keeps only what a container writes to **stdout** and **stderr**. An app that writes to a file inside its container has no logs as far as `kubectl logs` is concerned. And when the Pod is deleted, its logs go with it. Tasks in this area are practical: save the logs of one container, or of the previous instance of a crashing container, into a given file. The exam averages about 6 minutes per task (15-20 tasks in 2 hours; sources: [E2](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad), [E3](https://docs.linuxfoundation.org/tc-docs/certification/faq-cka-ckad-cks)), so you need the right flag on the first try.

## 2. Concepts

### 2.1 What a container log is

A **container log** is the text that the main process of a container writes to its standard output (**stdout**, file descriptor 1) and standard error (**stderr**, file descriptor 2). The container runtime (containerd on kind and kubeadm clusters) attaches to those two streams, adds a timestamp and a stream tag to each line, and appends the line to a file on the node.

**The problem this solves.** Every app can log to its own file in its own format, but then each one needs its own way to read it. Kubernetes picks one rule for everyone: write to stdout and stderr. Then one command (`kubectl logs`) works for every app, and the kubelet (the node agent) can rotate the files for you.

**What breaks without it.** An app that writes only to `/var/log/app.log` inside its container shows an empty `kubectl logs`. The file is also lost when the container restarts, because it lives in the container's writable layer. Section 2.12 shows the two fixes (reconfigure the app, or add a streaming sidecar).

Two facts you must remember:

- `kubectl logs` shows stdout and stderr **mixed together** in one stream. Their relative order is not guaranteed to be exact (in the worked example below, a stderr line appeared before the stdout line of the same loop round).
- Logs belong to the **container instance**, on one **node**. They are not stored in the API server and not in etcd.

### 2.2 `kubectl logs` and what happens under the hood

The basic form is `k logs POD`. It prints the whole current log of the container. If the Pod has one container you do not need a name.

**Under the hood.** `kubectl logs` is a client for one API call: `GET /api/v1/namespaces/<ns>/pods/<pod>/log`, with query parameters such as `container`, `follow`, `previous`, `tailLines`, `sinceSeconds`, `sinceTime`, `timestamps` and `limitBytes`. Each kubectl flag maps to one of them. The API server does not store logs. It looks up the node of the Pod and forwards the request to the **kubelet** on that node (the kubelet listens on port 10250). The kubelet opens the log file of that container on its own disk and streams it back through the API server to kubectl. So:

- A log request needs a working path API server to kubelet. If the node is down, you cannot read the logs of its Pods, even though the files are still on its disk.
- RBAC applies: you need the `get` verb on the `pods/log` subresource.

You can see the raw call with `k get --raw`. A call without a container name on a two-container Pod is rejected by the API server:

```bash
k get --raw "/api/v1/namespaces/lab-t322/pods/web/log"
```

REAL OUTPUT (kind v0.33.0, v1.37.0)

```text
Error from server (BadRequest): a container name must be specified for pod web, choose one of: [app helper]
```

This is the exact text from the first common mistake in the entry. Section 2.4 explains why `kubectl` itself usually does not show it.

### 2.3 The flags, one table

All flags below exist in `kubectl` v1.37.1 (checked with `kubectl logs --help`).

| Flag | What it does | Default | Notes and risky values |
|---|---|---|---|
| `-c NAME` / `--container NAME` | Choose the container | First container in `spec.containers` (or the one named by the `kubectl.kubernetes.io/default-container` annotation) | A name that does not exist: `error: container nope is not valid for pod web out of: app, helper` |
| `--all-containers` | Print every container of the Pod, init containers included | off | Lines of different containers are not labelled unless you add `--prefix` |
| `--prefix` | Put `[pod/<name>/<container>]` in front of each line | off | Needed to tell pods apart when you use a selector or `deploy/x --all-pods` |
| `-f` / `--follow` | Keep the stream open and print new lines | off | Blocks the terminal. Press Ctrl+C. Never combine with `> file` unless you want an open-ended capture |
| `--tail N` | Show only the last N lines | `-1` (all lines) for one Pod; **10** when you use a selector `-l` | `--tail=0` prints nothing (useful with `-f` to see only new lines). `--tail=-1` means all lines |
| `--since DURATION` | Only lines newer than a relative time such as `30s`, `10m`, `2h` | all | Cannot be combined with `--since-time` |
| `--since-time TIMESTAMP` | Only lines after an RFC 3339 time such as `2026-10-28T05:47:36Z` | all | Use UTC (`Z`). Cannot be combined with `--since` |
| `--timestamps` | Put the runtime's RFC 3339 timestamp (nanoseconds) in front of each line | off | The time is when the runtime read the line, not when the app created it |
| `-p` / `--previous` | Logs of the **previous** instance of the container (before the last restart) | off | Fails with `previous terminated container ... not found` if the container never restarted |
| `--limit-bytes N` | Stop after N bytes | `0` (no limit) | Cuts in the middle of a line. Use for huge logs when you only need the start |
| `--ignore-errors` | With a selector or `-f`: do not stop when one Pod cannot be read | off | Errors are still printed. Without it, one bad Pod aborts the whole command |
| `--max-log-requests N` | Maximum number of streams followed at the same time when you use a selector with `-f` | `5` | More matching Pods than N with `-f` is an error (see section 6) |
| `--all-pods` | With `deploy/x` (or another controller): read every Pod, not just one. Turns `--prefix` on | off | Only for controller targets |
| `--pod-running-timeout` | How long to wait for at least one Pod to be running | `20s` | Does not wait for a Pod that cannot start |
| `-l SELECTOR` | Read all Pods with this label | none | Applies the `--tail=10` default |

Flags that take a value use `=` or a space: `--tail=50` and `--tail 50` are the same.

**Examples with real output.** The Pod `web` has two containers (`app` writes a line to stdout and a line to stderr every second, `helper` prints a line every five seconds; the YAML is in section 5).

```bash
k logs web -c helper --tail=3
k logs web -c app --since-time=2026-10-28T05:47:36Z | head -3
k logs web -c app --limit-bytes=30; echo "<EOF>"
k logs web -c app --since=5s --since-time=2026-10-28T05:47:36Z
```

REAL OUTPUT (kind v0.33.0, v1.37.0)

```text

helper alive
---
app line 11
app warn 11
app line 12
---
app line 1
app warn 1
app line<EOF>
---
error: at most one of `sinceTime` or `sinceSeconds` may be specified
```

(The `---` lines were printed by `echo` between the commands to separate the outputs. `--limit-bytes=30` stopped in the middle of the word `line`.)

With `--timestamps` the runtime adds its own time. Together with `--prefix` and `--all-containers`:

```bash

```

### 2.4 Which container do you get? (`-c`, default container)

A Pod with more than one container needs a choice. Modern `kubectl` makes the choice for you and prints a notice on stderr:

```text
Defaulted container "app" out of: app, helper
```

It picks the first container in `spec.containers`, unless the Pod has the annotation `kubectl.kubernetes.io/default-container: <name>`. In the notice, init containers are shown with `(init)`. The risk is silent: you read the wrong container and think the app has no errors. In a multi-container Pod, **always write `-c`**.

The error `a container name must be specified for pod ..., choose one of: [...]` comes from the API server when no container is sent. You meet it with the raw API call above, with client libraries and scripts that call the API directly, and on old `kubectl` versions that did not default. If you see it, add `-c <name>` and pick from the list in the message.

The annotation changes the default. Test on the `web` Pod:

```bash
k annotate pod web kubectl.kubernetes.io/default-container=helper
k logs web --tail=1
```

REAL OUTPUT (kind v0.33.0, v1.37.0)

```text
pod/web annotated
helper alive
```

(No `Defaulted container` line appeared, because the annotation names the container.)

### 2.5 Logs of init containers and sidecars

An **init container** runs to completion before the app starts (see [T3.08](../part3-ckad/T3.08-multi-container-pod-patterns-init-sidecar.md)). Its logs stay available after it exits, so you read them with `-c <init-name>`. This is the first place to look when a Pod is stuck in `Init:0/1` or `Init:Error`.

A **sidecar** is a helper container that runs next to the app. The modern form is a **native sidecar**: an entry in `spec.initContainers` with `restartPolicy: Always`. It is read with `-c` like any other container. A sidecar of the older style is simply a second entry in `spec.containers`.

`--all-containers` includes init containers and native sidecars. Real output for a Pod `multi` with an init container `prep`, a native sidecar `shipper` and an app container `app`:

```bash
k logs multi -c prep
k logs multi --all-containers --prefix --tail=2
```

REAL OUTPUT (kind v0.33.0, v1.37.0)

```text
prep: creating config
---
[pod/multi/prep] prep: creating config
[pod/multi/shipper] shipper: heartbeat
[pod/multi/shipper] shipper: heartbeat
[pod/multi/app] app: serving
[pod/multi/app] app: serving
```

Plain `k logs multi` printed `Defaulted container "app" out of: app, prep (init), shipper (init)` and then the lines of `app`.

Three rules for selectors:

1. **`--tail` defaults to 10 per container** with `-l`. For a Pod name the default is "all". In the lab below, 3 Pods with `-l` and no `--tail` gave exactly 30 lines, while `--tail=-1` gave 63. If a task says "save the logs", add `--tail=-1`.
2. **`--prefix` is how you tell the Pods apart.** The format is `[pod/<pod>/<container>]`.
3. **`--max-log-requests` limits `-f`.** The default is 5 streams. With 7 matching Pods and `-f`:

```bash

k logs -l app=shop -f --tail=1 --max-log-requests=10
```

(The second command ran without an error and followed all 7 Pods; it is a streaming command, so no fixed output is shown.) Without `-f`, 7 Pods are read without any error.

### 2.7 Where logs live on the node

The kubelet and the runtime keep the log files on the node's disk:

```text
/var/log/pods/<namespace>_<pod-name>_<pod-uid>/<container-name>/<restart-count>.log
/var/log/containers/<pod>_<namespace>_<container>-<container-id>.log   (symbolic link to the file above)
```

The file name is the restart count of that container: `0.log` for the first run, `1.log` after one restart, and so on. Every line has the format `<RFC3339 time> <stdout|stderr> <F|P> <text>`. `F` means "full line", `P` means "partial line" (a long line the runtime cut into pieces).

Real listing, from the worker node of a Pod `payments` that had restarted four times:

```bash
docker exec k-t322-worker ls -la /var/log/pods/lab-t322_payments_<uid>/app/
docker exec k-t322-worker cat /var/log/pods/lab-t322_payments_<uid>/app/4.log
```

REAL OUTPUT (kind v0.33.0, v1.37.0)

```text
total 4
drwxr-xr-x 1 root root  10 Oct 28 05:54 .
drwxr-xr-x 1 root root   6 Oct 28 05:52 ..
-rw-r----- 1 root root 129 Oct 28 05:54 4.log
---
2026-10-28T05:54:19.002923711Z stdout F payments starting
2026-10-28T05:54:27.003711923Z stderr F FATAL: missing setting DB_HOST
```

(On kind a node is a Docker container, so `docker exec <node>` replaces `ssh <node>`. In the exam, use the `ssh <node>` command from the task, then `sudo -i`; see [E7](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad) and E8.) To find the node and the UID: `k get pod payments -o wide` and `k get pod payments -o jsonpath='{.metadata.uid}'`.

On a node you can also use `crictl logs <container-id>` (the CRI command-line tool) or, for the kubelet's own log, `journalctl -u kubelet`.

### 2.8 Rotation (`containerLogMaxSize`, `containerLogMaxFiles`)

Without a limit a chatty app would fill the node disk. The kubelet **rotates** container logs. Two fields of the `KubeletConfiguration` control it:

| Field | Meaning | Default in kubelet v1.37.0 (checked) | Risky values |
|---|---|---|---|
| `containerLogMaxSize` | Size at which a log file is rotated | `10Mi` | A very large value lets logs eat the node disk |
| `containerLogMaxFiles` | Number of files kept per container, **the live file included** | `5` | Setting it low loses old lines sooner |
| `containerLogMonitorInterval` | How often the kubelet checks sizes | `10s` | A fast writer can overshoot the size between checks |
| `containerLogMaxWorkers` | Parallel rotation workers | `1` | Raise only on nodes with very many containers |

I read these from a running kubelet through the API server (this is the effective configuration, defaults included):

```bash
k get --raw /api/v1/nodes/k-t322-worker/proxy/configz | python3 -c "import sys,json; c=json.load(sys.stdin)['kubeletconfig']; print({k:v for k,v in c.items() if 'ontainerLog' in k})"
```

REAL OUTPUT (kind v0.33.0, v1.37.0)

```text
{'containerLogMaxSize': '10Mi', 'containerLogMaxFiles': 5, 'containerLogMaxWorkers': 1, 'containerLogMonitorInterval': '10s'}
```

(`python3` was only used here to pick fields; in an exam use `yq` or `grep` instead, because `jq` and `python3` are not promised on the exam hosts; see [E9](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad).) On a kubeadm node the kubelet file is `/var/lib/kubelet/config.yaml`; add `containerLogMaxSize: 20Mi` there and restart the kubelet to change it. On the kind node I checked, that file did not contain these fields, which means the defaults above applied.

What rotation looks like: a Pod `spew` wrote about 1.2 million lines quickly. The node directory afterwards:

```text
-rw-r----- 1 root root  6922766 Oct 28 05:56 0.log
-rw-r----- 1 root root   729672 Oct 28 05:55 0.log.20261028-055538.gz
-rw-r----- 1 root root   723070 Oct 28 05:56 0.log.20261028-055558.gz
-rw-r----- 1 root root   733375 Oct 28 05:56 0.log.20261028-055618.gz
-rw-r----- 1 root root 20558211 Oct 28 05:56 0.log.20261028-055638
```

REAL OUTPUT (kind v0.33.0, v1.37.0)

Read it like this. `0.log` is the live file. The others are rotated files named with the rotation time; the older ones are compressed with gzip (`.gz`). The total is 5 files, as `containerLogMaxFiles: 5` says. The newest rotated file is 20 MB, not 10Mi, because the writer was fast and the size is only checked every 10 seconds. When a sixth file would appear, the oldest one is deleted, so the oldest lines are lost for good.

**`kubectl logs` reads only the live file.** For `spew`, `k logs spew | wc -l` returned `66001` lines, although the app had written about 1.2 million. The lines in the rotated files are not returned. If you need them, read the rotated files on the node (use `zcat` for the `.gz` ones).

### 2.9 When logs disappear

| Event | What happens to the logs | Real observation |
|---|---|---|
| Pod deleted | The kubelet removes `/var/log/pods/<ns>_<pod>_<uid>/` and `kubectl logs` cannot find the Pod | `error: error from server (NotFound): pods "spew" not found in namespace "lab-t322"`. The directory was still there for a few seconds, then gone |
| Container restarted | A new file `<n+1>.log` starts. The previous instance can be read with `-p` | See 2.10 |
| Older dead containers | The kubelet keeps only the latest dead container per container name; older ones are removed together with their logs | Only attempt 4 existed after four restarts (checked with `crictl ps -a`) |
| Rotation | The oldest file is deleted when there are more than `containerLogMaxFiles` | Section 2.8 |
| Node lost or replaced | All its logs are gone | n/a |

This is why real clusters run a **log collector** that copies logs off the node (section 2.12). `kubectl logs` is a live view, not an archive. In a task, save what you need into a file **before** you delete or recreate anything.

### 2.10 Crash loops and `--previous`

A **crash loop** is a container that starts, exits (usually with a non-zero **exit code**), is restarted by the kubelet, and exits again. The kubelet waits longer between restarts (a **back-off**), and when it waits, `k get pods` shows `CrashLoopBackOff`.

The trap: when you run `k logs` the container may be a brand new instance that has only just started and has not reached the error yet. The error is in the log of the **previous** instance. `-p` (`--previous`) gives that log.

Real run. The Pod `payments` prints one line, sleeps 8 seconds, prints `FATAL: missing setting DB_HOST` to stderr and exits with code 3. Look at the same Pod in two moments:

```bash
k get pod payments
k logs payments            # current instance
k logs payments -p         # previous instance
```

REAL OUTPUT (kind v0.33.0, v1.37.0)

```text
NAME       READY   STATUS    RESTARTS      AGE
payments   1/1     Running   4 (53s ago)   2m4s
---
payments starting
---
payments starting
FATAL: missing setting DB_HOST
```

The current instance had only printed its first line. The previous one has the error. (`---` lines are separators added by `echo`.)

Now the second moment, a few seconds later, when the current instance has died and the kubelet is waiting to restart it:

```text
NAME       READY   STATUS   RESTARTS      AGE
payments   0/1     Error    4 (59s ago)   2m10s
---
payments starting
FATAL: missing setting DB_HOST
---
unable to retrieve container logs for containerd://15e37d9ea37ab63b424a50150e8e904b5045a12deeace0b97edb58064a03e43c
```

REAL OUTPUT (kind v0.33.0, v1.37.0), the three parts are the output of `k get pod payments`, `k logs payments` and `k logs payments -p` in that order.

Read this carefully, because it is the opposite of the first moment:

- When the **current** instance is already dead, plain `k logs` shows that dead instance, and it has the error.
- `-p` then asks for the instance **before** that. The kubelet had already removed it (it keeps one dead container per container name), so `-p` printed `unable to retrieve container logs for containerd://<id>`. That text arrived on **stdout** and the exit code was `0`. I checked: `k logs payments -p > file` writes this message into your file and reports success.
- Which case you are in depends on the timing, so the rule is: try `k logs`, and if it is empty or short, try `-p`. If `-p` says `unable to retrieve`, run plain `k logs` again, or wait for the next restart (`k get pods -w`) and run `-p` while the Pod is `Running`. Always read the saved file before you finish.

A Pod in the `CrashLoopBackOff` state looks like this, from the same cluster with a Pod `cl` that prints `boot` and exits with code 1 immediately:

```bash
k get pod cl
k logs cl -p
k describe pod cl | grep -E -A3 'State:|Last State'
```

REAL OUTPUT (kind v0.33.0, v1.37.0), trimmed

```text
NAME   READY   STATUS             RESTARTS      AGE
cl     0/1     CrashLoopBackOff   4 (77s ago)   2m52s
---
boot
---
    State:          Waiting
      Reason:       CrashLoopBackOff
    Last State:     Terminated
      Reason:       Error
      Exit Code:    1
```

`-p` without any restart is an error: `Error from server (BadRequest): previous terminated container "busybox" in pod "orders-68b59cd5b-gk2bt" not found`.

Also read the **exit code** (`Last State ... Exit Code`). A log tells you what the app said; the exit code tells you how it ended: 1 is a general error, 137 means the process was killed (often out of memory), 0 means it exited cleanly (a wrong command for a long-running app).

### 2.11 Jobs and CronJobs

A **Job** runs Pods to completion; a **CronJob** creates Jobs on a schedule. Their Pods remain after they finish (state `Completed`), so their logs can be read. Use `job/<name>`:

```bash
k logs job/pi
k logs job/pi > ~/lab/t322/pi.txt
k logs cronjob/tick
k create job tick-now --from=cronjob/tick
k logs job/tick-now
```

REAL OUTPUT (kind v0.33.0, v1.37.0)

```text
computing
result=3.14159
---
(no output on screen; the file contains the same two lines)
---
error: cannot get the logs from *v1.CronJob: selector for *v1.CronJob not implemented
---
job.batch/tick-now created
tick at 05:57:43
```

`kubectl logs` does not accept a CronJob. Two ways round it: read the Pod of a Job it already created (`k get pods`, then `k logs <pod>`; or `k logs job/<job-name>`), or start a Job from it on demand with `k create job NAME --from=cronjob/NAME`. If the Job has several Pods, `job/x` reads one and prints `Found N pods, using pod/...`; use `--all-pods` for all. A Job keeps its finished Pods only until the Job is deleted or the history limits of the CronJob (`successfulJobsHistoryLimit`, default 3, and `failedJobsHistoryLimit`, default 1) remove them, so read the log early.

### 2.12 Logging patterns

Kubernetes does not ship a log storage system. It gives you the node files. The patterns in the official logging page are:

| Pattern | How it works | When to use it | Observe it |
|---|---|---|---|
| **Write to stdout and stderr** (the standard) | The app prints to the console; the runtime writes the node file | Always, if you can change the app or its config | `k logs POD` |
| **Streaming sidecar** | The app writes a **file** in a shared volume. A sidecar container in the same Pod reads the file (`tail -F`) and prints it to its own stdout | You cannot change the app, and it only writes to a file | `k logs POD -c sidecar` |
| **Node-level agent** | A DaemonSet (one Pod per node) runs a log collector that reads `/var/log/pods` on the node and sends the lines to central storage | Production clusters, so logs outlive Pods | Not needed on the exam. Look for a DaemonSet in `kube-system` or a logging namespace |
| **Sidecar with logging agent** | A sidecar that ships logs itself (to a remote service) | Per-app destinations | Awareness only |
| **App pushes logs directly** | The app sends logs to a backend over the network | Apps that already include a log library for it | Awareness only |

For the CKAD you must be able to do the first two and recognise the others. A streaming sidecar is built from two things you already know from [T3.08](../part3-ckad/T3.08-multi-container-pod-patterns-init-sidecar.md): an `emptyDir` volume mounted in both containers, and a second container. The exact YAML is in section 4; it was tested end to end (section 4 YAML and Lab C).

**The other way: make the app log to stdout.** Many images offer a setting for it. Common image practice is to make the log file a link to `/dev/stdout`. Before you add a sidecar, check whether a config flag or env variable solves it, because it is simpler and uses no extra container.

### 2.13 Saving logs exactly

A task usually says "save the logs of X to /opt/something.log". Rules:

- Use the shell redirect: `k logs web -c app > /opt/app.log`. Use `>>` to append.
- stdout and stderr of the **app** are already merged in the log. Messages from `kubectl` itself (such as `Found 3 pods, using ...` and `Defaulted container ...`) go to stderr, so they do not enter the file. I observed this for `Found 2 pods, using pod/...` while redirecting.
- Name the container (`-c`) and say whether you want the current or previous instance. For all Pods of a Deployment, `-l app=x --tail=-1` (and `--prefix` if asked).
- After saving, **read the file**: `cat /opt/app.log | head` and `wc -l`. This catches an empty file and the `unable to retrieve` message from section 2.10.
- Do not use `-f` when saving unless the task asks for it: the command never ends.
- A path under `/opt` may need `sudo` if the exam user cannot write there. The task text tells you the path; read it twice.

### 2.14 Related but different

| Tool | Answers | When it is better than `logs` |
|---|---|---|
| `k logs` | What did the container print? | The app started and ran |
| `k describe pod` / `k get events` | Why did Kubernetes not start it or why did it restart it (image pull errors, probes, OOM kill, scheduling)? | The container never started, so there is no log yet |
| `k exec POD -- cat /var/log/app.log` | What is in this file? | The app logs to a file and you only need one look |
| `k debug` | Start an ephemeral debug container | The image has no shell or tools |
| `k logs -n kube-system POD` | Logs of control-plane and add-on Pods | Control-plane components run as Pods on kubeadm clusters |
| `k top pod` | CPU and memory | Resource questions, not text |

## 3. How it works (diagram)

```text
 +---------------------------+
 | app process in container  |
 +---------------------------+
      | writes to stdout (fd 1) and stderr (fd 2)
      v
 +---------------------------+
 | container runtime         |   containerd: reads both streams,
 | (containerd)              |   adds "<time> <stdout|stderr> <F|P>"
 +---------------------------+
      | appends one line at a time
      v
 +--------------------------------------------------------------+
 | node disk: /var/log/pods/<ns>_<pod>_<uid>/<container>/N.log  |
 | (link: /var/log/containers/<pod>_<ns>_<ctr>-<id>.log)        |
 | rotated by the kubelet: 10Mi per file, 5 files (defaults)    |
 +--------------------------------------------------------------+
      ^                                   |
      | reads the live file               | (a node-level agent can also
      |                                   |  read these files and ship them)
 +---------------------------+            v
 | kubelet  :10250           |      central log storage (awareness)
 +---------------------------+
      ^
      | proxied request
 +---------------------------+
 | kube-apiserver            |   GET /api/v1/namespaces/<ns>/pods/<pod>/log
 +---------------------------+
      ^
      | kubectl logs POD -c NAME [-f] [-p] [--tail] [--since]
 +---------------------------+
 | you                       |
 +---------------------------+
```

Walkthrough:

1. The app writes to stdout or stderr. If it writes to a file inside the container, nothing enters this flow.
2. The container runtime captures both streams and appends each line, with a time and stream tag, to `N.log` under `/var/log/pods/...`. `N` is the restart count.
3. The kubelet rotates the file at `containerLogMaxSize` and keeps `containerLogMaxFiles` files.
4. `kubectl logs` sends a request to the API server. The API server forwards it to the kubelet of the Pod's node, which reads the live file and streams the lines back. `-p` makes the kubelet read the file of the previous instance.
5. If the Pod is deleted, the kubelet removes the directory. A node-level agent is the only thing that keeps the lines for longer.

**Imperative commands** (all tested on the lab cluster):

```bash

```

Generate the Pod YAML for the sidecar task, then edit it:

```bash

```

This gives a Pod with one container named `logger`. You must add the volume, the volume mounts and the sidecar yourself. The complete result:

**Declarative YAML: a sidecar that streams a log file to stdout.** The app writes only to `/var/log/app.log`. The sidecar prints that file, so `k logs logger -c sidecar` works.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: logger
  labels:
    app: logger
spec:
  volumes:
  - name: logs                    # a volume that both containers mount
    emptyDir: {}                  # empty directory created with the Pod, deleted with the Pod; default medium is the node disk
  containers:
  - name: app                     # the main container; its default name for kubectl logs (first in the list)
    image: busybox:1.36           # pinned tag
    command: ["sh", "-c", "i=0; while true; do i=$((i+1)); echo \"$(date +%T) request $i handled\" >> /var/log/app.log; sleep 2; done"]
                                  # writes to a FILE only: nothing on stdout, so 'k logs logger -c app' is empty
    volumeMounts:
    - name: logs                  # must match a name in spec.volumes
      mountPath: /var/log         # where the volume appears in this container (replaces whatever the image has at this path)
  - name: sidecar                 # the streaming sidecar; read it with: k logs logger -c sidecar
    image: busybox:1.36
    command: ["sh", "-c", "tail -n+1 -F /var/log/app.log"]
                                  # -n+1: start at line 1; -F: keep trying if the file does not exist yet or is replaced
    volumeMounts:
    - name: logs                  # the SAME volume
      mountPath: /var/log         # the same path, so the file name is the same
      readOnly: true              # the sidecar only reads; default is false
```

Notes on risky values: if `mountPath` differs between the containers, the sidecar tails a path that does not exist, and `tail -F` waits for ever without an error. If you use `tail -f` (lowercase) and the file is not there yet, `tail` may exit with an error and the container restarts (not tested; `-F` avoids the question). If you forget `readOnly` nothing breaks, but the sidecar could change the file by mistake.

**The native sidecar form** (an init container with `restartPolicy: Always`, Kubernetes v1.33 and later; the sidecar starts before the app and keeps running). It was tested too:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: logger2
spec:
  volumes:
  - name: logs
    emptyDir: {}
  initContainers:
  - name: sidecar
    image: busybox:1.36
    restartPolicy: Always         # this field turns an init container into a native sidecar
    command: ["sh", "-c", "tail -n+1 -F /var/log/app.log"]
    volumeMounts:
    - name: logs
      mountPath: /var/log
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "i=0; while true; do i=$((i+1)); echo \"request $i handled\" >> /var/log/app.log; sleep 2; done"]
    volumeMounts:
    - name: logs
      mountPath: /var/log
```

Both forms are read with `-c sidecar`. For `logger2` the plain `k logs logger2` printed `Defaulted container "app" out of: app, sidecar (init)`, so the default is still the app container.

## 6. Common mistakes and how to fix them

| Symptom | What you will see (exact text) | Cause | Fix (command) |
|---|---|---|---|
| Multi-container Pod: no container named | `Error from server (BadRequest): a container name must be specified for pod web, choose one of: [app helper]` (API server, raw calls and old kubectl). Current kubectl prints `Defaulted container "app" out of: app, helper` and shows the first container | Pod has several containers and none was chosen | `k logs web -c helper`; list names with `k get pod web -o jsonpath='{.spec.containers[*].name}'` |
| Wrong container name | `error: container nope is not valid for pod web out of: app, helper` | Typo, or the name belongs to an init container (then it is shown with `(init)`) | Use a name from the message |
| Logs empty or short for a crashing container | `k logs payments` shows only `payments starting` while `STATUS` is `Running` and `RESTARTS` grows | The current instance has just started; the error is in the previous one | `k logs payments -p` |
| `-p` returns an error text instead of logs | `unable to retrieve container logs for containerd://15e37d9e...` (printed to stdout, exit code 0) | The instance before the current (dead) one was already removed | `k logs payments` (the dead instance is the current one), or wait for `Running` and run `-p` again |
| `-p` on a Pod that never restarted | `Error from server (BadRequest): previous terminated container "busybox" in pod "orders-68b59cd5b-gk2bt" not found` | There is no previous instance | Use plain `k logs` |
| App logs to a file; `kubectl logs` is empty | no output, exit code 0 | The app does not write to stdout or stderr | Add a streaming sidecar (section 4), or reconfigure the app to log to the console |
| Only 10 lines per Pod | `k logs -l app=orders` prints 30 lines for 3 Pods | `--tail` defaults to 10 with a selector | Add `--tail=-1` |
| Only one Pod read | `Found 3 pods, using pod/shop-8577d46489-qgclj` | A controller target reads one Pod | `--all-pods`, or `-l app=shop --prefix` |
| Too many streams with `-f` | `error: you are attempting to follow 7 log streams, but maximum allowed concurrency is 5, use --max-log-requests to increase the limit` | More than 5 Pods matched | `--max-log-requests=10` |
| One bad Pod aborts a selector read | `Error from server (BadRequest): container "broken" in pod "broken" is waiting to start: image can't be pulled` | A matching Pod has no running container | `--ignore-errors`; fix the Pod with `k describe pod broken` |
| Time flags clash | ``error: at most one of `sinceTime` or `sinceSeconds` may be specified`` | `--since` and `--since-time` together | Use only one |
| Logs of a deleted Pod | `error: error from server (NotFound): pods "web" not found in namespace "lab-t322"` | The Pod and its logs are gone | Save logs before deleting; use a node-level agent in real clusters |
| CronJob target | `error: cannot get the logs from *v1.CronJob: selector for *v1.CronJob not implemented` | `kubectl logs` does not take a CronJob | `k logs job/<job-name>`, or `k create job x --from=cronjob/<name>` |
| `k logs deploy/x -c sidecar` fails during a rollout | `error: container log-tail is not valid for pod billing-5fb7cc9d86-9jmtp out of: app` | The command picked an old Pod that is still terminating | Wait until `k get pods -l app=billing` shows one Pod, then repeat |

**Troubleshooting path 1: "a container name must be specified".**

1. `k get pod web -o jsonpath='{.spec.containers[*].name}'` prints the regular container names. Init containers are in `.spec.initContainers[*].name`.
2. `k logs web -c <name>` for each one that interests you, or `k logs web --all-containers --prefix` to see all at once.
3. If one container is silent, check if it is the one you expect to write logs: `k describe pod web` shows each container's `State` and `Restart Count`.

Fix: always give `-c` for multi-container Pods. Do not trust the first container.

**Troubleshooting path 2: "Logs empty for a crashing container".**

1. `k get pod payments` : read `STATUS` and `RESTARTS`. A growing `RESTARTS` means a restart loop.
2. `k logs payments` : if it shows only the start of the output, the current instance is new.
3. `k logs payments -p` : the full previous instance. If the output is `unable to retrieve container logs for containerd://...`, read plain `k logs` again, because the dead instance is then the current one.
4. `k describe pod payments` : read `Last State`, `Reason` and `Exit Code`. `OOMKilled` or `137` explains a crash that has no log line.
5. `k get events --field-selector involvedObject.name=payments` : look for `BackOff` lines such as `Back-off restarting failed container ...`.

Fix: change what the logs show (config, command, env, image), then recreate the Pod. Use `k delete pod payments $now` and `k apply -f` again if the field is immutable.

**Troubleshooting path 3: "App logs to a file, `kubectl logs` shows nothing".**

1. `k logs web -c app` is empty and exit code is 0: the container is running but silent.
2. Confirm the file exists: `k exec web -c app -- ls -l /var/log` and `k exec web -c app -- tail -3 /var/log/app.log` (or the path from the task or the image docs).
3. Decide: change the app's logging (a flag, env variable or config file) or add a sidecar that tails the file. The sidecar needs a **shared volume** on the directory of the file.

Fix: add the `emptyDir` volume, mount it in both containers at the log directory, and add a sidecar with `tail -n+1 -F <file>` (section 4). If the app currently writes to a directory that is not on a volume, you must mount the volume at that directory in the app container, because files in the container's own layer cannot be shared.

### Lab A (Easy): collect the logs of 3 replicas into one file

**Setup:**

```bash
mkdir -p ~/lab/t322
k create deploy orders --image=busybox:1.36 --replicas=3 -- sh -c 'i=0; while true; do i=$((i+1)); echo "order $i from $(hostname)"; sleep 2; done'
k rollout status deploy/orders
sleep 40
```

**Task.** In namespace `lab-t322`, Deployment `orders` runs three replicas. Save the complete logs of all its Pods into `~/lab/t322/orders.log`. Each line must start with the Pod name in the form `[pod/<pod>/<container>]`. The file must hold all lines written so far, not just the last few.

<details><summary>Hints</summary>

1. A label selector reads all Pods; `k get deploy orders --show-labels` shows the label (`k create deploy` sets `app=orders`).
2. `--prefix` adds the source in front of each line.
3. With a selector, `--tail` defaults to 10 lines per Pod. How do you ask for all?

</details>

<details><summary>Solution</summary>

```bash
k logs -l app=orders --prefix --tail=-1 > ~/lab/t322/orders.log
```

Why each part: `-l app=orders` selects all three Pods (a `deploy/orders` target would read only one). `--prefix` writes the Pod and container name in front of each line, which is the required format. `--tail=-1` overrides the selector default of 10 lines per Pod. The redirect `>` saves the stream; the `Found ...` style notices go to stderr, so they are not in the file. Equivalent: `k logs deploy/orders --all-pods --tail=-1 > ~/lab/t322/orders.log`.

</details>

**Verification** (each command prints a result and sets an exit status; all four must print `OK`):

```bash

test "$(grep -vc '^\[pod/orders-' ~/lab/t322/orders.log)" -eq 0 && echo OK                         # every line has the prefix
test "$(wc -l < ~/lab/t322/orders.log)" -gt 30 && echo OK                                          # more than the 3 x 10 default lines
grep -q 'order 1 from' ~/lab/t322/orders.log && echo OK                                            # the earliest lines are there
```

Real run: the file had 63 lines; with the default tail the same command gave 30.

**Cleanup:**

```bash

```

### Lab B (Medium): find the error in the previous instance of a crash-looping container

**Setup:**

```bash
mkdir -p ~/lab/t322
k apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: payments
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "echo payments starting; sleep 8; echo \"FATAL: missing setting DB_HOST\" >&2; exit 3"]
EOF
sleep 45
```

**Task.** In namespace `lab-t322`, Pod `payments` keeps restarting. Do not change the Pod. (1) Use the logs of the previous instance of its container to find the line that starts with `FATAL`, and save that line alone in `~/lab/t322/payments-reason.txt`. (2) Save the exit code of the last failed run in `~/lab/t322/payments-exit.txt` (just the number).

<details><summary>Hints</summary>

1. `k get pod payments` : is `RESTARTS` growing? Try plain `k logs payments` and see how much it shows.
2. `-p` shows the previous instance. If it prints `unable to retrieve container logs ...`, the timing is wrong: wait for the next restart. Pipe the output to `grep FATAL`, so a bad result gives an empty file.
3. The exit code is in `.status.containerStatuses[0].lastState.terminated.exitCode`.

</details>

<details><summary>Solution</summary>

```bash
until k logs payments -p | grep FATAL > ~/lab/t322/payments-reason.txt; do sleep 2; done
k get pod payments -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}' > ~/lab/t322/payments-exit.txt
```

Why: the current instance prints only `payments starting` for its first 8 seconds, so plain `k logs` hides the error. `-p` reads the instance before it. Depending on the moment, `-p` may print `unable to retrieve container logs ...` (the earlier dead container was already removed, and the message goes to stdout with exit code 0). `grep FATAL` returns a failure when the line is missing, so the `until` loop repeats every 2 seconds until a `-p` call lands on a moment when the previous instance exists. The exit code is stored in `lastState` of the container status, which is where the kubelet records how the last instance ended.

</details>

**Verification:**

```bash
test "$(cat ~/lab/t322/payments-reason.txt)" = "FATAL: missing setting DB_HOST" && echo OK    # exactly one line, exactly this text
test "$(cat ~/lab/t322/payments-exit.txt)" = "3" && echo OK                                    # exit code of the last run
test "$(k get pod payments -o jsonpath='{.spec.containers[0].command[2]}' | grep -c exit)" -eq 1 && echo OK   # the Pod was not changed
```

**Cleanup:**

```bash
k delete pod payments $now; rm -f ~/lab/t322/payments-reason.txt ~/lab/t322/payments-exit.txt
```

### Lab C (Break-fix): the app logs only to a file, add a streaming sidecar

**Setup** (`break.sh`, run it with `bash break.sh`):

```bash
cat > ~/lab/t322/break.sh <<'EOS'
cat <<'YAML' | kubectl apply -n lab-t322 -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: billing
spec:
  replicas: 1
  selector:
    matchLabels:
      app: billing
  template:
    metadata:
      labels:
        app: billing
    spec:
      terminationGracePeriodSeconds: 2
      volumes:
      - name: logs
        emptyDir: {}
      containers:
      - name: app
        image: busybox:1.36
        command: ["sh", "-c", "i=0; while true; do i=$((i+1)); echo \"invoice $i paid\" >> /var/log/app/app.log; sleep 2; done"]
        volumeMounts:
        - name: logs
          mountPath: /var/log/app
YAML
EOS
bash ~/lab/t322/break.sh
k rollout status deploy/billing
sleep 5
```

**Task.** In namespace `lab-t322`, Deployment `billing` runs one container `app`, which writes its log lines to `/var/log/app/app.log`. `k logs deploy/billing` shows nothing. Do not change the `app` container. Add a sidecar container named `log-tail` (image `busybox:1.36`) to the Pod template so that `k logs deploy/billing -c log-tail` prints the app's lines. Then save that output into `~/lab/t322/billing.log`.

<details><summary>Hints</summary>

1. The file is in a directory that already sits on a volume of the Pod. Look at `k get deploy billing -o yaml` (the `volumes` and `volumeMounts` parts).
2. The sidecar must mount the same volume at the same path and run `tail -n+1 -F /var/log/app/app.log`.
3. A Deployment's Pod template can be changed with `k edit deploy billing` or `k patch`. After the change a new Pod replaces the old one, so wait until only one Pod is left before you read logs.

</details>

<details><summary>Solution</summary>

```bash
k patch deploy billing -p '{"spec":{"template":{"spec":{"containers":[{"name":"log-tail","image":"busybox:1.36","command":["sh","-c","tail -n+1 -F /var/log/app/app.log"],"volumeMounts":[{"name":"logs","mountPath":"/var/log/app","readOnly":true}]}]}}}}'
k rollout status deploy/billing
sleep 8
k get pods -l app=billing          # wait until exactly one Pod is listed, READY 2/2
k logs deploy/billing -c log-tail > ~/lab/t322/billing.log
```

Why each step: the `app` container only appends to a file, so there is nothing on its stdout. The volume `logs` already exists and is mounted in `app` at `/var/log/app`, so a second container can share it. The patch is a strategic merge patch: the `containers` list is merged by `name`, so `app` stays as it is and `log-tail` is added. `tail -n+1 -F` prints the file from line 1 and keeps following it; `-F` also retries until the file exists, which matters because the sidecar may start before the app writes its first line. You may see `tail: can't open '/var/log/app/app.log': No such file or directory` and then `tail: /var/log/app/app.log has appeared; following end of new file` at the top of the sidecar log. That is normal. The Pod template changed, so the Deployment starts a new Pod; reading `deploy/billing` while the old Pod still terminates picks the old Pod (it has no `log-tail`), hence the wait. `terminationGracePeriodSeconds: 2` in the setup keeps that wait short. You can also edit the YAML with `k edit deploy billing` and add the container by hand; the result is the same.

</details>

**Verification:**

```bash
test "$(k get deploy billing -o jsonpath='{.spec.template.spec.containers[?(@.name=="log-tail")].image}')" = "busybox:1.36" && echo OK   # the sidecar exists
test "$(k get deploy billing -o jsonpath='{.spec.template.spec.containers[?(@.name=="app")].command[2]}' | grep -c 'app.log')" -eq 1 && echo OK   # app command untouched
grep -q 'invoice [0-9]* paid' ~/lab/t322/billing.log && echo OK       # the file has the app's lines
test "$(k logs deploy/billing -c app | wc -c)" -eq 0 && echo OK       # the app itself is still silent on stdout
```

Real run: before the fix `k logs deploy/billing | wc -c` printed `0`. After the fix `billing.log` began with the two `tail:` lines above, followed by `invoice 1 paid` and so on.

**Cleanup:**

```bash
k delete deploy billing; rm -f ~/lab/t322/break.sh ~/lab/t322/billing.log
k delete ns lab-t322        # only after the last lab; this returns the cluster to the baseline
```

## 8. Exam tips

- Practise the full pattern in one line: `k logs POD -c CONTAINER [-p] [--tail=-1] > /path/file`, then `cat /path/file | head -3`. An empty file or an `unable to retrieve` line means the task is not done.
- For multi-container Pods always use `-c`, and use `--all-containers --prefix` when you are not sure which container writes the error. List names with `k get pod POD -o jsonpath='{.spec.containers[*].name}'`.
- If the app is crash-looping, try `k logs` first, then `-p`, then `k describe pod` for `Exit Code` and `Reason`. Exit code 137 or `OOMKilled` often has no log line.
- Read the task for the target: `deploy/x` reads one Pod; add `--all-pods` or use `-l` with `--tail=-1` when the task wants every replica.
- In-terminal help is faster than the browser: `k logs --help` lists examples for every flag. Open these pages when you need more: the logging architecture page https://kubernetes.io/docs/concepts/cluster-administration/logging/ (sidecar YAML), the kubectl logs reference https://kubernetes.io/docs/reference/kubectl/generated/kubectl_logs/ and the debugging page https://kubernetes.io/docs/tasks/debug/debug-application/debug-running-pod/.
- Before you move on: is the path in the task exactly what you wrote? Did you write to the right namespace (`-n`)? Is the file non-empty? Did you leave a background `-f` process running (Ctrl+C it)?

## 9. Quick review

1. Which command shows the last 50 lines of container `app` in Pod `web` and keeps following?
<details><summary>Answer</summary>`k logs web -c app --tail=50 -f`. `--tail` limits the history, `-f` keeps the stream open.</details>

2. A Pod is crash-looping and `k logs` shows only the first line of the output. What do you run, and why?
<details><summary>Answer</summary>`k logs POD -p` (add `-c NAME` if there are several containers). The current instance has just started; the error is in the previous instance. If it prints `unable to retrieve container logs`, run plain `k logs` or wait for the next restart.</details>

3. Why does `kubectl logs` show nothing for an app that writes to `/var/log/app.log`?
<details><summary>Answer</summary>Because the kubelet and runtime keep only stdout and stderr. Fix: log to the console, or add a sidecar that tails the file from a shared `emptyDir` and prints it to its own stdout.</details>

4. What does `k logs deploy/shop` read when the Deployment has 3 Pods, and how do you read all of them?
<details><summary>Answer</summary>One Pod (it prints `Found 3 pods, using pod/...`). Use `--all-pods` or `-l app=shop --prefix`, and `--tail=-1` for full logs.</details>

5. What is the default of `--tail` with `-l`, and with a Pod name?
<details><summary>Answer</summary>10 lines per container with a selector; all lines (`-1`) with a Pod name.</details>

6. Where are container logs on the node, and what limits their size?
<details><summary>Answer</summary>`/var/log/pods/<ns>_<pod>_<uid>/<container>/<restart-count>.log`, with links in `/var/log/containers/`. The kubelet rotates them: `containerLogMaxSize` (default 10Mi) and `containerLogMaxFiles` (default 5, live file included), checked every `containerLogMonitorInterval` (10s).</details>

7. Why can you not read the logs of a Pod you deleted a minute ago?
<details><summary>Answer</summary>The kubelet removes the log directory with the Pod, and the API server stores no logs. Save logs before deleting, or use a node-level agent that ships them off the node.</details>

8. How do you save the log of a Job named `pi` to `/opt/pi.txt`? And of a CronJob `tick`?
<details><summary>Answer</summary>`k logs job/pi > /opt/pi.txt`. A CronJob is not accepted by `kubectl logs`: use the log of a Job it created (`k logs job/<job-name>`) or run `k create job x --from=cronjob/tick` first.</details>

9. What do `--limit-bytes` and `--ignore-errors` do?
<details><summary>Answer</summary>`--limit-bytes=N` stops the output after N bytes, even in the middle of a line, which is useful for huge logs. `--ignore-errors` keeps going when one Pod of a selector cannot be read; the error is still printed but the other Pods are shown and the exit code is 0.</details>

10. `k logs -l app=shop -f` fails with `you are attempting to follow 7 log streams, but maximum allowed concurrency is 5`. Fix?
<details><summary>Answer</summary>`--max-log-requests=10` (any number of 7 or more). The default is 5 concurrent streams.</details>

11. How do you read the log of an init container, and which flag includes it automatically?
<details><summary>Answer</summary>`k logs POD -c INIT_NAME`. `--all-containers` includes init containers and native sidecars.</details>
