## 1. Why this matters

Kubernetes removes old API versions on a published schedule. A manifest that said `apiVersion: extensions/v1beta1` and applied fine years ago now fails on v1.37 with `no matches for kind "Ingress" in version "extensions/v1beta1"`, and so do the Helm charts, CI jobs and Git repos that still contain it. In real life this is what breaks after a cluster upgrade. A task may hand you an old manifest, so practise spotting the dead `apiVersion`, converting it to the current version, adding the fields the new version requires, and getting it to apply. This lesson teaches the policy behind removals, how to see what your cluster serves, how to read the warnings the API server sends, and how to migrate by hand (fast) or with the `kubectl convert` plugin (not available everywhere).

## 2. Concepts

### 2.1 What `apiVersion` means, and why versions exist

Every object starts with `apiVersion` and `kind`. The `apiVersion` has two parts: an **API group** and a **version**, written `group/version`. The old **core** group has no name, so its objects write just `v1` (Pod, Service, ConfigMap). Other groups write `apps/v1`, `batch/v1`, `networking.k8s.io/v1`. See [T2.01](../part2-basics/T2.01-kubernetes-architecture-and-the-api-model.md) for the full model.

Why are there versions at all? The API must change as people learn. A new version lets the project change a field name, make a field required, or change a default, without breaking everyone at once. Old and new versions are served side by side for a while, then the old one goes away. If versions did not exist, every API change would break every user on the day of the upgrade.

Source for the version levels and group syntax: [API overview](https://kubernetes.io/docs/reference/using-api/).

### 2.2 Maturity levels: alpha, beta, GA

The **version name** tells you how stable the API is. Three levels:

| Level | Name looks like | Enabled by default? | Can change or vanish? | Use it for |
|---|---|---|---|---|
| **Alpha** | `v1alpha1` | No. A built-in alpha API must be switched on in the kube-apiserver. | Yes, any release, without notice. | Short-lived test clusters only. |
| **Beta** | `v1beta1`, `v2beta3` | No for new beta APIs (beta APIs introduced before Kubernetes 1.22 were on by default, which is why so many old manifests used them). | The feature stays but details may change. A beta version has a limited lifetime (2.3). | Trying features; not production. |
| **GA** (also "stable") | `v1`, `v2` | Yes | A GA version stays available for the whole major version. There is no plan for a Kubernetes 2.0 that removes GA APIs. | Production. |

Source: [API overview](https://kubernetes.io/docs/reference/using-api/) ("Different API versions indicate different levels of stability and support").

**Two different things share the words alpha, beta, GA**: API *versions* (`v1beta1`) and *feature gates* (a switch for a feature, which also goes alpha, beta, GA). They are tracked separately. A beta feature gate can be on by default while the API version it uses is a beta version that is off by default. This lesson is about API versions.

### 2.3 The deprecation policy and removal timelines

The rules are in the [deprecation policy](https://kubernetes.io/docs/reference/using-api/deprecation-policy/). The ones you need (the policy calls the lifetime rule "Rule #4a"):

| Track | Minimum life | What it means in practice |
|---|---|---|
| **GA** (`v1`) | May be marked deprecated, but not removed within a major version. | A GA API you use today keeps working. |
| **Beta** (`v1beta1`) | Deprecated no more than **9 months or 3 minor releases** after introduction (whichever is longer). Stops being served **9 months or 3 minor releases** after deprecation (whichever is longer). | From the day a beta API is deprecated you have at least 3 releases (about 9 months) to move. |
| **Alpha** (`v1alpha1`) | May be removed in any release, with no deprecation notice. | Never depend on it. |

A new Kubernetes minor release arrives roughly every 4 months (3 per year), per the policy page.

Other rules worth knowing:
- **Rule 1**: API elements are only removed by incrementing the version of the API group. A field in `v1` stays in `v1`.
- **Rule 2**: objects must round-trip between versions without losing information. That is why the server can read an object stored as `v1beta1` and show it to you as `v1`.
- **Rule 3**: a version cannot be deprecated in favor of a less stable one. A beta cannot replace a GA.
- **Rule 4b**: the "preferred" and "storage" version of a group may not advance until a release has supported both the new and old version. This lets you upgrade and roll back.

**Deprecated vs removed.** These are two different states:
1. **Deprecated**: still works. The API server sends you a warning.
2. **Removed** ("no longer served"): the endpoint is gone. Requests fail.

Here is the policy's own example, shortened to a beta version. Time runs left to right (see also section 3):
- Release X+3: `v1beta1` is deprecated (warnings start).
- Releases X+4 and X+5: still served, still deprecated.
- Release X+6: `v1beta1` is removed.

### 2.4 Deprecation warnings from the API server

Since Kubernetes v1.19, when you send a request to a deprecated API, the server adds a **`Warning` HTTP response header** (RFC 7234). `kubectl` prints it. For API versions that are going away, the text has a fixed shape:

```text
Warning: <group>/<version> <Kind> is deprecated in v1.X+, unavailable in v1.Y+; use <group>/<newversion> <Kind>
```

Read it like this: "deprecated in v1.X+" means the version is deprecated from release X on. "unavailable in v1.Y+" means it will no longer be served from release Y on. "use ..." names the replacement. A real example from the Kubernetes warnings blog (an old Ingress): `networking.k8s.io/v1beta1 Ingress is deprecated in v1.19+, unavailable in v1.22+; use networking.k8s.io/v1 Ingress`. Source: [Warning: Helpful Warnings Ahead](https://kubernetes.io/blog/2020/09/03/warnings/).

A warning is not an error: the command succeeded. The risk is that the same manifest will fail after you upgrade past release Y. Treat a warning as a to-do item with a deadline.

Three more things the server does for a deprecated call (same blog and the policy page):
1. It adds the audit annotation `"k8s.io/deprecated":"true"` to the audit event.
2. It sets the gauge metric `apiserver_requested_deprecated_apis` to `1` (see 2.12).
3. `kubectl` can turn warnings into failures: `k apply -f x.yaml --warnings-as-errors` exits non-zero if the server returned any warning. Use it in CI. (Flag added in kubectl v1.19, same blog.)

**An important detail about removed APIs.** When an API version is *removed*, there is no warning, because there is no endpoint left to answer. `kubectl` asks the server for a list of served resources (discovery) before it sends your object. If your `apiVersion` and `kind` are not in that list, `kubectl` stops on the client side with `no matches for kind ... in version ...`. See section 6, row 1.

### 2.5 Finding the supported versions on your cluster

Never guess. Ask the cluster what it serves. Three commands:

| Command | What it answers | Example |
|---|---|---|
| `k api-versions` | Every `group/version` the server serves (one per line). | `k api-versions \| grep autoscaling` |
| `k api-resources` | Every resource kind, its short name, its group/version, whether it is namespaced, and its Kind. Add `-o wide` for verbs. | `k api-resources \| grep -i cronjob` |
| `k explain <kind> --api-version=<g/v>` | The schema (fields, types, which are required) of a kind in a **specific** version. | `k explain hpa --api-version=autoscaling/v2` |

Notes:
- `k api-versions` lists *served* versions only. A removed version such as `extensions/v1beta1` is simply missing from the list. That absence is your proof.
- `k api-resources` shows the **preferred** version for each kind. That is the version you should write in new manifests.
- `k explain` with no `--api-version` uses the preferred version. Add the flag when you need the fields of another served version, for example to compare `autoscaling/v1` and `autoscaling/v2`.
- You can also drill into a field: `k explain ingress.spec.rules.http.paths --api-version=networking.k8s.io/v1`. Fields marked `-required-` in the output must be present. For an Ingress path that includes `pathType`.

### 2.6 The Deprecated API Migration Guide

The official page lists, per release, what was removed and what to move to: [Deprecated API Migration Guide](https://kubernetes.io/docs/reference/using-api/deprecation-guide/). Open it in the exam; do not memorize it all. The entries that matter most for CKAD-style manifests:

| Removed in | Old `apiVersion` | Kind | Use instead | Notable changes (from the guide) |
|---|---|---|---|---|
| v1.16 | `extensions/v1beta1`, `apps/v1beta1`, `apps/v1beta2` | Deployment (also DaemonSet, StatefulSet, ReplicaSet) | `apps/v1` | `spec.selector` is required and immutable; `spec.rollbackTo` removed; `progressDeadlineSeconds` defaults to 600; `revisionHistoryLimit` to 10; `maxSurge`/`maxUnavailable` to 25%. |
| v1.22 | `extensions/v1beta1`, `networking.k8s.io/v1beta1` | Ingress | `networking.k8s.io/v1` | `spec.backend` becomes `spec.defaultBackend`; `serviceName` becomes `service.name`; numeric `servicePort` becomes `service.port.number`; string `servicePort` becomes `service.port.name`; `pathType` is required on every path (`Prefix`, `Exact`, `ImplementationSpecific`). |
| v1.22 | `apiextensions.k8s.io/v1beta1` | CustomResourceDefinition | `apiextensions.k8s.io/v1` | `spec.scope` must be set; `spec.version/validation/subresources` move under `spec.versions[*]`; schema must be structural. |
| v1.22 | `rbac.authorization.k8s.io/v1beta1`, `storage.k8s.io/v1beta1`, `certificates.k8s.io/v1beta1`, others | Role, ClusterRole, bindings, StorageClass, CSR, ... | the `v1` of the same group | CertificateSigningRequest: `spec.signerName` and `spec.usages` are required. |
| v1.25 | `batch/v1beta1` | CronJob | `batch/v1` | None notable. |
| v1.25 | `policy/v1beta1` | PodDisruptionBudget | `policy/v1` | In `v1`, an empty selector (`{}`) selects all Pods in the namespace; in `v1beta1` it selected none. |
| v1.25 | `policy/v1beta1` | PodSecurityPolicy | None: use Pod Security Admission (or a webhook) | The whole feature was removed. |
| v1.25 | `autoscaling/v2beta1` | HorizontalPodAutoscaler | `autoscaling/v2` | `targetAverageUtilization: 50` becomes `target: {type: Utilization, averageUtilization: 50}`. |
| v1.26 | `autoscaling/v2beta2` | HorizontalPodAutoscaler | `autoscaling/v2` | Same shape as the v1.25 note. |
| v1.26 | `flowcontrol.apiserver.k8s.io/v1beta1` | FlowSchema, PriorityLevelConfiguration | `flowcontrol.apiserver.k8s.io/v1beta2` (the guide's target at that release; today use `.../v1`) | None notable. |
| v1.27 | `storage.k8s.io/v1beta1` | CSIStorageCapacity | `storage.k8s.io/v1` | None. |
| v1.29 | `flowcontrol.apiserver.k8s.io/v1beta2` | FlowSchema, PriorityLevelConfiguration | `.../v1` | `assuredConcurrencyShares` renamed `nominalConcurrencyShares`. |
| v1.32 | `flowcontrol.apiserver.k8s.io/v1beta3` | FlowSchema, PriorityLevelConfiguration | `.../v1` | `nominalConcurrencyShares` defaults to 30 only when unset. |

The guide's last entry is **v1.32**. When this lesson was written (2026-10-28) the guide on kubernetes.io had no removal sections for v1.33 to v1.38. That means no new API *version* removals are listed after v1.32; the deprecations since then are of fields, features and the Endpoints resource (2.9). Confirm this on the live page before an exam (section 11).

The guide also tells you how to find your own usage ("Locate use of deprecated APIs": warnings, metrics, audit events) and how to test an upgrade: start a test API server with `--runtime-config=<group>/<version>=false` to simulate a removal.

### 2.7 The `kubectl convert` plugin

`kubectl convert` rewrites a manifest from one API version to another. It **used to be part of kubectl** and is now a **separate plugin binary** called `kubectl-convert`. kubectl finds any executable named `kubectl-<name>` on your `PATH` and runs it as `kubectl <name>`. If the binary is not there, you get: `error: unknown command "convert" for "kubectl"`.

**Install (Linux, from the official page [Install kubectl convert plugin](https://kubernetes.io/docs/tasks/tools/install-kubectl-linux/#install-kubectl-convert-plugin)).** The official page uses the latest stable release. I checked that the URL pattern exists for v1.37.1 (HTTP 200 for linux/amd64, linux/arm64, darwin/amd64, darwin/arm64). `stable.txt` returned `v1.37.1` on 2026-10-28.

```bash
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl-convert"
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl-convert.sha256"
echo "$(cat kubectl-convert.sha256) kubectl-convert" | sha256sum --check     # expect: kubectl-convert: OK
sudo install -o root -g root -m 0755 kubectl-convert /usr/local/bin/kubectl-convert
kubectl convert --help          # no error means it is installed
rm kubectl-convert kubectl-convert.sha256
```

Use `arm64` in place of `amd64` on ARM. Download the binary and its checksum from the **same** version. The exam hosts list `kubectl`, `yq`, `curl`, `wget` and `man` ([E9](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)). `kubectl-convert` is not on that list, so learn to migrate by hand (2.8) and treat the plugin as a bonus on your own machine.

**Use:**

```bash
k convert -f old.yaml --output-version apps/v1
k convert -f old-ingress.yaml --output-version networking.k8s.io/v1 > new-ingress.yaml
```

`-f` accepts a file, a directory or a URL. Output goes to stdout as YAML (add `-o json` for JSON). It does not edit the file in place; redirect it. Without `--output-version`, the plugin converts to the latest version it knows.

Things I saw when I ran `kubectl-convert` v1.37.0 offline (it needs no cluster). Input `old-deploy.yaml` is the old Deployment from section 4:

```text
REAL OUTPUT (kubectl-convert v1.37.0, offline, no cluster)
$ kubectl-convert -f old-deploy.yaml --output-version apps/v1
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: web
  name: web
spec:
  progressDeadlineSeconds: 2147483647
  replicas: 2
  revisionHistoryLimit: 2147483647
  selector:
    matchLabels:
      app: web
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
    type: RollingUpdate
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - image: nginx:1.27
        imagePullPolicy: IfNotPresent
        name: nginx
        ports:
        - containerPort: 80
          protocol: TCP
        resources: {}
        terminationMessagePath: /dev/termination-log
        terminationMessagePolicy: File
      dnsPolicy: ClusterFirst
      restartPolicy: Always
      schedulerName: default-scheduler
      securityContext: {}
      terminationGracePeriodSeconds: 30
status: {}
```

Read this output carefully; it teaches four things:
1. **It added the missing `spec.selector`**, built from the template labels. That is the rule the migration guide gives.
2. **It wrote the old defaults, not the new ones.** `progressDeadlineSeconds` and `revisionHistoryLimit` are `2147483647` (the old "never" behavior), and `maxSurge`/`maxUnavailable` are `1`, not the `25%` / `600` / `10` that a hand-written `apps/v1` Deployment gets. The official guide warns: "This conversion may use non-ideal default values." After converting, review and trim.
3. **It dumps every defaulted field** (`imagePullPolicy`, `terminationMessagePath`, `status: {}`). That is noise; delete what you do not need.
4. **It cannot convert everything.** See the HPA failure in section 6, row 5.

```text
REAL OUTPUT (kubectl-convert v1.37.0, offline, no cluster)
$ kubectl-convert -f old-ingress.yaml --output-version networking.k8s.io/v1
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  annotations:
    kubernetes.io/ingress.class: traefik
  name: web
spec:
  rules:
  - host: web.example.test
    http:
      paths:
      - backend:
          service:
            name: web
            port:
              number: 80
        path: /
        pathType: ImplementationSpecific
status:
  loadBalancer: {}
```

It renamed `serviceName`/`servicePort` to `service.name`/`service.port.number` and chose `pathType: ImplementationSpecific`, the value the guide says matches the undefined v1beta1 behavior. You probably want `Prefix` or `Exact`; decide yourself.

Asking for a group the kind does not belong to fails clearly:

```text
REAL OUTPUT (kubectl-convert v1.37.0, offline, no cluster)
$ kubectl-convert -f old-ingress.yaml --output-version apps/v1
networking.Ingress is not suitable for converting to "apps/v1" in scheme "pkg/api/legacyscheme/scheme.go:30"
```

### 2.8 Migrating by hand

Hand migration is the skill the exam rewards. The method is the same every time:

1. Read the **warning or error**. Note the kind and the old version.
2. Look up the **replacement version**: the guide (2.6), or `k api-resources | grep -i <kind>`, or `k explain <kind>` (its header shows `GROUP` and `VERSION`).
3. Change `apiVersion`.
4. Look up **what else changed** (guide, "Notable changes"; or `k explain <kind>.spec... ` and look for `-required-`).
5. `k apply --dry-run=server -f file.yaml`. The server validates fully without saving anything. Fix, repeat.
6. Apply for real.

The fastest hand path for most kinds is to let kubectl generate a current skeleton and move your values into it: `k create deploy ... $do`, `k create ingress ... $do`, `k create cronjob ... $do`, `k create pdb ... $do`. Section 4 has each one. For small edits, `yq` is on the exam hosts ([E9](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)); section 4 has tested one-liners.

**The four migrations to know cold:**

| Kind | From | To | What you must change |
|---|---|---|---|
| Deployment (also DaemonSet, StatefulSet, ReplicaSet) | `extensions/v1beta1` (no selector) | `apps/v1` | Add `spec.selector.matchLabels` that equals the Pod template labels. `apps/v1` requires it, and it cannot be changed later. |
| Ingress | `extensions/v1beta1` or `networking.k8s.io/v1beta1` | `networking.k8s.io/v1` | `backend.serviceName` to `backend.service.name`; `servicePort` to `backend.service.port.number` (or `.name`); add `pathType` to every path; `spec.backend` to `spec.defaultBackend`. |
| HPA | `autoscaling/v2beta1` | `autoscaling/v2` | Replace `targetAverageUtilization: N` with `target: {type: Utilization, averageUtilization: N}`. |
| CronJob / PDB | `batch/v1beta1` / `policy/v1beta1` | `batch/v1` / `policy/v1` | Only `apiVersion` (check the PDB empty-selector behavior change). |

**Why the selector rule exists.** In the old versions, if `spec.selector` was omitted, the API defaulted it from the template labels. That hidden default caused trouble when labels were edited. `apps/v1` removed the default and made the selector explicit and immutable. If you forget it, the server tells you (section 6, row 3).

**Ingress `pathType` explained.** It tells the controller how to match the path:

| `pathType` | Match rule | `/foo` matches | `/foo/bar` matches |
|---|---|---|---|
| `Exact` | The URL path must equal the path exactly (case-sensitive). | yes | no |
| `Prefix` | Matches by path elements split on `/`. Prefix `/foo` matches `/foo` and `/foo/bar` but not `/foobar`. | yes | yes |
| `ImplementationSpecific` | Up to the Ingress controller. | depends | depends |

`pathType` has no default in `networking.k8s.io/v1`; omitting it is rejected. (Source: the migration guide and [Ingress concepts](https://kubernetes.io/docs/concepts/services-networking/ingress/).)

**The Ingress class annotation.** Old Ingress manifests often have `kubernetes.io/ingress.class: <name>` in `metadata.annotations`. The Ingress docs call it the deprecated way and say the `spec.ingressClassName` field replaces it, but it is not a direct equivalent: the field refers to an IngressClass object. When you migrate, prefer `spec.ingressClassName`.

### 2.9 Current deprecations (v1.33 to v1.37)

None of these remove an API *version*; they deprecate a resource, a field, a CLI flag or an add-on. Each row cites the release blog.

| Release | What is deprecated | What you should do | Source |
|---|---|---|---|
| **v1.33** (2025-04-23) | The **v1 Endpoints API**. The API server warns when you read or write Endpoints: `Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice`. The type itself will probably not completely go away. | Use EndpointSlices (`k get endpointslices -l kubernetes.io/service-name=<svc>`). Do not write Endpoints in new manifests. | [Release blog](https://kubernetes.io/blog/2025/04/23/kubernetes-v1-33-release/) and [Endpoints to EndpointSlices](https://kubernetes.io/blog/2025/04/24/endpoints-deprecation/) |
| **v1.34** (2025-08-27) | `PreferClose` traffic distribution (replaced by newer values). Not related to manifests you migrate in this lesson; named so you recognise the pattern. | Use the newer `trafficDistribution` values in the Service docs. | [Release blog](https://kubernetes.io/blog/2025/08/27/kubernetes-v1-34-release/) |
| **v1.35** (2025-12-17) | `ipvs` mode of kube-proxy deprecated; ingress-nginx retirement announced; cgroup v1 support removed. | Use iptables or nftables for kube-proxy; use another Ingress controller (the labs here use Traefik). | [Release blog](https://kubernetes.io/blog/2025/12/17/kubernetes-v1-35-release/) |
| **v1.36** (2026-04-22) | **Service `.spec.externalIPs`**. You see deprecation warnings when it is used. Full removal is planned for v1.43. The field was a known security problem (CVE-2020-8554). | Do not use it. Use a LoadBalancer Service, NodePort, or Gateway API. | [Release blog](https://kubernetes.io/blog/2026/04/22/kubernetes-v1-36-release/) and [Deprecation and removal of Service ExternalIPs](https://kubernetes.io/blog/2026/05/14/kubernetes-v1-36-deprecation-and-removal-of-service-externalips/) |
| **v1.37** (2026-08-26) | **`kubectl run --filename/-f`**: the flag is being deprecated because the Pod is always built from CLI arguments like `NAME` and `--image`. | Do not use `k run -f`. Write a Pod manifest and `k apply -f`. | [Release blog](https://kubernetes.io/blog/2026/08/26/kubernetes-v1-37-release/) and [Sneak peek](https://kubernetes.io/blog/2026/07/31/kubernetes-v1-37-sneak-peek/) |
| **v1.37** | **`kube-dns`** (the old DNS add-on). CoreDNS has been the default since v1.13. The blog says no new packages are expected for kube-dns after v1.40. | If you still run `kube-dns`, migrate to CoreDNS. | [Release blog](https://kubernetes.io/blog/2026/08/26/kubernetes-v1-37-release/) |

Two clarifications so you do not mix things up:
- The **Service named `kube-dns`** in the `kube-system` namespace is a normal Service object. The deprecated item is the kube-dns *software*. I did not verify on a cluster whether CoreDNS keeps the Service name in v1.37 (section 11).
- The `EXTERNAL-IP` column in `k get svc` and the Node address type `ExternalIP` are **not** deprecated. Only the Service `.spec.externalIPs` field is.

Per the conventions file, labs here do not use `externalIPs`, `Endpoints` objects, or `k run -f`. When a lab touches Endpoints it is only to read the warning.

### 2.10 API-level vs field-level deprecation

| | API-level (a whole version or resource) | Field-level (one field inside a version) |
|---|---|---|
| Example | `extensions/v1beta1` Ingress; v1 Endpoints resource | `Service.spec.externalIPs`; Node `status.nodeInfo.kubeProxyVersion` (deprecated in v1.33 per the release blog) |
| How you spot it | Warning with `deprecated in ... unavailable in ...`, or `no matches for kind` once removed | A warning naming the field, or a `DEPRECATED` note in `k explain` output |
| What breaks | The manifest fails to apply after removal | Usually nothing: the policy says a field present in `v1` must exist and function until `v1` is removed, and GA `v1` APIs are not removed within a major version |
| What you do | Change `apiVersion` and migrate fields | Stop using the field; plan for the feature behind it to be switched off |

Why does the difference matter? A removed API version is a hard failure with a date. A deprecated field in a GA version may stay for years, but the *behavior behind it* can still be disabled (for example, `externalIPs` support is planned to be switched off in kube-proxy, v1.40 at the earliest and fully by v1.43 at the earliest, per the blog). Check `k explain <kind>.<field>` for the word DEPRECATED.

### 2.11 Under the hood

- **The server serves each `group/version` as its own REST path**: `/apis/networking.k8s.io/v1/...` (core group: `/api/v1/...`). `k api-versions` reads the discovery documents at `/api` and `/apis`.
- **One storage version per resource.** etcd stores each object once, in the group's *storage version*. When you read it as another served version, the server converts on the fly. That is Rule 2 (round-trip without loss). This is why live objects survive a version removal: they are stored in a version that still exists. What breaks is your *manifests*, which still name the dead version.
- **Removal = the path disappears.** The server stops registering the endpoint. `kubectl` fails at discovery lookup before sending anything.
- **Deprecation = the path still works, plus metadata.** The server adds the `Warning` header, the audit annotation and the metric (2.4, 2.12).
- **Upgrade rule of thumb.** Between your current version and the target version, read the guide entries for every release you cross. Move every manifest, chart and CI job off any version removed in that range before you upgrade.

### 2.12 The metric `apiserver_requested_deprecated_apis` (awareness)

The kube-apiserver exposes a gauge `apiserver_requested_deprecated_apis`. It is set to `1` when a request used a deprecated API. Labels: `group`, `version`, `resource`, `subresource`, and `removed_release` (the release in which the API stops being served). An administrator joins it with `apiserver_request_total` to see who is still calling deprecated APIs, for example:

```text
apiserver_requested_deprecated_apis{removed_release="1.22"} * on(group,version,resource,subresource) group_right() apiserver_request_total
```

(from the policy page). You can look at the raw metric as cluster admin: `k get --raw /metrics | grep apiserver_requested_deprecated_apis`. Expect this to print nothing on a v1.37 cluster that serves no deprecated API versions: the gauge is about deprecated *versions*. Whether the Endpoints warning (a deprecated resource in `v1`) also sets it is UNVERIFIED. The metric is for admins and monitoring. You do not need Prometheus for CKAD; you need to know it exists and what `removed_release` means.

### 2.13 Storage version migration (awareness)

Removing an API version from *serving* is separate from rewriting what is *stored* in etcd. The storage version of a resource can change (for example `v1beta1` to `v1`); objects written earlier stay in the old storage encoding until they are rewritten. The **StorageVersionMigration** API, `storagemigration.k8s.io/v1`, graduated to Stable and is **enabled by default in v1.37** ([v1.37 release blog](https://kubernetes.io/blog/2026/08/26/kubernetes-v1-37-release/), [feature blog](https://kubernetes.io/blog/2026/08/31/kubernetes-v1-37-storage-version-migration-ga/)). You create one object that names a resource, and a built-in controller rewrites every stored object of that resource to the current storage version. It is also used to re-encrypt data after an encryption-at-rest change. The task page shows the object:

```yaml
kind: StorageVersionMigration
apiVersion: storagemigration.k8s.io/v1
metadata:
  name: secrets-migration
spec:
  resource:
    group: ""
    resource: secrets
```

Source: [Migrate Kubernetes Objects Using Storage Version Migration](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/storage-version-migration/). That page checks success with `k wait --for=condition=Succeeded storageversionmigration.storagemigration.k8s.io/secrets-migration`. This is a cluster-admin task; for CKAD you only need to know it exists and that it does not change your manifests. It is not part of any lab here.

### 2.14 Related but different

- **Deprecated vs end-of-life Kubernetes version.** Old Kubernetes *releases* stop getting patches; that is a support policy, not an API deprecation.
- **`apiVersion` inside `scaleTargetRef`.** An HPA's `scaleTargetRef.apiVersion: apps/v1` names the version of the *target* Deployment. Migrating the HPA's own `apiVersion` does not change it. If your Deployment moved to `apps/v1`, update `scaleTargetRef.apiVersion` too.
- **`kubectl apply` vs `kubectl convert`.** `apply` sends the object to the server. `convert` only rewrites a file and never contacts the server.
- **Deprecated flags in kubectl** (like `k run -f`) follow a CLI rule: a GA kubectl element must keep working at least 12 months or 2 releases after its announced deprecation (policy Rule 5a) and must print a warning. A live example: `k autoscale --cpu-percent` prints `Flag --cpu-percent has been deprecated` on kubectl v1.37.1; use `--cpu=50%` (4.1).

## 3. How it works (diagram)

An ASCII timeline of API versions through their life, based on the policy page's worked example (X is the release that introduces the group). Each column is one release, about 4 months apart.

```text
 release ->   X        X+1      X+2      X+3      X+4      X+5      X+6      X+7      X+8
              |        |        |        |        |        |        |        |        |
 v1alpha1     served   REMOVED
 v1alpha2              served   REMOVED
 v1beta1                        served   DEPREC   DEPREC   DEPREC   REMOVED
 v1beta2                                 served   served   DEPREC   DEPREC   DEPREC   REMOVED
 v1                                                        served   served   served   served
                                                                    ^        ^
 storage / preferred: v1alpha1 v1alpha2 v1beta1 v1beta1  v1beta2  v1beta2  v1       v1       v1
                                                  ^                          ^
 server behavior:                         Warning headers begin     v1beta1 gone: `kubectl apply` of
                                          for v1beta1 (X+3)         a v1beta1 manifest fails (X+6)

 alpha: may vanish any release, no notice.
 beta:  at least 3 releases (about 9 months) between "deprecated" and "removed".
 GA:    deprecated at most, never removed inside the major version.
```

Walkthrough:
1. Alpha versions (`v1alpha1`) live one release and can be dropped with no notice. Do not use them for anything you keep.
2. A beta version (`v1beta1`) arrives at X+2. The next release (X+3) ships a newer beta (`v1beta2`), and `v1beta1` is marked **deprecated**: the server begins sending `Warning` headers.
3. GA `v1` appears at X+5. The beta versions it replaces stay deprecated for the rest of their window. `v1beta1` has been deprecated for three releases and is **removed at X+6**: from then on `kubectl apply` of a `v1beta1` manifest fails.
4. The column called "storage / preferred" moves only after a release that supported both the old and the new version (Rule 4b). That is why a rollback after an upgrade does not lose data.
5. Your action window is the deprecated span (X+3 to X+5 here). Fix manifests as soon as the first warning appears.

### 4.1 Imperative shortcuts

Generate a current, valid manifest and move your values into it. All of these use `$do` so nothing is created.

```bash
k create deploy web --image=nginx:1.27 --replicas=2 --port=80 $do > deploy.yaml   # apps/v1, selector already included
k create ingress web --class=traefik --rule="web.example.test/*=web:80" $do > ing.yaml   # networking.k8s.io/v1; trailing * on the path = pathType Prefix
k create cronjob hello --image=busybox:1.36 --schedule="*/5 * * * *" $do -- date > cj.yaml   # batch/v1
k create pdb web --selector=app=web --min-available=1 $do > pdb.yaml               # policy/v1
k autoscale deploy web --min=2 --max=5 --cpu=50% $do > hpa.yaml                    # needs a reachable cluster and an existing Deployment "web"; see note
```

The first four lines are client dry runs and create nothing. The last line (`k autoscale`) contacts the API server to look up the target Deployment, so it needs a cluster and a Deployment named `web` in the current namespace (for example after Step 5 of section 5).

Notes:
- `k create deploy` sets labels `app=web` and a matching `spec.selector.matchLabels` for you. That is the exact field the old manifest lacks.
- For `k create ingress`, a path ending in `*` means `pathType: Prefix`; without `*` it is `Exact` (kubectl help text). Run it with `$do` and check the `pathType` line before you trust it. The exact YAML is not captured here (section 11).
- `k autoscale` is a shortcut for simple resource targets (`--cpu`, and `--memory` per `k autoscale --help`). If a task needs other metric types, a `behavior` block or anything the flags cannot express, write the `autoscaling/v2` YAML by hand (below). Which version `k autoscale` writes was not captured here (section 11).
- Use `--cpu=50%`, not `--cpu-percent=50`. On kubectl v1.37.1 the old flag is itself deprecated (output below, which I captured). This is a live example of a CLI deprecation (2.14): kubectl accepts the old flag but warns, and `--cpu` is the replacement.
- `k explain <kind> | head -5` shows `GROUP` and `VERSION` of the preferred version in one second.


### 4.2 Old Deployment to `apps/v1`

The old manifest. It does **not** apply on v1.37 (that is the point):

```yaml
# old-deploy.yaml  -- extensions/v1beta1 was removed in Kubernetes v1.16 (apps/v1 since v1.9)
apiVersion: extensions/v1beta1     # REMOVED group/version -> "no matches for kind"
kind: Deployment
metadata:
  name: web
  labels:
    app: web
spec:
  replicas: 2
  # no spec.selector: the old API defaulted it from the template labels
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - containerPort: 80
```

The migrated manifest. It applies cleanly (namespace `lab-t321`):

```yaml
# deploy.yaml
apiVersion: apps/v1                # GA group/version; the only valid one for Deployment today
kind: Deployment                   # unchanged
metadata:
  name: web                        # object name, unchanged
  labels:
    app: web                       # labels on the Deployment itself; not used for selecting Pods
spec:
  replicas: 2                      # desired Pod count; defaults to 1 if omitted
  selector:                        # NEW and REQUIRED in apps/v1; immutable after creation
    matchLabels:
      app: web                     # must match template.metadata.labels exactly, or the API rejects it
  template:
    metadata:
      labels:
        app: web                   # labels given to every Pod; the selector above finds Pods by these
    spec:
      containers:
      - name: nginx
        image: nginx:1.27          # pinned tag, never :latest
        ports:
        - containerPort: 80        # informational; does not open or close a port
```

The same change with `yq` (REAL tool, yq v4.54.1, run on the old file; I applied only these two edits and the output was the old file with the two changes):

```bash
cp old-deploy.yaml deploy.yaml
yq -i '.apiVersion = "apps/v1" | .spec.selector.matchLabels.app = "web"' deploy.yaml
```

```text
REAL OUTPUT (yq v4.54.1) - first lines of deploy.yaml after the command
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels:
    app: web
spec:
  replicas: 2
  template:
    ...
```

(`yq` adds the new `selector` key at the end of `spec`, after `template`. Key order does not matter to the API. Check with `grep -n -A2 selector deploy.yaml`.)

### 4.3 Old Ingress to `networking.k8s.io/v1`

Old (does not apply):

```yaml
# old-ingress.yaml
apiVersion: extensions/v1beta1     # REMOVED in v1.22; networking.k8s.io/v1beta1 was removed too
kind: Ingress
metadata:
  name: web
  annotations:
    kubernetes.io/ingress.class: traefik     # old way to pick a controller
spec:
  rules:
  - host: web.example.test
    http:
      paths:
      - path: /
        backend:
          serviceName: web         # renamed
          servicePort: 80          # renamed and restructured
```

New (applies cleanly; no Ingress controller is needed to create the object):

```yaml
# ing.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: traefik        # replaces the kubernetes.io/ingress.class annotation; names an IngressClass (need not exist yet)
  rules:
  - host: web.example.test         # optional; omit to match any host
    http:
      paths:
      - path: /                    # URL path to match
        pathType: Prefix           # REQUIRED in v1: Exact | Prefix | ImplementationSpecific
        backend:
          service:                 # NEW nesting: backend now names a Service ...
            name: web              # was backend.serviceName
            port:
              number: 80           # was backend.servicePort (a number). Use `name: http` for a named port.
```

Edit with `yq` (REAL tool, yq v4.54.1 on the old file; it also changes the backend and adds `pathType`):

```bash
cp old-ingress.yaml ing.yaml
yq -i '.apiVersion = "networking.k8s.io/v1"
  | .spec.rules[0].http.paths[0].pathType = "Prefix"
  | .spec.rules[0].http.paths[0].backend = {"service": {"name": "web", "port": {"number": 80}}}' ing.yaml
```

```text
REAL OUTPUT (yq v4.54.1) - ing.yaml after the command

kind: Ingress
metadata:
  name: web
  annotations:
    kubernetes.io/ingress.class: traefik
spec:
  rules:
    - host: web.example.test
      http:
        paths:
          - path: /
            backend:
              service:
                name: web
                port:
                  number: 80
            pathType: Prefix
```

Note that `yq` left the annotation in place. It still applies; swap it for `spec.ingressClassName` when you have time.

### 4.4 Old HPA to `autoscaling/v2`

```yaml
# hpa.yaml  (v2beta1 had `targetAverageUtilization: 50` under `resource:`)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:                  # what to scale
    apiVersion: apps/v1            # the TARGET's version (not the HPA's)
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:                      # NEW structure
        type: Utilization          # Utilization | AverageValue | Value

```

```bash

  | .spec.metrics[0].resource.target = {"type":"Utilization","averageUtilization":50}
  | del(.spec.metrics[0].resource.targetAverageUtilization)' old-hpa-v2beta1.yaml
```

## 6. Common mistakes and how to fix them

| # | Symptom | What you will see (exact text) | Cause | Fix (command) |
|---|---|---|---|---|
| 1 | `k apply` fails on an old Ingress or Deployment | `error: resource mapping not found for name: "web" namespace: "..." from "old-ingress.yaml": no matches for kind "Ingress" in version "extensions/v1beta1"` followed by `ensure CRDs are installed first` | The `apiVersion` was removed from the server. `extensions/v1beta1` Ingress was removed in v1.22; Deployment in v1.16. | `k api-resources \| grep -i ingress`, then set `apiVersion: networking.k8s.io/v1` and fix the fields (2.8). Re-test with `k apply --dry-run=server -f`. |
| 2 | `kubectl convert` does not exist | `error: unknown command "convert" for "kubectl"` | `convert` is a separate plugin binary `kubectl-convert`, not installed by default. | Install it (2.7), or migrate by hand (2.8). Check with `command -v kubectl-convert`. |
| 3 | Migrated Deployment rejected | `The Deployment "web" is invalid: spec.selector: Required value` | `apps/v1` requires `spec.selector`. The old API defaulted it. | Add `selector.matchLabels` that equals `template.metadata.labels`. The server may print row 4's second line together with this one; the same fix clears both. |
| 4 | Selector present but still rejected | `... spec.template.metadata.labels: Invalid value: map[string]string{...}: `selector` does not match template `labels`` | `matchLabels` has a key or value the template labels do not have. | Make every `matchLabels` pair appear in `template.metadata.labels`. |
| 5 | `kubectl-convert` fails on an HPA | `error: unable to decode "old-hpa.yaml": no kind "HorizontalPodAutoscaler" is registered for version "autoscaling/v2beta1" in scheme "pkg/api/legacyscheme/scheme.go:30"` | The plugin only knows versions still built into its scheme. The HPA beta versions are not. The version string in the message is whatever `apiVersion` the file contains (`v2beta1` for the `old-hpa.yaml` of 4.6; I reproduced it with `v2beta1`). | Migrate by hand (4.4). |
| 6 | Ingress rejected after renaming `apiVersion` only | text not captured: expect a message about `pathType` being required, or unknown fields `serviceName`/`servicePort` | `networking.k8s.io/v1` requires `pathType` and uses `backend.service.name` and `backend.service.port`. | Apply 4.3. Use `k explain ingress.spec.rules.http.paths` to see required fields. |
| 7 | Changing an existing Deployment's selector | text not captured: expect `spec.selector: Invalid value: ...: field is immutable` | `spec.selector` is immutable in `apps/v1`. The live Deployment has the selector it was created with. | Use the existing template labels as the selector (the guide says so). To change it for real, delete and recreate the Deployment. |
| 8 | Warning ignored, breaks on upgrade | `Warning: ... is deprecated in v1.X+, unavailable in v1.Y+; use ...` | The manifest still uses a deprecated version. | Fix now. In CI, use `k apply -f ... --warnings-as-errors`. |

### 6.1 How to diagnose a failed apply (repeatable path)

Run these in order. Each step narrows the cause.

1. **Read the first line of the error.** `no matches for kind ... in version ...` is a removed or misspelled `apiVersion`/`kind`. `is invalid:` followed by a field path is a schema or validation error from the server. `unknown field` means the field name belongs to another version.
2. **Is the pair served?** `k api-versions | grep <group>` and `k api-resources | grep -i <kind>`. If the group/version is not in `api-versions`, it is removed (or you misspelled it). The `api-resources` line gives the replacement.
3. **What does the new version require?** `k explain <kind>.spec --api-version=<g/v>` and drill down. Look for `-required-` fields. Also check the migration guide row for that kind.
4. **Server dry-run until clean.** `k apply --dry-run=server -f file.yaml`. Server dry-run runs real validation, which client dry-run does not.
5. **Apply, then verify.** `k get <kind> <name> -o yaml | head` and, for a Deployment, `k rollout status`.

**Row 1 in detail.** The error appears before kubectl sends your object. Proof: `k apply --dry-run=server` fails the same way with no cluster change. Read `kind` and `version` in the quoted text, not the object name. Fix the version, then follow step 3.

**Row 3 vs row 7.** Row 3 happens for a *new* Deployment. Row 7 happens when the Deployment already exists in the cluster (it was created long ago). Check which case you are in: `k get deploy web -o jsonpath='{.spec.selector}'`. If the live selector is already `{"matchLabels":{"app":"web"}}`, write exactly that in the file.

**Row 5 in detail.** The `kubectl-convert` error names the version it cannot decode. This is not your mistake. Do the manual rename in 4.4. After migration, the plugin does not need to run again.

## 8. Exam tips

- **Do not trust a manifest you were handed.** First look at `apiVersion` and `kind`. Run `k apply --dry-run=server -f file.yaml` before anything else. It shows removal and validation errors in one second and creates nothing.
- **Use the docs the exam allows.** Open the [Deprecated API Migration Guide](https://kubernetes.io/docs/reference/using-api/deprecation-guide/) for the per-kind field changes, and the [deprecation policy](https://kubernetes.io/docs/reference/using-api/deprecation-policy/) if a question is about timelines. kubernetes.io/docs and kubernetes.io/blog are allowed ([E13](https://docs.linuxfoundation.org/tc-docs/certification/certification-resources-allowed)).
- **Do not rely on `kubectl-convert`.** The documented exam-host tools are kubectl, yq, curl, wget and man ([E9](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)). Practice the hand migration; the install page is [Install kubectl convert plugin](https://kubernetes.io/docs/tasks/tools/install-kubectl-linux/#install-kubectl-convert-plugin) if you ever need it (and whether you can download it on the exam host is UNVERIFIED).
- **Generate instead of editing.** `k create deploy|ingress|cronjob|pdb ... $do` gives you the current version and the required fields; paste your values in. It is often faster than editing an old file.
- **Check the second failure.** After the first fix you usually get a second error (selector, `pathType`, HPA target). Read it and fix it before you conclude the file is wrong. Check traps before moving on: selector equals template labels; `pathType` on every path; `backend.service.name` and `.port.number`; HPA `target` block.
- **Finish by verifying.** `k get <kind> <name>` plus `k rollout status` for a Deployment. A task that says "must be running" is not done at `created`.

## 9. Quick review

1. What is the minimum time a beta API must be served after it is deprecated?
2. Which command shows every `group/version` the cluster serves?
3. How do you see the fields of an HPA in `autoscaling/v2` only?
4. Why does a removed API produce no `Warning` header?
5. Which field must you add when you move an `extensions/v1beta1` Deployment to `apps/v1`, and what must it equal?
6. Name the three changes to make an old Ingress valid in `networking.k8s.io/v1`.
7. Which command converts `old.yaml` to `apps/v1`, and what do you see if the plugin is missing?
8. Is `Service.spec.externalIPs` an API-level or a field-level deprecation? In which release was it deprecated?
9. What does the metric `apiserver_requested_deprecated_apis` tell an administrator, and what is the label `removed_release`?
10. What is storage version migration, and which release enabled it by default?

<details><summary>Answers</summary>

1. 9 months or 3 minor releases, whichever is longer (policy Rule 4a). Alpha has no guarantee; GA is not removed within the major version.
2. `k api-versions` (and `k api-resources` for the kinds and their preferred versions).
3. `k explain hpa --api-version=autoscaling/v2` (drill down with `hpa.spec.metrics.resource.target`).
4. Because the endpoint no longer exists. The failure happens in kubectl's discovery lookup (`no matches for kind ...`) before any request reaches the server. A warning only comes from a deprecated but still served version.
5. `spec.selector.matchLabels`; it must match `spec.template.metadata.labels`. It is immutable after creation.
6. `apiVersion: networking.k8s.io/v1`; `backend.serviceName`/`servicePort` become `backend.service.name`/`backend.service.port.number` (or `.name`); each path needs `pathType` (`spec.backend` also becomes `spec.defaultBackend`).
7. `k convert -f old.yaml --output-version apps/v1`. Without the plugin: `error: unknown command "convert" for "kubectl"`.
8. Field-level (the Service `v1` API stays). Deprecated in v1.36; the release notes plan removal in v1.43.
9. Whether anything is still calling a deprecated API (gauge is `1`), broken down by group, version, resource, subresource. `removed_release` is the Kubernetes release in which that API stops being served.
10. It is the `storagemigration.k8s.io/v1` API, which makes the control plane rewrite stored objects to the current storage version (also used to re-encrypt). Stable and enabled by default in v1.37.

</details>
