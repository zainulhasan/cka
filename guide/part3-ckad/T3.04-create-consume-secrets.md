## 1. Why this matters

Applications need passwords, API tokens and TLS private keys. A **Secret** is the Kubernetes object that holds them, so they do not live in the image or in the Pod manifest. In real life the dangerous part is the false sense of safety: by default a Secret is only **base64-encoded** (a reversible text encoding, not encryption), and anyone who can `get` it, or can create a Pod in its namespace, can read it. "Create a Secret and inject it into a Pod" belongs to the Application Environment, Configuration and Security domain (25% of the CKAD curriculum), so practise it until it is fast. The exam averages about 6 minutes per task (15-20 tasks in 2 hours; sources: [E2](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad), [E3](https://docs.linuxfoundation.org/tc-docs/certification/faq-cka-ckad-cks)). The common slips are small ones: a trailing newline in the value, a wrong key name in `secretKeyRef`, or a `defaultMode` written as `400` instead of `0400`.

## 2. Concepts

### 2.1 What a Secret is, and the problem it solves

A **Secret** is a namespaced API object (`apiVersion: v1`, `kind: Secret`) that stores a small amount of confidential data as key-value pairs. A key is a short name such as `password`. A value is a string or binary data.

Without Secrets you have two bad options. You can bake the password into the image (anyone who can pull the image has it, and changing it means a rebuild), or you can write it in plain text in every Pod spec (it then lives in your Git history and in every `kubectl get pod -o yaml`). A Secret separates the jobs: the image holds code, the Secret holds the credential, and the Pod spec only says "take it from there". Because a Secret is its own object, you can also give it its own access rules (RBAC) and its own storage protection.

| Fact | Detail |
|---|---|
| Scope | Namespaced. The Pod and the Secret must be in the same namespace. |
| Object name | A valid DNS subdomain name (lowercase letters, digits, `-` and `.`). |
| Size limit | 1 MiB (1,048,576 bytes) per Secret. The API server adds up the length of all values and rejects a bigger object. Large files do not belong in a Secret. |
| Key names | Letters, digits, `-`, `_` and `.` only (same rule as ConfigMap keys). A key becomes a file name in a volume. |
| Top-level fields | `data`, `stringData`, `type`, `immutable`. There is no `spec`. |
| `type` | Optional. If you omit it, the server sets `Opaque`. After creation the type cannot be changed (section 2.3). |

**Related but different: Secret vs ConfigMap.** The API shape and the four ways to consume them are almost identical (see [T3.03](../part3-ckad/T3.03-configmaps.md)). The differences are about handling, not syntax:

| | ConfigMap | Secret |
|---|---|---|
| Intended content | Non-confidential settings | Credentials, tokens, keys |
| Values in the API | Plain text in `data` | Base64 text in `data` (plus write-only `stringData`) |
| Binary data field | `binaryData` | None: `data` is already base64, so it carries binary values |
| Types | None | Yes (`type`), and the API validates the keys of some types |
| Volume on the node | Written to the node's disk | Written to **tmpfs** (memory) so it is not left on the node disk |
| Kubelet access | Reads the ConfigMaps of Pods on its node | Same, and the control plane limits each node to the Secrets of Pods scheduled on it (Node authorizer) |
| Common protections | RBAC | RBAC, encryption at rest, `kubectl describe` hides values |

**Related but different: Secret vs ServiceAccount token.** Every Pod automatically gets a short-lived token for the Kubernetes API through a projected volume. That token is requested by the kubelet from the API (the TokenRequest API), it is not stored as a Secret, and you do not create it. A Secret of type `kubernetes.io/service-account-token` is the old, long-lived form (section 2.3).

### 2.2 Under the hood

Knowing who does what explains every "my Secret does not arrive" symptom.

1. **API server.** `kubectl create secret` sends a `Secret` object. The API server validates the key names, the size and (for typed Secrets) the required keys. It converts `stringData` into `data` (section 2.5), stores the object in **etcd** (the cluster database) and does nothing else. It never pushes the data into Pods.
2. **Storage.** By default etcd stores the Secret **unencrypted**. The base64 you see in YAML and JSON is only how the API shows binary data in a text format. It is not a protection. Encryption at rest is an API server option (an `EncryptionConfiguration` file); you configure it in the CKA track (T4.10).
3. **Scheduler and controllers** do not care about Secrets. A Pod that references a missing Secret is still scheduled to a node.
4. **Kubelet** (the agent on the node) does the work. Before it starts a container, it reads every Secret the Pod references. The control plane only lets a node read Secrets that belong to Pods scheduled on that node.
   - **Env vars** (`env.valueFrom.secretKeyRef`, `envFrom.secretRef`): the kubelet decodes the values and passes them to the container runtime as the process environment each time it starts the container. A process environment is fixed when the process starts, so a running process never sees a new value.
   - **Volumes** (`volumes[].secret`): the kubelet mounts a **tmpfs** (a file system that lives in RAM) at the volume's directory and writes one file per key into it. The data is never written to the node's disk, and it disappears when the Pod is removed. The kubelet keeps watching the Secret and rewrites the files after a change (up to about a minute later). Like ConfigMaps, the kubelet writes a new timestamped directory and switches a `..data` symlink atomically, and each key is a symlink to `..data/<key>`. A `subPath` mount bypasses this and never updates.
5. **A failing reference blocks the container, not the Pod object.** If the Pod points at a Secret or key that does not exist, the kubelet cannot build the container. It reports `CreateContainerConfigError` (env reference) or keeps the Pod in `ContainerCreating` with a `FailedMount` event (volume reference), and retries. When the missing object appears, the Pod recovers by itself (section 6).

### 2.3 Secret types

The `type` field tells Kubernetes (and tools) what the Secret is for. For some types the API server checks that the required keys exist, so a wrong key name is rejected at creation time instead of failing later in the application.

| Type | Use | Required keys (checked by the API) | Created by |
|---|---|---|---|
| `Opaque` | Anything. The default. | None | `k create secret generic` |
| `kubernetes.io/tls` | A certificate and its private key (Ingress, Gateway, your own server) | `tls.crt`, `tls.key` | `k create secret tls` |
| `kubernetes.io/dockerconfigjson` | Credentials for a private image registry | `.dockerconfigjson` | `k create secret docker-registry` |
| `kubernetes.io/basic-auth` | A username and password | at least one of `username`, `password` | `k create secret generic --type=kubernetes.io/basic-auth` |
| `kubernetes.io/ssh-auth` | An SSH private key | `ssh-privatekey` | `k create secret generic --type=kubernetes.io/ssh-auth` |
| `kubernetes.io/service-account-token` | A long-lived API token for a ServiceAccount (legacy) | annotation `kubernetes.io/service-account.name`; the control plane fills `token`, `ca.crt`, `namespace` | You write YAML |

Other types exist and you will meet them: `kubernetes.io/dockercfg` (the old registry format), `bootstrap.kubernetes.io/token` (used by kubeadm for node joins). A type string you invent yourself (for example `example.com/api-key`) is allowed and not validated.

**The type cannot be changed later.** If you created a certificate as `Opaque` and an Ingress needs `kubernetes.io/tls`, you must delete and recreate the Secret (break-fix lab).

Runnable examples, one per type. Run them in a scratch namespace; section 5 uses the same names:

```bash
k create ns lab-t304; k config set-context --current --namespace=lab-t304
mkdir -p ~/lab/t304 && cd ~/lab/t304
```

```bash
# Opaque (the default type)
k create secret generic db --from-literal=user=app --from-literal=password='S3cr3t!'

# basic-auth (the API only checks that username or password exists)
k create secret generic site-login --type=kubernetes.io/basic-auth \
  --from-literal=username=admin --from-literal=password='t0p'

# ssh-auth (the key MUST be stored under the name ssh-privatekey)
printf 'FAKE-KEY-FOR-DEMO\n' > id_rsa
k create secret generic deploy-key --type=kubernetes.io/ssh-auth --from-file=ssh-privatekey=id_rsa

# dockerconfigjson and tls: sections 2.4 and 5
```

Delete the namespace when you are done experimenting (`k delete ns lab-t304; k config set-context --current --namespace=default`); section 5 recreates it.

**A ServiceAccount token Secret** is the one type you cannot create with a `kubectl create secret` subcommand. Since Kubernetes 1.24 the control plane no longer creates these automatically; tokens for Pods come from the TokenRequest API instead, and for a one-off token you run `k create token <sa>` (time-limited). Create the long-lived form only when an external tool really needs a token that never expires:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: builder
  namespace: lab-t304
---
apiVersion: v1
kind: Secret
metadata:
  name: builder-token
  namespace: lab-t304
  annotations:
    kubernetes.io/service-account.name: builder   # which ServiceAccount the token is for
type: kubernetes.io/service-account-token
```

EXPECTED OUTPUT (not captured)

```
$ k apply -f sa-token.yaml
serviceaccount/builder created
secret/builder-token created
$ k get secret builder-token -o jsonpath='{.data}' | head -c 80
{"ca.crt":"LS0tLS1CRUdJTi...","namespace":"bGFiLXQzMDQ=","token":"ZXlK...
```

The token controller fills `token`, `ca.crt` and `namespace` within a second or two. A leaked token of this kind is valid until you delete the Secret, which is why it is discouraged.

### 2.4 Creating Secrets imperatively

`kubectl create secret` has three subcommands: `generic`, `tls` and `docker-registry`. This is the real list from the v1.37.1 client:

REAL OUTPUT (kubectl v1.37.1 client, --dry-run=client, no cluster)

```
$ k create secret -h
...
Available Commands:
  docker-registry   Create a secret for use with a Docker registry
  generic           Create a secret from a local file, directory, or literal value
  tls               Create a TLS secret
```

There is no `basic-auth` or `ssh-auth` subcommand: use `generic --type=...` (above). Add `$do` to any command to print the object instead of creating it.

**`generic`: three data sources.** You can mix them in one command, and you can repeat each flag.

| Flag | What it reads | Resulting key | Resulting value |
|---|---|---|---|
| `--from-literal=KEY=value` | The text you type | `KEY` | `value` (no newline added) |
| `--from-file=path` | One file | The **file name** (without the directory) | The whole file content, **including its final newline** |
| `--from-file=key=path` | One file | The `key` you choose | The whole file content |
| `--from-file=dir/` | Every regular file directly in the directory (subdirectories and symlinks are ignored) | Each file name | Each file content |
| `--from-env-file=path` | A file of `KEY=value` lines | Each `KEY` | Each `value` |
| `--type=...` | n/a | n/a | Sets the Secret `type` (default: none given, server sets `Opaque`) |
| `--append-hash` | n/a | n/a | Adds a hash of the content to the name, for rolling updates |

The three methods from the task entry, with real output (the `.data` map as JSON):

REAL OUTPUT (kubectl v1.37.1 client, --dry-run=client, no cluster)

```
$ k create secret generic db --from-literal=user=app --from-literal=password='S3cr3t!' $do
apiVersion: v1
data:
  password: UzNjcjN0IQ==
  user: YXBw
kind: Secret
metadata:
  name: db

$ printf 'S3cr3t!\n' > pw.txt          # a file as an editor or echo would write it
$ k create secret generic f1 --from-file=pw.txt --dry-run=client -o jsonpath='{.data}'
{"pw.txt":"UzNjcjN0IQo="}              # key = file name; note the final "o=" vs "==": a newline is inside

$ printf 'S3cr3t!' > pw-nonl.txt
$ k create secret generic f1 --from-file=password=pw-nonl.txt --dry-run=client -o jsonpath='{.data}'
{"password":"UzNjcjN0IQ=="}            # key chosen with key=path; no newline inside

$ printf 'user=app\n# a comment\npassword=S3cr3t!\n' > db.env
$ k create secret generic e1 --from-env-file=db.env $do
apiVersion: v1
data:
  password: UzNjcjN0IQ==
  user: YXBw
kind: Secret
metadata:
  name: e1
```

(`$do` already contains `-o yaml`, so for a `jsonpath` view write `--dry-run=client -o jsonpath=...` instead of adding `-o` after `$do`.) Details that matter:

- **`--from-file` uses the file name as the key.** `--from-file=pw.txt` gives a key called `pw.txt`, not `password`. If a Pod expects `password`, use `--from-file=password=pw.txt`.
- **`--from-env-file` splits the file into many keys.** It skips blank lines and `#` comment lines. `--from-file=db.env` instead makes ONE key `db.env` holding the whole file.
- **`--from-literal` adds no newline; `--from-file` keeps every byte of the file**, including the newline most editors and `echo` add. That newline is mistake 1 in section 6.
- **Quote literals with single quotes.** The shell expands `$`, backticks and `!` in double quotes (mistake 3 in section 6).

**`tls`: certificate and key.** `k create secret tls NAME --cert=tls.crt --key=tls.key` reads two PEM files, checks that they look like a certificate and a private key, and stores them under the fixed keys `tls.crt` and `tls.key` with type `kubernetes.io/tls`. Real certificates (made with `openssl req -x509`, see [T1.12](../part1-linux/T1.12-tls-pki-and-openssl-for-kubernetes.md)):

REAL OUTPUT (OpenSSL 4.1.0, macOS host)

```
$ openssl req -x509 -newkey rsa:2048 -nodes -keyout tls.key -out tls.crt -days 365 \
    -subj "/CN=web.example.com" -addext "subjectAltName=DNS:web.example.com"
.+......+.+...+...+.....+.......+..+......+...+++++++++++++++++++++++++*...
-----
$ openssl x509 -in tls.crt -noout -subject -ext subjectAltName -dates
subject=CN=web.example.com
X509v3 Subject Alternative Name:
    DNS:web.example.com
notBefore=Oct 28 03:08:42 2026 GMT
notAfter=Oct 28 03:08:42 2027 GMT
```

REAL OUTPUT (kubectl v1.37.1 client, --dry-run=client, no cluster)

```
$ k create secret tls web-tls --cert=tls.crt --key=tls.key $do | cut -c1-90
apiVersion: v1
data:
  tls.crt: LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0tLS0tCk1JSURFRENDQWZpZ0F3SUJBZ0lVVnBoQVZ2cml5dFl
  tls.key: LS0tLS1CRUdJTiBQUklWQVRFIEtFWS0tLS0tCk1JSUV2UUlCQURBTkJna3Foa2lHOXcwQkFRRUZBQVN
kind: Secret
metadata:
  name: web-tls
type: kubernetes.io/tls

$ k create secret tls web-tls --cert=tls.crt --key=tls.key --dry-run=client -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -subject
subject=CN=web.example.com

$ k create secret tls bad --cert=tls.key --key=tls.crt $do
error: tls: failed to find certificate PEM data in certificate input, but did find a private key; PEM inputs may have been switched
```

Read the first value: `LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0tLS0t` is the base64 of `-----BEGIN CERTIFICATE-----`. That is how you recognize a certificate in a Secret without decoding all of it. The last command shows the client catching swapped `--cert` and `--key` arguments before anything reaches the cluster.

**`docker-registry`: private registry login.** It builds a `.dockerconfigjson` document (the same JSON shape as `~/.docker/config.json`) and stores it with type `kubernetes.io/dockerconfigjson`.

| Flag | Default | Meaning |
|---|---|---|
| `--docker-server` | `https://index.docker.io/v1/` | Registry host the credentials belong to. The kubelet uses it to pick the right login for an image. |
| `--docker-username` | none | User name. |
| `--docker-password` | none | Password or access token. Single-quote it. |
| `--docker-email` | none | Optional e-mail. |
| `--from-file=path` | none | Use an existing Docker config file instead of the four flags above. The key is always `.dockerconfigjson`. |

REAL OUTPUT (kubectl v1.37.1 client, --dry-run=client, no cluster)

```
$ k create secret docker-registry regcred --docker-server=registry.example.com \
    --docker-username=bob --docker-password='pw' --docker-email=bob@example.com $do
apiVersion: v1
data:
  .dockerconfigjson: eyJhdXRocyI6eyJyZWdpc3RyeS5leGFtcGxlLmNvbSI6eyJ1c2VybmFtZSI6ImJvYiIsInBhc3N3b3JkIjoicHciLCJlbWFpbCI6ImJvYkBleGFtcGxlLmNvbSIsImF1dGgiOiJZbTlpT25CMyJ9fX0=

metadata:
  name: regcred

$ k create secret docker-registry regcred --docker-server=registry.example.com --docker-username=bob \
```

Notice `"auth":"Ym9iOnB3"`: it is `base64("bob:pw")`. Even the "encoded" login is just the password again.

### 2.5 `data` (base64) vs `stringData` (plain, write-only)

The `data` field holds **base64-encoded** values. **Base64** is a way to write any bytes using 64 safe text characters (`A-Z a-z 0-9 + /`, padded with `=`). It exists so that binary data (a certificate, a key) can travel inside JSON. It is **not** encryption: anyone can reverse it with `base64 -d`.

The `stringData` field is a convenience for writing manifests by hand. You put **plain text** values in it; the API server base64-encodes them and merges them into `data` when it stores the object.

| | `data` | `stringData` |
|---|---|---|
| You write | Base64 text | Plain text |
| Stored as | As written | Converted into `data`, the `stringData` field is not stored |
| Returned by `k get -o yaml` | Yes (base64) | **Never**: write-only |
| If the same key is in both | Overwritten by `stringData` | Wins |
| Risk | A value that is not valid base64 is rejected | Plain text sits in your manifest file and, with `k apply`, in the `last-applied-configuration` annotation (see below) |

A complete Secret manifest using both:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
  namespace: lab-t304
type: Opaque
data:
  user: YXBw                  # base64 of "app"  (echo -n app | base64)
stringData:
  password: S3cr3t!           # plain text; the server stores it base64-encoded under data.password
```

EXPECTED OUTPUT (not captured)

```
$ k apply -f app-secret.yaml
secret/app-secret created
$ k get secret app-secret -o yaml
apiVersion: v1
data:
  password: UzNjcjN0IQ==      # stringData was merged into data
  user: YXBw
kind: Secret
metadata:
  annotations:
    kubectl.kubernetes.io/last-applied-configuration: |
      {"apiVersion":"v1","kind":"Secret", ... "stringData":{"password":"S3cr3t!"} ...}   # plain text again!
  name: app-secret
  namespace: lab-t304
type: Opaque
```

Two traps are visible there. First, the plain `stringData` value comes back as `data`, which is why `stringData` never appears in `get`. Second, `k apply` stores a copy of your manifest in the annotation `kubectl.kubernetes.io/last-applied-configuration`, and that copy contains your plain-text `stringData`. `k create -f` (without `--save-config`) and `k create secret ...` do not add that annotation. In real life, prefer `create`, or accept that the annotation is readable by anyone who can read the Secret.

### 2.6 Decoding a Secret

Reading a value back is a skill you need in every Secret task, to check your work.

```bash
k get secret db -o jsonpath='{.data.password}' | base64 -d      # one key
k get secret web-tls -o jsonpath='{.data.tls\.crt}' | base64 -d  # a key with a dot: escape the dot
k get secret db -o go-template='{{range $k,$v := .data}}{{$k}}={{$v | base64decode}}{{"\n"}}{{end}}'   # all keys
k get secret db -o yaml                                           # base64 values, as stored
k describe secret db                                              # names and sizes only, never values
```

REAL OUTPUT (kubectl v1.37.1 client, --dry-run=client, no cluster)

```
$ k create secret generic db --from-literal=user=app --from-literal=password='S3cr3t!' \
    --dry-run=client -o go-template='{{range $k,$v := .data}}{{$k}}={{$v | base64decode}}{{"\n"}}{{end}}'
password=S3cr3t!
user=app
$ k create secret generic db --from-literal=password='S3cr3t!' --dry-run=client -o jsonpath='{.data.password}' | base64 -d; echo
S3cr3t!
```

The `jq` tool is not guaranteed on exam hosts ([E9](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad) lists kubectl, `yq`, `curl`, `wget` and `man`), so use `-o jsonpath` and `base64 -d` (`-d`, long form `--decode`, decodes). Tools used in this lesson besides kubectl (`base64`, `openssl`, `od`, `cmp`, `sed`) are there for lab verification; whether they exist on exam hosts is UNVERIFIED ([E9](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad) lists only kubectl, `yq`, `curl`, `wget` and `man`; E22 is UNVERIFIED). The optional `sd` tool in Lab C is a personal tool, not part of any exam.

**Encoding by hand, and the newline trap.** When you write `data:` by hand you must encode with `-n`:

REAL OUTPUT (OpenSSL 4.1.0, macOS host)

```
$ printf 'S3cr3t!' | base64          # no newline: this is what you want
UzNjcjN0IQ==
$ echo S3cr3t! | base64              # echo adds "\n": the encoding differs
UzNjcjN0IQo=
$ echo 'UzNjcjN0IQ==' | base64 -d
S3cr3t!
```

REAL OUTPUT (Docker)

```
$ docker run --rm busybox:1.36 sh -c 'echo -n "S3cr3t!" | base64; echo "S3cr3t!" | base64'
UzNjcjN0IQ==
UzNjcjN0IQo=
```

`echo -n` and `printf` write no newline. Plain `echo` writes one, and the encoded value ends in `Qo=` instead of `Q==`. Both are valid base64, so Kubernetes accepts both, and your application gets a password with an invisible extra character.

### 2.7 Consuming a Secret

There are four ways. The first three put the value inside the container; the fourth is used by the kubelet itself.

| Method | Pod field | Updates in a running Pod? | Use for |
|---|---|---|---|
| One key as an env var | `env[].valueFrom.secretKeyRef` | No (needs a restart) | One value the app reads from the environment |
| All keys as env vars | `envFrom[].secretRef` | No | Many values, names fixed by the key names |
| Files in a volume | `volumes[].secret` + `volumeMounts` | Yes, after up to about a minute (not with `subPath`) | Certificates, key files, anything an app reads from a file |
| Registry login | `imagePullSecrets` | n/a, used when pulling | Private images (section 2.8) |

**One key as an env var (`secretKeyRef`).**

```yaml
env:
- name: DB_PASSWORD        # the variable name inside the container; you choose it
  valueFrom:
    secretKeyRef:
      name: db             # Secret name (same namespace as the Pod)
      key: password        # key inside the Secret; a wrong key gives CreateContainerConfigError
      optional: false      # default false. true = start the container even if the Secret/key is missing
```

**All keys as env vars (`envFrom`).** Every key becomes a variable **with the key name unchanged** (`envFrom` does not upper-case it). `prefix` is added in front. If a key is not a valid variable name, the kubelet skips it and records an event. The classic rule for a valid name is letters, digits and `_`, not starting with a digit; newer releases accept more characters, so keep keys to the classic form.

```yaml
envFrom:
- secretRef:
    name: db               # all keys of Secret db
    optional: false        # default false
  prefix: DB_              # optional: variables become DB_user, DB_password
```

**Files in a volume.** Two parts: a `volumes` entry on the Pod and a `volumeMounts` entry on the container.

```yaml
volumes:
- name: creds              # a name you choose; the volumeMount refers to it
  secret:
    secretName: db         # NOTE: the field is secretName, not name (ConfigMap volumes use name)
    defaultMode: 0400      # permission bits for every file; default 0644; write in octal with a leading 0
    optional: false        # default false
    items:                 # optional: project only these keys, with chosen file names
    - key: password        # key in the Secret
      path: db/pw          # file path relative to the mount directory
      mode: 0400           # optional: mode for this file only (overrides defaultMode)
```

| Field | What it does | Default | Risky value |
|---|---|---|---|
| `secretName` | Name of the Secret | required | Misspelled name: Pod stuck in `ContainerCreating` |
| `defaultMode` | Permission bits of all files | `0644` | `400` (decimal 400 is `0620` in octal) instead of `0400`. A mode above `0777` is invalid. |
| `items[].key` | Key to project | required inside `items` | A key that does not exist: the mount fails unless `optional: true` |
| `items[].path` | File path under the mount directory | required inside `items` | An absolute path or one containing `..` is rejected |
| `items[].mode` | Mode of that one file | `defaultMode` | Same octal trap |
| `optional` | Allow the Secret to be absent | `false` | `true` hides a typo: the Pod starts with an empty directory |

With no `items`, every key becomes a file. With `items`, **only the listed keys** become files; the others are not mounted.

**Mount it read-only.** Add `readOnly: true` on the `volumeMount`. Setting it is correct and explicit, and it is the field to write when a task asks for a read-only mount. It is not what makes the files unwritable: the kubelet mounts Secret (and ConfigMap, downward API and projected) volumes read-only by itself, whatever `readOnly` says, so a write inside the container fails either way. Section 5 step 5 proves this with a Pod that omits `readOnly`.

```yaml
volumeMounts:
- name: creds              # must match volumes[].name
  mountPath: /etc/creds    # directory inside the container; its previous content is hidden
  readOnly: true
```

**The permission trap.** Files in the volume are owned by `root`. With `defaultMode: 0400`, only root can read them. A container running as a non-root user (`securityContext.runAsUser: 1000`) gets `Permission denied`. Fix it with a pod-level `securityContext.fsGroup`: the kubelet then makes the files group-owned by that group and the files become group-readable, so use `defaultMode: 0440` for that case. Which exact bits the kubelet adds when `fsGroup` is set is listed in section 11 as unverified.

**`subPath` caveat.** Mounting one key with `subPath` is possible, but such a mount does not receive updates when the Secret changes.

**Which to choose.** Environment variables are easy but leak easily: they are visible to every process of the container (`/proc/<pid>/environ`), they are inherited by child processes, and applications and crash reporters often dump them to logs. Files on tmpfs with mode `0400` are safer for highly sensitive values. Use env vars for low-risk values or when the application only supports them.

### 2.8 `imagePullSecrets` on a Pod or a ServiceAccount

When an image is in a private registry, the kubelet needs a login. You give it a `kubernetes.io/dockerconfigjson` Secret through `imagePullSecrets`. Two places work:

| Where | How | Effect |
|---|---|---|
| On the Pod | `spec.imagePullSecrets: [{name: regcred}]` | Only this Pod uses it |
| On the ServiceAccount | `imagePullSecrets` list on the ServiceAccount | Every **new** Pod that runs as this ServiceAccount gets the list copied into its spec by the ServiceAccount admission step. Existing Pods are not changed. |

```bash
k create secret docker-registry regcred --docker-server=registry.example.com \
  --docker-username=bob --docker-password='pw'
k patch serviceaccount default -p '{"imagePullSecrets":[{"name":"regcred"}]}'   # all new Pods in the namespace
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: private-img
  namespace: lab-t304
spec:
  imagePullSecrets:
  - name: regcred              # Secret of type kubernetes.io/dockerconfigjson in THIS namespace
  containers:
  - name: app
    image: registry.example.com/team/app:1.0   # pulled with the credentials for registry.example.com
```

The kubelet picks the login by matching the registry host in the image name against the keys in `auths`. If no secret matches, it pulls anonymously. A wrong or missing login shows as `ErrImagePull` then `ImagePullBackOff`. The Secret must be in the Pod's namespace; a Secret from another namespace is not found.

### 2.9 Immutable Secrets and the size limit

Set `immutable: true` and the API server rejects every later change to the data, and the kubelet stops watching the Secret, which lowers the load on the API server in big clusters. The only way to change it is to delete it and create a new one (and restart the Pods that use it). You cannot turn `immutable` back off.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-v1
  namespace: lab-t304
type: Opaque
immutable: true          # data below can never change; recreate to change
stringData:
  password: S3cr3t!
```

```bash
k patch secret db-v1 -p '{"immutable":true}'      # make an existing Secret immutable
```

EXPECTED OUTPUT (not captured)

```
$ k patch secret db-v1 -p '{"stringData":{"password":"other"}}'
The Secret "db-v1" is invalid: data: Forbidden: field is immutable when `immutable` is set
```

A pattern that goes well with `immutable`: name the Secret with a version or hash (`db-v2`, or `--append-hash`), point the Deployment at the new name and let the rollout restart the Pods.

The **1 MiB** limit applies to the sum of all values in one Secret. The limit exists because the API server stores every Secret as one object in etcd and sends it whole to every watcher (including the kubelet of each node that uses it), so very large objects slow down the control plane. A bigger Secret is rejected at creation. Try it (namespace `lab-t304`, any directory):

```bash
head -c 1100000 /dev/urandom > big.bin       # 1,100,000 bytes, above 1,048,576
k create secret generic big --from-file=big.bin
```

EXPECTED OUTPUT (not captured)

```
The Secret "big" is invalid: data: Too long: ... must have at most 1048576 bytes
```

Symptom -> diagnose -> fix. The symptom is the "Too long" validation error and no Secret is created (`k get secret big` says NotFound). Diagnose with `wc -c big.bin`: the sum of all your files must stay below 1,048,576 bytes. Fix by not putting the big file in a Secret: bake it into the image, put it on a PersistentVolume, or fetch it at start-up from a vault, and keep only the small credential (a token or password) in the Secret. Clean up with `rm big.bin`.

### 2.10 Security

| Topic | Fact | What to do |
|---|---|---|
| Base64 is not encryption | `base64 -d` reverses it in one command. Etcd stores the values in plain bytes unless encryption at rest is configured. | Treat anyone who can read the Secret as having the password. Never commit Secret YAML with real values. |
| RBAC | `get`, `list` and `watch` on `secrets` all return values. `list` returns every Secret in the namespace. | Grant `get` on named Secrets with `resourceNames`, and avoid `list`. Check with `k auth can-i get secret/db --as=system:serviceaccount:lab-t304:default -n lab-t304`. |
| Pod creation is read access | Whoever can create a Pod in a namespace can mount any Secret of that namespace and print it. | Limit who may create Pods; use separate namespaces. |
| Encryption at rest | An API server option that encrypts Secret values before they reach etcd. Backups of etcd contain Secrets. | Configure it as part of cluster administration: covered in the CKA track (T4.10). |
| Env vs files | Env vars leak into logs, child processes and `/proc`. | Prefer a tmpfs volume with `0400` for very sensitive values. |
| Node access | The kubelet receives only the Secrets of Pods on its node, and the volume lives in tmpfs. | Keep node access (SSH, container runtime) restricted. |
| `kubectl describe` | Shows key names and byte sizes, not values. | Do not rely on it as protection: `get -o yaml` shows the values. |

The Kubernetes page "Good practices for Kubernetes Secrets" (link in section 10) is the checklist for this topic.

**External secret operators (awareness only).** Tools such as the External Secrets Operator, the Secrets Store CSI Driver, Sealed Secrets and Vault integrations keep the real secret in an external vault (or encrypted in Git) and create or mount the Kubernetes Secret for you. You do not need them for the commands in this lesson. Know that they exist and that they are the usual answer to "how do we avoid storing credentials in manifests".

### 2.11 Projected volume: a Secret together with a ServiceAccount token

A **projected volume** merges several sources into **one directory**. The sources can be Secrets, ConfigMaps, downward API fields and ServiceAccount tokens. This is useful when an application expects one directory holding both its credential and a token.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: projected-demo
  namespace: lab-t304
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: all-in-one
      mountPath: /etc/combined
      readOnly: true
  volumes:
  - name: all-in-one
    projected:
      defaultMode: 0440              # mode for all files from all sources
      sources:
      - secret:
          name: db                   # the Secret from section 2.3
          items:
          - key: password
            path: db/password        # /etc/combined/db/password
      - serviceAccountToken:
          path: token                # /etc/combined/token
          audience: vault            # who the token is meant for; default is the API server
          expirationSeconds: 3600    # kubelet requests it for this long and refreshes it; minimum 600
```

EXPECTED OUTPUT (not captured)

```
$ k apply -f projected.yaml
pod/projected-demo created
$ k wait --for=condition=Ready pod/projected-demo --timeout=90s
pod/projected-demo condition met
$ k exec projected-demo -- ls -R /etc/combined
/etc/combined:
db
token

/etc/combined/db:
password
$ k exec projected-demo -- sh -c 'cut -c1-20 /etc/combined/token; echo'
eyJhbGciOiJSUzI1NiIs
```

The token file is a JWT (JSON Web Token) that starts with `eyJ`. The kubelet renews it before it expires. Save the YAML above as `projected.yaml` and apply it in a namespace where the Secret `db` exists (section 2.3 or the speed drill creates it). File paths from different sources must not collide: two sources that write the same path are rejected when the Pod is created or fail when the volume is set up (which of the two happens is UNVERIFIED, section 11).

### 2.12 Static Pods cannot reference Secrets

A **static Pod** is a Pod the kubelet starts directly from a manifest file on the node (for example the control-plane components). The API server only shows a read-only mirror of it. The documentation states that the spec of a static Pod cannot refer to other API objects such as a ServiceAccount, a ConfigMap or a Secret (https://kubernetes.io/docs/tasks/configure-pod-container/static-pod/). So a static Pod cannot use `secretKeyRef`, `envFrom.secretRef`, a `secret` volume, or `imagePullSecrets`. If one needs a credential, put it in a file on the node and use a `hostPath` volume, and protect that file with file permissions. Whether and how v1.37 rejects such a manifest is listed in section 11 (it needs a node, which kind and this machine could not provide for this topic).

### 2.13 Anything else worth knowing

- **Missing Secret or key.** `CreateContainerConfigError` for env references, `ContainerCreating` plus `FailedMount` for volume references. `optional: true` turns the failure into an empty value or directory.
- **Updates.** A `k replace` or `k apply` of a changed Secret updates volume files within about a minute. Env vars change only when the container restarts. A Deployment does not restart on a Secret change by itself: run `k rollout restart deploy/<name>`.
- **Default `defaultMode`.** The Kubernetes documentation gives `0644` as the default. Section 5 shows how to check it; the check is listed as unverified.
- **Naming a Secret in a Deployment.** The Pod template uses the same fields; nothing changes except that the Secret must exist before the Pods start.

## 3. How it works (diagram)

```
 You (kubectl)                           CONTROL PLANE                        NODE (worker)
 ------------                            -------------                        -------------
 k create secret generic db ...
        |  Secret object (JSON/YAML shows base64)
        v
   +-------------+      authN/authZ      +----------------------+
   | kube-       |---------------------->| etcd                 |
   | apiserver   |  RBAC: get/list/watch | Secret stored        |
   | (validates  |<----------------------| UNENCRYPTED by       |
   |  type, size,|                       | default (T4.10 adds  |
   |  stringData |                       | encryption at rest)  |
   |  -> data)   |                       +----------------------+
   +------+------+
          |  Node authorizer: this node may read only the Secrets
          |  of Pods scheduled on it
 ==========|=============================== TRUST BOUNDARY ===================================
          v                                   (below this line, the plain value exists)
   +-------------+
   |   kubelet   |  base64-decodes the value
   +------+------+
          |                      mounts tmpfs (RAM)                   +----------------------------+
          +--------------------> /var/lib/kubelet/pods/<uid>/volumes/ | container "app"            |
          |                      kubernetes.io~secret/creds/          |  /etc/creds/password  0400 | <- file (volume)
          |                          password   user   (..data -> ts) |  $DB_PASSWORD              | <- env var
          |                                                           +----------------------------+
          +---- env vars passed to the runtime when the container starts (fixed for the process life)
```

Walkthrough:

1. `kubectl` sends the Secret to the API server. The API server checks RBAC, validates the type and keys, merges `stringData` into `data` and writes the object to etcd. Nothing is encrypted unless the administrator turned on encryption at rest.
2. When a Pod that references the Secret is scheduled to a node, that node's kubelet is allowed to read this one Secret (the Node authorizer refuses other Secrets).
3. For a `secret` volume the kubelet mounts a tmpfs and writes one file per key, with the `defaultMode` you set. For `env`/`envFrom` it decodes the values and hands them to the runtime when it starts the container.
4. The line marked TRUST BOUNDARY is where protection stops: everything above it is protected by RBAC and (optionally) encryption at rest; everything below it is plain text in memory, in `/proc/<pid>/environ` and in the tmpfs files. Anyone who can `exec` into the container or reach the node can read it.
5. A change to the Secret reaches the volume files after the kubelet's next sync (about a minute). It never reaches an env var of a running container.

## 4. Commands and YAML you must produce fast

### 4.1 Imperative shortcuts

```bash
k create secret generic db --from-literal=user=app --from-literal=password='S3cr3t!'   # literals, single-quoted
k create secret generic cfg --from-file=password=pw.txt                                # key=path form; check the file has no trailing newline
k create secret generic envs --from-env-file=db.env                                    # one key per KEY=value line
k create secret tls web-tls --cert=tls.crt --key=tls.key                               # type kubernetes.io/tls
k create secret docker-registry regcred --docker-server=registry.example.com --docker-username=bob --docker-password='pw'   # type dockerconfigjson
k create secret generic site-login --type=kubernetes.io/basic-auth --from-literal=username=admin --from-literal=password='t0p'
k get secret db -o jsonpath='{.data.password}' | base64 -d                             # read a value back
k set env deploy/api --from=secret/db                                                  # copy every key of a Secret into a Deployment as env vars
k set env deploy/api --from=secret/db --prefix=DB_                                     # same, with a name prefix
k patch serviceaccount default -p '{"imagePullSecrets":[{"name":"regcred"}]}'          # registry login for all new Pods
k explain pod.spec.volumes.secret                                                      # field help, read from the cluster API
```

`k set env --from=secret/db` is expected to create one env entry per key, each with `valueFrom.secretKeyRef` (the variable name is the key, upper-cased, with unusable characters replaced). This is expected behaviour, not verified here (section 11); always confirm with `k set env deploy/api --list` or `k get deploy api -o yaml`.

### 4.2 The Pod YAML to write from memory

Generate the base with the imperative command, then add the two Secret pieces:

```bash
k run creds-demo --image=busybox:1.36 $do -- sleep 3600 > pod.yaml
```

Final file (complete and ready for `k apply -f pod.yaml`; it assumes the Secret `db` from section 2.3 exists):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: creds-demo
  namespace: lab-t304
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    env:
    - name: DB_PASSWORD            # name of the variable inside the container
      valueFrom:
        secretKeyRef:
          name: db                 # Secret name
          key: password            # key in the Secret; spelling must match exactly
    volumeMounts:
    - name: creds                  # must equal volumes[].name below
      mountPath: /etc/creds        # directory inside the container
      readOnly: true              # explicit read-only mount; add it when a task asks for one
  volumes:
  - name: creds
    secret:
      secretName: db               # the Secret to mount (field is secretName)
      defaultMode: 0400            # octal with leading 0: owner read only; default would be 0644
```

If a task wants the whole Secret as env vars, replace the `env:` block with:

```yaml
    envFrom:
    - secretRef:
        name: db
```

## 5. Worked example

One end-to-end run: create a Secret, consume it as env and as files, inspect it from inside the Pod, prove that base64 is reversible, then change the Secret and see what updates. Environment: kind, namespace `lab-t304`.

**Step 1. Namespace and Secret.**

```bash
k config use-context kind-lab
k delete ns lab-t304 --ignore-not-found; k create ns lab-t304
k config set-context --current --namespace=lab-t304
mkdir -p ~/lab/t304 && cd ~/lab/t304
k create secret generic db --from-literal=user=app --from-literal=password='S3cr3t!'
k get secret db
```

EXPECTED OUTPUT (not captured)

```
secret/db created
NAME   TYPE     DATA   AGE
db     Opaque   2      1s
```

`TYPE` is `Opaque` because the `generic` subcommand sets no type and the server fills the default. `DATA 2` is the number of keys.

**Step 2. Look at it, and reverse the encoding.**

```bash
k get secret db -o yaml
k get secret db -o jsonpath='{.data.password}' | base64 -d; echo
k describe secret db
```

EXPECTED OUTPUT (not captured)

```
apiVersion: v1
data:
  password: UzNjcjN0IQ==
  user: YXBw
kind: Secret
metadata:
  creationTimestamp: "2026-10-28T10:00:00Z"
  name: db
  namespace: lab-t304
  resourceVersion: "..."
  uid: ...
type: Opaque
S3cr3t!
Name:         db
Namespace:    lab-t304
Labels:       <none>
Annotations:  <none>

Type:  Opaque

Data
====
password:  7 bytes
user:      3 bytes
```

The password is 7 bytes: `S3cr3t!` has 7 characters, so there is no hidden newline. `describe` shows sizes, never values. The two base64 strings and the decoding are the same as the real captures in sections 2.4 and 2.6.

**Step 3. The Pod from section 4.2.** Save the YAML as `pod.yaml` and apply it.

```bash
k apply -f pod.yaml
k wait --for=condition=Ready pod/creds-demo --timeout=90s
```

EXPECTED OUTPUT (not captured)

```
pod/creds-demo created
pod/creds-demo condition met
```

**Step 4. Check the env var and the files from inside the container.**

```bash
k exec creds-demo -- printenv DB_PASSWORD
k exec creds-demo -- ls -lL /etc/creds
k exec creds-demo -- stat -L -c '%a %U' /etc/creds/password
k exec creds-demo -- sh -c 'wc -c < /etc/creds/password'
k exec creds-demo -- mount | grep /etc/creds
k exec creds-demo -- sh -c 'echo x > /etc/creds/new'
```

EXPECTED OUTPUT (not captured)

```
S3cr3t!
total 8
-r--------    1 root     root             7 Oct 28 10:00 password
-r--------    1 root     root             3 Oct 28 10:00 user
400 root
7
tmpfs on /etc/creds type tmpfs (ro,relatime,size=...k,...)
sh: can't create /etc/creds/new: Read-only file system
```

How to read it. `ls -lL` follows the symlinks (the plain `ls -l` would show `password -> ..data/password`) and displays mode `-r--------`, which is `0400`. `wc -c` returns 7: the file has exactly the 7 characters of the password. The `mount` line proves the volume is a tmpfs (RAM) and is mounted read-only (`ro`), and the write fails with `Read-only file system`. Do not credit `readOnly: true` for this: the kubelet mounts Secret volumes read-only anyway (step 5 proves it with a Pod that has no `readOnly`). The tmpfs behaviour on kind nodes is a fact to verify (section 11): a kind node is itself a container, so the kubelet runs inside it, and the tmpfs mount is expected to appear as shown.

**Step 5. Check the default mode.** Mount the same Secret in a second Pod without `defaultMode` and read the mode:

```bash
k run mode-check --image=busybox:1.36 --overrides='{"spec":{"containers":[{"name":"mode-check","image":"busybox:1.36","command":["sleep","3600"],"volumeMounts":[{"name":"s","mountPath":"/s"}]}],"volumes":[{"name":"s","secret":{"secretName":"db"}}]}}'
k wait --for=condition=Ready pod/mode-check --timeout=90s
k exec mode-check -- stat -L -c '%a' /s/password
k exec mode-check -- sh -c 'mount | grep " /s "; echo x > /s/new'
k delete pod mode-check $now
```

EXPECTED OUTPUT (not captured)

```
pod/mode-check created
pod/mode-check condition met
644
tmpfs on /s type tmpfs (ro,relatime,size=...k,...)
sh: can't create /s/new: Read-only file system
pod/mode-check force deleted
```

`644` is the documented default (`0644`). The next two lines are the proof for the read-only point: this Pod has no `readOnly` on its `volumeMount`, yet the mount is `ro` and the write fails, so the kubelet makes Secret volumes read-only by itself. Both are listed in section 11 until someone runs them on v1.37.

**Step 6. Change the Secret and watch what updates.**

```bash
k create secret generic db --from-literal=user=app --from-literal=password='N3w-pass' $do | k replace -f -
k exec creds-demo -- printenv DB_PASSWORD                 # immediately
ok=; for i in $(seq 24); do k exec creds-demo -- cat /etc/creds/password | grep -q 'N3w-pass' && { ok=1; break; }; sleep 5; done; test -n "$ok" && echo "file updated" || echo "file NOT updated after 2 minutes"
k exec creds-demo -- printenv DB_PASSWORD                 # still the old value
k delete pod creds-demo $now; k apply -f pod.yaml
k wait --for=condition=Ready pod/creds-demo --timeout=90s; k exec creds-demo -- printenv DB_PASSWORD
```

EXPECTED OUTPUT (not captured)

```
secret/db replaced
S3cr3t!                      # env: unchanged
file updated                 # printed after up to about a minute
S3cr3t!                      # env: still unchanged
pod "creds-demo" force deleted
pod/creds-demo created
pod/creds-demo condition met
N3w-pass                     # new Pod, new container: new value
```

`k replace` is used because the Secret was created without the `last-applied-configuration` annotation that `k apply` needs. The file changes by itself (the kubelet rewrote it); the environment variable does not, until the container is created again.

**Step 7. Cleanup.**

```bash
cd ~; k delete ns lab-t304; k config set-context --current --namespace=default
```

## 6. Common mistakes and how to fix them

| # | Symptom | What you will see | Cause | Fix (command) |
|---|---|---|---|---|
| 1 | The application says "authentication failed" with a password that "looks right" | `k get secret db -o jsonpath='{.data.password}' \| base64 -d \| od -c` ends with `\n` | The value was created with plain `echo`, or from a file that ends with a newline | Recreate: `k create secret generic db --from-literal=password='S3cr3t!' $do \| k replace -f -`. For hand-written YAML use `echo -n` or `printf`. For a file use `printf` instead of an editor. |
| 2 | `k apply -f secret.yaml` is rejected | `Error from server (BadRequest): ... Secret in version "v1" cannot be handled as a Secret: illegal base64 data at input byte N` | Plain text was written under `data:` | Put it under `stringData:` or encode it: `printf 'S3cr3t!' \| base64` |
| 3 | The password inside the Pod is shorter or different from what you typed | `printenv` shows `pa` for `pa$sword` | The shell expanded `$sword` (empty) before kubectl saw it. Backticks and `!` have the same problem in double quotes. | Single-quote the literal: `--from-literal=password='pa$sword'` |
| 4 | Pod stuck, status `CreateContainerConfigError` | Event: `Error: couldn't find key password in Secret lab-t304/db-cred` | `secretKeyRef.key` does not match any key of the Secret | Fix the Pod (`k replace --force`) or add the key to the Secret |
| 5 | Pod stuck, status `ContainerCreating` | Event: `MountVolume.SetUp failed for volume "creds" : secret "db" not found` | Wrong `secretName`, or the Secret is in another namespace | `k get secret -A \| grep db`; create it in the Pod's namespace |
| 6 | Secret is rejected at creation | `The Secret "web-tls" is invalid: data[tls.crt]: Required value` | Typed Secret (`kubernetes.io/tls`) written with wrong key names | Use `k create secret tls` or rename keys to `tls.crt`, `tls.key` |
| 7 | Cannot change the type of an existing Secret | `type: Invalid value: "kubernetes.io/tls": field is immutable` | `type` is immutable | `k delete secret web-tls` then create it again with the right type |
| 8 | `Permission denied` when the app reads `/etc/creds/password` | `cat: can't open ...: Permission denied` | Mode `0400` plus files owned by root and the container runs as another user | Add `fsGroup` and use `defaultMode: 0440`, or run as root |
| 9 | Mode shows `-rw--w----` instead of `-r--------` | `stat` shows `620` | `defaultMode: 400` was written; YAML reads it as decimal 400 | Write `0400` |
| 10 | File does not update after the Secret changed | Old content in the file | The mount uses `subPath`, or the Secret is `immutable` | Remove `subPath` or restart the Pod |
| 11 | Env var does not update after the Secret changed | Old value in `printenv` | Env vars are fixed at container start | `k rollout restart deploy/<name>` |
| 12 | Edit of a Secret is rejected | `field is immutable when `immutable` is set` | `immutable: true` | Delete and recreate it under a new name |
| 13 | `ErrImagePull` / `ImagePullBackOff` on a private image | Event text from the registry, such as `unauthorized` or `pull access denied` | No `imagePullSecrets`, wrong registry host in the Secret, or the Secret is in another namespace | Recreate with the right `--docker-server`; add `imagePullSecrets` to the Pod or ServiceAccount |

Every row above uses the same troubleshooting path. Run these in this order; each answers one question.

1. `k get pod <pod>`: what is the `STATUS`? `CreateContainerConfigError` points at an env or `envFrom` reference. `ContainerCreating` for more than a few seconds points at a volume. `ImagePullBackOff` points at the registry login.
2. `k describe pod <pod>`: read the **Events** at the bottom. The text names the Secret, the key and the namespace.
3. `k get secret -n <ns>`: does the Secret exist in the right namespace?
4. `k get secret <name> -o jsonpath='{.data}'` or `k describe secret <name>`: do the **key names** match the Pod's `key:` or `items[].key`? (`describe` lists key names, which is enough for this check.)
5. `k get pod <pod> -o yaml | grep -n -A4 -i secret`: what does the Pod really reference?

**Mistake 1: the trailing newline.** *Reasoning:* the application sends `S3cr3t!\n` to the database, which does not know that password. The Kubernetes side shows no error, because a newline is a valid byte. *Diagnose:* (1) `k get secret db -o jsonpath='{.data.password}'` ends in `Qo=` instead of `Q==` (see section 2.6); (2) `k get secret db -o jsonpath='{.data.password}' | base64 -d | od -c` prints the bytes, and a last `\n` confirms it; (3) `k exec <pod> -- sh -c 'wc -c < /etc/creds/password'` gives 8 instead of 7. Real bytes from a `--from-literal` and a `--from-file` of the same text:

REAL OUTPUT (kubectl v1.37.1 client, --dry-run=client, no cluster)

```
$ k create secret generic l1 --from-literal=password='S3cr3t!' --dry-run=client -o jsonpath='{.data.password}' | base64 -d | od -c
0000000    S   3   c   r   3   t   !
0000007
$ k create secret generic f1 --from-file=pw.txt --dry-run=client -o jsonpath='{.data.pw\.txt}' | base64 -d | od -c
0000000    S   3   c   r   3   t   !  \n
0000010
```

*Fix:* recreate the Secret with `--from-literal` (adds no newline) or `printf`/`echo -n`, then restart the Pods that read it through env vars.

**Mistake 2: `illegal base64 data`.** *Reasoning:* `data` values must be valid base64. The API server decodes them when it reads your YAML and fails if a character is not in the base64 alphabet (`!` is not). *Diagnose:* the error names the file and a byte offset. Look at the line under `data:`. *Fix:* use `stringData` for plain text, or `printf 'value' | base64`. A nasty variant: a plain word whose length is a multiple of 4 and only uses base64 letters (for example `test`) is valid base64, so no error appears and the stored bytes are garbage:

REAL OUTPUT (Docker)

```
$ docker run --rm busybox:1.36 sh -c 'echo -n test | base64 -d | od -An -tx1'
 b5 eb 2d
```

The Pod would read three unprintable bytes instead of `test`. If a hand-written `data:` value "works" but the application fails, decode it with `base64 -d` and compare.

EXPECTED OUTPUT (not captured)

```
$ cat bad.yaml
apiVersion: v1
kind: Secret
metadata:
  name: bad
data:
  password: S3cr3t!
$ k apply -f bad.yaml
Error from server (BadRequest): error when creating "bad.yaml": Secret in version "v1" cannot be handled as a Secret: illegal base64 data at input byte N
```

**Mistake 3: special characters mangled by the shell.** *Reasoning:* the shell runs before `kubectl`. In double quotes (and unquoted), `$name` is replaced by a variable, `` `cmd` `` is run, `\` can swallow characters and an interactive bash treats `!` as history expansion. kubectl only sees the result. *Diagnose:* decode what was stored. Real output with the variable `sword` unset:

REAL OUTPUT (kubectl v1.37.1 client, --dry-run=client, no cluster)

```
$ k create secret generic sp --from-literal=password=pa$sword --dry-run=client -o jsonpath='{.data.password}' | base64 -d; echo
pa
$ k create secret generic sp --from-literal=password='pa$sword' --dry-run=client -o jsonpath='{.data.password}' | base64 -d; echo
pa$sword
```

*Fix:* put the whole `KEY=value` or just the value in single quotes. A value that contains a single quote needs `--from-file` with a file made by `printf '%s' "$VALUE"`, or `$'...'` quoting; that is rare in exam tasks.

**Mistakes 4 and 5: missing key, missing Secret.** *Reasoning:* the kubelet resolves the reference only when it creates the container. For env references it cannot build the container configuration, so the status is `CreateContainerConfigError`. For a volume it cannot even mount, so the Pod stays `ContainerCreating`. Both retry with back-off and recover on their own when the object appears. *Diagnose:* the flow above; the event names the missing piece. *Fix:* correct the name or key; remember Pod env and `secretName` are immutable fields, so a Pod is replaced with `k replace --force -f pod.yaml`.

EXPECTED OUTPUT (not captured)

```
$ k get pod api
NAME   READY   STATUS                       RESTARTS   AGE
api    0/1     CreateContainerConfigError   0          25s
$ k describe pod api | tail -4
  Warning  Failed     ...  kubelet  Error: couldn't find key password in Secret lab-t304/db-cred
```

### Lab A (Easy): create a Secret, inject it as env and as files

**Setup**

```bash
k config use-context kind-lab
k delete ns lab-t304 --ignore-not-found; k create ns lab-t304
k config set-context --current --namespace=lab-t304
mkdir -p ~/lab/t304 && cd ~/lab/t304
```

**Task.** In namespace `lab-t304`:

1. Create a Secret `app-cred` with `username=app` and `password=S3cr3t!`.
2. Create a Pod `reader` (image `busybox:1.36`, command `sleep 3600`) that has the environment variable `APP_USER` from key `username` and `APP_PASS` from key `password` of `app-cred`, and mounts the whole Secret read-only at `/etc/app-cred` with file mode `0400`.
3. Write the decoded password, read from the Secret object with kubectl, to `~/lab/t304/easy-out.txt`.
4. Prove inside the Pod that the file content has exactly 7 bytes.

<details><summary>Hints</summary>

- A literal with `!` needs single quotes.
- `k run reader --image=busybox:1.36 $do -- sleep 3600 > reader.yaml` gives you the skeleton; add `env`, `volumeMounts`, `volumes`.
- The field in the volume is `secretName`; the mode is `defaultMode: 0400`.
- `base64 -d` prints no newline, so redirect it straight into the file.

</details>

<details><summary>Solution</summary>

```bash
k create secret generic app-cred --from-literal=username=app --from-literal=password='S3cr3t!'
```
This is the fastest form, and `--from-literal` guarantees no trailing newline.

```bash
cat > reader.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: reader
  namespace: lab-t304
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    env:
    - name: APP_USER
      valueFrom:
        secretKeyRef:
          name: app-cred
          key: username
    - name: APP_PASS
      valueFrom:
        secretKeyRef:
          name: app-cred
          key: password
    volumeMounts:
    - name: cred
      mountPath: /etc/app-cred
      readOnly: true
  volumes:
  - name: cred
    secret:
      secretName: app-cred
      defaultMode: 0400
EOF
k apply -f reader.yaml
k wait --for=condition=Ready pod/reader --timeout=90s
k get secret app-cred -o jsonpath='{.data.password}' | base64 -d > ~/lab/t304/easy-out.txt
k exec reader -- sh -c 'wc -c < /etc/app-cred/password'
```
Why each step: `secretKeyRef` reads one key into a variable; the `secret` volume writes every key as a file; `readOnly` goes on the `volumeMount` (container side) and `defaultMode` on the `volume` (file side). `wc -c` counts bytes and shows there is no hidden newline.

</details>

**Verification** (each line prints `OK` or fails with a non-zero exit code):

```bash

test "$(k get secret app-cred -n lab-t304 -o jsonpath='{.data.username}' | base64 -d)" = 'app' && echo OK-user

test "$(cat ~/lab/t304/easy-out.txt)" = 'S3cr3t!' && echo OK-file
```

### Lab B (Medium): a TLS Secret from openssl certificates

**Setup**

```bash
k config use-context kind-lab
k delete ns lab-t304 --ignore-not-found; k create ns lab-t304
k config set-context --current --namespace=lab-t304
mkdir -p ~/lab/t304/medium && cd ~/lab/t304/medium
openssl req -x509 -newkey rsa:2048 -nodes -keyout tls.key -out tls.crt -days 365 \
  -subj "/CN=shop.example.com" -addext "subjectAltName=DNS:shop.example.com" 2>/dev/null
ls
```

(See [T1.12](../part1-linux/T1.12-tls-pki-and-openssl-for-kubernetes.md) for what each `openssl` option does.) You now have `tls.crt` and `tls.key` for `shop.example.com`.

**Task.** In namespace `lab-t304`:

1. Create a TLS Secret `shop-tls` from `tls.crt` and `tls.key`. It will later be referenced by an Ingress (`spec.tls[].secretName`), which needs the type `kubernetes.io/tls`.
2. Create a Pod `tls-viewer` (`busybox:1.36`, `sleep 3600`) that mounts `shop-tls` read-only at `/etc/tls` so that the certificate appears as `/etc/tls/server.crt` (mode `0644`) and the key as `/etc/tls/private/server.key` (mode `0400`). No other file may be present in `/etc/tls`.
3. Read the certificate **from the Secret** (not from your local file), and write its subject and expiry date (`openssl x509 -noout -subject -enddate`) to `~/lab/t304/medium-out.txt`.

<details><summary>Hints</summary>

- `k create secret tls NAME --cert=... --key=...` sets the type and the key names for you.
- Use `items` in the volume: each item has `key`, `path` and `mode`.
- `path` may contain a directory (`private/server.key`).
- `k get secret shop-tls -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -subject -enddate`.

</details>

<details><summary>Solution</summary>

```bash
k create secret tls shop-tls --cert=tls.crt --key=tls.key
```
This stores the files under the keys `tls.crt` and `tls.key` and sets the type, which a `generic` Secret would not do.

```bash
cat > tls-viewer.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: tls-viewer
  namespace: lab-t304
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "sleep 3600"]
    volumeMounts:
    - name: tls
      mountPath: /etc/tls
      readOnly: true
  volumes:
  - name: tls
    secret:
      secretName: shop-tls
      items:
      - key: tls.crt
        path: server.crt
        mode: 0644
      - key: tls.key
        path: private/server.key
        mode: 0400
EOF
k apply -f tls-viewer.yaml
k wait --for=condition=Ready pod/tls-viewer --timeout=90s
k get secret shop-tls -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -subject -enddate > ~/lab/t304/medium-out.txt
cat ~/lab/t304/medium-out.txt
```
Why: `items` makes the kubelet project only the listed keys under the chosen paths, so the default file names `tls.crt`/`tls.key` do not appear. `mode` inside an item overrides `defaultMode` for that one file. The last pipeline decodes the Secret value (the escape `\.` is needed because the key name contains a dot) and lets `openssl` print the fields.

</details>

**Verification**

```bash
test "$(k get secret shop-tls -n lab-t304 -o jsonpath='{.type}')" = kubernetes.io/tls && echo OK-type
k get secret shop-tls -n lab-t304 -o jsonpath='{.data.tls\.crt}' | base64 -d | cmp - ~/lab/t304/medium/tls.crt && echo OK-cert-same
k get secret shop-tls -n lab-t304 -o jsonpath='{.data.tls\.key}' | base64 -d | cmp - ~/lab/t304/medium/tls.key && echo OK-key-same
test "$(k exec -n lab-t304 tls-viewer -- ls /etc/tls | sort | tr '\n' ' ')" = 'private server.crt ' && echo OK-files
test "$(k exec -n lab-t304 tls-viewer -- stat -L -c %a /etc/tls/server.crt)" = 644 && echo OK-crt-mode
test "$(k exec -n lab-t304 tls-viewer -- stat -L -c %a /etc/tls/private/server.key)" = 400 && echo OK-key-mode
grep -q 'shop.example.com' ~/lab/t304/medium-out.txt && grep -q '^notAfter=' ~/lab/t304/medium-out.txt && echo OK-out
```

EXPECTED OUTPUT (not captured)

```
OK-type
OK-cert-same
OK-key-same
OK-files
OK-crt-mode
OK-key-mode
OK-out
```

**Cleanup**

```bash

k config set-context --current --namespace=default
```

**Step 1: diagnose.**

## 8. Exam tips

- **Open the right page first.** For YAML shapes: https://kubernetes.io/docs/concepts/configuration/secret/ (types table and "Using Secrets"). For env and volume examples: https://kubernetes.io/docs/tasks/inject-data-application/distribute-credentials-secure/. For the `kubectl create secret` forms: https://kubernetes.io/docs/tasks/configmap-secret/managing-secret-using-kubectl/. For the security checklist: https://kubernetes.io/docs/concepts/security/secrets-good-practices/. All are under kubernetes.io/docs, which the exam allows ([E13](https://docs.linuxfoundation.org/tc-docs/certification/certification-resources-allowed)).
- **Create with the imperative command, not YAML.** `k create secret generic NAME --from-literal=K='V'` takes 20 seconds and cannot produce a base64 mistake. Only write `data:` or `stringData:` by hand if the task gives you a manifest to extend.
- **Single-quote every literal.** Then prove the stored value: `k get secret NAME -o jsonpath='{.data.KEY}' | base64 -d`. If the task says "exact" or you used a file, also check the byte count (`wc -c`).
- **Check namespace and key names before you apply.** The Secret and the Pod must share a namespace (`-n`), and `secretKeyRef.key` must match a key from `k describe secret NAME`. A wrong key shows as `CreateContainerConfigError`.
- **Octal modes and `readOnly`.** Write `defaultMode: 0400` with the leading 0, and put `readOnly: true` on the `volumeMount` when the task says read-only. Verify with `k exec POD -- stat -L -c %a /path/file`.
- **Know when a restart is needed.** Env vars from a changed Secret need new containers (`k rollout restart deploy/NAME`); mounted files update on their own after about a minute. Do not use `jq`; use `-o jsonpath` ([E9](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)).

## 9. Quick review

1. Which command creates a Secret with `user=app` and `password=S3cr3t!`, and why single quotes?
<details><summary>Answer</summary>`k create secret generic db --from-literal=user=app --from-literal=password='S3cr3t!'`. Single quotes stop the shell from expanding `$`, backticks and `!` before kubectl sees the value.</details>

2. How do you print the decoded password of Secret `db`?
<details><summary>Answer</summary>`k get secret db -o jsonpath='{.data.password}' | base64 -d`. For a key with a dot, escape it: `{.data.tls\.crt}`.</details>

3. Why is base64 not a security measure, and what does protect Secrets?
<details><summary>Answer</summary>`base64 -d` reverses it without a key. Protection comes from RBAC (limit `get`/`list`/`watch` on secrets and Pod creation), encryption at rest in etcd (T4.10) and node security.</details>

4. What is the difference between `data` and `stringData`?
<details><summary>Answer</summary>`data` holds base64 values. `stringData` holds plain text, is write-only (never returned) and is merged into `data` by the API server; `stringData` wins on conflicts. A plain value under `data` fails with `illegal base64 data`.</details>

5. Which command creates a TLS Secret, and which type and keys result?
<details><summary>Answer</summary>`k create secret tls web-tls --cert=tls.crt --key=tls.key`. Type `kubernetes.io/tls`, keys `tls.crt` and `tls.key`.</details>

6. A Pod shows `CreateContainerConfigError`. What are the first two commands, and the most likely causes?
<details><summary>Answer</summary>`k get pod`, then `k describe pod` (read Events). Causes: the Secret does not exist in the namespace, or `secretKeyRef.key` does not match a key in the Secret.</details>

7. What does `defaultMode: 400` do compared with `0400`?
<details><summary>Answer</summary>YAML reads `400` as decimal 400, which is octal 0620 (not owner-read-only). `0400` is the intended octal mode. The default when you write nothing is `0644`.</details>

8. You change a Secret. Which consumers see the change without a restart?
<details><summary>Answer</summary>Volume files (after up to about a minute), except `subPath` mounts. Env vars (`env`, `envFrom`) do not change until the container is restarted.</details>

9. How do you make every new Pod of a namespace use a registry login?
<details><summary>Answer</summary>Create a `docker-registry` Secret and add it to the ServiceAccount: `k patch serviceaccount default -p '{"imagePullSecrets":[{"name":"regcred"}]}'`. New Pods get it copied into their spec; existing Pods do not.</details>

10. Why can you not change the `type` of a Secret, and what is the fix? What other field makes the whole Secret unchangeable?
<details><summary>Answer</summary>`type` is immutable. Delete the Secret and create it again. `immutable: true` makes `data` unchangeable too (delete and recreate under a new name instead).</details>

11. Why does a static Pod not work with a Secret?
<details><summary>Answer</summary>The kubelet starts a static Pod from a node file, and its spec cannot refer to other API objects such as Secrets, ConfigMaps or ServiceAccounts. Use a file on the node (`hostPath`) instead.</details>
