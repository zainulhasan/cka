## 1. Why this matters

When something does not work in Kubernetes, the cluster usually already wrote down why. It wrote it in two places: the **Events** list (short messages from the scheduler, the kubelet and the controllers) and the **status conditions** on the object (true/false flags with a reason). Reading those two places takes seconds. Guessing, or jumping straight to logs, takes minutes. The Linux Foundation says the exams have 15-20 performance-based tasks in 2 hours (https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad and https://docs.linuxfoundation.org/tc-docs/certification/faq-cka-ckad-cks), which is about 6 minutes per task on average. A broken Pod that you can classify in 30 seconds leaves time for the rest.

In real life the same skill is the first step of every incident: "Pending" and "CrashLoopBackOff" are only symptoms. The Events section tells you if the cause is the scheduler (no node fits), the image (wrong tag), the config (missing ConfigMap), or the probe (app answers too slowly). The debugging lessons in Parts 3 and 4 assume you do this reading step automatically.

### 2.1 What an Event is

An **Event** is a small API object (kind `Event`) that says "something happened to object X". The problem it solves: Pods and nodes are managed by several independent components (the scheduler, the kubelet on each node, the controllers in the controller manager). None of them has a user interface. When one of them cannot do its job, it needs a way to tell the human. It cannot write to your terminal, so it creates an Event object that points at the broken object. Without Events, "Pod stays Pending" would have no visible reason except reading component logs on the control plane.

**Under the hood.** Each component has an *event recorder* (a client-go helper). When the scheduler fails to place a Pod, it calls the recorder with the Pod, a type, a reason and a message. The recorder sends a `create` to the API server. If the same event happens again (same object, reason, message), the recorder does not create a new object. It updates the existing one: `count` goes up and `lastTimestamp` moves forward. This is why `kubectl describe` shows `x7 over 3m` instead of seven lines. The recorder also has a spam filter that drops events when one source floods the same object. The API server stores Events in etcd like any other object, but with a **time to live** (TTL, a lifetime after which etcd deletes the key; see 2.5). Events are *best-effort*. The API reference says consumers must not rely on their timing or on their continued existence (https://kubernetes.io/docs/reference/kubernetes-api/cluster-resources/event-v1/).

An Event is **not** a log line. Logs come from your container's stdout. Events come from Kubernetes components and describe what Kubernetes did *to* your object.

Fields you will read (core/v1 `Event`):

| Field | Meaning | Notes |
|---|---|---|
| `involvedObject` | The object the event is about: `kind`, `name`, `namespace`, `uid`, `fieldPath` | `fieldPath` names the container, for example `spec.containers{app}` |
| `type` | `Normal` or `Warning` | Only these two exist today. Anything that needs attention is `Warning`. |
| `reason` | A short CamelCase code: `FailedScheduling`, `BackOff`, ... | Meant for machines and for you to search for |
| `message` | The human text | The part that holds the real answer (taint name, missing object, quota numbers) |
| `count` | How many times it repeated | Starts at 1 |
| `firstTimestamp`, `lastTimestamp` | First and latest time seen | May be empty on events written through the newer events API (see 2.3) |
| `eventTime` | Time of the first observation, newer API | May be set when the two above are empty |
| `source.component`, `source.host` / `reportingComponent` | Who wrote it: `default-scheduler`, `kubelet` on node X, `replicaset-controller` | Tells you which layer failed |
| `metadata.namespace` | Where the Event lives | Same namespace as the involved object. For cluster-scoped objects (Nodes), it is `default`. |

### 2.2 `kubectl describe` sections

`k describe <kind> <name>` calls the API for the object and also for the Events whose `involvedObject` points at it, then prints both in one readable page. It is the fastest single command for "why". For a Pod the sections come in this order:

| Section | What it shows | Use it to find |
|---|---|---|
| header (`Name`, `Namespace`, `Node`, `Labels`, `Status`, `IP`, `Controlled By`) | Identity and phase. `Node: <none>` means not scheduled yet. | Is it scheduled? Who owns it? |
| `Containers:` per container | `Image`, `State`, `Reason`, `Last State`, `Exit Code`, `Ready`, `Restart Count`, `Limits`, `Requests`, probes, `Environment`, `Mounts` | Why the container is waiting or dying |
| `Conditions:` | `Type` / `Status` table (see 2.7) | Which stage passed: scheduled, initialized, containers ready, Pod ready |
| `Volumes:` | Each volume and its source | Which ConfigMap/Secret/PVC the Pod needs |
| `QoS Class`, `Node-Selectors`, `Tolerations` | Scheduling inputs | Why a node was rejected |
| `Events:` | `Type`, `Reason`, `Age`, `From`, `Message` | The story, oldest first |

**The container State block.** Each container has a current `State` and a `Last State` (what the *previous* run did). They hold one of three shapes:

| Shape | Fields | Typical reasons |
|---|---|---|
| `Waiting` | `Reason`, `Message` | `ContainerCreating`, `ErrImagePull`, `ImagePullBackOff`, `CrashLoopBackOff`, `CreateContainerConfigError` |
| `Running` | `Started` | none |
| `Terminated` | `Reason`, `Exit Code`, `Started`, `Finished` | `Completed` (exit 0), `Error` (non-zero), `OOMKilled` (memory limit hit), `ContainerCannotRun` |

`Last State` is the key to crash loops. While the container is in `Waiting: CrashLoopBackOff`, the *current* state tells you nothing about the crash. The `Last State: Terminated` block holds the exit code of the run that just died. Reading exit codes:

| Exit code | Meaning |
|---|---|
| 0 | Normal exit |
| 1 | Application error (read `k logs --previous`) |
| 126 / 127 | Command found but not executable / command not found (bad `command:` in the spec) |
| 137 | 128 + 9: killed by SIGKILL. `OOMKilled` reason means memory limit; a probe kill that the app ignored for the grace period ends the same way. In the test Pod below, PID 1 is `sleep`, which has no SIGTERM handler, and PID 1 ignores signals without a handler. So each liveness kill waits the full `terminationGracePeriodSeconds` (default 30 s) and then ends with SIGKILL, exit 137. |
| 143 | 128 + 15: ended by SIGTERM (normal stop) |

`Restart Count` counts how many times the kubelet restarted this container. A number that keeps growing means a loop.

### 2.3 `kubectl get events`

`k get events` lists the Event objects of one namespace (the namespace of your context, unless you pass `-n NS` or `-A`). It is a normal `get`, so `-o yaml`, `-o custom-columns`, `-w` and `--field-selector` all work. The default columns are `LAST SEEN`, `TYPE`, `REASON`, `OBJECT`, `MESSAGE`.

**Order.** The API returns events in no useful order (by name, which contains a random hex string). Always sort:

```bash
k get events -n lab-t208 --sort-by=.metadata.creationTimestamp
k get events -A --sort-by=.lastTimestamp | tail
```

| Sort key | Meaning | Risk |
|---|---|---|
| `.metadata.creationTimestamp` | When the Event object was first created | Always set. A repeating event keeps its first position. |
| `.lastTimestamp` | Last time the event repeated | Can be empty on events written through the newer `events.k8s.io` API. Empty values sort together at one end, so the order can look wrong. Check with `k get events -o custom-columns=R:.reason,LAST:.lastTimestamp,TIME:.eventTime`. |

If the tail of the list looks old or random, switch the key to `.metadata.creationTimestamp`. `tail` shows the newest lines because the sort is ascending (newest last).

**Watch.** `k get events -w` prints the current list and then keeps printing new or updated events until Ctrl-C. Open it in a second terminal while you create a broken Pod and you see the whole story live.

**Field selectors.** A **field selector** filters on fields of the object on the server, so you get a short list. The API server supports a limited set of fields per type (the kubectl help says so for `--field-selector`). For Events the useful ones are `involvedObject.name`, `involvedObject.kind`, `involvedObject.namespace`, `involvedObject.uid`, `reason`, `type`, `reportingComponent` and `source`. Combine with a comma (AND). Operators are `=`, `==` and `!=`.

```bash
k get events -n lab-t208 --field-selector involvedObject.name=big-request
k get events -n lab-t208 --field-selector type=Warning
k get events -A --field-selector type=Warning,reason=FailedScheduling
k get events -n lab-t208 --field-selector type!=Normal
k get events -A --field-selector involvedObject.kind=Node
```

`involvedObject.name` matches the name only. Two objects of different kinds with the same name (a Deployment `web` and a Pod `web`) both match. Add `involvedObject.kind=Pod` to be exact.

**Custom columns.** The fast report from the entry:

```bash
k get events --field-selector type=Warning -A \
  -o custom-columns=NS:.metadata.namespace,OBJ:.involvedObject.name,REASON:.reason,MSG:.message
```

Each column is `HEADER:JSONPath`. Spaces inside a message do not break the table, because only the header and path are split on commas.

```text

  kubectl events [(-o|--output=)json|yaml|kyaml|name|go-template|go-template-file|template|templatefile|jsonpath|jsonpath-as-json|jsonpath-file] [--for TYPE/NAME] [--watch] [--types=Normal,Warning] [options]
```

Compare the two commands:

| | `k get events` | `k events` |
|---|---|---|
| Filter by object | `--field-selector involvedObject.name=x,involvedObject.kind=Pod` | `--for pod/x` (also `deploy/x`, `node/x`) |
| Filter by type | `--field-selector type=Warning` | `--types=Warning` (comma list: `--types=Warning,Normal`) |
| Sorting | You must pass `--sort-by` | There is no `--sort-by` flag. It prints in time order on its own (oldest first, newest last; confirm on a run, section 11). |
| Other field selectors, `-l` | `--field-selector` works with any supported field | No `--field-selector` and no `-l` flag in v1.37.0 |
| Custom columns | `-o custom-columns=...` | Not in the `-o` list. Use `-o jsonpath`, `-o yaml` or `-o name`. |
| All namespaces | `-A` | `-A` |
| Watch | `-w` | `-w` |

Use `k events --for pod/web --types=Warning` when you know the object. Use `k get events --field-selector ... -o custom-columns=...` when you need a filter that `k events` lacks or a report with chosen columns.

`--for` takes `TYPE/NAME`. For namespaced kinds it uses `-n` (or your context's namespace). Events for **cluster-scoped objects** (nodes) live in the `default` namespace (2.11), so for nodes the dependable commands are `k describe node NAME` or the `k get events -n default --field-selector involvedObject.kind=Node,involvedObject.name=NAME` form. Whether `k events --for node/NAME` finds them without extra flags is untested here (section 11).

### 2.5 Event retention (the TTL) and why old failures vanish

The API server deletes every Event after a fixed time. The setting is the kube-apiserver flag `--event-ttl`. Real flag text from the v1.37.0 kube-apiserver:

REAL OUTPUT (kube-apiserver v1.37.0 `--help` text only, no cluster running; command `kube-apiserver --help | grep -A2 -- --event-ttl`)

```text
      --event-ttl duration                               Amount of time to retain events. (default 1h0m0s)
      --kubelet-certificate-authority string             Path to a cert file for the certificate authority.
      --kubelet-client-certificate string                Path to a client cert file for TLS.
```

The default is **1 hour** (`1h0m0s`). On a kubeadm or kind control plane the flag is set only if the admin added it to the static Pod manifest `/etc/kubernetes/manifests/kube-apiserver.yaml`. Check with `grep event-ttl /etc/kubernetes/manifests/kube-apiserver.yaml`: no match means the 1 hour default applies (not checked on a live cluster here, section 11). Managed clusters (EKS, GKE, AKS) may use another value and you cannot change it.

Why this matters to you:

- A Pod that failed 2 hours ago shows `Events: <none>` in `describe`. The Pod object (and its `Last State`, `Restart Count`, conditions) stays. Only the story is gone.
- Do not delay. If a task says "find out why Pod X failed yesterday", the event is gone. Reproduce the failure (delete the Pod so the controller recreates it, or restart the rollout) and read the new events.
- The TTL is per Event object. To my knowledge each update (a repeat) refreshes the timer, so a Pod that keeps failing keeps a fresh event. One that failed once and is now fine loses it after the hour (section 11).
- Events are not an audit trail. For history you need logs, metrics or the audit log (T4 topics).

### 2.6 Common event reasons

Learn the reasons as a map from reason to the component that wrote it to the next command you run.

| Reason | Type | Written by | What it means | Next check or fix |
|---|---|---|---|---|
| `Scheduled` | Normal | default-scheduler | A node was chosen: `Successfully assigned NS/POD to NODE` | none. Shows the node name. |
| `FailedScheduling` | Warning | default-scheduler | No node fits. The message counts nodes per reason: `0/3 nodes are available: ...` | Read each phrase: `untolerated taint(s)` (tolerations), `Insufficient cpu` / `Insufficient memory` (requests), `didn't match Pod's node affinity/selector` (nodeSelector, affinity), `persistentvolumeclaim ... not found` / `unbound immediate PersistentVolumeClaims` (storage) |
| `Pulling` / `Pulled` | Normal | kubelet | Image pull started / finished (or already on the node: `Container image "x" already present on machine`) | `Pulled` is not an error. It also repeats on every restart. |
| `Failed` | Warning | kubelet | The container could not be created or the image could not be pulled. The message says which: `Failed to pull image ...`, `Error: ErrImagePull`, `Error: ImagePullBackOff`, `Error: configmap "x" not found` | Fix the image name/tag/pull secret, or create the missing ConfigMap/Secret/key |
| `BackOff` | Warning | kubelet | The kubelet is waiting before the next try: `Back-off pulling image "x"` or `Back-off restarting failed container app in pod ...` | Image: fix name/tag. Restart loop: `k logs --previous`, `Last State` exit code |
| `Created` / `Started` | Normal | kubelet | Container created and started | Many of these in a row for the same Pod means restarts |
| `Killing` | Normal | kubelet | The kubelet is stopping a container: `Container app failed liveness probe, will be restarted`, or a Pod deletion | Normal type but meaningful when it follows `Unhealthy` |
| `Unhealthy` | Warning | kubelet | A probe failed: `Liveness probe failed: ...`, `Readiness probe failed: ...`, `Startup probe failed: ...` | Fix the probe (path, port, delay) or the app |
| `FailedMount` | Warning | kubelet | A volume could not be mounted: `MountVolume.SetUp failed for volume "cfg" : configmap "app-config" not found` | Create the ConfigMap/Secret, fix the PVC name |
| `FailedAttachVolume` | Warning | attachdetach-controller | A block volume could not be attached to the node | Check the PV/PVC and the storage backend |
| `FailedCreate` | Warning | replicaset-controller, job-controller, daemonset-controller, statefulset-controller | The controller could not create a Pod: `Error creating: pods "x" is forbidden: exceeded quota: ...` | The event is on the **ReplicaSet/Job**, not on a Pod. `k describe rs`. Look for quota, admission, missing ServiceAccount. |
| `SuccessfulCreate` | Normal | replicaset-controller, job-controller | A Pod was created | none |
| `ScalingReplicaSet` | Normal | deployment-controller | The Deployment changed a ReplicaSet size | Shows rollout steps |
| `FailedCreatePodSandBox` | Warning | kubelet | The Pod sandbox (network namespace) could not be built, often a CNI problem | Look at the CNI Pods in `kube-system` |
| `Evicted` | Warning | kubelet | The node removed the Pod (disk, memory pressure) | `k describe node` conditions |
| `NodeNotReady` | Warning | node-controller | The node stopped reporting | `k describe node`, then the kubelet (Part 4) |
| `WaitForFirstConsumer` | Normal | persistentvolume-controller | A PVC waits for a Pod before it binds | Create a Pod that uses the PVC |
| `ProvisioningFailed` | Warning | persistentvolume-controller / provisioner | A PVC could not get a volume: `storageclass.storage.k8s.io "x" not found` | Fix `storageClassName` |
| `BackoffLimitExceeded` | Warning | job-controller | A Job failed more times than `backoffLimit` | `k logs` of a failed Pod, fix the command |

Two reasons that confuse beginners: `Failed` is a *reason* (the event kind), while `ErrImagePull` is a text in the message and a container *waiting reason*. `BackOff` appears for both image pulls and container restarts. Read the message to tell them apart.

### 2.7 Status conditions per object

A **condition** is a structured fact in `.status.conditions[]` with these fields:

| Field | Meaning |
|---|---|
| `type` | The name of the fact: `Ready`, `Available`, `Progressing`, `MemoryPressure` |
| `status` | `"True"`, `"False"` or `"Unknown"` (a string, not a boolean) |
| `reason` | CamelCase code for the last change |
| `message` | Human text |
| `lastTransitionTime` | When `status` last changed |
| `lastProbeTime` / `lastUpdateTime` / `lastHeartbeatTime` | Kind-specific, when it was last checked |

The big trap: **the polarity differs by type**. For `Ready`, `Available`, `Initialized` you want `True`. For node `MemoryPressure`, `DiskPressure`, `PIDPressure` and `NetworkUnavailable` you want `False`. `True` there means a problem.

| Object | Conditions you will read | Healthy value | What a bad value tells you |
|---|---|---|---|
| Pod | `PodScheduled` | True | False + reason `Unschedulable`: the scheduler could not place it (see `FailedScheduling`) |
| Pod | `PodReadyToStartContainers` | True | False: the sandbox or network setup is not done |
| Pod | `Initialized` | True | False: init containers still running or failing |
| Pod | `ContainersReady` | True | False: at least one container is not ready (readiness probe, not started) |
| Pod | `Ready` | True | False: the Pod receives no Service traffic. A failing readiness probe gives this. |
| Deployment | `Available` | True | False: fewer ready replicas than `replicas - maxUnavailable` |
| Deployment | `Progressing` | True | False + reason `ProgressDeadlineExceeded`: no progress for `progressDeadlineSeconds` (default 600) |
| Deployment / ReplicaSet | `ReplicaFailure` | absent | True: the controller could not create Pods (look for `FailedCreate`) |
| Node | `Ready` | True | False or Unknown: kubelet is down or unreachable |
| Node | `MemoryPressure`, `DiskPressure`, `PIDPressure` | False | True: the kubelet will evict Pods |
| Node | `NetworkUnavailable` | False (or absent) | True: the CNI has not set up the node network |
| Job | `Complete` | True when done | False or absent: still running, or failed (then check `Failed`) |
| Job | `Failed` | absent | True: failed. Reason `BackoffLimitExceeded` or `DeadlineExceeded` |
| Job | `Suspended`, `FailureTarget`, `SuccessCriteriaMet` | situational | Newer conditions that appear while a Job is suspended or being finished |

Read all conditions of any object in one line:

```bash
k get pod web -o jsonpath='{range .status.conditions[*]}{.type}={.status}{" "}{.reason}{"\n"}{end}'
```

Read one condition: `k get pod web -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}'`. In `jsonpath`, `[?(@.type=="Ready")]` is a filter, and the double quotes inside single quotes are required.

EXPECTED OUTPUT (not captured)

Conditions of a Deployment whose new image cannot be pulled. The old Pods still serve, so `Available` stays True.

```text
Available=True MinimumReplicasAvailable
Progressing=True ReplicaSetUpdated
```

After `progressDeadlineSeconds` with no progress, the second line becomes `Progressing=False ProgressDeadlineExceeded`.

### 2.8 `kubectl wait`

`k wait` blocks until a condition on one or more objects is true, then prints `... condition met` and exits 0. If the time runs out it prints an error and exits 1. It replaces `sleep 20` guesses in scripts and in exam tasks ("create the Pod, then verify it is Ready"). Real help text from the v1.37.0 binary (shortened):

REAL OUTPUT (kubectl v1.37.0 from a kindest/node:v1.37.0 container; help text only, shortened)

```text
$ kubectl wait --help
...
Examples:
  kubectl wait --for=condition=Ready pod/busybox1
  # The default value of status condition is true; you can wait for other targets after an equal delimiter ...
  kubectl wait --for=condition=Ready=false pod/busybox1
  kubectl wait --for=jsonpath='{.status.phase}'=Running pod/busybox1
  kubectl wait --for='jsonpath={.status.conditions[?(@.type=="Ready")].status}=True' pod/busybox1
  kubectl wait --for=jsonpath='{.status.loadBalancer.ingress}' service/loadbalancer

```

| Form | Waits until | Example |
|---|---|---|
| `--for=condition=Ready` | the condition has `status: "True"` | `k wait --for=condition=Ready pod/web --timeout=60s` |
| `--for=condition=Ready=false` | the condition has the given status (compared without case) | `k wait --for=condition=Ready=false pod/bad-ready` |
| `--for=condition=complete` | a Job has finished OK | `k wait --for=condition=complete job/job-ok --timeout=60s` |
| `--for=condition=Available` | a Deployment has enough ready replicas | `k wait --for=condition=Available deploy/shop --timeout=90s` |
| `--for=jsonpath='{.status.phase}'=Running` | any field equals a value | `k wait --for=jsonpath='{.status.phase}'=Bound pvc/data` |
| `--for=delete` | the object is gone | `k wait --for=delete pod/web --timeout=60s` |
| `--for=create` | the object exists | `k wait --for=create secret/s1 --timeout=30s` |

Rules and traps:

- The default `--timeout` is **30s**. A slow image pull needs `--timeout=90s`.
- Without `--for=create`, waiting for an object that does not exist fails at once with `Error from server (NotFound)`.
- Select many objects with `-l app=web` or `--all`: `k wait --for=condition=Ready pod -l app=web --timeout=60s`.
- The jsonpath form needs the value part after `=`. Without it, `wait` only waits for the field to exist.
- Timeout text: `error: timed out waiting for the condition on pods/web`. The exit code is 1, which makes `k wait ... && echo OK` a valid pass/fail check.
- A Pod stuck in `CrashLoopBackOff` flips between Ready and not Ready. A wait can succeed in the brief window of the running state.

Two outcomes, success and timeout.

### 2.9 Reading `.status` of nodes, PVCs and Jobs

`spec` is what you asked for. `.status` is what the cluster observed. You cannot edit `.status` (components write it). Read it directly when `describe` is too long.

**Node.** `.status` holds `conditions` (2.7), `capacity` and `allocatable` (the usable part: capacity minus system reserve), `addresses`, `nodeInfo` (kernel, kubelet version, container runtime) and `images`. The `allocatable` numbers are what the scheduler compares with Pod `requests`.

```bash
k get nodes -o wide
k describe node lab-worker | sed -n '/^Conditions:/,/^Addresses:/p'
k get node lab-worker -o jsonpath='{.status.allocatable}{"\n"}'
k get nodes -o custom-columns='NAME:.metadata.name,READY:.status.conditions[?(@.type=="Ready")].status'
k describe node lab-worker | sed -n '/^Allocated resources:/,/^Events:/p'
```

The last command shows how much of `allocatable` is already requested. This is where "Insufficient cpu" comes from.

Node conditions on a healthy kind worker.

**PVC (PersistentVolumeClaim).** `.status.phase` is `Pending` (not bound), `Bound` or `Lost`. `.status.capacity.storage` is the size actually given. ### 2.10 Recording what you found into an answer file

Tasks in any practice or exam setting may ask you to save a value to a file. The skill is small but each point is easy to lose:

- Redirect only the answer, nothing else: `k get pod web -o jsonpath='{.status.phase}' > ~/lab/t208/phase.txt`. `>` replaces the file; `>>` appends.
- Never redirect a whole `describe` when the task asks for one value. Extract with `-o jsonpath`, or with `yq` (listed on the exam hosts at https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad), or with `awk`/`sed`/`grep`. Do not rely on `jq`: it is not in the list of exam host tools. Here I use `jq` nowhere.
- The directory must exist. If `mkdir -p ~/lab/t208` was skipped, bash prints `No such file or directory` before kubectl runs.
- `jsonpath` prints no trailing newline. Add `{"\n"}` when you want a line end, or use `echo "$(...)" >> file` for several lines.
- Warnings from kubectl go to stderr and do not land in the file. Errors do not either, so an empty file usually means the command failed. Run it without `>` first.
- Check the file with `cat -A file` (shows `$` at each line end and spaces), then compare with `test "$(cat file)" = "expected"`.
- Write exactly the format asked. If the task wants the event *reason*, write `FailedScheduling`, not the whole message.

Example, saving the reason of the first Warning event of one Pod:

```bash
k -n lab-t208 get events --field-selector involvedObject.name=big-request,type=Warning \
  --sort-by=.metadata.creationTimestamp -o jsonpath='{.items[0].reason}{"\n"}' > ~/lab/t208/reason.txt
```

### 2.11 Node and component events, cluster-scoped objects, `kube-system`

- **Events live in a namespace.** The Event takes the namespace of the object it is about. A Node is not in any namespace, so the recorder puts its Events in the `default` namespace. If `k get events` (in another namespace) never shows `NodeNotReady`, look in `-n default`, or use `-A`.
- **System Pods run in `kube-system`.** The API server, scheduler, controller manager, etcd, CoreDNS, kube-proxy and the CNI run there. Events about them are in `kube-system`: `k -n kube-system get events --sort-by=.metadata.creationTimestamp`. On a kubeadm cluster the control plane Pods are *static Pods* (the kubelet reads them from files). Their Events appear on the mirror Pod objects. Leader elections of the scheduler and controller manager also write `LeaderElection` events there.
- **Node events** come from the kubelet and the node controller (`Starting`, `NodeHasSufficientMemory`, `NodeReady`, `NodeNotReady`, `RegisteredNode`). On a long-running cluster they are older than the 1 hour TTL and gone; `k describe node` then shows `Events: <none>`. Conditions stay.
- **Cluster-wide sweep:** `k get events -A --field-selector type=Warning --sort-by=.metadata.creationTimestamp` is the first command when "something is wrong somewhere".

### 2.12 Related but different

| Pair | Difference |
|---|---|
| Events vs logs | Events: what Kubernetes components did to the object. Logs (`k logs`): what your process printed. A Pod that never started has events and no logs. A running Pod with an app bug has logs and no events. |
| Events vs conditions | Events are history (and expire). Conditions are the current state (and stay). Use conditions to know *now*, events to know *why*. |
| Pod `phase` vs `STATUS` column | `.status.phase` is only `Pending`, `Running`, `Succeeded`, `Failed` or `Unknown`. The `STATUS` column of `k get pods` is computed by kubectl from the phase and the container states, so you see `ImagePullBackOff`, `CrashLoopBackOff`, `Init:0/1`, `Terminating`. A Pod showing `ImagePullBackOff` has phase `Pending`. Details in [T2.03](../part2-basics/T2.03-pods-in-depth.md). |
| `describe` vs `get -o yaml` | `describe` is formatted for people and adds Events. `-o yaml` is the full raw object (use it for exact field names, no Events). |
| `k get events` vs `k events` | See the table in 2.4. |
| core `v1` Event vs `events.k8s.io/v1` | Two API versions of the same stored data. The newer one has `regarding`, `note`, `series`. kubectl shows the core view. The reference page is https://kubernetes.io/docs/reference/kubernetes-api/cluster-resources/event-v1/ . |
| Events vs the audit log | The audit log records API requests (who changed what). Events record what components decided. |

**What to remember from section 2.**

1. Events say why (and expire after about 1 hour); conditions say what is true now (and stay).
2. `describe` for one object; `get events --sort-by=.metadata.creationTimestamp` for a namespace or `-A`; `k events --for TYPE/NAME --types=Warning` for one object.
3. `Last State` plus `Restart Count` explain a restart loop; the exit code tells the kind of death (137 = SIGKILL).
4. Condition polarity differs: `Ready`, `Available` want `True`; `MemoryPressure`, `DiskPressure`, `PIDPressure` want `False`.
5. Node events live in `default`; controller failures (`FailedCreate`) sit on the ReplicaSet or Job, not on a Pod.

## 3. How it works (diagram)

ASCII flow: symptom to the place to look.

```text
START: something is not working
  |
  v
k get <kind> -A -o wide        right namespace? right name? READY x/y? STATUS? NODE?
  |
  +-- object not found / empty list ------------> wrong -n? typo? try -A, then k api-resources
  |
  +-- Deployment shows 0/N and NO Pods exist ----> k describe rs / k get rs -o wide
  |                                                Events on the ReplicaSet: FailedCreate
  |                                                (quota, admission, missing ServiceAccount)
  |
  +-- Pod STATUS = Pending
  |      |
  |      +-- NODE is <none> --------------------> k describe pod -> Events: FailedScheduling
  |      |                                         read: untolerated taint / Insufficient cpu,memory /
  |      |                                         didn't match node affinity/selector / PVC problems
  |      |
  |      +-- NODE set, ContainerCreating -------> Events: FailedMount (ConfigMap, Secret, PVC),
  |                                                FailedCreatePodSandBox (CNI), Pulling (slow image)
  |
  +-- STATUS = ErrImagePull / ImagePullBackOff --> Events: Failed "Failed to pull image", BackOff
  |                                                fix image name, tag or imagePullSecrets
  |
  +-- STATUS = CreateContainerConfigError -------> Events: Failed "Error: configmap/secret ... not found"
  |
  +-- STATUS = CrashLoopBackOff / Error,
  |   RESTARTS keeps rising -------------------> k describe pod: Last State (Reason, Exit Code)
  |                                                Events: BackOff, Unhealthy + Killing (liveness)
  |                                                then  k logs POD --previous
  |
  +-- STATUS = Running but READY 0/1 ------------> Conditions: Ready=False
  |                                                Events: Unhealthy "Readiness probe failed"
  |
  +-- Node NotReady / pressure ------------------> k describe node: Conditions + Events (ns default)
  |                                                then the kubelet on the node (Part 4)
  |
  +-- Running, READY 1/1, app answers wrong -----> k logs POD  (Events will not help)

Events empty?  --> wrong namespace? -A.  older than 1 hour (TTL)? --> reproduce the failure, read again.
```

Walkthrough:

1. Always start with `k get ... -A -o wide`. It tells you whether the object exists, where it runs and what `STATUS` kubectl derived. That one word picks the branch.
2. `Pending` has two sub-cases. `NODE <none>` means the scheduler has not chosen a node, so the answer is a `FailedScheduling` event from `default-scheduler`. If a node is set, the kubelet has the Pod and the problem is on the node (mounts, image, sandbox).
3. Image and config errors show in the `STATUS` text itself (`ImagePullBackOff`, `CreateContainerConfigError`). The `Failed` event message gives the exact cause (tag not found, ConfigMap name).
4. A restarting container needs two reads: `Last State` in `describe` (what ended it, exit code) and then `k logs --previous` (what it said before dying). Events only say that restarts happen.
5. `Running` but `0/1 READY` is a readiness problem. `Running` and `1/1` with a wrong answer is the application, so go to logs.
6. If you see nothing, suspect the namespace or the 1 hour TTL before suspecting the cluster.

## 4. Commands and YAML you must produce fast

**Imperative shortcuts**

```bash
k get events -A --sort-by=.lastTimestamp | tail                  # newest events cluster-wide (if order looks wrong, sort by .metadata.creationTimestamp)
k get events -n NS --sort-by=.metadata.creationTimestamp         # one namespace, reliable order
k get events -w                                                  # live stream; Ctrl-C to stop
k get events -n NS --field-selector involvedObject.name=POD      # events of one object
k get events -A --field-selector type=Warning                    # only problems
k events --for pod/web --types=Warning                           # same idea, simplest syntax
k events -A --types=Warning                                      # all warnings, all namespaces
k describe pod web | sed -n '/^Events:/,$p'                      # only the Events part of describe
k wait --for=condition=Ready pod/web --timeout=60s               # block until Ready (exit 0) or fail after 60s
k wait --for=jsonpath='{.status.phase}'=Bound pvc/data           # wait on any field
k get pod web -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}'   # one condition value
```

The report from the entry (a custom-columns table of every Warning in the cluster):

```bash
k get events --field-selector type=Warning -A -o custom-columns=NS:.metadata.namespace,OBJ:.involvedObject.name,REASON:.reason,MSG:.message
```

For a report you reuse, put the columns in a file (first line headers, second line paths) and pass `-o custom-columns-file=cols.txt`:

```bash
printf 'NS  OBJ  REASON  MSG\n.metadata.namespace  .involvedObject.name  .reason  .message\n' > ~/lab/t208/cols.txt
k get events -A --field-selector type=Warning -o custom-columns-file=$HOME/lab/t208/cols.txt
```

**The declarative YAML.** The entry has no object to create for this topic, so the YAML you must produce fast is the *test Pod*: the quickest way to make a failure on purpose. Generate the skeleton, then add the probe:

```bash
k run bad-probe --image=busybox:1.36 $do -- sh -c 'sleep 3600' > bad-probe.yaml
```

Then edit it to this (complete, applies with `k apply -n NS -f bad-probe.yaml`):

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: bad-probe                 # Pod name; events and `--for pod/bad-probe` use it
spec:
  containers:
    - name: app                   # container name; appears in event messages and `Last State`
      image: busybox:1.36         # pinned tag, never :latest
      command: ["sh", "-c", "sleep 3600"]   # keeps the container alive; the probe decides health
      livenessProbe:              # liveness: the kubelet restarts the container when it fails
        exec:
          command: ["cat", "/tmp/healthy"]  # fails: the file does not exist (exit code 1)
        initialDelaySeconds: 2    # wait 2 s after start before the first check (default 0)
        periodSeconds: 3          # check every 3 s (default 10; minimum 1)
        failureThreshold: 1       # one failure is enough to restart (default 3; must be >= 1)
```

Risky values: `periodSeconds: 0` is rejected (minimum 1). `failureThreshold: 1` with a slow app causes restart loops, which is exactly the point of this test Pod. In real manifests give slow apps a `startupProbe` instead (see [T2.03](../part2-basics/T2.03-pods-in-depth.md)).

## 6. Common mistakes and how to fix them

| Symptom | What you will see (exact error/event text) | Cause | Fix (command) |
|---|---|---|---|
| No events shown | `describe` ends with `Events:  <none>`; `k get events` prints `No resources found in lab-t208 namespace.` | Wrong namespace, or the events expired after the 1 hour TTL | `k get events -A --sort-by=.metadata.creationTimestamp \| tail`; if the object is older than 1 hour, reproduce: `k delete pod X` (a controller recreates it) or `k rollout restart deploy/X`, then read again |
| Pod `Pending`, no obvious error | `k get pod`: `Pending`, `NODE <none>`; event `Warning FailedScheduling default-scheduler 0/3 nodes are available: ...` | The scheduler cannot place it: taints, too-large requests, selector/affinity, storage | `k describe pod X \| sed -n '/^Events:/,$p'`, then fix the matching input (see below) |
| `ErrImagePull` / `ImagePullBackOff` | `Failed to pull image "nginx:1.27-nope": ...`, `Error: ErrImagePull`, `Back-off pulling image "..."` | Tag or repository does not exist, or private registry without a pull secret | `k get pod X -o jsonpath='{.spec.containers[*].image}'`, then `k set image` or fix the Pod spec |
| `CreateContainerConfigError` | Event `Warning Failed kubelet Error: configmap "app-config" not found` (or `secret`, or `couldn't find key`) | An env var references a ConfigMap/Secret/key that does not exist | `k create configmap app-config --from-literal=mode=prod`; the kubelet retries by itself |
| `ContainerCreating` for long | `Warning FailedMount ... MountVolume.SetUp failed for volume "cfg" : configmap "app-config" not found` | A mounted ConfigMap, Secret or PVC is missing | Create the object, or fix its name in the volume |
| Restart loop | `STATUS CrashLoopBackOff`, `Warning BackOff ... Back-off restarting failed container app in pod ...` | The process exits (bad command, app error) or a probe kills it | `k describe pod X` (`Last State`, `Exit Code`), then `k logs X --previous` |
| Liveness restarts | `Warning Unhealthy ... Liveness probe failed: ...`, then `Normal Killing ... failed liveness probe, will be restarted` | Probe path/port/command wrong, or `initialDelaySeconds` too small | Fix the probe: `k edit` the Deployment or recreate the Pod |
| `Running`, `READY 0/1` | `Warning Unhealthy ... Readiness probe failed: ...`; condition `Ready=False` | Readiness probe fails (wrong port or path), so the Pod gets no Service traffic | `k get pod X -o jsonpath='{.status.conditions[?(@.type=="Ready")].message}'`, fix the probe |
| Deployment `0/3`, no Pods at all | Event on the ReplicaSet: `Warning FailedCreate ... Error creating: pods "x" is forbidden: exceeded quota: q, requested: pods=1, used: pods=2, limited: pods=2` | A ResourceQuota or an admission rule blocks Pod creation. The Event is on the ReplicaSet, not on a Pod. | `k describe rs -l app=X`, `k get resourcequota`, then raise the quota or lower the requests |
| `k wait` times out | `error: timed out waiting for the condition on pods/web` | The condition never became true in 30 s (the default), or the Pod is failing | Run `k describe pod web`; use a longer `--timeout=90s` only if events show progress (`Pulling`) |
| `k wait` fails at once | `Error from server (NotFound): pods "web" not found` | The object does not exist yet | Create it first, or use `--for=create` |
| `sort-by=.lastTimestamp` looks wrong | Old events at the bottom, `<unknown>` or odd order | `lastTimestamp` is empty on some events | `--sort-by=.metadata.creationTimestamp` |
| Empty answer file | `cat file` prints nothing | The kubectl command failed (error went to the terminal), or jsonpath matched nothing | Run the command without `> file` and read the message |

**Reasoning path: "No events shown".** Run in this order. 1) `k get pod X -n NS`: does the object exist in the namespace you think? If you get `Error from server (NotFound)`, the namespace is wrong; try `k get pod X -A`. 2) `k get events -A --sort-by=.metadata.creationTimestamp | tail`: if events appear in another namespace you were looking in the wrong place. 3) Check the object age (`AGE` column). Older than 1 hour means the TTL removed the events; the default of `--event-ttl` is `1h0m0s`. 4) Make the failure happen again (`k delete pod X` for a Pod owned by a controller; `k rollout restart` for a Deployment). Wait 10 to 30 seconds and read again. 5) If still nothing, the problem is inside the container: use `k logs`.

**Reasoning path: "Pod Pending, no obvious error".** 1) `k get pod X -o wide`: `NODE <none>` means the scheduler is the culprit. 2) `k describe pod X | sed -n '/^Events:/,$p'`. The one `FailedScheduling` line holds the answer: `0/3 nodes are available:` then a comma list, each item `COUNT reason`. Each item is `COUNT reason`. One node can be counted under more than one phrase (for example both `Insufficient cpu` and `Insufficient memory`), so the counts can add up to more than the node count. 3) Map the phrase to the fix:

| Phrase in the message | Cause | Fix |
|---|---|---|
| `node(s) had untolerated taint(s)` | The node has a taint the Pod does not tolerate (the control-plane node always has one on kind and kubeadm) | Add a `tolerations` entry, or use other nodes |
| `Insufficient cpu` / `Insufficient memory` | `requests` larger than any node's free allocatable | Lower `requests`. Compare with `k describe node \| sed -n '/^Allocated resources:/,/^Events:/p'` |
| `node(s) didn't match Pod's node affinity/selector` | `nodeSelector` or `nodeAffinity` matches no node | Fix the label in the Pod, or label a node on purpose: `k label node NODE key=value` |
| `persistentvolumeclaim "x" not found` | The Pod mounts a PVC that does not exist | Create the PVC |

If the message contains text you do not recognize, copy a short part into the kubernetes.io search box. 4) Prove the fix: `k get pod X -o wide` shows a NODE.

## 8. Exam tips

- First move on any broken workload: `k get <kind> -A -o wide`, then `k describe` and read from `Events:` upward. Use `k describe pod X | sed -n '/^Events:/,$p'` to skip the noise. This takes under 30 seconds and finds most causes.
- Use `k get events -A --field-selector type=Warning --sort-by=.metadata.creationTimestamp` for "something somewhere is wrong". Sort by `.metadata.creationTimestamp`, because `.lastTimestamp` can be empty.
- Replace `sleep` with `k wait --for=condition=Ready pod/X --timeout=60s`. Remember the default timeout is 30 s and that waiting for a missing object fails immediately.
- When a task says "write ... to a file", extract only the value (`-o jsonpath`), create the directory first, and check the file with `cat -A`. Do not rely on `jq`. The host tools listed are kubectl, `yq`, `curl`, `wget` and `man` (https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad).
- Docs pages to open (allowed docs site, https://kubernetes.io/docs): https://kubernetes.io/docs/reference/kubectl/generated/kubectl_events/ , https://kubernetes.io/docs/tasks/debug/debug-application/debug-pods/ , https://kubernetes.io/docs/reference/kubernetes-api/cluster-resources/event-v1/ and the kubectl Quick Reference https://kubernetes.io/docs/reference/kubectl/quick-reference/ . The kubectl help (`k events --help`, `k wait --help`) has copyable examples and works offline.
- Traps before moving on: right namespace (`-n`)? Events older than 1 hour are gone, so reproduce the failure. Events about a Deployment's Pods may sit on the ReplicaSet. `Normal` reasons like `Killing` and `Pulled` can matter, so do not filter to Warning only when a Pod restarts.

10. Where do the Events about a Node appear (which namespace), and why?

<details><summary>Answers</summary>

1. `k events --for pod/web --types=Warning` (add `-n NS` if needed). The `get` form is `k get events --field-selector involvedObject.name=web,type=Warning`.
2. `lastTimestamp` can be empty on events written through the newer events API, and empty values sort together. Use `--sort-by=.metadata.creationTimestamp`, which is always set.
3. The API server removes Events after the TTL (`--event-ttl`, default 1 hour). Conditions and `Last State` remain. Reproduce the failure (delete the Pod so its controller recreates it, or `rollout restart`) and read the new events.
4. `--event-ttl` on kube-apiserver; the default is `1h0m0s`.
5. The `default-scheduler`; the reason is `FailedScheduling`, and the message lists why each node was rejected.
6. `Waiting`, `Running`, `Terminated`. `Last State` holds the previous run (reason and exit code), which is how you see why a container in `CrashLoopBackOff` died.
7. `MemoryPressure`, `DiskPressure`, `PIDPressure` (and `NetworkUnavailable`) should be `False`. `Ready` should be `True`.
8. Success: `pod/web condition met`, exit code 0. Timeout: `error: timed out waiting for the condition on pods/web`, exit code 1.
9. The ReplicaSet: `k describe rs -l app=NAME`. Expect `FailedCreate` (for example `exceeded quota`), because the controller could not create Pods.
10. In `default`, because a Node has no namespace and the recorder falls back to `default`. `k describe node` shows them without you choosing a namespace.
