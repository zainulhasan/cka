## 1. Why this matters

Both exams are timed command-line tasks: the Linux Foundation says they consist of 15-20 performance-based tasks and last 2 hours (sources: https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad and https://docs.linuxfoundation.org/tc-docs/certification/faq-cka-ckad-cks). That is about 6 minutes per task, so typing a full YAML manifest by hand is too slow, and one `kubectl` command run in the wrong cluster or namespace costs the whole task. This lesson is the toolkit every later lesson assumes: pick the right context and namespace, generate YAML with `kubectl ... $do`, query exactly the data you need, change objects safely, and prove each change with a `get`.

### 2.1 kubectl, the API server, and what it really does

`kubectl` is a command-line HTTP client. Every command becomes one or more REST calls to the API server (the front door of the cluster, see [T2.01](../part2-basics/T2.01-kubernetes-architecture-and-the-api-model.md)). `kubectl get pods` is `GET /api/v1/namespaces/<ns>/pods`. `kubectl create deploy` is a `POST`. `kubectl delete` is a `DELETE`. Nothing runs on your laptop except the request building and the output formatting.

**Under the hood.**

1. kubectl finds the kubeconfig file (section 2.2) and reads the current context. This tells it which server URL to call, which credentials to send, and which namespace to use when you do not pass `-n`.
2. kubectl asks the API server which resource types exist (the discovery call). That is how `k get po`, `k get pods` and `k get pod` all map to the same type. It caches the answer under `~/.kube/cache`.
3. The API server authenticates you, checks authorization (RBAC), runs admission (mutation and validation), and only then stores the object in etcd.
4. kubectl prints the reply. Add `-v=6` to any command to see each HTTP request it made; `-v=8` adds response bodies. Use this when a command behaves strangely.

Two consequences matter for speed. First, kubectl needs no cluster-side install, so anything you do imperatively is just a quick way to produce the same object a YAML file would produce. Second, the server is the source of truth: client-side checks are weak (section 2.7), so verify with a `get` after every change.

### 2.2 kubeconfig: clusters, users, contexts

A kubeconfig is a YAML file that answers three questions: where is the API server and which CA do I trust (a **cluster** entry), who am I and how do I prove it (a **user** entry), and which pair do I use right now and in which default namespace (a **context** entry). The `current-context` field points at one context. Without this file you would have to type `--server`, `--certificate-authority`, `--client-certificate` and `--client-key` on every command. Without contexts you could not hold several clusters in one file and switch safely.

**Where kubectl looks** (from `kubectl config --help` on v1.37.1):

| Order | Rule |
|---|---|
| 1 | `--kubeconfig <file>`: only that file is loaded, no merging. The flag may be set once. |
| 2 | `$KUBECONFIG` (a colon-separated list on Linux): all files are merged. When a value is modified, it is modified in the file that defines it. When a value is created, it is created in the first file that exists. |
| 3 | Otherwise `$HOME/.kube/config`, no merging. |

**The fields.**

| Section | Key fields | Meaning |
|---|---|---|
| `clusters[].cluster` | `server`, `certificate-authority-data` (or `certificate-authority`) | URL and CA of one API server. `insecure-skip-tls-verify: true` turns off server checking; it is risky and only for throwaway labs. |
| `users[].user` | `client-certificate-data` + `client-key-data`, or `token`, or `exec` | The credentials. Anyone with this file and the key can act as you, so never paste it unredacted. |
| `contexts[].context` | `cluster`, `user`, `namespace` (optional) | A named triple. If `namespace` is missing, the default is `default`. |
| top level | `current-context` | The context used when you pass no `--context`. |

**Commands you must know.**

| Task | Command |
|---|---|
| List contexts (`*` marks the current one) | `k config get-contexts` |
| Print the current context name | `k config current-context` |
| Switch context | `k config use-context kind-lab` |
| Set the default namespace of the current context | `k config set-context --current --namespace=dev` |
| Create a context from an existing cluster and user | `k config set-context ops --cluster=kind-a --user=kind-a --namespace=alpha` |
| Rename / delete a context | `k config rename-context OLD NEW` / `k config delete-context NAME` |
| List cluster and user entries | `k config get-clusters` / `k config get-users` |
| Show only the active context's data | `k config view --minify` |
| Run one command in another context without switching | `k get pods --context kind-b -n beta` |

`k config view` hides certificate and key data (`DATA+OMITTED`). Add `--raw` to see them. Do that only when you must.

(`kind-a` and `kind-b` were created for this capture with `k config set-context` and `k config rename-context`; kind itself creates one context per cluster, named `kind-<cluster name>`.)

**The two settings people confuse.** A *context* picks a cluster and a user. A *namespace* picks a partition inside that cluster. `use-context` changes the first. `set-context --current --namespace=...` changes the second and leaves the context in place. Switching context does not switch namespace in a useful way: each context remembers its own default namespace.

**What breaks without this knowledge.** You create the Deployment in `default` because the task said "in namespace dev" and you forgot `-n dev` (section 6, mistake 1). Or the task is about the second cluster and you change the first one. Exam advice: at the start of each task run `k config current-context` and `k config view --minify | grep namespace`, or set the namespace once with `set-context --current --namespace=...` and verify.

### 2.3 Selecting objects: -n, -A, -l, --field-selector

| Flag | Meaning | Example |
|---|---|---|
| `-n NS`, `--namespace NS` | Use namespace `NS` for this command only | `k get pods -n kube-system` |
| `-A`, `--all-namespaces` | List across every namespace (adds a NAMESPACE column) | `k get pods -A` |
| `-l`, `--selector` | Filter by **labels**. Supports `=`, `==`, `!=`, `key`, `!key` and set forms `in`, `notin` | `k get pods -l app=web`, `-l 'app in (web,busy)'` |
| `--field-selector` | Filter by **object fields** (server side). Only a few fields are supported per type; `metadata.name` and `metadata.namespace` work everywhere, Pods also support `status.phase` and `spec.nodeName` | `k get pods --field-selector status.phase=Running` |
| `--show-labels` | Add a LABELS column | `k get pods --show-labels` |
| `--sort-by` | Sort by a JSONPath expression | `k get pods --sort-by=.metadata.creationTimestamp` |

A label is a key/value tag stored in `metadata.labels`. A label selector is a query over those tags; Services, Deployments and `kubectl` all use the same syntax. A field selector queries real fields rather than tags, which is why you can ask for `status.phase=Running` even though no one labelled the Pod that way.

### 2.4 Reading objects: get, describe, explain, logs, exec, cp, port-forward, top

| Command | What it does | Use it when |
|---|---|---|
| `k get TYPE [NAME]` | Table (or other format) of objects | First look, every time |
| `k describe TYPE NAME` | Human summary of one object plus its **Events** (scheduler, kubelet and controller messages) | A Pod is Pending, crashing, or a Service has no backends. Read the Events at the bottom first. |
| `k explain PATH` | Schema docs for any field, from the API server's own OpenAPI data | You forgot a field name. This is your offline docs. |
| `k logs POD` | Container stdout/stderr | Application errors |
| `k exec POD -- CMD` | Run a command inside a container | Check files, env, DNS, connectivity |
| `k cp SRC DST` | Copy files to/from a container (needs `tar` inside the image) | Pull a file out for inspection |
| `k port-forward POD LOCAL:REMOTE` | Tunnel a local port to a Pod port | Test an app without a Service |
| `k top nodes\|pods` | CPU and memory use | Needs the metrics-server add-on |

**describe.** Read it from the bottom. REAL OUTPUT (kind v0.33.0, v1.37.0), last lines of `k describe pod web`:

```text
Events:
  Type    Reason     Age   From               Message
  ----    ------     ----  ----               -------
  Normal  Scheduled  37s   default-scheduler  Successfully assigned lab-t202/web to k-t202-worker
  Normal  Pulling    36s   kubelet            spec.containers{web}: Pulling image "nginx:1.27"
  Normal  Pulled     24s   kubelet            spec.containers{web}: Successfully pulled image "nginx:1.27" in 12.894s (12.894s including waiting). Image size: 68857691 bytes.
  Normal  Created    24s   kubelet            spec.containers{web}: Container created
  Normal  Started    24s   kubelet            spec.containers{web}: Container started
```

The `From` column tells you who spoke: `default-scheduler` chose the node, `kubelet` (the node agent) pulled and started the container. An image problem shows as `Failed` / `ErrImagePull` events from the kubelet; a "no node fits" problem shows as `FailedScheduling` from the scheduler.

**explain.** `k explain deploy.spec.strategy` prints the type, the field description and the child fields. Use `--recursive` to print the whole tree of field names below a path (no descriptions), which is the fastest way to see every sub-field of, say, a probe. REAL OUTPUT (kind v0.33.0, v1.37.0):

```text
$ k explain deploy.spec.strategy

    The deployment strategy to use to replace existing pods with new ones.

    RollingUpdate.

$ k explain pod.spec.containers.livenessProbe --recursive | sed -n '12,22p'

  exec	<ExecAction>
```

(Blank lines trimmed.) Types in angle brackets matter: `<integer>` takes a bare number, `<string>` may need quotes, `<[]string>` is a YAML list, `<IntOrString>` accepts `25%` or `2`, `<map[string]string>` is a key/value map. `explain` is the same data the website shows, so it works with no internet; in the exam it is often faster than searching the docs.

**logs.** Useful flags: `-f` follow, `--tail=N` last N lines, `--since=1m`, `-c NAME` pick a container in a multi-container Pod, `--previous` (or `-p`) the logs of the previous, crashed container instance, and `-l app=web` for all Pods with a label. `k logs deploy/shop` picks one Pod of the Deployment and says so. REAL OUTPUT (kind v0.33.0, v1.37.0):

```text
$ k logs deploy/shop --tail=3
Found 3 pods, using pod/shop-b6c4c6c96-kdv77
2026/10/27 08:30:19 [notice] 1#1: start worker process 42
2026/10/27 08:30:19 [notice] 1#1: start worker process 43
2026/10/27 08:30:19 [notice] 1#1: start worker process 44
```

For a CrashLoopBackOff Pod, the current container may have no output yet; the `--previous` flag asks for the last terminated one. In my capture on kind, `k logs crash --previous` printed `unable to retrieve container logs for containerd://<container id>` while `k logs crash` and `k describe pod crash` (Last State: Terminated, Reason: Error, Exit Code: 1) worked. The cause was not confirmed (see section 11). If `--previous` fails, read `Last State` and `Exit Code` in `describe`.

**exec, cp, port-forward.** REAL OUTPUT (kind v0.33.0, v1.37.0):

```text
$ k exec web -- nginx -v
nginx version: nginx/1.27.5
$ k exec busy -- sh -c 'echo hi from $(hostname)'
hi from busy
$ echo hello > f.txt; k cp f.txt busy:/tmp/f.txt; k exec busy -- cat /tmp/f.txt
hello
$ k cp busy:/tmp/f.txt back.txt
tar: removing leading '/' from member names
$ k port-forward pod/web 8081:80 &      # then, from another shell:
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:8081
200
Forwarding from 127.0.0.1:8081 -> 80
Forwarding from [::1]:8081 -> 80
Handling connection for 8081
```

Why `200` comes before the `Forwarding from` lines: the three `port-forward` lines are printed by the background job, and the capture shows them after the `curl` result. In your terminal they appear as soon as the tunnel is ready, mixed in with whatever you type next. Notes. Put `--` between the Pod name and the command so kubectl does not parse the command's flags. Add `-it` for an interactive shell (`k exec -it web -- sh`); `-i` keeps stdin open and `-t` allocates a terminal. `-c NAME` picks the container. The `tar:` line from `cp` is a harmless warning, not an error. `port-forward` stays in the foreground until Ctrl+C; run it with `&` or in a second terminal. It binds to localhost only by default.

**top.** Needs metrics-server (see `env/kind-addons.sh metrics-server`). Without it, REAL OUTPUT (kind v0.33.0, v1.37.0):

```text
$ k top nodes
error: Metrics API not available
```

With it, `k top pods -n NS` prints NAME, CPU(cores), MEMORY(bytes), and `--sort-by=cpu` (or `--sort-by=memory`) orders the rows with the biggest user first. `k top nodes` prints NAME, CPU(cores), CPU(%), MEMORY(bytes), MEMORY(%). `CPU(cores)` is in millicores (`250m` is a quarter of one core); `MEMORY(bytes)` is in `Mi`. The numbers come from metrics-server, which averages over a short window, so a Pod that started a few seconds ago may be missing from the list. EXPECTED OUTPUT (not captured), `<n>` are placeholders:

```text
$ k top pods -n kube-system --sort-by=cpu
NAME         CPU(cores)   MEMORY(bytes)
<pod name>   <n>m         <n>Mi
```

This block is listed in section 11.

### 2.5 Output formats

`-o` (`--output`) controls how `get` prints. Choose by what you need.

| Format | Use | Example |
|---|---|---|
| (default table) | Quick look. Columns depend on the type (see below). | `k get pods` |
| `-o wide` | More columns (Pods: IP, NODE, NOMINATED NODE, READINESS GATES; Nodes: INTERNAL-IP, EXTERNAL-IP, OS-IMAGE, KERNEL-VERSION, CONTAINER-RUNTIME after the default five) | `k get pods -o wide` |
| `-o yaml` / `-o json` | The full object, including `status`. Source for copy-edit. | `k get pod web -o yaml` |
| `-o name` | Only `type/name`, one per line. Ideal for saving a list or for loops. | `k get pods -o name` |
| `-o jsonpath='...'` | Extract values with a JSONPath template | `k get pod web -o jsonpath='{.status.podIP}'` |
| `-o custom-columns=H:.path,...` | Your own table | `k get pods -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName` |
| `--show-labels` | Add LABELS column | |
| `-w` / `--watch` | Keep running and print every change. Ctrl+C to stop. | `k get pods -w` |

`kubectl create --help` on v1.37.1 lists these output values: json, yaml, kyaml, name, go-template, go-template-file, template, templatefile, jsonpath, jsonpath-as-json, jsonpath-file. This guide does not use `kyaml`; its details were not verified (section 11).

**Default columns** (REAL OUTPUT, kind v0.33.0, v1.37.0) are worth knowing because the exam asks you to read them quickly:

| Type | Columns |
|---|---|
| Pod | NAME, READY (ready containers / total), STATUS, RESTARTS, AGE |
| Deployment | NAME, READY (ready/desired), UP-TO-DATE, AVAILABLE, AGE |
| Service | NAME, TYPE, CLUSTER-IP, EXTERNAL-IP, PORT(S), AGE |
| Node | NAME, STATUS, ROLES, AGE, VERSION |

`RESTARTS` can also read like `1 (31s ago)`: one restart, 31 seconds ago.

REAL OUTPUT (kind v0.33.0, v1.37.0):

```text
$ k get pod web -o jsonpath='{.status.podIP}{"\n"}'
10.244.1.2
$ k get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.nodeName}{"\n"}{end}'
busy	k-t202-worker2
shop-b6c4c6c96-ck49m	k-t202-worker2
...
web	k-t202-worker
$ k get pods -o custom-columns=NAME:.metadata.name,IMAGE:.spec.containers[0].image,NODE:.spec.nodeName
NAME                   IMAGE          NODE
busy                   busybox:1.36   k-t202-worker2
shop-b6c4c6c96-ck49m   nginx:1.27     k-t202-worker2
...
web                    nginx:1.27     k-t202-worker
```

**Watching with `-w`.** `k get pods -w` prints the table once, then keeps running and prints one new line every time a matching object changes. It never prints "done": press Ctrl+C to stop. Use it in one terminal while you change something in another, and read the STATUS column move through its steps. EXPECTED OUTPUT (not captured), after `k run w1 --image=nginx:1.27` in a second terminal (ages will differ):

```text
$ k get pods -w
NAME   READY   STATUS    RESTARTS   AGE
w1     0/1     Pending   0          0s
w1     0/1     ContainerCreating   0          0s
w1     1/1     Running             0          <n>s
^C
```

What to look for: each state change is a new line, not a rewritten line, so the last line for a name is its current state. This block is listed in section 11.

JSONPath refresher (details in [T1.13](../part1-linux/T1.13-yaml-and-json-with-jq-yq.md)): `{.a.b}` walks keys; `[0]` indexes a list; `[*]` means every element; `{range .items[*]}...{end}` loops; `{"\n"}` and `{"\t"}` print a newline and a tab. kubectl's JSONPath is its own dialect, not `jq`. The tools list at https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad names `yq`, `curl`, `wget` and `man` and does not mention `jq`, so do not rely on `jq` in exam-style work.

### 2.6 Imperative generators and the YAML factory

An **imperative** command tells the cluster what to do now (`k create deploy ...`). A **declarative** manifest describes the end state and you `apply` it. Imperative commands are fast to type; manifests are reviewable and repeatable. The exam trick is to combine them: let the imperative command *write* the manifest, then edit and apply.

`k create --help` on v1.37.1 lists these subcommands: `clusterrole`, `clusterrolebinding`, `configmap`, `cronjob`, `deployment`, `ingress`, `job`, `namespace`, `poddisruptionbudget`, `priorityclass`, `quota`, `role`, `rolebinding`, `secret` (with `generic`, `tls`, `docker-registry`), `service` (with `clusterip`, `nodeport`, `loadbalancer`, `externalname`), `serviceaccount` and `token`. There is no `create pod`; Pods come from `k run`. `k expose` builds a Service from an existing workload.

| Want | Command | Notes (all verified with `$do` on v1.37) |
|---|---|---|
| Pod | `k run p --image=nginx:1.27 $do` | Label `run=p` is added unless you pass `--labels`. `restartPolicy: Always` unless `--restart=Never`. |
| Deployment | `k create deploy web --image=nginx:1.27 --replicas=3 $do` | Container name is the image name part (`nginx`). Label and selector `app=web`. |
| Service for a workload | `k expose deploy web --port=80 --target-port=8080` | Copies the workload's labels into the Service `selector`. Works on Pod, Deployment, ReplicaSet, Service. |
| Service from scratch | `k create service clusterip db --tcp=5432:5432 $do` | Selector is `app=<service name>`; it may not match your Pods (section 7, break-fix). |
| ConfigMap | `k create cm app --from-literal=MODE=dev --from-literal=LEVEL=3 $do` | Also `--from-file=`, `--from-env-file=`. |
| Secret | `k create secret generic db-pass --from-literal=password=S3cr3t $do` | Value is base64 in `data`. |
| Job | `k create job once --image=busybox:1.36 $do -- echo hi` | Pod `restartPolicy: Never`. |
| CronJob | `k create cronjob tick --image=busybox:1.36 --schedule='*/5 * * * *' $do -- date` | Pod `restartPolicy: OnFailure`. |
| ServiceAccount | `k create sa builder $do` | |
| Role | `k create role pod-reader --verb=get,list,watch --resource=pods $do` | |
| RoleBinding | `k create rolebinding rb --role=pod-reader --serviceaccount=lab-t202:builder $do` | `--serviceaccount` is `namespace:name`. |
| Ingress | `k create ingress ing --class=traefik --rule="web.example.com/*=shop:80" $do` | `/*` becomes `pathType: Prefix`, `path: /`. |

```text
spec:
  ports:
  - port: 80
    protocol: TCP
    targetPort: 80
  selector:
    app: shop
status:
  loadBalancer: {}
```

The empty `resources: {}`, `strategy: {}` and `status: {}` are noise; they are valid and harmless. When a command needs a command inside the container, put it after `--`: for Jobs and CronJobs it becomes `command:`; the Job above printed `command: [echo, hi]`.

**The factory pattern.** `--dry-run=client -o yaml` (your `$do`) builds the object in memory, prints it, and sends nothing. Redirect it to a file, edit the file, apply it:

```bash
k create deploy web --image=nginx:1.27 --replicas=3 $do > web.yaml
vi web.yaml            # add what the generator cannot: ports, env, volumes, probes
k apply -f web.yaml
```

Use `>` to write and always `cat` or `less` the file before applying. A generated `status: {}` block is ignored on create.

### 2.7 --dry-run=client versus --dry-run=server

| Mode | Where it runs | What it checks | Use it for |
|---|---|---|---|
| `--dry-run=client` | Only in kubectl | Builds the object from your flags or reads the file; limited schema validation. Nothing is sent for the dry-run itself | The YAML factory (`$do`) |
| `--dry-run=server` | The API server runs the full request path (decoding, defaulting, validation, admission) and stops before storing | Real validation, including rules only the server knows (types, immutable fields, quotas, admission) | "Will this manifest be accepted?" |

REAL OUTPUT (kind v0.33.0, v1.37.0). The file `bad.yaml` has `replicas: three`:

```text
$ k apply -f bad.yaml --dry-run=client
deployment.apps/web created (dry run)
$ k apply -f bad.yaml --dry-run=server
Error from server (BadRequest): error when creating "bad.yaml": Deployment in version "v1" cannot be handled as a Deployment: json: cannot unmarshal string into Go struct field DeploymentSpec.spec.replicas of type int32
$ k create deploy ok --image=nginx:1.27 --dry-run=server
deployment.apps/ok created (server dry run)
```

So a client dry-run passing proves little. Before you leave a task, `--dry-run=server` or the real `apply` plus a `get` is the proof.

### 2.8 kubectl run flags

| Flag | Effect | Default / risk |
|---|---|---|
| `--image=IMG` | Container image | Required. Pin a tag; with `latest` or no tag the node may pull a different image later. |

### 2.9 Modifying objects

| Command | What it does | Notes |
|---|---|---|
| `k apply -f FILE` | Create or update to match the file | Declarative. Records the file in the annotation `kubectl.kubernetes.io/last-applied-configuration` and does a three-way merge: it compares the last applied file, the live object and the new file, so fields set by others (for example by a controller) are kept, and fields you removed from the file since the last apply are removed. |
| `k create -f FILE` | Create only; fails with `AlreadyExists` | |
| `k edit TYPE NAME` | Opens the live object in `$KUBE_EDITOR`/`$EDITOR` and applies on save | Quick, but leaves no file. Invalid saves are rejected and reopen. |
| `k patch` | Change selected fields with a small patch | Three types, below. |
| `k set image\|env\|resources` | Edit a pod template without opening YAML | `k set --help` lists: env, image, resources, selector, serviceaccount, subject. |
| `k scale` | Change replicas of a Deployment, ReplicaSet, StatefulSet | `k scale deploy/web --replicas=4` |
| `k label` / `k annotate` | Add or change metadata | `key=value`; `key=value2 --overwrite` to change; `key-` to remove |
| `k replace -f FILE` | Replace the whole object with the file | Fails if an immutable field changes |
| `k replace --force -f FILE` | Delete then recreate | Causes downtime; a Pod gets a new UID and IP |
| `k diff -f FILE` | Show what `apply` would change; exit code 1 means differences, 0 none | |
| `k wait --for=...` | Block until a condition is true or a timeout | |
| `k auth can-i VERB RESOURCE` | Ask RBAC whether an action is allowed | |

**patch.** A patch is a partial document. The `--type` says how the server merges it:

| `--type` | Body | Lists | Use |
|---|---|---|---|
| `strategic` (default for built-in types) | JSON object | Merged by a **merge key**: the field that says which list items are "the same one" (for `containers` that key is `name`), so you can change one container without listing all of them | Most edits to Deployments and Pods |
| `merge` (JSON merge patch, RFC 7386) | JSON object | A list is **replaced** whole | CRDs (strategic is unavailable); simple scalar changes |
| `json` (RFC 6902) | JSON array of `{op, path, value}` | Edit one element by index (`/spec/ports/0/targetPort`) | Exact edits, `remove`, edits inside lists |

REAL OUTPUT (kind v0.33.0, v1.37.0):

```text
$ k patch deploy web -p '{"spec":{"replicas":2}}'
deployment.apps/web patched
$ k patch deploy web --type=merge -p '{"spec":{"template":{"spec":{"containers":[{"name":"nginx","image":"nginx:1.27"}]}}}}'
deployment.apps/web patched
$ k patch deploy web --type=json -p '[{"op":"replace","path":"/spec/replicas","value":3}]'
deployment.apps/web patched
$ k patch deploy web -p '{"spec":{"replica":3}}'
Warning: unknown field "spec.replica"
deployment.apps/web patched (no change)
```

The last command shows a trap: a misspelled field is only a **warning**, and "patched (no change)" means nothing changed. Always check the result with `get`. To see the difference between `merge` and `strategic` on a list, use server dry-run (REAL OUTPUT, kind v0.33.0, v1.37.0): the same patch that adds a container `side` gives `side` alone with `--type=merge` (the list was replaced) and `side nginx` with the default strategic patch (merged by name).

### 2.10 Deleting

| Command | Effect |
|---|---|
| `k delete pod NAME` | Graceful: the Pod gets SIGTERM, then SIGKILL after `terminationGracePeriodSeconds` (default 30 s) |
| `k delete pod NAME --grace-period=N` | Override the grace period; The flag help says `--grace-period=0` is only valid together with `--force`; without `--force`, kubectl treats 0 as 1 second (so it is the same as `--now`, not an immediate delete) |
| `k delete pod NAME --now` | Shortcut for `--grace-period=1` |
| `k delete pod NAME --force --grace-period=0` (`$now`) | Removes the object from the API immediately without waiting for the kubelet to confirm. Prints a warning: the container may still be running on the node |
| `k delete pod NAME --wait=false` | Return at once; deletion continues in the background |
| `k delete pods -l grp=del` | Delete by label |
| `k delete pod --all` | Everything of that type in the namespace |
| `k delete pod/web deploy/imp` | Several objects in one command |
| `k delete -f file.yaml` | Everything in the file |

REAL OUTPUT (kind v0.33.0, v1.37.0), timing a Pod running `sleep 3600` (it ignores SIGTERM, so the full grace period passes):

```text
default grace (30s):  pod "sl1" deleted from lab-t202 namespace   real 0m30.418s
--now:                pod "sl2" deleted from lab-t202 namespace   real 0m3.012s
--wait=false:         pod "sl3" deleted from lab-t202 namespace   real 0m0.050s
```

The `--wait=false` Pod was still `Terminating` 41 seconds later when I looked and was gone after the grace period. On the exam the 30-second wait adds up over many tasks, so for throw-away Pods use `--now` (or `$now` when the Pod is stuck). Do not use `--force` on a StatefulSet Pod or anything with storage you care about: the API says it is gone while the node may still run it.

### 2.12 .kuberc: user preferences (beta, on by default since v1.34)

`kuberc` is a file of **your kubectl preferences**: command aliases and default flags. It holds no cluster data or credentials (unlike kubeconfig). The kubernetes.io page (https://kubernetes.io/docs/reference/kubectl/kuberc/) marks it beta from v1.34. It solves the problem of retyping the same flags (`-o wide`, `--interactive`) and of building shortcuts that are real kubectl commands, not shell aliases.

- Default location: `$HOME/.kube/kuberc`. A custom path: the `--kuberc` flag, or the `KUBERC` environment variable.
- Format: `apiVersion: kubectl.config.k8s.io/v1beta1`, `kind: Preference`, with `aliases`, `defaults`, and (since v1.35, beta) `credentialPluginPolicy` / `credentialPluginAllowlist`.
- Disable it: `KUBECTL_KUBERC=false`. The help text of `--kuberc` says "This can be disabled by exporting KUBECTL_KUBERC=false feature gate".
- Explicit flags on the command line beat the defaults in the file.
- On by default since v1.34: you do not have to switch anything on. If a file exists at the default path it is read on every `kubectl` command, so a stray `~/.kube/kuberc` can change the behaviour of commands (for example a default `-o wide`). When a command behaves oddly, run it once with `KUBECTL_KUBERC=false` to rule the file out.

Example file (verified on v1.37.1):

```yaml
apiVersion: kubectl.config.k8s.io/v1beta1
kind: Preference
aliases:
  - name: getn                  # new command name; must not collide with a built-in command
    command: get                # the real command it runs (sub-commands like "create role" are allowed)
    prependArgs:                # inserted right after the command
      - nodes
    options:                    # default flag values for this alias
      - name: output
        default: wide
defaults:                       # default flag values for a real command
  - command: delete
    options:
      - name: interactive       # make "k delete" ask for confirmation
        default: "true"         # option values are strings
```

REAL OUTPUT (kind v0.33.0, v1.37.0), file saved as `/tmp/kr`:

```text
$ KUBERC=/tmp/kr kubectl getn -o name
node/k-t202b-control-plane
$ KUBECTL_KUBERC=false KUBERC=/tmp/kr kubectl getn
error: unknown command "getn" for "kubectl"

Did you mean this?
...
$ KUBERC=/tmp/kr kubectl delete pod nonexist
You are about to delete the following 1 resource(s):
pod/nonexist
Do you want to continue? (y/N): deletion is cancelled
$ kubectl --kuberc /tmp/kr getn

```

The last result is a trap: use the `KUBERC` environment variable (or put the file at the default path) when you call an alias. `kubectl kuberc view` prints the active preferences; with no file present it printed `kuberc file not found at <path>` and asked `Would you like to generate a default kuberc file with recommended options? (y/N):`. `kubectl kuberc set --section defaults --command get --option output=wide` writes values for you (from `k kuberc set --help` examples); with `--kuberc` it expected the file to exist already (section 11).

Caveat for the exam: do not assume your `~/.kube/kuberc` exists there. Whether the exam hosts ship a kuberc is UNVERIFIED; use `k` and `$do` from your own shell setup.

### 2.13 Related but different

| Pair | Difference |
|---|---|
| `create` vs `apply` | `create` fails if the object exists; `apply` creates or updates and tracks the file. |
| `apply` vs `replace` | `apply` merges changes; `replace` swaps the whole object (and fails on immutable changes). |
| `k run` vs `k create deploy` | `run` makes one bare Pod (nothing restarts it elsewhere if the node dies); `create deploy` makes a Deployment that keeps N Pods alive. |
| `--force --grace-period=0` vs `--now` | `--now` still lets the kubelet stop the container (1 s grace). `--force` removes the API object without waiting for the node. |
| Label selector (`-l`) vs field selector | Labels are tags you set; fields are the object's real data, supported for few paths. |
| `describe` vs `get -o yaml` | `describe` adds Events and readable summaries; `-o yaml` is the exact stored object. |
| `kubectl exec` vs `kubectl run` | `exec` runs inside an existing container; `run` starts a new Pod. |

### 2.14 Exam habits

- Start every task with `k config current-context` and the namespace check (section 2.2). The exam gives each task its own host and says which `ssh` command to use; the number of kubeconfig contexts is UNVERIFIED (https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad describes a separate host per task, not a context count).
- Always name the namespace, either with `-n` or via `set-context --current --namespace`.
- After every change run a `get` (or `rollout status`, `wait`) and read it.
- When the task says "save to FILE", redirect to that exact path and `cat` it.
- Never leave a half-applied file: `apply`, then `get`, then move on.

## 3. How it works (diagram)

```text
  ~/.kube/config  (or the files in $KUBECONFIG, merged)

  clusters:                       users:
  +-------------------------+     +-----------------------------+
  | name: kind-a            |     | name: kind-a                |
  | server: https://...:6443|     | client-certificate-data: .. |
  | certificate-authority.. |     | client-key-data: ..         |
  +-----------+-------------+     +--------------+--------------+
  | name: kind-b            |     | name: kind-b                |
  +-----------+-------------+     +--------------+--------------+
              |                                   |
              +-----------------+-----------------+
                                |  (cluster + user + namespace)
                                v
  contexts:
  +---------------------------------------------------------------+
  | name: kind-a   cluster: kind-a  user: kind-a  namespace: alpha|
  | name: kind-b   cluster: kind-b  user: kind-b  namespace: beta |
  | name: ops      cluster: kind-a  user: kind-a  namespace: alpha|
  +--------------------------+------------------------------------+
                             ^
                             | picks one
  current-context: kind-a ---+      <-- changed by "k config use-context"
                             |
                             v
  k get pods            -> uses kind-a, namespace alpha
  k get pods -n kube-system        -> same context, namespace overridden for this call
  k get pods --context kind-b      -> context overridden for this call only
  k config set-context --current --namespace=dev
                                   -> rewrites the namespace field of the current context
```

Walkthrough:

1. Clusters and users are separate lists. One cluster can be paired with many users, and one user with many clusters; the pairing is made only by a context.
2. A context is a named triple (cluster, user, namespace). `ops` and `kind-a` use the same cluster and user but may have different default namespaces.
3. `current-context` selects one context. Every command without `--context` uses it.
4. Flags beat the file for a single command: `--context`, `-n`, `--cluster`, `--user`, `--server`, `--kubeconfig`.
5. `use-context` rewrites only `current-context`. `set-context --current --namespace=...` rewrites only the namespace of the current context. Neither touches clusters or users.

### 4.2 The declarative YAML

You must be able to produce Pod, Deployment, Service, ConfigMap, Secret, Job and CronJob YAML purely from `kubectl create/run ... $do` in under 5 minutes total (about 40 seconds each). Below are the finished manifests with the fields the generators do not add (ports, env, backoff) and every field explained. All seven were applied with `kubectl apply -f` on v1.37.0 with no errors. They go in namespace `lab-t202`; create it first with `k create ns lab-t202`.

```yaml
# pod.yaml
apiVersion: v1                  # core group: Pods, Services, ConfigMaps, Secrets live here
kind: Pod
metadata:
  name: web                     # unique within the namespace
```

**Risky or invalid values to remember.**

| Field | Default | Invalid or risky |
|---|---|---|
| Deployment `spec.selector` | none (required) | Must match `template.metadata.labels`; changing it later is rejected |
| Deployment `spec.replicas` | 1 | `"three"` fails server validation (section 2.7) |
| Pod `restartPolicy` | `Always` | Job/CronJob Pods must be `Never` or `OnFailure` |
| Service `targetPort` | same as `port` | A port nobody listens on gives timeouts or refused connections (section 5) |
| ConfigMap `data` values | strings | Unquoted `3` or `true` is rejected |
| Secret `data` | base64 | `data` needs base64; `stringData` takes plain text. Base64 is encoding, not encryption. |
| CronJob `concurrencyPolicy` | `Allow` | `Allow` lets slow runs pile up |
| Job `backoffLimit` | 6 | Too high hides a broken command for a long time |

## 5. Worked example

Goal: create namespace `lab-t202`, run a 3-replica Deployment, expose it, find and fix a wrong `targetPort`, update the image, and verify each step. Environment: kind (`kind-lab` context). Start from a cluster with no `lab-t202` namespace. All blocks below are REAL OUTPUT (kind v0.33.0, v1.37.0) unless noted; long outputs are trimmed with `...`.

**Step 1. Namespace and context default.** Every later command now lands in `lab-t202` without `-n`.

Read this carefully. The Service **has** endpoints (three Pod IPs), so the selector is right. The endpoint port is `8080`, which is the problem. Having endpoints does not mean the port works.

**Step 5. Test from inside the cluster.** A throw-away Pod with `wget` (busybox):

```text

pod lab-t202/probe terminated (Error)
```

A timeout (or a refused connection) from a Service that has endpoints usually means: traffic is forwarded to a port where nothing listens. It is not the only cause: a NetworkPolicy that drops the traffic also gives a timeout. To tell them apart, (1) compare `k get svc web -o jsonpath='{.spec.ports[0].targetPort}'` (prints `8080`) with the port the container actually serves (`80`); (2) test the Pod directly, bypassing the Service: take a Pod IP from `k get pods -l app=web -o wide`, then run the same probe against `POD_IP:80` and `POD_IP:8080`. If port 80 answers and 8080 does not, the Service's `targetPort` is wrong. If neither answers, look at the Pod and at NetworkPolicies instead.

**Step 6. Fix it with a JSON patch** (the exact element is `ports[0].targetPort`, which is what `--type=json` is for), then test again:

```text

service/web patched
$ k run probe --image=busybox:1.36 --rm -i --restart=Never -- wget -qO- -T 3 web 2>&1 | head -6
```

## 6. Common mistakes and how to fix them

| # | Symptom | What you will see (exact text) | Cause | Fix (command) |
|---|---|---|---|---|
| 1 | Resource created in the wrong namespace | `k get pods` shows the new Pod in `default`, or `k get pods -n dev` shows `No resources found in dev namespace.`; `k apply -f` with a namespaced manifest and a different `-n` prints `error: the namespace from the provided object "lab-t202" does not match the namespace "other". You must pass '--namespace=lab-t202' to perform this operation.` | `-n` was forgotten and the context namespace is `default` | `k config set-context --current --namespace=dev`; then move the object: `k get pod web -o yaml` to a file, delete the wrong one, `k apply -f file -n dev` |
| 2 | `kubectl run` made a Pod, not a Deployment | `k run web2 --image=nginx:1.27 --replicas=3` prints `error: unknown flag: --replicas`; without the flag `k get deploy` prints `No resources found in default namespace.` and only `pod/web2` exists | Modern `run` creates a single Pod | `k create deploy web2 --image=nginx:1.27 --replicas=3` |
| 3 | Patch rejected | `error decoding patch: json: cannot unmarshal object into Go value of type []handlers.jsonPatchOp` (object sent with `--type=json`); `error decoding patch: json: cannot unmarshal array into Go value of type map[string]interface {}` (array sent with `--type=merge`); `error: --type must be one of [json merge strategic], not "foo"` | The body does not fit the patch type | JSON patch needs an array of `{op,path,value}`; merge and strategic need an object. Use `--type=json` for list edits, `--type=merge` for CRDs |
| 4 | `apply` warns about the last-applied annotation | `Warning: resource deployments/imp is missing the kubectl.kubernetes.io/last-applied-configuration annotation which is required by kubectl apply. ...The missing annotation will be patched automatically.` | The object was created imperatively with `k create` | Nothing is broken. For clean tracking create with `k apply -f` or `k create -f f.yaml --save-config` and keep using `apply` |
| 5 | Deployment rejected on apply | `The Deployment "web" is invalid: spec.template.metadata.labels: Invalid value: {"app":"webapp"}: `selector` does not match template `labels`` | Selector and template labels differ | Make `spec.selector.matchLabels` equal `template.metadata.labels` |
| 6 | Service has no endpoints | `k describe svc web-svc` shows `Selector: app=web-svc` and an empty `Endpoints:`; EndpointSlice shows `<unset>` | `k create service clusterip` sets selector `app=<service name>` | `k patch svc web-svc -p '{"spec":{"selector":{"app":"web"}}}'` or generate with `k expose` |
| 7 | Misspelled field in a patch looks successful | `Warning: unknown field "spec.replica"` and `deployment.apps/web patched (no change)` | Server only warns about unknown fields in patches | Check spelling with `k explain deploy.spec`, then `get` to confirm |
| 8 | `replace` refused | `The Pod "imm" is invalid: spec: Forbidden: pod updates may not change fields other than ...` | Pod fields are immutable | `k replace --force -f file` (or `k delete` then `k apply`) |

**Mistake 1, the diagnostic path.** (1) `k config current-context` and `k config view --minify | grep namespace:` show where you are. (2) `k get pods -A | grep NAME` finds the stray object; the NAMESPACE column is the answer. (3) Fix the default with `set-context --current --namespace=dev`. (4) Recreate the object in the right namespace and delete the wrong one with `k delete pod NAME -n default`. Reading: a result `No resources found in dev namespace.` is often the first sign you looked in the wrong place.

**Mistake 2, the diagnostic path.** (1) `k get deploy,pod` right after the command. (2) If only a `pod/` line exists and there is no ReplicaSet, it was a bare Pod. (3) Delete it (`k delete pod web2 --now`) and use `k create deploy`. The reason it matters: a bare Pod is not rescheduled if its node fails and cannot be scaled.

**Mistake 3, the diagnostic path.** (1) Read the first words of the error: `error decoding patch` means the body parse failed before any field was checked. (2) Compare the body with the type table in section 2.9. (3) If you need to edit an element in a list, switch to `--type=json` with the list index. (4) If the resource is a custom resource, use `--type=merge`. Older material reports the text `unable to find api field` for a patch whose body does not fit the object. I could not reproduce that phrase on v1.37.0 with several wrong strategic patches, so it is not in the exact-text column above and I cannot say which path produces it. The wrong strategic patches I tried gave `cannot restore slice from map`, `does not contain declared merge key: name`, `unrecognized type: int32`, or only the `unknown field` warning, all REAL OUTPUT (kind v0.33.0, v1.37.0). If you ever see `unable to find api field`, treat it as the same family of problem (a field name or structure that does not exist in the object, or the wrong patch type) and fix it the same way: check the path with `k explain`, and pick the patch type from the table in section 2.9. See section 11.

**Mistake 4, the diagnostic path.** (1) `k get deploy imp -o yaml | grep last-applied` shows the annotation was absent. (2) The warning appears once; the second `apply` is silent. (3) Pick one workflow per object. Mixing `create` and `apply` is the cause; it does not damage data.

**Mistake 5, the diagnostic path.** The error appears at `apply`, nothing is created (`k get deploy` shows nothing). (1) `k explain deploy.spec.selector` says "It must match the pod template's labels." (2) `grep -n -B1 -A2 'labels:' web.yaml` compares both blocks. (3) Fix the YAML and apply again.

**Mistake 6, the diagnostic path.** (1) `k get svc` shows a ClusterIP, which proves nothing. (2) `k describe svc web-svc` shows the selector. (3) `k get pods --show-labels` shows the Pods' labels. (4) The two do not overlap, so the endpoint list is empty. Fix whichever is easier, then `k get endpointslice -l kubernetes.io/service-name=web-svc` must list Pod IPs.

### 7.3 Break-fix: manifests generated with the wrong flags

Environment: kind (`kind-lab`). Setup, which injects the fault (`break.sh`):

```bash

cat > break.sh <<'EOF'

k create service clusterip web-svc --tcp=80:80 $do > svc.yaml
EOF
source break.sh
```

(`sed -i` here is GNU sed on Linux; on macOS use `sed -i ''`.) `break.sh` is saved in `~/lab/T2.02`. Sourcing it leaves your shell inside `~/lab/T2.02/bf`, where you now have `web.yaml` and `svc.yaml`.

Task (exam style). In namespace `lab-t202`, the manifests in `~/lab/T2.02/bf` must create Deployment `web` (3 Ready Pods) and a Service `web-svc` that sends traffic on port 80 to those Pods. Apply both files. Fix the files; do not rewrite them from scratch and do not use `kubectl edit`.

<details><summary>Hint 1: read the first error</summary>

`k apply -f web.yaml` fails and prints which field is wrong. After you fix that, apply the other file and check whether it actually has backends.

</details>

<details><summary>Hint 2: Services need matches</summary>

`k describe svc web-svc` shows `Selector:` and `Endpoints:`. Compare the selector with `k get pods --show-labels`.

</details>

<details><summary>Hint 3: where the selector came from</summary>

`k create service clusterip` chooses the selector from the Service's own name. Compare it with the label the Deployment's Pods carry.

</details>

<details><summary>Solution</summary>

Diagnose (REAL OUTPUT, kind v0.33.0, v1.37.0):

```text
$ k apply -f web.yaml
The Deployment "web" is invalid: spec.template.metadata.labels: Invalid value: {"app":"webapp"}: `selector` does not match template `labels`
$ k apply -f svc.yaml
service/web-svc created
$ k get endpointslice -l kubernetes.io/service-name=web-svc
NAME            ADDRESSTYPE   PORTS     ENDPOINTS   AGE
web-svc-wgqvt   IPv4          <unset>   <unset>     0s

Endpoints:
```

Fault 1: the Deployment's `spec.selector.matchLabels` is `app: web` but `template.metadata.labels` is `app: webapp`. The API requires the selector to match the template, so nothing was created. Fault 2: the Service applied cleanly, but its selector is `app: web-svc` (the generator used the Service name), which no Pod carries, so it has no endpoints; a Service with an empty endpoint list accepts no traffic and `get svc` still looks healthy.

Fix:

```bash

sed -i 's/app: web-svc/app: web/' svc.yaml                       # Service selector -> app: web

k apply -f svc.yaml
k rollout status deploy/web
```

## 8. Exam tips

- Set up the shell first: `alias k=kubectl`, `export do="--dry-run=client -o yaml"`, `export now="--force --grace-period=0"`. The hosts provide kubectl with an alias and Bash autocompletion; the exact alias name is UNVERIFIED (source: https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad). Your own `k` costs ten seconds.
- Before each task: `k config current-context` and the namespace check. Then type the namespace in the command anyway when the task names one.
- Generate, do not type: `k run`/`k create ... $do > f.yaml`, edit, `k apply -f f.yaml`, then `k get` (or `k wait`, `k rollout status`). Use `k explain ...` for a field you forgot; open the `kubectl` Quick Reference when you need a flag: https://kubernetes.io/docs/reference/kubectl/quick-reference/ . Other pages to bookmark: https://kubernetes.io/docs/reference/kubectl/conventions/ , https://kubernetes.io/docs/reference/kubectl/kuberc/ , https://kubernetes.io/docs/concepts/configuration/organize-cluster-access-kubeconfig/ . Allowed docs are listed at https://docs.linuxfoundation.org/tc-docs/certification/certification-resources-allowed (kubernetes.io/docs, kubernetes.io/blog, helm.sh/docs, and gateway-api.sigs.k8s.io for the CKA only).
- Save output to the exact path the task gives, then `cat` it. Use `-o name` for lists of names and `-o jsonpath` for single values; do not rely on `jq` (the tools list at the LF tips page names `yq`, `curl`, `wget` and `man` and does not list `jq`).
- Traps: a bare `k run` is one Pod, not a Deployment; `--labels` replaces the default `run` label; `create service` selects `app=<name>`; a passing client dry-run does not prove validity; the default Pod delete waits up to 30 seconds (use `--now`); a typo in a patch is only a warning.
- Do not spend more than the average (about 6 minutes) on one task; mark it and move on (pace from the 2 hours and 15-20 tasks cited in section 1).

## 9. Quick review

1. What command shows which contexts exist and which is active?
   <details><summary>Answer</summary>`k config get-contexts` (the `*` marks the current one). `k config current-context` prints only the name.</details>
2. A task says "in namespace dev". You do not want to type `-n dev` on every command. What do you run, and what does it change?
   <details><summary>Answer</summary>`k config set-context --current --namespace=dev`. It rewrites the `namespace` field of the current context in the kubeconfig; cluster, user and current-context stay the same.</details>
3. Why does `k run web --image=nginx:1.27 --replicas=3` fail, and what do you use instead?
   <details><summary>Answer</summary>`k run` has no `--replicas`; it makes one Pod (`error: unknown flag: --replicas`). Use `k create deploy web --image=nginx:1.27 --replicas=3`.</details>
4. Write the one-line command that produces Deployment YAML in a file without touching the cluster.
   <details><summary>Answer</summary>`k create deploy web --image=nginx:1.27 --replicas=3 $do > web.yaml` where `$do` is `--dry-run=client -o yaml`.</details>
5. Why can a manifest pass `--dry-run=client` and still be rejected?
   <details><summary>Answer</summary>Client dry-run does little validation. In the capture, `replicas: three` passed client dry-run and failed with `cannot unmarshal string into Go struct field ... of type int32` under `--dry-run=server`, which runs the real validation and admission path.</details>
6. You need to change `targetPort` of the first port of a Service. Which patch type and why?
   <details><summary>Answer</summary>`--type=json` with `[{"op":"replace","path":"/spec/ports/0/targetPort","value":80}]`, because it addresses a list element by index. A merge patch would replace the whole list.</details>
7. What is the difference between `k delete pod x --now` and `k delete pod x --force --grace-period=0`?
   <details><summary>Answer</summary>`--now` means grace period 1 second and still waits for the kubelet to stop the container. `--force --grace-period=0` removes the object from the API without waiting for the node, so the container may still run; it prints a warning.</details>
8. A Service has three endpoints but a request times out. What do you compare?
   <details><summary>Answer</summary>The Service's `targetPort` (`k get svc X -o jsonpath='{.spec.ports[0].targetPort}'`) with the port the container really listens on. Endpoints prove the selector matches; they do not prove the port is right.</details>
9. How do you list only the names of the Running Pods and write them to a file?
   <details><summary>Answer</summary>`k get pods --field-selector status.phase=Running -o name > file`. Wait for rollouts first, because terminating Pods still count as Running.</details>
10. Where does a `kuberc` file live, how do you turn it off, and what is the catch with aliases?
    <details><summary>Answer</summary>Default `$HOME/.kube/kuberc` (or the `KUBERC` variable / `--kuberc`). Turn it off with `KUBECTL_KUBERC=false`. The `--kuberc` flag cannot come before an alias name (`flags cannot be placed before plugin name`), so use `KUBERC=path kubectl alias ...`.</details>
11. What does `k auth can-i get pods --as=system:serviceaccount:lab-t202:builder` tell you, and when do you use it?
    <details><summary>Answer</summary>Whether that ServiceAccount may get Pods in the current namespace (yes/no). Use it to prove an RBAC change worked.</details>
