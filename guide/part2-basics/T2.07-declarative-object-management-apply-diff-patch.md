## 1. Why this matters

On the exam you mix two kinds of work: creating objects fast with imperative commands, and changing objects that already exist. The wrong method for the second kind either breaks the object (a `replace` that wipes fields, a `--force` that deletes a Deployment) or silently undoes someone else's change (an `apply` that resets replicas every time). In real clusters the same mistakes cause outages and "who changed this?" arguments. Server-side apply and `kubectl diff` are also the engine under Helm upgrades, Kustomize and GitOps tools, so understanding them explains what those tools do when they "sync" a cluster.

### 2.1 Three ways to manage objects

Kubernetes stores objects in the API server. Every `kubectl` command that changes something ends up as one HTTP request: `POST` (create), `PUT` (replace the whole object), `PATCH` (change part of it) or `DELETE`. What differs between the techniques is who decides which request to send and how much kubectl remembers about your intent.

| Technique | Example | You give kubectl | Request sent | Trace left on the object |
|---|---|---|---|---|
| Imperative commands | `k create deploy web --image=nginx:1.27`, `k scale`, `k set image`, `k label` | A verb and flags | `POST` or `PATCH` | Only the new values, plus a field manager such as `kubectl-scale` |
| Imperative object configuration | `k create -f d.yaml`, `k replace -f d.yaml`, `k delete -f d.yaml` | A file and a verb you choose | `POST`, `PUT`, `DELETE` | Nothing extra (unless `create --save-config`) |
| Declarative object configuration | `k apply -f d.yaml`, `k apply -f dir/ -R`, `k apply -k dir/` | A file (or directory) that describes the end state | `PATCH` (or `POST` the first time) | Client-side: the `last-applied-configuration` annotation. Server-side: `managedFields` |

Why three? Imperative commands are fastest for one change and for generating YAML (`$do`). Imperative configuration puts the state in a file but you still choose create or replace, so running the same command twice either errors (`create`) or overwrites everything (`replace`). Declarative configuration lets you run the same command forever: kubectl (or the API server) works out what changed. That is why teams keep manifests in git and run `apply`.

What breaks if you mix them blindly: `create` on an existing name fails with `AlreadyExists`; `apply` on an object made by `create` prints a warning (section 2.2); `replace` on an object other people edit erases their fields; `apply` on a field that a controller also writes (replicas with an HPA) makes both sides fight (section 6).

Real output of the first two failures is in section 5. Rule of thumb for the exam: create with an imperative command or `$do`, change with the smallest tool that does the job, and use `apply` when you are given a YAML file.

### 2.2 Client-side apply and the last-applied-configuration annotation

`kubectl apply -f file` without extra flags is **client-side apply** (CSA). kubectl does the thinking on your machine. To change an object it needs three inputs, a "three-way merge":

| Input | Where it comes from |
|---|---|
| New configuration | Your file |
| Live configuration | A `GET` of the object from the API server |
| Last-applied configuration | The annotation `kubectl.kubernetes.io/last-applied-configuration` on the live object (a JSON copy of the file you applied last time) |

Why do we need the third one? Without it kubectl could not tell the difference between "field is missing from my file because I deleted it" and "field is missing from my file because a controller or another person added it". The annotation records what you said last time, so kubectl can delete exactly the fields you removed and leave the rest alone.

The merge rules:

| Field is... | Result of `apply` |
|---|---|
| in the file, and the live value is different | Set to the file's value (the file wins) |
| in the last-applied annotation but not in the file | Removed from the live object |
| only on the live object (set by `scale`, a controller, an admission webhook, another `patch`) | Left alone |
| a list of a built-in type (containers, env, ports) | Merged by a key such as `name` (a strategic merge, section 2.5) |
| a list in a custom resource | Replaced as a whole (no merge keys are known) |

Look at what the annotation really contains (captured in section 5): it is the JSON form of the file, with `"annotations":{}` left empty and `namespace` added by kubectl. It does not contain defaulted fields such as `imagePullPolicy`.

Commands that touch the annotation:

| Command | What it does |
|---|---|
| `k apply view-last-applied deploy web` | Print the stored last-applied configuration |
| `k create -f d.yaml --save-config` | Create an object and also write the annotation, so a later `apply` works without a warning |
| `k apply set-last-applied -f d.yaml` | Write the annotation from a file without changing anything else |
| `k apply edit-last-applied deploy web` | Edit the stored annotation by hand (rare). Use it to fix a wrong baseline, and as the first step when handing a field such as `replicas` to an autoscaler (section 6.1) |

**Adopting an object made by `create`.** `create` writes no annotation. The first `apply` on that object prints a warning and patches the annotation in (real output in section 5): `Warning: resource deployments/web is missing the kubectl.kubernetes.io/last-applied-configuration annotation ... The missing annotation will be patched automatically.` It is only a warning. The effect is that this first apply has no baseline, so fields you removed from the file before this first apply are not deleted.

**The size limit.** All annotations of one object together may not exceed 262144 bytes (256 KiB). The last-applied annotation is a full copy of your file, so a very large manifest, for example a big CustomResourceDefinition, fails with an error such as `metadata.annotations: Too long: must have at most 262144 bytes`. Server-side apply (next section) does not need the copy and is the fix.

**Under the hood.** `kubectl apply` fetches the live object, builds a patch (a strategic merge patch for built-in types, a JSON merge patch for custom resources) from the three inputs, and sends one `PATCH`. If the object does not exist it sends `POST` and sets the annotation. The server never sees "your intent"; it only sees the computed patch. Consequences: only kubectl can use the annotation, and two people applying different files to one object each delete the other's fields.

**The fight with other writers.** CSA reverts any field that appears in your file whenever you run it, even if somebody else changed that field on purpose. A field that is not in your file (and was never in last-applied) is never touched. Real example in section 5: `k patch` sets replicas to 4, the next `k apply -f d.yaml` silently sets them back to 3, with no error.

### 2.3 Server-side apply, field managers and conflicts

**Server-side apply** (SSA) moves the merge into the API server. You run `k apply -f d.yaml --server-side` and kubectl sends the file as an "apply" request. The server compares the request with the live object and records, for every field, which **field manager** owns it. This replaces the last-applied annotation as the memory of "who set what".

Problems SSA solves:

| Problem with client-side apply | What SSA does |
|---|---|
| Two actors (you and a controller) write the same field and neither knows | Ownership is tracked per field; a clash is reported as a conflict instead of a silent overwrite |
| Annotation grows with the file (256 KiB limit) | No annotation needed |
| Merge happens in kubectl, so Helm, operators and your CI each merge differently | The server merges for everyone, using the same rules |
| Custom resources: lists are replaced because kubectl does not know merge keys | The CRD schema can declare list types (map or set), so lists merge per item |

**`managedFields`.** Every object has `metadata.managedFields`. It is a list of entries; each entry has a `manager` (a name), an `operation`, an optional `subresource`, a timestamp and `fieldsV1` (the set of fields that manager owns, as a nested map where `f:name: {}` means "field name"). `operation` is `Apply` if the last request that changed the field was an SSA request, otherwise `Update`. kubectl hides `managedFields` by default; add `--show-managed-fields` to see them.

Two terms used in the table and in the rules after it. An **Apply** operation is a request sent with `--server-side` (or by a controller that uses server-side apply); every other write (`create`, client-side `apply`, `patch`, `edit`, `scale`, `set`, `replace`, and controllers that update an object) is an **Update** operation. Two managers **co-own** a field when both list it and the value is the same; the rules below say what happens when one of them later changes it. Real output from this cluster (section 5):

| You ran | Manager name | Operation | Notes |
|---|---|---|---|
| `k create -f` | `kubectl-create` | Update | |
| `k apply -f` (client-side) | `kubectl-client-side-apply` | Update | The `--field-manager` default for CSA |
| `k apply -f --server-side` | `kubectl` | Apply | A second entry, `kubectl-last-applied` (Apply), also appears when the object carries the old annotation |
| `k edit` | `kubectl-edit` | Update | |
| `k patch` | `kubectl-patch` | Update | |
| `k set image` / `k set env` | `kubectl-set` | Update | |
| `k label` / `k annotate` | `kubectl-label` / `kubectl-annotate` | Update | |
| `k replace -f` | `kubectl-replace` | Update | |
| `k rollout restart` | `kubectl-rollout` | Update | |
| `k scale` | `kubectl` | Update | `subresource: scale` |
| Deployment controller (status) | `kube-controller-manager` | Update | `subresource: status` |

An entry whose field set becomes empty is removed from the list. That is why `kubectl-patch` disappears from the list after a CSA apply resets the field it owned.

**The ownership rules** (how SSA decides):

1. An `Apply` request says: "these fields, with these values, are what I want". The manager name defaults to `kubectl` and can be set with `--field-manager=NAME`.
2. If a field in the request has a value different from the live one **and another manager owns that field**, the request fails with a **conflict**. Nothing is changed (the whole request is rejected, not only the conflicting field).
3. If the value is the same, there is no conflict and the field becomes **co-owned** (shared). If one co-owner later changes the value, the others conflict.
4. `Update` operations (`patch`, `edit`, `scale`, `set`, ...) never conflict. They overwrite and take the field away from the previous owner. Conflicts are a feature of `Apply` requests only.
5. If you remove a field from your manifest and apply again, and you were the only owner, the field is deleted (or reset to its default). If someone else also owns it, it stays.
6. `--force-conflicts` tells the server "overwrite the value and make me the only owner". The previous owners lose the field.

Real conflict messages (section 5 and 7). The wording depends on how the other owner wrote the field:

```text
error: Apply failed with 1 conflict: conflict with "kubectl-patch" using apps/v1: .spec.replicas
error: Apply failed with 1 conflict: conflict with "kubectl" with subresource "scale" using apps/v1: .spec.replicas
error: Apply failed with 1 conflict: conflict with "ops": .spec.replicas
```

Ways to resolve a conflict (kubectl prints the same three choices):

| Choice | Command or edit | Use it when |
|---|---|---|
| Take the field | Re-run with `--force-conflicts` | You really want your value and your name as owner (a controller or CI that is the intended owner) |
| Give up the field | Remove the field from your manifest | Another manager is the right owner (replicas owned by an HPA or by ops) |
| Co-own | Change your manifest to the live value | You agree with the value; you will share the field |

**Upgrading from client-side to server-side apply.** The Kubernetes docs say `kubectl apply --server-side` on an object managed by CSA moves ownership without conflicts, as long as you kept the last-applied annotation up to date; fields changed by other tools after your last apply (for example with `kubectl scale`) are not owned by CSA and cause conflicts. Downgrading back to plain `kubectl apply` works because `kubectl apply --server-side` keeps the annotation up to date. Source: https://kubernetes.io/docs/reference/using-api/server-side-apply/. In the section 5 capture, after the first SSA the `kubectl-client-side-apply` entry was gone and two Apply entries (`kubectl` and `kubectl-last-applied`) existed instead.

**Under the hood.** The SSA request is a `PATCH` with content type `application/apply-patch+yaml` and a `fieldManager` query parameter (and `force=true` for `--force-conflicts`). The API server keeps `managedFields` in etcd, merges with schema knowledge (list types, map keys) from the object's OpenAPI schema, and updates the owner sets in the same write. The subresource note matters: `kubectl scale` writes through the `scale` subresource, so its owner entry carries `subresource: scale`.

**Related flag: `--subresource`.** `k apply --server-side --subresource=status ...` (and `k patch --subresource=...`) apply to a subresource instead of the main object. You rarely need it; know it exists.

### 2.4 `kubectl diff` before apply

`k diff -f d.yaml` shows what `apply` would change, without changing anything. It asks the API server for a server-side dry-run of the apply, then compares the live object with the result using the system `diff -u -N`. This is why the output shows server-added defaults (such as `imagePullPolicy`) as context and why it needs permission for create, patch and update on the objects (the Kubernetes docs list `PATCH`, `CREATE` and `UPDATE`).

Exit status, from `kubectl diff --help`: `0` no differences, `1` differences found, `>1` kubectl or diff failed. Beware in scripts and in `&&` chains: exit status 1 is **not** an error here. Real output in section 5 shows all three: exit 1 with a diff, exit 0 with empty output, and exit 2 when the server rejects the change (section 6).

Useful facts:

- Works with `-f`, `-R`, `-k`, stdin (`-f -`), like `apply`.
- A manifest for an object that does not exist yet shows every line as an added line (`@@ -0,0 +1,66 @@`) and exits 1.
- `--server-side` makes the diff use SSA semantics, including conflict errors (real output in section 5).
- `KUBECTL_EXTERNAL_DIFF="colordiff -N -u"` selects another diff program (from the help text). Whether `diff` itself is installed on the exam host is UNVERIFIED (the allowed-tools list in https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad names kubectl, yq, curl, wget and man).
- The output hides `managedFields` and the changes of `generation` are normal: `generation` goes up by one when `spec` changes.

Review workflow: edit the file, `k diff -f file`, read the `-`/`+` lines, then `k apply -f file`. After a successful apply, `k diff -f file` prints nothing and exits 0. That is a quick "is the live object equal to my file?" test.

### 2.5 `kubectl patch`: strategic, merge, json

`k patch` changes a few fields of a live object with a small patch document. No file of the whole object is needed. The patch type decides how the document is read:

| `--type` | Standard | The patch document looks like | Lists | Typical use |
|---|---|---|---|---|
| `strategic` (default) | Kubernetes strategic merge patch | Partial object: `{"spec":{"replicas":4}}` | Merged by a key for fields that declare one (containers and env by `name`, ports by `containerPort`) | Built-in kinds: Deployment, Pod, Service |
| `merge` | JSON Merge Patch, RFC 7386 | Partial object | **Replaced as a whole** | Custom resources; simple scalar fields |
| `json` | JSON Patch, RFC 6902 | A list of operations: `[{"op":"replace","path":"/spec/replicas","value":4}]` | You address one item by index (`/0`) or append with `/-` | Surgical edits; removing one list item |

JSON patch operations: `add`, `remove`, `replace`, `move`, `copy`, `test`. The path is a JSON pointer: `/` separates levels and list items are addressed by number (`/containers/0`). `-` at the end of a list path means "append". If a key contains `/` or `~`, escape `/` as `~1` and `~` as `~0` (an annotation key `example.com/owner` becomes `example.com~1owner`). `test` makes the whole patch fail if the value is not what you expect.

Let us add an env var to container 0 in all three styles. Real output of the patched file, from `--local` on the lesson's `d.yaml` (no cluster). In this block and the next one only the part of the printed YAML that matters is shown (the `containers:` or `metadata:` fragment); with `-o yaml` kubectl prints the whole Deployment, so you will see more lines on your screen:

REAL OUTPUT (kubectl v1.37.1, client only, no cluster):

```text
$ k patch --local -f d.yaml -o yaml -p '{"spec":{"template":{"spec":{"containers":[{"name":"nginx","env":[{"name":"MODE","value":"prod"}]}]}}}}'
      containers:
      - env:
        - name: MODE
          value: prod
        image: nginx:1.26
        name: nginx
        ports:
        - containerPort: 80

$ k patch --local -f d.yaml --type=json -o yaml -p '[{"op":"add","path":"/spec/template/spec/containers/0/env","value":[{"name":"MODE","value":"prod"}]}]'
      containers:
      - env:
        - name: MODE
          value: prod
        image: nginx:1.26
        name: nginx
        ports:
        - containerPort: 80

$ k patch --local -f d.yaml --type=merge -o yaml -p '{"spec":{"template":{"spec":{"containers":[{"name":"nginx","env":[{"name":"MODE","value":"prod"}]}]}}}}'
      containers:
      - env:
        - name: MODE
          value: prod
        name: nginx
```

Read the third block carefully. The merge patch **replaced the whole `containers` list** with the one item in the patch, so `image` and `ports` are gone. The server rejects that result (real output in section 5): `The Deployment "web" is invalid: spec.template.spec.containers[0].image: Required value`. The strategic patch found the container with `name: nginx` and merged into it. This is the single most important difference. Why: the Go type of `containers` carries the tags `patchStrategy:"merge" patchMergeKey:"name"`, so a strategic patch knows to merge by `name`. A list with no such tags (for example `tolerations`) is replaced even in a strategic patch. The merge key tags are also visible in the OpenAPI schema as `x-kubernetes-patch-merge-key` and `x-kubernetes-patch-strategy`.

Strategic patch details you may need:

- `null` as a value deletes a key (JSON merge patch and strategic): `{"metadata":{"labels":{"app":null}}}` removes the label (real output below shows `labels: {}`).
- `"$patch":"delete"` inside a list item removes that item from a merged list: `{"containers":[{"name":"nginx","ports":[{"containerPort":80,"$patch":"delete"}]}]}`. Real output below shows `ports: []`.
- A JSON patch `add` to a list needs the parent to exist. `/env/-` fails on a container that has no `env` yet; then add the whole array to `/env` first.
- Custom resources do not support strategic merge. Real output (a Widget custom resource on the capture cluster): `error: application/strategic-merge-patch+json is not supported by example.com/v1, Kind=Widget: the body of the request was in an unknown format - accepted media types include: application/json-patch+json, application/merge-patch+json, application/apply-patch+yaml`. Use `--type=merge` or `--type=json` for custom resources.

REAL OUTPUT (kubectl v1.37.1, client only, no cluster):

```text
$ k patch --local -f d.yaml --type=merge -o yaml -p '{"metadata":{"labels":{"app":null}}}'
metadata:
  labels: {}
  name: web

$ k patch --local -f d.yaml -o yaml -p '{"spec":{"template":{"spec":{"containers":[{"name":"nginx","ports":[{"containerPort":80,"$patch":"delete"}]}]}}}}'
      containers:
      - image: nginx:1.26
        name: nginx
        ports: []

$ k patch --local -f d.yaml --type=json -o yaml -p '[{"op":"add","path":"/metadata/annotations","value":{}},{"op":"add","path":"/metadata/annotations/example.com~1owner","value":"ops"}]'
metadata:
  annotations:
    example.com/owner: ops

$ k patch --local -f d.yaml --type=json -p '[{"op":"test","path":"/spec/replicas","value":9},{"op":"replace","path":"/spec/replicas","value":4}]'
error: testing value /spec/replicas failed: test failed

$ k patch --local -f d.yaml --type=json -o yaml -p '[{"op":"add","path":"/spec/template/spec/containers/0/env/-","value":{"name":"A","value":"1"}}]'
error: add operation does not apply: doc is missing path: "/spec/template/spec/containers/0/env/-": missing value
```

Other `patch` flags (from `k patch --help`):

| Flag | Meaning |
|---|---|
| `-p '...'` / `--patch-file FILE` | Patch text inline or from a file (use a file for long patches; write JSON patches as JSON) |
| `--type=strategic\|merge\|json` | Patch type (default `strategic`) |
| `--field-manager=NAME` | Owner name recorded (default `kubectl-patch`) |
| `--subresource=status\|scale\|...` | Patch a subresource |
| `--local` | Apply the patch to the file only (with `-f`), no API call; `-o yaml` prints the result |
| `--dry-run=server -o yaml` | Ask the server what the result would be, change nothing |

`patch` is the right tool when there is no manifest, when you must change a field no `set` subcommand covers, or when you must do it from a script.

### 2.6 `kubectl replace` and `replace --force`

`k replace -f file` sends a `PUT`: the object is replaced by exactly what is in the file. Fields that are missing from the file are removed or reset to defaults, including fields that controllers or other people added. The object must already exist. It does not read or write the last-applied annotation.

REAL OUTPUT (kind v0.33.0, v1.37.0). A Deployment that had gained an env var (`k set env`), a label (`k label`) and 3 replicas (`k scale`) is replaced by the original `d.yaml` (2 replicas, no env, no extra label). The two jsonpath lines print env, then labels, then replicas:

```text
$ k get deploy web -o jsonpath='{.spec.template.spec.containers[0].env}{"\n"}{.metadata.labels}{"\n"}'
[{"name":"MODE","value":"prod"}]
{"app":"web","tier":"fe"}
$ k replace -f d.yaml
deployment.apps/web replaced
$ k get deploy web -o jsonpath='{.spec.template.spec.containers[0].env}{"\n"}{.metadata.labels}{"\n"}{.spec.replicas}{"\n"}'

{"app":"web"}
2
$ mf deploy web
kubectl-create	Update	
kube-controller-manager	Update	status
kubectl-replace	Update	
```

The env line is empty after the replace (the variable is gone), the `tier` label is gone, and replicas are back to 2. The managers `kubectl-set`, `kubectl-label` and `kubectl-rollout` vanished from the list because `replace` rewrote everything they owned.

**Immutable fields.** Some fields cannot change after creation. `replace` (and `apply`, `patch`, `edit`) are rejected for them:

| Kind | Immutable field(s) | Real error text |
|---|---|---|
| Deployment | `spec.selector` | `The Deployment "web" is invalid: spec.selector: Invalid value: {"matchLabels":{"app":"other"}}: field is immutable` |
| Pod | Almost everything except container images, `activeDeadlineSeconds`, added tolerations | `The Pod "p1" is invalid: spec: Forbidden: pod updates may not change fields other than ...` |
| Service | `spec.clusterIP` (and a few others) | rejected with a `field is immutable`-style message (not captured) |
| Job | `spec.template`, `spec.selector` | rejected (not captured) |

**`k replace --force`** means delete the object and create it again from the file. Real output for a Pod:

```text
pod "p1" deleted from lab-t207 namespace
pod/p1 replaced
```

It is the standard way to change an immutable field of a **Pod**: nothing else depends on the Pod object, and a bare Pod has no controller that would restart it. For a Deployment it is dangerous: deleting the Deployment deletes its ReplicaSets and Pods (garbage collection), so you get downtime until the new Pods start (section 6). For a Deployment, `selector` is immutable, so there is no in-place alternative: you must delete and recreate, accepting the downtime, or create a new Deployment next to the old one and switch the Service.

When `k edit` is refused (for example you changed a Pod command), kubectl prints `error: pods "p1" is invalid`, then `A copy of your changes has been stored to "<tmpdir>/kubectl-edit-NNNN.yaml"` and `error: Edit cancelled, no valid changes were saved.` Running `k replace --force -f <that file>` finishes the change (verified on the capture cluster).

### 2.7 Applying directories: `-R`, `-k`, and `--prune` awareness

`-f` accepts a file, a directory, a URL, or `-` for stdin. One file may hold several objects separated by `---`.

| Command | What it processes |
|---|---|
| `k apply -f d.yaml` | One file |
| `k apply -f dir/` | Every `.yaml`, `.yml` and `.json` file directly inside `dir/`, in file-name order. **Sub-directories are skipped silently.** |
| `k apply -f dir/ -R` | The same, plus every sub-directory (`-R` is `--recursive`) |
| `k apply -f https://.../x.yaml` | A file at a URL |
| `k apply -k dir/` | `dir/` holds a `kustomization.yaml`; kubectl builds the objects it describes, then applies them. `-k` **replaces** `-f`; it cannot be combined with `-f` or `-R` (section below). |
| `cat d.yaml \| k apply -f -` | Read stdin |

**What `-k` does.** Kustomize is a tool that builds final manifests from base files plus a `kustomization.yaml` that lists them (and can add a name prefix, labels, patches and so on). A directory is a "kustomization" when it contains a file named `kustomization.yaml`. `k apply -k dir/` runs that build inside kubectl and applies the result; `k diff -k dir/` diffs the same result against the cluster; `k kustomize dir/` only prints the build and needs no cluster. Kustomize has its own topic later in the course; this lesson uses only the smallest form (a plain `resources:` list), so there is nothing else to learn here. Note that the Kustomize built into kubectl is a different version from the standalone `kustomize` binary (`kubectl version --client` prints both; kubectl v1.37.1 embeds Kustomize v5.8.1), so a feature of a newer standalone release may be missing from `k apply -k`.

Runnable example with the lesson's `d.yaml` (a directory `kdir/` that contains `d.yaml` and a two-line `kustomization.yaml`):

```bash
mkdir kdir && cp d.yaml kdir/ && printf 'resources:\n- d.yaml\n' > kdir/kustomization.yaml
k kustomize kdir/        # print the build (no cluster needed)
k apply -k kdir/         # build and apply
k diff -k kdir/          # after editing kdir/d.yaml: what would change (exit 1 = differences)
```

REAL OUTPUT (kubectl v1.37.1, client only, no cluster) for `k kustomize kdir/`. Note the keys are sorted and `name` comes after `image`; the content equals `d.yaml`:

```text

  labels:
    app: web
```

EXPECTED OUTPUT (not captured) for `k apply -k kdir/` on an empty namespace; it prints the same one-line result as `apply -f` (`created`, later `configured` or `unchanged`):

```text

```

The sub-directory trap is real: with `shop/extra/ratelimit.yaml`, `k apply -f shop/` applies three objects and ignores the fourth without any message (section 7, medium lab).

**`--prune`.** Applying a directory never deletes objects whose file you removed. `--prune` adds that: kubectl deletes objects that carry the last-applied annotation, match your label selector (`-l key=value`) or `--all`, and are not in the set of files you just applied. The command help marks this as **alpha** ("not yet complete"). Awareness points:

- You must give `-l` or `--all`. The delete set is limited to a default list of kinds (ConfigMap, Secret, Service, Pod, PVC, Deployment, StatefulSet, DaemonSet, Job, CronJob, Ingress and a few more); `--prune-allowlist=group/version/kind` replaces the list.
- Whatever you did **not** pass with `-f`/`-R` counts as "removed". Forgetting `-R` prunes the objects in the sub-directories (real output in the medium lab).
- It prints `Deprecated: kubectl apply will no longer prune non-namespaced resources by default when used with the --namespace flag in a future release...` on this version.
- Helm, Kustomize and GitOps tools do their own tracking instead. On the exam, delete by name unless the task says otherwise.

### 2.8 `kubectl edit` vs `patch` vs `set`

| Tool | How you use it | Strength | Weakness | Manager name |
|---|---|---|---|---|
| `k edit deploy web` | Opens the live object in `$KUBE_EDITOR`, `$EDITOR` or `vi`; saving sends a patch of your changes | You see the whole object; no need to remember the path | Interactive, slow to type; refuses invalid edits (reopens with error comments or stores a temp copy) | `kubectl-edit` |
| `k patch` | One command, a patch document | Scriptable; exact; any field | Quoting is easy to get wrong; wrong `--type` replaces lists | `kubectl-patch` |
| `k set image/env/resources/selector/serviceaccount` | A typed shortcut for the pod template | Shortest for those fields; `--local` / `$do` friendly | Only covers a few fields | `kubectl-set` |
| `k scale`, `k label`, `k annotate`, `k expose`, `k rollout` | One-purpose commands | Fastest for their job | One job each | see table in 2.3 |
| `k apply -f` | Edit the file, apply | Keeps file and cluster in step | Reverts fields in your file | `kubectl-client-side-apply` |

Examples that you should be able to type without thinking (all used on the capture cluster):

```bash
k set image deploy/web nginx=nginx:1.27          # container name = image name part before the tag, here "nginx"
k set env deploy/web MODE=prod                   # add or change an env var
k set resources deploy/web --limits=cpu=200m,memory=128Mi
k scale deploy web --replicas=3
k label deploy web tier=fe ; k annotate deploy web note=hi
```

`k edit` honours `KUBE_EDITOR`. For a scripted, repeatable edit (used in lab 1) set it to a command that edits the temp file it is given: `KUBE_EDITOR="yq -i '.spec.replicas = 3'" k edit deploy web`. On the exam you use the interactive editor.

### 2.9 Delete semantics: `delete -f`, `--cascade`, `--wait`

`k delete -f d.yaml` deletes the objects **named in the file** (kind, name, namespace). It does not need the last-applied annotation. `k delete -f dir/ -R` does the same for a directory. Other forms: `k delete deploy web`, `k delete pods -l app=web`, `k delete deploy --all`.

What happens inside: kubectl sends `DELETE` with a `propagationPolicy`. The object gets a `deletionTimestamp`, finalizers (if any) run, and then the object disappears. Objects that **own** other objects (a Deployment owns ReplicaSets, a ReplicaSet owns Pods through `ownerReferences`) are handled by the garbage collector:

| `--cascade=` | What happens to dependents (children) | Check |
|---|---|---|
| `background` (default) | The parent is deleted at once; the garbage collector then deletes the children | `k get rs,pods` shows the children terminating after the parent is gone |
| `foreground` | The parent stays (with `deletionTimestamp` and the `foregroundDeletion` finalizer) until all children are gone | `k delete --cascade=foreground` returns after the children are deleted |
| `orphan` | The parent is deleted; the children are kept and lose their owner reference | `k get rs,pods -l app=web` still lists them (real output in section 5) |

Other delete flags (from `k delete --help`):

| Flag | Meaning | Risk |
|---|---|---|
| `--wait=true` (default for delete) | Wait until the object is really gone, including finalizers | Can hang on a stuck finalizer; use `--timeout=30s` |
| `--wait=false` | Return at once | The object may still be Terminating when the next command runs |
| `--grace-period=N` | Seconds the Pod gets to stop (default: the Pod's own `terminationGracePeriodSeconds`) | |
| `--now` | Same as `--grace-period=1` (the flag, not the `$now` shell variable) | |
| `--force --grace-period=0` (the shell variable `$now`) | Remove the object from the API immediately without waiting for the kubelet | The container may still be running on the node; for StatefulSet Pods this can cause two copies |
| `--ignore-not-found` | No error if the name does not exist | Hides typos |
| `-l`, `--all`, `--field-selector` | Select several objects | `--all` in the wrong namespace is a disaster |

The help text also says that `delete` does not do resource version checks, so a concurrent update is lost along with the object.

**Related but different.** Deleting a Deployment with `--cascade=orphan` leaves ReplicaSets and Pods running with nobody managing them. Deleting only the Pods of a Deployment (`k delete pod -l app=web`) is harmless: the ReplicaSet creates new ones.

### 2.10 Validation: `--dry-run` and `--validate`

Two different safety tools exist.

**`--dry-run=none|client|server`.**

| Mode | What runs | What it can catch | What it cannot catch |
|---|---|---|---|
| `client` | kubectl builds and prints the object. No request to change anything. | Bad YAML, wrong flags | Unknown fields, `AlreadyExists`, quota, admission, immutable-field errors |
| `server` | The full request goes to the API server, passes validation and admission, but is not stored | Unknown fields, `AlreadyExists`, quota, immutable fields, webhook denials | Runtime problems (image missing, no capacity) |

Real output that proves the difference (typo in the file, section 5): `apply --dry-run=client` prints `deployment.apps/web2 created (dry run)` and passes, while `apply --dry-run=server` fails with the strict decoding error. Likewise `k create -f d.yaml --dry-run=client` says `created (dry run)` for a name that exists, and `--dry-run=server` fails with `AlreadyExists`. **Use `$do` to generate YAML, but use `--dry-run=server` to test it.**

**`--validate=strict|warn|ignore`** (also `true`/`false`). It controls what happens to unknown or duplicate fields, using server-side field validation:

| Value | Unknown / duplicate field | Real result in section 5 |
|---|---|---|
| `strict` (also `true`), **the default in kubectl v1.37.1** | The request fails | `strict decoding error: unknown field "spec.template.spec.containers[0].imagePullPolisy"` |
| `warn` | A warning is printed, the request goes through, the unknown field is dropped | `Warning: unknown field "..."` then `deployment.apps/web2 created` |
| `ignore` (also `false`) | Silently dropped | `created`, no message; the typo field is not stored |

The default is verified two ways: `kubectl apply --help` on v1.37.1 shows `--validate='strict'`, and the typo above was rejected without any flag. Fix a rejected field name with `k explain` (for example `k explain deploy.spec.template.spec.containers --recursive | grep -i pullpolicy`), not by switching validation off. Note `k diff` has no `--validate` flag (real output: `error: unknown flag: --validate`).

### 2.11 `kubectl convert` is a plugin

`kubectl convert` rewrites a manifest from one API version to another (for example an old `extensions/v1beta1` Ingress to `networking.k8s.io/v1`). It is **not built into kubectl**: it is a separate binary named `kubectl-convert` that you must install and put on your `PATH`. Real output on the capture machine: `error: unknown command "convert" for "kubectl"`. Do not plan on it during a task; use `k explain` and `k api-versions` to find the current version and edit by hand. The API deprecation lesson, [T3.21](../part3-ckad/T3.21-understand-api-depreciations.md), shows when and how to use the plugin.

### 2.12 Related but different

- **`apply` vs `create`:** `create` fails if the name exists and records no intent; `apply` creates or updates. `create --save-config` bridges the two.
- **`replace` vs `apply`:** `replace` overwrites the whole object (`PUT`); `apply` computes a partial update (`PATCH`). `replace` forgets everyone else's fields; `apply` leaves fields it does not know.
- **`edit` vs `apply`:** both change the live object, but `edit` is a patch from your editor with manager `kubectl-edit`, and the file in git does not change.
- **`$do` (client dry-run) vs `--dry-run=server`:** one prints, the other validates.
- **The `--now` flag vs the `$now` shell variable:** `--now` is `--grace-period=1`; the variable in the shell setup expands to `--force --grace-period=0`.

### 2.13 Choosing the method

| Situation | Best tool |
|---|---|
| Make a new object quickly | `k create ...` / `k run ... $do > f.yaml`, edit, `k apply -f f.yaml` |
| One scalar field on an existing object | `k scale`, `k set ...`, `k label`, or `k patch --type=merge -p ...` |
| One field deep in the pod template | `k set image/env`, else a strategic `k patch` (container by name) |
| Remove a list item or touch exactly one index | `k patch --type=json` |
| You do not remember the path | `k edit` |
| You are given a YAML file to apply | `k diff -f f.yaml` then `k apply -f f.yaml` |
| A shared object that a controller also writes | `k apply --server-side` without the shared field |
| An immutable field of a Pod | `k replace --force -f pod.yaml` |
| An immutable field of a Deployment/Job | Delete and recreate (accept downtime) |

```text
+----------------------------+------------------------------------------+--------------------------------------+----------------------------------------+
|                            | IMPERATIVE COMMANDS                      | IMPERATIVE CONFIG                    | DECLARATIVE CONFIG                     |
+----------------------------+------------------------------------------+--------------------------------------+----------------------------------------+
| Example                    | k create deploy web --image=nginx:1.27   | k create -f d.yaml                   | k apply -f d.yaml                      |
|                            | k scale deploy web --replicas=3          | k replace -f d.yaml                  | k apply -f dir/ -R                     |

|                            |                                          |                                      | k diff -f d.yaml                       |
+----------------------------+------------------------------------------+--------------------------------------+----------------------------------------+
| You tell the API           | one action (verb + flags)                | one action + a whole file            | the end state (the file)               |
+----------------------------+------------------------------------------+--------------------------------------+----------------------------------------+
| Who works out the change   | you, in your head                        | you (create or replace)              | kubectl (client-side) or the           |
|                            |                                          |                                      | API server (server-side)               |
+----------------------------+------------------------------------------+--------------------------------------+----------------------------------------+
| What is remembered         | nothing but the live object              | nothing (replace overwrites          | client-side: last-applied annotation   |
|                            |                                          | the whole object)                    | server-side: managedFields             |
+----------------------------+------------------------------------------+--------------------------------------+----------------------------------------+
| Safe to run twice?         | create: AlreadyExists error              | create: error                        | yes, this is the design goal           |
|                            | scale/set: yes                           | replace: yes, but drops              |                                        |
|                            |                                          | fields not in the file               |                                        |
+----------------------------+------------------------------------------+--------------------------------------+----------------------------------------+
| Use it when                | exam: make a new object fast,            | replace --force to recreate          | files in git; many objects;            |
|                            | or change one field (scale, set,         | a Pod / immutable field;             | reviewable changes; teams              |
|                            | label, expose, run)                      | rare otherwise                       |                                        |
+----------------------------+------------------------------------------+--------------------------------------+----------------------------------------+
| Main risk                  | no file = no record; easy to             | replace erases fields that           | two writers fight over one             |
|                            | drift from what is in git                | controllers or other people set      | field (replicas, image)                |
+----------------------------+------------------------------------------+--------------------------------------+----------------------------------------+
```

Walkthrough:

1. Read a column from the top. The left column starts from a verb, the middle column from a file plus a verb, the right column from a file only.
2. "Who works out the change" is the core difference. In the right column kubectl or the server computes the patch, so repeating the command is safe.
3. "What is remembered" explains conflicts: client-side apply remembers only your last file (annotation); server-side apply remembers every writer per field (`managedFields`).
4. "Main risk" tells you what to check after the command: left column, did you also update the file; middle column, did `replace` wipe a field; right column, did a second writer's value get reverted.
5. Use the "Use it when" row to choose in under 10 seconds on the exam.

## 4. Commands and YAML you must produce fast

**Imperative shortcuts.**

```bash
k create deploy web --image=nginx:1.27 --replicas=2 $do > d.yaml   # generate a Deployment manifest, nothing is created
k create -f d.yaml                       # imperative config: fails with AlreadyExists the second time
k apply -f d.yaml                        # declarative: create or update (client-side)
k apply -f d.yaml --server-side          # server-side apply, manager "kubectl"
k apply -f d.yaml --server-side --field-manager=ops   # same, with your own manager name
k apply -f d.yaml --server-side --force-conflicts     # take over fields owned by others
k diff -f d.yaml                         # show what apply would change (exit 1 = differences)
k patch deploy web -p '{"spec":{"replicas":4}}'       # strategic merge patch (default type)
k patch deploy web --type=merge -p '{"spec":{"replicas":4}}'
k patch deploy web --type=json -p '[{"op":"replace","path":"/spec/template/spec/containers/0/image","value":"nginx:1.27"}]'
k replace --force -f pod.yaml            # delete + create from the file (Pods, immutable fields)
k set image deploy/web nginx=nginx:1.27  # change a container image
k set env deploy/web MODE=prod           # add an env var
k scale deploy web --replicas=3
k delete -f d.yaml --wait=false          # delete what the file names, do not wait
k delete deploy web --cascade=orphan     # keep ReplicaSets and Pods
k apply -f d.yaml --dry-run=server       # validate against the real API server
k explain deploy.spec.template.spec.containers.imagePullPolicy   # check a field name
```

**Declarative YAML** (the lesson's `d.yaml`; it applies as written with `k apply -f d.yaml`):

```yaml
apiVersion: apps/v1          # group/version of the kind; Deployment lives in apps/v1
kind: Deployment             # the object type
metadata:
  name: web                  # name, unique per namespace and kind; cannot be changed later
  labels:
    app: web                 # labels on the Deployment itself (not on its Pods)
spec:
  replicas: 2                # desired Pod count; default 1; 0 means no Pods; negative is invalid. Risky field: HPAs also write it
  selector:
    matchLabels:
      app: web               # which Pods this Deployment owns; IMMUTABLE after creation; must match template labels
  template:                  # the Pod template (changing it triggers a rollout)
    metadata:
      labels:
        app: web             # must match spec.selector.matchLabels, or the API rejects the Deployment
    spec:
      containers:
      - name: nginx          # container name; the merge key for strategic patches
        image: nginx:1.26    # pinned tag (never :latest)
        ports:
        - containerPort: 80  # informational; does not open or close anything
```

**Add an env var to container 0: the two patch documents** (patch documents, not objects, so they cannot be applied with `apply`):

```text
# strategic merge patch (default type): container found by name, env list merged
{"spec":{"template":{"spec":{"containers":[{"name":"nginx","env":[{"name":"MODE","value":"prod"}]}]}}}}

# JSON patch (--type=json): container addressed by index 0; "add" on /env creates the list
[{"op":"add","path":"/spec/template/spec/containers/0/env","value":[{"name":"MODE","value":"prod"}]}]
# when env already exists, append one item instead:
[{"op":"add","path":"/spec/template/spec/containers/0/env/-","value":{"name":"LEVEL","value":"debug"}}]
```

```bash
k patch deploy web -p '{"spec":{"template":{"spec":{"containers":[{"name":"nginx","env":[{"name":"MODE","value":"prod"}]}]}}}}'
k patch deploy web --type=json -p '[{"op":"add","path":"/spec/template/spec/containers/0/env","value":[{"name":"MODE","value":"prod"}]}]'
k set env deploy/web MODE=prod    # the shortest way
```

## 6. Common mistakes and how to fix them

| # | Symptom | What you will see (exact text) | Cause | Fix |
|---|---|---|---|---|
| 1 | `apply` undoes another writer's change (HPA, `scale`, `patch`) | Client-side: no error, `deployment.apps/web configured`, replicas jump back. Server-side: `error: Apply failed with 1 conflict: conflict with "kubectl-patch" using apps/v1: .spec.replicas` | Both your file and the other actor own `spec.replicas` | Remove `replicas` from the manifest in the safe order (section 6.1: annotation first for client-side apply), or use `--force-conflicts` only if the file must win |
| 2 | Typo in a field name | `Error from server (BadRequest): error when creating "bad.yaml": Deployment in version "v1" cannot be handled as a Deployment: strict decoding error: unknown field "spec.template.spec.containers[0].imagePullPolisy"` | Strict field validation (the default) caught it on the server | `k explain deploy.spec.template.spec.containers --recursive \| grep -i <word>`; fix the name; re-test with `--dry-run=server` |
| 3 | `replace --force` caused downtime | `deployment.apps "web" deleted from lab-t207 namespace` then `deployment.apps/web replaced` (EXPECTED OUTPUT, not captured for a Deployment; the Pod form was captured in section 5, step 10); Pods vanish and restart | `--force` deletes first, so the Deployment's ReplicaSets and Pods are garbage-collected | Use `apply`/`patch` for Deployments; reserve `--force` for Pods and unavoidable immutable-field changes |
| 4 | Merge patch wipes a container | `The Deployment "web" is invalid: spec.template.spec.containers[0].image: Required value` | `--type=merge` replaces lists, so `containers` became one item without `image` | Use the default strategic patch (container found by `name`), or a JSON patch with an index |
| 5 | Immutable field | `The Deployment "web" is invalid: spec.selector: Invalid value: {"matchLabels":{"app":"other"}}: field is immutable` or `The Pod "p1" is invalid: spec: Forbidden: pod updates may not change fields other than ...` | The field cannot change after creation | Pod: `k replace --force -f pod.yaml`. Deployment: delete and recreate (downtime), or add a new Deployment |
| 6 | `apply` prints a warning on a new object | `Warning: resource deployments/web is missing the kubectl.kubernetes.io/last-applied-configuration annotation ...` | Object was made with `create` | Ignore (it self-heals) or create with `--save-config` next time |
| 7 | `diff` looks like a failure in a script | `echo $?` prints `1` | Exit 1 means "differences found" | Test with `k diff -f f.yaml; [ $? -le 1 ]`; exit `2` means a real error |
| 8 | `diff` itself errors | `The Pod "p1" is invalid: spec: Forbidden: ...` then exit `2` | The server-side dry-run was rejected (an immutable field in your file) | Same as row 5; fix the file or use `replace --force` |
| 9 | Huge manifest rejected | `metadata.annotations: Too long: must have at most 262144 bytes` (EXPECTED OUTPUT, not captured) | The last-applied annotation copies the whole file | `k apply --server-side -f big.yaml` |

**6.1 Reading failure 1: apply fights a controller (HPA) on replicas.**

Why it happens: a HorizontalPodAutoscaler changes `spec.replicas` on its own. If your manifest also sets `replicas`, then every `apply` sets it back and every HPA decision sets it away again. The lab cluster has no metrics server, so the captured runs use `k patch` and `k scale` as stand-ins for the autoscaler; the mechanism (a second writer on the same field) is identical. The HPA's own manager name is not captured (see section 11).

Diagnostic path, in order:

1. `k get hpa` and `k get deploy web -w`: do the replica counts jump back after each apply? If yes, two writers exist.
2. `mf deploy web`: look for a manager other than `kubectl-client-side-apply` / `kubectl`. After a stand-in `k scale` the list contains `kubectl  Update  scale`; an autoscaler appears as its own manager with `subresource: scale`.
3. `k get deploy web --show-managed-fields -o jsonpath='{.metadata.managedFields[?(@.manager=="kubectl")].fieldsV1}'`: if `f:replicas` appears in your own manager's set, your file owns the field.
4. `k apply -f d.yaml --server-side` (or `k diff -f d.yaml --server-side`): the conflict message names the other manager and the exact field.

Fix: the file must stop managing `replicas`. The order of the steps matters, and it differs for the two apply modes. The block below uses `k scale` as the stand-in for the autoscaler (it is a second writer, like the HPA). The Kubernetes docs describe the same two paths under "Transferring ownership" (https://kubernetes.io/docs/reference/using-api/server-side-apply/).

**Case A: the object was applied client-side (plain `k apply -f`).** The last-applied annotation still lists `replicas`. If you only delete the line from the file, the next `k apply` sees "in last-applied, not in the file" (second row of the merge-rules table in section 2.2), removes the field from the live object, and the server resets it to the default of 1 until the autoscaler reacts. An HPA does not "take ownership" in a way that prevents this. So remove the field from the annotation first, then from the file:

EXPECTED OUTPUT (not captured). Start state: `d.yaml` has `replicas: 3` and was applied with `k apply -f d.yaml`; the autoscaler stand-in then scaled to 5.

```text
$ k scale deploy web --replicas=5
deployment.apps/web scaled
# wrong: delete the replicas line from d.yaml only, then apply
$ yq -i 'del(.spec.replicas)' d.yaml ; k apply -f d.yaml
deployment.apps/web configured
$ k get deploy web -o jsonpath='{.spec.replicas}{"\n"}'
1
```

Reset (`k scale deploy web --replicas=5`, put `replicas: 3` back in `d.yaml`, `k apply -f d.yaml`, `k scale deploy web --replicas=5`), then do it in the safe order:

```text
$ KUBE_EDITOR="yq -i 'del(.spec.replicas)'" k apply edit-last-applied deploy web   # or run it without KUBE_EDITOR and delete the line in the editor
deployment.apps/web edited
$ yq -i 'del(.spec.replicas)' d.yaml
$ k apply -f d.yaml
deployment.apps/web configured        # "unchanged" is also fine
$ k get deploy web -o jsonpath='{.spec.replicas}{"\n"}'
5
$ k diff -f d.yaml | grep -E '^[-+] +replicas:'
```

The live count stays 5 because `replicas` is now in neither the annotation nor the file (third row of that table: left alone). The last command prints nothing: the diff has no `replicas` line, so the file no longer manages it. `k apply edit-last-applied` is the command from the table in section 2.2.

**Case B: the object is applied server-side.** Ownership is in `managedFields`, not in an annotation. Removing `replicas` from your manifest and re-applying with the same manager releases your claim (rule 5 in section 2.3). The live value is kept only if another manager owns the field; if you were the sole owner, the server deletes the field and it resets to 1. A write from an autoscaler (an `Update` operation with a different value) takes the field away from you (rule 4), so after the autoscaler has written once, your manager is no longer the owner and the removal is safe. Check first with step 3 of the diagnostic path: `f:replicas` must be absent from your manager's field set, or present only together with the other manager.

EXPECTED OUTPUT (not captured). Start state: `d.yaml` (`replicas: 3`) applied with `k apply -f d.yaml --server-side`; the stand-in then scaled to 5.

```text
$ k scale deploy web --replicas=5
deployment.apps/web scaled
$ yq -i 'del(.spec.replicas)' d.yaml
$ k apply -f d.yaml --server-side
deployment.apps/web serverside-applied
$ k get deploy web -o jsonpath='{.spec.replicas}{"\n"}'
5
```

Advice for either case: after the change run `k get deploy web` and `k diff -f d.yaml` (add `--server-side` for case B) and confirm the replica count is the one the autoscaler chose.

**6.2 Reading failure 2: `unknown field`.**

1. Read the quoted path in the message. It is the full path from the object root: `spec.template.spec.containers[0].imagePullPolisy`. The last word is the wrong one.
2. `k explain deploy.spec.template.spec.containers --recursive | grep -i pull` lists the real names (`imagePullPolicy`). Without `--recursive` use `k explain deploy.spec.template.spec.containers.<field>`.
3. Fix the file, then `k apply -f f.yaml --dry-run=server`. A clean server dry run (`... created (server dry run)`) means the file is valid; a client dry run proves nothing about field names.
4. Do not add `--validate=ignore` to make the error go away: the unknown field is dropped and your intent (the pull policy) is silently lost.

**6.3 Reading failure 3: `replace --force` caused downtime.**

1. Symptom: Pods of the Deployment disappear and come back. `k get events` shows `Killing` events for the old Pods, then `ScalingReplicaSet ... Scaled up` events for the recreated Deployment (deleting a Deployment does not scale its ReplicaSet down; the garbage collector deletes the ReplicaSets and Pods).
2. Look at the command you ran. `--force` prints two lines, `... deleted ...` then `... replaced`. The first line is the delete.
3. Fix going forward: for a change that is allowed in place (replicas, image, env, labels), use `apply`, `patch`, `set` or `edit`. For a Pod with an immutable field, `replace --force` is the right tool. For an immutable field on a Deployment, plan a short outage or run the new Deployment under a new name and move the Service selector.
4. Recovery after the fact: `k apply -f d.yaml` recreates anything missing; wait with `k rollout status deploy web`.

## 9. Quick review

1. Which command shows what `apply` would change without changing it, and what does exit status 1 mean?
<details><summary>Answer</summary>

`k diff -f f.yaml`. Exit 0 means no differences, exit 1 means differences were found, and exit greater than 1 means an error (for example the server rejected the change).
</details>

2. Why does client-side apply need the `last-applied-configuration` annotation?
<details><summary>Answer</summary>

It records what you applied last, so kubectl can tell "I removed this field from my file" (delete it) from "someone else added this field" (leave it). Without it there is no third input for the three-way merge.
</details>

3. What command applies a manifest server-side under the manager name `ci`, and what happens if another manager owns a field with a different value?
<details><summary>Answer</summary>

`k apply -f f.yaml --server-side --field-manager=ci`. The request fails with `Apply failed with N conflict(s)` and nothing is changed. Resolve it by `--force-conflicts`, by removing the field from the manifest, or by matching the live value to co-own it.
</details>

4. Which patch type replaces a whole list, and which merges containers by name?
<details><summary>Answer</summary>

`--type=merge` (JSON merge patch) replaces lists; the default `--type=strategic` merges `containers` (and `env`, `ports`) by their merge key. A JSON patch (`--type=json`) addresses list items by index or `/-`.
</details>

5. Write a JSON patch that sets container 0's image to `nginx:1.27` on Deployment `web`.
<details><summary>Answer</summary>

`k patch deploy web --type=json -p '[{"op":"replace","path":"/spec/template/spec/containers/0/image","value":"nginx:1.27"}]'`
</details>

6. Why is `k replace --force -f pod.yaml` fine for a Pod but risky for a Deployment?
<details><summary>Answer</summary>

`--force` deletes the object and creates it again. A bare Pod has nothing depending on it. Deleting a Deployment garbage-collects its ReplicaSets and Pods, so the application is down until the new Pods are ready.
</details>

7. A directory has a sub-directory with one more manifest. Which flag makes `k apply -f dir/` include it, and what happens to it without the flag?
<details><summary>Answer</summary>

`-R` (`--recursive`). Without it the sub-directory is skipped silently, with no warning.
</details>

8. What does `k delete deploy web --cascade=orphan` do?
<details><summary>Answer</summary>

It deletes only the Deployment. Its ReplicaSets and Pods are kept (the owner reference is removed) and nothing manages them any more; delete them with `k delete rs -l app=web`.
</details>

9. Why does `k apply -f f.yaml --dry-run=client` not catch a misspelled field, and what does?
<details><summary>Answer</summary>

Client dry-run never sends the object to the server, and field validation runs on the server. `--dry-run=server` (with the default `--validate=strict`) rejects the unknown field with `strict decoding error: unknown field "..."`.
</details>

10. An HPA and your manifest both set `replicas` and the count keeps flipping. What is the fix?
<details><summary>Answer</summary>

Make the manifest stop owning `spec.replicas`, in the safe order (section 6.1): with client-side apply remove the field from the last-applied annotation first (`k apply edit-last-applied`), then from the file, then apply; with server-side apply remove it from the file once another manager has written it. Otherwise the count drops to 1 in between. With server-side apply the conflict message names the other manager; do not just add `--force-conflicts`.
</details>
