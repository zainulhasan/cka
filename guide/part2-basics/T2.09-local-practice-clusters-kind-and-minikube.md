## 1. Why this matters

Kubernetes is a skill of the hands. You need a cluster you can break, delete and rebuild ten times a day without paying for it or asking anyone. If you only read, the first time you see `ImagePullBackOff`, `NotReady` or a missing `metrics-server` will be during a timed exam task, and you will lose minutes you do not have.

kind (Kubernetes IN Docker) builds a multi-node cluster on a laptop in about a minute and runs the same Kubernetes minor version as the exam (v1.37, see E6 in section 10). Almost every lab in Parts 2 and 3 runs on it. This lesson also shows where kind lies to you: it is not a real machine, so the node-level topics of Part 4 need virtual machines.

## 2. Concepts

### 2.1 What kind is, and what it does when you run `kind create cluster`

**The problem it solves.** A real cluster needs several machines. A laptop has one. kind turns each "machine" into a Docker (or Podman) container. Inside each container runs a full node: systemd, containerd, kubelet. The control-plane container also runs the API server, etcd, scheduler and controller manager as static Pods (T2.01).

**What kind does, in order** (the progress lines are real, see section 5):

1. Reads your config file (or uses a default 1-node config) and validates it. A bad file fails here, before any container exists (section 2.4).
2. Makes sure the node image exists locally; pulls it if not (`Ensuring node image`).
3. Creates one container per node on a Docker network called `kind` (`Preparing nodes`).
4. Writes a `kubeadm` configuration into the control-plane container (`Writing configuration`).
5. Runs `kubeadm init` inside the control-plane container (`Starting control-plane`).
6. Installs the default CNI (a small plugin called kindnet) unless you disabled it, and a default StorageClass backed by local-path (`Installing StorageClass`).
7. Runs `kubeadm join` inside each worker container (`Joining worker nodes`).
8. Writes a context named `kind-<name>` into your kubeconfig and switches to it (`Set kubectl context to "kind-<name>"`).

So a kind cluster is a real kubeadm cluster. What differs is the "hardware": the containers share your laptop's kernel (section 2.13).

| Term | Meaning |
|---|---|
| node image | A Docker image that contains systemd, containerd, kubelet, kubeadm, kubectl and all control-plane images for one Kubernetes version. Every node container starts from it. |
| provider | The container engine kind talks to: `docker` (default), `podman`, or `nerdctl`. |
| cluster name | A label you choose with `--name`. Default is `kind`. Node containers are `<name>-control-plane`, `<name>-worker`, `<name>-worker2`. |
| context | The kubeconfig entry kind creates: `kind-<name>`. |

### 2.3 The node image, and pinning it by digest

kind v0.33.0 uses this image by default: `kindest/node:v1.37.0@sha256:a1ed56cfb0e7b93589bdf97c8cd566405a265939e3620fc4f5de89adff580ae5`. This exact string is compiled into the v0.33.0 binary, and a cluster built from it reported `Server Version: v1.37.0`.

| Form | Example | What it means | Risk |
|---|---|---|---|
| tag only | `kindest/node:v1.37.0` | Whatever the registry says `v1.37.0` is today. A tag can be re-pushed. | Two people get different nodes. |
| digest only | `kindest/node@sha256:a1ed...` | The exact content. Immutable. | Hard to read. |
| tag + digest | `kindest/node:v1.37.0@sha256:a1ed...` | Human label plus exact content. The runtime checks the digest and ignores the tag for lookup. | None. Use this. |

The digest is the digest of the multi-architecture image index, so the same string works on amd64 and arm64 machines (the capture ran it on arm64). kind prints only `kindest/node:v1.37.0` in its progress lines even when the config has a digest; that is cosmetic.

Set the image per node in the config (`nodes[].image`) or for every node with `kind create cluster --image <ref>`. Risky values: an image built for another kind release, or a different Kubernetes minor. kind's release notes list which images go with which release. A wrong pairing can fail at `kubeadm init` with errors about unsupported fields.

### 2.4 The kind config file

A kind config looks like a Kubernetes object (it has `kind` and `apiVersion`) but it is **not** one. You do not `kubectl apply` it. Only `kind create cluster --config <file>` reads it. Validation happens before any container is created, so mistakes cost you a second:

REAL OUTPUT (kind v0.33.0), four deliberately bad files:

```text
$ kind create cluster --name k-t209x --config bad/a.yaml      # apiVersion: kind.x-k8s.io/v1alpha5
ERROR: failed to create cluster: unknown apiVersion: kind.x-k8s.io/v1alpha5

$ kind create cluster --name k-t209x --config bad/b.yaml      # networking.kubeProxyMode: bogus
ERROR: failed to create cluster: invalid kubeProxyMode: bogus

$ kind create cluster --name k-t209x --config bad/c.yaml      # only a worker node, no control-plane
ERROR: failed to create cluster: must have at least one control-plane node

$ kind create cluster --name k-t209x --config bad/d.yaml      # extraPortMappings protocol: HTTP
ERROR: failed to create cluster: unable to decode config: Unknown PortMappingProtocol: "HTTP"
```

The fields you must know:

| Field | What it does | Default | Invalid or risky value |
|---|---|---|---|
| `kind: Cluster` | Object type of the file. | required | Any other kind. |
| `apiVersion: kind.x-k8s.io/v1alpha4` | Config schema version. v0.33.0 accepts `v1alpha4`. | required | `v1alpha5` -> `unknown apiVersion` (above). |
| `name` | Cluster name inside the file. The `--name` flag overrides it. | `kind` | Two clusters with the same name. |
| `nodes[].role` | `control-plane` or `worker`. One list entry = one container. | one control-plane | No control-plane (above). Several control-planes make kind add an extra load-balancer container (documented behaviour, not run here). |
| `nodes[].image` | Node image for that node. | the kind release default | Mixed Kubernetes versions on nodes beyond the version-skew rules; image from another kind release. |
| `nodes[].extraPortMappings` | Publishes a container port on the host. Fields: `containerPort`, `hostPort`, `listenAddress` (default `0.0.0.0`), `protocol` (`TCP` default, `UDP`, `SCTP`). | none | `protocol: HTTP` (above). A `hostPort` already used on the host. `listenAddress: 0.0.0.0` exposes the port to your whole network; use `127.0.0.1` on a shared network. |
| `networking.disableDefaultCNI` | If `true`, kind does not install kindnet. You must install a CNI or no node becomes Ready. | `false` | `true` with no CNI installed -> nodes stay `NotReady` (section 6). |
| `networking.podSubnet` | The Pod IP range (the controller manager's `--cluster-cidr`). | `10.244.0.0/16` | A range that overlaps the Docker network or the Service range (section 6, row 6). |
| `networking.serviceSubnet` | The Service ClusterIP range. | `10.96.0.0/16` (the API Service was `10.96.0.1` in the capture) | Overlap with `podSubnet`. |
| `networking.kubeProxyMode` | How kube-proxy programs Service rules: `iptables`, `nftables`, `ipvs`, or `none`. | `iptables` (the `kube-proxy` ConfigMap showed `mode: iptables`) | `ipvs` is deprecated in this course (conventions section 6). `none` means no Service routing unless you install a replacement. Any other word is rejected (above). |

**`kubeProxyMode` variants.** The mode decides how kube-proxy turns Services into packet rules on each node. The check for every variant is the same: read the mode back from the ConfigMap that kubeadm writes, `k -n kube-system get cm kube-proxy -o yaml | grep -E '^\s+mode:'`.

| Value | Effect | Use in this course |
|---|---|---|
| `iptables` | iptables rules (the default; captured above as `mode: iptables`) | Yes. |
| `nftables` | nftables rules; needs a kernel and `nft` tool recent enough for kube-proxy's nftables backend | Optional, example below. |
| `ipvs` | IPVS kernel tables | No. Deprecated (conventions section 6). |
| `none` | kind skips kube-proxy entirely, so Services have no rules until you install a replacement | No. Check: `k -n kube-system get ds kube-proxy` should report `NotFound`. |

EXPECTED OUTPUT (not captured): example for `nftables`. Save as `nft.yaml`:

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
networking:
  kubeProxyMode: "nftables"      # default is iptables
```

```bash
kind create cluster --name nft --config nft.yaml
k --context kind-nft -n kube-system get cm kube-proxy -o yaml | grep -E '^\s+mode:'      # expected:     mode: nftables
kind delete cluster --name nft
```

The default CNI (kindnet) is used here because the file does not disable it, so the single node becomes Ready without Calico. If the node's kernel is too old for nftables, kube-proxy fails to start; `k -n kube-system logs ds/kube-proxy` shows why (text not captured).

Other documented fields that this course does not use (not run in this lesson): `networking.ipFamily`, `networking.apiServerAddress`, `networking.apiServerPort`, `nodes[].labels`, `nodes[].extraMounts`, `nodes[].kubeadmConfigPatches`, `featureGates`, `runtimeConfig`, `containerdConfigPatches`. The full list is on https://kind.sigs.k8s.io/docs/user/configuration/ (a study site, not an allowed exam doc site; see E13 in section 10).

**Why this course turns the default CNI off.** NetworkPolicy objects are only enforced if the CNI plugin implements them. The CKAD labs on NetworkPolicy (Part 3) need a plugin you know enforces them, so the cluster uses Calico instead of kindnet. The price: right after creation the cluster has no networking and every node is `NotReady` until Calico is installed (2.8).

**The exact config used by every later lesson** (`env/kind.yaml`). The same config is copied in the conventions file:

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
networking:
  disableDefaultCNI: true        # Calico is installed by kind-up.sh (needed for NetworkPolicy)
  podSubnet: 192.168.0.0/16
nodes:
  - role: control-plane
    image: kindest/node:v1.37.0@sha256:a1ed56cfb0e7b93589bdf97c8cd566405a265939e3620fc4f5de89adff580ae5
    extraPortMappings:
      - { containerPort: 30080, hostPort: 30080, protocol: TCP }   # NodePort lab traffic
  - role: worker
    image: kindest/node:v1.37.0@sha256:a1ed56cfb0e7b93589bdf97c8cd566405a265939e3620fc4f5de89adff580ae5
  - role: worker
    image: kindest/node:v1.37.0@sha256:a1ed56cfb0e7b93589bdf97c8cd566405a265939e3620fc4f5de89adff580ae5
```

**How `extraPortMappings` works.** It makes Docker publish port 30080 of the control-plane container on port 30080 of your laptop. In the capture, `docker ps` showed `0.0.0.0:30080->30080/tcp` on the control-plane container only (section 5). A NodePort Service listens on the same port on every node (kube-proxy programs it everywhere), so a request that enters through the control-plane container reaches Pods on any worker. The mapping is why `curl localhost:30080` works. It only works for the exact port you listed. A NodePort of 30081 is not reachable from the host unless you add a mapping and recreate the cluster, because Docker cannot add a published port to a running container.

### 2.5 Cluster lifecycle commands

| Command | What it does |
|---|---|
| `kind create cluster --name ckad --config kind.yaml` | Create a cluster. `--name` sets the name (default `kind`). `--config` sets the file. Other flags: `--image`, `--wait <duration>` (default `0s`, so it returns without waiting for Ready), `--retain` (keep the failed node containers for debugging), `--kubeconfig <path>`. |
| `kind get clusters` | List cluster names. |
| `kind get nodes --name ckad` | List the node container names of one cluster. |
| `kind get kubeconfig --name ckad` | Print a kubeconfig for that cluster to stdout. |
| `kind delete cluster --name ckad` | Delete the node containers and remove the context from your kubeconfig. |
| `kind export kubeconfig --name ckad` | Re-write the cluster's context into your kubeconfig (for example after you deleted it by mistake). |
| `kind export logs ./logs --name ckad` | Copy node and kubelet logs into a folder. Use it when a create fails. |

**Names and contexts.** The entry's example uses the cluster name `ckad`, which gives the context `kind-ckad`. The course's standard cluster is named `lab`, which gives `kind-lab`. The name is only a label: pick one, and then every `docker exec` target and `--name` flag must use it. Several clusters can exist at once. kubectl talks to the one named by the *current context*.

### 2.7 Local images: `kind load docker-image`

**The problem.** You build an image on your laptop with `docker build -t myapp:1 .`. It lives in your laptop Docker's image store. The node containers have their *own* containerd with its *own* image store. They know nothing about your laptop's images, so the kubelet tries to pull `docker.io/library/myapp:1` from the internet, finds nothing, and fails.

Setup for this section: `k create ns lab-t209` (the Pods below run in it), and a folder `img` with a two-line Dockerfile (`FROM busybox:1.36` and a `CMD` that prints and sleeps; drill 4 in 4.4 shows a similar one).

REAL OUTPUT (kind v0.33.0, v1.37.0):

```text
$ kubectl -n lab-t209 run myapp --image=myapp:1
pod/myapp created

$ kubectl -n lab-t209 get pod myapp
NAME    READY   STATUS             RESTARTS   AGE
myapp   0/1     ImagePullBackOff   0          25s

$ kubectl -n lab-t209 get events --field-selector involvedObject.name=myapp | tail -6
```

**The fix.** `kind load docker-image` copies the image from your Docker into the containerd of **every** node:

```text
$ kind load docker-image myapp:1 --name k-t209
Image: "myapp:1" with ID "sha256:54b3ee6a...b69fe4e" not yet present on node "k-t209-worker", loading...
Image: "myapp:1" with ID "sha256:54b3ee6a...b69fe4e" not yet present on node "k-t209-control-plane", loading...
Image: "myapp:1" with ID "sha256:54b3ee6a...b69fe4e" not yet present on node "k-t209-worker2", loading...

$ docker exec k-t209-worker crictl images | grep -E 'IMAGE|myapp'
IMAGE                                           TAG                  IMAGE ID            SIZE
docker.io/library/myapp                         1                    54b3ee6a16dd4       4.34MB
```

The image is now stored as `docker.io/library/myapp:1` on each node. The broken Pod may recover by itself when its pull back-off timer expires, but that can take minutes, and running `k run myapp` again would fail with `AlreadyExists` while the old Pod exists. For a clean test delete it first: `k -n lab-t209 delete pod myapp`. A new Pod then finds the image locally and skips the pull, **if the pull policy allows that**:

| Image reference | Default `imagePullPolicy` | Works after `kind load`? |
|---|---|---|
| `myapp:1` (any tag except `latest`) | `IfNotPresent` | Yes. |
| `myapp` or `myapp:latest` | `Always` | No. The kubelet always asks the registry and fails. (And this course never uses `:latest`.) |
| any tag with `imagePullPolicy: Always` | `Always` | No (captured below). |
| any tag with `imagePullPolicy: Never` | `Never` | Yes, and it fails if the image is missing. |

REAL OUTPUT (kind v0.33.0, v1.37.0), same loaded image, explicit policies:

```text
$ kubectl -n lab-t209 run myapp --image=myapp:1 --image-pull-policy=IfNotPresent
pod/myapp created
$ kubectl -n lab-t209 wait --for=condition=Ready pod/myapp --timeout=60s
pod/myapp condition met

$ kubectl -n lab-t209 run myapp-always --image=myapp:1 --image-pull-policy=Always
pod/myapp-always created
$ kubectl -n lab-t209 get pod myapp-always
NAME           READY   STATUS             RESTARTS   AGE
myapp-always   0/1     ImagePullBackOff   0          20s
```

**Rebuild rule.** `kind load` skips a node if the image ID there already matches. If you rebuild `myapp:1` and load it again, the node gets the new image, but running Pods keep the old one until they restart. Use a new tag for each build (`myapp:2`) so there is no doubt which code runs.

**Variants.** `kind load image-archive myapp.tar --name lab` loads a tar from `docker save`. A local registry also works (kind's docs describe the pattern), but it needs more setup than this course uses. Some Docker setups that use the containerd image store fail `kind load` with `content digest ... not found`; kind's known-issues page lists it. That error did not occur in the capture, so the workaround here (`docker save` then `kind load image-archive`) is untested (section 11).

### 2.8 Calico on kind, for NetworkPolicy labs

**What happens without a CNI.** The container runtime reports `NetworkReady=false` until a CNI config file exists in `/etc/cni/net.d` on the node. The kubelet copies that into the node's Ready condition, so the node is `NotReady`. The scheduler also refuses to put ordinary Pods on it (the node has a `not-ready` taint). (The control-plane Pods `etcd`, `kube-apiserver`, ... run anyway because they are static Pods that use the host network and need no CNI. **Install Calico.** The manifest URL for v3.33.0 returned HTTP 200 and its images are `quay.io/calico/{node,calico,third-party-cni-plugins}:v3.33.0`:

```bash
k apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.33.0/manifests/calico.yaml
k -n kube-system rollout status ds/calico-node --timeout=600s
k wait --for=condition=Ready nodes --all --timeout=300s
```

**Why the Pod range matters.** In that manifest `CALICO_IPV4POOL_CIDR` is commented out (`# value: "192.168.0.0/16"`), so Calico uses its default pool `192.168.0.0/16`. That is why `env/kind.yaml` sets `podSubnet: 192.168.0.0/16`: the two must agree. If you change `podSubnet`, you must also set `CALICO_IPV4POOL_CIDR` in the manifest. The pool was read back after install (`k get ippools.crd.projectcalico.org -o jsonpath='{.items[0].spec.cidr}'` printed `192.168.0.0/16`) and `cluster-cidr=192.168.0.0/16` in the controller manager flags.

**Under the hood.** `calico-node` is a DaemonSet. Its init containers copy the CNI plugin binaries to `/opt/cni/bin` and write `10-calico.conflist` and `calico-kubeconfig` into `/etc/cni/net.d` on the node (visible in 2.6). containerd sees the file, `NetworkReady` becomes true, the kubelet sets the node `Ready`, and the pending Pods get scheduled. The DaemonSet's main container then runs the agent that programs routes and, for NetworkPolicy, packet filters.

**First run is slow.** Each node pulls three Calico images from quay.io. On the capture network that took 6 to 7 minutes on a cold cache, both times the cluster was built. The script `kind-up.sh` (section 4.3) therefore waits up to 600 s for the DaemonSet and 300 s for the nodes, so the first run completes. An earlier version waited only 180 s and ended with `error: timed out waiting for the condition` while the cluster was still healthy and still pulling. On a connection slower than the capture's, section 6, row 4, explains what to do.

### 2.9 metrics-server on kind (why it needs `--kubelet-insecure-tls`)

`k top nodes` and `k top pods` read the Metrics API, which is served by the add-on **metrics-server**. It scrapes every kubelet over HTTPS on port 10250. By default it connects to the node's InternalIP and checks the kubelet's serving certificate. In a kind node the kubelet certificate is self-signed and has no IP SANs, so verification fails. The flag `--kubelet-insecure-tls` makes metrics-server skip that check. It is fine for a throwaway lab. Never use it on a real cluster.

REAL OUTPUT (kind v0.33.0, v1.37.0), metrics-server v0.9.0 `components.yaml` applied as-is:

### 2.10 minikube v1.39: the alternative

minikube is a different tool with the same goal. It builds the cluster with kubeadm too, but it ships add-ons and has its own node handling.

| | kind | minikube |
|---|---|---|
| Node is | a container (always) | a container (Docker/Podman driver) or a VM (other drivers) |
| Default Kubernetes version | set by the node image (v1.37.0 for kind v0.33.0) | v1.37.0 for v1.39.0 (its `--kubernetes-version` help says `'stable' for v1.37.0`) |
| Multi-node | list nodes in the config file | `minikube start --nodes 3` |
| Cluster name | `--name` (default `kind`) | profile `-p` (default `minikube`) |
| Container runtime in the node | containerd | containerd for new clusters in v1.39.0 (from its source, `defaultRuntime()`), selectable with `--container-runtime=docker\|containerd\|cri-o` |
| Add-ons | install by hand | `minikube addons enable <name>` (ingress, metrics-server, ...) |
| Load a local image | `kind load docker-image` | `minikube image load <image>` |
| LoadBalancer Services | pending (needs MetalLB) | `minikube tunnel` |
| Shell into a node | `docker exec -it <node> bash` | `minikube ssh -p <profile> -n <node>` |
| Port exposure | `extraPortMappings` | `minikube service`, `minikube tunnel` |

Commands (EXPECTED OUTPUT (not captured); the version and flags were checked on the installed binary and its help text, but no cluster was started):

Notes on the commands above (EXPECTED OUTPUT (not captured); none of this was run):

- **Driver.** `--driver=docker` (short `-d docker`) runs each minikube node as a container, like kind. If you omit it, minikube picks a driver itself; pass it to be explicit.
- **Memory.** Each node gets `--memory=2g`, so 3 nodes ask for 6 GiB, on top of what the container engine already needs. Give the engine more than that, or use `--nodes 2`, or a lower `--memory`.
- **CNI.** The default `--cni=auto` lets minikube choose a CNI itself for a multi-node cluster (which one v1.39.0 chooses is UNVERIFIED). `--cni=calico` is only needed when you want NetworkPolicy enforcement as in the course; the answers in 4.4 and section 9 leave it out because they only ask for a 3-node cluster.
- **Add-ons.** `minikube -p mk addons list` shows what is enabled. `addons enable ingress` historically deploys a controller into the namespace `ingress-nginx`; check with `k -n ingress-nginx get pods` (controller identity in v1.39.0 is UNVERIFIED).
- **Lifecycle.** `minikube status -p mk` shows each node. `minikube stop -p mk` keeps the cluster and `minikube start -p mk` resumes it. `minikube delete -p mk` removes one profile and `minikube delete --all` removes every profile.

Flags from `minikube start --help` (real): `--nodes` ("The total number of nodes to spin up. Defaults to 1."), `--kubernetes-version`, `--container-runtime` / `-c` ("Valid options: docker, cri-o, containerd (default: auto)"), `--cni` ("Valid options: auto, bridge, calico, cilium, flannel, kindnet, or path to a CNI manifest"), `--cpus` (default `2`), `--memory`, `--addons`, `--driver` / `-d`.

Two warnings. First, the `ingress` add-on has historically installed the ingress-nginx controller. That project is retired (conventions section 6), so use the add-on to learn the Ingress API only. For controller-specific work use Traefik as in the Medium lab. Which controller the exam uses is UNVERIFIED (E23). Second, minikube profiles that you created with an older minikube keep their old runtime (some are `docker`); only new clusters default to containerd.

### 2.11 Resource sizing, and Docker versus Podman

**Memory.** A kind node is a normal Linux userspace in a container, so idle usage is small. REAL numbers (`docker stats --no-stream`, 3-node cluster with Calico, no workload, kind v0.33.0):

```text
NAME                   CPU %     MEM USAGE / LIMIT
k-t209-worker          3.66%     198.9MiB / 15.66GiB
k-t209-worker2         4.37%     352.2MiB / 15.66GiB
k-t209-control-plane   21.75%    958.9MiB / 15.66GiB
```

So the cluster alone is about 1.5 GiB. Advice (not a measured limit): give the container engine at least 4 GiB if you run only the course cluster, and 6 to 8 GiB if you also run Traefik, metrics-server and a few Deployments. On Docker Desktop or OrbStack this is the VM memory setting. On Linux, Docker uses host RAM directly. Do not run more than one 3-node cluster at a time. CPU: 2 cores is workable; Calico's first start and image pulls are the heavy part.

**inotify (Linux hosts).** Each node's kubelet and containers use inotify watches. These limits are per user on the host, not per container. The defaults depend on the distribution and kernel (`max_user_instances=128` is a common default, and newer kernels scale `max_user_watches` with RAM), and they can be too low for a multi-node cluster. Check yours, and raise them if `max_user_instances` is 128 or `max_user_watches` is well below 524288. The values below are the ones kind's known-issues page recommends:

```bash
sysctl fs.inotify.max_user_watches fs.inotify.max_user_instances     # check first
sudo sysctl fs.inotify.max_user_watches=524288 fs.inotify.max_user_instances=512
printf 'fs.inotify.max_user_watches=524288\nfs.inotify.max_user_instances=512\n' | sudo tee /etc/sysctl.d/99-kind.conf
```

**Docker versus Podman.**

| | Docker | Podman |
|---|---|---|
| kind | default provider | `KIND_EXPERIMENTAL_PROVIDER=podman kind create cluster ...` (the variable is in the v0.33.0 binary; behaviour not run here) |
| Node shell | `docker exec -it lab-worker bash` | `podman exec -it lab-worker bash` |
| Rootless | possible but needs extra setup | commonly used rootless; kind's docs describe the cgroup v2 delegation it needs |
| minikube | `--driver=docker` | `--driver=podman` (marked experimental in the v1.39.0 help) |

All commands in this course say `docker`. With Podman, substitute `podman` for `docker`. The Docker network override in section 6 has a Podman twin: `KIND_EXPERIMENTAL_PODMAN_NETWORK`.

### 2.13 Limitations: what kind cannot teach you

| Limit | Why | What to use instead |
|---|---|---|
| No kernel of its own | The nodes share the laptop's kernel (`uname -r` above). You cannot load a different kernel module, reboot a node, or test kernel settings per node. | A VM. |
| systemd exists but it is a container's systemd | PID 1 is systemd and `systemctl status kubelet` works (2.6), but there is no boot, no real disks, no package manager workflow that persists a node across a reboot. | A VM. |
| kubeadm and kubelet are baked into the node image | The CKA upgrade task (`apt-get install kubeadm=1.37.1-...`, `kubeadm upgrade apply`, restart kubelet) has no package repo to work against inside the node. | 3 Ubuntu VMs with `pkgs.k8s.io` packages. |
| Node IPs are Docker IPs | On macOS and Windows you cannot reach a node IP from the host. Only published ports work. | `extraPortMappings`, `kubectl port-forward`. |
| `LoadBalancer` Services stay `<pending>` | No cloud controller. | MetalLB (conventions add-on table). |
| Not durable | Treat the cluster as disposable; rebuild instead of repairing after a host reboot. | `kind-up.sh`. |

So Part 4 topics about nodes (kubeadm install and upgrade, certificates on disk, kubelet and container-runtime troubleshooting, etcd data directories, static Pod directories and admission plugin flags on a real host) use VMs. Those are the topics T4.01 to T4.05, T4.17, T4.18, T4.23, T4.25 and T4.26 plus the VM parts of T4.10, T4.13, T4.16 and T4.27 in the conventions file (section 2.3 there). Everything else, including Pods, Deployments, Services, Ingress, NetworkPolicy, RBAC, storage with local-path, and Helm, runs on kind.

**Related but different.**

- `docker exec` is not `ssh`. The exam hands you hosts with `ssh <node>` and `sudo -i` (E7, E8). `docker exec -it lab-worker bash` is the kind stand-in. Practise the muscle memory "go to the node, fix it, exit back" but do not conclude that every node tool exists the same way.
- A kind "node" is not a kubeadm node you installed. If a lab says "SSH to a node", it means a VM lab.
- `kind load` is not `docker push`. A pushed image goes to a registry any node can pull from. A loaded image exists only on the nodes of that one cluster.
- `kubectl port-forward` and `extraPortMappings` both give you host access. Port-forward needs a running command and one Pod. The port mapping is fixed at cluster creation and goes through a NodePort.

## 3. How it works (diagram)

```text
 YOUR LAPTOP (host OS; ONE kernel, shared by everything below)
 +---------------------------------------------------------------------------------+
 |  kubectl --kubeconfig context kind-lab--> https://127.0.0.1:<random>  ----+     |
 |  curl localhost:30080 ---------------------------------------+           |     |
 |                                                                |           |     |
 |  Docker (or Podman) engine         user-defined network "kind" (a /16 or /24)   |
 |  +-----------------------------+  +----------------+  +----------------+        |
 |  | container: lab-control-plane|  | lab-worker     |  | lab-worker2    |        |
 |  |  published: 30080 -> 30080 -+  |                |  |                |        |
 |  |  published: <random> -> 6443   |                |  |                |        |
 |  |  systemd (PID 1)            |  |  systemd       |  |  systemd       |        |
 |  |   kubelet                   |  |   kubelet      |  |   kubelet      |        |
 |  |   containerd  (own images)  |  |   containerd   |  |   containerd   |        |
 |  |    static Pods: etcd,       |  |    kube-proxy  |  |    kube-proxy  |        |
 |  |     apiserver, scheduler,   |  |    calico-node |  |    calico-node |        |
 |  |     controller-manager      |  |    your Pods   |  |    your Pods   |        |
 |  |    kube-proxy, calico-node  |  |                |  |                |        |
 |  |    coredns, your Pods       |  |                |  |                |        |
 |  +-----------------------------+  +----------------+  +----------------+        |
 |   Pod IPs come from podSubnet 192.168.0.0/16 (Calico); Service IPs 10.96.0.0/16 |
 |   Local images: laptop Docker --kind load docker-image--> containerd in each node |
 +---------------------------------------------------------------------------------+
```

- Each node is one container. Inside it, systemd runs containerd and the kubelet, exactly as on a real machine. The Pods you create are containers *inside* that containerd, not siblings in your laptop's Docker. `docker ps` shows only the three node containers.
- `kubectl` reaches the API server through the port Docker published for the control-plane container's 6443, on `127.0.0.1`. The kubeconfig context `kind-lab` stores that address.
- `curl localhost:30080` enters at the published port 30080 of the control-plane container. A NodePort Service on 30080 (programmed by kube-proxy on every node) forwards it to a Pod on any node.
- The `kind` Docker network gives each node an IP. The Pod range (`podSubnet`) must not overlap it, or Pod-to-node traffic breaks (section 6, row 6).
- Images are per node. `kind load docker-image` copies an image from the laptop's Docker store into each node's containerd store.

### 4.2 The declarative YAML you must write from memory

You cannot type a 64-character digest from memory, and you do not need to. In kind v0.33.0 the default node image *is* the pinned digest (2.3), so omit the `image` lines. This is the version to type in the exam-like speed drill:

```yaml
kind: Cluster                        # object type: a kind cluster definition (not a Kubernetes object)
apiVersion: kind.x-k8s.io/v1alpha4   # config schema version understood by kind v0.33.0
networking:
  disableDefaultCNI: true            # do not install kindnet; you install Calico yourself (default: false)
  podSubnet: 192.168.0.0/16          # Pod IP range; must equal Calico's default pool (default: 10.244.0.0/16)
nodes:
  - role: control-plane              # one container running the control plane
    extraPortMappings:
      - containerPort: 30080         # port inside the control-plane container
        hostPort: 30080              # port on your laptop
        protocol: TCP                # TCP is the default; UDP and SCTP are also valid
  - role: worker                     # first worker container
  - role: worker                     # second worker container
```

Compared with `env/kind.yaml` (2.4), the only difference is that this one has no `image:` lines. Because the default image for kind v0.33.0 equals the pinned digest, both build identical nodes. No cluster was created from this exact short file; the claim rests on the digest match (section 11).

`env/kind-addons.sh <name>`: install an add-on (the lessons use `metrics-server`, `gateway-api-crds`, `traefik`; `metallb`, `helm` and `kustomize` exist too).

```bash
#!/usr/bin/env bash
# usage: kind-addons.sh metrics-server|gateway-api-crds|traefik|metallb|helm|kustomize
# helm and kustomize are downloaded into $BIN_DIR (default ~/.local/bin); add it to PATH.
set -euo pipefail

BIN_DIR=${BIN_DIR:-$HOME/.local/bin}
os=$(uname -s | tr '[:upper:]' '[:lower:]')
arch=$(uname -m)
case "$arch" in x86_64) arch=amd64 ;; aarch64|arm64) arch=arm64 ;; esac

# fetch_bin <tar.gz url> <binary name>: unpack the archive and copy that one binary into $BIN_DIR
fetch_bin() {
  local tmp; tmp=$(mktemp -d)
  curl -fsSL "$1" | tar -xz -C "$tmp"
  mkdir -p "$BIN_DIR"
  install -m 0755 "$(find "$tmp" -type f -name "$2" | head -1)" "$BIN_DIR/$2"
  rm -rf "$tmp"
  echo "installed $BIN_DIR/$2"
}

case "${1:?add-on name}" in
  metrics-server)
    kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.9.0/components.yaml
    kubectl -n kube-system patch deploy metrics-server --type=json \
      -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]' ;;
  gateway-api-crds)
    kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.6.3/standard-install.yaml ;;
  traefik)
    helm repo add traefik https://traefik.github.io/charts && helm repo update
    helm upgrade --install traefik traefik/traefik -n traefik --create-namespace --version 42.1.3 \
      --set providers.kubernetesGateway.enabled=true ;;
  metallb)
    helm repo add metallb https://metallb.github.io/metallb && helm repo update
    helm upgrade --install metallb metallb/metallb -n metallb-system --create-namespace --version 0.16.1 ;;
  helm)
    fetch_bin "https://get.helm.sh/helm-v4.3.1-$os-$arch.tar.gz" helm ;;
  kustomize)
    fetch_bin "https://github.com/kubernetes-sigs/kustomize/releases/download/kustomize%2Fv5.8.3/kustomize_v5.8.3_${os}_${arch}.tar.gz" kustomize ;;
  *) echo "unknown add-on: $1" >&2; exit 1 ;;
esac
```

What the add-ons pin (matching the conventions table): metrics-server v0.9.0 plus `--kubelet-insecure-tls`, Gateway API CRDs v1.6.3 (standard channel), Traefik chart 42.1.3 (app v3.7.16, the version that resolved in the capture; pinned so a later chart release cannot change every later lesson), MetalLB chart 0.16.1, Helm v4.3.1 and kustomize v5.8.3. `helm` and `kustomize` download the release archive for your OS and CPU and copy one binary into `$BIN_DIR`. Use a folder that is on your `PATH`, or add `~/.local/bin` to it.

## 6. Common mistakes and how to fix them

| # | Symptom | What you will see (exact error/event text) | Cause | Fix (command) |
|---|---|---|---|---|
| 1 | `kind create cluster` hangs at "Starting control-plane" | The line `Starting control-plane` stays on screen for minutes, then `ERROR: failed to create cluster: failed to init node with kubeadm` (EXPECTED OUTPUT (not captured)). Kubelet logs may show `too many open files` (kind's known-issues page describes this symptom) | Low memory in the Docker VM, or low inotify limits on a Linux host | Free RAM or raise Docker memory; set `fs.inotify.max_user_watches=524288` and `fs.inotify.max_user_instances=512` (2.11); recreate |
| 2 | Pods and nodes not ready after `disableDefaultCNI: true` | `k get nodes` -> `NotReady`; node message `container runtime network not ready: NetworkReady=false reason:NetworkPluginNotReady message:Network plugin returns error: cni plugin not initialized` (REAL); CoreDNS `Pending` | No CNI installed yet, `/etc/cni/net.d` is empty | `k apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.33.0/manifests/calico.yaml` then wait for `ds/calico-node` |
| 3 | Local image fails | `ImagePullBackOff`; event `Failed to pull image "myapp:1": failed to pull and unpack image "docker.io/library/myapp:1": ... pull access denied, repository does not exist or may require aut...` (REAL) | The image exists only in your laptop's Docker, not in the nodes' containerd | `kind load docker-image myapp:1 --name lab`, use a non-`latest` tag, and `imagePullPolicy: IfNotPresent` (or leave the default) |
| 4 | `kind-up.sh` stops during the Calico wait | `Waiting for daemon set "calico-node" rollout to finish: 0 of 3 updated pods are available...` then `error: timed out waiting for the condition` (REAL, captured when the script still used a 180 s wait) | Calico's images were still downloading. This took 6 to 7 minutes on the cold-cache capture; the script now waits 600 s, so only a slower connection reaches it. The cluster itself is fine | `k -n kube-system get pods -l k8s-app=calico-node` (look for `Init:N/4`), then `k -n kube-system rollout status ds/calico-node --timeout=600s` and `k wait --for=condition=Ready nodes --all --timeout=300s` |
| 5 | `k top nodes` fails | `error: Metrics API not available`; APIService `False (MissingEndpoints)`; log `x509: cannot validate certificate for 172.29.0.4 because it doesn't contain any IP SANs` (REAL) | metrics-server verifies the kubelet certificate and the kind kubelet certificate has no IP SAN | Patch `--kubelet-insecure-tls` into the Deployment (2.9) |
| 6 | Pods on worker nodes cannot reach the API Service; metrics-server crashes | `panic: unable to load configmap based request-header-client-ca-file: Get "https://10.96.0.1:443/api/v1/namespaces/kube-system/configmaps/extension-apiserver-authentication": dial tcp 10.96.0.1:443: i/o timeout`; probes `context deadline exceeded`; `wget: download timed out` from a Pod on a worker (REAL) | The Docker network `kind` had a subnet inside the Pod CIDR (see below) | Recreate on a dedicated network (below) |
| 7 | Port 30080 cannot be bound | Docker error ending in `port is already allocated` or `address already in use` (EXPECTED OUTPUT (not captured)) | Another process or another kind cluster already uses host port 30080 | `docker ps --format '{{.Names}} {{.Ports}}' \| grep 30080`; delete the other cluster, or pick a different `hostPort` |
| 8 | `kubectl` acts on the wrong cluster | Objects "disappear", or `k get nodes` shows `drill-control-plane` | The current context is another cluster | `k config current-context`; `k config use-context kind-lab` |
| 9 | Config rejected | `ERROR: failed to create cluster: unknown apiVersion: kind.x-k8s.io/v1alpha5` (REAL) | Typo in `apiVersion` (or any other bad field, see 2.4) | Use `kind.x-k8s.io/v1alpha4`; the error is raised before any container exists, so nothing to clean up |

**Troubleshooting path for a create that hangs (row 1).** Run these in order:

1. `docker info --format '{{.MemTotal}}'` (or the Docker Desktop settings): is there under about 4 GiB?
2. `sysctl fs.inotify.max_user_watches fs.inotify.max_user_instances` on a Linux host: is `max_user_instances` 128, or `max_user_watches` well below 524288? (kind's known-issues page recommends 524288 and 512. Compare with those numbers, not with a remembered default.)
3. Cancel, then recreate with `kind create cluster --name lab --config kind.yaml --retain`. `--retain` keeps the node containers when the create fails.
4. `docker logs lab-control-plane | tail -30`, then `docker exec lab-control-plane journalctl -u kubelet --no-pager | tail -30` and `kind export logs ./logs --name lab`. A kubelet that restarts or logs `too many open files` points to row 1's causes.
5. Fix the cause, `kind delete cluster --name lab`, recreate.

**Troubleshooting path for NotReady nodes (row 2).** Read it from the cheapest to the most specific:

1. `k get nodes`: which nodes? All of them right after create means "no CNI yet". Only some of them means a node-local problem (the Break-fix lab).
2. `k describe node <n>` or the JSONPath command in 2.8: read the `Ready` condition message. `cni plugin not initialized` -> a CNI problem.
3. `docker exec <n> ls -la /etc/cni/net.d`: empty means no CNI config was ever written (or was removed).
4. `k -n kube-system get ds,pods -o wide`: is `calico-node` scheduled on that node? `DESIRED` 0 or a missing Pod on that node means the DaemonSet is not selecting it.
5. Fix the writer of that directory (the DaemonSet), not the symptom.

**Related but different: row 6 in detail, the Pod range overlaps the Docker network.** This is the mechanism and the fix behind row 6; skip it if `docker network inspect kind` shows a `172.x` subnet. In the first capture the Docker network `kind` was `192.168.147.0/24`, and `podSubnet` was `192.168.0.0/16`, so the node IPs were *inside* the Pod range. Observed symptoms: Pods on control-plane worked; Pods on workers could not reach `10.96.0.1:443` or the control-plane node IP (`wget: download timed out`); metrics-server crash-looped with the `panic` text above; the readiness probe reported `Get "https://192.168.18.3:10250/readyz": context deadline exceeded`. Packets were not traced, so only what was observed is stated: after moving the cluster to `172.29.0.0/16`, all of it worked (metrics-server section above). The likely mechanism is that Calico treats addresses inside its pool as Pod addresses, so traffic to a node IP is not handled as traffic leaving the pool.

Detect it before you debug anything:

```bash
docker network inspect kind --format '{{range .IPAM.Config}}{{.Subnet}} {{end}}'
```

If an IPv4 subnet in the output starts with `192.168.`, you have the clash. Fix by creating the cluster on its own network:

```bash
kind delete cluster --name lab
docker network create --subnet 172.29.0.0/16 kind-lab
export KIND_EXPERIMENTAL_DOCKER_NETWORK=kind-lab     # kind prints: WARNING: Overriding docker network due to KIND_EXPERIMENTAL_DOCKER_NETWORK
"$ENV_DIR/kind-up.sh"
# when you delete the cluster later:  kind delete cluster --name lab && docker network rm kind-lab
```

Keep the variable exported in every shell that creates the cluster. On a machine whose Docker network `kind` is `172.x.x.x` (as is usual with Docker Engine on Linux) there is no clash and you do not need this. Only the OrbStack case could be tested (section 11). The other way out is to change `podSubnet` and set `CALICO_IPV4POOL_CIDR` to match, but then your cluster no longer matches the course config.

```bash
      - { containerPort: 30080, hostPort: 30080, protocol: TCP }
  - role: worker
  - role: worker

diff kind.yaml "$ENV_DIR/kind.yaml"        # differences: the image lines and the comments only
```

</details>

<details><summary>Solution</summary>


### 7.3 Break-fix: nodes NotReady, find out why and repair

**Setup.** The cluster `lab` from the Easy lab, with only Calico (run the Medium cleanup first if needed). Save the fault injector as `~/lab/t209/break.sh` and run it:

```bash
cd ~/lab/t209
cat > break.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
kubectl -n kube-system patch ds calico-node --type=merge \
  -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/os":"windows"}}}}}'
for n in lab-worker lab-worker2; do
  docker exec "$n" sh -c 'rm -f /etc/cni/net.d/*'
done
EOF
chmod +x break.sh && ./break.sh
sleep 30
```

**Task.** Two of the three nodes are `NotReady`. Without recreating the cluster, without editing `kind.yaml`, and without touching the Pods of other namespaces, find the cause and bring all three nodes back to `Ready`. Do not delete the DaemonSet. Afterwards `calico-node` must run on every node and the CNI config must exist on both workers.

<details><summary>Hint 1</summary>

`k get nodes`, then `k describe node lab-worker` and read the `Ready` condition message. What is the runtime missing?

</details>

<details><summary>Hint 2</summary>

The CNI config lives in a directory on each node: `docker exec lab-worker ls -la /etc/cni/net.d`. Which Kubernetes object writes files there? Is it running on those nodes? Check `k -n kube-system get ds,pods -o wide`.

</details>

<details><summary>Hint 3</summary>

Look at the `NODE SELECTOR` column of the DaemonSet and at its `DESIRED` count. A DaemonSet only runs on nodes that match its selector. New Pods of this DaemonSet recreate the config files on start.

</details>

<details><summary>Solution</summary>

```bash
k get nodes
k describe node lab-worker | grep -A8 '^Conditions'
k -n kube-system get ds calico-node
k -n kube-system get ds calico-node -o jsonpath='{.spec.template.spec.nodeSelector}'
docker exec lab-worker ls -la /etc/cni/net.d
```

REAL OUTPUT (kind v0.33.0, v1.37.0), capture cluster names:


Reading it: the Ready message says the CNI is not initialised, so this is a network-plugin problem and not a kubelet problem. (`NetworkUnavailable False / CalicoIsUp` is an old condition set by Calico when it ran; it does not mean the plugin works now.) The directory `/etc/cni/net.d` is empty on the NotReady workers. The control-plane node, which still has its file, stays `Ready`. The object that writes the file is the `calico-node` DaemonSet, and it has `DESIRED 0`: its selector `kubernetes.io/os=windows` matches no node (all nodes are `linux`). Restore the original selector. The new Pods' init containers then rewrite the CNI config:

```bash
k -n kube-system patch ds calico-node --type=merge \
  -p '{"spec":{"template":{"spec":{"nodeSelector":{"kubernetes.io/os":"linux"}}}}}'
k -n kube-system rollout status ds/calico-node --timeout=180s
k wait --for=condition=Ready nodes --all --timeout=120s
docker exec lab-worker ls /etc/cni/net.d
```

```text
calico-kubeconfig
```

Why a merge patch: a merge patch replaces the value of the one key `kubernetes.io/os` and leaves the rest of the DaemonSet alone. Why not just create the files by hand: the DaemonSet would still be selecting no node, so the next restart or a new node would be broken again. Fix the owner, not the symptom.

</details>

## 9. Quick review

1. What command creates a kind cluster named `ckad` from a file `kind.yaml`, and what is the kubectl context called afterwards?
<details><summary>Answer</summary>`kind create cluster --name ckad --config kind.yaml`; the context is `kind-ckad`.</details>

2. Why do the nodes stay `NotReady` after creating a cluster with `disableDefaultCNI: true`, and how do you confirm it?
<details><summary>Answer</summary>No CNI config exists in `/etc/cni/net.d`, so the runtime reports `NetworkReady=false`. Confirm with the Ready condition message (`cni plugin not initialized`) and `docker exec <node> ls /etc/cni/net.d`. Fix: install Calico.</details>

3. Why must `podSubnet` be `192.168.0.0/16` in the course config?
<details><summary>Answer</summary>Calico's manifest has `CALICO_IPV4POOL_CIDR` commented out, so Calico's default pool is `192.168.0.0/16`. The kind Pod range and the Calico pool must agree.</details>

4. How do you pin a kind node image by digest, and why is it better than a tag?
<details><summary>Answer</summary>`image: kindest/node:v1.37.0@sha256:<digest>` in each node entry (or `--image`). A tag can be re-pushed; a digest is immutable.</details>

5. A Pod using `myapp:1` is in `ImagePullBackOff` on kind. Give the command that fixes it and the pull-policy condition under which the fix works.
<details><summary>Answer</summary>`kind load docker-image myapp:1 --name lab`. The kubelet must be allowed to use a local image: a non-`latest` tag with the default `IfNotPresent` (or `Never`). With `Always` or `:latest` it still pulls and fails.</details>

6. Why does the host reach `localhost:30080` on kind, and what limits it?
<details><summary>Answer</summary>`extraPortMappings` publishes port 30080 of the control-plane container on the host; a NodePort Service on 30080 is served on every node by kube-proxy. Only listed ports work, and they are fixed at cluster creation.</details>

7. What is the one extra flag metrics-server needs on kind, and why?
<details><summary>Answer</summary>`--kubelet-insecure-tls`. The kind kubelet serving certificate has no IP SANs, so verification of `https://<node IP>:10250` fails with `x509: cannot validate certificate for ... because it doesn't contain any IP SANs`.</details>

8. `docker network inspect kind` shows `192.168.147.0/24` and your `podSubnet` is `192.168.0.0/16`. What goes wrong and what do you do?
<details><summary>Answer</summary>Node IPs sit inside the Pod range; Pods on workers time out to Service and node addresses (for example `10.96.0.1:443`). Recreate the cluster on a dedicated Docker network outside `192.168.0.0/16` (`docker network create --subnet 172.29.0.0/16 kind-lab`, `KIND_EXPERIMENTAL_DOCKER_NETWORK=kind-lab`).</details>

9. Which Part 4 topics cannot be practised on kind, and why?
<details><summary>Answer</summary>Node-level work: kubeadm install and upgrade, kubelet and runtime troubleshooting on real hosts, certificates and etcd files on disk. The nodes share the host kernel, kubeadm and kubelet are baked into the node image, and there is no package-based upgrade path. Use 3 VMs.</details>

10. Write the minikube command for a 3-node cluster on Kubernetes v1.37.0 using containerd, in profile `mk`, and the command that enables metrics-server.
<details><summary>Answer</summary>`minikube start -p mk --nodes 3 --kubernetes-version=v1.37.0 --container-runtime=containerd`; `minikube -p mk addons enable metrics-server`.</details>

11. What does `env/kind-reset.sh` remove, and what does it leave behind?
<details><summary>Answer</summary>It deletes every namespace named `lab-*`. It leaves cluster-wide objects (ClusterRoles, PVs, CRDs, StorageClasses), node changes (taints, cordons, labels) and anything in `default` or `kube-system`. For those, uninstall add-ons or rebuild.</details>
