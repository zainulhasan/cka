## 1. Why this matters

A Service, a Deployment, a NetworkPolicy and the scheduler never hold a list of Pods. They each hold a **label selector** (a rule such as `app=web`) and re-evaluate it all the time. If the labels on the Pods and the selector in the object differ by one character, nothing errors. The Service just has no endpoints, the NetworkPolicy matches nothing, or a Deployment manages the wrong Pods. In an exam task this is the classic "everything looks fine and nothing works" trap, and it costs minutes you do not have: the Linux Foundation says the exams have 15-20 performance-based tasks in 2 hours (sources: https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad and https://docs.linuxfoundation.org/tc-docs/certification/faq-cka-ckad-cks). Namespaces are the second half of the same trap: most tasks name a namespace, and one forgotten `-n` creates the right object in the wrong place.

### 2.1 Labels

A **label** is a key/value pair of text attached to any API object, in `metadata.labels`. Labels have no meaning to Kubernetes itself. Their only job is to be matched by selectors. The problem they solve: Pods come and go and their names are random (`web-7d9c5b6f4-x8k2p`), so nothing can refer to "the web Pods" by name. Instead you tag Pods with `app: web` and let other objects say "everything tagged `app=web`". Without labels you would have to keep lists of Pod names in sync by hand.

Labels are **not unique**. Many objects can share a label, and one object has many labels. That is the point.

**Syntax.** A label key is `[prefix/]name`.

| Part | Rule |
|---|---|
| name (required) | 63 characters or fewer. Starts and ends with a letter or digit (`[a-zA-Z0-9]`). In the middle: letters, digits, `-`, `_`, `.`. |
| prefix (optional) | A DNS subdomain such as `example.com`, 253 characters or fewer, then a `/`. |
| value | 63 characters or fewer, and it may be empty. If not empty: starts and ends with a letter or digit, with `-`, `_`, `.` allowed in the middle. |
| reserved prefixes | `kubernetes.io/` and `k8s.io/` belong to Kubernetes core components. Do not invent keys under them. |

Source: https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/ . The regular expression for a value in the v1.37.0 source is `(([A-Za-z0-9][-A-Za-z0-9_.]*)?[A-Za-z0-9])?`.

An un-prefixed key (`app`, `tier`) is private to the user. A tool that adds labels to objects it did not create must use a prefix.

Invalid values you will meet in tasks: `my app` (space), `-web` (starts with dash), `web.` (ends with dot), a 64-character string, and an unquoted YAML number or boolean. That last one is common: `version: 1.27` in YAML is a number, and the manifest is rejected (by kubectl or by the API server, depending on where the decoding fails) because a label value must be a string. Write `version: "1.27"`.

EXPECTED OUTPUT (not captured): the error for a bad value. The sentence after `Invalid value` comes from the v1.37.0 source; the rest of the line is shortened.

```text
$ k label pod web 'owner=my team'
The Pod "web" is invalid: metadata.labels: Invalid value: "my team": a valid label must be an empty string or consist of alphanumeric characters, '-', '_' or '.', and must start and end with an alphanumeric character (e.g. 'MyValue', ...)
```

**Recommended labels.** Kubernetes documents a shared set of prefixed labels so that tools (dashboards, Helm, Kustomize) can understand any application. Page: https://kubernetes.io/docs/concepts/overview/working-with-objects/common-labels/ .

| Label | Meaning | Example |
|---|---|---|
| `app.kubernetes.io/name` | Name of the application | `mysql` |
| `app.kubernetes.io/instance` | Unique name of this installation | `mysql-abcxyz` |
| `app.kubernetes.io/version` | Current version | `"5.7.21"` |
| `app.kubernetes.io/component` | Role inside the architecture | `database` |
| `app.kubernetes.io/part-of` | The larger application this belongs to | `wordpress` |
| `app.kubernetes.io/managed-by` | The tool managing it | `Helm` |

In the exam you will usually see plain `app: web`. Real Helm charts use the `app.kubernetes.io/*` keys. When a Service "does not work" with a Helm-installed app, check which of the two styles the Pods really carry (Lab 7.3 uses this).

**Under the hood.** Labels are stored in etcd inside the object, like every other field. The API server also keeps them indexed for `list` and `watch` calls, so a label query is a filter on the server, not on your laptop. Add `-v=6` to a kubectl command and you will see the request: `GET .../pods?labelSelector=env+in+%28dev%2Cqa%29`.

### 2.2 Selectors

A **label selector** is a rule that picks objects by their labels. It is a list of requirements joined by `AND`, written with commas. There is **no OR**: to get "dev or qa" you use one requirement with a set (`env in (dev,qa)`), or you run two queries.

**Equality-based** requirements:

| Form | Meaning |
|---|---|
| `app=web` or `app==web` | the key exists and equals `web` |
| `tier!=db` | the value is not `db`, **or the key is missing** |

**Set-based** requirements:

| Form | Meaning |
|---|---|
| `env in (dev,qa)` | the key exists and its value is `dev` or `qa` |
| `env notin (prod)` | the value is not `prod`, **or the key is missing** |
| `legacy` | the key exists (any value) |
| `!legacy` | the key does not exist |

The two bold parts are the usual source of wrong answers. `tier!=db` and `env notin (prod)` both match objects that have no such label at all. If you want "has a label and it is not prod", write two requirements: `env,env!=prod`.

You can mix both styles: `app=web,env in (dev,qa),!legacy`.

**Real evaluation of these selectors.** kubectl sends the `-l` text to the API server, which parses it with the Go package `k8s.io/apimachinery/pkg/labels`. I ran that exact parser (version v0.37.0, the library of Kubernetes 1.37) against the six Pods of Lab 7.1. This is a small Go program, not a cluster, so it proves which Pods each selector matches, not what `kubectl get` prints. The Pod labels were: p1 `app=web,env=dev,tier=frontend`; p2 `app=web,env=qa,tier=frontend`; p3 `app=web,env=prod,tier=frontend`; p4 `app=api,env=dev,tier=backend`; p5 `app=api,env=prod,tier=backend,legacy=true`; p6 `app=db,tier=db` (no `env`).

```text
REAL OUTPUT (Go, k8s.io/apimachinery v0.37.0 labels.Parse + Matches, no cluster)
-l 'app=web'  ->  [p1 p2 p3]
-l 'app=web,env!=prod'  ->  [p1 p2]
-l 'env in (dev,qa)'  ->  [p1 p2 p4]
-l 'env notin (prod)'  ->  [p1 p2 p4 p6]
-l 'legacy'  ->  [p5]
-l '!legacy'  ->  [p1 p2 p3 p4 p6]
-l 'tier=frontend,env in (dev,qa)'  ->  [p1 p2]
-l 'app in (api,db),!legacy'  ->  [p4 p6]
-l 'env,env!=prod'  ->  [p1 p2 p4]
```

Note `env notin (prod)` returns p6, which has no `env` at all, while `env,env!=prod` (key must exist, then not prod) does not.

**Where each selector style is accepted.** The kubectl `-l` flag takes both. The API objects differ:

| Where | Field | Style |
|---|---|---|
| kubectl | `-l` / `--selector` | equality and set-based text |
| Service | `spec.selector` | **only** a map of `key: value` (equality AND). No `matchExpressions`. |
| Deployment, ReplicaSet, StatefulSet, DaemonSet, Job | `spec.selector` | a `LabelSelector`: `matchLabels` and/or `matchExpressions` |
| NetworkPolicy | `podSelector`, `namespaceSelector` | `LabelSelector` (later lesson) |
| Pod scheduling to nodes | `spec.nodeSelector` | only a map of `key: value` |
| Node affinity | `matchExpressions` | `In`, `NotIn`, `Exists`, `DoesNotExist`, plus `Gt` and `Lt` (later lesson) |

Source for Service versus workload support: https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/ .

**Under the hood: who evaluates a selector.**

1. The **ReplicaSet controller** (inside kube-controller-manager) lists the Pods in the ReplicaSet's namespace that match its selector. It counts the ones it owns and creates or deletes Pods until the count equals `replicas`. A matching Pod that nobody owns is **adopted**: the controller writes an `ownerReference` into it. A Pod whose labels stop matching is **released**, and the controller then creates a replacement. (Source: `pkg/controller/replicaset/replica_set.go`, v1.37.0, the `PodControllerRefManager` adoption logic.)
2. The **EndpointSlice controller** watches Services and Pods. For each Service it lists the ready Pods in the same namespace that match `spec.selector` and writes their IPs into EndpointSlice objects. kube-proxy then programs the node's packet rules from those slices. A Service with a wrong selector therefore gets an empty slice and no error.
3. A Deployment does not manage Pods directly. It creates ReplicaSets and adds one extra label, `pod-template-hash`, to each ReplicaSet's selector and Pod template. That is why two ReplicaSets of the same Deployment (old and new version) do not fight over each other's Pods.

### 2.3 `matchLabels` versus `matchExpressions`

A `LabelSelector` has two optional parts. Everything in both parts is ANDed.

```yaml
selector:
  matchLabels:            # a map; each pair is "key In [value]"
    app: web
  matchExpressions:       # a list of {key, operator, values}
  - key: tier
    operator: In
    values: [frontend, cache]
```

`matchLabels: {app: web}` is exactly `matchExpressions: [{key: app, operator: In, values: [web]}]`. Use `matchLabels` when every requirement is "equals". Use `matchExpressions` for the rest.

| Operator | `values` | Matches | Kubectl text form |
|---|---|---|---|
| `In` | required, non-empty list | key exists and value is in the list | `tier in (a,b)` |
| `NotIn` | required, non-empty list | value not in the list, or key missing | `tier notin (a,b)` |
| `Exists` | must be omitted | key exists | `tier` |
| `DoesNotExist` | must be omitted | key missing | `!tier` |

Risky values: `In` with an empty `values` list is rejected; `Exists` with a `values` list is rejected. The Kubernetes API reference describes these rules at https://kubernetes.io/docs/reference/kubernetes-api/common-definitions/label-selector/ . For `apps/v1` workloads `spec.selector` is a required field, and the controller also requires that the selector **matches the Pod template labels**. If it does not, `apply` fails with:

```text
VERIFIED FROM SOURCE (kubernetes v1.37.0 tag): message text in pkg/apis/apps/validation/validation.go
spec.template.metadata.labels: Invalid value: map[string]string{...}: `selector` does not match template `labels`
```

(The surrounding words `The Deployment "web" is invalid:` are added by kubectl.) So the YAML you must produce has two places that agree: `spec.selector` and `spec.template.metadata.labels`. Section 4.2 shows it.

A second trap: `k expose deploy web` copies a **map** selector from the Deployment. The v1.37.0 source returns the error `invalid deployment: no selectors, therefore cannot be exposed` when the Deployment has no `matchLabels` (for example it uses only `matchExpressions`). In that case write the Service YAML by hand or use `k create svc clusterip web --tcp=80:80` and fix the selector with `k set selector`.

### 2.4 The label commands

| Task | Command |
|---|---|
| Show labels as a column | `k get pods --show-labels` |
| Show chosen label keys as columns | `k get pods -L app,tier` (capital L) |
| Filter by selector | `k get pods -l app=web,tier!=db` (lowercase l) |
| Set-based filter | `k get pods -l 'env in (dev,qa)' -L env` |
| Add or change a label | `k label pod web tier=frontend` |
| Overwrite an existing value | `k label pod web tier=backend --overwrite` |
| Remove a label (key, then a dash) | `k label pod web tier-` |
| Label many objects | `k label pods --all env=dev` or `k label pods -l app=web env=dev` |
| Label a namespace or node | `k label ns dev team=a` / `k label node w1 disktype=ssd` |
| Edit labels in a file's object without sending it | `k label -f pod.yaml tier=x --local -o yaml` |

Rules to remember:

- Without `--overwrite`, changing an existing key fails. The message in the kubectl v0.37.0 source (`pkg/cmd/label/label.go`, the kubectl release that matches Kubernetes 1.37) is `'tier' already has a value (frontend), and --overwrite is false`. The check in `validateNoOverwrites` fires only when the key exists **and the existing value differs** from the new one. Setting the same value again without `--overwrite` is therefore not an error: nothing changes and kubectl prints `not labeled`. A different value always needs `--overwrite`.
- **Quote** any selector that contains spaces, parentheses or `!`: `-l 'env in (dev,qa)'`. Without quotes bash treats `(` as syntax.
- `k label deploy web x=y` labels the **Deployment object**, not its Pods. To change Pod labels you edit `spec.template.metadata.labels` (this triggers a rollout), or you label the Pods one by one.
- `-l` and `-L` are different: `-l` filters rows, `-L` adds columns. They combine: `k get pods -l 'env in (dev,qa)' -L env`.

EXPECTED OUTPUT (not captured): the `--overwrite` failure and its fix. The error text comes from the kubectl v0.37.0 source; kubectl puts `error: ` in front of it.

```text
$ k label pod web tier=backend
error: 'tier' already has a value (frontend), and --overwrite is false

$ k label pod web tier=backend --overwrite
pod/web labeled
```

VERIFIED FROM SOURCE (kubectl v0.37.0, `pkg/cmd/label/label.go`): the result words and the extra line for a missing key. The `pod/web` prefix is the usual object printer; the example is not a cluster run.

```text
pod/web labeled        # at least one key was added or its value changed
pod/web unlabeled      # at least one key was removed with key-
pod/web modified       # keys were added/changed and removed in one command
pod/web not labeled    # nothing changed: same value set again, or a removed key was not there
label "x" not found.   # printed first, on its own line, for each removed key that the object does not have
```

So `k label pod web nosuch-` prints `label "nosuch" not found.` and then `pod/web not labeled`.

### 2.5 Annotations

An **annotation** is also a key/value pair in `metadata.annotations`, but it is **not selectable**. No selector ever reads it. It carries information for humans and tools: build IDs, contact names, ingress controller settings, the reason for a rollout.

| | Labels | Annotations |
|---|---|---|
| Used by selectors | yes | no |
| Value rules | strict (63 chars, restricted characters) | any string |
| Size | tiny | all annotations of one object together must be 256 KiB or less (`TotalAnnotationSizeLimitB` in the v1.37.0 source) |
| Key syntax | `[prefix/]name`, same rules | `[prefix/]name`, same rules |
| Typical content | identity: `app`, `tier`, `env` | metadata: `description`, `owner`, `kubernetes.io/change-cause` |
| Command | `k label` | `k annotate` |

`k annotate` works like `k label`: `k annotate deploy web owner=team-a`, `--overwrite` to change a value, `key-` to remove one, `-l selector` and `--all` to hit many objects.

Annotations you should recognize:

| Annotation | Set by | What it does |
|---|---|---|
| `kubernetes.io/change-cause` | you | Text shown in the `CHANGE-CAUSE` column of `k rollout history`. This is how you record why a revision exists, because the old `--record` flag is deprecated (the kubectl v0.37.0 source still has it, marked deprecated: `--record will be removed in the future`). Use the annotation. |
| `deployment.kubernetes.io/revision` | the Deployment controller | The revision number of a ReplicaSet. Do not edit it. |
| `kubectl.kubernetes.io/last-applied-configuration` | `k apply` (client-side apply) | The last manifest you applied, used for three-way merge. If you copy an object to another namespace, remove it. |

**How change-cause works.** The Deployment controller copies the Deployment's annotations (except a few it owns) onto the ReplicaSet of the newest revision. `k rollout history` reads that annotation from each ReplicaSet. So the usual order is: change the Deployment, then annotate it. The annotation lands on the current revision.

### 2.6 Field selectors

A **field selector** filters objects by the value of a field of the object, not by its labels. It is evaluated by the API server too. Syntax is smaller than label selectors:

- Operators: `=`, `==` (same thing) and `!=`. The set-based forms (`in`, `notin`, bare key) are **not** supported.
- Several requirements are joined with a comma and ANDed: `--field-selector status.phase!=Running,spec.restartPolicy=Always`.
- It works across several types in one command: `k get statefulsets,services -A --field-selector metadata.namespace!=default`.
- It cannot be used to match any field. Each resource type exposes only a short fixed list. An unsupported field gives a `BadRequest` error.

Supported fields. The first table is the official list (https://kubernetes.io/docs/concepts/overview/working-with-objects/field-selectors/). Every resource supports `metadata.name`, and every **namespaced** resource also supports `metadata.namespace`.

| Resource | Extra supported fields (official page) |
|---|---|
| Pod | `spec.nodeName`, `spec.restartPolicy`, `spec.schedulerName`, `spec.serviceAccountName`, `spec.hostNetwork`, `status.phase`, `status.podIP`, `status.podIPs`, `status.nominatedNodeName` |
| Node | `spec.unschedulable` |
| Namespace | `status.phase` |
| Service | `spec.clusterIP`, `spec.type` |
| Secret | `type` |
| Event | `involvedObject.kind`, `.namespace`, `.name`, `.uid`, `.apiVersion`, `.resourceVersion`, `.fieldPath`, `reason`, `reportingComponent`, `source`, `type` |
| ReplicaSet, ReplicationController | `status.replicas` |
| Job | `status.successful` |
| CertificateSigningRequest | `spec.signerName` |
| Deployment, DaemonSet, StatefulSet, ConfigMap, most others | only `metadata.name` and `metadata.namespace` |
| Custom resources | `metadata.name`, `metadata.namespace`, plus fields the CRD lists in `spec.versions[*].selectableFields` |

Two differences to remember: the official page lists `status.podIPs` for Pods but the v1.37.0 Pod code does not register it, so expect `status.podIP` to work and `status.podIPs` to fail (re-check on a live cluster, see section 11). And Node and Namespace objects are cluster-scoped, so only `metadata.name` applies there.

**Useful forms.**

```bash
k get pods -A --field-selector metadata.namespace!=default     # everything outside default
k get pods -A --field-selector spec.nodeName=lab-worker         # Pods on one node
k get pods -A --field-selector spec.nodeName=                   # Pods NOT yet scheduled (empty node name)
k get pods -A --field-selector status.phase!=Running            # failing or finished Pods
k get nodes --field-selector spec.unschedulable=true            # cordoned nodes
k get events -n dev --field-selector type=Warning,involvedObject.name=web
k get svc -A --field-selector spec.type=ClusterIP
k get secrets -A --field-selector type=kubernetes.io/service-account-token
```

`spec.nodeName=` with nothing after the `=` matches Pods whose node name is empty, which means the scheduler has not placed them. That is the fast way to list stuck-Pending Pods across the cluster.

EXPECTED OUTPUT (not captured): an unsupported field. The shape of the message comes from the official field-selector page; for a Deployment the field list after `only` is `"metadata.name", "metadata.namespace"`.

```text
$ k get deploy -n lab-t204 --field-selector spec.replicas=3
Error from server (BadRequest): Unable to find "..." that match label selector "", field selector "spec.replicas=3": "spec.replicas" is not a known field selector: only "metadata.name", "metadata.namespace"
```

### 2.7 Namespaces

A **namespace** is a named scope inside one cluster. Names of namespaced objects must be unique only inside their namespace, so two teams can both have a Deployment called `web`. A namespace is also the unit you attach quotas, RBAC rules and (later) NetworkPolicies to. Without namespaces one cluster could not be shared safely, and every name would have to be globally unique.

A namespace is **not** a security wall by itself. By default Pods in different namespaces can still reach each other over the network.

**Initial namespaces** (https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/):

| Namespace | Purpose |
|---|---|
| `default` | Where objects go when you give no namespace. Fine for tests, not for real work. |
| `kube-system` | Objects created by Kubernetes itself: CoreDNS, kube-proxy, the control plane Pods on kubeadm clusters. |
| `kube-public` | Readable by everyone, including unauthenticated clients. By convention it holds public cluster information (for example the `cluster-info` ConfigMap on kubeadm clusters). |
| `kube-node-lease` | One Lease object per node. The kubelet renews it as a heartbeat. |

kind adds a fifth namespace, `local-path-storage`, for its storage provisioner. It is not part of Kubernetes.

**Naming.** A namespace name must be an RFC 1123 DNS label: lowercase letters, digits and `-`, 63 characters or fewer, starting and ending with a letter or digit. Avoid the `kube-` prefix, which is reserved for system namespaces. The control plane puts the immutable label `kubernetes.io/metadata.name=<name>` on every namespace, so you can select a namespace by name with a label selector (NetworkPolicy uses this later).

**Namespaced versus cluster-scoped.** Pods, Services, Deployments, ConfigMaps, Secrets, PVCs, Roles and ServiceAccounts live in a namespace. Nodes, PersistentVolumes, StorageClasses, Namespaces and ClusterRoles do not. `-n` has no effect on a cluster-scoped object. List them with `k api-resources --namespaced=false` (and `=true`).

**Creating and using namespaces.**

```bash
k create ns dev                              # imperative
k create ns dev $do                          # see the YAML (kind: Namespace)
k get ns                                      # list
k get pods -n dev                             # one namespace
k get pods -A                                 # all namespaces (-A = --all-namespaces)
k config set-context --current --namespace=dev   # make dev the default for this context
k config view --minify | grep namespace:          # check which namespace is the default now
```

The namespace comes from, in order: the `-n` flag; the `metadata.namespace` in a manifest you apply (it must equal `-n` if both are given, otherwise kubectl refuses: `the namespace from the provided object does not match the namespace "x". You must pass '--namespace=y' to perform this operation.`); the namespace stored in the current context; and finally `default`. After `set-context --current --namespace=dev`, every later command silently targets `dev`. Reset it when a task is done (see [T2.02](../part2-basics/T2.02-kubectl-fluency-and-productivity.md) for contexts).

**`k get all` is not "all".** `all` is a category that holds only a fixed set of common types (Pods, Services, Deployments, ReplicaSets, StatefulSets, DaemonSets, Jobs, CronJobs, HorizontalPodAutoscalers). It does **not** include ConfigMaps, Secrets, PVCs, Ingresses, ServiceAccounts, Roles or NetworkPolicies. To list every namespaced type that exists in a namespace:

```bash
for r in $(k api-resources --verbs=list --namespaced -o name); do k get "$r" -n dev -o name --ignore-not-found; done
```

(`-o name` prints `type/name` and nothing when empty.)

### 2.8 Namespace-scoped DNS names (preview)

Every Service gets a DNS name from cluster DNS (CoreDNS):

```text
<service>.<namespace>.svc.cluster.local        # fully qualified name
<service>.<namespace>                           # short cross-namespace form
<service>                                       # works only inside the SAME namespace
```

Why the short forms work: kubelet writes a `/etc/resolv.conf` into every Pod with a search list that starts with the Pod's own namespace, and `ndots:5`. For a Pod in namespace `dev` it reads (shape, values vary by cluster):

```text
search dev.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5
```

`wget web` becomes a lookup of `web.dev.svc.cluster.local` first, so it finds `dev/web`. From another namespace the same short name resolves to nothing, and you must write `web.dev` (or the full name). The namespace documentation states the same rule: a bare service name resolves inside the Pod's own namespace, and cross-namespace access needs the fully qualified form. Services, ports and traffic are taught in the Services lessons later in the guide.

Related risk: the namespace page warns that a namespace named like a public top-level domain (for example `com`) can shadow real DNS names. Do not create such names.

### 2.9 Deleting a namespace, Terminating and finalizers

`k delete ns dev` deletes **everything inside it**: Pods, Deployments, Services, ConfigMaps, Secrets, PVCs and all other namespaced objects. There is no confirmation and no undo. PersistentVolumes are cluster-scoped, so they stay unless a PVC with a `Delete` reclaim policy removes them. (Official task page: https://kubernetes.io/docs/tasks/administer-cluster/namespaces/ .)

Deletion is **asynchronous**. The namespace moves to phase `Terminating`, new objects cannot be created in it, and the namespace controller deletes the content.

**Ordered namespace deletion (GA in v1.34).** The namespace controller deletes all Pods first and waits until they are gone. Only then does it delete the other objects. Why it exists: with a random order a NetworkPolicy or a similar object could disappear while Pods were still running, leaving them briefly unprotected. History from the v1.33.0 and v1.34.0 source: feature gate `OrderedNamespaceDeletion` was Beta but off by default from 1.30, became on by default in 1.33, and went GA (locked on) in 1.34. In the v1.37.0 source the gate no longer exists and the pods-first logic is unconditional (`pkg/controller/namespace/deletion/namespaced_resources_deleter.go`, comment "Ensure all pods in the namespace are deleted first"). This is described here from source; the official documentation pages I fetched do not mention it.

**Finalizers.** A **finalizer** is a string in `metadata.finalizers` of an object. It means "someone must do cleanup before this object may disappear". When you delete an object that has finalizers, the API server only sets `metadata.deletionTimestamp`. The object stays visible until the owner of each finalizer finishes its cleanup and removes its own string. Normal examples: `kubernetes.io/pvc-protection` on a PVC that a Pod still uses; finalizers added by operators for external resources (cloud load balancers, databases).

The Namespace object also has its own finalizer, `spec.finalizers: [kubernetes]`, which the namespace controller removes when the content is gone.

**Why a namespace sticks in `Terminating`.** The controller cannot finish while at least one of these holds:

| Cause | Where you see it |
|---|---|
| An object inside the namespace has a finalizer that nobody removes (the controller that owns it is gone or broken) | condition `NamespaceFinalizersRemaining` |
| Objects are still being deleted (a Pod with a long grace period, a stuck volume) | condition `NamespaceContentRemaining` |
| An API group cannot be reached (for example an aggregated API such as metrics-server is down), so the controller cannot even list what to delete | condition `NamespaceDeletionDiscoveryFailure` |

The condition texts in the v1.37.0 source are:

```text
VERIFIED FROM SOURCE (kubernetes v1.37.0 tag): pkg/controller/namespace/deletion/status_condition_utils.go
NamespaceContentRemaining    reason SomeResourcesRemain   message "Some resources are remaining: <resource>.<group> has <N> resource instances"
NamespaceFinalizersRemaining reason SomeFinalizersRemain  message "Some content in the namespace has finalizers remaining: <finalizer> in <N> resource instances"
NamespaceDeletionDiscoveryFailure reason DiscoveryFailed
```

**The repeatable path when a namespace is stuck** (never start by stripping finalizers):

1. `k get ns <ns> -o jsonpath='{range .status.conditions[*]}{.type}{"\t"}{.status}{"\t"}{.message}{"\n"}{end}'`. Read the two messages. They name what remains and which finalizer holds it.
2. Find the objects: the `api-resources` loop from section 2.7, with `-n <ns>`.
3. `k get <type>/<name> -n <ns> -o jsonpath='{.metadata.deletionTimestamp}{"\n"}{.metadata.finalizers}'`. A set `deletionTimestamp` plus a finalizer list means "deleted, waiting for cleanup".
4. Ask who owns the finalizer. Is its controller or operator still installed (`k get pods -A`, `k get crd`)? If the controller is down, bring it back so it can clean up. If the discovery condition appears, fix the unavailable API (`k get apiservices` shows `False` entries).
5. Only when the owner is truly gone and the external resource is not a concern, remove the finalizer from that **one object**: `k patch <type> <name> -n <ns> --type=merge -p '{"metadata":{"finalizers":null}}'`. Removing a finalizer skips the cleanup it stood for, so an external resource (a cloud disk, a load balancer) can be left behind.

There is also a last-resort trick of editing the namespace through its `/finalize` subresource. It forces the namespace away while leaving orphaned objects in etcd. Do not use it in a task.

### 2.10 Selector immutability

`spec.selector` of an `apps/v1` Deployment, ReplicaSet, StatefulSet or DaemonSet cannot be changed after creation. The update validation (`ValidateImmutableField` on `spec.selector`, v1.37.0 source) rejects it with `field is immutable`. Why: the selector decides which Pods a ReplicaSet owns. Changing it in place would orphan existing Pods and could make two ReplicaSets claim the same Pods.

What you can and cannot change:

| Field | Mutable? | What happens |
|---|---|---|
| Deployment `spec.selector` | no | `field is immutable`. Delete and recreate. |
| Deployment `spec.template.metadata.labels` | yes | A new ReplicaSet and a rolling update. The labels must still satisfy `spec.selector`. |
| Service `spec.selector` | yes | Takes effect at once, endpoints are recomputed. `k set selector svc NAME key=value` replaces the whole selector. |
| Labels on a running Pod | yes | Can attach or detach the Pod from a Service or ReplicaSet right now. |

If you must change a Deployment selector: delete the Deployment and apply the new one (Pods are deleted too, so there is a gap), or run a new Deployment under a **new name** with the new selector and then switch the Service selector to it. The second way has no gap.

### 2.11 Node labels (preview for scheduling)

Nodes are objects too and carry labels. The kubelet sets some automatically; clouds and tools add more.

| Label | Meaning |
|---|---|
| `kubernetes.io/hostname` | the node's host name (value equals the node name in most setups, not guaranteed) |
| `kubernetes.io/os`, `kubernetes.io/arch` | `linux`, `amd64` or `arm64` |
| `topology.kubernetes.io/zone`, `topology.kubernetes.io/region` | the failure domain; set by cloud providers or by you on bare metal |
| `node-role.kubernetes.io/control-plane` | present on control plane nodes in kubeadm and kind clusters (empty value) |

Show them with `k get nodes --show-labels` or pick columns: `k get nodes -L kubernetes.io/hostname,topology.kubernetes.io/zone`. A Pod chooses nodes with `spec.nodeSelector`, a map that must equal node labels:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: on-ssd
  namespace: lab-t204
spec:
  nodeSelector:
    disktype: ssd          # node must carry label disktype=ssd, otherwise the Pod stays Pending
  containers:
  - name: c
    image: busybox:1.36
    command: ["sleep", "3600"]
```

`k label node <name> disktype=ssd` adds the label. The scheduler lessons later cover affinity, taints and topology spread. A zone label is not set on kind nodes by default (to verify, section 11); on a cloud it is.

### 2.12 Related but different

- **Name vs label.** A name is unique per type and namespace and addresses one object. A label addresses a group.
- **Label vs annotation.** If a selector must find it, it is a label. If only a human or tool reads it, it is an annotation.
- **Label selector vs field selector.** Labels are free-form tags you control. Fields are properties of the object that you cannot add.
- **`ownerReferences` vs labels.** Ownership (who deletes what, via garbage collection) is set by `metadata.ownerReferences`. A label match alone does not make a Pod owned, but a matching, unowned Pod can be adopted (2.2).
- **`nodeSelector` vs `selector`.** `nodeSelector` picks nodes for a Pod and is a plain map. `selector` picks Pods for a controller or Service.
- **Namespace vs label.** A namespace is a hard scope for names and access rules. A label is a soft tag. `env=dev` does not isolate anything.

## 3. How it works (diagram)

```text
 Namespace lab-t204

  Service "web"                               Deployment "web"  (creates ReplicaSet web-<hash>)
  spec.selector:                              spec.selector.matchExpressions:
    app: web                                    app  In [web]
    tier: frontend                              tier In [frontend]
        |                                       spec.template.metadata.labels: app=web, tier=frontend
        |  EndpointSlice controller                 |
        |  lists matching READY Pods                |  ReplicaSet controller lists matching Pods,
        v                                           v  adopts unowned ones, keeps replicas=3
  +-----------------+  +-----------------+  +-----------------+       +--------------------+
  | Pod web-...-a   |  | Pod web-...-b   |  | Pod web-...-c   |       | Pod web-stray      |
  | app=web         |  | app=web         |  | app=web         |       | app=web            |
  | tier=frontend   |  | tier=frontend   |  | tier=frontend   |       | tier=debug         |
  | pod-template-   |  | pod-template-   |  | pod-template-   |       |                    |
  |   hash=7d9c...  |  |   hash=7d9c...  |  |   hash=7d9c...  |       | no match on tier:  |
  | IN endpoints    |  | IN endpoints    |  | IN endpoints    |       | NOT in endpoints,  |
  | OWNED by RS     |  | OWNED by RS     |  | OWNED by RS     |       | NOT owned by RS    |
  +-----------------+  +-----------------+  +-----------------+       +--------------------+
```

Walkthrough:

1. The three Pods come from the Deployment's Pod template, so they carry `app=web` and `tier=frontend`, plus the `pod-template-hash` label added by the Deployment controller.
2. The ReplicaSet selector (`app In [web]` AND `tier In [frontend]`) matches those three Pods and no others. It owns them and keeps the count at 3.
3. The Service selector (`app=web`, `tier=frontend`) matches the same three Pods, so their IPs appear in the Service's EndpointSlice.
4. `web-stray` has `app=web` but `tier=debug`. Both selectors need `tier=frontend`, so neither the Service nor the ReplicaSet touches it. If it had `tier=frontend` it would join the Service at once (once Ready) and the ReplicaSet would adopt it and delete one Pod to get back to 3.
5. Removing the `tier` label from one of the three Pods does the opposite: it leaves the Service and the ReplicaSet (a replacement Pod is created). That is the standard way to pull one Pod out for debugging.

### 4.2 Deployment and Service whose selectors match (YAML)

Save this as `~/lab/t204/web.yaml`. It applies cleanly with `kubectl apply -f web.yaml` after `k create ns lab-t204`.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: lab-t204               # where the object lives; must match -n if you pass it
  labels:                           # labels of the Deployment object itself, NOT of its Pods
    app.kubernetes.io/name: web
    app.kubernetes.io/part-of: shop
    app.kubernetes.io/version: "1.27"   # quoted: an unquoted 1.27 is a number and is rejected
  annotations:
    kubernetes.io/change-cause: "v1 initial deploy"   # shown by `k rollout history`
spec:
  replicas: 3                       # default 1
  selector:                         # which Pods this Deployment owns; IMMUTABLE after creation
    matchExpressions:               # list of requirements, all ANDed
    - key: app
      operator: In                  # In, NotIn, Exists, DoesNotExist
      values: [web]                 # required for In/NotIn, must be omitted for Exists/DoesNotExist
    - key: tier
      operator: In
      values: [frontend]
  template:                         # the Pod blueprint
    metadata:
      labels:                       # MUST satisfy spec.selector or the API server rejects the manifest
        app: web
        tier: frontend
    spec:
      containers:
      - name: web
        image: nginx:1.27           # pinned tag, never :latest
        ports:
        - containerPort: 80         # documentation only; does not open or close anything
---
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: lab-t204
spec:
  selector:                         # equality map only; ANDed; empty map would select nothing useful
    app: web
    tier: frontend
  ports:
  - port: 80                        # Service port
    targetPort: 80                  # container port (default: same as port)
```

The same Deployment with `matchLabels` is shorter and is what `k create deploy` generates:

```bash
k create deploy web --image=nginx:1.27 --replicas=3 $do > web-simple.yaml
# generated selector:  matchLabels: {app: web}     template labels: {app: web}
```

Field notes and risky values:

- `spec.selector` omitted: rejected, it is required in `apps/v1`.
- `spec.selector` not satisfied by `template.metadata.labels`: rejected with `` `selector` does not match template `labels` ``.
- Selector too broad (for example only `tier: frontend`): the Deployment may adopt unrelated Pods that carry the same label in the same namespace. Use at least the app key.
- `version: 1.27` (unquoted) as a label value: rejected, a number is not a string.
- Service `selector` empty or missing: the Service has no selector and the EndpointSlice controller does nothing for it (used on purpose for hand-made endpoints, a mistake otherwise).

## 6. Common mistakes and how to fix them

The table gives the quick map. The three entry failures are explained step by step below it.

| Symptom | What you will see (exact error/event text) | Cause | Fix (command) |
|---|---|---|---|
| Service has no endpoints | `k get endpointslices -l kubernetes.io/service-name=web` shows `ENDPOINTS <unset>`; `k describe svc web` shows `Endpoints: <none>` (no error anywhere) | `spec.selector` differs from Pod labels (typo, wrong key, wrong value, Pods not Ready, or Pods in another namespace) | Compare `k get svc web -o wide` with `k get pods --show-labels`; then `k set selector svc web app=web,tier=frontend` or fix the Pod template |
| Changing a Deployment selector | `The Deployment "web" is invalid: spec.selector: Invalid value: v1.LabelSelector{...}: field is immutable` | `spec.selector` of apps/v1 workloads cannot change | `k delete deploy web` then apply the new manifest, or create a new Deployment and switch the Service selector |
| Namespace stuck Terminating | `k get ns` shows `Terminating`; conditions `NamespaceFinalizersRemaining` / `NamespaceContentRemaining` | an object inside has a finalizer nobody removes, or an API group is unreachable | Read conditions, list the remaining objects, resolve the owner; patch `finalizers` to `null` on that one object only as a last step |
| Label change refused | `'tier' already has a value (frontend), and --overwrite is false` | changing an existing label without `--overwrite` | `k label pod web tier=backend --overwrite` |
| Selector does not match template | `` `selector` does not match template `labels` `` | `spec.selector` and `spec.template.metadata.labels` disagree | make the template labels satisfy the selector |
| `k expose` refuses a Deployment | `invalid deployment: no selectors, therefore cannot be exposed` (v1.37.0 source text) | the Deployment selector has only `matchExpressions` | write the Service YAML, or `k create svc clusterip` then `k set selector` |
| Object created in the wrong namespace | `Error from server (NotFound): ... "x" not found` on a later command, or the object is in `default` | forgot `-n`, or the context has another default namespace | `k config view --minify \| grep namespace:`; `k get <type> -A \| grep <name>`; recreate with `-n` and delete the wrong one |
| `-l` returns everything | no filter applied | `-l` missing quotes, so the shell split it, or `-L` (columns) was used instead of `-l` | quote the selector; check the capital letter |

### Reasoning on the three failures from the entry

**1. Service has no endpoints (selector and label mismatch).** Nothing fails when you create such a Service, so the symptom is only seen when traffic fails (`wget: download timed out` or connection refused, depending on what answers). Diagnostic order:

1. `k get svc web -o wide`. Read the `SELECTOR` column. Write it down exactly: `app=web,tier=frontend`.
2. `k get pods --show-labels` in the same namespace (check `-n`). Do any Pods carry **all** the selector pairs? Look for the near misses: `tier=front-end`, `App=web`, `app=web ` with a trailing space, key `app.kubernetes.io/name` instead of `app`.
3. `k get endpointslices -l kubernetes.io/service-name=web`. `<unset>` confirms zero matches. If the endpoints exist but marked not ready, the selector is right and the problem is readiness: `k describe pod` shows the failing probe.
4. Same namespace? A Service only selects Pods in its own namespace. `k get pods -A --show-labels | grep web` finds Pods elsewhere.
5. Fix the side that is cheaper to change. Service selector is mutable: `k set selector svc web app=web,tier=frontend`. Pod labels come from the template: `k patch deploy web --type=merge -p '{"spec":{"template":{"metadata":{"labels":{"tier":"frontend"}}}}}'` (this rolls the Pods).
6. Re-check step 3. Verify with a request, for example `k run t --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- -T2 web`.

**2. `field is immutable` when changing a Deployment selector.** The apply reaches the server and is rejected, so nothing changes in the cluster. Read the field name in the message (`spec.selector`). Decide: do you really need a new selector? Often you only wanted to change Pod labels, which is allowed through the template as long as the selector still matches. If the selector must change, recreate (section 2.10). Before deleting, save the old object with `k get deploy web -o yaml > backup.yaml` in case you need the replica count or other settings.

**3. Namespace stuck Terminating.** Follow the six-step path in section 2.9: read the conditions, list what remains, read `deletionTimestamp` and `finalizers` on the remaining object, find the owner, bring the owner back, and only then remove that object's finalizer. Do not run a command that strips finalizers from everything or force the namespace through `/finalize`: it can leave cloud resources (volumes, load balancers) behind and orphan objects in etcd.

```bash
        - containerPort: 80

```

**Task.** The Deployment `shop` and the Service `shop` in namespace `lab-t204-src` must move to namespace `lab-t204-dst`. Assume `shop-src.yaml` is lost: work from the live objects. In `lab-t204-dst` the Deployment and Service must keep the same names, the same labels on the Deployment, on its Pods and in both selectors, and the annotation `owner=team-a`. The Service in `lab-t204-dst` must have two ready endpoints. Afterwards `lab-t204-src` must contain no Deployment and no Service. Write the names of the Pods in `lab-t204-dst` that carry `app=shop,tier=web,version=v1` (format `-o name`) to `~/lab/t204/moved.txt`.

<details>
<summary>Hints</summary>

1. An object cannot change namespace. You must create a copy in the new namespace and delete the original. `k get deploy/shop svc/shop -n lab-t204-src -o yaml` exports both (the `type/name` form works for several types).
2. The export contains fields that must not be copied: `metadata.namespace`, `uid`, `resourceVersion`, `creationTimestamp`, `generation`, `managedFields`, `status`, and the Service's `spec.clusterIP` and `spec.clusterIPs` (the old Service still owns that IP). `yq 'del(...)'` removes them.
3. Create the new objects first, check the endpoints, and delete the old ones last. A Service selects Pods only in its own namespace, so the old Service has no use after the Pods move.

</details>

<details>
<summary>Solution</summary>

```bash
cd ~/lab/t204
# 1. export the live objects (a List with both items)
k -n lab-t204-src get deploy/shop svc/shop -o yaml > old.yaml

# 2. strip the cluster-owned fields (yq v4 syntax); the namespace is dropped so that -n decides it
yq 'del(.items[].metadata.namespace, .items[].metadata.uid, .items[].metadata.resourceVersion,
        .items[].metadata.creationTimestamp, .items[].metadata.generation, .items[].metadata.managedFields,
        .items[].metadata.annotations."deployment.kubernetes.io/revision",
        .items[].status, .items[].spec.clusterIP, .items[].spec.clusterIPs)' old.yaml > new.yaml

# 3. create in the new namespace; labels and selectors are copied unchanged
k -n lab-t204-dst create -f new.yaml
k -n lab-t204-dst rollout status deploy/shop

# 4. prove the Service selects the moved Pods
k -n lab-t204-dst get svc shop -o wide
k -n lab-t204-dst get pods --show-labels
k -n lab-t204-dst get endpointslices -l kubernetes.io/service-name=shop

# 5. record the Pod names, then remove the originals
k -n lab-t204-dst get pods -l app=shop,tier=web,version=v1 -o name > moved.txt
k -n lab-t204-src delete deploy/shop svc/shop
```

Why each step: the namespace must be deleted from the export because kubectl refuses `metadata.namespace` that differs from `-n`. `uid` and `resourceVersion` belong to the old object and make `create` fail. `clusterIP` is still allocated to the old Service (`provided IP is already allocated`). The Pod template labels travel inside `spec.template`, so the new Pods get the same labels with no extra work, which is why the new Service selector matches at once. If you had forgotten to move the Service and kept it in `lab-t204-src`, it would have an empty endpoint list, because it can only see Pods of its own namespace. The cluster DNS name of the app changes from `shop.lab-t204-src` to `shop.lab-t204-dst`, so any client using the old name needs updating.

The export was made with `get -o yaml`; if the objects had been created with `k apply` there would also be a `kubectl.kubernetes.io/last-applied-configuration` annotation that still names the old namespace. Add `.items[].metadata.annotations."kubectl.kubernetes.io/last-applied-configuration"` to the `del(...)` list in that case.

</details>

**Verify.**

<details>
<summary>Hints</summary>

1. For each Service, run the comparison from section 6: `k -n lab-t204-fix get svc -o wide` next to `k -n lab-t204-fix get pods --show-labels`, and `k get endpointslices -A -l kubernetes.io/service-name`.

</details>

<details>
<summary>Solution</summary>

Diagnosis, in the order of the ladder from section 6:

```bash
k -n lab-t204-fix get svc -o wide
k -n lab-t204-fix get pods --show-labels
k get endpointslices -A -l 'kubernetes.io/service-name in (shop,api,cart)'
```

What you see and why:

- `shop`: the Service wants `tier=web` but the Pods carry `tier=wbe` (letters swapped). Fix the Pod template, because the labels there are mutable and the Service selector is the correct side. The Deployment selector only has `app: shop`, so it is untouched.
- `api`: the Service selects `app=api` but the Pods use the recommended label `app.kubernetes.io/name=api`. The key differs. Fix the Service selector. (Adding `app: api` to the Pod template labels would also give two endpoints, because the Deployment selector only needs `app.kubernetes.io/name`; the Service-side fix is the smaller change.)
- `cart`: the Service exists in the wrong namespace (`lab-t204-fix-b`), where there are no Pods. A Service only selects Pods of its own namespace.

```bash
# shop: fix the label in the template (rolling update, new Pods get tier=web)

k -n lab-t204-fix rollout status deploy/shop

# api: replace the Service selector
k -n lab-t204-fix set selector svc api app.kubernetes.io/name=api

# cart: remove the stray Service and expose the Deployment in the right namespace
k -n lab-t204-fix-b delete svc cart
k -n lab-t204-fix expose deploy cart --port=80

# record the result
k -n lab-t204-fix get svc --no-headers -o custom-columns=NAME:.metadata.name,SELECTOR:.spec.selector > ~/lab/t204/fixed.txt
```

`expose` works for `cart` because that Deployment uses `matchLabels`; it copies `app=cart` and uses port 80 for both the Service port and target port. The merge patch only touches the `tier` key of the template labels; `app` stays.

</details>

**Verify.**

```bash
  n=$(kubectl -n lab-t204-fix get endpointslices -l kubernetes.io/service-name=$s \
    -o jsonpath='{range .items[*].endpoints[?(@.conditions.ready==true)]}{.addresses[0]}{"\n"}{end}' | grep -c .)
  test "$n" = 2 && echo "PASS $s" || echo "FAIL $s ($n ready endpoints)"
done
kubectl -n lab-t204-fix-b get svc cart >/dev/null 2>&1 && echo "FAIL cart still in lab-t204-fix-b" || echo "PASS cart removed from -b"
f=~/lab/t204/fixed.txt
{ grep '^shop ' "$f" | grep -q 'app:shop.*tier:web' && grep '^cart ' "$f" | grep -q 'app:cart' \
  && grep '^api ' "$f" | grep -qv '<none>'; } 2>/dev/null && echo PASS-fixed-file || echo FAIL-fixed-file
for d in shop api cart; do test "$(kubectl -n lab-t204-fix get deploy $d -o jsonpath='{.spec.replicas}')" = 2 || echo "FAIL replicas $d"; done
```

Expected: `PASS shop`, `PASS api`, `PASS cart`, `PASS cart removed from -b`, `PASS-fixed-file` and no `FAIL` lines. Right after `break.sh` every endpoint check fails. If a check shows fewer than two for `shop`, wait for the rollout to finish and retry. The fixed-file check assumes the custom-columns output prints each selector as a Go map such as `map[app:shop tier:web]` on a line that starts with the Service name; if your output looks different, inspect the file with your eyes instead (section 11). It checks the `shop` and `cart` selectors exactly as the task states them and only that `api` has a selector; the endpoint checks decide whether the `api` fix works.

- Always state the namespace: `-n NAME` on every command, or set it once with `k config set-context --current --namespace=NAME` and reset it afterwards. Before moving to the next task run `k config view --minify | grep namespace:`.
- Quote every selector with spaces, parentheses or `!`: `-l 'env in (dev,qa)'`. Use `-l` to filter and `-L` to show columns.
- Do not retype a Deployment selector: `k create deploy NAME --image=IMG $do > d.yaml` writes selector and template labels that already match. Edit the YAML, never the live selector.

- Before deleting a namespace, read what is in it. Deleting is immediate and complete; there is no undo.

## 9. Quick review

1. Which command removes the label `tier` from Pod `web`, and why is the dash needed?
2. A Pod has no `env` label. Does `-l 'env notin (prod)'` select it? Does `-l env!=prod`?
3. Write the selector text for "key `legacy` is absent" and for "app is api or db".
4. What is the difference between `-l` and `-L`?
5. Why does `kubectl apply` reject a Deployment whose `spec.selector` is `app: web` but whose template labels are `app: webapp`?
6. Which of these cannot be changed on a live Deployment: the template labels, the selector, the replicas? What do you do if you need a different selector?
7. Which selector styles can a Service use, and which can a Deployment use?
8. How do you list all Pods in the cluster that are not scheduled yet? Name the flag and the field.
9. A namespace is stuck in `Terminating`. List your first three commands and what you look for.
10. From a Pod in namespace `a`, what name do you use to reach Service `db` in namespace `b`? Why does plain `db` fail?

<details>
<summary>Answers</summary>

1. `k label pod web tier-`. The key followed by `-` means "remove". Without the dash kubectl treats `tier` as a label to set and reports an error.
2. Yes to both. `notin` and `!=` match objects that lack the key. To require the key and exclude `prod`, use `-l 'env,env!=prod'`.
3. `!legacy` and `app in (api,db)`.
4. `-l` filters the rows by a label selector. `-L` adds a column per label key (and does not filter).
5. The API server checks that the selector matches the Pod template. Here `app=web` does not equal `app=webapp`, so the manifest is rejected with `` `selector` does not match template `labels` ``.
6. The selector. Replicas and template labels can be changed. For a new selector: delete and recreate, or run a new Deployment under another name and switch the Service selector.
7. A Service: only a plain map (equality, ANDed). A Deployment: `matchLabels` and/or `matchExpressions` with `In`, `NotIn`, `Exists`, `DoesNotExist`.
8. `k get pods -A --field-selector spec.nodeName=` (empty value).
9. `k get ns NAME -o jsonpath='{.status.conditions}'` for the remaining content and finalizer messages; the `api-resources` loop to find the remaining objects; `k get <obj> -o jsonpath='{.metadata.deletionTimestamp}{.metadata.finalizers}'` to see the finalizer and then find its owner. Strip a finalizer only after that.
10. `db.b` (or `db.b.svc.cluster.local`). The Pod's search path starts with its own namespace `a`, so plain `db` looks for `db.a.svc.cluster.local`.

</details>
