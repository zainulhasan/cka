## 1. Why this matters

Many tasks in the CKA and CKAD exams need you to edit text on a Linux command line: a manifest from `$do`, a Deployment through `kubectl edit`, a config file on a node. The Linux Foundation describes the exams as "15-20 performance-based tasks" solved on the command line in 2 hours (sources: [tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad), [FAQ](https://docs.linuxfoundation.org/tc-docs/certification/faq-cka-ckad-cks)). That is about 6 minutes per task, so a minute lost to a stuck editor is a sixth of a task.

YAML makes this worse than ordinary text. Indentation is the syntax. One tab character, or one pasted line that moved three spaces to the right, and the file is either rejected or, worse, accepted with the field in the wrong place. In real life the same mistakes cause `kubectl edit` sessions that end in an error you did not read, with your changes thrown into a temporary file you did not know existed.

If you do not learn a small set of Vim keys and three lines of `~/.vimrc`, you will still finish tasks, but you will retype instead of repeat, fix indentation by hand, and lose time on avoidable errors.

## 2. Concepts

### 2.1 What `kubectl edit` really does (and why the editor matters)

`kubectl edit` does not edit the object on the server. It edits a **copy**. The steps below were read from the `kubectl` source for v1.37.1 (`staging/src/k8s.io/kubectl/pkg/cmd/util/editor/`) and section 5 walks through the flow (its cluster outputs are expected, not captured; see section 11).

1. `kubectl` does a GET of the object and renders it as YAML (without `managedFields`, unless you pass `--show-managed-fields`).
2. It writes the YAML to a temporary file named `kubectl-edit-<random digits>.yaml` in the system temporary directory. That directory is `$TMPDIR` if set, otherwise `/tmp`. On a Linux VM it is `/tmp`; on macOS `$TMPDIR` is set to a long `/var/folders/...` path, so look at the path printed in the message instead of guessing. The file starts with a comment block (`# Please edit the object below...`).
3. It starts your editor on that file and waits. The editor is the first non-empty variable among `KUBE_EDITOR`, then `EDITOR`. If neither is set it uses `vi`. `VISUAL` is **not** read. If the value contains spaces but no quotes, `kubectl` splits it on spaces (`KUBE_EDITOR="vim -u ~/.vimrc"` works); if it contains quotes, the shell parses it.
4. When the editor exits, `kubectl` removes the `#` comment lines and validates the result against the API schema. If the YAML does not parse or has an unknown field, the file is **reopened in the editor** with the error written at the top as comments.
5. If nothing changed it prints `Edit cancelled, no changes made.` and deletes the temp file. If the file is empty it prints `Edit cancelled, saved file was empty.`
6. Otherwise it sends a patch to the API server. The server can still reject it (for example an immutable field, or an admission rule). Again the file is reopened with the reason at the top.
7. If you leave a reopened file unchanged, `kubectl` gives up: `Edit cancelled, no valid changes were saved.` and prints `A copy of your changes has been stored to "/tmp/kubectl-edit-<digits>.yaml"`. That file is the only copy of your work.

Why this matters for you: the speed of `kubectl edit` is the speed of your editor, and the failures all leave a file in `/tmp` that you can reuse.

| Variable | Read by `kubectl edit`? | Notes |
|---|---|---|
| `KUBE_EDITOR` | Yes, first | Use this to override only for `kubectl`. |
| `EDITOR` | Yes, second | Also read by `git`, `crontab -e` and many other tools. |
| `VISUAL` | No | Do not rely on it for `kubectl`. |
| none set | Falls back to `vi` | On Ubuntu with the `vim` package, `vi` is `vim.basic` (REAL OUTPUT (Docker): `readlink -f $(which vi)` printed `/usr/bin/vim.basic`). On a minimal install `vi` may be `vim.tiny`, a reduced build; see 2.7. |

**Related but different.** `kubectl edit` (interactive GET, edit, PATCH), `kubectl apply -f file` (declarative, from a file you keep), `kubectl replace -f` (full overwrite), `kubectl patch` (one change from the command line, no editor) and `kubectl set env` / `kubectl set image` (imperative, no editor at all). When a single field changes, an imperative command beats any editor; use the editor when the change is a block (section 4 shows both).

### 2.2 Vim is modal: four modes you must know

**What it is.** Vim ("Vi IMproved") is a text editor in which the same key does different things depending on the **mode**. **Problem it solves:** your hands never leave the home row, and a key like `dd` can mean "delete this line" without a mouse or a menu. **What breaks without understanding it:** you type `dd` in insert mode and get the text "dd" in your manifest, or you type YAML in normal mode and trigger a dozen commands.

| Mode | How you enter it | What the keys do | Screen text at the bottom (REAL OUTPUT (Docker)) |
|---|---|---|---|
| **Normal** | Start here. Press `Esc` from any other mode. | Every key is a command: move, delete, copy, indent. | (empty) |
| **Insert** | `i` insert before the cursor, `a` after the cursor, `o` new line below, `O` new line above (also `I` start of line, `A` end of line) | Keys type text. | `-- INSERT --` |
| **Visual** | `v` characters, `V` whole lines, `Ctrl+V` a rectangular block of columns | Move to extend the selection, then press an operator (`>`, `d`, `y`, `I`). | `-- VISUAL --`, `-- VISUAL LINE --`, `-- VISUAL BLOCK --` |
| **Command-line** | `:` from normal mode | A line typed at the bottom, run with `Enter`: `:w`, `:%s/a/b/g`, `:set paste`. | the `:` prompt |

A fifth mode, **Replace** (`R`), overtypes existing characters and shows `-- REPLACE --`. You rarely need it.

**Exam rule for entering insert mode.** The exam page says "The INSERT key is prohibited" (source: [tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)). In Vim the Insert key also enters insert mode, so use `i`, `a`, `o` or `O` instead. The same page says to use `Ctrl+Alt+W` instead of `Ctrl+W`. `Ctrl+W` is also the prefix of Vim's window commands (split, switch), so do not rely on those in the exam; you do not need them for this lesson.

**If you are stuck in a mode:** press `Esc` twice, then type `:q!` and `Enter`. `Esc` returns to normal mode from every mode (so does `Ctrl+[`). `:q!` quits and discards changes.

### 2.3 Save, quit and the swap file

| Keys | Meaning | Notes |
|---|---|---|
| `:w` | Write (save), stay in the editor | `:w newname.yaml` saves a copy under another name. |
| `:q` | Quit | Refuses if there are unsaved changes: `E37: No write since last change (add ! to override)` (REAL OUTPUT (Docker)). |
| `:q!` | Quit and **discard** changes | In `kubectl edit` this means "cancel". |
| `:wq` | Write and quit | Always writes, even if nothing changed. |
| `:x` | Write only if changed, then quit | Same as `ZZ`. Safer in `kubectl edit`, because an unchanged file is not rewritten. |
| `ZZ` | Same as `:x` | Two capital Z, normal mode. |
| `ZQ` | Same as `:q!` | (REAL OUTPUT (Docker): after changing a file, `ZQ` left it unchanged.) |

**Under the hood: the swap file.** While you edit `name.yaml`, Vim keeps a crash-recovery copy in the same directory called `.name.yaml.swp`. Vim writes it after about 200 typed characters or 4 seconds of idle time (the defaults of `updatecount` and `updatetime`). It is removed when you quit normally. If the terminal dies, your SSH session drops or Vim is killed, the `.swp` stays. The next time you open the same file Vim stops with a warning. In the exam a dropped connection can leave one behind, so know the screen.

```text
REAL OUTPUT (Docker) - opening a file whose editor was killed with kill -9
E325: ATTENTION
Found a swap file by the name ".sw.yaml.swp"
          owned by: root   dated: Tue Oct 27 07:11:00 2026
         file name: ~root/lab/t103/sw.yaml
          modified: YES
         user name: root   host name: 92640a1853ad
        process ID: 3618 (STILL RUNNING)
While opening file "sw.yaml"
...
(2) An edit session for this file crashed.
    If this is the case, use ":recover" or "vim -r sw.yaml"
    to recover the changes (see ":help recovery").
    If you did this already, delete the swap file ".sw.yaml.swp"
    to avoid this message.

Swap file ".sw.yaml.swp" already exists!
[O]pen Read-Only, (E)dit anyway, (R)ecover, (Q)uit, (A)bort:
```

How to read it. First look at `modified: YES`: the crashed session had unsaved edits. Then check that no other Vim is really running on the file (`pgrep -a vim`); in this capture the line says `STILL RUNNING` because I killed Vim with `kill -9` inside a container, so treat that line as something to check, not as proof. Choose:

| Key | Action | Use when |
|---|---|---|
| `R` | Recover the unsaved edits from the swap file | The session crashed and you want the edits back. |
| `O` | Open read-only | Someone else may be editing; you only want to look. |
| `E` | Edit anyway | You know the swap file is stale and want a fresh start. Two editors on one file can overwrite each other. |
| `D` | Delete the swap file | Offered by Vim when it can tell the swap file is stale (not shown in my capture above). |
| `Q` / `A` | Quit / abort | You want to stop and investigate. |

After `R`, Vim prints `Recovery completed. You should check if everything is OK.`. Then run `:w` to save the recovered text (REAL OUTPUT (Docker): after `R` and `:w`, the file contained both lines, `a: 1` and `b: 2`), quit, and delete the leftover swap file with `rm .sw.yaml.swp`, otherwise the warning returns.

### 2.4 Motions: moving without the mouse

A **motion** moves the cursor. Counts work on all of them (`3w` moves three words). Every motion below was run and the cursor position read back (REAL OUTPUT (Docker)).

| Keys | Moves to | Example result on a 12-line file |
|---|---|---|
| `gg` | First line | cursor at line 1, column 1 |
| `G` | Last line (`12G` or `:12` goes to line 12) | line 12 |
| `:N` | Line `N` (type the number after the colon, then `Enter`) | `:4` put the cursor at line 4 (first non-blank character) |
| `w` / `b` | Start of next / previous word. Punctuation such as `:` counts as its own word. | `w` on `  name: web` from column 1 moved to `name` (column 3); `b` then went to the `:` of `metadata:` on the line above, because punctuation is its own word |
| `0` / `$` | Start / end of the line | column 1 / last column |
| `%` | Matching `(`, `[` or `{` | on `[` in `args: ["-g", "daemon off;"]` it jumped to the closing `]` |
| `/text` + `Enter` | Search forward for a regular expression | `/image` jumped to the next `image:` line |
| `n` / `N` | Next / previous match of the last search | `n` after `/name` moved forward; `N` moved back |

Reading `yaml: line 27: ...` errors is why `set number` is in the vimrc: type `:27` and you are on the offending line.

### 2.5 Editing in normal mode: the operator and motion grammar

Most editing keys follow one pattern: **operator + motion** (and an optional count). An operator says what to do: `d` delete, `y` yank (copy), `c` change (delete and enter insert mode), `>` shift right, `<` shift left. Doubling the operator applies it to the whole line: `dd`, `yy`, `cc`, `>>`, `<<`.

| Keys | Effect | Notes (all REAL OUTPUT (Docker) unless said) |
|---|---|---|
| `dd` | Delete the line (it goes into the register, so it can be pasted) | `3dd` on four lines `a`..`d` left only `d` |
| `yy` | Copy the line | |
| `p` / `P` | Paste after / before the cursor line | `yy`, `j`, `p`, `k`, `P` on `one/two/three` gave `one one two one three` |
| `u` | Undo | |
| `Ctrl+R` | Redo | On `a b c` with the cursor on `c`, `dd`, `u`, `Ctrl+R` left `a b` (the line is deleted again). Checked headless in Neovim, not in Docker. A new change after `u` (for example a second `dd`) clears the redo history, so `Ctrl+R` does nothing then. |
| `x` | Delete the character under the cursor | `x` then `.` then `.` on `abcdef` gave `def` |
| `cw` | Change to the end of the word | **Stops at punctuation.** On `image: nginx:1.25`, `cw` on `nginx` produced `image: redis:1.25` (the `:1.25` stayed). `cW` (capital W, "big word", stops only at spaces) produced `image: redis:7`. |
| `.` | Repeat the last change | `cw X Esc w .` on `a b c d` gave `X X c d` |
| `>>` / `<<` | Shift the line right / left by one `shiftwidth` (2 spaces after the vimrc below) | |
| `5>>` | Shift 5 lines, counting from the cursor | on seven lines `a`..`g` the first five gained two spaces and `f`, `g` did not |
| `c$` | Change from the cursor to the end of the line | after `/1`, `c$` then `1.27` changed `nginx:1.25` into `nginx:1.27` |

**Insert-mode indentation shortcuts (bonus).** In insert mode, `Ctrl+T` indents the current line by one `shiftwidth` and `Ctrl+D` removes one. With `autoindent` on, they let you type nested YAML without leaving insert mode (REAL OUTPUT (Docker): `b:` then `Ctrl+T` then `c: 1` then `Ctrl+D` then `d: 2` produced `b:`, `  c: 1`, `d: 2`).

### 2.6 Indenting YAML blocks with visual mode, and column inserts

YAML structure is indentation, so moving a whole block is the most common edit. Three equivalent ways, all REAL OUTPUT (Docker) on a 12-line block starting at line 4:

| Keys | What happens |
|---|---|
| `:4` then `V` then `11j` then `>` | `V` starts visual-line mode on line 4, `11j` extends the selection down 11 lines (12 lines in total), `>` shifts them one `shiftwidth`. Vim says `12 lines >ed 1 time`. Press `.` to repeat on the same 12 lines. |
| `:4` then `V` `11j` `2>` | A count before `>` shifts that many times: `12 lines >ed 2 times` (two levels = 4 spaces). |
| `:4,15>>` | The command-line form. In the command line, **each `>` is one shift**, so `>>` shifts twice. (A single `:4,15>` shifts once.) |

`12>>` (normal mode, count 12) shifts twelve lines **once**. The count there is the number of lines, not the number of shifts. That difference is the usual source of "I indented it the wrong number of times".

**Column inserts with `Ctrl+V`.** Visual-block mode selects a rectangle, and `I` (capital i) inserts the same text at the start of the rectangle on every line when you press `Esc`. This comments out a block of lines:

```text
REAL OUTPUT (Docker) - keys: :2 Enter  Ctrl+V  j  j  I  "# "  Esc  :wq
env:
# - name: A
#   value: "1"
# - name: B
x: 1
```

To uncomment, select the `#` columns with `Ctrl+V` and press `d`.

### 2.7 `~/.vimrc` for YAML: three lines, from memory

Vim reads `~/.vimrc` when it starts. The following three lines are all you need. Type them from memory until it takes 15 seconds.

```vim
set expandtab tabstop=2 shiftwidth=2 autoindent
set number
syntax on
```

| Setting | What it does | Vim default | Risky or invalid values |
|---|---|---|---|
| `expandtab` | The `Tab` key inserts spaces instead of a tab character | off | Leaving it off lets a tab slip into the file: YAML rejects it (section 6). |
| `tabstop=2` | How wide a tab character is **drawn**; also what `:retab` uses to convert tabs to spaces; with `expandtab` the `Tab` key inserts spaces up to the next multiple of `tabstop` (2 spaces from column 0, 1 space from an odd column) | 8 | At 8, `:retab` turns every tab into 8 spaces (REAL OUTPUT (Docker): `metadata:` children came back indented by 8). Set it **before** you run `:retab`. |
| `shiftwidth=2` | How many columns `>>`, `<<`, `>` in visual mode and `autoindent` use per level | 8 | Using 4 is valid YAML, but then it differs from the 2-space style of every Kubernetes example. `shiftwidth=0` means "use tabstop". |
| `autoindent` | A new line starts with the same indent as the previous line | off | Great while typing, harmful while pasting (2.8). |
| `number` | Shows line numbers | off | Display only; no risk. Needed to read `yaml: line N` errors. |
| `syntax on` | Colours keys, strings and comments | off in a minimal vimrc | On `vim.tiny` it prints an error (below). |

What the three lines changed (REAL OUTPUT (Docker), Ubuntu Vim 9.1, opening a `.yaml` file):

```text
no ~/.vimrc:        expandtab   tabstop=8  shiftwidth=2  noautoindent  nonumber  filetype=yaml
with the 3 lines:   expandtab   tabstop=2  shiftwidth=2  autoindent    number    filetype=yaml
```

Without a `~/.vimrc`, Ubuntu's Vim already turned on `expandtab` and `shiftwidth=2` for `.yaml` files through its YAML plugin, but `tabstop` stayed 8 and `autoindent` and `number` were off. Do not rely on that: it needs a file that Vim recognises as YAML, and whether the exam hosts ship a `~/.vimrc` or the same Vim build is **UNVERIFIED**. This lesson therefore teaches you to type the three lines (the exam facts say only that the SSH hosts have `kubectl` with an alias and completion, `yq`, `curl`, `wget` and `man`; source [tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)). A vimrc is per user and per host, so on each new host check `cat ~/.vimrc` before you start typing YAML.

**`vim.tiny` warning.** Some minimal installs only have `vim-tiny`, which is what `vi` points to. REAL OUTPUT (Docker, Ubuntu 24.04 with only `vim-tiny`): `readlink -f $(which vi)` printed `/usr/bin/vim.tiny`, the version string shows `-syntax` and `-eval`, and starting `vi` with the three-line vimrc printed:

```text
Error detected while processing /root/.vimrc:
line    3:
E319: Sorry, the command is not available in this version: syntax on
Press ENTER or type command to continue
```

Press `Enter`. The other two lines still applied (`expandtab`, `tabstop=2` and `number` were set). Only the colours are missing, and you do not need colours to edit YAML.

### 2.8 Pasting without a staircase: `:set paste` and `:set nopaste`

**The problem.** With `autoindent` on, every time Vim receives a newline it adds the previous line's indent. If your paste arrives as typed keys, each line's own leading spaces are added on top. The result is a staircase. REAL OUTPUT (Docker), pasting this snippet in insert mode as typed keys with the three-line vimrc loaded:

```text
REAL OUTPUT (Docker) - cat -A of the saved file, "$" marks the end of each line
spec:$
  containers:$
    - name: web$
        image: nginx:1.27$
            env:$
                - name: A$
                      value: "1"$
```

The snippet that was pasted had `containers:` at 2 spaces, `- name: web` at 2, `image:` at 4, `env:` at 4, `- name: A` at 4 and `value:` at 6. The file got 2, 4, 8, 12, 16 and 22: each line added its own indent on top of the previous line's. The YAML is now wrong: `image` sits deeper than the `name` line above it, so it is no longer a field of the container. A staircase like this usually does not parse. REAL OUTPUT (Docker): `yq` (and PyYAML) reject the first four lines with `mapping values are not allowed in this context` at line 4, because the deeper `image: nginx:1.27` line is read as a continuation of the scalar `web`. Read that error as "a pasted line moved right" and go to the line it names.

**A paste can also parse and still be wrong.** If a pasted line lands one level too deep under a line that already has children, YAML accepts it and attaches it to the wrong parent. REAL OUTPUT (Docker): in a container with `ports:` followed by `- containerPort: 80`, a `resources:` block pasted two spaces too deep parsed without any error, and `yq '.containers[0] | keys'` listed `name`, `image` and `ports` but no `resources`: the block had become a field of the port item. Always read the indentation of what you pasted, and parse it (6.2).

**The fix.** Run `:set paste` **before** entering insert mode and pasting. Vim turns off `autoindent` and other helpers and shows `-- INSERT (paste) --` at the bottom. After pasting, press `Esc` and run `:set nopaste` to turn the helpers back on. With `:set paste` the same snippet was saved with correct indentation (REAL OUTPUT (Docker)).

**A modern note.** Vim 9.1 understands the terminal's *bracketed paste* mode. In my tmux test, pasting through `tmux paste-buffer -p` without `:set paste` also produced a correct file (with one extra blank line at the end, because the snippet ended with a newline). So you may not see a staircase in a modern terminal. Whether the exam terminal sends bracketed paste is **UNVERIFIED**, so make `:set paste` a reflex. In the exam terminal the paste shortcut is `Ctrl+Shift+V` and copy is `Ctrl+Shift+C` (source: [tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)).

If you forget `:set nopaste`, nothing breaks, but `autoindent` stays off for the rest of the session and the next block you type by hand has no indent. When indentation behaves oddly, check `:set paste?`.

### 2.9 Search and replace: `:%s` and `:g`

**Substitute.** `:[range]s/pattern/replacement/[flags]`.

| Part | Meaning |
|---|---|
| `%` | Range: every line. `:2,3s/...` is lines 2 to 3. Without a range only the current line is changed. |
| `s/old/new/` | Replace the first match on each line. |
| flag `g` | Replace **all** matches on each line. |
| flag `c` | **Confirm** each replacement. Vim shows `replace with nginx:1.27 (y/n/a/q/l/^E/^Y)?` (REAL OUTPUT (Docker)). `y` yes, `n` no, `a` all remaining, `q` quit, `l` last (do this one and stop). |
| flag `i` | Ignore case. |

`pattern` is a regular expression. A dot matches any character, so `1.25` also matches `1x25`. Write `1\.25` for a literal dot. If the pattern contains `/`, use another delimiter: `:%s#registry.old/app#registry.new/app#g` worked (REAL OUTPUT (Docker)).

REAL OUTPUT (Docker) - file with three `nginx:1.25` lines and one `redis:7` line, `:%s/nginx:1.25/nginx:1.27/gc` then `a`:

```text
replace with nginx:1.27 (y/n/a/q/l/^E/^Y)?
3 substitutions on 3 lines
```

**Global command.** `:g/pattern/command` runs a command on every line that matches. `:g/pattern/d` deletes every matching line. `:g!/pattern/d` or `:v/pattern/d` deletes every line that does **not** match. `:g/redis/s/7/8/` runs a substitute only on matching lines. All three were run (REAL OUTPUT (Docker)):

| Command | Result on `image: nginx:1.25 / # note / image: nginx:1.25 / "  # keep spaced comment" / image: redis:7 / image: nginx:1.25` |
|---|---|
| `:g/^\s*#/d` | Both comment lines removed, four `image:` lines left. `^\s*#` means "start of line, any spaces, then #". |
| `:v/image/d` | Only the `image:` lines remain. |
| `:g/redis/s/7/8/` | Only the redis line changed, to `image: redis:8`. |

### 2.10 Seeing tabs and trailing spaces

**Why.** A tab and its equivalent spaces look identical on screen. YAML forbids tab characters for indentation, so you need a way to see them.

- In Vim: `:set list`. A tab shows as `^I`, the end of each line as `$` (so trailing spaces show up as spaces before the `$`). `:set nolist` turns it off. `:set listchars=tab:>-,trail:~` shows tabs as `>-` and trailing spaces as `~` (REAL OUTPUT (Docker), below).
- In the shell: `cat -A file.yaml | grep -n '\^I'` prints each line that contains a tab, with its line number. `cat -A` makes tabs `^I` and line ends `$`; the `\^I` in `grep` is a literal caret followed by `I`. `grep -nP '\t'` finds tabs too.

```text
REAL OUTPUT (Docker) - :set list, then :set listchars=tab:>-,trail:~
  1 a:$                     |   1 a:
  2 ^Ib: 1$                 |   2 >-b: 1
  3   c: 2   $              |   3   c: 2~~~
```

Fix tabs with `:retab` (needs `expandtab` and the right `tabstop`; see 2.7). REAL OUTPUT (Docker): a file with eight lines that began with tabs had `grep -c` of tab lines 8 before and 0 after `:retab` with the vimrc loaded.

### 2.11 tmux basics (for your home lab)

**tmux availability in the exam is UNVERIFIED.** The only tools the exam page lists for the SSH hosts are `kubectl` (with an alias and Bash completion), `yq`, `curl`, `wget` and `man`, and the page says host `base` has none of these (source: [tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)). `tmux` is not on that list. Practise with it at home, but do not plan an exam strategy that needs it.

## 3. How it works (diagram)

```text
                         +-------------------------------------------+
                         |            COMMAND-LINE MODE              |
        ':'              |  :w  :q!  :wq  :x  :12  :%s/a/b/gc        |
   +-------------------->|  :g/pat/d  :set paste  :set list  :retab  |
   |                     +----------------------+--------------------+
   |                           Enter (run it)    |   or Esc (cancel)
   |                                             v
+--+------------------------------------------------------------------+
|                         NORMAL MODE  (Vim starts here)               |
|  gg G w b 0 $ %  /text n N     dd yy p P u Ctrl+R x cw .   >> << 5>> |
|  ZZ (save+quit)  ZQ (quit, discard)                                  |
+--+--------------+----------------+---------------+------------+-----+
   | i a o O      | v              | V             | Ctrl+V     | R
   v              v                v               v            v
+--------+   +----------+   +--------------+  +--------------+ +---------+
| INSERT |   |  VISUAL  |   | VISUAL LINE  |  | VISUAL BLOCK | | REPLACE |
| type   |   | chars    |   | whole lines  |  | columns      | | overtype|
| text   |   | d y >    |   | > < d y      |  | I A d        | |         |
+---+----+   +----+-----+   +------+-------+  +------+-------+ +----+----+
    |             |                |                 |              |
    +------- Esc -+----------------+-----------------+--------------+
                          (every mode returns to NORMAL)
```

How to read it:

1. You always start in **normal** mode. Everything you type is a command until you choose another mode.
2. `i`, `a`, `o`, `O` enter **insert** mode (text goes into the file); `v`, `V`, `Ctrl+V` enter the three **visual** modes (you select first, then act); `R` enters replace; `:` opens the **command line**.
3. `Esc` is the key to use to get back to normal mode from insert, visual and replace (`Ctrl+[` does the same); from the command line `Enter` runs the command and `Esc` cancels it. If you are lost, `Esc` `Esc`.
4. Insert and visual are not connected: press `Esc` first. The diagram leaves out two shortcuts: `v`, `V` and `Ctrl+V` switch directly between the visual modes, and `:` typed in a visual mode opens the command line with the selected range filled in (`:'<,'>`).
5. In the exam use `i`, `a`, `o` or `O` and never the Insert key (source: [tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)).

## 4. Commands and YAML you must produce fast

**Imperative shortcuts (use these before opening any editor):**

```bash
vim pod.yaml                                  # open (or create) a file in Vim

```

`k set env` is the fastest way to add one variable. The block below is for when the variables arrive as a block, or when the task says "edit the Deployment".

**The vimrc (type it from memory, 3 lines):**

```vim
set expandtab tabstop=2 shiftwidth=2 autoindent   " Tab key = 2 spaces, indent steps of 2, copy previous indent
set number                                        " show line numbers so 'yaml: line N' is easy to find
syntax on                                         " colours (prints E319 on vim.tiny; safe to ignore)
```

Fast way to write it without opening Vim: `printf 'set expandtab tabstop=2 shiftwidth=2 autoindent\nset number\nsyntax on\n' > ~/.vimrc`.

**The declarative YAML: a Deployment with a 4-line env block.** This is the result you should reach inside `k edit deploy web` within 30 seconds. Every field is explained.

```yaml
apiVersion: apps/v1               # Deployments live in the apps/v1 API group
kind: Deployment
metadata:
  name: web                       # object name; immutable once created
  namespace: lab-t103             # namespace the object lives in
spec:
  replicas: 2                     # desired Pod count; default 1
  selector:
    matchLabels:
      app: web                    # which Pods this Deployment owns; immutable after creation
  template:                       # the Pod template
    metadata:
      labels:
        app: web                  # must match spec.selector.matchLabels or the API rejects the Deployment
    spec:
      containers:
      - name: web                 # container name, unique inside the Pod
        image: nginx:1.27         # pinned tag, not the floating latest tag
        env:                      # --- the 4-line block you add ---
        - {name: TIER, value: web}        # flow style: one list item on one line
        - name: LOG_LEVEL                 # block style: name ...
          value: debug                    # ... and value (a string; quote numbers such as "1")
```

How the 4 lines get typed (Vim, with the vimrc loaded, cursor on the `image:` line): `o` opens a new line with the same indent as `image:` (8 spaces, because of `autoindent`), then type `env:` `Enter` `- {name: TIER, value: web}` `Enter` `- name: LOG_LEVEL` `Enter` then two spaces and `value: debug`, then `Esc`. The list items line up under `env:`, which is valid YAML. Type the flow-style item first so `autoindent` never needs a dedent. In a real `kubectl edit` buffer the keys are sorted, so the first container line is `- image: nginx:1.27` (with the dash) and `o` under it would indent too little; search `/imagePull` and press `o` there instead (section 5).

## 6. Common mistakes and how to fix them

| Symptom | What you will see (exact text) | Cause | Fix (command) |
|---|---|---|---|
| Apply or `kubectl edit` rejects the YAML at a line with an odd indent | `error: error parsing v.yaml: error converting YAML to JSON: yaml: line 10: found character that cannot start any token` (REAL OUTPUT (Docker), `kubectl` v1.37.1). The table gives the text. The sections below give the order in which to investigate.

### 6.1 `found character that cannot start any token`

1. Read the line number in the message (`line 10` means the tenth line of the file you gave to `kubectl`, not the line in the Deployment on the server).
2. Print the tab lines: `cat -A f.yaml | grep -n '\^I'`. If line 10 is in the output, tabs are the cause. If the output is empty, the cause is something else (for example a stray character); look at the line with `:10` and `:set list` in Vim.
3. Look at the shape of the output. `^I` at the start of a line is a tab used as indentation. `^I` after a colon (`name:^Iweb`) is a tab used as a separator. In my test the second form did not give a parse error at all (the parse succeeded and the failure came later), so a clean parse does not prove there are no tabs.
4. Fix: in Vim run `:set expandtab tabstop=2` (already in your vimrc) and `:retab`. Check with `grep -c $'\t' f.yaml`, which must print 0.

### 6.2 Staircase after pasting

1. Look at the file with `:set list` or `cat -A`. Every line is indented more than the one before.
2. Decide: is it faster to undo (`u`) and paste again with `:set paste`, or to fix the block with `V`, `j` and `<`? For a short block, undo and paste again.
3. Before the next paste, run `:set paste`. After it, run `:set nopaste`. Confirm with `:set paste?`, which prints `nopaste`.
4. Validate: `yq . f.yaml` parses it, or `k apply --dry-run=client -f f.yaml`. A staircase usually fails to parse (`mapping values are not allowed in this context`), but a paste can also parse and still be wrong (the `resources:` example in 2.8), so read the indentation too.

### 6.3 A `kubectl edit` that did not apply

1. Scroll up in the terminal. The last lines are the only explanation: `error: ... is invalid` and `A copy of your changes has been stored to "..."`.
2. `ls -t /tmp/kubectl-edit-*.yaml` shows the newest saved file. On macOS use the path printed in the message, because the file is under `$TMPDIR`.
3. Open it. The `#` lines at the top say which field was refused and why. A typo in a field name or a bad type is fixed in place. A message that ends in `field is immutable` means the field cannot be changed on a live object; either revert it or create a new object.
4. Apply the fixed file with `k apply -f`. Remove `resourceVersion` from the file first if the object may have changed in the meantime.
5. Read it back with `k get` and compare to what you meant to change. "applied" is not the same as "correct".

### 6.4 Stuck in Vim

1. Press `Esc` twice. If the bottom line then shows nothing, you are in normal mode.
2. Decide whether to keep the edits. Keep: `:wq`. Discard: `:q!`. In `kubectl edit`, `:q!` cancels the whole edit.
3. If `:q` shows `E37`, Vim is protecting unsaved changes. That is not an error in your file.

### Lab 3 (Break-fix): a rejected `kubectl edit`

**Setup.** Save the next block as `break.sh`, run it with `bash break.sh`, and do not read it before you try the task (it plays the part of a colleague).

```bash
#!/usr/bin/env bash
set -e
export TMPDIR=/tmp
mkdir -p ~/lab/t103/fix && cd ~/lab/t103/fix
kubectl create ns lab-t103
kubectl -n lab-t103 create deploy web --image=nginx:1.27 --replicas=2
kubectl -n lab-t103 rollout status deploy/web --timeout=120s
cat > ed.sh <<'E'
#!/usr/bin/env bash
n=/tmp/.t103-ed-count
c=$(cat "$n" 2>/dev/null || echo 0)
echo $((c + 1)) > "$n"
[ "$c" = 0 ] || exit 0
sed -i -e 's/app: web/app: frontend/' -e '/^spec:/,/^status:/s/replicas: 2/replicas: 3/' \
  -e '/^        imagePullPolicy:/i\        env:\n        - name: TIER\n          value: frontend' "$1"
E
chmod +x ed.sh
rm -f /tmp/.t103-ed-count /tmp/kubectl-edit-*.yaml
KUBE_EDITOR="$PWD/ed.sh" kubectl -n lab-t103 edit deploy web >/dev/null 2>&1 || true
rm -f ed.sh /tmp/.t103-ed-count
echo "A colleague's edit of Deployment web was rejected. Find out what they changed."
```

**Task.** A colleague edited Deployment `web` in namespace `lab-t103` with `kubectl edit`, closed the editor when it showed an error, and says their changes are gone. Deployment `web` must stay exactly as it is now (2 replicas, selector `app=web`). Recover the colleague's edits from the file `kubectl` kept on disk and create a **new** Deployment named `frontend` in `lab-t103` from it, so that `frontend` has all the colleague's changes. Work in `~/lab/t103/fix`.

<details><summary>Hint 1</summary>
`kubectl` printed a path when the edit was abandoned. Look for `/tmp/kubectl-edit-*.yaml` and sort by time: `ls -t /tmp/kubectl-edit-*.yaml`. There may be two files; either one has the edits. `diff` it against `k -n lab-t103 get deploy web -o yaml` to see what changed.
</details>

<details><summary>Hint 2</summary>
The saved file is a copy of a live object, so it carries fields the server owns: `uid`, `resourceVersion`, `creationTimestamp`, `generation`, `status` and an annotations block. A new object must not carry them. Delete them (with `yq` or with `:g` in Vim) and change `metadata.name`.
</details>

<details><summary>Hint 3</summary>
Why was the edit rejected in the first place? Read the lines that start with `#` at the top of the newest file. Some fields of a Deployment can never be changed after creation, which is why the task asks for a new object.
</details>

<details><summary>Solution</summary>

```bash
ls -t /tmp/kubectl-edit-*.yaml                 # newest first
f=$(ls -t /tmp/kubectl-edit-*.yaml | head -1)
cp "$f" ~/lab/t103/fix/frontend.yaml
cd ~/lab/t103/fix
head -12 frontend.yaml                         # the error header: which field was rejected and why
diff <(k -n lab-t103 get deploy web -o yaml) frontend.yaml | head -40
```

The header says the server refused to change `spec.selector`: a Deployment's selector is immutable, so changing `app: web` to `app: frontend` in place can never work. The other two edits (replicas and the env var) were fine on their own, but the request was rejected as a whole. A new object is the only way to keep all three changes.

Make the copy a valid new object. The server-owned fields must go, and the name must change. With `yq`:

```bash
yq -i 'del(.status, .metadata.uid, .metadata.resourceVersion, .metadata.creationTimestamp, .metadata.generation, .metadata.annotations) | .metadata.name = "frontend"' frontend.yaml
k apply -f frontend.yaml
```

Or with Vim: `vim frontend.yaml`, `:g/^  \(uid\|resourceVersion\|creationTimestamp\|generation\):/d`, then find `status:` with `/^status` and delete to the end of the file with `dG`, delete the `annotations:` block, and change `name: web` under `metadata:` to `name: frontend`.

</details>

**Verification**

```bash

test "$(k -n lab-t103 get deploy web -o jsonpath='{.spec.selector.matchLabels.app}/{.spec.replicas}')" = "web/2" && echo "WEB_UNTOUCHED"
```

## 8. Exam tips

- **Type the vimrc first on every host.** Each task runs on a designated host and you leave it with `exit` (source: [tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)). Whether `~/.vimrc` is shared across hosts or already present is **UNVERIFIED**, so run `cat ~/.vimrc` and, if it is missing, paste the one-line `printf` from section 4. It costs about 15 seconds and saves much more.
- **Do not open an editor when a command will do.** `k create ...`, `k run ... $do`, `k set env`, `k set image`, `k scale` and `k label` change one thing without indentation risk. Use `k edit` or Vim for blocks. Keep `$do > file.yaml` for new objects, then edit the file.
- **Read the last line `kubectl edit` prints.** `deployment.apps/web edited` means the server accepted it. `Edit cancelled, no changes made.` means nothing changed. `Edit cancelled, no valid changes were saved.` means your work is in `/tmp/kubectl-edit-*.yaml`; find it with `ls -t /tmp/kubectl-edit-*.yaml`. Confirm every edit with a `k get` before you move on.
- **Keys the exam page prohibits or remaps (source: [tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)):** the INSERT key is prohibited (use `i`, `a`, `o`, `O`), `Ctrl+Alt+W` replaces `Ctrl+W`, and the terminal copy/paste is `Ctrl+Shift+C` / `Ctrl+Shift+V`. Press `:set paste` before you paste.
- **Pages to open (allowed documentation):** [kubectl edit](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_edit/) for flags such as `-o json`, `--save-config` and `--output-patch`, and the [kubectl Quick Reference](https://kubernetes.io/docs/reference/kubectl/quick-reference/) (section "Editing resources", plus the YAML snippets you can copy).
- **Traps before you move on:** `:set list` if a pasted file errors (tabs); `cat ~/.vimrc` if indentation is 4 or 8 spaces; `:set paste?` if autoindent stopped working (you forgot `:set nopaste`); a `.swp` file next to your manifest if Vim shows `E325`. tmux is **UNVERIFIED** in the exam, so do not depend on it.

## 9. Quick review

1. **What command lists the lines of `pod.yaml` that contain a tab, with their line numbers?**
   <details><summary>Answer</summary>`cat -A pod.yaml | grep -n '\^I'` (or `grep -nP '\t' pod.yaml`). `cat -A` prints a tab as `^I`.</details>
2. **Why does `:retab` need `expandtab` and the right `tabstop` set first?**
   <details><summary>Answer</summary>`:retab` rewrites existing tabs using the current `tabstop` for the width, and only turns them into spaces if `expandtab` is on. With the default `tabstop=8` each tab becomes 8 spaces.</details>
3. **What does `V11j2>` do?**
   <details><summary>Answer</summary>`V` selects the current line, `11j` extends the selection down 11 lines (12 lines in total), and `2>` shifts them right two `shiftwidth` levels (4 spaces with `shiftwidth=2`).</details>
4. **Why does pasted YAML sometimes form a staircase, and how do you prevent it?**
   <details><summary>Answer</summary>`autoindent` adds the previous line's indent to every new line, on top of the indent in the pasted text. Run `:set paste` before entering insert mode, paste, `Esc`, then `:set nopaste`.</details>
5. **Which environment variables does `kubectl edit` read to choose an editor, and in what order?**
   <details><summary>Answer</summary>`KUBE_EDITOR`, then `EDITOR`. If neither is set it uses `vi`. `VISUAL` is not read.</details>
6. **A `kubectl edit` finished with `Edit cancelled, no valid changes were saved.` Where are your edits, and what is the next step?**
   <details><summary>Answer</summary>In the file named in the line above it, `/tmp/kubectl-edit-<digits>.yaml` (on Linux). Read the `#` error lines at the top of that file, fix the problem in the file, and apply it with `k apply -f` (or `k replace -f`).</details>
7. **Replace every `nginx:1.25` with `nginx:1.27` in a file, asking before each change. What do you type?**
   <details><summary>Answer</summary>`:%s/nginx:1\.25/nginx:1.27/gc`, then `y` or `n` for each prompt, or `a` for all.</details>
8. **Why can the exam not be assumed to have tmux, and what does the exam page list instead?**
    <details><summary>Answer</summary>The tips page lists `kubectl` with an alias and Bash completion, `yq`, `curl`, `wget` and `man` on the SSH hosts, and says host `base` has none of them. tmux is not listed, so its availability is UNVERIFIED.</details>
9. **You see `E325: ATTENTION` when opening a file. What is it and what are your choices?**
    <details><summary>Answer</summary>A leftover swap file `.name.swp` from a crashed or still-running session. Check `pgrep -a vim`, then press `R` to recover the unsaved edits (then `:w` and delete the `.swp`), `O` to open read-only, `E` to edit anyway, or `Q` to quit.</details>
10. **Why is `cw` on `nginx` in `image: nginx:1.25` unlikely to give you the result you want?**
    <details><summary>Answer</summary>`w` treats `:` as punctuation, so `cw` changes only `nginx`. Use `cW` (stops at spaces), or `c$` after jumping to the start of what you want to replace.</details>
