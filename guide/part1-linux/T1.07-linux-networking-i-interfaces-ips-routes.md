## 1. Why this matters

Every Pod gets its own network namespace (a private copy of the network stack). The container runtime and the CNI plugin (the program that wires Pods into the network) connect that namespace to the node with a **veth pair**, and the node reaches other nodes with **routes**. Pod networking is not magic. It is the same `ip` tooling you can type by hand.

When you do not know this, "Pod A cannot reach Pod B on another node" is a black box. When you do know it, the problem becomes three questions: is there an interface, is there an address, is there a route. The exam gives you shells on the nodes (`ssh <nodename>`, then `sudo -i`; see [the exam tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)), so `ip route get <pod-ip>` and `sysctl net.ipv4.ip_forward` are the fastest way to prove where a packet dies. Two small kernel settings (`ip_forward` and, on some setups, `br_netfilter`) are also the classic reasons a freshly built node "works" for node-local traffic and fails for everything else.

## 2. Concepts

### 2.1 The `ip` command and network interfaces

A **network interface** (also called a link) is the kernel object that sends and receives packets. Some interfaces are real hardware (`eth0`, `ens3`). Most on a Kubernetes node are virtual: loopback, bridges, veth ends, tunnels.

`ip` (from the **iproute2** package) is the one tool for all of it. It replaced the old `ifconfig`, `route` and `arp` commands (the `net-tools` package), which are often not installed. The general shape is `ip [OPTIONS] OBJECT COMMAND`. The objects used in this lesson:

| Object | Meaning | Common commands |
|---|---|---|
| `ip link` | Interfaces (layer 2: the link, MAC address, MTU, up/down) | `show`, `add`, `set`, `del` |
| `ip addr` (or `ip a`) | IP addresses on interfaces (layer 3) | `show`, `add`, `del` |
| `ip route` (or `ip r`) | Routing table: where to send packets | `show`, `add`, `del`, `get` |
| `ip neigh` | Neighbour (ARP) table: IP address to MAC address | `show`, `flush` |
| `ip netns` | Named network namespaces | `add`, `del`, `list`, `exec` |
| `bridge` (a separate command) | Bridge ports and the MAC learning table | `link`, `fdb show` |

You can shorten any word until it is unique (`ip a`, `ip r`, `ip l`). Three options save the most time:

- `-br` (brief): one line per interface, easy to read. `ip -br a` and `ip -br link` are the first commands to run on any node.
- `-4` / `-6`: show only IPv4 or IPv6.
- `-n NAME`: run the `ip` command inside the network namespace `NAME` (short for `ip netns exec NAME ip ...`).

**BusyBox `ip` has no `-br`.** The full `ip` (iproute2) is on nodes and VMs. Inside a small test Pod such as `busybox:1.36`, `ip` is the BusyBox applet: it supports `ip a`, `ip route`, `ip link show` and `-o`, but `ip -br a` prints the BusyBox usage text and exits with status 1. Use `ip a` in Pods and `ip -br a` on nodes.

**REAL OUTPUT (Docker)** of `ip -br a` and `ip -br link`:

```text
$ ip -br a
lo               UNKNOWN        127.0.0.1/8 ::1/128 
eth0@if219       UP             192.168.215.3/24 
$ ip -br link
lo               UNKNOWN        00:00:00:00:00:00 <LOOPBACK,UP,LOWER_UP> 
eth0@if219       UP             0a:ae:85:2b:4d:82 <BROADCAST,MULTICAST,UP,LOWER_UP> 
```

How to read it:

| Part | Meaning |
|---|---|
| `eth0` | The interface name. |
| `@if219` | This interface is one end of a veth pair (or another "linked" device). `219` is the **interface index** (`ifindex`) of the other end. The other end is in a different namespace here, so you cannot see it. This number is how you will map a Pod to its node-side interface in the Easy lab. |
| `UP` / `DOWN` / `UNKNOWN` | The operational state. `UNKNOWN` is normal for `lo` and for bridges and tunnels: they have no physical carrier to measure. |
| `<BROADCAST,MULTICAST,UP,LOWER_UP>` | Flags. `UP` means an administrator enabled the interface (`ip link set X up`). `LOWER_UP` means the link layer has a carrier (a cable is plugged in or, for a veth, the other end is up). `UP` without `LOWER_UP` means "enabled but nothing on the wire". |
| `192.168.215.3/24` | Address and prefix length (section 2.2). |

**Interfaces that exist but are down are the most common silent fault.** A new veth, bridge or dummy interface starts `DOWN`. It has no carrier and drops every packet until you run:

```bash
ip link set dev eth1 up      # enable
ip link set dev eth1 down    # disable (also removes routes that use it)
ip link show dev eth1        # state, MTU, MAC for one interface
ip link set dev eth1 mtu 1400   # change the MTU (section 2.11)
```

`ip link set X down` on an interface also removes its connected route (section 2.4) and fails every connection that used it. Bringing it `up` again re-creates the connected route, but not routes you added by hand through it (the kernel removes those when the interface goes down).

**Under the hood.** The kernel keeps a list of `net_device` objects per network namespace. `ip link` sends a netlink message (`RTM_NEWLINK`, `RTM_SETLINK`) to the kernel to change that list. Nothing in `ip` is stored in a file: if you reboot, everything you typed is gone. Persistent configuration lives in netplan, systemd-networkd, NetworkManager or a CNI plugin (which re-creates the interfaces at Pod start).

### 2.2 IPv4 addressing and CIDR

An IPv4 address is 32 bits, written as four numbers from 0 to 255: `192.168.215.3`. **CIDR notation** adds a **prefix length**: `192.168.215.3/24` means "the first 24 bits are the network part, the last 8 bits are the host part". Two machines are on the same **subnet** (they can talk directly without a router) when the network parts are equal.

The prefix length also tells you how many addresses are in the block:

| CIDR | Netmask | Addresses | Typical use |
|---|---|---|---|
| `/8` | 255.0.0.0 | 16,777,216 | All of `10.0.0.0/8` |
| `/16` | 255.255.0.0 | 65,536 | A whole Pod network, e.g. `192.168.0.0/16` in this guide's labs |
| `/24` | 255.255.255.0 | 256 (254 usable hosts) | One subnet; the default per-node Pod range in many CNIs |
| `/26` | 255.255.255.192 | 64 | Calico's default per-node address block |
| `/30` | 255.255.255.252 | 4 (2 usable) | A point-to-point link |
| `/32` | 255.255.255.255 | 1 | Exactly one host: a host route, a Service IP, a loopback-style address |

Quick maths: addresses in a block = 2 to the power (32 minus prefix). `/24` is 2^8 = 256. `/20` is 2^12 = 4,096. In a normal subnet the first address is the **network address** and the last is the **broadcast address**, so a `/24` has 254 usable hosts. Example: `192.168.215.3/24` is in the block `192.168.215.0` to `192.168.215.255`.

**Private ranges (RFC 1918).** These are never routed on the public internet. You can reuse them in every company:

| Range | Size | Notes |
|---|---|---|
| `10.0.0.0/8` | 16.7 M addresses | Large clouds, kubeadm's default Service range sits inside it |
| `172.16.0.0/12` | 172.16.0.0 to 172.31.255.255 | Docker's default bridge uses `172.17.0.0/16`; kind uses a `172.x` Docker network |
| `192.168.0.0/16` | 65,536 addresses | Home and lab networks; this guide's Pod CIDR |

Other ranges you will see: `127.0.0.0/8` (loopback, "this machine"), `169.254.0.0/16` (link-local: addresses that are valid only on one link; Calico uses `169.254.1.1` as the fake gateway inside Pods), `100.64.0.0/10` (carrier-grade NAT, sometimes used by cloud providers).

**Three different address ranges inside one cluster.** This is the most important sorting exercise in Kubernetes networking, and one of the most common causes of broken installs:

| Range | Who assigns it | Where you see it | Is it on an interface? | Example in this guide's labs |
|---|---|---|---|---|
| **Node network** | Your infrastructure (cloud, DHCP, hypervisor) | `k get nodes -o wide` (INTERNAL-IP), `ip -br a` on the node | Yes, on `eth0` of the node | kind: a `172.x.x.x` Docker address; VMs: whatever the hypervisor gives |
| **Pod CIDR** | The CNI plugin (the range is passed to `kubeadm init --pod-network-cidr`) | `k get pods -o wide` (IP), `ip -br a` **inside the Pod** | Yes, on `eth0` inside each Pod namespace | `192.168.0.0/16` (conventions file); each node gets a slice |
| **Service CIDR** | The API server (`--service-cluster-ip-range`; kubeadm default `10.96.0.0/12`) | `k get svc` (CLUSTER-IP) | **No.** It is virtual: no interface owns it. kube-proxy writes iptables/nftables rules that rewrite it to a Pod IP | The Service data path is covered in a later lesson |

Two rules to remember:

1. The three ranges must **not overlap** with each other or with any network the nodes must reach (office VPN, database subnet). If a node's own IP falls inside the Pod CIDR, the kernel cannot tell "this is a Pod" from "this is a node" and routing becomes ambiguous. Always compare `ip -br a` on a node with the Pod CIDR before you blame the CNI.
2. A Service IP never shows up in `ip -br a` and never answers `ping` by itself. Do not look for it with `ip`. (The Service data path belongs to a later lesson on kube-proxy and iptables.)

Reference page for the three ranges: [Cluster Networking, Kubernetes IP address ranges](https://kubernetes.io/docs/concepts/cluster-administration/networking/).

**Adding and removing addresses by hand:**

```bash
ip addr add 10.10.0.1/24 dev br0        # add (an interface can have many addresses)
ip addr del 10.10.0.1/24 dev br0        # remove
ip -4 addr show dev br0                 # only IPv4 on br0
```

Adding the same address twice fails with `Error: ipv4: Address already assigned.` (REAL OUTPUT (Docker)). Adding an address automatically creates a **connected route** for the whole prefix (section 2.4). That is why `ip addr add 10.10.0.1/24` makes `10.10.0.0/24` reachable and why a wrong prefix length (`/32` instead of `/24`) leaves you with no route to your neighbours.

### 2.3 Layer 2 and layer 3 in one picture

Two ideas keep every later section clear:

- **Layer 2 (L2) moves frames between machines on the same link.** It uses MAC addresses (six bytes, `0a:ae:85:2b:4d:82`). Switches and Linux bridges work here. They know nothing about IP.
- **Layer 3 (L3) moves packets between networks.** It uses IP addresses and routing tables. Routers work here.

A host sends to an IP address in three steps: look up the route (L3: which interface, which next hop), find the MAC address of the next hop (L2: ARP, section 2.5), and put the frame on the wire. Every symptom in this lesson maps to one of those three steps failing.

### 2.4 Routing: `ip route`, the default gateway, `ip route get`

The **routing table** is a list of rules of the form "packets for this destination range go out this interface, optionally through this next hop". The kernel picks the **most specific match**: the rule with the **longest prefix** wins. A `/32` beats a `/24`, which beats `/0`.

**REAL OUTPUT (Docker)** of `ip route`:

```text
$ ip route
default via 192.168.215.1 dev eth0 
192.168.215.0/24 dev eth0 proto kernel scope link src 192.168.215.3 
```

| Piece | Meaning |
|---|---|
| `default via 192.168.215.1 dev eth0` | The **default route** (`0.0.0.0/0`, the shortest possible prefix, so it matches only when nothing else does). "Send everything unknown to the router `192.168.215.1` through `eth0`". `192.168.215.1` is the **default gateway**. |
| `192.168.215.0/24 dev eth0 proto kernel scope link` | A **connected route**. The kernel created it when the address `192.168.215.3/24` was added. `scope link` means "directly reachable on this link, no router needed". No `via`, because there is no next hop. |
| `via X` | The next hop: a router that is itself on a directly connected network. The gateway must be reachable by a connected route, or the kernel refuses the route: `Error: Nexthop has invalid gateway.` (REAL OUTPUT (Docker)). |
| `src 192.168.215.3` | The source address chosen for packets that use this route. |
| `proto kernel` / `proto bird` / `proto static` | Who installed the route. `kernel` = automatic (connected routes). `static` (the default when you type `ip route add`) = by hand. `bird` = Calico's BGP daemon (Calico marks the routes it programs, including its tunnel routes, with it). `boot` = installed by a boot script. This is how you tell CNI-installed routes from your own. |

**Which route will this packet use? `ip route get`.** Reading a long table by eye is slow and error-prone. Ask the kernel instead:

```text
$ ip route get 8.8.8.8
8.8.8.8 via 192.168.215.1 dev eth0 src 192.168.215.3 uid 0 
    cache 
```

**REAL OUTPUT (Docker).** The answer is "via the gateway, out of `eth0`, with source address `192.168.215.3`". On a node, `ip route get <pod-ip>` is the best single command for Pod connectivity: it shows exactly which interface (for example `cali...`, `vxlan.calico`, `tunl0` or `eth0`) and which next hop the node will use. On clusters like this guide's labs (an overlay or BGP CNI, no cloud route table), `via <default-gateway> dev eth0` for a remote Pod IP means no CNI route exists and traffic goes to the router, which does not know your Pod CIDR. (Cloud setups that program the provider's route tables, or VPC-native CNIs, can legitimately send Pod traffic through the default gateway.)

When there is no matching route, `ip route get` fails, and `ping` says `connect: Network is unreachable`:

```text
$ ip netns exec red ip route get 172.31.0.1
RTNETLINK answers: Network is unreachable
$ ip netns exec red ping -c1 -W1 172.31.0.1
ping: connect: Network is unreachable
```

**REAL OUTPUT (Docker).** "Network is unreachable" is an error from the local routing step. It is not a timeout. The packet never left the machine. (A timeout means the packet left and no answer came back: a different problem.)

**Adding and removing routes:**

```bash
ip route add 10.244.1.0/24 via 192.168.1.20          # to a remote range, through a node
ip route add 172.31.0.1/32 via 10.10.0.1             # a single host
ip route add default via 10.10.0.1                   # default gateway
ip route add 10.244.1.0/24 dev cni0                  # directly on an interface (no next hop)
ip route del 10.244.1.0/24                           # delete
ip route replace default via 10.10.0.1               # add or change in one step
ip route show table all                              # include the 'local' and 'broadcast' tables
ip rule                                              # policy-routing rules (which table is used)
```

Adding a route that already exists fails with `RTNETLINK answers: File exists` (REAL OUTPUT (Docker)). Use `ip route replace` to avoid that.

Routes you add by hand are lost on reboot. Persistent routes belong in netplan or the CNI.

**`ip rule` in one paragraph.** The kernel does not have one routing table; it has several (`local`, `main`, `default`, plus numbered ones). `ip rule` decides which table to consult and in which order. By default it is `local` (this machine's own addresses), then `main` (what `ip route` shows), then `default`. CNIs such as Cilium and some cloud setups add their own rules. When `ip route get` and `ip route` disagree, run `ip rule` and `ip route show table all`.

**Related but different: gateway versus next hop versus proxy.** The "gateway" in `default via X` is only a next hop. It does not need to be a separate machine. In Calico's Pod network, the "gateway" `169.254.1.1` inside a Pod is a fake address that nobody owns: the node's veth answers ARP for it (proxy ARP). The route inside the Pod is still `default via 169.254.1.1 dev eth0`. The pattern is the same, the mechanism for answering is different (section 2.13).

### 2.5 The neighbour (ARP) table: `ip neigh`

To put a frame on the wire the kernel needs the MAC address of the next hop. It learns it with **ARP** (Address Resolution Protocol) for IPv4, and **NDP** (Neighbour Discovery) for IPv6, and caches the answers in the **neighbour table**.

```text
$ ip neigh
192.168.215.1 dev eth0 lladdr c6:af:26:ea:fd:21 REACHABLE 
```

**REAL OUTPUT (Docker).** `lladdr` is the link-layer (MAC) address. The last word is the **state**:

| State | Meaning | What to do |
|---|---|---|
| `REACHABLE` | The neighbour answered recently. | Healthy. |
| `STALE` | The entry is old. It is still used and re-checked on the next packet. | Healthy; not a fault. |
| `DELAY` / `PROBE` | The kernel is re-checking an entry. | Transient. |
| `INCOMPLETE` | ARP requests were sent and **no reply has come yet**. | If it stays, the neighbour is down, on another L2 segment, or the interface/bridge port is down. |
| `FAILED` | ARP gave up. No reply. | Same causes as `INCOMPLETE`. The IP exists in the table but has no MAC. |
| `PERMANENT` | You added it by hand with `ip neigh add`. | Rare. |

**REAL OUTPUT (Docker)**, a namespace that tried an address with nobody behind it, and one where the interface was set down:

```text
$ ip -n red neigh
10.10.0.1 dev v-red lladdr 7e:53:27:55:db:ed REACHABLE 
10.10.0.99 dev v-red INCOMPLETE 
10.10.0.12 dev v-red lladdr 62:3b:1d:9a:16:dc REACHABLE 
```

`10.10.0.99` is `INCOMPLETE` because no machine owns it. This is the key diagnostic: **if the neighbour entry for the next hop is `INCOMPLETE` or `FAILED`, the problem is below IP (link down, wrong bridge, wrong subnet), and no amount of route editing will fix it.** If the neighbour is `REACHABLE` and packets still do not arrive, look at routes, forwarding and firewall rules.

Useful commands: `ip neigh show dev eth0`, `ip neigh flush dev eth0` (forget the cache; harmless), `ip -s neigh` (statistics).

### 2.6 Linux bridge: a virtual switch

A **bridge** is a software layer-2 switch inside the kernel. You create it as an interface, and you plug other interfaces into it as **ports** (the kernel calls this "enslaving to a master"). The bridge learns which MAC address lives behind which port (the **forwarding database**, FDB) and forwards frames accordingly. It floods frames for unknown MACs out of all ports.

```bash
ip link add br0 type bridge          # create a bridge named br0
ip link set br0 up                   # bridges start DOWN
ip link set p-red master br0         # plug the interface p-red into br0 as a port
ip link set p-red nomaster           # unplug it
bridge link                          # list ports and their state
bridge fdb show br br0               # list learned MAC addresses and ports
ip -br link show master br0          # alternative: interfaces that are ports of br0
```

A bridge is a normal interface. It can carry an IP address, and that is how the **host joins its own virtual network**: `ip addr add 10.10.0.1/24 dev br0` gives the host an address on the same subnet as the ports, so the host can be the gateway for everything plugged into the bridge. Without an address on `br0`, the namespaces on the bridge can talk to each other (the bridge only switches frames) but not to the host.

**REAL OUTPUT (Docker)** of `bridge link` (two ports in `forwarding` state) and of `bridge fdb show br br0`:

```text
$ bridge link
4: p-red@eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br0 state forwarding priority 32 cost 2 
5: p-blue@eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br0 state forwarding priority 32 cost 2 
$ bridge fdb show br br0
33:33:00:00:00:01 dev br0 self permanent
01:00:5e:00:00:6a dev br0 self permanent
86:e3:70:26:5c:4c dev v-red-br master br0 
...
```

Read it as: `master br0` = this interface is a port of `br0`; `state forwarding` = the port passes traffic (`disabled` or `blocking` would not); the `86:e3:...` line = the bridge learned that this MAC is behind port `v-red-br`. The `@eth0` after the port name is a display quirk: the number after `@if` is the peer's interface index in the *other* namespace, and the tool looks it up in the current one, so the printed name can be wrong. Trust the number (`ip -br link` prints `@if2`), not the name.

Which CNIs use a bridge? Some do (the reference `bridge` plugin, Flannel with its `cni0` bridge, Docker's `docker0`). Calico does **not**: it uses one veth per Pod and a route per Pod, no bridge (section 2.13). `bridge link` on a Calico node prints nothing.

**Under the hood.** The bridge code runs in the kernel (`net/bridge`). Frames received on a port are matched against the FDB by destination MAC. With the `br_netfilter` module loaded, bridged frames can also be passed to iptables (section 2.9).

### 2.7 veth pairs and network namespaces

A **network namespace** (netns) is a private copy of the whole network stack: its own interfaces, addresses, routing table, neighbour table, firewall rules and port numbers. A new namespace starts with only a `lo` interface, and it is `DOWN`. A later lesson covers all eight namespace types; here we only use the network one.

A **veth pair** (virtual Ethernet pair) is a virtual cable with a network card on each end. Whatever goes into one end comes out of the other. You always create the two ends together:

```bash
ip link add v0 type veth peer name v1       # two interfaces, v0 and v1, linked
```

One end alone is useless. The trick that makes containers work: **put one end in the Pod's namespace and leave the other in the node's namespace.** The cable then crosses the namespace wall.

```bash
ip netns add red                            # create /run/netns/red
ip link set v1 netns red                    # move one end into red
ip -n red link set v1 up                    # it arrives DOWN and without any address
ip -n red addr add 10.10.0.11/24 dev v1     # configure it inside
ip netns exec red ping 10.10.0.1            # run any command inside the namespace
ip netns list                               # all named namespaces
ip netns del red                            # delete (also destroys the veth end inside, and with it the other end)
```

Facts to know:

- `ip netns add NAME` creates a file `/run/netns/NAME` that holds a reference to the namespace. Named namespaces are only the ones created this way. A container runtime that creates its namespaces elsewhere (for example under `/var/run/netns/cni-...`) may or may not show up in `ip netns list`.
- Moving an interface into a namespace removes its addresses and sets it `DOWN`. Always re-add the address and bring it up **inside** the namespace.
- When one end of a veth is deleted or its namespace disappears, the other end disappears too. Deleting the namespace is therefore a complete cleanup, but the kernel does it asynchronously: wait a second before you check.
- `ip netns exec NAME CMD` runs one command with the namespace's network stack. It needs root (`sudo`); a non-root user gets a permission error. A missing name gives `Cannot open network namespace "nosuch": No such file or directory`.

**REAL OUTPUT (Docker)** of a veth end seen from both sides:

```text
$ ip -d link show v-red-br         # host side (details: -d)
4: v-red-br@if5: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue master br0 state UP mode DEFAULT group default qlen 1000
    link/ether ce:0d:ab:a4:12:ec brd ff:ff:ff:ff:ff:ff link-netns red promiscuity 1  allmulti 1 ...
    veth 
$ ip -n red -d link show v-red     # inside the namespace
5: v-red@if4: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP mode DEFAULT group default qlen 1000
    link/ether 86:e3:70:26:5c:4c brd ff:ff:ff:ff:ff:ff link-netnsid 0 promiscuity 0  allmulti 0 ...
    veth addrgenmode eui64 ...
```

The two ends point at each other: index `4` says `@if5` and index `5` says `@if4`. `veth` on its own line tells you the interface type. `link-netns red` means "the peer is in namespace red". On a Kubernetes node this is how you pair a Pod with its host interface (Easy lab).

**Related but different: veth versus macvlan, ipvlan and tunnels.** Other virtual devices connect a namespace to the network too, but they work differently. A veth is a point-to-point pipe that needs a bridge or routes on the other side. `macvlan` and `ipvlan` attach a namespace directly to a physical interface with its own MAC or IP. Tunnels (`vxlan`, `ipip`, `wireguard`) carry packets inside other packets (section 2.10). The CNI chooses; the exam asks about Pods, not about picking a device type.

### 2.8 IP forwarding

By default, Linux behaves like a host: it accepts packets addressed to itself and **drops** packets addressed to somebody else. A router must do the opposite: take a packet that arrived on one interface and send it out of another. That behaviour is called **IP forwarding** and it is controlled by a **sysctl** (a kernel parameter) named `net.ipv4.ip_forward`.

```bash
sysctl net.ipv4.ip_forward              # read; prints net.ipv4.ip_forward = 0 or 1
cat /proc/sys/net/ipv4/ip_forward       # same value, as a file (this is where kubeadm reads it)
sudo sysctl -w net.ipv4.ip_forward=1    # set now; lost on reboot
```

Why Kubernetes needs it: a Pod's packet to a Pod on another node leaves the Pod's veth, **arrives at the node**, and the node must forward it out of the node's `eth0` (or the tunnel). The packet is not addressed to the node itself, so the node must forward it. With `ip_forward=0` the node silently drops the packet. There is no ICMP error and no log line. The same thing happens in the other direction when the destination node receives the packet and must forward it from `eth0` to the Pod's veth.

**REAL OUTPUT (Docker)**, two namespaces with the container acting as the router, after forwarding was turned off (the ping gets no answer, no error):

```text
$ sysctl -w net.ipv4.ip_forward=0
net.ipv4.ip_forward = 0
$ ip netns exec pod-a ping -c1 -W1 10.244.2.2 | tail -2
1 packets transmitted, 0 received, 100% packet loss, time 0ms
```

**Make it permanent.** `sysctl -w` changes only the running kernel. The official container-runtime setup page uses a drop-in file:

```bash
cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.ipv4.ip_forward = 1
EOF
sudo sysctl --system          # re-read every config file, in order, and apply
sysctl net.ipv4.ip_forward    # verify
```

Source: [Container runtimes, enable IPv4 packet forwarding](https://kubernetes.io/docs/setup/production-environment/container-runtimes/#prerequisite-ipv4-forwarding-optional).

**Load order decides who wins.** `sysctl --system` reads the `.conf` files from `/etc/sysctl.d`, `/run/sysctl.d`, `/usr/lib/sysctl.d` (and the others it lists) and applies them **sorted by file name**. A later file overrides an earlier one. Digits sort before letters, so `99-x.conf` is applied **before** `k8s.conf`, and `zz-x.conf` is applied after it. **REAL OUTPUT (Docker)** with a second file named `zz-demo.conf` that sets the value to 0:

```text
$ sysctl --system | grep -E "zz-demo|k8s.conf|ip_forward"
* Applying /etc/sysctl.d/k8s.conf ...
* Applying /etc/sysctl.d/zz-demo.conf ...
net.ipv4.ip_forward = 1
net.ipv4.ip_forward = 0
```

The lines are in the order applied; the last value for a key wins. So `k8s.conf` alone is not a guarantee: find overrides with `grep -r ip_forward /etc/sysctl.d/ /etc/sysctl.conf /usr/lib/sysctl.d/`.

| Method | Survives reboot? | Use when |
|---|---|---|
| `sysctl -w key=value` | No | Test a fix right now |
| `echo 1 > /proc/sys/net/ipv4/ip_forward` | No | Same as above, without the `sysctl` tool |
| File in `/etc/sysctl.d/*.conf` + `sysctl --system` | Yes | The permanent fix |
| `sysctl -p` | Reads only `/etc/sysctl.conf` | Does **not** read `/etc/sysctl.d`. Do not use it for drop-in files |

Per-interface forwarding also exists (`net.ipv4.conf.<if>.forwarding`). The global `net.ipv4.ip_forward` sets all of them. IPv6 uses `net.ipv6.conf.all.forwarding` (section 2.12).

**What kubeadm checks.** According to the kubeadm source for v1.37.1, `kubeadm init` and `kubeadm join` run a preflight check that reads `/proc/sys/net/ipv4/ip_forward` and fails when it is not `1`, with an error of this form (message text taken from the source; not run on a live node, see section 11):

```text
[preflight] Some fatal errors occurred:
	[ERROR FileContent--proc-sys-net-ipv4-ip_forward]: /proc/sys/net/ipv4/ip_forward contents are not set to 1
```

If the cluster has an IPv6 Pod or Service CIDR, the same style of check reads `/proc/sys/net/ipv6/conf/default/forwarding`.

### 2.9 `br_netfilter` and `bridge-nf-call-iptables`

**The problem.** A bridge forwards frames at layer 2. By default, iptables (and nftables) rules and connection tracking only see layer-3 packets that *route* through the host, so a frame that is merely *bridged* skips them. Consider a cluster that uses a Linux bridge for Pods on the same node (Flannel's `cni0`, the `bridge` CNI plugin). Pod A sends a packet to the ClusterIP of a Service whose backend is Pod B on the same bridge:

1. The packet is addressed to the bridge's gateway MAC, so the host routes it and the kube-proxy DNAT rule in `PREROUTING` does run: the destination becomes Pod B's IP. The request goes back out of the same bridge to Pod B.
2. Pod B replies to Pod A's IP. Both Pods are on the same bridge, so the bridge switches the reply straight to Pod A at layer 2. The reply never passes iptables or connection tracking, so the reverse translation (source Pod B's IP back to the ClusterIP) never happens.
3. Pod A receives a reply from Pod B's IP, but it sent its request to the ClusterIP. It does not recognise the reply as belonging to that connection and drops it. The connection hangs.

Loading `br_netfilter` and setting `bridge-nf-call-iptables=1` makes bridged frames traverse the iptables hooks too, so the reply is tracked and un-translated. The symptom to remember: the Service works from other nodes (and from Pods whose backend is on another node) and fails only from a Pod on the **same node as the backend**. This is the commonly documented explanation for the requirement; it was not reproduced for this lesson (section 11).

**The mechanism.** The kernel module **`br_netfilter`** makes bridged traffic traverse the iptables hooks. Its behaviour is switched on by sysctls that **only exist after the module is loaded**:

| sysctl | Effect when `1` |
|---|---|
| `net.bridge.bridge-nf-call-iptables` | IPv4 bridged packets pass through iptables |
| `net.bridge.bridge-nf-call-ip6tables` | IPv6 bridged packets pass through ip6tables |
| `net.bridge.bridge-nf-call-arptables` | ARP frames pass through arptables |

When the module is not loaded, reading the sysctl fails with: `sysctl: cannot stat /proc/sys/net/bridge/bridge-nf-call-iptables: No such file or directory`. The file does not exist at all, because the module creates it.

**Load it now and at every boot** (this is the same pair of commands the guide's `env/vm-prereqs.sh` runs):

```bash
sudo modprobe br_netfilter                                   # load now
echo br_netfilter | sudo tee /etc/modules-load.d/k8s.conf    # load at boot (systemd-modules-load)
printf 'net.bridge.bridge-nf-call-iptables=1\nnet.bridge.bridge-nf-call-ip6tables=1\n' | sudo tee -a /etc/sysctl.d/k8s.conf
sudo sysctl --system
lsmod | grep br_netfilter                                    # confirm the module is loaded
```

**Order matters at boot.** `sysctl` settings in a file run early. If the module is not loaded yet, the `net.bridge.*` keys do not exist and the setting is skipped. `/etc/modules-load.d/*.conf` is read by `systemd-modules-load.service`, which runs before `systemd-sysctl.service`, so listing the module there fixes the order. Verify by rebooting, or by `sudo systemctl restart systemd-modules-load systemd-sysctl` and checking the value again.

**What changed in kubeadm.** The older instructions and many blog posts say "kubeadm requires `bridge-nf-call-iptables`". Comparing the kubeadm preflight source across releases: v1.28.0 and v1.29.0 contain a check on `/proc/sys/net/bridge/bridge-nf-call-iptables`; **v1.30.0 and every later release that was read (v1.31 to v1.37.1) do not**. So in v1.37 a missing `br_netfilter` no longer stops `kubeadm init`, and the upstream page for the container runtime lists only IPv4 forwarding. You still load `br_netfilter` when your CNI uses a Linux bridge, or because your distribution's CNI documentation says so. The failure you can still hit is a Service that only fails for clients on the same node as the backend. The old kubeadm error (up to v1.29) looked like this, built from the source's message format (not run):

```text
[ERROR FileContent--proc-sys-net-bridge-bridge-nf-call-iptables]: /proc/sys/net/bridge/bridge-nf-call-iptables does not exist
```

Rule of thumb: ask the question "does my CNI put Pods on a Linux bridge?" If yes, load `br_netfilter` and set the sysctls. If the CNI uses routed veths (Calico) the setting is harmless and costs nothing, so the guide's VM script sets it everywhere.

### 2.10 Overlay versus routed networking

A Pod on node A must reach a Pod on node B. The nodes are connected by the underlay (the real network). There are two ways to carry the Pod's packet across it:

| Model | How it works | Needs from the underlay | Examples | `ip route` on node A for node B's Pod range |
|---|---|---|---|---|
| **Routed (no encapsulation)** | Each node has a route: "B's Pod range is reachable via B's node IP". The packet is sent as is. Routes are programmed by the CNI or learned by **BGP** (Border Gateway Protocol, the routing protocol of the internet). | Nodes on the same L2 subnet, or routers that learn the Pod ranges | Calico in BGP mode, kindnet, cloud-native CNIs | `192.168.x.0/26 via <node-B-IP> dev eth0 proto bird` |
| **Overlay: VXLAN** | The Pod packet is wrapped inside a UDP packet between node IPs and unwrapped on the other side. | Any IP network. Nodes must reach each other on the VXLAN UDP port | Flannel (`flannel.1`), Calico VXLAN (`vxlan.calico`), Cilium | `... via <vtep-IP> dev vxlan.calico onlink` or `dev flannel.1` |
| **Overlay: IP-in-IP** | The Pod packet is wrapped inside another IP packet (protocol 4). | Underlay must allow IP protocol 4 | Calico IPIP (`tunl0`, the default in the v3.33.0 manifest) | `... via <node-B-IP> dev tunl0 proto bird onlink` |
| **WireGuard** | Encrypted tunnel (UDP). | UDP reachability | Calico/Cilium encryption | `dev wg...` |

Overlay trades simplicity for overhead: every packet carries extra headers (next section), and the CPU wraps and unwraps. Routed networking is simpler and faster, but needs an underlay that accepts the routes (cloud route tables, or all nodes in one L2 network, or BGP-speaking routers). The node IPs are the only addresses the underlay needs to know about in an overlay.

The UDP port is part of the debug story: if a firewall between nodes blocks the tunnel port, Pods on the same node work and Pods across nodes fail. The ports in common use are `4789/UDP` (Calico VXLAN, the VXLAN standard) and `8472/UDP` (Flannel VXLAN, and the Linux kernel's default when you do not pass `dstport`).

**REAL OUTPUT (Docker)** of a VXLAN interface created by hand, to show that the kernel itself lowers the MTU when it is created on a 1500-byte underlay:

```text
$ ip link add vxlan0 type vxlan id 42 dev eth0 dstport 4789 local 192.168.215.2 nolearning
$ ip -d link show vxlan0 | head -3
7: vxlan0: <BROADCAST,MULTICAST> mtu 1450 qdisc noop state DOWN mode DEFAULT group default qlen 1000
    link/ether e6:cb:93:04:85:18 brd ff:ff:ff:ff:ff:ff promiscuity 0  allmulti 0 minmtu 68 maxmtu 65535 
    vxlan id 42 fan-map local 192.168.215.2 dev eth0 srcport 0 0 dstport 4789 nolearning ttl auto ageing 300 ...
```

The tunnel interface's MTU is 1450 on a 1500 underlay. The 50 bytes are the VXLAN overhead.

### 2.11 MTU and why encapsulation lowers it

The **MTU** (Maximum Transmission Unit) is the largest packet, in bytes, that an interface can send in one frame. Standard Ethernet is **1500**. Every device on the path has its own MTU, and a packet bigger than the smallest one on the path cannot pass unfragmented.

**Why encapsulation lowers it.** The wrapped packet is *inside* another packet. The outer packet must still fit in 1500 bytes on the underlay, so the inner packet gets less room:

| Encapsulation | Added bytes | Inner (Pod) MTU on a 1500 underlay |
|---|---|---|
| None (routed) | 0 | 1500 |
| IP-in-IP | 20 (outer IPv4 header) | 1480 |
| VXLAN | 50 (inner Ethernet 14 + outer IPv4 20 + UDP 8 + VXLAN 8) | 1450 |
| WireGuard (IPv4) | 60 | 1440 |

A VXLAN payload is a whole Ethernet frame, which is why the inner Ethernet header (14 bytes) counts. The outer Ethernet header is not counted: it is added by the underlay interface and is not part of its MTU.

**The failure mode that confuses people: ping works, big transfers hang.** A ping has 64 bytes of payload and fits in any MTU. A TCP download sends full-size segments (1460 bytes of data in a 1500-byte packet). The TCP handshake (small packets) completes, the first small responses arrive, and then the first full-size packet is too big for the tunnel. Normally the router in the middle replies with an ICMP "fragmentation needed" message and the sender lowers its packet size (**Path MTU Discovery**, PMTUD). If the Pod's interface still says 1500, or ICMP is filtered somewhere, the packets are silently dropped and the transfer **stalls** with no error, just a timeout.

**Test the real MTU of a path with a "do not fragment" ping.** The `-M do` flag sets the DF (don't fragment) bit; `-s N` sets the data size. The packet size on the wire is `N + 28` (20 bytes IP header + 8 bytes ICMP header). So to test whether a path carries a 1400-byte packet, use `-s 1372`:

```bash
ping -c1 -M do -s 1372 10.244.2.2     # 1372 + 28 = 1400 bytes: should work if the path MTU is >= 1400
ping -c1 -M do -s 1472 10.244.2.2     # 1472 + 28 = 1500 bytes: fails if the path MTU is < 1500
```

**REAL OUTPUT (Docker)**, an interface with MTU 1400:

```text
$ ip netns exec pod-a ping -c1 -W1 -M do -s 1372 10.244.2.2 | tail -3
1 packets transmitted, 1 received, 0% packet loss, time 0ms
$ ip netns exec pod-a ping -c1 -W1 -M do -s 1400 10.244.2.2 | tail -3
ping: local error: message too long, mtu=1400
```

`message too long, mtu=1400` also tells you the local MTU. If the MTU problem is in the middle of the path, the local interface accepts the packet and you get either an ICMP reply `Frag needed and DF set (mtu = 1450)` or, if ICMP is blocked, a silent timeout.

**The fix.** Set the MTU of the Pod interfaces so that the Pod MTU is **less than or equal to** (underlay MTU minus encapsulation overhead). The right place is the CNI configuration, not each Pod. For example, on a node: `ip link set dev vxlan.calico mtu 1450` tests the theory quickly, but only the CNI setting survives Pod restarts. The exact CNI setting name differs by product and version (Calico manifest v3.33.0: the `veth_mtu` key in the `calico-config` ConfigMap, default `"0"` = auto-detect, which the manifest passes to `FELIX_IPINIPMTU`, `FELIX_VXLANMTU` and `FELIX_WIREGUARDMTU`; see section 11). TCP derives its segment size (**MSS**) from the interface MTU: MSS = MTU minus 40 (20 IP + 20 TCP header).

### 2.12 IPv6 and dual-stack awareness

IPv6 addresses are 128 bits, written in hexadecimal groups: `fd00:10:244::1/64`. `::` replaces one run of zero groups. A normal IPv6 subnet is a `/64`. Every IPv6-enabled interface automatically gets a **link-local address** starting with `fe80::` that is valid only on that link (you will see one on most interfaces on a node, as in the output below). IPv6 has no broadcast and no ARP: it uses NDP, and `ip neigh` shows those entries too.

```bash
ip -6 addr                                  # IPv6 addresses only
ip -6 route                                 # IPv6 routes
ip -6 addr add fd00:10:244::1/64 dev va-h   # add (fd00::/8 is the IPv6 'private' range, unique-local addresses)
sysctl net.ipv6.conf.all.forwarding         # IPv6 equivalent of ip_forward
```

**REAL OUTPUT (Docker)**: the host side of a veth after adding an IPv6 address next to its IPv4 one:

```text
$ ip -6 addr add fd00:10:244::1/64 dev va-h
$ ip -br a show va-h
va-h@if4         UP             10.244.1.1/24 fd00:10:244::1/64 fe80::70cc:c5ff:fee3:226e/64 
```

**Dual-stack** means a Pod, a node or a Service can have an IPv4 and an IPv6 address at the same time (`status.podIPs` holds both). Dual-stack has been stable since Kubernetes v1.23. For this lesson, three things are enough:

1. All components must agree on the primary IP family, and the CNI, API server and kubelet/cloud provider must all be configured for it. See [Cluster Networking, cluster network types](https://kubernetes.io/docs/concepts/cluster-administration/networking/#cluster-network-ipfamilies).
2. IPv6 has its own forwarding switch, `net.ipv6.conf.all.forwarding`, and kubeadm checks `/proc/sys/net/ipv6/conf/default/forwarding` when your config contains an IPv6 CIDR (from the v1.37.1 source).
3. `ip -6 route get <addr>` works exactly like `ip route get`. Everything in this lesson applies to IPv6 with `-6`.

### 2.13 Reading the interfaces a CNI creates on a node

When you run `ip -br a` on a node, most of the lines are the CNI's work. Here is the translation table:

| Interface | Created by | What it is |
|---|---|---|
| `lo` | Kernel | Loopback. One per namespace. |
| `eth0` (or `ens3`, `enp0s3`) | Hardware / hypervisor | The node's real NIC, with the node IP. Inside a Pod, `eth0` is the Pod's end of its veth pair. |
| `cali<hash>` (e.g. `cali3f0b1c2d4e5`) | Calico | The **node end** of one Pod's veth pair. One per Pod. It has no IP address. A host route `POD-IP dev cali... scope link` points at it. |
| `tunl0` | Calico (IP-in-IP mode) | The IP-in-IP tunnel device. This is the default mode of the `calico.yaml` v3.33.0 manifest (`CALICO_IPV4POOL_IPIP=Always`, read from the manifest), so a kind node in this guide's labs is expected to show `tunl0` and not `vxlan.calico`. |
| `vxlan.calico` | Calico (VXLAN mode) | The VXLAN tunnel device (the node's VTEP, a VXLAN tunnel end point). |
| `wireguard.cali` | Calico (WireGuard mode) | The encrypted tunnel device. |
| `cni0` | Flannel and other CNIs that use the `bridge` plugin | A Linux bridge. All local Pods' veths are ports of it. It has the Pod gateway IP (first address of the node's Pod range). |
| `flannel.1` | Flannel (VXLAN backend) | The VXLAN device. |
| `veth<hash>` | Flannel, kindnet and others | The node end of a Pod's veth pair (CNI-specific names). |
| `lxc<hash>`, `cilium_host`, `cilium_vxlan` | Cilium | Node ends of Pod veths, host device, tunnel. |
| `docker0` | Docker | Docker's default bridge (`172.17.0.0/16`). Not present on containerd-only nodes. |
| `kube-ipvs0` | kube-proxy in ipvs mode | A dummy interface that holds all Service IPs. **Deprecated mode; this guide uses iptables.** |

The Pod side, shown with `kubectl exec <pod> -- ip a` (BusyBox has no `-br`, section 2.1), is always `lo` and `eth0@ifN`. The `N` is the ifindex of the node-side interface. That number is how you map a Pod to its veth, which you do in the Easy lab:

1. In the Pod: `cat /sys/class/net/eth0/iflink` gives the ifindex of the **peer** (the node-side end).
2. On the node: `ip -o link | grep '^<that number>:'` shows the node-side name (`cali...`, `veth...`, `lxc...`).
3. Cross-check on the node: `ip route get <pod-ip>` shows `dev <that name>` (routed CNIs) or `ip -br link show master cni0` lists it (bridge CNIs).

The official page [Cluster Networking](https://kubernetes.io/docs/concepts/cluster-administration/networking/) describes the model: every Pod gets its own IP, and Pods can reach each other without NAT. The interfaces above are how a given CNI implements that promise.

### 2.14 Putting it together: what happens when Pod A talks to Pod B

**Same node, routed CNI (Calico):** Pod A's `eth0` sends the packet to its default gateway `169.254.1.1`. The node's `cali` interface answers the ARP request itself (proxy ARP), so Pod A learns a MAC address for the fake gateway. The node receives the frame, looks up `ip route` for Pod B's IP, finds `POD-B-IP dev caliB scope link`, and forwards to Pod B. This is **forwarding on the node**, and it needs `ip_forward=1`.

**Same node, bridge CNI (Flannel):** Pod A's veth is a port of `cni0`. The bridge switches the frame to Pod B's port at layer 2. No routing, no forwarding.

**Different node, routed:** the node looks up `ip route`, finds `POD-B-RANGE via NODE-B-IP dev eth0`, forwards the packet out of `eth0`. Node B receives it, finds the local `cali...` route and delivers. Both nodes need `ip_forward=1`.

**Different node, overlay:** the route says `POD-B-RANGE ... dev vxlan.calico` (or `flannel.1`, `tunl0`). The tunnel device wraps the packet in UDP to node B's IP and sends it out of `eth0`. Node B's tunnel device unwraps it and routes it locally.

In every case: **a missing interface, missing address, missing route, disabled forwarding, or too-small MTU** is the cause of the failure. That is the reason this lesson is about those five things.

## 3. How it works (diagram)

Two namespaces on one node, joined by a bridge, and a route to the Pod range on the other node:

```text
 NODE A  (eth0 = 192.168.1.10/24, ip_forward = 1)
+----------------------------------------------------------------------+
|  netns "red"                         netns "blue"                    |
|  +----------------------+            +----------------------+        |
|  | v-red  10.10.0.11/24 |            | v-blue 10.10.0.12/24 |        |
|  | default via 10.10.0.1|            | default via 10.10.0.1|        |
|  +-----------+----------+            +-----------+----------+        |
|              |  veth pair                        |  veth pair        |
|==============|===================================|==== namespace wall|
|  +-----------+----------+            +-----------+----------+        |
|  | p-red (bridge port)  |            | p-blue (bridge port) |        |
|  +-----------+----------+            +-----------+----------+        |
|              |                                   |                   |
|     +--------+-----------------------------------+--------+          |
|     | br0  10.10.0.1/24  (L2 switch + the host's own IP)  |          |
|     +------------------------+----------------------------+          |
|                              | routing decision                      |
|     ip route: 10.10.1.0/24 via 192.168.1.20 dev eth0                 |
|                              |                                       |
|                       +------+------+                                |
|                       |    eth0     |                                |
|                       +------+------+                                |
+------------------------------|---------------------------------------+
                               |  underlay network
+------------------------------|---------------------------------------+
|                       +------+------+                                |
|                       |    eth0     |  192.168.1.20/24               |
|                       +------+------+                                |
|  NODE B  (Pod range 10.10.1.0/24, ip_forward = 1, route back:        |
|           10.10.0.0/24 via 192.168.1.10)                             |
|           -> forwards to its own bridge or veth -> the remote Pod    |
+----------------------------------------------------------------------+
```

Walkthrough:

1. `red` sends a packet to `10.10.0.12`. That address is in its own `/24`, so the connected route applies. ARP finds the MAC address of `blue` through the veth and the bridge. The bridge switches the frame at layer 2. No routing and no forwarding is involved.
2. `red` sends a packet to `10.10.1.7` (a Pod on node B). The only matching route in `red` is `default via 10.10.0.1`. The frame goes to `br0`, which is the host's own interface, so the packet now **arrives at the host**.
3. The packet is not addressed to the host, so the host must forward it. This works only when `net.ipv4.ip_forward = 1`.
4. The host's routing table has `10.10.1.0/24 via 192.168.1.20 dev eth0`, so the packet leaves through `eth0` toward node B. Node B must have the mirror-image route back and forwarding enabled too, or the reply is lost.
5. In an overlay CNI the `dev eth0` in that route is `dev tunl0`, `dev vxlan.calico` or `dev flannel.1`: the packet is wrapped and sent to `192.168.1.20` as UDP, and the MTU shrinks by the overhead (section 2.11).

## 4. Commands and YAML you must produce fast

### 4.1 Imperative commands

The 15 commands below are enough for almost any Linux-networking diagnosis on a node. Run them as root (`sudo -i`).

```bash
ip -br a                                   # every interface with its addresses, one line each
ip -br link                                # state and MAC of every interface
ip route                                   # the routing table
ip route get 10.244.1.5                    # which interface and next hop would a packet to this IP use?
ip neigh                                   # ARP/NDP cache: is the next hop's MAC known?
ip link set dev eth1 up                    # enable an interface (down to disable)
ip addr add 10.10.0.1/24 dev br0           # add an address (also adds the connected route)
ip route add 10.10.1.0/24 via 192.168.1.20 # route a remote range through another node
ip netns add red                           # create a network namespace
ip netns exec red ip -br a                 # run a command inside it (short: ip -n red -br a)
ip link add v0 type veth peer name v1      # create a veth pair
ip link set v1 netns red                   # move one end into the namespace
bridge link                                # bridge ports (empty on routed CNIs such as Calico)
sysctl net.ipv4.ip_forward                 # is this machine allowed to forward packets?
sudo sysctl -w net.ipv4.ip_forward=1       # turn it on now (not persistent)
```

**Build two network namespaces joined by a bridge and ping between them: six typed lines, thirteen commands.** The count by hand: 1 bridge add, 1 bridge up, 2 namespace adds, 2 veth adds, 2 plug-in-and-up, 2 inner ups, 2 addresses, 1 ping. Every one of these is needed (a new bridge, port or inner interface starts `DOWN`, and an interface needs an address), so "10 commands or fewer" is not reachable when typed one by one. The `for` loop is what brings it to six lines to type or paste, which is the fast form to practise. Copy and paste as root:

```bash
ip link add br0 type bridge
ip link set br0 up
for n in red blue; do ip netns add $n; ip link add v-$n netns $n type veth peer name p-$n; ip link set p-$n master br0 up; ip -n $n link set v-$n up; done
ip -n red  addr add 10.10.0.11/24 dev v-red
ip -n blue addr add 10.10.0.12/24 dev v-blue
ip netns exec red ping -c2 10.10.0.12
```

What each line does:

| Line | Effect |
|---|---|
| 1-2 | Create the virtual switch and turn it on. A `DOWN` bridge forwards nothing. |
| 3 | For each name: create the namespace; create the veth pair with one end **already inside** the namespace (`netns $n` before `type veth`) and the other end named `p-$n` on the host; plug the host end into `br0` and bring it up (`master br0 up` in one command); bring up the inner end. |
| 4-5 | Give each inner interface an address in the same `/24`. The connected route appears with the address. |
| 6 | Ping from inside `red` to `blue`. |

**Do not put `master br0` after `peer name p-$n`.** In a test with iproute2 6.1.0, `ip link add ... type veth peer name p-red master br0` was accepted without an error, but did **not** plug the port into the bridge (`bridge link` was empty, the ping failed with 100% loss). Use the separate `ip link set p-$n master br0` as in line 3.

**REAL OUTPUT (Docker)** of the block above, plus `ip netns list` and `ip -br link show master br0`:

```text
PING 10.10.0.12 (10.10.0.12) 56(84) bytes of data.
64 bytes from 10.10.0.12: icmp_seq=1 ttl=64 time=0.067 ms
64 bytes from 10.10.0.12: icmp_seq=2 ttl=64 time=0.056 ms

--- 10.10.0.12 ping statistics ---
2 packets transmitted, 2 received, 0% packet loss, time 1014ms
rtt min/avg/max/mdev = 0.056/0.061/0.067/0.005 ms
$ ip netns list
red (id: 1)
```

### 4.2 The "declarative" files for this topic

This topic has no Kubernetes YAML to produce. The declarative objects here are two small files that make the node settings survive a reboot, plus the one Deployment used in the Easy lab. Every setting is explained.

`/etc/sysctl.d/k8s.conf`: read by `sysctl --system` (and by `systemd-sysctl` at boot):

```ini
# net.ipv4.ip_forward: allow the node to forward packets that are not for itself.
#   0 (kernel default on a plain server) = drop them. Pods on other nodes become unreachable.
#   1 = forward. kubeadm preflight fails when this is not 1.
net.ipv4.ip_forward = 1
# net.bridge.bridge-nf-call-iptables: send bridged IPv4 frames through iptables.
#   Only exists after "modprobe br_netfilter". Needed when the CNI uses a Linux bridge (cni0).
#   Setting it before the module is loaded is skipped at boot (see /etc/modules-load.d/k8s.conf).
net.bridge.bridge-nf-call-iptables = 1
# Same for IPv6 bridged frames. Harmless on an IPv4-only cluster.
net.bridge.bridge-nf-call-ip6tables = 1
```

`/etc/modules-load.d/k8s.conf`: read by `systemd-modules-load.service` at boot, one module name per line:

```text
overlay
br_netfilter
```

(`overlay` is the filesystem module that container images use; it is covered in T1.11. `br_netfilter` is the one for this lesson.)

The Deployment used in the Easy lab, produced the fast way (`busybox:1.36` includes a BusyBox `ip` applet, which `nginx` images do not; it supports `ip a`, `ip route` and `ip link show`, but not `-br`, section 2.1):


**Goal:** follow one Pod from `kubectl` down to the node-side interface and the routes, then break and repair cross-node traffic by switching forwarding off on one node.

**Environment:** kind (cluster `lab`, context `kind-lab`: 1 control plane + 2 workers, Calico v3.33.0, created by `env/kind-up.sh`). kind nodes are Docker containers, so `docker exec lab-worker <cmd>` here is the same as running `<cmd>` in a root shell on the node. ```bash

| Symptom | What you will see | Cause | Fix (command) |
|---|---|---|---|
| Pods on different nodes cannot talk (same-node Pods are fine) | `ping`/`curl` from a Pod to a remote Pod IP: no reply, `100% packet loss` or a timeout. `ip route get <remote-pod-ip>` on the node shows `via <default-gateway> dev eth0`, not a tunnel or a node IP. | No route to the remote Pod CIDR: the CNI is not running or crashed on a node, or was installed with a different Pod CIDR than `--pod-network-cidr` | `k -n kube-system get pods -o wide` to find the CNI Pod on each node; `k -n kube-system logs <cni-pod>`; fix the CNI (restart it or reinstall with the right CIDR). Prove with `ip route get <remote-pod-ip>` on both nodes. |
| Cross-node traffic fails although every route is right | Sender `ip route get` is correct. Receiver `ip route get` is correct. Ping still gets nothing, **and no ICMP error**. | `net.ipv4.ip_forward = 0` on a node on the path, or a later file in `/etc/sysctl.d` overrides it | `sysctl net.ipv4.ip_forward` on **each** node; `grep -r ip_forward /etc/sysctl.d/ /etc/sysctl.conf /usr/lib/sysctl.d/`; fix the file; `sysctl --system` |
| Ping works, large transfers hang | `ping` OK; `curl` connects and then stalls; `ping -M do -s 1472 <ip>` fails or times out; `ip link show dev <if>` (look for `mtu N`) shows a Pod MTU that is higher than the tunnel can carry | MTU mismatch: Pod MTU (1500) is higher than the tunnel can carry (1480 for IP-in-IP, 1450 for VXLAN), and ICMP "fragmentation needed" is dropped or never sent | Find the working size with `ping -M do -s <N> <ip>` (size on wire = N + 28). Lower the MTU in the CNI configuration; test with `ip link set dev <if> mtu 1450` |
| kubeadm: bridge sysctl missing (kubeadm up to v1.29; or a Service that fails only for same-node clients on a bridge CNI) | `[ERROR FileContent--proc-sys-net-bridge-bridge-nf-call-iptables]: /proc/sys/net/bridge/bridge-nf-call-iptables does not exist` (message format from the kubeadm source; kubeadm v1.30 and later no longer run this check). `sysctl net.bridge.bridge-nf-call-iptables` prints `sysctl: cannot stat /proc/sys/net/bridge/bridge-nf-call-iptables: No such file or directory`. | `br_netfilter` is not loaded, so the sysctl does not exist | `sudo modprobe br_netfilter`; `echo br_netfilter \| sudo tee /etc/modules-load.d/k8s.conf`; add `net.bridge.bridge-nf-call-iptables = 1` to `/etc/sysctl.d/k8s.conf`; `sudo sysctl --system` |

### 6.1 Walk-through: Pods on different nodes cannot talk

Run the steps in this order. Each step is a yes/no question, and the first "no" is your fault.

1. **Is it really cross-node?** `k get pods -o wide` and look at the NODE column. Test Pod to Pod on the same node first. If same-node works and cross-node fails, continue.
2. **Is the CNI running everywhere?** `k -n kube-system get pods -o wide | grep -E 'calico|flannel|cilium|weave|kindnet'`. One CNI Pod per node, all `Running` and `READY 1/1`. A missing or crash-looping CNI Pod on one node explains the whole symptom.
3. **Does the sender have a route?** On the node of the source Pod: `ip route get <dest-pod-ip>`. Read the answer:
   - `via <other-node-ip> dev tunl0 / vxlan.calico / flannel.1`: good, a tunnel route exists.
   - `via <other-node-ip> dev eth0 proto bird`: good, a routed (BGP) route exists.
   - `via <default-gateway> dev eth0`: **bad on an overlay or BGP CNI like this guide's labs.** The kernel has no route to the Pod range and uses the default gateway, which knows nothing about Pods. (On a cloud setup that uses the provider's route tables, the default gateway can be the correct path; then check the cloud routes instead.)
4. **Does the receiver have a route back?** Repeat step 3 on the other node, with the source Pod's IP. Return traffic needs a route as well.
5. **Is forwarding on?** `sysctl net.ipv4.ip_forward` on both nodes. Must be `1`.
6. **Is the underlay up?** From node A: `ping <node-B-ip>`. If that fails, the problem is below Kubernetes (firewall, cloud security group, a blocked tunnel UDP port 4789 or 8472, or IP protocol 4 for IP-in-IP).
7. **Is it size-dependent?** Small ping works, large fails: go to 6.2.

### 6.2 Walk-through: ping works, large transfers hang

1. Reproduce with a real size: `k exec <pod> -- wget -qO- http://<dest>/bigfile` or `curl` stalls, while `ping -c1 <dest>` is fine. A stall after a successful connect is the signature.
2. Read the MTU of every hop: `ip -br link` shows only state; use `ip link show dev <if>` (look for `mtu N`) on the Pod's `eth0` (`k exec <pod> -- ip link show eth0`), on the node's `cali...`/`cni0` veth, and on the tunnel device (`tunl0`, `vxlan.calico`, `flannel.1`), and on the node's `eth0`.
3. Rule: Pod MTU must be less than or equal to (tunnel MTU), and the tunnel MTU less than or equal to (underlay MTU minus overhead). Overheads are in section 2.11.
4. Measure: `ping -c1 -M do -s 1472 <ip>` (1500 on the wire) then smaller sizes, until it passes. The largest passing `N` plus 28 is the real path MTU.
5. Fix: set the MTU in the CNI configuration so that every new Pod gets it. For a quick test only: `ip link set dev <if> mtu <value>`.

### 6.3 Walk-through: bridge sysctl missing

1. `sysctl net.bridge.bridge-nf-call-iptables`. If it prints `cannot stat ... No such file or directory`, the module is not loaded.
2. `lsmod | grep br_netfilter`. Empty = not loaded.
3. `sudo modprobe br_netfilter`; the sysctl now exists. Set it to `1`.
4. Make it permanent twice: the module in `/etc/modules-load.d/k8s.conf`, the sysctl in `/etc/sysctl.d/k8s.conf`. If you only do the second one, it is skipped at boot because the key does not exist yet.
5. Check: `sudo sysctl --system | grep bridge`, then reboot (or `systemctl restart systemd-modules-load systemd-sysctl`) and read the value again.

**Task:** In namespace `lab-t107`, Deployment `web` has four Pods. For each Pod, find the interface on its node that is the node-side end of the Pod's veth pair. Write `~/lab/t107/pod-veth.txt` with exactly four lines, each in the form `<pod-name> <node-name> <pod-ip> <interface-name>` (single spaces, no `@ifN` suffix). Use only `k` and `docker exec <node>` (the exam equivalent is `ssh <node>` then `sudo -i`).

<details>
<summary>Hint 1</summary>

Inside the Pod, `/sys/class/net/eth0/iflink` holds the interface index of the other end of the pair. `k exec` can `cat` it (busybox has `cat`).

</details>

<details>
<summary>Hint 2</summary>

On the node, `ip -o link` prints one line per interface and starts with the index and a colon (`12: cali...@if4: ...`). Match the index at the start of the line.

</details>

<details>
<summary>Hint 3</summary>

Get the node with `-o jsonpath='{.spec.nodeName}'`. The kind node name is also the Docker container name. Strip the `@ifN:` part with `awk` (`sub(/@.*/,"",$2)`).

</details>

<details>
<summary>Solution</summary>

Why this works: a veth pair is two interfaces that point at each other. Inside the Pod, `iflink` tells you the index of the other end. Interface indexes are unique per network namespace, and the other end lives in the node's namespace, so the index identifies one interface in `ip -o link` on that node.

```bash
: > ~/lab/t107/pod-veth.txt
for P in $(k -n lab-t107 get pod -l app=web -o name); do
  N=$(k -n lab-t107 get $P -o jsonpath='{.spec.nodeName}')
  IP=$(k -n lab-t107 get $P -o jsonpath='{.status.podIP}')
  IDX=$(k -n lab-t107 exec $P -- cat /sys/class/net/eth0/iflink)
  IF=$(docker exec $N ip -o link | awk -v i="$IDX:" '$1==i {sub(/@.*/,"",$2); print $2}')
  echo "${P#pod/} $N $IP $IF" >> ~/lab/t107/pod-veth.txt
done
cat ~/lab/t107/pod-veth.txt
```

The loop: `-o name` prints `pod/web-...`, so `${P#pod/}` removes the prefix for the file. `$1==i` compares the first field (`12:`) with the index plus a colon. The `sub` removes everything from `@`, so `cali3f0b1c2d4e5@if4:` becomes `cali3f0b1c2d4e5`.

Cross-check by hand for one Pod: `docker exec <node> ip route get <pod-ip>` must print `dev <that interface>`.

EXPECTED OUTPUT (not captured) of `cat ~/lab/t107/pod-veth.txt`:

```text
web-<hash>-<id1> lab-worker  192.168.<x>.<y> cali<hash1>
web-<hash>-<id2> lab-worker  192.168.<x>.<y> cali<hash2>
web-<hash>-<id3> lab-worker2 192.168.<x>.<y> cali<hash3>
web-<hash>-<id4> lab-worker2 192.168.<x>.<y> cali<hash4>
```

</details>

**Verification** (each line must print `PASS`; any `FAIL` means that Pod's interface is wrong):

```bash

while read P N IP IF; do
  docker exec $N ip route get $IP | grep -q "dev $IF " && echo "PASS $P" || echo "FAIL $P"
done < ~/lab/t107/pod-veth.txt
```

Why it can fail: `ip route get <pod-ip>` names the interface the kernel really uses for that Pod, so a wrong index, a swapped node or a typo in `$IF` is caught. (On a CNI that uses a bridge, `dev` would be the bridge; this lab assumes the guide's Calico cluster.)

### 7.2 Medium: two namespaces, a bridge, and a route to the host

**Environment:** linux-vm (Ubuntu 24.04 or newer), as root (`sudo -i`).

**Setup:**

```bash
mkdir -p ~/lab/t107
ip netns list            # must print nothing
ip link show br0 2>&1    # must print: Device "br0" does not exist.
iptables -S FORWARD 2>&1 | head -1   # see the note below
```

**Firewall note.** If this VM has Docker installed (or another firewall that sets the iptables `FORWARD` policy to `DROP`) and the `br_netfilter` module is loaded (`lsmod | grep br_netfilter`), frames switched by `br0` pass through the `FORWARD` chain (section 2.9) and the `red`/`blue` pings can fail with 100% loss even though everything is built correctly. The first line above prints `-P FORWARD DROP` in that case. For the lab only, allow the bridge: `iptables -I FORWARD -i br0 -o br0 -j ACCEPT`, and remove it in the cleanup with `iptables -D FORWARD -i br0 -o br0 -j ACCEPT`. On a plain Ubuntu VM the policy is `ACCEPT` and no rule is needed. (This workaround was not run on a VM, section 11.)

**Task:** Build this network with `ip` commands, from scratch:

1. Namespaces `red` and `blue`, joined by a Linux bridge `br0`. `br0` has the address `10.10.0.1/24` and is up. `red` has `10.10.0.11/24` on interface `v-red`, `blue` has `10.10.0.12/24` on `v-blue`. The host ends of the veth pairs are `p-red` and `p-blue` and are ports of `br0`.
2. `red` and `blue` can ping each other and `10.10.0.1`.
3. Create a dummy interface `dummy0` on the host with the address `172.31.0.1/32` (it stands for "a network the host has and the namespaces do not know").
4. Make `red` reach `172.31.0.1` with a **specific `/32` route** via `10.10.0.1`, and make `blue` reach it with a **default route** via `10.10.0.1`.
5. Save the output of `ip -n red route get 172.31.0.1` to `~/lab/t107/route-get.txt`.

<details>
<summary>Hint 1</summary>

Use the six-line recipe from section 4.1 and then add `10.10.0.1/24` to `br0`. A veth moved or created inside a namespace needs `ip -n <ns> link set <if> up`; the host end needs `master br0` and `up`.

</details>

<details>
<summary>Hint 2</summary>

Before you add any route, `ip netns exec red ping -c1 -W1 172.31.0.1` should fail with `Network is unreachable`. That error means "no route", not "no answer". Adding a route is the cure.

</details>

<details>
<summary>Hint 3</summary>

`ip link add dummy0 type dummy; ip addr add 172.31.0.1/32 dev dummy0; ip link set dummy0 up`. The host is the destination here, so **no forwarding is needed**: a packet addressed to one of the host's own addresses is delivered locally.

</details>

<details>
<summary>Solution</summary>

```bash
ip netns add red; ip netns add blue
ip link add br0 type bridge
ip addr add 10.10.0.1/24 dev br0          # the host's own address on the virtual network
ip link set br0 up
for n in red blue; do ip link add v-$n netns $n type veth peer name p-$n; ip link set p-$n master br0 up; ip -n $n link set v-$n up; done
ip -n red  addr add 10.10.0.11/24 dev v-red
ip -n blue addr add 10.10.0.12/24 dev v-blue
ip link add dummy0 type dummy; ip addr add 172.31.0.1/32 dev dummy0; ip link set dummy0 up
ip -n red  route add 172.31.0.1/32 via 10.10.0.1
ip -n blue route add default via 10.10.0.1
ip -n red route get 172.31.0.1 | tee ~/lab/t107/route-get.txt
```

Why each step: the bridge address is both the bridge's identity on the subnet and the next hop for the namespaces. The next hop must be on a connected subnet (`10.10.0.0/24`), otherwise `ip route add` fails with `Error: Nexthop has invalid gateway.` The two route styles do the same job here; a `/32` is the most specific route and wins over any default route, while the default route catches everything that has no better match.

**REAL OUTPUT (Docker)** of `ip -n red route get 172.31.0.1` and of `ip -n blue route get 172.31.0.1` after the routes exist:

```text
172.31.0.1 via 10.10.0.1 dev v-red src 10.10.0.11 uid 0 
    cache 
172.31.0.1 via 10.10.0.1 dev v-blue src 10.10.0.12 uid 0 
    cache 
```

The return path needs no extra route: the reply to `10.10.0.11` is delivered on the connected route `10.10.0.0/24 dev br0` of the host.

Stretch (not required, not captured): to reach beyond the host (for example the internet) the namespaces would also need `net.ipv4.ip_forward=1` on the host and a source NAT rule, because `10.10.0.0/24` is unknown outside. That is the same job a CNI does with masquerade rules for Pod traffic leaving the cluster.

</details>

**Verification** (every line must print `PASS`):

```bash
t(){ if "$@" >/dev/null 2>&1; then echo "PASS: $*"; else echo "FAIL: $*"; fi; }
t ip netns exec red  ping -c1 -W1 10.10.0.12
t ip netns exec blue ping -c1 -W1 10.10.0.11
t ip netns exec red  ping -c1 -W1 10.10.0.1
t ip netns exec red  ping -c1 -W1 172.31.0.1
t ip netns exec blue ping -c1 -W1 172.31.0.1
grep -q 'via 10.10.0.1 dev v-red' ~/lab/t107/route-get.txt && echo PASS-file || echo FAIL-file
test "$(ip -br link show master br0 | wc -l)" = 2 && echo PASS-ports || echo FAIL-ports
ip -n red route | grep -q '^172.31.0.1 via 10.10.0.1' && echo PASS-red-32 || echo FAIL-red-32
ip -n blue route | grep -q '^default via 10.10.0.1' && echo PASS-blue-default || echo FAIL-blue-default
```

Each check fails if you forget to bring an interface up, plug a port in, add a route or use the wrong next hop. The solution was run in a Docker container for the two cross pings, the two pings to `172.31.0.1`, the route file and the port count (REAL OUTPUT (Docker): all `PASS`), not on a VM. The ping to `10.10.0.1` and the two `grep` route checks are plain re-statements of the same configuration and were not run separately (section 11).

**Cleanup:**

```bash
ip netns del red; ip netns del blue; ip link del br0; ip link del dummy0
iptables -D FORWARD -i br0 -o br0 -j ACCEPT 2>/dev/null   # only if you added the firewall workaround
sleep 1; ip -br link; ip netns list
rm -rf ~/lab/t107
```

The last two listings should show only `lo` and the VM's normal NIC, and nothing from `ip netns list`.

### 7.3 Break-fix: cross-node Pod traffic fails

**Environment:** linux-vm, as root, on an Ubuntu VM. The setup script needs the file name `/etc/sysctl.d/k8s.conf` to be free. If the VM was prepared with `env/vm-prereqs.sh` (which creates that file), first run `mv /etc/sysctl.d/k8s.conf /etc/sysctl.d/k8s.conf.bak` (sysctl ignores files that do not end in `.conf`); the cleanup moves it back. The VM plays the part of a worker node that must forward traffic between two "Pod" networks: namespace `pod-a` (`10.244.1.2/24`, gateway `10.244.1.1` on the VM) and `pod-b` (`10.244.2.2/24`, gateway `10.244.2.1` on the VM). On a real cluster the same fault stops a Pod on one node from reaching a Pod on another node whenever a node on the path refuses to forward.

**Setup** (save as `~/lab/t107/setup.sh`, run once):

```bash
mkdir -p ~/lab/t107
cat > ~/lab/t107/setup.sh <<'EOS'
test ! -e /etc/sysctl.d/k8s.conf || { echo "k8s.conf already exists: mv it to k8s.conf.bak first (see Environment)"; exit 1; }
sysctl -n net.ipv4.ip_forward > ~/lab/t107/orig-forward
echo 'net.ipv4.ip_forward = 1' > /etc/sysctl.d/k8s.conf
sysctl --system >/dev/null
for i in a b; do
  n=$([ $i = a ] && echo 1 || echo 2)
  ip netns add pod-$i
  ip link add v$i netns pod-$i type veth peer name v$i-h
  ip addr add 10.244.$n.1/24 dev v$i-h; ip link set v$i-h up
  ip -n pod-$i addr add 10.244.$n.2/24 dev v$i; ip -n pod-$i link set v$i up; ip -n pod-$i link set lo up
  ip -n pod-$i route add default via 10.244.$n.1
done
EOS
bash ~/lab/t107/setup.sh
ip netns exec pod-a ping -c1 -W1 10.244.2.2     # must work before you break it
```

**Fault injection** (`break.sh`; run it as root. Reading it spoils the exercise, so paste it without studying it):

```bash
cat > ~/lab/t107/break.sh <<'EOS'
sysctl -w net.ipv4.ip_forward=0 >/dev/null
echo 'net.ipv4.ip_forward = 0' > /etc/sysctl.d/zz-lab.conf
EOS
bash ~/lab/t107/break.sh
```

**Task:** `pod-a` can no longer reach `pod-b`. Find the cause and fix it **permanently**: after your fix, traffic must work now, and must still work after `sysctl --system` is re-applied (what a reboot would do). Do not delete `/etc/sysctl.d/k8s.conf`, and do not change the namespaces, addresses or routes: they are correct.

<details>
<summary>Hint 1</summary>

Check the layers in order. `ip -n pod-a route get 10.244.2.2`, `ip -n pod-a neigh`, `ip route`. If routes and neighbours are fine, the packet reaches the VM and then disappears. What decides whether the VM forwards packets?

</details>

<details>
<summary>Hint 2</summary>

`sysctl net.ipv4.ip_forward`. If you change it with `sysctl -w` the ping works, but run `sudo sysctl --system` and it breaks again. Something re-applies the wrong value.

</details>

<details>
<summary>Hint 3</summary>

`sysctl --system` applies files in file-name order and the last value wins. Search all places: `grep -r ip_forward /etc/sysctl.d/ /etc/sysctl.conf /usr/lib/sysctl.d/`. Which file sorts after `k8s.conf`?

</details>

<details>
<summary>Solution</summary>

**Diagnose, bottom-up.**

```bash
ip netns exec pod-a ping -c1 -W1 10.244.2.2     # 100% packet loss, no error text
ip -n pod-a route get 10.244.2.2                 # via 10.244.1.1 dev va ...: the route is right
ip -n pod-a neigh                                # 10.244.1.1 ... REACHABLE: layer 2 is fine
ip route | grep 10.244                           # both connected routes exist on the VM
sysctl net.ipv4.ip_forward                       # 0  <-- the VM drops packets that are not for itself
```

Routes and neighbours are healthy, and the ping dies silently: that points to forwarding.

**Quick (volatile) fix, to confirm the diagnosis:**

```bash
sysctl -w net.ipv4.ip_forward=1
ip netns exec pod-a ping -c1 -W1 10.244.2.2     # works
sysctl --system >/dev/null; sysctl -n net.ipv4.ip_forward    # 0 again!
```

The value went back to `0` because a file applied **after** `k8s.conf` sets it to `0`.

**Find and fix the cause:**

```bash
grep -r ip_forward /etc/sysctl.d/ /etc/sysctl.conf /usr/lib/sysctl.d/
# /etc/sysctl.d/k8s.conf:net.ipv4.ip_forward = 1
# /etc/sysctl.d/zz-lab.conf:net.ipv4.ip_forward = 0     <-- sorts after k8s.conf, so it wins
rm /etc/sysctl.d/zz-lab.conf
sysctl --system >/dev/null
sysctl -n net.ipv4.ip_forward                    # 1
```

Why this is the right fix: `k8s.conf` already says `1`; the real fault is the override, so we remove the override (or change its value to `1`). Editing `k8s.conf` would change nothing, because the later file still wins.

**REAL OUTPUT (Docker)** of the diagnosis and the persistence proof (a container, not a VM):

```text
10.244.2.2 via 10.244.1.1 dev va src 10.244.1.2 uid 0 
    cache 
10.244.1.1 dev va lladdr ca:b1:df:62:5a:6c REACHABLE 
10.244.1.0/24 dev va-h proto kernel scope link src 10.244.1.1 
10.244.2.0/24 dev vb-h proto kernel scope link src 10.244.2.1 
net.ipv4.ip_forward = 0
...
/etc/sysctl.d/k8s.conf:net.ipv4.ip_forward = 1
/etc/sysctl.d/zz-lab.conf:net.ipv4.ip_forward = 0
/etc/sysctl.conf:#net.ipv4.ip_forward=1
```

On a real cluster: the sender's `ip route get` and the receiver's `ip route get` both look right, the ping gets nothing, and you must run `sysctl net.ipv4.ip_forward` on every node on the path.

</details>

**Verification** (all must print `PASS`; the persistence check simulates a reboot):

```bash
t(){ if "$@" >/dev/null 2>&1; then echo "PASS: $*"; else echo "FAIL: $*"; fi; }
t ip netns exec pod-a ping -c1 -W1 10.244.2.2
t ip netns exec pod-b ping -c1 -W1 10.244.1.2
test "$(sysctl -n net.ipv4.ip_forward)" = 1 && echo PASS-live || echo FAIL-live
sysctl -w net.ipv4.ip_forward=0 >/dev/null; sysctl --system >/dev/null
test "$(sysctl -n net.ipv4.ip_forward)" = 1 && echo PASS-persist || echo FAIL-persist
grep -q '^net.ipv4.ip_forward *= *1' /etc/sysctl.d/k8s.conf && echo PASS-k8s-conf || echo FAIL-k8s-conf
```

`PASS-persist` fails if any later file still sets the value to 0. If you only ran `sysctl -w net.ipv4.ip_forward=1`, `PASS-live` and both pings show `PASS` but `FAIL-persist` appears (the check re-applies every file, as a reboot would); if you did nothing, the pings, `FAIL-live` and `FAIL-persist` all fail. The fault, the fix and these checks were run in a Docker container (all `PASS`), not on a VM (section 11).

**Cleanup** (returns the VM to baseline):

```bash
ip netns del pod-a; ip netns del pod-b
rm -f /etc/sysctl.d/k8s.conf /etc/sysctl.d/zz-lab.conf
test ! -e /etc/sysctl.d/k8s.conf.bak || mv /etc/sysctl.d/k8s.conf.bak /etc/sysctl.d/k8s.conf   # only if you moved it aside
sysctl -w net.ipv4.ip_forward=$(cat ~/lab/t107/orig-forward)
sleep 1; ip -br link; ip netns list
rm -rf ~/lab/t107
```

## 8. Exam tips

- **`ip route get <pod-ip>` first.** On a node it answers "which interface and next hop will this packet use?" in one line. If it names the default gateway for a Pod IP on an overlay or BGP CNI (as in this guide's labs), you are looking at a missing CNI route and can skip every other check.
- **Check `sysctl net.ipv4.ip_forward` on every node on the path**, not just one. It is the cause that leaves routes looking correct. When you fix it, put the value in `/etc/sysctl.d/` and run `sysctl --system`; `sysctl -w` alone does not survive a reboot. Remember that files apply in name order, last wins.
- **Know the two doc pages.** [Cluster Networking](https://kubernetes.io/docs/concepts/cluster-administration/networking/) for the model and address ranges, and [Container runtimes, IPv4 forwarding](https://kubernetes.io/docs/setup/production-environment/container-runtimes/#prerequisite-ipv4-forwarding-optional) for the exact `k8s.conf` snippet. Both are on kubernetes.io/docs, which the exam allows ([allowed resources](https://docs.linuxfoundation.org/tc-docs/certification/certification-resources-allowed)).
- **Node tasks are done on the node.** Each task gives an `ssh <nodename>` command; use `sudo -i` for root and `exit` back to `base` before the next host ([exam tips](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)); nested `ssh` is not supported.
- **Do not count on extra tools.** The exam tips page lists `kubectl`, `yq`, `curl`, `wget` and `man` on the ssh hosts. It does not list `ip`, `sysctl`, `tcpdump` or `jq`. `ip` and `sysctl` come with the operating system and are very likely present, but that is **UNVERIFIED** for the exam hosts. Practise with `curl`/`wget` and `ip` only.
- **Traps before you move on:** an interface that is `DOWN`; a `/32` where you wanted `/24`; an MTU lower than the tunnel can carry; a node IP inside the Pod CIDR; and a Service IP that you cannot find in `ip -br a` (it is virtual, so that is normal).

## 9. Quick review

1. What command shows which interface and next hop a packet to `10.244.1.5` would use?
   <details><summary>Answer</summary>`ip route get 10.244.1.5`. It asks the kernel to do the routing lookup and prints the result, including `dev`, `via` and the chosen source address.</details>
2. A route says `default via 192.168.215.1 dev eth0` and another says `192.168.215.0/24 dev eth0 scope link`. A packet goes to `192.168.215.9`. Which route is used and why?
   <details><summary>Answer</summary>The `/24` connected route, because the longest matching prefix wins. The default route (`/0`) is used only when nothing more specific matches.</details>
3. How many addresses are in a `/24`, a `/16` and a `/32`?
   <details><summary>Answer</summary>256 (254 usable hosts), 65,536, and exactly 1.</details>
4. Why does a Service ClusterIP never appear in `ip -br a`?
   <details><summary>Answer</summary>It is a virtual address from the Service CIDR. No interface owns it. kube-proxy writes iptables/nftables rules that rewrite it to a Pod IP.</details>
5. What are the three commands to put one end of a veth pair into a namespace and make it usable?
   <details><summary>Answer</summary>`ip link set v1 netns red`, then `ip -n red addr add 10.10.0.11/24 dev v1`, then `ip -n red link set v1 up`. The interface arrives with no address and in the `DOWN` state.</details>
6. Cross-node Pod traffic fails. Both nodes' `ip route get` output is correct. What do you check next, and why?
   <details><summary>Answer</summary>`sysctl net.ipv4.ip_forward` on both nodes (and any file overriding it in `/etc/sysctl.d`). With forwarding off, a node drops packets that are not addressed to itself, silently, so the Pod-to-Pod packet dies at the node.</details>
7. You ran `sysctl -w net.ipv4.ip_forward=1` and it works, but after a reboot it is `0` again. Why, and what is the correct fix?
   <details><summary>Answer</summary>`sysctl -w` changes only the running kernel. Put `net.ipv4.ip_forward = 1` in a file under `/etc/sysctl.d/` and apply with `sysctl --system`. Also check that no later-sorted file sets it back to 0.</details>
8. Why does `ping` work but `curl` of a large file hang, in an overlay network?
   <details><summary>Answer</summary>A ping is tiny and passes any MTU. Full-size TCP packets (1500 bytes) do not fit into the tunnel (1480 for IP-in-IP, 1450 for VXLAN). Path MTU Discovery fails if ICMP is dropped or the Pod MTU is too high, so the large packets vanish silently. Fix the MTU in the CNI.</details>
9. What size do you pass to `ping -s` to test a 1450-byte packet with the DF bit set?
   <details><summary>Answer</summary>`-s 1422`, because 20 bytes of IP header and 8 bytes of ICMP header are added (1422 + 28 = 1450). Command: `ping -M do -s 1422 <ip>`.</details>
10. What does `br_netfilter` do, how do you load it at every boot, and does kubeadm v1.37 still require it?
    <details><summary>Answer</summary>It makes frames forwarded by a Linux bridge pass through iptables, which creates the `net.bridge.bridge-nf-call-*` sysctls. Load it now with `modprobe br_netfilter` and at boot by listing `br_netfilter` in `/etc/modules-load.d/k8s.conf`. According to the kubeadm source, kubeadm checked `bridge-nf-call-iptables` up to v1.29 and no longer checks it from v1.30; v1.37 checks `ip_forward`. You still need it for a bridge-based CNI.</details>
11. In `ip a` inside a Pod you see `eth0@if23:`. What does `23` mean and how do you use it?
    <details><summary>Answer</summary>It is the interface index of the other end of the veth pair, in the node's namespace. On the node, `ip -o link | grep '^23:'` shows the node-side interface (`cali...`).</details>
12. A new bridge `br0` has two ports and the namespaces on it cannot ping each other. Name two things to check.
    <details><summary>Answer</summary>That `br0` is `UP` (a down bridge forwards nothing, shown in the Docker test: 100% loss until `ip link set br0 up`), and that every interface (both veth ends) is `UP` and the ports show `master br0` in `bridge link`. Then check addresses are in the same subnet.</details>
