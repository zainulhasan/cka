## 1. Why this matters

A container is not a small virtual machine. It is a normal Linux process that the kernel has wrapped in two things: **namespaces** (what the process can see) and **cgroups** (how much it can use). Every Pod `resources.limits` value you write ends up as a number in a cgroup file on the node.

When you do not know this, you cannot explain why a Pod is `OOMKilled` while the app "only uses 100 MiB", why an app is slow although the node is idle (CPU throttling), or why the kubelet will not start on an old node. Since Kubernetes v1.35 the kubelet refuses to run on a node that uses cgroup v1 by default, so "kubelet does not start after a node was rebuilt on an old image" is a plausible node-troubleshooting scenario. The exam gives you shells on nodes (`ssh <node>`, then `sudo -i`; see [the exam tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)), so reading `/sys/fs/cgroup` and `/proc/<pid>/ns` is a way to prove what is happening.

## 2. Concepts

### 2.1 The problem: many processes, one kernel

All containers on a node share one kernel. Without extra help, a process in container A could list the processes of container B, bind the same port, change the hostname, or eat all the memory. Linux solves this with two independent features:

| Feature | Question it answers | Controls | Breaks without it |
|---|---|---|---|
| Namespaces | What can this process **see**? | Isolation of views: PIDs, network, mounts, hostname, IPC, users, clock | Containers see each other's processes, ports and files |
| cgroups (control groups) | How much can this process **use**? | Limits and accounting: CPU, memory, PIDs, disk I/O | One container can starve the node |

A container runtime (containerd, CRI-O, runc) creates a process, puts it in a fresh set of namespaces, puts it in a cgroup with limits, and gives it a different root filesystem. That is all "a container" is. There is no "container" object in the kernel.

### 2.2 Namespace types

A namespace wraps one global resource so that processes inside it see their own private copy. Linux has eight kinds in current kernels:

| Namespace | `unshare` flag | What it isolates | Used by Kubernetes for |
|---|---|---|---|
| `pid` | `--pid` (`-p`) | The PID number space. The first process inside is PID 1 | Each container has its own, unless `shareProcessNamespace: true` or `hostPID: true` |
| `net` | `--net` (`-n`) | Interfaces, IP addresses, routes, iptables/nftables rules, port numbers, `/proc/net` | One per Pod, shared by all containers in the Pod. `hostNetwork: true` uses the node's |
| `mnt` | `--mount` (`-m`) | The mount table (what is mounted where) | Each container has its own root filesystem and volume mounts |
| `uts` | `--uts` (`-u`) | Hostname and NIS domain name | Shared inside a Pod, so the hostname is the Pod name |
| `ipc` | `--ipc` (`-i`) | System V IPC objects and POSIX message queues | Shared inside a Pod. `hostIPC: true` uses the node's |
| `user` | `--user` (`-U`) | UID and GID numbers (maps "root inside" to "unprivileged outside") | Off by default. `hostUsers: false` turns it on (section 2.7) |
| `cgroup` | `--cgroup` (`-C`) | The view of the cgroup tree: the process sees its own cgroup as `/` | Containers do not see the node's whole cgroup tree |
| `time` | `--time` (`-T`) | Offsets of the monotonic and boot clocks (Linux 5.6+) | Rarely used by Kubernetes. Awareness only |

Important facts:

- A namespace lives as long as at least one process is in it, or something else holds a reference to it (an open file descriptor to `/proc/<pid>/ns/net`, or a bind mount such as the files `ip netns add` creates under `/run/netns`). That is why `ip netns` namespaces survive with no process in them. On a kind node `lsns` shows the same thing for Pods: the CNI network namespaces are mounted at `/run/netns/cni-...`.
- A process joins namespaces at creation (`clone`), moves itself into new ones (`unshare`), or joins existing ones (`setns`). The commands `unshare` and `nsenter` are thin wrappers for `unshare(2)` and `setns(2)`.
- Namespaces are **not** a security boundary by themselves. A container with root in the host user namespace, extra capabilities, or `privileged: true` can escape. See the Pod security lessons later in the guide.

### 2.3 Looking at namespaces: `lsns`, `/proc/<pid>/ns`

Every process has one symlink per namespace in `/proc/<pid>/ns/`. The number in brackets is the **inode** of the namespace. **Two processes are in the same namespace if and only if the numbers are equal.** This is the one trick that proves isolation or sharing.

REAL OUTPUT (Docker): `ls -l /proc/self/ns` inside a plain container (trimmed to the names):

```text
cgroup -> cgroup:[4026532615]
ipc -> ipc:[4026532613]
mnt -> mnt:[4026532611]
net -> net:[4026532616]
pid -> pid:[4026532614]
pid_for_children -> pid:[4026532614]
time -> time:[4026532720]
time_for_children -> time:[4026532720]
user -> user:[4026531837]
uts -> uts:[4026532612]
```

Read it like this:

- Ten links, eight kinds. `pid_for_children` and `time_for_children` are the namespaces that **children** of this process will be created in. They differ from `pid` / `time` only after a process calls `unshare --pid` without forking (see below).
- The `user` inode `4026531837` is the well-known number of the **initial** (host) user namespace. This container does not use a user namespace, so its root is the host's root. This is the default for Pods too.

`lsns` lists namespaces known on the host, one row per namespace:

```bash
lsns                 # all types
lsns -t net          # only network namespaces
lsns -t pid -o NS,TYPE,NPROCS,PID,COMMAND
sudo lsns -t net     # as root you see namespaces of all users' processes
```

Columns: `NS` (inode), `TYPE`, `NPROCS` (number of processes in it), `PID` (the **lowest** PID in it), `COMMAND` (that process's command line). Without `sudo` you only see your own processes' namespaces. Exam-host note: `lsns` is a util-linux tool that is normally present on Linux nodes, but the exam hosts' tool list only names kubectl, yq, curl, wget and man. The `/proc` equivalent is `readlink /proc/<pid>/ns/net` (compare the inode numbers).

### 2.4 Making your own: `unshare`

`unshare` runs a command in new namespaces. This is the smallest possible "container".

```bash
sudo unshare --fork --pid --mount-proc bash
```

Why each flag:

| Flag | Why it is needed |
|---|---|
| `--pid` | Create a new PID namespace. The calling process itself does **not** move into it. Only its **children** do |
| `--fork` | Fork a child so there is a child to be PID 1 of the new namespace. Without it, `bash` fails with `Cannot allocate memory` (the kernel cannot create more processes in a PID namespace whose PID 1 never existed). |
| `--mount-proc` | Mount a fresh `/proc` for the new PID namespace (this also creates a new mount namespace). `ps` and `top` read `/proc`, so without it they would still show the host's processes |

REAL OUTPUT (kind node, root): a session with `--pid --mount-proc --uts --net`. The commands are typed into the new shell; the last line is run back on the host:

```text
$ echo "inner pid: $$"
inner pid: 1
$ ps -e -o pid,comm
    PID COMMAND
      1 bash
      2 ps
$ hostname lab-ns; hostname
lab-ns
$ ip -br a
lo               DOWN
$ exit
$ hostname                     # back on the node
t110-worker
```

What to notice: the shell is PID 1, `ps` sees only two processes, the hostname change did not leak to the node, and the new network namespace has only a `lo` that is DOWN (no `eth0`, no routes). Compare a Pod: the runtime creates the Pod's network namespace and then the CNI plugin adds `eth0` (one end of a veth pair, see T1.07).

Combine flags freely. Exam-host note: `unshare` and `nsenter` are lab tools; the exam checks Kubernetes objects, so you will not need them to solve a task. They teach what the runtime does.

**The other four namespace types, one runnable example and one observation each.** REAL OUTPUT (Docker): these ran in a privileged `ubuntu:24.04` container (`docker run --rm --privileged ...`), as root.

| Type | Command | What to look for | Observed |
|---|---|---|---|
| `ipc` | `ipcmk -M 1024; ipcs -m` then `unshare --ipc ipcs -m` | A shared-memory segment created before is visible on the first command and gone in the new IPC namespace | The first `ipcs -m` listed key `0x02df6332`, 1024 bytes; the one run under `unshare --ipc` listed no segments |
| `user` | `unshare --user --map-root-user bash -c 'id -u; cat /proc/self/uid_map; readlink /proc/self/ns/user'` | You are UID 0 inside, the map has exactly one entry, and the `user:[...]` inode differs from the host's | `0`, then `0 0 1` (inside UID 0 = parent UID 0, range of 1), and `user:[4026532724]` instead of the host's `user:[4026531837]`. (A normal user would see its own UID on the right.) |
| `cgroup` | `cat /proc/self/cgroup` then `unshare --cgroup bash -c 'cat /proc/self/cgroup'` | Inside the new cgroup namespace your cgroup is shown as the root `/`, so the process cannot see where it sits in the node's tree | Run with `docker run --cgroupns=host`: the host view was `0::/docker/<container id>`, inside `unshare --cgroup` it was `0::/`; the `cgroup:[...]` inodes differed |
| `time` | `cat /proc/uptime` then `unshare --time --boottime 3600 bash -c 'cat /proc/uptime'` | The boot clock is shifted by the offset (here +3600 s) only inside | Uptime seconds `152547` on the host, `156147` inside (+3600); `uptime -p` inside printed `up 1 day, 19 hours, 22 minutes` (the host's 152547 s is 1 day 18 hours 22 minutes) |

(`--boottime` and `--monotonic` set the clock offsets; needs util-linux 2.36 or newer and Linux 5.6 or newer.) A Pod uses the `ipc` and `user` rows through `hostIPC` and `hostUsers` (sections 2.6 and 2.7); the `cgroup` namespace is why `cat /proc/self/cgroup` inside a container prints `0::/`; Kubernetes does not use the `time` namespace.

### 2.5 Entering an existing namespace: `nsenter`

`nsenter` runs a command inside the namespaces of an **already running** process. It is how you debug a container that has no shell or no `ip` tool: run the **node's** tool inside the container's namespaces.

```bash
sudo nsenter -t <pid> -n ip a          # network ns only: node's `ip` sees the container's interfaces
sudo nsenter -t <pid> -n -m            # network + mount ns (starts a shell, since no command is given)
sudo nsenter -t <pid> -p -m ps -e      # pid + mount ns: needed together so /proc matches the pid ns
sudo nsenter -t <pid> --all            # every namespace (roughly what `kubectl exec` gives you)
```

| Flag | Namespace to enter | Flag | Namespace to enter |
|---|---|---|---|
| `-t PID` | **target** process whose namespaces to join (required) | `-u` | uts |
| `-n` | net | `-i` | ipc |
| `-m` | mnt | `-U` | user |
| `-p` | pid | `-C` | cgroup |

Rules that bite:

- `-m` also changes the filesystem you see, so tools that are in the container's filesystem are used, not the node's. If you only need networking, use `-n` alone: you keep the node's `ip`, `ss`, `tcpdump`.
- `ps` reads `/proc`. `/proc` is a mount, and each mount belongs to one PID namespace. To make `ps` show the container's processes you need the container's mount namespace (`-m`) **and** the pid namespace (`-p`).
- You need root (or `CAP_SYS_ADMIN`).
- Pods and `nsenter`: a Pod has one network namespace. Any process of any container in the Pod is a good `-t` for `-n`.

### 2.6 What a Pod shares: the pause (sandbox) container

A Pod is "a group of containers that share some namespaces". The default is:

| Namespace | Shared between containers of one Pod? | How to change |
|---|---|---|
| net | **Yes** (one IP, containers talk on `localhost`, port numbers must not clash) | `hostNetwork: true` uses the node's namespace instead |
| uts | **Yes** (hostname = Pod name) | `spec.hostname` changes the name inside the Pod |
| ipc | **Yes** | `hostIPC: true` uses the node's |
| pid | **No**, each container has its own | `shareProcessNamespace: true` shares one pid ns in the Pod. `hostPID: true` uses the node's |
| mnt | **No**, each container has its own root FS. Volumes are the same files mounted into several containers | none |
| user | Host user namespace (not isolated) | `hostUsers: false` gives the Pod its own user ns |
| cgroup | Container sees its own cgroup as root | none |

The three `host*` fields give a Pod the **node's** namespace and are a security risk. They are checked by the Pod Security Standards ("baseline" forbids `hostNetwork`, `hostPID`, `hostIPC`).

Observing the `host*` variants (one example each; compare inode numbers with `readlink`). `hostNetwork: true`: `k exec x -- readlink /proc/1/ns/net` equals the node's `readlink /proc/1/ns/net`, and `k exec x -- ip -br a` lists the node's interfaces. `hostIPC: true`: same test with `/proc/1/ns/ipc`; a segment made with `ipcmk -M 1024` on the node shows in the Pod's `ipcs -m`. `hostPID: true`: `ps` inside the container lists node processes (real output in section 6.4). A Pod that sets `hostUsers: false` together with `hostNetwork` is rejected (section 2.7). Output for `hostNetwork` and `hostIPC` was not captured in this lesson (section 11).

REAL OUTPUT (kind node, root): namespace inodes of the first process of each scope in two Pods. The first Pod has an app container and the pause sandbox; the second has `shareProcessNamespace: true` with two app containers plus the sandbox. `net`, `ipc` and `uts` are equal inside one Pod. `pid` differs in the first Pod and is equal in the second. `mnt` always differs. (Inode numbers shortened to the last 4 digits.)


**Who owns the shared namespaces?** The **pause container**, also called the **Pod sandbox**. When the kubelet starts a Pod it first asks the runtime (over the CRI, the Container Runtime Interface) for `RunPodSandbox`. The runtime starts a tiny container (on the captured node the image was `registry.k8s.io/pause:3.10`) that does nothing but sleep. That process creates and holds the Pod's net, uts and ipc namespaces. The CNI plugin then configures the network namespace (creates `eth0`). Then the app containers are created and **join** those namespaces. Reasons for this design:

- Containers in a Pod can start, crash and restart without destroying the Pod's IP, because the namespaces stay alive as long as the pause process lives.
- With `shareProcessNamespace: true`, the pause process is PID 1 of the shared pid namespace and reaps zombie (defunct) processes.

You see the sandbox with the runtime CLI on the node (`crictl pods`; `crictl ps` lists app containers only). `kubectl` never shows it. It is also why the Pod's cgroup directory has two scopes in it for a one-container Pod (section 2.9).

### 2.7 User namespaces in Pods (`hostUsers: false`), awareness

By default "root" (UID 0) in a container is UID 0 on the node. If an attacker escapes the container they are root on the node. A **user namespace** maps UIDs: UID 0 inside is, for example, UID 3425828864 outside, which has no rights on the node.

In Kubernetes you ask for this with one field, `spec.hostUsers: false`. The default is `true` (no user namespace). The feature is GA in v1.36 (the v1.36 release blog is titled "User Namespaces in Kubernetes are finally GA" and the cgroups blog repeats it). Requirements, from the docs page [User Namespaces](https://kubernetes.io/docs/concepts/workloads/pods/user-namespaces/):

| Requirement | Minimum stated on the page |
|---|---|
| Linux kernel | idmap mounts on the filesystems used; in practice **Linux 6.3** (tmpfs got idmap mount support then; ServiceAccount tokens and Secrets use tmpfs) |
| OCI runtime | runc **1.2** or greater; crun **1.9** or greater (1.13+ recommended) |
| CRI runtime | containerd **2.0** or later; CRI-O **1.25** or later |
| Node ID range | `/etc/subuid` and `/etc/subgid` entries for the user `kubelet`; the count must be a multiple of 65536 and at least 65536 x `maxPods` (each Pod gets 65536 IDs) |

A Pod with `hostUsers: false` **cannot** also set `hostNetwork`, `hostPID` or `hostIPC`; the API server rejects it. REAL OUTPUT (kind): `spec.hostNetwork: Forbidden: when `hostUsers` is false`.

```yaml
# userns.yaml
apiVersion: v1
kind: Pod
metadata:
  name: userns
  namespace: lab-t110
spec:
  hostUsers: false             # default true. false = Pod gets its own user namespace (root in Pod != root on node)
  containers:
  - name: app
    image: busybox:1.36
    command: ["sleep", "3600"]
```

REAL OUTPUT (kind): `k exec -n lab-t110 userns -- cat /proc/self/uid_map` and, for comparison, the same in a normal Pod. Columns: first UID inside, first UID on the node, length of the range.

```text
         0 3425828864      65536      <- hostUsers: false  (the middle number differs per Pod)
         0          0 4294967295      <- normal Pod: identity map, root is the node's root
```

This is awareness material: know the field name, what it does and that it cannot be combined with `host*`.

### 2.8 cgroup v2: the unified hierarchy

A **cgroup** (control group) is a node in a tree. You put processes in a node, and the kernel applies the controllers (cpu, memory, pids, io) to the node's whole group of processes. cgroups are exposed as a special filesystem: **directories are cgroups, files are settings and counters.** You create a cgroup with `mkdir` and put a process in with `echo PID > cgroup.procs`.

Why v2? Version 1 had one separate tree per controller (a process could be in different places in the cpu tree and the memory tree), with inconsistent rules. Version 2 has **one unified tree**, mounted at `/sys/fs/cgroup`, with consistent files. Pressure information (PSI), Memory QoS and accurate memory accounting need v2. cgroup v1 is unsupported for the kubelet by default from v1.35 (section 2.13).

**Check which version a node uses:**

```bash
stat -fc %T /sys/fs/cgroup
```

| Output | Meaning |
|---|---|
| `cgroup2fs` | cgroup v2 (what Kubernetes v1.37 needs) |
| `tmpfs` | cgroup v1 (or hybrid). The kubelet will refuse to start by default |

REAL OUTPUT (kind node, root): `cgroup2fs`.

**Core files** (every cgroup directory):

| File | Meaning | Notes |
|---|---|---|
| `cgroup.controllers` | Controllers available in this cgroup | read only. REAL: `cpuset cpu io memory pids` |
| `cgroup.subtree_control` | Controllers enabled for children | systemd/kubelet manage it; do not edit on a Kubernetes node |
| `cgroup.procs` | PIDs in this cgroup | write a PID to move that process in |
| `cgroup.kill` | Write `1` to SIGKILL every process in the cgroup and below | not an OOM setting; useful for cleanup |
| `cgroup.events` | `populated 0/1` | whether any process is below |

**CPU controller**

| File | Meaning | Default | Valid values | Failure symptom |
|---|---|---|---|---|
| `cpu.max` | `"<quota> <period>"` in microseconds: the group may run `quota` µs per `period` µs, summed over all its threads | `max 100000` (no cap) | quota `max` or a number >= 1000; period 1000 to 1000000 | Too small a quota = throttling, slow app |
| `cpu.weight` | Relative share when CPUs are contended | `100` | 1 to 10000 | Only matters under contention. It is not a cap |
| `cpu.stat` | Counters: `usage_usec`, `nr_periods`, `nr_throttled`, `throttled_usec` | n/a | read only | growing `nr_throttled` = being throttled |

**Memory controller**

| File | Meaning | Default | Valid values | Failure symptom |
|---|---|---|---|---|
| `memory.max` | **Hard limit** in bytes. Over it: reclaim, then **OOM kill** | `max` | bytes (`40M` accepted) or `max` | OOM kill, exit 137 |
| `memory.high` | **Soft limit**. Over it the group is throttled with forced reclaim. **Never kills** | `max` | bytes or `max` | Process becomes very slow; with no swap and mostly anonymous memory it can stall almost completely |
| `memory.min` / `memory.low` | Memory protected from reclaim (hard / best effort) | `0` | bytes | Too high = starves siblings. Kubernetes writes them only with Memory QoS tiered reservation |
| `memory.swap.max` | Swap allowed | `max` | bytes, `0` = no swap | With swap allowed, `memory.max` may not kill because pages go to swap |
| `memory.oom.group` | `1` = an OOM kills **all** processes of the cgroup together | `0` | 0 or 1 | The kubelet sets it to `1` for containers on cgroup v2 (REAL: `1`) |
| `memory.current` | Memory in use now, bytes. Includes page cache and tmpfs | n/a | read only | |
| `memory.stat` | Breakdown: `anon`, `file`, `shmem`, `kernel`, `slab`... | n/a | read only | |
| `memory.events` | Counters: `low`, `high`, `max`, `oom`, `oom_kill`, `oom_group_kill` | n/a | read only | `oom_kill` > 0 = something was killed |

**PIDs controller**

| File | Meaning | Default | Valid values | Failure symptom |
|---|---|---|---|---|
| `pids.max` | Max number of tasks (processes and threads) | `max` | number or `max` | `fork: retry: Resource temporarily unavailable` |
| `pids.current` / `pids.events` | Current count / how many forks were refused (`max N`) | n/a | read only | |

**I/O controller**

| File | Meaning | Default | Valid values | Failure symptom |
|---|---|---|---|---|
| `io.max` | Per block device limits: `MAJ:MIN rbps=.. wbps=.. riops=.. wiops=..` | empty (no limit) | numbers or `max` per key | Slow disk access for that group |
| `io.weight` | Relative I/O share | `default 100` | 1 to 10000 | |
| `io.stat` | Counters per device | n/a | read only | |

Kubernetes does **not** set `io.max` for Pods. It is shown here for completeness. `io.max` does not exist in the root cgroup and the `io` controller must be listed in the parent's `cgroup.subtree_control`, so the example runs in a child cgroup made like the one in the next demo (`mkdir /sys/fs/cgroup/demo; cd /sys/fs/cgroup/demo`). REAL OUTPUT (kind node, root): set on the device `254:0` (numbers from `cat /proc/partitions`) and read back, then reset:

```text
$ echo "254:0 rbps=max wiops=max" > io.max ; cat io.max     # prints nothing: no limits left
```

(Find the device numbers with `cat /proc/partitions`.)

REAL OUTPUT (Docker): after `docker run --memory 128m --cpus 0.5 --pids-limit 200`, the container sees these in its own root cgroup:

```text
100                # default weight

```

Exactly the same conversion is done for Pods (section 2.10).

**Two behaviours that cause confusion**

- `memory.max` is enforced by the kernel and kills. `memory.high` only throttles. A process that hits `memory.high` becomes slow; one that hits `memory.max` and cannot reclaim is killed.
- `cpu.max` is a **quota**, not a speed limit. A process that wants more CPU time than the quota is **paused** until the next period (section 2.12).

**Build a cgroup by hand (every controller in one demo).**

This is the exact thing the runtime does for a container, done by hand. Run as root. (Lab 7.1 repeats it as a task.) Swap matters for the memory part: with swap enabled the kernel can push pages to swap instead of killing, so the demo sets `memory.swap.max` to `0` for the `memory.max` step, like a Kubernetes node (which runs without swap by default).

```bash
mkdir /sys/fs/cgroup/demo && cd /sys/fs/cgroup/demo      # creating the directory creates the cgroup
cat cgroup.controllers                                    # cpuset cpu io memory pids

# 1. pids.max: at most 5 tasks in the group
echo 5 > pids.max
bash -c 'echo $$ > /sys/fs/cgroup/demo/cgroup.procs     # move this shell into the group
         for i in 1 2 3 4 5 6 7 8; do sleep 20 & done'
cat pids.events                                           # max 5 = forks refused
echo 1 > cgroup.kill; echo max > pids.max

# 2. memory.high: slow, never killed (about 100 MB needed by the test program)
echo 40M > memory.high
bash -c 'echo $$ > /sys/fs/cgroup/demo/cgroup.procs; x=$(head -c 100000000 /dev/zero | tr "\0" a); echo "held ${#x} bytes"'
grep -E '^(high|max|oom_kill) ' memory.events

# 3. memory.max: killed
echo max > memory.high; echo 0 > memory.swap.max; echo 40M > memory.max
bash -c 'echo $$ > /sys/fs/cgroup/demo/cgroup.procs; x=$(head -c 100000000 /dev/zero | tr "\0" a); echo "held ${#x} bytes"'; echo "exit=$?"
grep -E '^(high|max|oom_kill) ' memory.events
echo max > memory.max

# 4. cpu.max: 20 ms per 100 ms period = 0.2 CPU, a busy loop for 3 seconds
echo "20000 100000" > cpu.max
bash -c 'echo $$ > /sys/fs/cgroup/demo/cgroup.procs; timeout 3 sh -c "while :; do :; done"; true'
grep -E 'usage_usec|nr_periods|nr_throttled|throttled_usec' cpu.stat

# cleanup: a cgroup can be removed only when empty
cd /; echo 1 > /sys/fs/cgroup/demo/cgroup.kill; sleep 1; rmdir /sys/fs/cgroup/demo
```

REAL OUTPUT (kind node, root, kernel 7.2): the output of the script above (the shell prints the fork errors for step 1):

```text

bash: fork: retry: Resource temporarily unavailable
```

How to read it: step 1 proves `pids.max` (fork fails, not a kill). Step 2 proves `memory.high` (the program finishes, only `high` counts rise). Step 3 proves `memory.max` (SIGKILL = exit 137, `oom_kill 1`). Step 4 proves the quota: the busy loop ran for 3 seconds (31 periods of 100 ms) and was throttled in all 31 of them. `throttled_usec` 2,416,483 is about 78 ms of waiting per 100 ms period, so the loop ran only about 22 ms per period, which matches the 20 ms quota (0.2 CPU). One more observation from testing: with `memory.high` set, swap forced to `0` and mostly anonymous memory, the test program stalled in uninterruptible sleep (state `D`) for as long as the limit stayed; resetting `memory.high` to `max` freed it. That is why Kubernetes does not use `memory.high` by default.

### 2.9 The `kubepods.slice` hierarchy and QoS slices

With the **systemd cgroup driver** (see 2.11) systemd owns the tree. A **slice** (`*.slice`) is a systemd unit that groups other units; a **scope** (`*.scope`) is a group of processes that were started by something other than systemd (here: the runtime). Kubernetes uses this layout:

| Level | Name pattern | Contains | Set by |
|---|---|---|---|
| Parent of all Pods | `kubepods.slice` | Everything the kubelet manages. `memory.max` is the node's **allocatable** memory | kubelet (`enforceNodeAllocatable: [pods]` default) |
| QoS slice | `kubepods-burstable.slice`, `kubepods-besteffort.slice` | Pods of that class. **Guaranteed Pods have no QoS slice**; they sit directly under `kubepods.slice` | kubelet |
| Pod slice | `kubepods-burstable-pod<UID>.slice` | One Pod. The Pod UID has `-` replaced by `_` because systemd treats `-` as a hierarchy separator | kubelet |
| Container scope | `cri-containerd-<container-id>.scope` (containerd) or `crio-<id>.scope` (CRI-O) | The processes of one container, and one more scope for the sandbox (pause) | runtime (runc) |

**kind adds a prefix.** kind starts the kubelet with `cgroupRoot: /kubelet`, so every name is `kubelet-kubepods...` under `kubelet.slice/kubelet-kubepods.slice/`. REAL OUTPUT (kind): `GET /api/v1/nodes/t110-worker/proxy/configz` returned `cgroupDriver: systemd`, `cgroupRoot: /kubelet`, `cgroupsPerQOS: true`, `failCgroupV1: true`, `cpuCFSQuota: true`, `cpuCFSQuotaPeriod: 100ms`, `podPidsLimit: -1`, `enforceNodeAllocatable: [pods]`, `memoryReservationPolicy: None`. A kubeadm node has no such prefix (`kubepods.slice/...`); that layout was not captured (section 11). The recipe in section 4.1 (`find -name "*<container id>*"`) works on both.

The QoS class decides where a Pod lives:

| QoS class | Rule (per Pod) | `oom_score_adj` | Where |
|---|---|---|---|
| Guaranteed | **Every** container has CPU and memory requests **and** limits, and request = limit | -997 | `kubepods.slice/kubepods-pod<UID>.slice` |
| Burstable | Not Guaranteed, but at least one request or limit is set | 2 to 999 (lower when the memory request is larger) | `kubepods-burstable.slice/...` |
| BestEffort | No requests or limits at all | 1000 | `kubepods-besteffort.slice/...` |

`oom_score_adj` is a per-process number the OOM killer uses when the **whole node** runs out of memory: higher is killed first. So under node-level pressure BestEffort dies first, Guaranteed last. (Per-container limits work differently: see 2.14.) REAL OUTPUT (kind): the kernel log for a Burstable container with a 32Mi memory request showed `oom_score_adj:999`.

REAL OUTPUT (kind node, root): `systemd-cgls /kubelet.slice` shows the same tree with the processes in it (the trimmed result of a node with three lab Pods):

### 2.10 Mapping requests and limits to cgroup files

The kubelet turns the Pod spec into CRI fields (`cpu_period`, `cpu_quota`, `cpu_shares`, `memory_limit_in_bytes`). The runtime (runc) converts them to v2 files.

| Pod spec field | cgroup v2 file | Conversion | Example (REAL, kind) |
|---|---|---|---|
| `limits.memory` | `memory.max` | bytes | `128Mi` -> `134217728` |
| `limits.cpu` | `cpu.max` | quota = limit in millicores * 100 (period is `100000` µs = 100 ms by default) | `500m` -> `50000 100000`; `1` -> `100000 100000`; `100m` -> `10000 100000` |
| `requests.cpu` | `cpu.weight` | millicores -> "shares" (`m * 1024 / 1000`, minimum 2) -> weight (formula below) | `250m` -> `35`, `500m` -> `59`, `50m` -> `11`, none -> `1` |
| `requests.memory` | **nothing** by default | Used by the scheduler, QoS class and `oom_score_adj`. Becomes `memory.min`/`memory.low` only with Memory QoS tiered reservation (off by default) | |
| no `limits.memory` | `memory.max` = `max` | | |
| no `limits.cpu` | `cpu.max` = `max 100000` | | |
| `ephemeral-storage` | **not a cgroup** | The kubelet measures disk use and evicts | |
| `podPidsLimit` (kubelet config) | `pids.max` | per Pod | default `-1` = unlimited (REAL: Pod slice `pids.max` was `max`) |

**The `cpu.weight` formula.** cgroup v2 `cpu.weight` runs from 1 to 10000 (default 100). Kubernetes still computes cgroup v1 "shares" (`shares = milliCPU * 1024 / 1000`, default 1024) and the OCI runtime converts shares to weight. From the Kubernetes blog "New Conversion from cgroup v1 CPU Shares to v2 CPU Weight" (2026-01-30):

| Runtime | Formula | 1000m | 500m | 250m | 100m |
|---|---|---|---|---|---|
| Old (linear), runc before 1.3.2, crun before 1.23 | `weight = 1 + (shares - 2) * 9999 / 262142` | 39 | 20 | 10 | 4 |
| New (quadratic), runc 1.3.2+, crun 1.23+ | `weight = ceil(10^(L^2/612 + 125*L/612 - 7/34))`, `L = log2(shares)` | 100 (the blog quotes 102 for 1 CPU) | 59 | 35 | 17 |

The new curve is built so that shares 1024 (1 CPU) land on the default weight 100 (the formula gives exactly 100; the blog text quotes 102, so the last digits depend on rounding in the runtime). I computed 59, 35, 17 and 11 for 500m, 250m, 100m and 50m, and the captured node showed 59, 35 and 11. The captured node runs runc 1.4.3, so containers got the new values (`500m` -> `59`, `250m` -> `35`). **Surprise worth knowing:** the Pod-level slice, which the kubelet writes itself, showed the old linear values on the same node: `500m` -> `20`, `250m` -> `10`. Both are correct for their level. Do not compare weights across levels; compare Pods at the same level. Always read the file rather than predicting it.

REAL OUTPUT (kind): the same limits at the container scope and the Pod slice. For the Burstable Pod (limits cpu `1`, memory `128Mi`; requests cpu `250m`, memory `64Mi`) the Pod slice had `memory.max 134217728`, `cpu.max 100000 100000`, `cpu.weight 10`. The parent `kubelet-kubepods-burstable.slice` had `memory.max max`, `cpu.max max 100000`, and `cpu.weight 14` (kubelet sums the requests of the class); `kubelet-kubepods.slice` had `memory.max 16818667520` (node allocatable on that machine) and `cpu.weight 469`.

Notes you need:

- The **CPU request** is a *weight*, used only when CPUs are contended. It is not a guarantee of a speed and not a cap. The **CPU limit** is the cap.
- The **memory request** does not protect memory in the cgroup by default. It only decides scheduling and QoS. REAL: on the captured node `memory.high` was `max` and `memory.min` / `memory.low` were `0` for containers, so Memory QoS was not active.
- The kubelet writes values at two levels: on the **Pod slice** (sum over containers; for memory only if every container has a limit) and on each **container scope**. If a value looks missing on the Pod slice, read the container scope.
- `pids.max` at the container scope was a number (`19283`) on the captured node, not `max`. Where that number comes from was not determined; expect it to differ between nodes.
- **Resizing resources.** The Pod spec is immutable for most fields. REAL OUTPUT (kind): a plain `k patch` of `resources` is rejected with `The Pod "x" is invalid: spec: Forbidden: pod updates may not change fields other than spec.containers[*].image, spec.initContainers[*].image, spec.activeDeadlineSeconds, spec.tolerations (only additions to existing tolerations), spec.terminationGracePeriodSeconds ...`. But CPU and memory requests and limits **can** be changed on a running Pod through the `resize` subresource (in-place Pod resize is stable since v1.35): `k patch pod x --subresource resize --patch '{"spec":{"containers":[{"name":"c","resources":{"requests":{"cpu":"500m","memory":"256Mi"},"limits":{"cpu":"500m","memory":"256Mi"}}}]}}'`. For a Guaranteed Pod patch requests and limits together (raising only the limit would change the QoS class, which a resize rejects). REAL: after resizing a Guaranteed Pod from 128Mi to 256Mi with that patch the container's `memory.max` became `268435456` with `restartCount` still `0`. Whether a container restarts is controlled by the container's `resizePolicy` (default `NotRequired` for CPU and memory). The QoS class cannot change through a resize. Delete-and-recreate (`k replace --force -f pod.yaml`) is the fallback for anything else.

### 2.11 cgroup driver: systemd vs cgroupfs

Someone must create the cgroup directories and write the files. The **cgroup driver** says who:

| Driver | Who manages the tree | Path looks like | Use when |
|---|---|---|---|
| `systemd` | systemd (runtime asks systemd over D-Bus to create transient units) | `kubepods.slice/kubepods-burstable.slice/kubepods-burstable-pod..._..._.slice/cri-containerd-<id>.scope` | The node uses systemd as init (all common distros). **Recommended**, and the one `kubeadm` expects |
| `cgroupfs` | The kubelet/runtime write the directories directly | `kubepods/burstable/pod<uid-with-dashes>/<container-id>` | Rare nodes without systemd |

Rule: **kubelet and container runtime must use the same driver.** Two managers on one tree fight and the node is unstable. Before v1.34 you set it twice: `cgroupDriver: systemd` in the kubelet config and `SystemdCgroup = true` in the containerd runc options. **Since v1.34 (GA, KEP-4033) the kubelet asks the runtime** through the CRI `RuntimeConfig` call which driver it uses and follows it. When the runtime reports a value, the kubelet uses it instead of its own `cgroupDriver` setting. This needs containerd v2.0+ or CRI-O v1.28+. The kubelet's own `cgroupDriver` field is deprecated in favour of this CRI auto-detection; it remains only as a manual override for a runtime that cannot report the driver (the cgroups blog shows `cgroupDriver: systemd` for that case). Check what is in use:

```bash
# kubelet side (the setting may be absent when auto-detection is used)
sudo grep -i cgroupDriver /var/lib/kubelet/config.yaml
# containerd side
sudo grep -n SystemdCgroup /etc/containerd/config.toml
# or look at the paths: ".slice/.scope" names => systemd, "/kubepods/burstable/pod..." => cgroupfs
sudo find /sys/fs/cgroup -maxdepth 2 -name '*kubepods*'
```

REAL OUTPUT (kind node, root): `cgroupDriver: systemd` and `cgroupRoot: /kubelet` in `/var/lib/kubelet/config.yaml`; `SystemdCgroup = true` twice in `/etc/containerd/config.toml`.

### 2.12 CPU throttling

CPU limits are enforced with the **CFS bandwidth controller**. Time is cut into periods (default 100 ms). A group with `cpu.max = 50000 100000` may run 50 ms of CPU time per period, summed over all its threads. When the quota is used up, **all its threads are paused until the next period starts**.

Example: limit `500m`, app with 4 busy threads on a 4-core node. The 4 threads use up 50 ms of CPU time in about 12.5 ms of wall time and then sleep for about 87.5 ms. The average is 0.5 CPU, but requests are delayed by up to 87 ms. Latency suffers even if the node and the Pod look idle on a 1-minute CPU graph.

`cpu.stat` shows it. REAL OUTPUT (kind): a Pod running `while :; do :; done` with `limits.cpu: 100m`, 10 seconds after start:

```text
$ cat cpu.max
10000 100000
$ cat cpu.stat
usage_usec 1017766
user_usec 1010965
system_usec 6801
nr_periods 101
nr_throttled 101            <- throttled in all 101 periods
throttled_usec 8030438      <- 8 s of waiting in about 10 s of wall time
$ awk '/nr_periods/{p=$2}/nr_throttled/{t=$2}END{print t/p}' cpu.stat
1
```

Meaning: if `nr_throttled / nr_periods` is high (say more than 25 %) and the app is slow, the app is limited by its CPU limit. The busy loop wanted a full CPU but got 0.1, so it was throttled in every period; it used about 1.0 s of CPU in 10 s.

Fixes, best first: raise the limit; remove the CPU limit but keep the request (many teams do this; the request still gives a fair share); reduce the app's thread count (for Go, `GOMAXPROCS`; for Java, container-aware JVM). Never "fix" it by lowering the request.

### 2.13 cgroup v1 is refused by the kubelet since v1.35

The official blog post [The Shift to cgroup v2 in Kubernetes: What You Need to Know](https://kubernetes.io/blog/2026/10/06/kubernetes-cgroups-v2-shift/) (Paco Xu, 2026-10-06) says:

- cgroup v1 support moved into maintenance mode in v1.31, and cgroup v2 has been stable since v1.25. Kubernetes has **deprecated cgroup v1**.
- "Starting with Kubernetes v1.35, `failCgroupV1` defaults to `true`, so the kubelet does not start on a cgroup v1 node by default." Administrators can **temporarily** set `failCgroupV1: false` in the kubelet configuration file. Removal follows the deprecation policy (KEP-5573: Remove cgroup v1 support); the post says the fallback is scheduled for removal in v1.38.
- If you run a release older than v1.35, migrate every Linux node to cgroup v2 before upgrading, or plan to set the temporary override.
- For kubeadm clusters, v1.35 makes the `SystemVerification` preflight check stricter: it returns an **error** (not a warning) during `kubeadm init`, `kubeadm join` and `kubeadm upgrade` when it detects cgroup v1 with kubelet v1.35 or later.
- Requirements the post lists for cgroup v2: kernel 5.8 or later (5.9+ recommended for Memory QoS), a runtime that supports v2 (containerd 1.4+, CRI-O 1.20+; containerd 2.0+ or CRI-O 1.28+ for automatic cgroup-driver detection), and a matching cgroup driver on kubelet and runtime.
- It also lists the troubleshooting commands used in this lesson: `stat -fc %T /sys/fs/cgroup/`, `systemd-cgls`, `systemd-cgtop`, and `tree -L 2 -d /sys/fs/cgroup/kubepods.slice`.

Proper fix on a v1 node: run the node on cgroup v2. All current LTS distributions (Ubuntu 22.04+, Debian 11+, RHEL 9+) default to v2. On a node that was forced to v1, boot with `systemd.unified_cgroup_hierarchy=1` (section 6.3) or move to a newer distribution image. All labs in this guide assume cgroup v2 (see the conventions file).

The exact kubelet message is in section 6.3. On v1.37.0 the field is visible in the live config: REAL OUTPUT (kind): `failCgroupV1: true` from `/configz`.

### 2.14 The OOM killer, `memory.events`, exit code 137, `OOMKilled`

When a cgroup hits `memory.max` the kernel first tries to **reclaim** memory (drop page cache, swap if allowed). If it cannot get below the limit, the **OOM killer** kills a process **inside that cgroup**. This is a *cgroup OOM* (kernel message says `constraint=CONSTRAINT_MEMCG`). It is different from a *node OOM*, when the whole machine is out of memory and the kernel picks victims by `oom_score_adj` (that is when QoS class matters). Kubernetes also has a third thing, **node-pressure eviction**, done by the kubelet before the kernel gets to OOM. Do not confuse them.

What you see, in the order the story unfolds:

1. The kernel log (`dmesg -T`, or `journalctl -k` on a VM) says the cgroup killed a process. REAL OUTPUT (kind node, root): `dmesg | grep -iE 'oom-kill:|Killed process'` after a Pod with a 64Mi limit ran out of memory (long cgroup paths shortened with `...`):

```text

Memory cgroup out of memory: Killed process 618463 (bash) total-vm:4044kB, ... oom_score_adj:999
Memory cgroup out of memory: Killed process 618464 (head) total-vm:2292kB, ... oom_score_adj:999
Memory cgroup out of memory: Killed process 618465 (tr) total-vm:2304kB, ... oom_score_adj:999
```

   How to read it: `constraint=CONSTRAINT_MEMCG` means a **cgroup limit**, not the whole node. `oom_memcg=` is the cgroup that hit its limit and `task_memcg=` the cgroup of the victim. `cpuset=cri-containerd-<id>.scope` names the container. `anon-rss:64596kB` is about the 64Mi limit. 2. The `memory.events` file of the cgroup counts it. REAL OUTPUT (Docker), after `tail /dev/zero` (reads without end until memory is full) in a container with `--memory 64m --memory-swap 64m`:

   REAL OUTPUT (kind): the **Pod slice** of the restarting Pod after several restarts: `max 7584`, `oom 3`, `oom_kill 13`, `oom_group_kill 3`, `memory.max 67108864`. `oom_group_kill 3` = three whole-container kills, `oom_kill 13` = the processes killed in them.

3. The killed process receives SIGKILL (signal 9). A shell reports exit code `128 + 9 = 137`. REAL OUTPUT (Docker): `docker run --rm --memory 64m --memory-swap 64m ubuntu:24.04 tail /dev/zero; echo $?` printed `137`.
4. The runtime reports it and the kubelet writes it to the Pod status. REAL OUTPUT (kind): `k describe pod hog` shows

```text

      Reason:       OOMKilled
      Exit Code:    137
```

   **But the reason is not always `OOMKilled`.** REAL OUTPUT (kind): the same Pod, polled while it restarted, first showed `Reason: Error` with `Exit Code: 137` (restart counts 1 and 2) and later `Reason: OOMKilled` with `Exit Code: 137` (restart count 3 and up), although the kernel killed it each time. The kernel log and `memory.events` were identical in both cases. So `Error` + `137` + a growing `oom_kill` is still an OOM kill; trust the cgroup counters over the label.

Notes:

- Exit code 137 alone is not proof of OOM. It means SIGKILL: it also appears after `kubectl delete` when the grace period ends. `oom_kill` in `memory.events` plus the kernel line "Memory cgroup out of memory" is the proof.
- `memory.events` on a **Pod slice** is hierarchical: it includes kills in the container scopes below it. A container that restarts gets a new scope with fresh counters, so look at the Pod slice to see the history of a restarting container.
- On cgroup v2 the kubelet sets `memory.oom.group = 1` on each container cgroup (REAL: `1`), so an OOM kills every process of that container together. The cgroups blog explains that `singleProcessOOMKill` defaults to `false` on cgroup v2; set it to `true` only to get the cgroup v1 behaviour (one process at a time). The scope is the container, not the whole Pod.

### 2.15 Tools for looking at the tree: `systemd-cgls`, `systemd-cgtop`

```bash
systemd-cgls                              # tree of all cgroups with their processes
systemd-cgls /kubepods.slice              # only below one slice (kind: /kubelet.slice/kubelet-kubepods.slice)
systemd-cgls --no-pager | less
systemd-cgtop                             # like top, per cgroup: tasks, %CPU, memory, I/O
systemd-cgtop -m -n 1 -b --depth=4        # sort by memory (-m), one batch iteration (-n 1 -b), 4 levels deep
```

`systemd-cgls` answers "which processes are in which Pod" (output and reading guide in section 2.9). `systemd-cgtop` answers "which Pod slice eats memory/CPU right now" (section 2.9). Use `systemd-cgls` as a cross-check of the `find` result (lab 7.2). They only work on nodes with systemd. Exam-host note: these are systemd tools and normally exist on a node, but are not in the exam's published tool list; the `/sys/fs/cgroup` files give the same information.

### 2.16 Under the hood: from `kubectl apply` to a number in a file

1. You create a Pod. The scheduler picks a node. The kubelet on that node sees the Pod.
2. The kubelet computes the QoS class and creates the **Pod cgroup** under the QoS slice (this is the `cgroupsPerQOS: true` default). It writes the Pod-level limits there.
3. The kubelet calls the CRI: `RunPodSandbox` (creates the pause container, namespaces; CNI sets up the network), then `CreateContainer` for each app container with the resources in the request.
4. containerd/runc creates the container: `clone()` with the namespace flags (or `setns()` to join the sandbox's net, uts and ipc), makes a cgroup scope under the Pod slice (via systemd), writes `memory.max`, `cpu.max`, `cpu.weight` and moves the process in.
5. From then on the kernel enforces everything. The kubelet only reads the counters (cAdvisor) and updates the Pod status.

### 2.17 Related but different

| Often confused | The difference |
|---|---|
| Namespace (Linux) vs namespace (Kubernetes) | A Kubernetes Namespace is an API grouping for names and RBAC. A Linux namespace isolates kernel resources. Unrelated, same word |
| `limits` vs `requests` | `limits` = hard cap (`memory.max`, `cpu.max`). `requests` = scheduling and relative share (`cpu.weight`) |
| `memory.max` vs `memory.high` | max kills, high slows |
| OOMKilled vs Evicted | OOMKilled = kernel killed a container over its limit. Evicted = the kubelet removed a whole Pod because the **node** was under pressure |
| `kubectl exec` vs `nsenter` | `exec` goes through the API server and the runtime into one container. `nsenter` is run on the node by root, no API needed |
| `shareProcessNamespace` vs `hostPID` | First: containers of one Pod share a pid ns. Second: the Pod uses the **node's** pid ns |

## 3. How it works (diagram)

ASCII tree of a systemd-driver node (kubeadm layout). kind nodes add one extra top level (`kubelet.slice/kubelet-kubepods.slice/...` with `kubelet-` in front of the names; captured in section 2.9).

```text
/sys/fs/cgroup                                         <- cgroup2fs mount, root of the unified tree
|-- cpu.max / memory.max / ...                         <- (root has few files)
|-- system.slice/ ...  (sshd, containerd.service, kubelet.service)
|-- kubepods.slice/                                    <- ALL Pods.  memory.max = node allocatable memory
|   |
|   |-- kubepods-pod<UID_G>.slice/                     <- GUARANTEED pod (no QoS slice)
|   |   |-- memory.max      = sum of container limits   (e.g. 134217728)
|   |   |-- cpu.max         = sum of CPU limits         (e.g. 50000 100000)
|   |   |-- cpu.weight      <- from requests.cpu (kubelet formula)
|   |   |-- cri-containerd-<SANDBOX_ID>.scope/         <- pause container (sandbox)
|   |   `-- cri-containerd-<CONTAINER_ID>.scope/       <- app container
|   |       |-- memory.max  <- limits.memory
|   |       |-- memory.current / memory.stat / memory.events   <- usage, OOM counters
|   |       |-- cpu.max     <- limits.cpu  (quota period)
|   |       |-- cpu.weight  <- requests.cpu (runtime formula)
|   |       |-- cpu.stat    <- nr_throttled
|   |       |-- pids.max
|   |       `-- cgroup.procs <- PIDs of the container (pick one for nsenter -t)
|   |
|   |-- kubepods-burstable.slice/                      <- BURSTABLE QoS slice
|   |   `-- kubepods-burstable-pod<UID_B>.slice/       <- one pod (UID with "-" -> "_")
|   |       |-- memory.events       <- hierarchical: includes container kills below
|   |       |-- cri-containerd-<SANDBOX_ID>.scope/
|   |       `-- cri-containerd-<CONTAINER_ID>.scope/
|   |
|   `-- kubepods-besteffort.slice/                     <- BESTEFFORT QoS slice
|       `-- kubepods-besteffort-pod<UID_E>.slice/
|           `-- cri-containerd-<CONTAINER_ID>.scope/   <- memory.max = max, cpu.max = "max 100000", cpu.weight = 1
`-- ...
```

How to read it:

1. The path from the root to a container scope is the whole story of a Pod: `kubepods.slice` (all Pods) -> QoS class -> Pod -> container. Guaranteed Pods skip the QoS level.
2. Limits live at the container scope (`limits.memory` -> `memory.max`, `limits.cpu` -> `cpu.max`) and the kubelet also sets sums on the Pod slice, so a Pod cannot exceed the total even if containers are added.
3. The pause/sandbox container has its own scope under the same Pod slice. If you count two scopes in a one-container Pod, that is why.
4. A Pod's UID in a slice name uses underscores (`1234abcd_5678_...`). To find a Pod's directory, replace `-` with `_` and use `find -name '*pod<uid>.slice'`.
5. `cgroup.procs` of a scope gives real PIDs. `/proc/<pid>/ns/*` of that PID gives the namespaces, and `nsenter -t <pid>` enters them. Cgroups and namespaces meet at the PID.

## 4. Commands and YAML you must produce fast

### 4.1 Imperative shortcuts

```bash
# Node side (after ssh <node>; sudo -i). Which cgroup version?
stat -fc %T /sys/fs/cgroup                         # cgroup2fs = v2

# List network namespaces (one per Pod + host). Root sees all.
lsns -t net

# Get a Pod's container ID, then its cgroup directory on the node
CID=$(k get pod web -n lab-t110 -o jsonpath='{.status.containerStatuses[0].containerID}'); CID=${CID#*://}
# on the node:
D=$(find /sys/fs/cgroup -type d -name "*${CID}*" | head -1); echo $D

# Read the limits of that container
cat $D/memory.max $D/cpu.max $D/cpu.weight

# Enter the Pod's network namespace with the node's tools
PID=$(head -1 $D/cgroup.procs); nsenter -t $PID -n ip a

# Any process in the cgroup tells you its own cgroup
cat /proc/$PID/cgroup                              # 0::/kubepods.slice/.../cri-containerd-<id>.scope

# Own mini-container
unshare --fork --pid --mount-proc bash

# Memory kill evidence
journalctl -k | grep -i oom                        # on kind nodes use: dmesg | grep -i oom
cat $D/memory.events; grep nr_throttled $D/cpu.stat
```

One line each:

- `stat -fc %T /sys/fs/cgroup`: prints the filesystem type of the cgroup mount: `cgroup2fs` = v2.
- `lsns -t net`: one row per network namespace, with the lowest PID in it.
- `jsonpath ...containerID`: Pod status holds the runtime ID as `containerd://<64 hex chars>`; `${CID#*://}` removes the prefix. The ID is empty until the container has started, so run `k wait --for=condition=Ready pod/web` first.
- `find ... -name "*${CID}*"`: works with any driver and any layout (systemd or cgroupfs, kind or kubeadm), so you do not have to remember paths.
- `head -1 $D/cgroup.procs`: first PID in the container's cgroup, usable as `nsenter -t`.
- `nsenter -t $PID -n ip a`: the node's `ip` command run inside the Pod's network namespace. Works even when the image has no `ip`.

Shortcut if `crictl` is available on the node (it is not listed among the exam tools, so do not rely on it there): `crictl ps --name web -q`, `crictl inspect <id> | grep -i cgroupsPath` (the value is a systemd unit path `slice:cri-containerd:id`, not a directory).

### 4.2 Declarative YAML: a Pod whose cgroup values you can predict

```yaml
# qos-demo.yaml : Burstable Pod (requests < limits)
apiVersion: v1                # Pod is core/v1
kind: Pod
metadata:
  name: web                   # Pod name; the Pod UID (not the name) appears in the cgroup path
  namespace: lab-t110         # one namespace per lesson (conventions)
spec:
  containers:
  - name: web
    image: nginx:1.27         # pinned tag, never :latest
    resources:
      requests:               # used for scheduling, QoS class and cpu.weight
        cpu: 250m             # default: none. -> cpu.weight (relative share only under contention)
        memory: 64Mi          # default: none. NOT written to a cgroup file by default
      limits:                 # hard caps
        cpu: 500m             # -> cpu.max "50000 100000". Risky: very small values cause throttling
        memory: 128Mi         # -> memory.max 134217728. Risky: below real use = OOMKilled. Must be >= request
```

Field notes: `limits` below `requests` is rejected by the API server (`must be less than or equal to memory limit`). If you set only `limits`, `requests` default to the same values. Setting both equal in every container makes the Pod Guaranteed. `memory: 128M` (no `i`) means 128,000,000 bytes, not 128 MiB. A common slip.

Generate a starting file fast:

```bash
k run web --image=nginx:1.27 -n lab-t110 $do > qos-demo.yaml   # then add the resources block
```

(`k run` has no flags for resources in v1.37, so you edit the file. For Deployments `k set resources deploy/x --limits=cpu=500m,memory=128Mi --requests=cpu=250m,memory=64Mi` works.)

## 6. Common mistakes and how to fix them

| Symptom | What you will see (exact error/event text) | Cause | Fix (command) |
|---|---|---|---|
| Pod `OOMKilled` although the app "only uses 100 MiB" under a 128 MiB limit | `Last State: Terminated  Reason: OOMKilled  Exit Code: 137` (the reason can also read `Error` with `137`, section 2.14) | The limit counts **everything charged to the cgroup**: anonymous memory plus page cache (files read/written), tmpfs / `emptyDir.medium: Memory` data, and kernel memory. App-level metrics show only heap | Read `memory.current` and `memory.stat`; raise `limits.memory` (in-place with `--subresource resize`, or delete and recreate) or reduce the tmpfs/cache use |
| App slow / high latency at low CPU use | App logs timeouts. No error in `k describe`. `cpu.stat` shows `nr_throttled` growing | CPU limit enforced with CFS quota pauses all threads for the rest of each 100 ms period | `grep throttled $D/cpu.stat`; raise or remove `limits.cpu` (keep `requests.cpu`) |
| Node: kubelet will not start | `systemctl status kubelet` is `failed`; journal has `kubelet is configured to not run on a host using cgroup v1. cgroup v1 support is unsupported and will be removed in a future release` | Node booted with cgroup v1 or hybrid; kubelet refuses since v1.35 | Boot with `systemd.unified_cgroup_hierarchy=1`, or use a newer OS image |
| A container shows all host processes | `k exec x -- ps aux` lists `kubelet`, `containerd`, `/sbin/init`... | `hostPID: true` in the Pod spec | Remove `hostPID`, recreate the Pod |

### 6.1 OOMKilled under the "theoretical" limit: reasoning and diagnosis

Think: the kernel does not know what your "app" is. It adds up what is **charged to the cgroup**. Walk down this path:

```bash
# 1. Confirm it was OOM (not eviction or a crash)
k describe pod x | grep -A4 'Last State'          # Reason OOMKilled (or Error), Exit Code: 137
# 2. On the node, find the container cgroup ($D, see section 4.1) and read the ceiling and usage
cat $D/memory.max $D/memory.current
# 3. Break usage down
grep -E '^(anon|file|shmem|kernel|slab) ' $D/memory.stat
# 4. Count kills (use the Pod slice, the container scope is replaced on each restart)
cat $(dirname $D)/memory.events
# 5. Kernel log for the full line
journalctl -k | grep -i 'out of memory'            # kind node: dmesg | grep -i 'out of memory'
```

How to read step 3: `anon` is private heap/stack (your app's own use). `file` is page cache; the kernel can reclaim it, so it alone rarely causes an OOM. `shmem` is tmpfs and shared memory (`/dev/shm`, `emptyDir` with `medium: Memory`); it is **not** reclaimable without swap, so it is the usual "invisible" cause. `kernel`/`slab` are kernel structures for your files and sockets. Compare `anon + shmem` to `memory.max`: if their sum is near the limit, the limit is simply too low or something writes into memory-backed storage. (REAL, Docker, 100 MB held in a shell variable: `anon 100585472`, `file 32768`, `memory.current 101597184`.)

Fix: raise `limits.memory` to the real peak plus headroom, or put big temporary data on a disk-backed `emptyDir` (default medium) with `sizeLimit`. How to apply: `k patch pod x --subresource resize --patch ...` for a running Pod (v1.37), or `k delete pod x`, edit the YAML and apply; in a Deployment edit the template and let the rollout run.

### 6.2 CPU throttling

```bash
# 1. Is there a CPU limit?
k get pod x -o jsonpath='{.spec.containers[*].resources.limits.cpu}'
# 2. On the node: read the limit and the counters
cat $D/cpu.max
cat $D/cpu.stat
# 3. Compute the ratio, then re-read 10 seconds later to see growth
awk '/nr_periods/{p=$2}/nr_throttled/{t=$2}END{print t/p}' $D/cpu.stat
```

A ratio near 0 means no throttling. A growing `nr_throttled` and `throttled_usec` while the app is slow is the proof (REAL example in section 2.12: ratio `1`). Fix: raise the limit (for example `500m` -> `2`) or remove `limits.cpu`. On v1.37 a running Pod can be changed with `k patch pod x --subresource resize --patch '{"spec":{"containers":[{"name":"c","resources":{"limits":{"cpu":"2"}}}]}}'`; the fallback is delete and recreate (Deployment: edit the template).

### 6.3 kubelet will not start on cgroup v1

```bash
# 1. Why did it stop?
systemctl status kubelet --no-pager
journalctl -u kubelet --no-pager | tail -20      # look for the cgroup v1 message
# 2. Which cgroup version does the node run?
stat -fc %T /sys/fs/cgroup                       # tmpfs = v1, cgroup2fs = v2
cat /proc/cmdline                                # look for systemd.unified_cgroup_hierarchy=0 or cgroup_no_v1
```

The message: `kubelet is configured to not run on a host using cgroup v1. cgroup v1 support is unsupported and will be removed in a future release`. This text was read from the strings of the v1.37.0 kubelet binary on the kind node; the failure itself was not reproduced because kind nodes are on cgroup v2 (section 11). With `failCgroupV1: false` the kubelet instead logs a warning, `cgroup v1 detected. cgroup v1 support is deprecated and will be removed in a future release. Please migrate to cgroup v2.`

Fix on a systemd/GRUB machine, then reboot:

```bash
# add the parameter to GRUB_CMDLINE_LINUX in /etc/default/grub:
#   GRUB_CMDLINE_LINUX="... systemd.unified_cgroup_hierarchy=1"
sudo update-grub && sudo reboot
# after reboot
stat -fc %T /sys/fs/cgroup && systemctl restart kubelet
```

This is a general Linux administration skill. Which distribution the exam hosts run (summary E22) and whether an exam task lets you reboot a node are UNVERIFIED; the exam tips page only forbids rebooting host `base` (https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad). Do not rely on this fix being available in an exam task.

Temporary workaround only (not recommended): `failCgroupV1: false` in `/var/lib/kubelet/config.yaml`, then `systemctl restart kubelet`. The blog says this fallback is scheduled for removal in v1.38.

### 6.4 Container sees host processes (`hostPID: true`)

```bash
k get pod x -o jsonpath='{.spec.hostPID}{" "}{.spec.hostNetwork}{" "}{.spec.hostIPC}{"\n"}'   # true false false
k exec x -- ps aux | head                                                                       # sees kubelet etc.
```

REAL OUTPUT (kind): in a Pod with `hostPID: true`, `ps` shows the node's processes:

```text

    1 root      0:00 {systemd} /sbin/init
```

### 7.1 Easy: create PID and net namespaces with `unshare`, enter them with `nsenter`, then build a cgroup by hand

**Environment:** linux-vm. Two terminals on the VM, called A and B. Exam-host note: `unshare`, `nsenter`, `lsns`, `pgrep` are lab tools. The `/proc` equivalents are `readlink /proc/<pid>/ns/net` and `cat /proc/<pid>/cgroup`.

**Setup**

```bash
mkdir -p ~/lab/t110 && cd ~/lab/t110

```

**Task**

Part A (namespaces)

1. In terminal A start a shell in new PID, mount (for `/proc`), UTS and network namespaces. Inside it set the hostname to `lab-ns` (this must not change the VM's hostname).
2. In terminal B find the PID of that inner shell and, using only `nsenter` from the VM, show: its interfaces, its processes and its hostname. Note that two processes are involved: `unshare` itself (which put **itself** in the new network namespace, then forked) and the `bash` child that is PID 1 of the new PID namespace. `lsns` shows the first one. You need the second one for `nsenter -p`.
3. Write three lines to `~/lab/t110/ns.txt`: the net namespace inode of the inner shell, the net namespace inode of your terminal-B shell, and the number of interfaces in the inner shell's net namespace.

Part B (cgroup by hand, as root in terminal B)

4. Create the cgroup `/sys/fs/cgroup/t110demo`. Set `pids.max` to `5` and show that a shell in it cannot start 8 background `sleep 20` processes. Then (swap off for this group, `memory.swap.max` = `0`) set `memory.max` to `40M` and run `x=$(head -c 100000000 /dev/zero | tr "\0" a)` in it so it is OOM-killed. Then set `cpu.max` to `20000 100000` and run a busy loop for 3 seconds. Write the three evidence numbers (refused forks from `pids.events`, `oom_kill` from `memory.events`, `nr_throttled` from `cpu.stat`) to `~/lab/t110/cg.txt`, one per line. Remove the cgroup afterwards.

<details><summary>Hint 1</summary>

`sudo unshare --fork --pid --mount-proc --uts --net bash`. Run `sudo lsns -t net` in B. You will see the new namespace, but its lowest PID belongs to the `unshare` process, not to `bash`.
</details>

<details><summary>Hint 2</summary>

`UPID=$(pgrep -x unshare)` then `PID=$(pgrep -P $UPID -x bash)`. To see processes you need the PID **and** mount namespace: `nsenter -t $PID -p -m ps -e`. For part B use `sudo -i`, `mkdir`, then `echo $$ > /sys/fs/cgroup/t110demo/cgroup.procs` inside a `bash -c '...'` so only that child is moved.
</details>

<details><summary>Hint 3</summary>

`readlink /proc/$PID/ns/net` (as root) gives `net:[inode]`. Count interfaces with `ip -o link | wc -l` run through `nsenter -n`. For part B, the counters are lines in `pids.events` (`max N`), `memory.events` (`oom_kill N`) and `cpu.stat` (`nr_throttled N`). A cgroup can only be removed with `rmdir` when it has no processes: write `1` to `cgroup.kill` first.
</details>

<details><summary>Solution</summary>

Terminal A (inside you are PID 1 of a new PID namespace; the new `/proc` is mounted automatically):

```bash
sudo unshare --fork --pid --mount-proc --uts --net bash
hostname lab-ns       # changes the hostname only in this uts namespace
hostname              # lab-ns
echo $$               # 1
ps -e -o pid,comm     # only bash and ps
ip -br a              # only lo, state DOWN
```

Terminal B:

```bash

sudo nsenter -t $PID -n ip -br a       # lo only
sudo nsenter -t $PID -p -m ps -e -o pid,comm
sudo nsenter -t $PID -u hostname       # lab-ns
hostname                               # VM's own name, unchanged
{ sudo readlink /proc/$PID/ns/net; readlink /proc/$$/ns/net; sudo nsenter -t $PID -n ip -o link | wc -l; } | tee ns.txt
```

REAL OUTPUT (kind node, root; the same commands, not an Ubuntu VM):

```text

4026533918 net       3  2913 unshare --fork --pid --mount-proc --uts --net bash -c hostname lab-ns; sleep 60; ...

    PID COMMAND
      1 bash
      3 sleep

```

Why each step: `unshare --fork` is needed so a child can be PID 1 of the new pid namespace; `--mount-proc` gives it a matching `/proc`; `nsenter -p -m` is needed together so `ps` reads the right `/proc`; `-n` alone is enough for `ip`, so the VM's own `ip` binary is used.

Part B (a root script run from your normal shell; `$1` is the output file path; only the `bash -c` children are moved into the cgroup):

```bash
cd ~/lab/t110
sudo bash -s "$PWD/cg.txt" <<'EOS'
mkdir /sys/fs/cgroup/t110demo && cd /sys/fs/cgroup/t110demo
echo 5 > pids.max
bash -c 'echo $$ > /sys/fs/cgroup/t110demo/cgroup.procs; for i in 1 2 3 4 5 6 7 8; do sleep 20 & done'
PIDS=$(awk '$1=="max"{print $2}' pids.events)
echo 1 > cgroup.kill; sleep 1; echo max > pids.max
echo 0 > memory.swap.max; echo 40M > memory.max
bash -c 'echo $$ > /sys/fs/cgroup/t110demo/cgroup.procs; x=$(head -c 100000000 /dev/zero | tr "\0" a)'
OOM=$(awk '$1=="oom_kill"{print $2}' memory.events)
echo max > memory.max; echo "20000 100000" > cpu.max
bash -c 'echo $$ > /sys/fs/cgroup/t110demo/cgroup.procs; timeout 3 sh -c "while :; do :; done"; true'
THR=$(awk '$1=="nr_throttled"{print $2}' cpu.stat)
printf '%s\n%s\n%s\n' "$PIDS" "$OOM" "$THR" > "$1"
cd /; echo 1 > /sys/fs/cgroup/t110demo/cgroup.kill; sleep 1; rmdir /sys/fs/cgroup/t110demo
EOS
cat cg.txt
```

Why: writing a PID to `cgroup.procs` moves that process (and the children it starts later) into the group; `pids.events` line `max N` counts refused forks; `memory.swap.max 0` makes `memory.max` kill instead of swapping; `oom_kill` in `memory.events` counts kills; `nr_throttled` in `cpu.stat` counts throttled periods. Values from the real run of the same commands on a kind node: `5`, `1` and `31`.
</details>

### 7.3 Break-fix: a memory-hungry Pod keeps restarting

**Environment:** kind (`lab-worker` node, `onnode` defined as in 7.2). The kernel log: on a kind node `dmesg` works (the node is privileged) and `journalctl -k` is empty; on a linux-vm or kubeadm node use `journalctl -k` (or `dmesg -T`). Exam-host note: on an exam node you are already on it; use `dmesg`/`journalctl -k` and the cgroup files directly.

**Setup: the fault script `break.sh`** (it also writes `node.sh`, so the lab is self-contained)

```bash
mkdir -p ~/lab/t110 && cd ~/lab/t110
onnode() { docker exec -i lab-worker "$@"; }
cat > node.sh <<'EOF'
# runs on the node: $1 = container id. Prints: memory.max cpu.max(quota period) cpu.weight. Path goes to stderr.
d=$(find /sys/fs/cgroup -type d -name "*$1*" | head -1)
echo "$d" >&2
echo "$(cat $d/memory.max) $(cat $d/cpu.max) $(cat $d/cpu.weight)"
EOF
cat > break.sh <<'EOF'
#!/usr/bin/env bash
# creates Pod hog
kubectl get ns lab-t110 >/dev/null 2>&1 || kubectl create ns lab-t110
cat > ~/lab/t110/hog.yaml <<'YAML'
apiVersion: v1
kind: Pod
metadata:
  name: hog
  namespace: lab-t110
spec:
  nodeName: lab-worker
  containers:
  - name: hog
    image: ubuntu:24.04
    command: ["bash", "-c"]
    args:
    - |
      x=$(head -c 100000000 /dev/zero | tr '\0' a)
      echo "held ${#x} bytes"
      sleep 3600
    resources:
      requests: {cpu: 50m, memory: 32Mi}
      limits:   {memory: 64Mi}
YAML
kubectl apply -f ~/lab/t110/hog.yaml
EOF
bash break.sh
sleep 30; k -n lab-t110 get pod hog
```

REAL OUTPUT (kind), after 26 seconds: `hog   1/1   Running   2 (13s ago)   26s`. The Pod flips between `Running`, `OOMKilled`/`Error` and `CrashLoopBackOff` while `RESTARTS` grows.

**Task**

Pod `hog` in namespace `lab-t110` keeps restarting. Do not change the command.

1. Find out why and write evidence to `~/lab/t110/oom.txt`, four lines: (a) the termination reason as reported by Kubernetes, (b) the exit code, (c) the value of `oom_kill` from the `memory.events` file of the Pod's cgroup on the node, (d) the text of the kernel-log line that says `Memory cgroup out of memory` (one line is enough).
2. Fix the Pod so that it stays `Running` for at least 60 seconds with `restartCount` 0.
3. Show that `memory.max` of the new container's cgroup equals the new limit.

<details><summary>Hint 1</summary>

`k -n lab-t110 get pod hog` shows a growing `RESTARTS`. `k describe pod hog` has `Last State`. The reason is in `.status.containerStatuses[0].lastState.terminated`. Be aware that the reason can be `OOMKilled` or `Error`; the exit code is 137 in both cases, so use the cgroup and the kernel log to settle it.
</details>

<details><summary>Hint 2</summary>

The container scope is replaced on each restart. The **Pod slice** keeps the counters of all its containers: find it with the Pod UID, dashes replaced by underscores: `find /sys/fs/cgroup -type d -name "*pod${U//-/_}.slice"` with `U=$(k -n lab-t110 get pod hog -o jsonpath='{.metadata.uid}')`. The kernel log is `dmesg | grep 'Memory cgroup out of memory'` (kind) or `journalctl -k | grep 'Memory cgroup out of memory'` (VM).
</details>

<details><summary>Hint 3</summary>

The program really needs about 190 MiB at its peak (the `$(...)` buffer grows by doubling), so 100 MiB is not enough. Use 256Mi. The fastest way to apply it: edit `hog.yaml` and `k replace --force -f hog.yaml` (delete and recreate). The alternative on v1.37 is in-place: `k patch pod hog --subresource resize --patch '{"spec":{"containers":[{"name":"hog","resources":{"limits":{"memory":"256Mi"}}}]}}'`.
</details>

<details><summary>Solution</summary>

Diagnose in order:

```bash
cd ~/lab/t110
k -n lab-t110 get pod hog                                  # RESTARTS grows
k -n lab-t110 describe pod hog | grep -A4 'Last State'     # Reason OOMKilled or Error, Exit Code 137
R=$(k -n lab-t110 get pod hog -o jsonpath='{.status.containerStatuses[0].lastState.terminated.reason}')
X=$(k -n lab-t110 get pod hog -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}')
U=$(k -n lab-t110 get pod hog -o jsonpath='{.metadata.uid}')
OOM=$(onnode bash -c "d=\$(find /sys/fs/cgroup -type d -name '*pod${U//-/_}.slice' | head -1); grep '^oom_kill ' \$d/memory.events | cut -d' ' -f2")
LOG=$(onnode dmesg | grep 'Memory cgroup out of memory' | tail -1)
printf '%s\n%s\n%s\n%s\n' "$R" "$X" "$OOM" "$LOG" | tee oom.txt
```

REAL OUTPUT (kind) of the kernel log and counters: see section 2.14 (`oom-kill:constraint=CONSTRAINT_MEMCG ...`, `Memory cgroup out of memory: Killed process ... (bash) ... anon-rss:64596kB ... oom_score_adj:999`, and Pod-slice `memory.events` `max 7584`, `oom 3`, `oom_kill 13`, `oom_group_kill 3`, `memory.max 67108864`).

How to read it: exit code `137` is SIGKILL. The kernel line has `constraint=CONSTRAINT_MEMCG`, so a cgroup limit was hit, not the whole node. `anon-rss` of about 64 MB equals the 64Mi limit. `oom_kill` greater than 0 is the kernel's own count and cannot be produced by a normal exit. The `Reason` is `OOMKilled` or sometimes `Error` (observed on the first restarts); the other three pieces of evidence do not change.

Fix: the process legitimately holds about 100 MB of data and peaks higher, so the limit is simply too low. Set 256Mi:

```bash
sed -i.bak 's/memory: 64Mi/memory: 256Mi/' hog.yaml     # the line with limits (requests stay 32Mi)
grep -n memory hog.yaml                                  # 32Mi (request) and 256Mi (limit)
k replace --force -f hog.yaml
k -n lab-t110 wait --for=condition=Ready pod/hog --timeout=60s
```

REAL OUTPUT (kind): after the replace, 45 seconds later: `Running restarts=0`, `k logs hog` printed `held 100000000 bytes`, and the new container's cgroup had `memory.max` `268435456` and `cpu.weight` `11` (request 50m). ## 8. Exam tips

- You get node shells with `ssh <node>` then `sudo -i`, and the tools on those hosts are `kubectl`, `yq`, `curl`, `wget` and `man` (source: [Linux Foundation exam tips](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)). `find`, `cat`, `grep` and `/proc` are standard on Linux nodes (the exam host OS is UNVERIFIED, summary E22). `crictl`, `lsns`, `nsenter`, `unshare` and `systemd-cgls` are part of normal Linux/Kubernetes nodes, but their presence on exam hosts is UNVERIFIED, so know the `/proc` and `/sys/fs/cgroup` way too.
- Do not memorise cgroup paths. Memorise the recipe: container ID from `jsonpath` -> `find /sys/fs/cgroup -name "*<id>*"` -> `cat memory.max cpu.max`.
- A Pod "keeps restarting": check `k describe pod` for `Exit Code: 137` and `OOMKilled` first (or `Error` with 137, which can still be an OOM). That takes 10 seconds and decides between "raise the memory limit" and "look at the app logs" (`k logs --previous`).
- Docs to open (all allowed on the exam): [cgroups](https://kubernetes.io/docs/concepts/architecture/cgroups/), [User namespaces](https://kubernetes.io/docs/concepts/workloads/pods/user-namespaces/), [Resource management for Pods and containers](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/) (it has a full "How Pods with resource limits are run" section and the QoS rules). The blog [The Shift to cgroup v2](https://kubernetes.io/blog/2026/10/06/kubernetes-cgroups-v2-shift/) is also allowed (kubernetes.io/blog) and lists the troubleshooting commands.
- Traps: `128M` is not `128Mi`; `limits` lower than `requests` is rejected; a plain `k edit`/`k patch` of Pod resources is rejected, so use `--subresource resize` (CPU and memory only) or `k replace --force -f`; `memory.high` never kills; `hostPID`, `hostNetwork` and `hostIPC` are the node's namespaces, not the Pod's.
- If the kubelet is down on a node, check `stat -fc %T /sys/fs/cgroup` and `journalctl -u kubelet` early; the cause can be OS-level and not in any manifest.

## 9. Quick review

1. Which command shows whether a node uses cgroup v2, and what does it print?
2. Why does `unshare --pid bash` fail without `--fork`, and what does `--mount-proc` add?
3. Name the namespaces all containers of a Pod share by default, and the one that is not shared but can be.
4. A Pod has `limits: {memory: 256Mi, cpu: "2"}`. What exactly will be in `memory.max` and `cpu.max`?
5. Which Pod field turns into `cpu.weight`, and why is that value not a cap?
6. In which directory does a Guaranteed Pod live compared with a Burstable one?
7. A Pod shows `Exit Code: 137` but not `OOMKilled`. What else can cause 137, and how do you tell?
8. Why can a Pod be OOMKilled although the application's heap is below the limit?
9. How can you see CPU throttling, and which two fixes are valid?
10. What changed for the kubelet on cgroup v1 nodes in Kubernetes v1.35, and what is the proper fix?

<details><summary>Answers</summary>

1. `stat -fc %T /sys/fs/cgroup`; `cgroup2fs` means v2 (`tmpfs` means v1).
2. The calling process does not join the new PID namespace, only its children do, so a child must be forked to be PID 1 (otherwise: `Cannot allocate memory`). `--mount-proc` mounts a fresh `/proc` that matches the new PID namespace, so `ps` shows only the new namespace's processes.
3. Shared: net, uts, ipc. Not shared but can be: pid (`shareProcessNamespace: true`). The mount namespace is separate per container.
4. `memory.max` = `268435456` (256 * 1048576). `cpu.max` = `200000 100000` (quota 200 ms per 100 ms period = 2 CPUs).
5. `requests.cpu`; it is a relative weight used only when CPUs are contended. A Pod can use more than its weight share when other Pods are idle. The cap is `limits.cpu` -> `cpu.max`.
6. Guaranteed: directly under `kubepods.slice` (`kubepods-pod<uid>.slice`). Burstable: under `kubepods-burstable.slice`. BestEffort: under `kubepods-besteffort.slice`.
7. SIGKILL from anything, for example a delete whose grace period ran out. Also a real OOM kill that Kubernetes labelled `Error` (observed on the first restarts). Tell them apart with `oom_kill` in `memory.events` and the kernel line "Memory cgroup out of memory".
8. The cgroup counts page cache, tmpfs (`emptyDir` with `medium: Memory`, `/dev/shm`) and kernel memory too, not only the heap. Read `memory.stat` (`anon`, `file`, `shmem`, `kernel`).
9. `cpu.stat`: growing `nr_throttled` and `throttled_usec` (ratio `nr_throttled/nr_periods`). Fixes: raise or remove `limits.cpu` (keep the request), or reduce the number of busy threads. (Lowering the request is not a fix.)
10. The kubelet refuses to start on cgroup v1 nodes by default (`failCgroupV1` defaults to `true`). The proper fix is to run the node on cgroup v2 (for example boot with `systemd.unified_cgroup_hierarchy=1` or use a newer OS image), not the temporary `failCgroupV1: false` override, which the blog says is scheduled for removal in v1.38.

</details>
