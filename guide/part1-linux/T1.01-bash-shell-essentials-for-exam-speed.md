## 1. Why this matters

Every task in the CKA and CKAD exams is solved by typing commands into a Bash terminal. The Linux Foundation says the exams are "15-20 performance-based tasks" solved on the command line, and that the exam lasts 2 hours (sources: [tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad), [FAQ](https://docs.linuxfoundation.org/tc-docs/certification/faq-cka-ckad-cks)). That is about 6 minutes per task, so every second you lose to retyping a long command, losing an error message, or fighting a quote is a second you do not have.

In real life the same habits stop outages. A redirection that sends errors to the wrong place hides the real failure. A script without `set -euo pipefail` carries on after a failed step and deletes the wrong thing. A heredoc whose delimiter is quoted (or not) writes a manifest with `$HOME` literally in it, or with your own home directory baked in.

If you do not know this topic you will still pass tasks, but slowly: typing `kubectl` 300 times, copying YAML by hand, and missing the typo that shows up as a silent empty file.

## 2. Concepts

### 2.1 Shell vs terminal; interactive vs login shell; ~/.bashrc vs ~/.bash_profile

**Terminal (terminal emulator).** A window that shows text and sends your key presses to a program. It does not understand commands.

**Shell.** The program inside that window that reads a line, expands it, starts programs and reports their exit code. Bash ("Bourne Again SHell") is the shell used here. `sh`, `zsh` and `fish` are other shells.

**Why it matters.** Two settings decide which startup files Bash reads. They are independent, so there are four combinations.

| | Interactive (a human types, stdin is a terminal) | Non-interactive (runs a script or `bash -c`) |
|---|---|---|
| **Login** (first shell of a session: `ssh host`, `bash -l`) | reads `/etc/profile`, then the first of `~/.bash_profile`, `~/.bash_login`, `~/.profile` that exists | same as left, but only if started with `-l` |
| **Non-login** (a terminal tab, `bash` typed inside a shell) | reads `/etc/bash.bashrc` (Debian/Ubuntu) and `~/.bashrc` | reads nothing (unless `BASH_ENV` is set) |

Facts that follow from the table:

- `~/.bashrc` is for interactive non-login shells. Put aliases, `$do` and completion here.
- `~/.bash_profile` / `~/.profile` is for login shells. Put things that run once per session here (extra `PATH` entries, for example).
- Because people open both kinds of shell, the usual fix is a one-line bridge: the login file sources `~/.bashrc`. Ubuntu's default `~/.profile` already does this (it contains `. "$HOME/.bashrc"` guarded by `if [ -n "$BASH_VERSION" ]`).
- If `~/.bash_profile` exists, Bash does not read `~/.profile` at all. Creating a `~/.bash_profile` without the bridge line silently disables your `.bashrc` for SSH logins.
- A script never reads `~/.bashrc`, so your aliases do not exist in scripts (see 2.11).

The next block shows the rule on a scratch home directory where each file prints a marker. `.bash_profile` contains the bridge line, which is why `.bashrc` appears in cases 2 and 3.

```text
REAL OUTPUT (Docker)
1) bash -i (interactive, non-login)
  [read .bashrc]
2) bash -l -c true (login, non-interactive)
  [read .bash_profile]
  [read .bashrc]
3) bash -li -c true (login + interactive)
  [read .bash_profile]
  [read .bashrc]
4) bash -c true (neither)
5) bash -l after removing .bash_profile
  [read .profile]
6) shell flags: `echo $-` in `bash -i` -> hiBHc  (the i means interactive)
```

Check which kind of shell you are in:

```bash
echo $0                 # bash   (a login shell often shows -bash)
echo $-                 # contains i when interactive
shopt login_shell       # login_shell    off   (or on)
```

**Under the hood.** `$SHELL` is the shell recorded in `/etc/passwd` for your user. It is not necessarily the shell you are running right now. Use `ps -p $$ -o comm=` (`$$` is the PID of the current shell) to see the real one. Every time you type a command, Bash forks a child process and the child runs the program. That is why a variable you set in the parent is not seen by the child unless you `export` it (2.6).

**Related but different.** `source file` (or `. file`) runs a file inside your current shell, so its aliases and variables stay. `bash file` or `./file` runs it in a child shell, so they vanish when it ends.

### 2.2 Navigation: pwd, cd -, ls -la, absolute vs relative paths, ~ expansion

| Command | Meaning |
|---|---|
| `pwd` | print the current (working) directory |
| `cd /etc` | go to an absolute path (starts with `/`; same result from anywhere) |
| `cd ../x` | relative path (resolved from where you are now; `.` is here, `..` is the parent) |
| `cd -` | go back to the previous directory and print it (Bash keeps it in `$OLDPWD`) |
| `cd` or `cd ~` | go to your home directory |
| `ls -la` | long listing (`-l`) including names that start with a dot (`-a`) |

`~` is expanded by the shell, not by the program: `~` becomes `$HOME`, `~root` becomes root's home, `~+` becomes `$PWD`. Because the shell does it, `~` inside quotes is NOT expanded (`"~/x"` is a directory literally named `~`).

```text
REAL OUTPUT (Docker)
$ pwd
/home/lab
$ cd /etc ; pwd
/etc
$ cd -
/home/lab
$ echo ~root ~lab
/root /home/lab
```

```text
REAL OUTPUT (Docker)   # ls -la in a directory that has f1.yaml f2.yaml f3.txt .hidden and a/
total 0
drwxr-xr-x 1 lab lab 56 Oct 27 06:25 .
drwxr-xr-x 1 lab lab 10 Oct 27 06:25 ..
-rw-r--r-- 1 lab lab  0 Oct 27 06:25 .hidden
drwxr-xr-x 1 lab lab  2 Oct 27 06:25 a
-rw-r--r-- 1 lab lab  0 Oct 27 06:25 f1.yaml
-rw-r--r-- 1 lab lab  0 Oct 27 06:25 f2.yaml
-rw-r--r-- 1 lab lab  0 Oct 27 06:25 f3.txt
```

(`total 0` and the tiny directory sizes are normal for empty files on the container's overlay file system.) Read the first column: `d` directory, `l` symlink, `-` regular file, then three `rwx` triplets for owner, group and others.

### 2.3 Files: cp -r, mv, rm -rf (danger), mkdir -p, touch, ln -s, file, stat

| Command | What it does | Risky when |
|---|---|---|
| `mkdir -p a/b/c` | create the directory and every missing parent; no error if it exists | never (it is the safe form) |
| `touch f` | create an empty file, or update its modification time | never |
| `cp a b` / `cp -r dir1 dir2` | copy a file / copy a directory tree (`-r` = recursive) | `cp` overwrites `b` without asking |
| `mv a b` | rename or move (same command for both) | overwrites `b` silently |
| `rm f` / `rm -r dir` / `rm -rf dir` | delete a file / a tree / a tree with no prompts and no errors for missing paths | `-f` hides every warning; there is no trash can |
| `ln -s target linkname` | symbolic link: a small file that holds the path `target` | link breaks if `target` moves |
| `file f` | guess the type from content | - |
| `stat f` | size, permissions, owner, timestamps, inode | - |

```text
REAL OUTPUT (Docker)
$ ln -s notes.txt link.txt; ls -l link.txt
lrwxrwxrwx 1 lab lab 9 Oct 27 06:25 link.txt -> notes.txt
$ file notes.txt link.txt a
notes.txt: empty
link.txt:  symbolic link to notes.txt
a:         directory
$ stat -c "%n | %F | %s bytes | mode=%a" notes.txt link.txt
notes.txt | regular empty file | 0 bytes | mode=644
link.txt | symbolic link | 9 bytes | mode=777
```

(The link is 9 bytes because that is the length of the string `notes.txt`.)

**`rm -rf` danger and the habit that prevents it.** The shell expands the glob BEFORE `rm` runs, so one stray space changes what is deleted. With files `keep.txt a.log b.log` in the directory:

```text
REAL OUTPUT (Docker)
$ echo rm -rf * .log          # what you typed by mistake (space after the star): echo shows what the shell built
rm -rf a.log b.log keep.txt .log
$ echo rm -rf /tmp/dg/*.log   # what you meant
rm -rf /tmp/dg/a.log /tmp/dg/b.log
```

The typo would delete everything in the directory. The habit: put `echo` in front of any `rm` with a glob, read the expanded line, then press Up and remove the `echo` (see history, 2.10). In the exam a wrong `rm -rf` can delete the very YAML you need.

### 2.4 Globbing: *, ?, [abc], brace expansion {a,b}, and quoting so globs don't expand

A **glob** is a pattern the shell turns into a list of matching file names before the program starts. The program never sees the pattern.

| Pattern | Matches | Example result (files f1.yaml f2.yaml f3.txt) |
|---|---|---|
| `*` | any string (including empty); does NOT match a leading dot | `ls *.yaml` -> `f1.yaml f2.yaml` |
| `?` | exactly one character | `ls f?.yaml` -> `f1.yaml f2.yaml` |
| `[abc]`, `[1-3]`, `[!a]` | one character from the set / range / not in set | `ls f[12].yaml` -> `f1.yaml f2.yaml` |
| `{a,b}`, `{1..3}` | **brace expansion**: the shell generates words. No files are looked at. | `echo f{1,2,3}.yaml` -> `f1.yaml f2.yaml f3.yaml` |

```text
REAL OUTPUT (Docker)
$ echo f{1,2,3}.yaml          # f3.yaml does not exist: braces never check
f1.yaml f2.yaml f3.yaml
$ echo {a..e}
a b c d e
$ mkdir -p demo-{dev,prod}; ls -d demo-*
demo-dev
demo-prod
$ echo *                      # the star skips .hidden
a a-copy demo-dev demo-prod f1.yaml f2.yaml f3.txt link.txt notes.txt old.txt x
$ echo "no match:" *.nomatch  # no match: the pattern stays literal (default Bash behaviour)
no match: *.nomatch
$ X=3; echo {1..$X}           # brace expansion runs before variables, so this is NOT 1 2 3
{1..3}
```

**Quoting so globs do not expand.** Sometimes the `*` must reach the program. In `k get pods -l 'app in (a,b)'` or `find . -name '*.yaml'` the pattern belongs to the program. Quote it with single quotes, double quotes or a backslash:

```text
REAL OUTPUT (Docker)
$ echo *.yaml
f1.yaml f2.yaml
$ echo "*.yaml"
*.yaml
$ echo \*.yaml
*.yaml
```

**Under the hood: the order of expansion.** Bash processes a command line in this order: brace expansion, tilde expansion, parameter/variable expansion + command substitution + arithmetic (left to right), word splitting, file-name expansion (globs), then quote removal. Redirections are handled after all of that. This order explains the `{1..$X}` result above (braces came first) and why an unquoted `$VAR` that contains spaces turns into several words (2.5).

**Risk.** An unquoted glob that matches nothing stays literal, so `rm *.logs` prints a confusing "No such file" about a file called `*.logs`. An unquoted glob that matches a file whose name starts with `-` is read as an option. Prefix with `./` or use `--`.

### 2.5 Quoting rules: single vs double quotes, escaping \$, why $(...) beats backticks

| Form | Variables (`$x`) | Command substitution `$(..)` | Globs | Use it for |
|---|---|---|---|---|
| `'single'` | no | no | no | text that must stay exactly as typed: jsonpath, regex, YAML with `$` |
| `"double"` | yes | yes | no | text with variables; also stops word splitting |
| no quotes | yes | yes | yes | simple words; **word splitting happens** |
| `\$` or `\"` | escapes the next character | - | - | one literal `$` inside double quotes |

```text
REAL OUTPUT (Docker)
$ N=world
$ echo "hello $N"
hello world
$ echo 'hello $N'
hello $N
$ echo "cost: \$5 and $N"
cost: $5 and world
$ V="a   b"; echo $V; echo "$V"       # unquoted: split into two words, spaces collapse
a b
a   b
```

A single quote cannot appear inside single quotes. To get one, close, add an escaped quote, reopen: `'it'\''s'`. If you need `$VAR` and also literal `{}`, use double quotes: `-o jsonpath="{.items[*].metadata.name}"` works because `{` and `[` have no special meaning inside double quotes.

**Command substitution.** `$(cmd)` runs `cmd` and pastes its output into the line. The older form is backticks: `` `cmd` ``. Prefer `$(...)`:

- It nests without escaping: `echo "ok: $(echo a$(echo b))"` prints `ok: ab`. Nested backticks need `\`` escapes that nobody reads correctly.
- Backslashes inside backticks behave differently from everywhere else.
- It is easy to see where it starts and ends.

```text
REAL OUTPUT (Docker)
$ echo "today: `date +%Y` vs $(date +%Y)"
today: 2026 vs 2026
$ echo "nested: $(echo outer-$(echo inner))"
nested: outer-inner
```

**Rule of thumb for the exam:** quote anything that has a `$`, `*`, `?`, `[`, `(`, `{`, space or `;` unless you want the shell to act on it. Use single quotes by default, double quotes when you need a variable.

### 2.6 Variables and export; env and printenv; PATH lookup; which / type -a

A **variable** is a name that holds text: `NS=lab-t101` (no spaces around `=`), read as `$NS` or `${NS}`. A variable is **shell-local** until you `export` it. Exported variables are copied into the environment of every child process.

```text
REAL OUTPUT (Docker)
$ MYVAR=local1
$ bash -c 'echo "child sees: [$MYVAR]"'      # not exported
child sees: []
$ export MYVAR
$ bash -c 'echo "child sees: [$MYVAR]"'      # exported
child sees: [local1]
$ FOO=temp bash -c 'echo "in cmd: $FOO"'     # one-command environment; parent stays clean
in cmd: temp
$ export FOO=bar; printenv FOO; unset FOO; printenv FOO; echo "rc=$?"
bar
rc=1
```

| Tool | Does |
|---|---|
| `env` | print the whole environment (or run a command with a changed environment) |
| `printenv NAME` | print one variable; exit code 1 if it is not set |
| `echo $NAME` | print a variable, set or not (an unset one prints an empty line) |
| `set` | print shell variables and functions too (long) |
| `unset NAME` | remove a variable |

A quoting surprise from the Docker run: the unquoted `echo child sees: [$MYVAR]` printed `child sees: a`, because `[local1]` is a glob (one character out of l, o, c, a, 1) and a directory named `a` existed. Quote anything in `[...]`.

**PATH lookup.** `PATH` is a colon-separated list of directories. When you type `kubectl`, Bash checks, in this order: alias, function, builtin/keyword, then each `PATH` directory from left to right. The first match wins, and Bash remembers it in a hash table (`hash -r` forgets it).

```text
REAL OUTPUT (Docker)
$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
$ type -a kubectl ; which kubectl
kubectl is /usr/local/bin/kubectl
/usr/local/bin/kubectl
$ type -a ls
ls is /usr/bin/ls
ls is /bin/ls
$ type -t cd; type -t if; type -t kubectl
builtin
keyword
file
$ mytool                         # in ~/bin, which is not in PATH
bash: mytool: command not found
$ echo $?
127
$ PATH=$PATH:$HOME/bin ; mytool ; type -a mytool
hi from mytool
mytool is /home/lab/bin/mytool
```

`type -a NAME` lists everything that answers to `NAME` (alias, function, builtin, every file in PATH), so it is the right tool to ask "what will actually run?". `which` is an external program that only searches PATH, so it cannot see aliases, functions or builtins. `type -t NAME` prints one word: `alias`, `function`, `builtin`, `keyword` or `file`.

The "command not found" exit code `127` and the "found but not executable" code `126` are worth remembering (2.9).

### 2.7 Redirection: >, >>, 2>, 2>&1, &>, /dev/null, tee, tee -a

Every process starts with three **file descriptors** (numbered handles to open files):

| fd | Name | Default | Typical use |
|---|---|---|---|
| 0 | stdin | keyboard / terminal | input |
| 1 | stdout | terminal | normal output |
| 2 | stderr | terminal | error messages and warnings |

Redirection changes where an fd points before the command starts. Bash implements it with the `open` and `dup2` system calls. Nothing in the program changes.

| Operator | Meaning | One-line demo |
|---|---|---|
| `> f` | stdout to file `f`, truncating it first | `echo one > out.txt` |
| `>> f` | stdout appended to `f` | `echo two >> out.txt` |
| `< f` | stdin from file `f` | `wc -l < t.txt` |
| `2> f` | stderr to file `f` | `ls /nonexistent 2> err.txt` |
| `2>&1` | make fd 2 point to wherever fd 1 points **right now** | `cmd > f 2>&1` |
| `&> f` | Bash shorthand for `> f 2>&1` (stdout and stderr to `f`) | `cmd &> f` |
| `&>> f` | same, appended | `cmd &>> f` |
| `> /dev/null` | throw stdout away (`/dev/null` is a file that swallows everything) | `cmd > /dev/null` |
| `2> /dev/null` | throw errors away | `cmd 2> /dev/null` |
| `<<< "text"` | here-string: a string as stdin | `grep -c line <<< "line a"` |
| `\| tee f` | copy stdin to `f` and to stdout (a "T" junction) | `cmd \| tee out.txt` |
| `\| tee -a f` | same, appending | `cmd \| tee -a out.txt` |

```text
REAL OUTPUT (Docker)       # cmd = ls /nonexistent /etc/hostname  (one path exists, one does not)
$ echo one > out.txt; echo two >> out.txt; echo three > out.txt; cat out.txt
three
$ cmd > out.txt 2> err.txt ; cat out.txt ; cat err.txt
/etc/hostname
ls: cannot access '/nonexistent': No such file or directory
$ cmd > both.txt 2>&1 ; cat both.txt
ls: cannot access '/nonexistent': No such file or directory
/etc/hostname
$ cmd &> both.txt ; cat both.txt            # same result, shorter
ls: cannot access '/nonexistent': No such file or directory
/etc/hostname
$ cmd 2>/dev/null                           # only stdout survives
/etc/hostname
$ cmd >/dev/null                            # only stderr survives
ls: cannot access '/nonexistent': No such file or directory
$ cmd &>/dev/null ; echo "rc=$?"            # nothing printed, but the exit code is still there
rc=2
$ echo line1 | tee t.txt ; echo line2 | tee -a t.txt > /dev/null ; cat t.txt
line1
line1
line2
$ wc -l < t.txt ; grep -c line <<< "line a"
2
1
```

Notes that save time:

- `tee` is how you both see and keep output: `k get pods -A | tee pods.txt`. Add `-a` or you overwrite the file.
- `echo data | sudo tee /etc/file` is the way to write a root-owned file, because in `sudo echo data > /etc/file` the redirection is done by YOUR shell, not by `sudo`.
- `: > file` or `> file` empties a file without deleting it. `set -o noclobber` makes `>` refuse to overwrite an existing file (`>|` forces it).

```text
REAL OUTPUT (Docker)
$ set -o noclobber; echo x > t.txt
bash: t.txt: cannot overwrite existing file
$ echo y >| t.txt      # force
$ set +o noclobber     # turn it off again, or every later > in this shell fails (no output)
```

**The order of redirections matters.** Bash handles them left to right, and `2>&1` means "copy where fd 1 points now". Section 3 draws it. The proof:

```text
REAL OUTPUT (Docker)
$ cmd > out.txt 2>&1 ; cat out.txt          # right order: both in the file
ls: cannot access '/nonexistent': No such file or directory
/etc/hostname
$ cmd 2>&1 > out.txt                         # wrong order: the error went to the terminal
ls: cannot access '/nonexistent': No such file or directory
$ cat out.txt
/etc/hostname
```

**A pipe carries stdout only.** Errors still go to the terminal unless you add `2>&1` before the pipe:

```text
REAL OUTPUT (Docker)
$ cmd | wc -l
ls: cannot access '/nonexistent': No such file or directory
1
$ cmd 2>&1 | wc -l
2
```

### 2.8 Here-documents: cat <<'EOF' > file.yaml

A **here-document** feeds several lines to a command's stdin, ending at a line that contains only the delimiter word. It is the fastest way to write a manifest with no editor.

```bash
cat <<'EOF' > pod.yaml
...lines...
EOF
```

The delimiter word (here `EOF`; any word works) decides whether the shell expands the body:

| Form | `$VAR`, `$(cmd)`, backticks in the body | Use for |
|---|---|---|
| `<<'EOF'` (quoted) | NOT expanded; text is kept literally | YAML that contains `$`, `` ` `` or `\` you want to keep |
| `<<EOF` (unquoted) | expanded when the file is written | templates where you want `$NS` replaced now |
| `<<-EOF` | like the above, but leading **tab** characters (not spaces) are stripped | indenting heredocs inside scripts |

```text
REAL OUTPUT (Docker)
$ cat <<'EOF' > q.yaml
home: $HOME
ns: $(date +%Y)
tick: `id -un`
EOF
$ cat q.yaml
home: $HOME
ns: $(date +%Y)
tick: `id -un`

$ export NS=lab-t101
$ cat <<EOF > u.yaml
home: $HOME
ns: $NS
year: $(date +%Y)
literal: \$HOME
EOF
$ cat u.yaml
home: /home/lab
ns: lab-t101
year: 2026
literal: $HOME
```

Choose on purpose. When the YAML needs a real shell value (a namespace you keep in `$NS`), leave the delimiter unquoted and escape the other `$` signs with `\$`. When the YAML must be copied exactly (a ConfigMap whose value is the text `$HOME`, a container `command` with `$(date)` to run inside the Pod), quote the delimiter.

Other uses: `cat <<EOF | k apply -f -` applies without a file; `cat <<'EOF' | tee -a file > /dev/null` appends; `cat <<'EOF' >> ~/.bashrc` appends settings (this is how Lab 1 works). The closing `EOF` must start at column 1 (unless you use `<<-` and tabs), with nothing after it.

**Multi-document YAML.** One file can hold several objects separated by a line that contains only `---`. `kubectl apply -f file` applies all of them in order.

```text
REAL OUTPUT (Docker)       # multi.yaml has 3 documents written with one quoted heredoc
$ wc -l multi.yaml ; grep -c "^---" multi.yaml
18 multi.yaml
2
$ csplit -s -z --suppress-matched -f doc- -b "%02d.yaml" multi.yaml "/^---$/" "{*}"
$ wc -l doc-*
  4 doc-00.yaml
  7 doc-01.yaml
  5 doc-02.yaml
 16 total
$ rm -f doc-*                                              # clear the csplit pieces first
$ yq -s '"doc-" + $index' multi.yaml ; ls doc-*          # yq v4.54.1 writes .yml
doc-0.yml
doc-1.yml
doc-2.yml
$ rm -f doc-* ; yq -s '"doc-" + (.kind | downcase)' multi.yaml ; ls doc-*
doc-configmap.yml
doc-namespace.yml
doc-serviceaccount.yml
```

`csplit` splits a file at lines that match a pattern. `-s` silences the byte counts, `-z` drops empty pieces, `--suppress-matched` removes the `---` line itself, `-f` sets the file prefix, `-b "%02d.yaml"` the numbering, and `{*}` repeats the pattern until the end. `yq -s EXPR` ("split exp") writes one file per document, named by the expression. `yq` is listed among the tools on the exam's SSH hosts (source: [tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)); which `yq` flavour and version is UNVERIFIED, and the commands above were run with mikefarah `yq` v4.54.1.

### 2.9 Pipes and exit codes: $?, set -o pipefail, &&, ||, ;

A **pipe** `a | b` connects stdout of `a` to stdin of `b`. Both run at the same time. An **exit code** is the number a program returns when it ends: `0` means success, anything else means failure. The shell stores the last one in `$?`.

| Code | Meaning |
|---|---|
| `0` | success |
| `1` | general failure (`grep` found nothing; `printenv` on an unset name; `kubectl` for most errors) |
| `2` | usage error / `ls` could not access a path |
| `124` | `timeout` killed the command (2.13) |
| `126` | found but not executable (for example a script without `chmod +x`) |
| `127` | command not found |
| `128+N` | killed by signal N: `137` = SIGKILL (9), `143` = SIGTERM (15), `130` = Ctrl+C (SIGINT, 2) |

```text
REAL OUTPUT (Docker)
$ true; echo "true: $?"; false; echo "false: $?"
true: 0
false: 1
$ ls /nonexistent 2>/dev/null; echo "ls missing: $?"
ls missing: 2
$ nosuchcmd 2>/dev/null; echo "not found: $?"
not found: 127
$ /tmp/noexec.sh ; echo "rc=$?"           # file exists, mode 644
bash: /tmp/noexec.sh: Permission denied
rc=126
$ sleep 30 & kill -TERM $!; wait $!; echo "TERM rc=$?"
TERM rc=143
```

**Chaining operators.**

| Operator | Runs the next command | Example |
|---|---|---|
| `a ; b` | always | `cd /tmp ; ls` |
| `a && b` | only if `a` succeeded (rc 0) | `mkdir d && cd d` |
| `a \|\| b` | only if `a` failed | `test -f x \|\| echo missing` |
| `a & b` | `a` runs in the background | `sleep 5 &` |

```text
REAL OUTPUT (Docker)
$ true && echo A; false && echo B; false || echo C; true || echo D; false; echo "E always"
A
C
E always
$ true && false || echo "C ran although A succeeded"      # A && B || C is NOT if/else
C ran although A succeeded
```

Use `if cmd; then ...; else ...; fi` when both branches matter.

**A pipeline's exit code is the LAST command's code.** A failure earlier in the pipe is hidden unless you turn on `pipefail`, which makes the pipeline's code the rightmost non-zero code. `${PIPESTATUS[@]}` shows each stage.

```text
REAL OUTPUT (Docker)
$ false | true; echo "rc=$?"
rc=0
$ set -o pipefail; false | true; echo "pipefail rc=$?"
pipefail rc=1
$ set +o pipefail; false | true | false; echo "${PIPESTATUS[@]}"
1 0 1
```

**Strict mode for scripts: `set -euo pipefail`.** `-e` exits at the first failing command, `-u` makes an unset variable an error, `-o pipefail` is described above. Put it at the top of scripts, not in your interactive shell (an interactive `set -e` closes your terminal at the first typo).

```text
REAL OUTPUT (Docker)       # nofail.sh has no set line; strict.sh starts with set -euo pipefail
$ bash nofail.sh; echo "script rc=$?"
step1
ls: cannot access '/nonexistent-dir': No such file or directory
step2 runs anyway
script rc=0
$ bash strict.sh; echo "script rc=$?"
step1
ls: cannot access '/nonexistent-dir': No such file or directory
script rc=2
$ bash unset.sh                      # set -u ; echo "ns is $NSX"
unset.sh: line 2: NSX: unbound variable
$ bash -c 'set -e; false | true; echo kept going'          # -e alone does not see the pipe failure
kept going
$ bash -c 'set -eo pipefail; false | true; echo kept going'; echo "rc=$?"
rc=1
```

Two more `kubectl` facts used later: `kubectl version --client` returns `0`; an unknown subcommand returns `1`. Always read `$?` (or use `&&`) before you assume a command worked.

### 2.10 History: Ctrl+R, !!, !$, history | grep; readline shortcuts

Bash records commands in memory (`HISTSIZE`, 1000 by default on Ubuntu) and writes them to `~/.bash_history` when the shell exits (`HISTFILESIZE`, 2000).

| Keys / syntax | What it does |
|---|---|
| Up / Down | walk through earlier commands |
| `Ctrl+R` | reverse search: type part of an old command, press `Ctrl+R` again for the next match, Enter to run, Right-arrow or `Ctrl+E` to edit |
| `!!` | the whole previous command (`sudo !!` reruns it as root) |
| `!$` | the last word of the previous command |
| `!^` | the first argument of the previous command |
| `!*` | all arguments of the previous command |
| `!echo` | the most recent command that starts with `echo` |
| `!-2` | the command two back |
| `^old^new^` | rerun the previous command with the first `old` replaced by `new` |
| `!!:p` | print what `!!` would run, without running it |
| `Alt+.` | insert the last word of the previous command (like `!$`, but you see it before you press Enter) |
| `history`, `history N`, `history \| grep x` | list, last N, search |

```text
REAL OUTPUT (Docker)      # an interactive bash --norc fed these lines; "$ " is the prompt
                          # history numbers: 1 echo get pods -n kube-system, 2 the rerun with default, 3 echo one two three, 4 echo three (the expanded !$), 5 history | grep one
$ echo get pods -n kube-system
get pods -n kube-system
$ ^kube-system^default^
echo get pods -n default
get pods -n default
$ echo one two three
one two three
$ echo !$
echo three
three
$ history | grep one
    3  echo one two three
    5  history | grep one
$ !echo
echo three
three
$ echo !!:p
echo echo three
```

Bash prints the expanded command before it runs (the line `echo three` above). If the substitution has no match it says `bash: :s^old^new^: substitution failed` and does nothing.

**Readline shortcuts (command-line editing).** These are bindings of the readline library inside Bash. The names were confirmed with `bind -p` / `bind -q`.

| Keys | readline function | Does |
|---|---|---|
| `Ctrl+A` / `Ctrl+E` | beginning-of-line / end-of-line | jump to start / end |
| `Alt+B` / `Alt+F` | backward-word / forward-word | move one word |
| `Ctrl+W` | unix-word-rubout | delete the word before the cursor (up to whitespace) |
| `Alt+Backspace` | backward-kill-word | delete the word before the cursor (stops at punctuation too) |
| `Alt+D` | kill-word | delete the word after the cursor |
| `Ctrl+U` | unix-line-discard | delete from the cursor back to the start of the line |
| `Ctrl+K` | kill-line | delete from the cursor to the end of the line |
| `Ctrl+Y` | yank | paste what the last delete removed |
| `Ctrl+_` | undo | undo the last edit |
| `Ctrl+L` | clear-screen | clear the screen |

**Exam trap about Ctrl+W.** In a normal terminal `Ctrl+W` deletes a word. The Linux Foundation tips page says to use `Ctrl+Alt+W` instead of `Ctrl+W` in the exam, and also notes that copy/paste in the terminal is `Ctrl+Shift+C` / `Ctrl+Shift+V`, and that the `INSERT` key is prohibited (source: [tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)). Use `Ctrl+U` or `Alt+Backspace` to delete words (whether the exam terminal forwards `Alt+Backspace` is UNVERIFIED), or `Ctrl+Alt+W` as the page says. Retrain your hands on your own machine now.

### 2.11 Aliases and functions: alias k=kubectl; complete -o default -F __start_kubectl k; export do=...

An **alias** is a text replacement done on the first word of a line. A **function** is a named block of shell code that takes arguments. A **shell variable** (`$do`) is substituted anywhere.

| Tool | Example | Good for | Limit |
|---|---|---|---|
| alias | `alias k=kubectl` | shorter command names | no arguments in the middle; not expanded in scripts or after `sudo`; takes effect on the NEXT line when defined and used on one line |
| variable | `export do="--dry-run=client -o yaml"` | long flags you paste anywhere | must NOT be quoted when used (`"$do"` is one word) |
| function | `kn() { k config set-context --current --namespace="$1"; }` | logic or arguments | lives in the shell; `export -f` passes it to child Bash |

```text
REAL OUTPUT (Docker)
$ alias k=kubectl
$ type -a k
k is aliased to `kubectl'
$ complete -p k
complete -o default -F __start_kubectl k
$ alias
alias k='kubectl'
$ alias ls="echo ALIASED"
$ ls                             # typed on its own line: the alias wins
ALIASED
$ \ls /etc/hostname              # backslash: skip the alias
/etc/hostname
$ command ls /etc/hostname       # command: skip aliases and functions
/etc/hostname
$ unalias ls
```

(`type -a k` shows only the alias line because `k` is not a file in PATH. `kubectl` itself is listed by `type -a kubectl`.)

A function example, run against a throw-away kubeconfig:

```text
REAL OUTPUT (Docker)
$ kn() { kubectl config set-context --current --namespace="$1" >/dev/null && echo "namespace now: $(kubectl config view --minify -o jsonpath="{..namespace}")"; }
$ type -a kn
kn is a function
kn ()
{
    kubectl config set-context --current --namespace="$1" > /dev/null && echo "namespace now: $(kubectl config view --minify -o jsonpath="{..namespace}")"
}
$ kn lab-t101
namespace now: lab-t101
$ printf '#!/bin/bash\nk version --client\n' > /tmp/s.sh ; bash /tmp/s.sh
/tmp/s.sh: line 2: k: command not found       # aliases are not visible in scripts
```

**Why `k` needs its own `complete` line.** Tab completion is attached to a command NAME. `source <(kubectl completion bash)` registers the function `__start_kubectl` for `kubectl` only. The alias `k` is a different name, so Tab on `k get po` falls back to file names until you run `complete -o default -F __start_kubectl k`. `-F` names the function to call, and `-o default` falls back to file-name completion when the function offers nothing. The kubectl docs show the same pair of lines (source: [kubectl Quick Reference](https://kubernetes.io/docs/reference/kubectl/quick-reference/), which also says "bash-completion package should be installed first").

```text
REAL OUTPUT (Docker)
$ alias k=kubectl
$ complete -p k                        # before: nothing registered
bash: complete: k: no completion specification
$ source <(kubectl completion bash)
$ complete -p kubectl                  # registered for the full name only
complete -o default -F __start_kubectl kubectl
$ complete -p k
bash: complete: k: no completion specification
$ complete -o default -F __start_kubectl k
$ complete -p k                        # after
complete -o default -F __start_kubectl k
```

**The `$do` and `$now` variables.** `export do="--dry-run=client -o yaml"` and `export now="--force --grace-period=0"` are plain text that the shell pastes in. Use them UNQUOTED. Quoted, Bash passes one argument and `kubectl` rejects it:

```text
REAL OUTPUT (Docker)
$ k run web --image=nginx:1.27 "$do"
error: Invalid dry-run value (client -o yaml). Must be "none", "server", or "client".
```

`$now` deletes a Pod immediately (`k delete pod web $now`). It skips the graceful shutdown, so use it only on throw-away objects. Why the name `do`? It is short. It is also a Bash reserved word only when it is the FIRST word of a command (`for ...; do`), so using it as a variable name is fine; `$do` after a command is expanded normally. (In the Docker run, `echo $do` and `k create ns lab-t101 $do` in an interactive shell with it exported both worked.)

### 2.12 Command substitution and simple loops

`$(cmd)` pastes the output of `cmd`. A `for` loop runs a body once per word:

```bash
for n in $(k get ns -o name); do echo "$n"; done      # needs a cluster; prints namespace/default ...
```

`-o name` prints `kind/name`, so the loop variable is `namespace/default`. Strip the prefix with parameter expansion: `${n#*/}` removes the shortest match of `*/` from the front, `${n%/*}` removes `/*` from the end, `${f%.yaml}` removes a suffix.

```text
REAL OUTPUT (Docker)       # names() prints three lines, standing in for k get ns -o name
$ for n in a b c; do echo "item $n"; done
item a
item b
item c
$ for f in f*.yaml; do echo "file $f"; done
file f1.yaml
file f2.yaml
$ for i in {1..3}; do echo -n "$i "; done; echo
1 2 3
$ for n in $(names); do echo "would run: kubectl get all -n ${n#*/}"; done
would run: kubectl get all -n default
would run: kubectl get all -n kube-system
would run: kubectl get all -n lab-t101
$ names | while read -r line; do echo "got: $line"; done      # safe with spaces in the data
got: namespace/default
got: namespace/kube-system
got: namespace/lab-t101
$ names | cut -d/ -f2 | xargs -I{} echo "ns={}"
ns=default
ns=kube-system
ns=lab-t101
```

The `for x in $(...)` form splits on whitespace, so it is only safe when the names have no spaces (Kubernetes object names never do). Use `while read -r` for free-form text. `xargs` turns lines on stdin into arguments (`-I{}` marks where each line goes).

### 2.16 Under the hood: what Bash does with one line

Take `k get pods -n $NS > out.txt 2>&1 | tee all.txt`. Bash (1) reads the line and splits it into tokens; (2) expands in the order given in 2.4 (alias `k` is replaced very first, at parse time); (3) creates the pipe because of `|`; (4) forks one child per pipeline stage; (5) in each child applies that stage's redirections left to right with `dup2`, then (6) `exec`s the program found through `PATH`; (7) waits and stores the exit code in `$?`. The parent shell never changes, which is why `cd` and `export` must be built-ins: a child cannot change its parent.

**Related but different (commonly confused):**

| Pair | Difference |
|---|---|
| `>` vs `\|` | `>` sends output to a file; `\|` sends it to another program |
| `&&` vs `;` | `;` always continues; `&&` continues only on success |
| `$VAR` vs `${VAR}` vs `$(cmd)` | variable / variable with clear boundaries (`${NS}x`) / output of a command |
| `source f` vs `bash f` | run in this shell / run in a child shell |
| alias vs function | text replacement of the first word / code with arguments |
| `which` vs `type -a` | PATH search only / everything Bash would run |

## 3. How it works (diagram)

File descriptors 0, 1, 2, and how redirections and pipes rewire them. Each step shows the fd table of the command being started (`TTY` is your terminal).

```text
DEFAULT                        cmd
  fd0 stdin  ----> TTY   (keyboard)
  fd1 stdout ----> TTY
  fd2 stderr ----> TTY

A) cmd > f 2>&1               (processed LEFT to RIGHT)
  start :   1 -> TTY    2 -> TTY
  > f   :   1 -> f      2 -> TTY      (fd1 re-pointed to f)
  2>&1  :   1 -> f      2 -> f        (fd2 copies what fd1 points to NOW = f)
  result: errors and output both land in f

B) cmd 2>&1 > f               (WRONG ORDER)
  start :   1 -> TTY    2 -> TTY
  2>&1  :   1 -> TTY    2 -> TTY      (fd2 copies TTY)
  > f   :   1 -> f      2 -> TTY      (only fd1 moves)
  result: output in f, errors still on screen

C) cmd1 | cmd2                (the pipe is created BEFORE the redirections)
  cmd1 fd1 ----> [pipe write end] ==== kernel buffer ==== [pipe read end] ----> cmd2 fd0
  cmd1 fd2 ----> TTY                                      cmd2 fd1 ----> TTY
  result: cmd2 sees only cmd1's stdout; cmd1's errors still go to the screen

D) cmd1 2>&1 | cmd2
  pipe   :  1 -> pipe
  2>&1   :  1 -> pipe   2 -> pipe     (fd2 copies the pipe)
  result: cmd2 sees stdout and stderr, in the order they were written

E) cmd1 > f 2>&1 | cmd2       (the mistake in section 6)
  pipe   :  1 -> pipe
  > f    :  1 -> f      (the pipe write end is no longer used by cmd1)
  2>&1   :  2 -> f
  result: cmd2 reads an empty pipe and gets end-of-file immediately; f holds everything

F) cmd 2>&1 | tee f | cmd3
  tee has two outputs: file f and its own fd1 (the next pipe). Good for "see it AND keep it".
```

Walkthrough:

1. A process starts with three open files: 0 for input, 1 for normal output, 2 for errors. By default all three point to your terminal.
2. `>` and `2>` change one entry of that table. `2>&1` does not link the two streams forever. It copies the current target of fd 1 into fd 2 at that moment, so the position of `2>&1` in the line matters (A versus B).
3. Bash creates the pipe first and connects fd 1 of the left command to it. Redirections on the left command then run and can override that connection (E).
4. A pipe carries only fd 1. To pipe errors too, put `2>&1` before the `|` (D).
5. `tee` is a program with one input and two outputs, so it is the way to copy a stream into a file without losing it on the screen (F).

The same file with every field explained (comments are allowed in YAML; you would not type them in the exam):

```yaml
apiVersion: v1              # ConfigMap lives in the core group, so just "v1"
kind: ConfigMap             # object type; case-sensitive
metadata:
  name: shell-demo          # unique within the namespace; lowercase letters, digits, "-", "."
  namespace: lab-t101       # must already exist; omit and it goes to the current context's namespace (default: "default")
  labels:                   # free key/value pairs used by selectors
    app: shell-demo
data:                       # map of string -> string; values are always text
  home: $HOME               # with a QUOTED heredoc delimiter this stays the 5 characters $HOME
  mode: demo                # YAML plain scalar; "demo" is a string
```

A bare `true` or `8080` is read by YAML as a boolean or a number, and the API server side rejects it for a ConfigMap (a "cannot unmarshal ... of type string" style error; exact text not captured here). Write `"true"` or `"8080"` in quotes. With an UNQUOTED delimiter the file would contain your home directory path instead of `$HOME`. This is the failure mode in section 6.

## 6. Common mistakes and how to fix them

| Symptom | What you will see (exact text) | Cause | Fix (command) |
|---|---|---|---|
| `$HOME` shows up literally in a file, or your own path shows up when you wanted the literal text | `home: $HOME` in `q.yaml` (quoted delimiter) or `home: /home/lab` in `u.yaml` (unquoted) | Quoted `<<'EOF'` stops expansion; unquoted `<<EOF` expands. You picked the wrong one. | Re-write the file with the right form; check with `grep -F 'home:' file`. To keep one `$` literal in an unquoted heredoc write `\$HOME`. |
| Alias `k` has no tab completion | Tab after `k get po` lists files in the directory or does nothing; `complete -p k` prints `bash: complete: k: no completion specification` | Completion is registered per command name. Only `kubectl` has it. | `complete -o default -F __start_kubectl k`. If you also get `_get_comp_words_by_ref: command not found`, install/load `bash-completion` (`source /usr/share/bash-completion/bash_completion`) first. |
| `grep` prints nothing after `cmd > f 2>&1 \| grep x`, and a file written by a later stage (`... \| grep x > g`) is empty | `wc -l f` prints 2 (both lines are in `f`), `wc -l g` prints 0 | The `> f` replaced the pipe on fd 1, so nothing flows into the pipe (diagram E). | `cmd 2>&1 \| tee f \| grep x`. If you only wanted the file, remove the pipe. If you wanted errors in `f` AND a pipe, use `tee`. |
| The browser tab closes when deleting a word | The entry reports that the exam browser tab closes (the exact effect of `Ctrl+W` there is UNVERIFIED). In a normal terminal nothing is wrong and a word is deleted. | `Ctrl+W` is "delete word" in readline. The tips page tells you to use `Ctrl+Alt+W` instead of `Ctrl+W` in the exam, so the exam browser treats `Ctrl+W` differently. | Use `Ctrl+Alt+W` (tips page), `Ctrl+U` or `Alt+Backspace`. Practise away from `Ctrl+W` now. |
| Script keeps going after a failure | `step2 runs anyway` is printed after `ls: cannot access '/nonexistent-dir': No such file or directory`, and `echo $?` after the script prints `0` | No `set -e`; the last command's code is the script's code. | Put `set -euo pipefail` on line 2 of the script. Check with `bash script.sh; echo $?` (becomes `2`). |
| `kubectl` rejects `$do` | `error: Invalid dry-run value (client -o yaml). Must be "none", "server", or "client".` | You quoted it: `"$do"`. | Remove the quotes: `k run web --image=nginx:1.27 $do`. |
| Alias works in the terminal but not in a script | `k: command not found` (rc 127) inside the script | Aliases are expanded only in interactive shells. | Use `kubectl` in scripts, or a function exported with `export -f`. |
| New shell: aliases and variables are missing, with an error at start | `bash: /home/lab/.bashrc: line 123: unexpected EOF while looking for matching `"'` | An unclosed quote in `~/.bashrc`. | Lab 3. `bash -n ~/.bashrc`, find the odd quote, fix, test in a new shell. |

**How to work a failure (repeatable path).**

1. Read the exact text and the exit code (`echo $?` right after). `127` = not found, `126` = not executable, `2` often usage or missing file.
2. Ask what the shell actually ran. Put `echo` in front of the command to see the expanded line, or run `bash -x` / `set -x` to print every command after expansion with a `+` prefix.
3. Ask what the command was given. `type -a NAME` (alias? function? which file?), `echo "$VAR"` (set? spaces?), `ls -ld PATH`.
4. Fix one thing and re-run.

**Mistake 1: `$HOME` literal / expanded.** Diagnose: `cat file` (look at the line), then `grep -n "<<" history` or `history | grep EOF` to see which delimiter you typed. Evidence from the Docker run: `q.yaml` (quoted) printed `home: $HOME`, `ns: $(date +%Y)`; `u.yaml` (unquoted) printed `home: /home/lab`, `year: 2026`, and `literal: $HOME` for the line written `\$HOME`. Fix by choosing on purpose, as described in 2.8.

**Mistake 2: alias without completion.** Diagnose in this order: `type -a k` (is it an alias?), `complete -p k` (is it registered?), `complete -p kubectl` (does the real command work?), `type -t __start_kubectl` (is the function defined; it prints `function`). If `kubectl` completes and `k` does not, the missing `complete` line is the cause. If neither completes, the `source <(kubectl completion bash)` line did not run (check `.bashrc` with 2.1) or `bash-completion` is missing. The real outputs are in 2.11 and 2.15.

**Mistake 3: `cmd > f 2>&1 | grep`.** Diagnose: `wc -l f` shows the data is in `f`. Reason with the diagram: the pipe is created first, then `> f` re-points fd 1 away from it, so nothing is ever written to the pipe and `grep` sees end-of-file at once. This is not an error, so there is no message; the only sign is silence. Real run with `ls /nonexistent /etc/hostname > f.txt 2>&1 | grep hostname > g.txt`: `f.txt` had 2 lines and `g.txt` had 0. Fix: `cmd 2>&1 | tee f | grep x`.

**Mistake 4: Ctrl+W.** There is no error message to read. The tips page says to use `Ctrl+Alt+W` instead of `Ctrl+W`, and the entry reports that the browser tab closes (the exact effect is UNVERIFIED). If it does, you lose time reopening it, and the cost is real because the timer does not stop. The tips page in section 2.10 gives the replacement. Training fix: `bind -q unix-word-rubout` shows the key you are training away from.

**Mistake 5: no `set -euo pipefail`.** Diagnose: run the script with `bash -x script.sh` to see which command failed (the first one with an error text), then `echo $?`. The captured contrast is in 2.9: `script rc=0` without strict mode, `script rc=2` with it. Remember the `A && B || C` trap too: `C` runs when `B` fails, not only when `A` fails.

<details><summary>Solution</summary>

```bash
# 1. Reproduce and read the error
```

Why: a double quote opened on the `export do=` line was never closed, so Bash kept reading across the next line until it found another `"` (the first one on the `export now=` line). The parser reports the line where the file ended, not the line where the quote was forgotten. ## 9. Quick review

1. A script of yours prints an error, then keeps running and ends with `echo $?` showing `0`. What do you add and where?
   <details><summary>Answer</summary>Add `set -euo pipefail` near the top of the script. `-e` stops at the first failing command, `-u` fails on unset variables, `pipefail` makes a failure anywhere in a pipe count. The script then exits with the failing command's code (we saw `2` for `ls` on a missing path).</details>
2. What is the difference between `cat <<'EOF' > f` and `cat <<EOF > f` when the body contains `$HOME`?
   <details><summary>Answer</summary>Quoted: the file contains the five characters `$HOME`. Unquoted: the shell expands it while writing, so the file contains your actual home path (an unset variable becomes empty). Use `\$HOME` to keep a single `$` literal in an unquoted heredoc.</details>
3. Why does tab completion not work for `k` even though it works for `kubectl`? Give the command that fixes it.
   <details><summary>Answer</summary>Completion is registered per command name and `source <(kubectl completion bash)` registers only `kubectl`. Run `complete -o default -F __start_kubectl k`.</details>
4. Which line sends both stdout and stderr to `f` and nothing to the terminal: `cmd > f 2>&1` or `cmd 2>&1 > f`? Why?
   <details><summary>Answer</summary>The first. Redirections run left to right and `2>&1` copies where fd 1 points at that moment. In the second, fd 2 copies the terminal first, then only fd 1 moves to `f`, so errors still show on screen.</details>
5. What does `type -a k` show that `which k` does not?
   <details><summary>Answer</summary>`type -a` also shows aliases, functions and builtins (here: `k is aliased to \`kubectl'`). `which` searches only PATH files, so for an alias it prints nothing useful.</details>
6. What does `false | true; echo $?` print, and what changes after `set -o pipefail`?
   <details><summary>Answer</summary>`0`, because the code of a pipeline is the last command's code. With `pipefail` it prints `1`, the code of the failed `false`. `${PIPESTATUS[@]}` lists every stage.</details>
7. Why is `$(...)` preferred over backticks, and what does `${n#*/}` do for `n=namespace/kube-system`?
   <details><summary>Answer</summary>`$(...)` nests cleanly and has no backslash oddities. `${n#*/}` removes the shortest prefix that matches `*/`, leaving `kube-system`.</details>
8. In the exam terminal you want to delete the last word you typed. Which keys do you avoid, and what do you use?
   <details><summary>Answer</summary>Avoid `Ctrl+W`, which the tips page says to replace with `Ctrl+Alt+W` in the exam. Use `Ctrl+Alt+W`, or `Ctrl+U` to clear back to the line start; `Alt+Backspace` is a readline word-delete (works if the terminal passes it through, UNVERIFIED for the exam terminal).</details>
9. What exit code does `timeout 2 sleep 10` give, and how is that different from a command that is not found or not executable?
   <details><summary>Answer</summary>`124`. Not found is `127`, found but not executable is `126`, killed by SIGKILL is `137`, by SIGTERM `143`.</details>
10. You type `export do="--dry-run=client -o yaml"` and then `k run web --image=nginx:1.27 "$do"`. What error do you get and why?
    <details><summary>Answer</summary>`error: Invalid dry-run value (client -o yaml). Must be "none", "server", or "client".` The quotes make `$do` a single argument, so `kubectl` sees `--dry-run=client -o yaml` as one value. Use `$do` unquoted.</details>
