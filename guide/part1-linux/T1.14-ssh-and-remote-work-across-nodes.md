## 2. Concepts

### 2.1 What SSH is and what happens when you connect

SSH (Secure Shell) gives you a shell on another machine over an encrypted TCP connection, normally to port 22. A server program (`sshd`) listens. Your `ssh` client connects. The handshake has three steps:

1. **Encrypt the channel.** Client and server agree on session keys.
2. **Check the server's identity.** The server shows its *host key*. The client compares it with `~/.ssh/known_hosts`. This is what stops someone pretending to be the server. It is also the source of the scary warnings in 2.6.
3. **Check your identity.** With key login, the server looks up your public key in `~/.ssh/authorized_keys` of the target user. It sends a challenge. Your client signs it with the private key. The private key never leaves your machine.

Without a working step 3 you get `Permission denied (publickey)`. Without step 2 you get `Host key verification failed`.

### 2.2 Connecting: `ssh user@host`, `ssh host`, and getting back

| Form | Meaning | When you use it |
|---|---|---|
| `ssh ubuntu@192.168.64.11` | Log in as user `ubuntu` on that IP | No config yet |
| `ssh ubuntu@w1` | Same, host name resolved by DNS, `/etc/hosts` or config | You know the user |
| `ssh w1` | User, address and key come from `~/.ssh/config` (2.4) | Your lab; the exam gives you the exact command in the infobox |
| `ssh w1 'cmd'` | Run one command, print its output, return to your shell | Loops, quick checks (2.5) |
| `exit` or Ctrl+D | Close the session and fall back to the shell you came from | After every task |

`exit` returns you to the shell that started the `ssh`. In the exam that shell is on host `base`: you ssh from `base` to the task host, work, `exit`, and you are on `base` again (E7). The check that you are where you think you are is `hostname`. Run it first, every time (section 8).

Nested ssh means running `ssh` from inside an ssh session to reach a third machine (`base` to `cp1` to `w1`). The exam hosts do not support it (E7). Your lab can, but do not build the habit: always `exit` first, then `ssh` to the next node. Section 3 shows the shape.

**Under the hood:** `ssh` allocates a terminal (a pty) when you ask for an interactive shell. With `ssh host 'cmd'` it does not. Programs that need a terminal then fail or misbehave: full-screen programs (`vim`, `top`) and anything that must prompt you (for example `sudo` asking for a password, which has nowhere to read it). Add `-t` to force a terminal: `ssh -t w1 'sudo vim /etc/hosts'`. Do not use `-t` when you redirect binary output (see the table in 2.5).

### 2.3 Keys: `ssh-keygen`, `ssh-copy-id`, and the file modes

A key pair is two files. The private key (`id_ed25519`) proves who you are. The public key (`id_ed25519.pub`) is safe to hand out. Anyone whose public key is in a user's `authorized_keys` can log in as that user, so protect the private key like a password.

```bash
ssh-keygen -t ed25519            # type ed25519; asks for a path and a passphrase
ssh-keygen -t ed25519 -N '' -C 'lab key' -f ~/.ssh/id_ed25519   # no prompts (lab only)
```

| Flag | What it does | Default | Risky value |
|---|---|---|---|
| `-t ed25519` | Key algorithm. Ed25519 is short, fast, and modern | `ed25519` in current OpenSSH (older versions: rsa) | `-t rsa -b 1024`: too weak; use ed25519 |
| `-f path` | Where to write the private key (`.pub` is added for the public key) | `~/.ssh/id_ed25519` | Overwriting a key you still need |
| `-N ''` | Empty passphrase, so no prompt | prompt | Fine in a throwaway lab. For a real key, use a passphrase |
| `-C text` | Comment stored in the public key, helps you recognise it | `user@host` | none |

REAL OUTPUT (Docker), key creation and resulting modes:

```text
$ ssh-keygen -t ed25519 -N "" -C "lab-key" -f ~/.ssh/id_ed25519
Generating public/private ed25519 key pair.
Your identification has been saved in /home/ubuntu/.ssh/id_ed25519
Your public key has been saved in /home/ubuntu/.ssh/id_ed25519.pub
The key fingerprint is:
SHA256:Z6S3ACeY9yl51mRZ6UBQled7sjfsbw8gNBnOps47fUQ lab-key
...
$ ls -l ~/.ssh
-rw------- 1 ubuntu ubuntu 399 Oct 27 07:19 id_ed25519
-rw-r--r-- 1 ubuntu ubuntu  89 Oct 27 07:19 id_ed25519.pub
```

`ssh-keygen` itself creates the private key with mode 600 (owner read/write only). The public key is 644.

**Installing the public key on a server.** `ssh-copy-id ubuntu@w1` logs in once (with a password, or another key that already works), appends your public key to `~ubuntu/.ssh/authorized_keys` on the server. It runs with `umask 077`, so a `.ssh` directory or `authorized_keys` file that it creates gets safe modes (700 and 600). It does not repair the modes of files that already exist. Run `ssh-copy-id -i ~/.ssh/id_ed25519.pub ubuntu@w1` to choose the key. If password login is disabled on the server (the Multipass default), `ssh-copy-id` has nothing to log in with. Then append the key out of band (Lab 1 does this with `multipass exec`, then runs `ssh-copy-id` once to show what it does when the key is already there). The manual equivalent of `ssh-copy-id` is:

```bash
cat ~/.ssh/id_ed25519.pub | ssh ubuntu@w1 'mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys'
```

REAL OUTPUT (Docker), `ssh-copy-id` when the key is already installed (it logs in with the key first, to filter out keys the server already has, and installs nothing):

```text
$ ssh-copy-id -i ~/.ssh/id_lab.pub w1
/usr/bin/ssh-copy-id: INFO: Source of key(s) to be installed: "/home/ubuntu/.ssh/id_lab.pub"
/usr/bin/ssh-copy-id: INFO: attempting to log in with the new key(s), to filter out any that are already installed

/usr/bin/ssh-copy-id: WARNING: All keys were skipped because they already exist on the remote system.
		(if you think this is a mistake, you may want to use -f option)
```

**Modes that must hold.** `sshd` has a safety check (`StrictModes yes` by default). If your home directory, `~/.ssh`, or `authorized_keys` can be written by anyone but you, `sshd` ignores the file, because another user could plant a key. The client has the same rule for private keys.

| Path | Required mode | Command |
|---|---|---|
| `~/.ssh/` (directory) | `700` (`drwx------`) | `chmod 700 ~/.ssh` |
| `~/.ssh/authorized_keys` | `600` (`644` also passes; anything writable by group/other fails) | `chmod 600 ~/.ssh/authorized_keys` |
| `~/.ssh/id_ed25519` (private key) | `600`, or the client refuses it | `chmod 600 ~/.ssh/id_ed25519` |
| `~/.ssh/config` | `600` (not writable by others) | `chmod 600 ~/.ssh/config` |
| `~` (home directory) | not group/other writable (`755` is fine) | `chmod go-w ~` |

Also the owner must be the user (see `chown` in [T1.04](./T1.04-users-groups-permissions-and-sudo.md)). A key file created by `sudo` is owned by root and will be refused for user `ubuntu`.

### 2.4 `~/.ssh/config`

The config file lets you give each host a short name and its settings. The client reads it top to bottom. For each setting, the first value found wins. So put specific `Host` blocks first and a catch-all `Host *` last.

| Keyword | Meaning | Default | Risky value |
|---|---|---|---|
| `Host w1` | Name you type after `ssh`. A block applies to commands whose name matches. `*` matches all | none | `Host *` at the top overrides everything below it |
| `HostName 192.168.64.11` | Real address or DNS name to connect to | the `Host` text itself | stale IP after the VM got a new DHCP lease |
| `User ubuntu` | Login user | your local user name | wrong user gives `Permission denied` |
| `IdentityFile ~/.ssh/id_ed25519` | Private key to offer. Can be given more than once | `~/.ssh/id_*` standard names | key file with mode 644 |
| `IdentitiesOnly yes` | Offer only the listed keys, not every key in your agent | `no` | leaving `no` with many keys gives `Too many authentication failures` |
| `Port 22` | TCP port | `22` | wrong port: `Connection refused` or timeout |
| `ServerAliveInterval 30` | Send a keepalive every 30 s so idle sessions are not dropped | `0` (off) | none |

A working config for the three lab nodes (replace the IPs with the ones from `multipass list`):

```text
# ~/.ssh/config   (chmod 600)
Host cp1
    HostName 192.168.64.10
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519

Host w1
    HostName 192.168.64.11
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519

Host w2
    HostName 192.168.64.12
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519

# Catch-all, last. Applies to every host not already set above.
Host *
    IdentitiesOnly yes
    ServerAliveInterval 30
    StrictHostKeyChecking accept-new    # lab only, see 2.6
```

Now `ssh w1` means `ssh -i ~/.ssh/id_ed25519 ubuntu@192.168.64.11`. Related: `Include ~/.ssh/config.d/*` pulls in other files, and `ProxyJump bastion` (or `ssh -J bastion w1`) reaches a host through a jump host without typing a nested `ssh`. `ProxyJump` is a lab convenience. Whether the exam allows it is UNVERIFIED; the verified rule is only "nested ssh is not supported" (E7).

**Debug one connection:** `ssh -v w1` prints each step (config read, key offered, auth result). Use `-vv` or `-vvv` for more.

### 2.5 Running commands remotely: `ssh host 'command'`, `scp`, `rsync`

**One-off commands.** `ssh w1 'sudo systemctl status kubelet'` runs the command in a non-interactive shell on `w1`, prints the output, and returns the exit code of the remote command. Quoting decides *where* variables expand:

| You type | Expanded on | Why |
|---|---|---|
| `ssh w1 'echo $HOSTNAME'` | w1 (remote) | single quotes keep `$HOSTNAME` literal until the remote shell runs it |
| `ssh w1 "echo $HOSTNAME"` | your machine (local) | double quotes let your shell expand it first |

Rule: single quotes unless you want the local value (as in `ssh w1 "sudo $JOIN"` below). A non-interactive remote shell does not load your aliases or the exam alias `k`, so write `kubectl` in one-off commands.

**scp (secure copy).** Syntax is `scp [options] source destination`, and either side can be `host:path`.

```bash
scp /tmp/snap.db cp1:/tmp/           # local file -> cp1
scp cp1:/tmp/snap.db .               # cp1 -> here
scp -r ./manifests w1:~/             # -r = whole directory
scp -3 cp1:/tmp/snap.db w1:/tmp/     # node -> node, data flows through your machine
```

`-3` sends remote-to-remote copies through your machine instead of asking `cp1` to open an ssh session to `w1`. That matters because the nodes do not have keys for each other. It also keeps you off the nested-ssh path. `-p` keeps times and modes; `-P 2222` sets the port (capital P, unlike `ssh -p`).

**rsync.** `rsync -avz src host:dst` copies only what changed. `-a` (archive) keeps modes, times, owners and recurses. `-v` prints file names. `-z` compresses in transit. Add `-n` for a dry run, and `-e 'ssh -p 2222'` for a non-default port. A trailing slash on the source matters: `rsync -avz dir/ w1:~/dir/` copies the *contents* of `dir`; `rsync -avz dir w1:~/` copies the directory itself. `rsync` must exist on both ends.

| Tool | Best for | Does not do |
|---|---|---|
| `scp` | One file, quick copy | Resume, skip unchanged files |
| `rsync -avz` | Directories, repeated syncs, big files | Needs `rsync` on both machines |
| `ssh host 'cat file' > file` | No `scp` available, simple text | Binary-safe only if no terminal is involved (not with `-t`) |

**Files owned by root.** An etcd snapshot written with `sudo` is owned by root and may be mode 600. Your `scp` runs as `ubuntu` and gets `Permission denied`. Fix on the source side first:

```bash
ssh cp1 'sudo cp /tmp/snap.db /tmp/snap-copy.db && sudo chown ubuntu: /tmp/snap-copy.db'
scp cp1:/tmp/snap-copy.db ./snap.db
```

**Join command.** `kubeadm join ...` needs root on the worker and a token made on the control plane. From one terminal:

```bash
JOIN=$(ssh cp1 'sudo kubeadm token create --print-join-command')   # runs on cp1, output captured locally
ssh w1 "sudo $JOIN"                                                  # double quotes: $JOIN expands locally, command runs on w1
```

That is the pattern for the kubeadm page's "Adding worker nodes" step (see [references](#10-references)). It needs no nested ssh.

**Controlling the cluster from your laptop.** The kubeadm install page describes copying the admin kubeconfig to another machine with `scp root@<control-plane-host>:/etc/kubernetes/admin.conf .` and then `kubectl --kubeconfig ./admin.conf get nodes`. It warns that `admin.conf` has superuser rights. That command logs in as `root`, which does not work on the lab VMs: Ubuntu does not allow a root ssh login by default, and Lab 1 installs a key only for `ubuntu`. Use the same pattern as for root-owned files instead, and lock the copy down because it is a superuser credential:

```bash
ssh cp1 'sudo cat /etc/kubernetes/admin.conf' > admin.conf && chmod 600 admin.conf
```

The redirect runs on your laptop, so the file lands there. This works once `kubeadm init` has created the file (Part 4). `ssh cp1 'sudo cat ...'` has no `-t`, so the bytes arrive unmodified.

### 2.6 `known_hosts`, host key warnings and `StrictHostKeyChecking`

The first time you connect, the client has no record of the server. It asks whether to trust the host key and, on yes, saves it in `~/.ssh/known_hosts`. Later connections compare. A mismatch is blocked.

| Message | Meaning | What to do |
|---|---|---|
| `The authenticity of host ... can't be established.` ... `Are you sure you want to continue connecting (yes/no/[fingerprint])?` | First contact with this host | In a lab type `yes`. In production compare the fingerprint first |
| `Warning: Permanently added '127.0.0.1' (ED25519) to the list of known hosts.` | Key saved after trusting it | nothing |
| `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!` then `Host key verification failed.` | The server presented a different key than the one saved | Real cause on a lab: you deleted and rebuilt the VM. Remove the old entry: `ssh-keygen -R <host>` |
| `Host key verification failed.` with no other text, in a script | First contact, but there was no terminal to ask `yes/no` | Use `-o StrictHostKeyChecking=accept-new` once, or connect by hand once |

REAL OUTPUT (Docker), first contact without a terminal (so no prompt can be shown):

```text
$ ssh w1 hostname
Host key verification failed.
$ echo $?
255
```

**`StrictHostKeyChecking` values** (set with `-o StrictHostKeyChecking=...` or in config):

| Value | Behaviour | Use |
|---|---|---|
| `ask` (default) | Prompt on unknown hosts, refuse changed keys | Normal |
| `accept-new` | Silently save unknown hosts, still refuse changed keys | Labs. Safe enough: you lose only first-contact checking |
| `no` | Connect even if the key changed (with a warning) | Lab only. Hides exactly the attack the check exists to stop |
| `yes` | Refuse unknown hosts as well | Locked-down environments |

A rebuild-proof lab setting is `-o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -o LogLevel=ERROR`. It never stores anything, so there is nothing to go stale. Use it only against throwaway VMs, never in anything real. The better habit is `ssh-keygen -R`.

**Under the hood:** Ubuntu hashes host names in `known_hosts` (lines start with `|1|`), so you cannot read the file to find an entry. `ssh-keygen -R host` finds it by hashing the name and writes a backup to `known_hosts.old`. You will see the stale-entry fix in the failure table. The lab cleanups in section 7 run `ssh-keygen -R` on every VM IP before they delete the VMs, because Multipass often hands a rebuilt VM the same IP with a new host key.

### 2.7 `sudo -i` after ssh, and why root's environment differs

After `ssh w1` you are user `ubuntu`. Many node tasks need root: reading `/etc/kubernetes`, restarting `kubelet`, running `etcdctl` with the cert files. `sudo -i` starts a *login shell* as root (it also reads root's profile). It matches the exam hint that `sudo -i` gives elevated privileges on any host (E8). Return with `exit` (back to ubuntu), then `exit` again (back to base).

| Command | Shell type | `$HOME` | Environment |
|---|---|---|---|
| `sudo cmd` | none, one command | `/root` on this Ubuntu 24.04 container (sudo sets `HOME` from the target user; older sudo versions may keep yours) | `env_reset`: most of your variables dropped; `PATH` from sudoers `secure_path` |
| `sudo -s` | non-login shell as root | `/root` on this container | Same reset; your working directory stays (no `cd /root`) |
| `sudo -i` | login shell as root | `/root` | Fresh: root's own `.profile`/`.bashrc`, cwd becomes `/root` |

REAL OUTPUT (Docker), `sudo -i` from the `ubuntu` user. Note the new user, home and directory:

```text
$ ssh w1 "sudo -i bash -c 'whoami; pwd; echo \$HOME'"
root
/root
/root
```

REAL OUTPUT (Docker, Ubuntu 24.04), `PATH`, `HOME` and user as the same `sh -c 'echo $PATH $HOME $(whoami)'` sees them under each form, and then as plain `ubuntu`:

```text
$ sudo sh -c 'echo $PATH $HOME $(whoami)'
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin /root root
$ sudo -s sh -c 'echo $PATH $HOME $(whoami)'
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin /root root
$ sudo -i sh -c 'echo $PATH $HOME $(whoami)'
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin /root root
$ echo $PATH $HOME
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin /home/ubuntu
```

How to read it: all three `sudo` forms give root's `HOME` and the sudoers `secure_path` here, while `ubuntu`'s own `PATH` also has `/usr/games` and `/usr/local/games`. The `PATH` differences on this image are small. The big differences are the variables and functions that vanish (aliases, `$do`, `$KUBECONFIG`) and the working directory. On a real node, root's `PATH` can differ more (for example, a directory that only your user profile adds, like `~/.local/bin`, is not in root's). Compare with `echo $PATH` as `ubuntu` and as root on your own VMs.

What this means for you:

- Your shell aliases, functions and `export do=...` variables are not in root's login shell. Check with `type k`. If it is missing, use `kubectl` or redefine the alias there. Whether the exam hosts give root the `k` alias is UNVERIFIED (E9 says kubectl "with kalias" is on every SSH host; the exact alias name is UNVERIFIED).
- `~` is now `/root`, so `~/.kube/config` is root's file, not `ubuntu`'s. On a kubeadm control plane the admin file is `/etc/kubernetes/admin.conf`.
- Your working directory is `/root`. Relative paths from before are gone. Use absolute paths.
- Do not leave a root shell open on `base`. Do the work, then `exit` twice.

### 2.8 Port forwarding with `ssh -L` (awareness)

`ssh -L 8080:localhost:30080 w1` makes your machine listen on port 8080 (`-L` is "local forward"). Connections to `localhost:8080` travel inside the ssh connection to `w1`, and `w1` connects to `localhost:30080` *from its own point of view*. Read it as: `-L <local port>:<target host as seen from the server>:<target port> <ssh server>`.

Use it to reach a NodePort Service, a dashboard or `kubectl proxy` on a cluster whose network your laptop cannot reach directly. Extra flags: `-N` (no remote command, just forward) and `-f` (go to background). Stop it with `pkill -f 'ssh.*-L 8080'` or Ctrl+C in the foreground.

REAL OUTPUT (Docker). A plain Python web server stood in for the NodePort, listening on 30080:

```text
$ ssh -f -N -L 8080:localhost:30080 w1
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:8080/
200
```

Caveat for real clusters: whether a NodePort answers on the node's `localhost` depends on the kube-proxy mode. UNVERIFIED on v1.37 (section 11). If `localhost:30080` on the node does not answer, forward to the node's own IP instead: `ssh -L 8080:192.168.64.11:30080 w1`. Related but different: `kubectl port-forward` forwards to a Pod or Service through the API server and needs no ssh access to nodes. `ssh -L` forwards to anything the ssh server can reach.

### 2.9 Multipass as an alternative for local VMs

Multipass VMs can be reached without ssh keys from the host machine that runs Multipass. This is a convenience; it is not how the exam works, so practise `ssh` too.

| Command | What it does |
|---|---|
| `multipass launch 24.04 --name w1 --cpus 2 --memory 2G --disk 10G` | Create a VM |
| `multipass list` | Names, state, IPs |
| `multipass shell w1` | Interactive shell as `ubuntu`, no ssh config needed |
| `multipass exec w1 -- hostname` | One command, like `ssh w1 hostname` |
| `multipass transfer ./file w1:/tmp/file` | Copy a file in; `multipass transfer w1:/tmp/file .` copies out |
| `multipass delete --purge w1` | Remove the VM for good |

`multipass shell` is also your back door when ssh itself is broken, as in Lab 3. `multipass transfer` is exercised in Lab 1 (copy in, copy out, `cmp` to compare).

### 2.10 Related but different

| Easily confused | Difference |
|---|---|
| `ssh` vs `kubectl exec` | `ssh` gets a shell on a node (host OS). `kubectl exec` gets a shell inside a container |
| `kubectl config use-context` vs `ssh` | Context switch changes which API server `kubectl` talks to, on the same machine. `ssh` moves you to a different machine. In your own multi-cluster labs you may need one, the other, or both; how many contexts the exam uses is UNVERIFIED (E21) |
| `exit` from `sudo -i` vs `exit` from ssh | The first leaves root's shell. The second leaves the remote host. Two nested shells need two `exit`s |

## 3. How it works (diagram)

```text
                    base (or your laptop)
                  you start here, you end here
                              |
          +-------------------+-------------------+
          | ssh cp1           | ssh w1            | ssh w2
          v                   v                   v
       +------+            +------+            +------+
       | cp1  |            |  w1  |            |  w2  |
       +------+            +------+            +------+
          |                   |                   |
          +-- exit: back to base after each task -+

   Never:   base --ssh--> cp1 --ssh--> w1     (nested ssh: not supported, E7)
   Instead: base --ssh--> cp1 ; exit ; base --ssh--> w1
   Node to node data:  scp -3 cp1:/tmp/snap.db w1:/tmp/    (run from base)
```

Walkthrough:

1. Every connection starts at `base` (the exam's start host) or your laptop. Each arrow is a separate `ssh` from there.
2. You do the task on the node, then `exit`. The prompt returns to `base`.
3. To work on a second node, return to `base` first. Do not type `ssh w1` from inside `cp1`.
4. If one task needs data on two nodes, copy it with `scp -3` or `rsync` from `base`, or via a file you copy down and back up.
5. A `-L` tunnel is a side channel from `base` through one node to a port; it does not change which host your shell is on.

## 4. Commands and YAML you must produce fast

### 4.1 Imperative shortcuts

```bash
ssh-keygen -t ed25519                          # make a key (accept defaults, empty passphrase in a lab)
ssh-copy-id ubuntu@w1                          # install the public key on w1
ssh w1                                         # login using ~/.ssh/config
ssh w1 'sudo systemctl status kubelet'         # one remote command, no interactive shell
ssh w1 'sudo systemctl status kubelet --no-pager | head -5'   # short output
scp /tmp/snap.db cp1:/tmp/                     # copy a file to cp1
rsync -avz ./manifests/ w1:~/manifests/        # copy a directory, only changes
ssh -L 8080:localhost:30080 w1                 # forward laptop:8080 to w1's localhost:30080
ssh-keygen -R w1                               # drop a stale known_hosts entry
```

`ssh-keygen -R w1` removes only the name `w1`. If your config maps `w1` to an IP, the stored entry may be under the IP. Run `ssh-keygen -R 192.168.64.11` too (REAL OUTPUT (Docker) of `-R` is in section 6).

### 4.2 The declarative file: `~/.ssh/config` with three hosts

There is no Kubernetes YAML in this topic. The file you must be able to write quickly is the config from 2.4. Annotated:

```text
Host cp1                              # the name you will type: ssh cp1
    HostName 192.168.64.10            # real IP or DNS name (default: the Host word itself)
    User ubuntu                       # remote login user (default: your local user)
    IdentityFile ~/.ssh/id_ed25519    # private key to use (must be mode 600)

Host w1
    HostName 192.168.64.11
```

## 6. Common mistakes and how to fix them

| Symptom | What you will see (exact text) | Cause | Fix |
|---|---|---|---|
| Key refused on the client | `@         WARNING: UNPROTECTED PRIVATE KEY FILE!          @` then `Permissions 0644 for '/home/ubuntu/.ssh/id_ed25519' are too open.` then `This private key will be ignored.` and finally `Permission denied (publickey).` | Private key readable by group/others | `chmod 600 ~/.ssh/id_ed25519` |
| Task done on the wrong host | No error. Nothing changes where the checker looks. Score for that task is lost | Skipped the `ssh` step, or stayed on the previous node | Run `hostname` before the first command of every task. Exit back to `base` after each task |
| Stale entry after rebuilding a VM | `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!` ... `Host key verification failed.` | New VM, new host key, old key in `known_hosts` | `ssh-keygen -R <host-or-ip>`, then connect again |
| Server ignores `authorized_keys` | Client: `ubuntu@127.0.0.1: Permission denied (publickey).` Server log: `Authentication refused: bad ownership or modes for file /home/ubuntu/.ssh/authorized_keys` (or `... for directory /home/ubuntu/.ssh`) | `~/.ssh` or `authorized_keys` writable by group/others, or wrong owner | On the server: `chmod 700 ~/.ssh; chmod 600 ~/.ssh/authorized_keys` |
| Config refused | `Bad owner or permissions on /home/ubuntu/.ssh/config` (ssh exits with status 255) | The config is writable by group/others, or owned by someone else | `chmod 600 ~/.ssh/config` (and `chown` it to yourself) |
| Config block missing | `ssh: Could not resolve hostname w1: Name or service not known` | No `Host w1` block, or a typo in the `Host` line, so `w1` is treated as a plain DNS name | Add the block. `ssh -G w1 \| head` shows what the client resolved |
| Many keys in the agent | `Received disconnect from ...: Too many authentication failures` | The agent offers every key, the server gives up after a few | Add `IdentitiesOnly yes` and `IdentityFile` for that host |
| Copying a root-only file | `scp: remote open "/tmp/snap.db": Permission denied` | File is owned by root, mode 600 | `ssh cp1 'sudo chown ubuntu: /tmp/snap.db'` then `scp` |

**Quoted text caveat:** REAL OUTPUT (Docker) confirmed the client and server messages in rows 1, 3, 4 and 5. The wording for rows 6 to 8 comes from OpenSSH behaviour that was not triggered here and is marked in section 11. The `Permission denied` text of `scp` is version-dependent.

REAL OUTPUT (Docker), row 4. The client only says `Permission denied (publickey).` The reason is in the server log (`/tmp/sshd.log` in the container; on Ubuntu 24.04 a VM use `sudo journalctl -u ssh`):

```text
Authentication refused: bad ownership or modes for file /home/ubuntu/.ssh/authorized_keys
Authentication refused: bad ownership or modes for directory /home/ubuntu/.ssh
```

**Troubleshooting path for "I cannot ssh in" (run in this order):**

1. `ssh -v w1` on the client. Read from the top. "Reading configuration data" shows your config was used. "Connecting to ..." shows the address. "Offering public key: ..." shows which key. "Permission denied (publickey)" after that means the server rejected the key, or never saw it.
2. If you see `UNPROTECTED PRIVATE KEY FILE` or `bad permissions`, fix the key mode on the client.
3. If `Connection refused` or a timeout, the address, port or `sshd` is wrong (`systemctl status ssh` on the server). It is not a key problem.
4. If the key was offered and refused, go to the server by another door (`multipass shell`, a console) and read the log. `Authentication refused: bad ownership or modes` means fix modes. No such line usually means the public key is simply not in `authorized_keys`.
5. If you see the changed-host-identification banner, fix `known_hosts`. Do not try to fix keys.
6. If ssh stops at once with `Bad owner or permissions on .../.ssh/config`, fix the config mode on the client. Nothing was sent to the server.

<details><summary>Solution</summary>

```bash
# 1. Key without passphrase, at a dedicated path (does not touch your real keys)
ssh-keygen -t ed25519 -N '' -C t114-lab -f ~/.ssh/id_ed25519_lab

# 2. Put the public key into authorized_keys of user ubuntu on each VM.
#    multipass exec runs as ubuntu and needs no ssh; ~/.ssh already exists (700) on these images.
PUB=$(cat ~/.ssh/id_ed25519_lab.pub)
for n in cp1 w1 w2; do
  multipass exec $n -- bash -c "mkdir -p ~/.ssh && chmod 700 ~/.ssh && echo '$PUB' >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

    HostName $(vmip cp1)
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519_lab
Host w1
    HostName $(vmip w1)
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519_lab

    User ubuntu
    IdentityFile ~/.ssh/id_ed25519_lab
Host cp1 w1 w2

multipass transfer w1:/tmp/xfer.txt ~/lab/t114/xfer.back
```

Why each step: the key file is private (mode 600 is set by `ssh-keygen`). `authorized_keys` makes the server accept the key. The `Host` blocks tie a short name to address, user and key. `accept-new` stops the first-contact prompt, so scripts do not fail with `Host key verification failed.` (2.6). The blocks are appended between `# BEGIN t114` and `# END t114` so your own entries stay untouched and cleanup can remove only the lab's lines. ### Lab 3 (Break-fix): SSH fails because of `authorized_keys` permissions

**Setup:** Labs 1 and 2 done. Run the fault injector from your laptop. It uses `multipass exec`, which does not need ssh.

```bash
# break.sh
multipass exec w2 -- chmod 777 /home/ubuntu/.ssh
multipass exec w2 -- chmod 666 /home/ubuntu/.ssh/authorized_keys
```

**Task.** `ssh w2` now fails and `cp1` and `w1` still work. Restore key-based login to `w2` for user `ubuntu`. Do not delete the VM, do not create new keys, and do not turn on password login. Afterwards `ssh -o BatchMode=yes w2 hostname` must print `w2`.

<details><summary>Hint 1</summary>
Run `ssh -v w2` and read the last lines. The client says the key was offered, then rejected. It does not say why.
</details>
<details><summary>Hint 2</summary>
The reason is in the server's log. Reach `w2` without ssh: `multipass shell w2`. Then `sudo journalctl -u ssh -n 20 --no-pager | grep -i refused`.
</details>
<details><summary>Hint 3</summary>
`sshd` refuses `authorized_keys` and the directory that holds it when group or others can write them. See the table in 2.3.
</details>

<details><summary>Solution</summary>

```bash
# 1. Symptom from the client
ssh -o BatchMode=yes w2 hostname        # Permission denied (publickey).
ssh -v -o BatchMode=yes w2 hostname 2>&1 | grep -E 'Offering|Permission denied'

# 2. Out-of-band door (ssh is the broken thing, so do not use it)
multipass exec w2 -- sudo journalctl -u ssh -n 20 --no-pager | grep -i 'bad ownership'
#    Expect: Authentication refused: bad ownership or modes for ... /home/ubuntu/.ssh ...

# 3. Fix both objects: the directory and the file
multipass exec w2 -- chmod 700 /home/ubuntu/.ssh
multipass exec w2 -- chmod 600 /home/ubuntu/.ssh/authorized_keys
multipass exec w2 -- ls -ld /home/ubuntu/.ssh /home/ubuntu/.ssh/authorized_keys
```

Why both: with `StrictModes yes`, `sshd` checks the home directory, `~/.ssh` and `authorized_keys`; any of them writable by others makes it ignore the key file. Fixing only the file leaves the directory at 777 and the login still fails. Why not ssh to fix it: the broken door is ssh, so use Multipass as the back door. On a KVM VM use the console.
</details>

## 9. Quick review

1. **What command makes an Ed25519 key, and which file must stay private?** <details><summary>Answer</summary>`ssh-keygen -t ed25519`. The file without `.pub` (`id_ed25519`) is private and must be mode 600.</details>
2. **Why does `sshd` ignore an `authorized_keys` file with mode 666?** <details><summary>Answer</summary>`StrictModes` is on by default. A file or directory that others can write could have a key planted in it, so `sshd` refuses it and logs `bad ownership or modes`.</details>
3. **What do the four fields of your config block do (`Host`, `HostName`, `User`, `IdentityFile`)?** <details><summary>Answer</summary>`Host` is the alias you type, `HostName` the real address, `User` the login name, `IdentityFile` the private key.</details>
4. **`ssh w1 "echo $HOSTNAME"` prints your laptop's name. Why, and how do you fix it?** <details><summary>Answer</summary>Double quotes: your local shell expands `$HOSTNAME` before `ssh` runs. Use single quotes so the node expands it.</details>
5. **What command copies a file from `cp1` to `w1` when the nodes cannot reach each other with ssh?** <details><summary>Answer</summary>`scp -3 cp1:/tmp/snap.db w1:/tmp/` from your laptop or `base`. `-3` sends the data through the local machine.</details>
6. **What does `rsync -avz` add over `scp`?** <details><summary>Answer</summary>It copies only changes, keeps modes and times (`-a`), prints files (`-v`), compresses (`-z`), and handles directories well. It needs `rsync` on both ends.</details>
7. **You rebuilt `w1` and now see `Host key verification failed.` What is the fix, and which value do you give it?** <details><summary>Answer</summary>`ssh-keygen -R <host>`, using the name or IP stored in `known_hosts` (try both the alias and the IP). Then reconnect.</details>
8. **Why is `StrictHostKeyChecking=no` acceptable only in a lab?** <details><summary>Answer</summary>It also lets a changed host key through, which is exactly the signal for an impersonating server. In a throwaway lab there is no one to impersonate.</details>
9. **What is different after `sudo -i`, compared with just `ssh w1`?** <details><summary>Answer</summary>You are root in a login shell: `$HOME` is `/root`, the working directory is `/root`, and your aliases and exported variables (`k`, `$do`) are not loaded.</details>
10. **What does `ssh -L 8080:localhost:30080 w1` do, and when would you use it?** <details><summary>Answer</summary>It listens on your port 8080 and sends traffic through ssh to port 30080 as seen from `w1`. Use it to reach a NodePort Service or a dashboard that your laptop cannot reach directly.</details>
11. **Why must you `exit` back to `base` between tasks instead of using `ssh` from inside a node?** <details><summary>Answer</summary>Nested ssh is not supported on the exam hosts (E7), and returning to `base` also makes it clear which host the next task's `ssh` starts from.</details>
