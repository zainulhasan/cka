## 1. Why this matters

Kubernetes is built on Linux files and processes, and Linux decides who may read a file or run a program using owner, group and mode. If `~/.kube/config` is owned by root, `kubectl` stops working for you. If a private key is world-readable, tools refuse it and security checks fail. The exam hosts allow you to use `sudo -i` to become root on a node (see [E8, LF tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)), and in a Pod, `runAsUser`, `runAsGroup` and `fsGroup` are the same numeric user and group IDs you learn here.

## 2. Concepts

### 2.1 Users and groups

**What it is.** Linux does not know names. Every process and every file carries two numbers: a **UID** (user ID) and a **GID** (group ID). Names such as `alice` are only labels that map to numbers in text files. The kernel checks numbers only. This is the key to the whole Pod security model: a container has no `alice`, only a number like `1000`.

**UID 0 is root.** The kernel gives UID 0 the right to bypass almost every permission check. The name `root` is not special, the number 0 is. Ubuntu convention:

| UID range | Meaning |
|---|---|
| 0 | root, the superuser |
| 1 to 999 | system accounts (services such as `www-data`), usually no login shell |
| 1000 and up | regular human users (Ubuntu default `UID_MIN` is 1000, set in `/etc/login.defs`) |

**Where the data lives.**

| File | One line per | Fields (separated by `:`) |
|---|---|---|
| `/etc/passwd` | user | `name:x:UID:GID:comment:home:shell`. The `x` means the password hash is in `/etc/shadow`. |
| `/etc/group` | group | `name:x:GID:member1,member2` |
| `/etc/shadow` | user | password hashes. Readable only by root (mode 0640, group `shadow`). |

**Commands to look up identity.**

| Command | What it shows |
|---|---|
| `whoami` | your user name (the effective user) |
| `id` | UID, primary GID and all group memberships. `id -u` and `id -g` print only the numbers. `id alice` asks about another user. |
| `groups [user]` | the group names |
| `getent passwd alice` | the passwd line for `alice`, from every configured source (local file, LDAP and others) |
| `getent group devs` | the group line, including members |

Prefer `getent` over `grep alice /etc/passwd`. `getent` asks the system's name service (NSS), so it also finds users that are not in the local file. On a kubeadm node both give the same answer.

REAL OUTPUT (Docker, ubuntu:24.04, run as root in a container; this is not a VM result):

```text
$ id
uid=0(root) gid=0(root) groups=0(root)
$ getent passwd root
root:x:0:0:root:/root:/bin/bash
$ getent group sudo
sudo:x:27:ubuntu
```

Read `uid=0(root) gid=0(root) groups=0(root)` as: effective user number 0 named root, primary group number 0, member of one group.

**Primary and supplementary groups.** Every user has one **primary group** (the `gid=` value). New files you create get this group, unless the directory has the setgid bit (section 2.6). A user can also belong to many **supplementary groups**, which only add access.

### 2.2 Creating users and groups

```bash
sudo useradd -m -s /bin/bash alice     # -m: create /home/alice, -s: login shell
sudo groupadd devs                      # create a group
sudo usermod -aG devs alice             # -a: APPEND, -G: supplementary group list
sudo passwd alice                       # set a password (lab only)
```

| Flag or command | What it does | Default if omitted | Risky use |
|---|---|---|---|
| `useradd -m` | creates the home directory | no home directory is created | none |
| `useradd -s /bin/bash` | sets the login shell | the distro default, often `/bin/sh` | `-s /usr/sbin/nologin` is a safe value for service accounts |
| `usermod -G devs alice` (no `-a`) | REPLACES the whole supplementary group list | n/a | removes alice from `sudo`. You can lock yourself out of sudo. Always use `-aG`. |
| `usermod -aG devs alice` | appends one group | n/a | none |
| `passwd alice` | sets a password | account has no password | weak passwords. Use only in the lab. |

`useradd` is the low-level tool (the same on every distro). Ubuntu also ships `adduser`, an interactive wrapper. Learn `useradd`, it is the one that behaves the same everywhere.

**Group changes need a new login.** A running shell keeps the groups it started with. After `usermod -aG devs alice`, alice must log out and in (or run `newgrp devs` for one shell) before `id` shows the new group.

REAL OUTPUT (Docker, ubuntu:24.04):

```text
$ useradd -m -s /bin/bash alice
$ useradd -m -s /bin/bash bob
$ groupadd devs
$ usermod -aG devs alice
$ usermod -aG devs bob
$ id alice
uid=1001(alice) gid=1001(alice) groups=1001(alice),1003(devs)
$ groups alice
alice : alice devs
$ getent group devs
devs:x:1003:alice,bob
$ tail -n 2 /etc/passwd
alice:x:1001:1001::/home/alice:/bin/bash
bob:x:1002:1002::/home/bob:/bin/bash
```

Why is the group `devs` number 1003 and not 1002? `useradd` made a private group for each user (GID 1001 for alice, 1002 for bob), so the next free number was 1003. This is called user private groups (UPG) and Ubuntu does it by default.

### 2.3 The rwx bits for files and directories

Every file has three sets of three bits: **user** (the owner), **group**, **other** (everyone else). The kernel picks one set: if you are the owner it uses the user bits only; else if you are in the file's group it uses the group bits only; else the other bits. It never adds sets together. So a file `-r--rw-rw-` is not writable by its owner, even though everyone else can write it.

The bits mean different things on files and directories:

| Bit | On a file | On a directory |
|---|---|---|
| `r` (read) | read the content (`cat`) | list the names inside (`ls`) |
| `w` (write) | change the content | create, rename or delete entries inside (needs `x` too) |
| `x` (execute) | run it as a program | enter it (`cd`) and reach files inside by name |

Consequences you will meet in real life:

- A directory with `r` but no `x` lets you see names but not open anything.
- A directory with `x` but no `r` lets you open a file if you know its exact name, but `ls` fails.
- Deleting a file needs `w` on the **directory**, not on the file.
- Root ignores `rwx` checks (except it cannot execute a file with no `x` bit at all).

`ls -l` shows the mode as ten characters:

```text
-rw-r--r--  1 root root  1123 Oct 27 07:05 ca.crt
drwxr-xr-x  2 root root  4096 Oct 27 07:05 etcd
│└┬┘└┬┘└┬┘
│ │  │  └─ other
│ │  └──── group
│ └─────── user (owner)
└───────── type: - file, d directory, l symlink
```

**Octal and symbolic modes.** `chmod` accepts two styles. Octal gives all nine bits at once (best for setting a full mode). Symbolic changes only some bits (best for "add this one thing").

```text
Each digit = r(4) + w(2) + x(1)

 bit value   4   2   1
             r   w   x      digit
 ---------------------------------
 ---         .   .   .        0
 --x         .   .   x        1
 -w-         .   w   .        2
 -wx         .   w   x        3
 r--         r   .   .        4
 r-x         r   .   x        5
 rw-         r   w   .        6
 rwx         r   w   x        7

 mode = [special][user][group][other]    e.g. 0644 = - rw- r-- r--
```

Three worked examples:

1. **0644**. User 6 = 4+2 = `rw-`. Group 4 = `r--`. Other 4 = `r--`. Result `-rw-r--r--`. Normal for public files such as certificates (`.crt`).
2. **0600**. User 6 = `rw-`. Group 0 = `---`. Other 0 = `---`. Result `-rw-------`. Only the owner can read and write. Normal for private keys and kubeconfigs.
3. **0755**. User 7 = 4+2+1 = `rwx`. Group 5 = 4+1 = `r-x`. Other 5 = `r-x`. Result `-rwxr-xr-x`. Normal for programs and directories everyone may enter.

Reverse direction: you see `-rw-r-----`. Split into `rw-` `r--` `---` and add: 6, 4, 0, so the mode is 0640.

Symbolic form is `chmod [ugoa][+-=][rwx]`:

| Command | Effect |
|---|---|
| `chmod u+x script.sh` | add execute for the owner |
| `chmod go-rwx key.pem` | remove all access for group and other |
| `chmod u=rw,go= key.pem` | set owner to rw, group and other to nothing (same as 600) |
| `chmod g+r file` | add read for the group |
| `chmod -R 755 dir` | apply recursively (careful: this gives files the `x` bit too) |
| `chmod -R u=rwX,go=rX dir` | capital `X` adds execute only to directories (and files that already have x) |

REAL OUTPUT (Docker, ubuntu:24.04):

```text
$ touch k.key; chmod 644 k.key; stat -c '%a %U:%G' k.key
644 root:root
$ chmod 600 k.key; stat -c '%a %U:%G' k.key
600 root:root
$ chmod u=rw,go= k.key; stat -c '%a' k.key
600
$ chmod g+r k.key; stat -c '%a' k.key
640
```

`stat -c '%a %U:%G' file` prints octal mode, owner and group on one line. Use it to check a mode quickly and without having to decode `ls -l` in your head.

### 2.4 Changing owner and group: chown and chgrp

```bash
sudo chown alice file            # owner only
sudo chown alice:devs file       # owner and group
sudo chown :devs file            # group only (same as chgrp devs file)
sudo chgrp devs file             # group only
sudo chown -R alice:devs dir     # -R: the whole tree, recursively
sudo chown $(id -u):$(id -g) f   # by numbers, from the current user
```

Rules: only root can give a file to another user. A normal user can use `chgrp` only on their own files and only to a group they belong to. `chown -R` is the fix you will use most on kubeadm nodes. Be careful with `-R` on a path like `/` or `/etc`: you can break the system. Never run `chown -R` with a variable that might be empty (`chown -R $x:$y /$dir`).

### 2.5 umask: the default mode of new files

When a program creates a file it asks for a mode: `0666` for files (never `x` by default) and `0777` for directories. The kernel then removes the bits listed in the **umask**. The rule is: `mode = requested AND NOT umask`.

| umask | New file (666 minus mask) | New directory (777 minus mask) | Typical use |
|---|---|---|---|
| 0022 | 644 | 755 | root and most shells: group and others can read |
| 0002 | 664 | 775 | Ubuntu normal users (private group makes this safe) |
| 0077 | 600 | 700 | private: only you can read |

Check with `umask` (prints the mask) and set it with `umask 077` (affects only the current shell and its children). The user's default comes from the login configuration, not from the file.

REAL OUTPUT (Docker, ubuntu:24.04, as root and then as `alice` in a login shell):

```text
$ umask
0022
$ su - alice -c 'umask; touch f1; mkdir d1; stat -c "%a %n" f1 d1; umask 077; touch f2; stat -c "%a %n" f2'
0002
664 f1
775 d1
600 f2
```

Why it matters: a file a program creates with the plain 0666 request ends up 644 under root's `0022` (664 under `0002`). A private key you save by pasting it into an editor, with `cat > key` or with `cp`, is therefore readable by group or others until you `chmod 600` it. Tools that generate keys usually ask for a stricter mode themselves: `openssl genrsa -out` creates 0600. Always check the mode of anything secret you create.

REAL OUTPUT (Docker, ubuntu:24.04, as `alice`, umask 0002):

```text
$ openssl genrsa -out k 2048 2>/dev/null; stat -c %a k
600
$ echo hi > plain; stat -c %a plain
664
```

### 2.6 setuid, setgid and the sticky bit

There is a fourth octal digit in front of the three: the **special bits**. `0644` has special digit 0. `2775` has special digit 2.

| Bit | Octal | Shows in `ls -l` as | On a file | On a directory |
|---|---|---|---|---|
| setuid | 4 | `s` in the user `x` position | the program runs as the file's owner, not as the caller | ignored on Linux |
| setgid | 2 | `s` in the group `x` position | the program runs with the file's group | new entries inherit the directory's group (and new subdirectories get setgid too) |
| sticky | 1 | `t` in the other `x` position | ignored on modern Linux | only the file's owner, the directory's owner or root may delete or rename entries |

A capital `S` or `T` means the special bit is set but the underlying `x` is not. That is usually a mistake.

**Why `passwd` has setuid.** `/etc/shadow` is root-only, yet any user can change their own password. `/usr/bin/passwd` is owned by root with setuid, so while it runs it acts as root. The same idea is why `sudo` has `s`. Setuid programs are a security risk, so audits list them with `find / -perm -4000 -type f 2>/dev/null`.

**Why `/tmp` is 1777.** Everyone needs to create files in `/tmp`, so it is `rwxrwxrwx`. But with only `rwx` for everyone, any user could delete anyone else's files (deleting needs `w` on the directory). The sticky bit (the leading `1`) fixes that.

**Why setgid on a shared directory.** If `ann` and `ben` both belong to `proj`, files they create get their own private primary group, and the other person cannot edit them. With setgid on the directory (`chmod 2770`), every new file gets the group `proj`. This is also what Kubernetes does for `fsGroup` volumes (section 2.9).

REAL OUTPUT (Docker, ubuntu:24.04):

```text
$ ls -ld /tmp
drwxrwxrwt 1 root root 0 Oct 27 07:05 /tmp
$ ls -l /usr/bin/passwd /usr/bin/sudo
-rwsr-xr-x 1 root root  72056 May 30  2024 /usr/bin/passwd
-rwsr-xr-x 1 root root 335120 Oct  6 13:51 /usr/bin/sudo
$ mkdir /srv/shared; chown root:devs /srv/shared; chmod 2775 /srv/shared
$ ls -ld /srv/shared
drwxrwsr-x 1 root devs 0 Oct 27 07:05 /srv/shared
$ su - alice -c 'touch /srv/shared/a.txt; ls -l /srv/shared/a.txt'
-rw-rw-r-- 1 alice devs 0 Oct 27 07:05 /srv/shared/a.txt
```

Read the last line: alice's own primary group is `alice`, yet the file's group is `devs`. The `s` in `drwxrwsr-x` did that.

### 2.7 sudo, sudo -i, sudo -u, sudoers and visudo

`sudo` runs one command as another user (root by default) after checking the policy in `/etc/sudoers`. It logs each use and asks for your own password (not root's), unless the policy says `NOPASSWD`.

| Command | What it does | Environment |
|---|---|---|
| `sudo cmd` | run `cmd` as root | your current directory and environment, but `PATH` is replaced by sudoers `secure_path` |
| `sudo -i` | start a root **login** shell | root's home (`/root`), root's profile, root's `PATH`. The exam hosts allow it (E8). |
| `sudo -s` | root shell that is NOT a login shell | `HOME` becomes `/root` (captured below), but root's login profile is not read |
| `sudo -u bob cmd` | run `cmd` as user `bob` | like `sudo cmd`: `HOME` becomes `/home/bob` (captured below), `PATH` is `secure_path`, no login profile |
| `sudo -iu bob` | login shell as `bob` | bob's home, bob's login profile and `PATH` |
| `sudo -l` | list what you are allowed to run | read-only |

**Where the rules live.** `/etc/sudoers` is the main file. Instead of editing it, drop a small file in `/etc/sudoers.d/`. Rules:

- Edit only with `visudo` (it locks the file and checks syntax before saving). Use `visudo -f /etc/sudoers.d/alice` for a drop-in.
- Drop-in files must be mode `0440` and owned by root. Ubuntu ignores file names that contain a dot or end with `~`.
- A syntax error in sudoers can break `sudo` for everyone. Check a file without installing it: `visudo -cf FILE`.
- A rule reads: `who where=(run-as) what`. `alice ALL=(ALL) NOPASSWD:ALL` means: alice, on any host, as any user, may run any command without a password. Lab only.

REAL OUTPUT (Docker, ubuntu:24.04):

```text
$ echo 'alice ALL=(ALL) NOPASSWD:ALL' > /etc/sudoers.d/alice; chmod 0440 /etc/sudoers.d/alice
$ visudo -cf /etc/sudoers.d/alice
/etc/sudoers.d/alice: parsed OK
$ su - alice -c 'sudo -n id; sudo -n -u bob id'
uid=0(root) gid=0(root) groups=0(root)
uid=1002(bob) gid=1002(bob) groups=1002(bob),1003(devs)
$ echo 'bad line' > /tmp/bad; visudo -cf /tmp/bad
/tmp/bad:1:9: syntax error
bad line
        ^
```

**Why `sudo: command not found` happens.** `sudo cmd` does not use your `PATH`. It uses the fixed `secure_path` from sudoers. If `cmd` lives in a directory that only your own `PATH` contains (for example `~/bin`), the root command cannot find it. `sudo -i` starts root's own login shell, which has root's `PATH` and `HOME=/root`. Either use the full path or `sudo -i`.

REAL OUTPUT (Docker, ubuntu:24.04, as `alice` with `~/bin/mytool` on her `PATH`):

```text
$ mytool
hello from mytool as alice
$ sudo mytool
sudo: mytool: command not found
$ sudo ~/bin/mytool
hello from mytool as root
$ sudo -i bash -c 'echo HOME=$HOME; id -un; pwd'
HOME=/root
root
/root
```

`sudo -i mytool` also fails, because root's `PATH` does not include alice's `~/bin`.

**`HOME` under sudo.** With `env_reset` on (the Ubuntu default) sudo sets `HOME` to the target user's home even without `-i`. REAL OUTPUT (Docker, ubuntu:24.04, as `alice`):

```text
$ sudo -u bob sh -c 'echo $HOME'
/home/bob
$ sudo -s <<< 'echo $HOME'
/root
$ sudo -iu bob sh -c 'echo $HOME'
/home/bob
```

So the reason to prefer `sudo -iu bob` over `sudo -u bob` is the login environment (profile files, `PATH`, starting in bob's home directory), not `HOME` itself.

**The same trap with `kubectl`.** On a kubeadm node installed from the apt packages, `kubectl` is in `/usr/bin`, which is inside `secure_path`, so `sudo kubectl` normally finds the binary. Where `kubectl` lives on the exam hosts is UNVERIFIED (E9 lists the tool, not its path). If `kubectl` fails under `sudo`, there are two different causes, and the message tells them apart. `command not found` means the binary is not on the `PATH`: use the full path from `command -v kubectl` (run as your normal user), or `sudo -i`. A kubeconfig error such as `The connection to the server localhost:8080 was refused` means `kubectl` ran but found no kubeconfig, because as root `HOME` is `/root`, where there may be none. Check `echo $KUBECONFIG` and `ls -l ~/.kube/config` after `sudo -i`, or run `kubectl` as your normal user.

### 2.8 File modes Kubernetes expects

A kubeadm node is a normal Linux host. Its security rests on file modes. Targets (kubeadm sets them for you, you must not weaken them):

| Path | Expected mode | Owner | Why |
|---|---|---|---|
| `/etc/kubernetes/pki/*.crt` | 0644 | root:root | certificates are public data |
| `/etc/kubernetes/pki/*.key` | 0600 | root:root | private keys: anyone who reads one can act as that component |
| `/etc/kubernetes/admin.conf` | 0600 | root:root | contains a client certificate and key of a cluster admin |
| `/etc/kubernetes/kubelet.conf` | 0600 | root:root | the kubelet's credentials |
| `/etc/kubernetes/controller-manager.conf`, `scheduler.conf` | 0600 | root:root | component credentials |
| `/etc/kubernetes/manifests/*.yaml` | 0600 | root:root | static Pod definitions. The kubelet runs them as root, so only root may change them. |
| `/var/lib/kubelet/config.yaml` | 0644 | root:root | kubelet configuration (no secrets) |

All of these are the values kubeadm normally produces, but "normally" must be checked on your own version: see section 5 part B and section 11. Check them with:

```bash
sudo ls -l /etc/kubernetes/pki
sudo stat -c '%a %U:%G %n' /etc/kubernetes/*.conf /etc/kubernetes/manifests/*
```

Everything under `/etc/kubernetes` is root-only, so use `sudo` (or `sudo -i`) to read it. Note that `ls -l /etc/kubernetes/pki` as a normal user may work for the listing (the directory is usually 0755) but not for reading the `.key` files.

**Related but different.** File modes protect against other Linux users on the node. They do not protect against anyone who can create a Pod that mounts the node's `/etc/kubernetes` with `hostPath`, and run it as root. That is why the next lessons on security contexts and admission matter.

### 2.9 Setting up ~/.kube/config after kubeadm init

`kubeadm init` writes the admin credentials to `/etc/kubernetes/admin.conf` (root-only). To use `kubectl` as a normal user, copy it to that user's home and give them ownership. These are the three commands that kubeadm itself prints at the end of `init`. Learn them by heart:

```bash
mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config
```

| Step | What it does | What goes wrong if you skip it |
|---|---|---|
| `mkdir -p $HOME/.kube` | creates the directory, `-p` means no error if it exists | `cp` fails: "No such file or directory" |
| `sudo cp -i ...` | copies the root-only file. `-i` asks before overwriting an existing config. | no config: `kubectl` talks to `localhost:8080` and fails |
| `sudo chown $(id -u):$(id -g) ...` | `$(id -u)` and `$(id -g)` expand to YOUR numbers, **before** `sudo` runs, so the file becomes yours | file stays owned by root with mode 0600: `permission denied` |

Why the `sudo cp` result is owned by root: the copy was made by a root process, so the new file belongs to root. And since `admin.conf` is mode 0600, the copy is 0600 root, which you cannot read.

REAL OUTPUT (Docker, ubuntu:24.04, same effect with a different file; `/etc/shadow` stands in for `admin.conf` because it is also root-only):

```text
$ mkdir ~/.kube; sudo cp /etc/shadow ~/.kube/config; ls -l ~/.kube/config; cat ~/.kube/config
-rw-r----- 1 root root 529 Oct 27 07:07 /home/alice/.kube/config
cat: /home/alice/.kube/config: Permission denied
$ sudo chown $(id -u):$(id -g) ~/.kube/config; ls -l ~/.kube/config
-rw-r----- 1 alice alice 529 Oct 27 07:07 /home/alice/.kube/config
```

The exact text `kubectl` prints is in section 6. The kubeadm docs show these commands: [create-cluster-kubeadm](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/).

### 2.10 Linking UIDs to Pods: runAsUser, runAsGroup, fsGroup

A container is a normal Linux process, so it has a UID and GID like any other. Container images usually run as root (UID 0) unless the image says otherwise. The Pod `securityContext` lets you choose the numbers. Full coverage is in T3.17; this is the preview you need now.

| Field | Where | What it does | Default | Risky value |
|---|---|---|---|---|
| `runAsUser` | Pod or container `securityContext` | UID of the container process | the image's `USER`, often 0 | `0` (root in the container) |
| `runAsGroup` | Pod or container | primary GID of the process | the image's group, often 0 | `0` |
| `fsGroup` | Pod `securityContext` only | the kubelet sets the group of supported volumes to this GID, sets the setgid bit and adds the GID to the process's supplementary groups | none: volume ownership untouched | a GID that overlaps host data |
| `fsGroupChangePolicy` | Pod `securityContext` | `OnRootMismatch` changes ownership only if the volume root does not match, `Always` (default) walks every file | `Always` | `Always` on a huge volume makes Pod start slow |
| `runAsNonRoot` | Pod or container | the kubelet refuses to start a container that would run as UID 0 | false | n/a |
| `supplementalGroups` | Pod | extra GIDs for the process | none | n/a |

Where a field exists at both levels, the container value wins over the Pod value.

**Flow of a UID** (also drawn in section 3):

1. The container process runs as the UID you set (for example 1000). Inside the container, that UID may have no name at all. With `runAsUser: 1000`, `runAsGroup: 3000` and `fsGroup: 2000`, the number 2000 appears in the process's group list. REAL OUTPUT (Docker, busybox:1.36, `--user 1000:3000 --group-add 2000`, which sets the same numbers): `uid=1000 gid=3000 groups=2000,3000`. The Kubernetes docs page shows `groups=2000` for a similar Pod, so whether the primary GID is repeated in `groups=` depends on the runtime and the `id` tool. Look for 2000 in the list, not for the exact string.
2. A volume is mounted at `/data`. On disk (on the node) the volume directory has an owner, a group and a mode. The numbers on disk are the same numbers the container sees. There is no translation by default. The starting mode depends on the volume type (table below).
3. If the owner, group and other bits that apply to the process do not give write access, `touch /data/f` fails with `Permission denied`.
4. `fsGroup: 2000` makes the kubelet, for volume types that support ownership changes, set the group of the volume to 2000, add group read and write plus the setgid bit, and add 2000 to the process's groups. Now the process can write through the group bits, and new files keep group 2000.

| Volume | Directory the container finds at the start | Write as UID 1000 without `fsGroup` | What `fsGroup` changes |
|---|---|---|---|
| `emptyDir` | created with mode 0777 | works (the other bits allow it) | group becomes 2000, setgid bit is added, so new files get group 2000. It does not fix a denial here, there is none. |
| `hostPath` with `DirectoryOrCreate` | created 0755, owned by the kubelet's user (root) | denied (UID 1000 uses the `r-x` other bits) | nothing: the kubelet does not change host directories |
| PVC | set by the storage provisioner or filesystem | depends on the provisioner. UNVERIFIED here: a freshly formatted block volume with a root-owned 0755 root directory is the case where `fsGroup` turns a denial into success | group, setgid and group rw, if the volume type supports ownership management |

The failing case you can reproduce is `hostPath`: see section 5 part D.

**Which volumes support `fsGroup`.** It is applied to `emptyDir`, PersistentVolumeClaims and most block and network volumes that support ownership changes. It does **not** apply to `hostPath`, because the kubelet does not chown host directories. For `hostPath` or a volume where it does nothing, use an **init container** that runs as root and runs `chown` before the app starts. The failure is reproduced in section 5 part D, the sample YAML is in section 4 and the diagnosis steps are in section 6.

Docs page: [Configure a Security Context for a Pod or Container](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/).

### 2.11 ACL basics (awareness)

Classic `rwx` allows only one owner and one group per file. An **ACL** (access control list) adds extra named users or groups to one file without changing owner or group. Tools: `getfacl` shows, `setfacl` sets. They need the `acl` package and a filesystem with ACL support (ext4 and xfs have it).

```bash
setfacl -m u:bob:r-- /root/acl/f      # -m: modify. Give user bob read only
getfacl /root/acl/f                    # show the ACL
setfacl -x u:bob /root/acl/f           # -x: remove bob's entry
```

A `+` at the end of the mode in `ls -l` (`-rw-r--r--+`) tells you an ACL exists. The ACL has a **mask**, which caps the rights of named users and groups. `chmod` on a file with an ACL changes the mask, so a later `chmod 600` can silently reduce bob's access.

REAL OUTPUT (Docker, ubuntu:24.04):

```text
$ setfacl -m u:bob:r-- /root/acl/f; getfacl /root/acl/f
getfacl: Removing leading '/' from absolute path names
# file: root/acl/f
# owner: root
# group: root
user::rw-
user:bob:r--
group::r--
mask::r--
other::r--

$ ls -l /root/acl/f
-rw-r--r--+ 1 root root 0 Oct 27 07:05 /root/acl/f
```

You rarely need ACLs on Kubernetes tasks. Know that a `+` in `ls -l` means "look at `getfacl` too".

### 2.12 Capabilities overview: getcap and setcap

Linux splits the power of root into about 40 pieces called **capabilities**. Instead of "root can do everything", a process can hold only `CAP_NET_BIND_SERVICE` (bind ports below 1024) or `CAP_CHOWN` and so on. A file can carry capabilities too, and then runs with them even when started by a normal user.

```bash
getcap /usr/local/bin/py-copy                        # show file capabilities
sudo setcap cap_net_bind_service=+ep /usr/local/bin/py-copy   # give bind-low-port power
sudo setcap -r /usr/local/bin/py-copy                # remove
getcap -r /usr/bin 2>/dev/null                       # search a tree
```

`+ep` means add the capability to the **e**ffective and **p**ermitted sets. REAL OUTPUT (Docker, ubuntu:24.04, run on a copy of the python3 binary):

```text
$ getcap /usr/local/bin/py-copy
(no output: no capabilities yet)
$ setcap cap_net_bind_service=+ep /usr/local/bin/py-copy
$ getcap /usr/local/bin/py-copy
/usr/local/bin/py-copy cap_net_bind_service=ep
```

(The first line is a note for you, not tool output: `getcap` prints nothing for a file without capabilities.)

In Pods you use capabilities in the container `securityContext`:

```yaml
securityContext:
  capabilities:
    drop: ["ALL"]               # start from nothing
    add: ["NET_BIND_SERVICE"]   # add back only what is needed (name without the CAP_ prefix)
```

This is the preview of T3.17: drop everything, add back only what you need. A complete Pod using it is in section 4.

**Under the hood.** When a process calls `execve`, the kernel computes its capability sets from the user's UID, the file's capability bits and the parent's sets. Root (UID 0) normally gets the full set. A container runtime (containerd with runc) starts the container process with a limited set (a default list of about 14 capabilities), then applies `drop` and `add` from the Pod. The UID check (this lesson) and the capability check (above) are two separate gates. A non-root process with `NET_BIND_SERVICE` listed in the Pod may still fail to bind low ports in some setups, see section 11.

### 2.13 Related but different

| Confused pair | Difference |
|---|---|
| Linux user vs Kubernetes `User` | A Linux user is a UID on a node. Kubernetes has no user objects: a "user" in RBAC is a name inside a client certificate or token. They are unrelated. |
| `chmod` vs `chown` | `chmod` changes who may do what (the bits). `chown` changes who owns the file. |
| `sudo -i` vs `su -` | `sudo -i` uses your password and sudoers policy. `su -` needs the target user's password. The exam gives you `sudo -i`. |
| `runAsUser: 0` vs `privileged: true` | the first is only the UID. The second gives the container nearly all capabilities and device access. |

## 3. How it works (diagram)

```text
(1) rwx bits -> octal                    (2) UID/GID: container -> volume on the host

 mode 0 6 4 4                              Pod spec                      Node disk
      | | | |                              --------                      ---------
      | | | +-- other : r-- = 4            runAsUser:  1000  -+
      | | +---- group : r-- = 4            runAsGroup: 3000   |  process in container
      | +------ user  : rw- = 6            fsGroup:    2000   |  uid=1000 gid=3000
      +-------- special: setuid 4          volume: /data      |  2000 is in its groups
                         setgid 2                             v
                         sticky 1          +-------------------------------+
                                           | kubelet prepares the volume:  |
      r = 4   w = 2   x = 1                | chgrp 2000 /data              |
      rwx = 7  rw- = 6  r-x = 5  r-- = 4   | chmod g+rws /data (setgid)    |
                                           +---------------+---------------+
 Which set is used? (first match wins)                     |
   caller UID == file owner  -> user bits                  v
   else caller in file group -> group bits       /var/lib/kubelet/pods/.../data
   else                      -> other bits       drwxrwsrwx  root  2000
                                                 (numbers on disk = numbers in
                                                  the container, no translation)
                                                           |
                                          touch /data/f -> gid 2000 in groups
                                          -> group bits rw- -> allowed
                                          file owner 1000, group 2000
```

Walkthrough:

1. Left side: the kernel reads exactly one set of bits. It checks owner first, then group, then other, and stops at the first match. It never combines them.
2. Octal is a sum per set: read 4, write 2, execute 1. `0644` is `rw-` + `r--` + `r--`. The leading digit is for setuid, setgid and sticky.
3. Right side: the Pod spec only chooses numbers. The container process gets UID 1000, GID 3000 and the extra group 2000 (from `fsGroup`).
4. The volume lives on the node as a normal directory. Its owner and group are numbers, and the container sees the same numbers.
5. If the numbers do not give access, the write fails. On volumes that support it, `fsGroup` makes them match by giving the volume group 2000 (and the setgid bit, so new files keep it), which the process now belongs to. An `emptyDir` starts as 0777, so there `fsGroup` changes the group and setgid but no write was denied before. On a `hostPath` volume nothing is changed, and a root init container is the fix (section 5 part D).

## 6. Common mistakes and how to fix them

| Symptom | What you will see (exact text) | Cause | Fix (command) |
|---|---|---|---|
| `kubectl` cannot read `~/.kube/config` | `error: error loading config file "/home/ubuntu/.kube/config": open /home/ubuntu/.kube/config: permission denied` (EXPECTED, not captured) | the file was copied with `sudo cp` and is owned by root with mode 0600 | `sudo chown $(id -u):$(id -g) ~/.kube/config` |
| Container cannot write to a volume | `touch: /hp/f: Permission denied` in the Pod logs (EXPECTED, not captured; section 5 part D) | the app runs as UID 1000 but the volume directory is `root:root 0755`; `hostPath` ignores `fsGroup` (an `emptyDir` starts as 0777, so it does not produce this error) | for `hostPath`: an init container as root that runs `chown` (section 4), or fix the directory on the node. For a PVC whose root directory is not writable: `fsGroup`, if the volume type supports ownership management (UNVERIFIED here) |
| `sudo` cannot find a command | `sudo: mytool: command not found` (REAL OUTPUT, Docker) | `sudo` uses `secure_path`, not your `PATH` | use the full path (`sudo ~/bin/mytool`) or `sudo -i` |
| Private key refused | `Permissions 0644 for '/home/alice/lab/T1.04/lab_key' are too open.` then `Load key ...: bad permissions` (REAL OUTPUT, Docker, from `ssh-keygen`, section 7.3) | mode 0644 lets other users read a key you own | `chmod 600 key` |
| `sudo` broken after editing sudoers | `/tmp/bad:1:9: syntax error` from `visudo -cf` (REAL OUTPUT, Docker) | the file was edited by hand and not checked | always `visudo -f`; check with `visudo -cf FILE`; fix from a root shell |
| Added to a group, still denied | `id` does not show the group | the old shell keeps its old groups | log out and in, or `newgrp GROUP`, then `id` |

The repeatable path for any "permission denied":

1. **Who am I?** `id`. Note UID, GID and groups. For a Pod: `k exec POD -- id`.
2. **What does the file say?** `stat -c '%a %U:%G %n' PATH`, or `ls -ld PATH` (use `-d` for a directory).
3. **Walk the path.** Every directory in the path needs `x` for you: `namei -l /full/path/to/file` prints the mode of each level (`namei` is part of util-linux, present on Ubuntu).
4. **Pick the bit set the kernel will use** (owner, then group, then other, section 2.3) and compare with what you need.
5. **Fix the smallest thing:** `chown` if the owner is wrong, `chmod` if only the bits are wrong, `fsGroup` or an init container if it is a volume in a Pod.
6. **Verify with the failing command again**, not with `ls`.

Failure 1 in detail (kubeconfig). `kubectl` reads the file as your user. The kernel compares your UID to the owner (root), finds no match, checks your groups against the group (root), no match, then uses the "other" bits, which are `---` for mode 0600. So the open is denied. The diagnostics: `ls -l ~/.kube/config` shows `root root`; `id -u` shows your number. The fix changes the owner only, so the mode 0600 stays.

Failure 2 in detail (volume). Run `k logs POD -n NS` to see the error (`touch: /hp/f: Permission denied`). Then `k exec POD -n NS -- id` to get the process's numbers and `k exec POD -n NS -- ls -ldn /mountpath` to get the directory's numbers (`-n` prints numbers, which is what the kernel compares). Apply the rule from section 2.3: if the directory owner is not your UID and its group is not in your group list, the kernel uses the "other" bits, and if those lack `w` that is the cause. `k exec` only works while the container is running, so a Pod whose command exits on the error needs `k logs --previous` instead; the section 4 Pods keep running for this reason. Then choose the fix by volume type (table in section 2.10): for `hostPath` `fsGroup` has no effect, so use the root init container (or fix the directory on the node); an `emptyDir` is 0777 and does not produce this error; for a PVC with a non-writable root directory `fsGroup` is the tool. The full run with the failing and the fixed Pod is section 5 part D.

Failure 3 in detail (`sudo` and `PATH`). `sudo` replaced `PATH`. Check with `sudo sh -c 'echo $PATH'`. Compare with `echo $PATH`. Fix: the full path, or `sudo -i`. REAL OUTPUT (Docker, ubuntu:24.04):

```text
$ sudo sh -c 'echo $PATH'
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin
$ echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin
```

### 7.1 Easy: shared directory with setgid (linux-vm)

**Environment:** the Ubuntu VM (`linux-vm`), your normal user with `sudo`.

**Setup:**

```bash
mkdir -p ~/lab/T1.04
sudo rm -rf /srv/proj
sudo groupdel proj 2>/dev/null; sudo userdel -r ann 2>/dev/null; sudo userdel -r ben 2>/dev/null; sudo userdel -r eve 2>/dev/null; true
```

**Task.** Create users `ann`, `ben` and `eve` (all with home directories and `/bin/bash`) and a group `proj`. Put `ann` and `ben` in `proj`, but not `eve`. Create `/srv/proj`, owned by `root:proj`, so that:

- members of `proj` can create and edit files in it,
- every new file in it gets the group `proj` automatically,
- other users (`eve`) cannot even list it.

As `ann`, create `/srv/proj/ann.txt`. Prove that `ben` can append to it.

<details><summary>Hint 1</summary>

Use `useradd -m -s /bin/bash` for each user, and `usermod -aG` (with `-a`) to add to the group.

</details>

<details><summary>Hint 2</summary>

The mode you need has a special digit (`2`) for setgid, then `7 7 0`.

</details>

<details><summary>Hint 3</summary>

To run a command as ann with ann's login environment (and her `umask 0002`), use `sudo su - ann -c '...'`. If ben cannot append, look at the mode of `ann.txt` with `ls -l`: the group needs `w`.

</details>

<details><summary>Solution</summary>

```bash
sudo useradd -m -s /bin/bash ann
sudo useradd -m -s /bin/bash ben
sudo useradd -m -s /bin/bash eve
sudo groupadd proj
sudo usermod -aG proj ann
sudo usermod -aG proj ben
sudo mkdir /srv/proj
sudo chown root:proj /srv/proj
sudo chmod 2770 /srv/proj
sudo su - ann -c 'touch /srv/proj/ann.txt; ls -l /srv/proj/ann.txt'
sudo su - ben -c 'echo from-ben >> /srv/proj/ann.txt'
```

Why each step: the users and group are the identities. `usermod -aG` appends the group (without `-a` it would replace the list). `chown root:proj` makes `proj` the directory's group, so the group bits apply to its members. `2770` gives the owner and group full rights, others nothing, and the setgid bit makes new files take the group `proj`. Without setgid, `ann.txt` would get group `ann` and `ben` would be denied. The `su - ann` login shell picks up ann's group list and her umask 0002, so the new file is `664`, group-writable. If your umask is 0022 the file is 644 and ben's append fails: fix with `chmod g+w`.

</details>

**Verification** (each line prints PASS or FAIL):

```bash
test "$(stat -c '%a %U:%G' /srv/proj)" = "2770 root:proj" && echo PASS-dir || echo FAIL-dir
test "$(stat -c '%G' /srv/proj/ann.txt)" = proj && echo PASS-group || echo FAIL-group
grep -q from-ben /srv/proj/ann.txt && echo PASS-ben-wrote || echo FAIL-ben-wrote
id -nG ben | grep -qw proj && ! id -nG eve | grep -qw proj && echo PASS-members || echo FAIL-members
sudo su - eve -c 'ls /srv/proj' 2>&1 | grep -q 'Permission denied' && echo PASS-eve-denied || echo FAIL-eve-denied
```

**Cleanup:**

```bash
sudo rm -rf /srv/proj
sudo userdel -r ann; sudo userdel -r ben; sudo userdel -r eve; sudo groupdel proj
```

### 7.2 Medium: kubeconfig for a non-root user (vms)

**Environment:** a kubeadm control-plane node, for example `cp1` from the `vms` environment (T4.01 builds it). If you only have the plain `linux-vm`, you cannot run `k get nodes`, but you can practise the ownership steps with a dummy root-only file instead (see the note at the end).

**Setup** (from `base`, go to the node first; stay on `cp1` for the whole lab):

```bash
ssh cp1
sudo userdel -r dev1 2>/dev/null; true
sudo useradd -m -s /bin/bash dev1
```

**Task.** The user `dev1` must be able to run `kubectl get nodes` using the admin credentials of this cluster.

1. Put the credentials at `/home/dev1/.kube/config`.
2. The file must be owned by `dev1:dev1` and have mode 600.
3. Prove it by running `kubectl get nodes` as `dev1` and saving the output to `~/lab/T1.04/nodes.txt`.

Do it as your own user with `sudo`. Do not log in as dev1 and do not change the mode of `/etc/kubernetes/admin.conf`.

<details><summary>Hint 1</summary>

The three post-kubeadm commands, but the destination is dev1's home, not yours.

</details>

<details><summary>Hint 2</summary>

`mkdir` and `cp` run as root with `sudo` create root-owned results. Use `chown -R dev1:dev1 /home/dev1/.kube` for the directory and the file.

</details>

<details><summary>Hint 3</summary>

To run a command as dev1 in dev1's login environment, use `sudo -iu dev1 COMMAND`. (Plain `sudo -u dev1` also sets `HOME` to `/home/dev1`, but it skips dev1's login profile and starts in your current directory.)

</details>

<details><summary>Solution</summary>

```bash
mkdir -p ~/lab/T1.04
sudo mkdir -p /home/dev1/.kube
sudo cp -i /etc/kubernetes/admin.conf /home/dev1/.kube/config
sudo chown -R dev1:dev1 /home/dev1/.kube
sudo -iu dev1 kubectl get nodes | tee ~/lab/T1.04/nodes.txt
```

Why: the directory and file are created by root, so they belong to root. `kubectl` runs as `dev1` and can only read files owned by `dev1` (the mode is 0600, so no one else may read). `chown -R` fixes both the directory and the file. `sudo -iu dev1` runs a login shell as dev1 with `HOME=/home/dev1`, so kubectl finds `.kube/config` there. Before the `chown`, `sudo -iu dev1 kubectl get nodes` fails with the permission denied error from section 6, which is a good way to see the problem first.

</details>

**Verification:**

```bash
test "$(sudo stat -c '%a %U:%G' /home/dev1/.kube/config)" = "600 dev1:dev1" && echo PASS-mode || echo FAIL-mode
test "$(sudo stat -c '%a %U:%G' /etc/kubernetes/admin.conf)" = "600 root:root" && echo PASS-admin-untouched || echo FAIL-admin-untouched
grep -q ' Ready' ~/lab/T1.04/nodes.txt && echo PASS-nodes || echo FAIL-nodes
```

EXPECTED OUTPUT (not captured): three lines starting with `PASS-`.

**Cleanup:**

```bash
sudo userdel -r dev1
rm -f ~/lab/T1.04/nodes.txt
exit                          # leave cp1, back to base
```

Note for `linux-vm` without a cluster: replace `/etc/kubernetes/admin.conf` with a dummy root-only file (`sudo sh -c 'echo dummy > /root/fake.conf; chmod 600 /root/fake.conf'`) and replace the `kubectl` check with `sudo -iu dev1 cat /home/dev1/.kube/config`. Remove `/root/fake.conf` at the end.

### 7.3 Break-fix: key file with the wrong mode (linux-vm)

**Environment:** the Ubuntu VM (`linux-vm`). The tool in this lab is `ssh-keygen`, which refuses a private key that others can read. (Kubernetes components generally do not refuse a key by mode. The lesson is the diagnosis path, which is the same everywhere.)

**Setup** (`break.sh`, run once as your normal user):

```bash
# break.sh
mkdir -p ~/lab/T1.04
rm -f ~/lab/T1.04/lab_key ~/lab/T1.04/lab_key.pub
ssh-keygen -q -t ed25519 -N '' -f ~/lab/T1.04/lab_key
chmod 644 ~/lab/T1.04/lab_key
```

**Task.** `ssh-keygen -y -f ~/lab/T1.04/lab_key` (it prints the public key that belongs to a private key) must work for your user. Find out why it fails, and fix it with the smallest change, using `stat` to show the state before and after. The final state must be mode 600 owned by you. Do not recreate the key and do not run `ssh-keygen` with `sudo`.

<details><summary>Hint 1</summary>

Run the failing command and read the whole message, then run `stat -c '%a %U:%G %n' ~/lab/T1.04/lab_key`.

</details>

<details><summary>Hint 2</summary>

The message names a mode (four digits) and says who must not be able to access the file. Compare that mode with the three triplets you learned in section 2.3: which triplets are non-zero for group and other?

</details>

<details><summary>Hint 3</summary>

The owner is already you, so no `chown` is needed. Only the bits are wrong. A private key should be readable and writable by its owner and nothing else.

</details>

<details><summary>Solution</summary>

```bash
stat -c '%a %U:%G %n' ~/lab/T1.04/lab_key      # 644 <you>:<you> ...
ssh-keygen -y -f ~/lab/T1.04/lab_key           # refused: bad permissions
chmod 600 ~/lab/T1.04/lab_key
stat -c '%a %U:%G %n' ~/lab/T1.04/lab_key      # 600 <you>:<you> ...
ssh-keygen -y -f ~/lab/T1.04/lab_key           # prints the public key
```

REAL OUTPUT (Docker, ubuntu:24.04, as `alice`; your path shows your own home):

```text
$ stat -c '%a %U:%G %n' ~/lab/T1.04/lab_key
644 alice:alice /home/alice/lab/T1.04/lab_key
$ ssh-keygen -y -f ~/lab/T1.04/lab_key
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@         WARNING: UNPROTECTED PRIVATE KEY FILE!          @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
Permissions 0644 for '/home/alice/lab/T1.04/lab_key' are too open.
It is required that your private key files are NOT accessible by others.
This private key will be ignored.
Load key "/home/alice/lab/T1.04/lab_key": bad permissions
$ chmod 600 ~/lab/T1.04/lab_key
$ ssh-keygen -y -f ~/lab/T1.04/lab_key
ssh-ed25519 AAAA...
```

Why each step: `stat` shows owner you and mode 644, which is `rw-` for you and `r--` for group and other. The message says the key is "accessible by others", and the 4 in the group and other positions is exactly that. The owner is correct, so only `chmod` is needed. Mode 600 removes group and other access, and `ssh-keygen` accepts the key. `chmod 400` would also be accepted by `ssh-keygen`, but the verification below asks for 600. A note on scope: in the Docker capture, a key that was owned by root and mode 644 was accepted by `ssh-keygen` run as another user, so this check applies to keys you own. That is why the lab leaves the owner alone.

</details>

**Verification** (both lines must print PASS):

```bash
test "$(stat -c '%a %U' ~/lab/T1.04/lab_key)" = "600 $(id -un)" && echo PASS-mode-owner || echo FAIL-mode-owner
ssh-keygen -y -f ~/lab/T1.04/lab_key 2>/dev/null | grep -q '^ssh-ed25519 ' && echo PASS-key-works || echo FAIL-key-works
```

Right after `break.sh` both lines print FAIL (mode is 644 and `ssh-keygen` prints nothing on stdout). After `chmod 600` both print PASS (checked in Docker).

**Cleanup:**

```bash
rm -rf ~/lab/T1.04
```

## 8. Exam tips

- On exam hosts, switch to root with `sudo -i` ([E8](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)) and leave with `exit`. After the task, make sure you are back on host `base` (E7: nested `ssh` is not supported, you exit back after each task). `kubectl` is available on the SSH hosts and `yq`, `curl`, `wget` and `man` too (E9). Do not assume `jq` or `tmux`.
- If `kubectl` fails right after `sudo -i`, check `ls -l ~/.kube/config` and `echo $KUBECONFIG`: `HOME` is now `/root`, so the config may be missing. Exit root and run `kubectl` as the normal user, or pass `--kubeconfig`.
- Before changing a mode, read it: `stat -c '%a %U:%G %n' FILE`. Octal is quicker to compare than the long form. Keys are 600, certificates are 644.
- Open these docs pages when you need a `securityContext` field: https://kubernetes.io/docs/tasks/configure-pod-container/security-context/ and the kubeadm page for the post-init commands: https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/.
- `fsGroup` goes at the **Pod** level, `capabilities` at the **container** level, `runAsUser` and `runAsGroup` can go on either. A misplaced field is rejected with `unknown field` or silently ignored by older tooling, so check with `k apply` output and `k explain pod.spec.securityContext`.
- Traps: `chown -R` on the wrong path, `usermod -G` without `-a`, forgetting that `fsGroup` does nothing for `hostPath`, and leaving a file in your home owned by root after `sudo cp`.

## 9. Quick review

1. What command prints your UID, GID and all groups? Why does the kernel not care about user names?
2. Convert `-rwxr-x---` to octal and say who can do what.
3. A new file ends up with mode 644 and a new directory with 755. What is the umask?
4. Why is `/tmp` mode 1777 and what does the `t` do?
5. Which three commands set up `~/.kube/config` after `kubeadm init`, and why `$(id -u):$(id -g)`?
6. `sudo kubectl get nodes` says `command not found`, but plain `kubectl` works. Why, and what are two fixes?
7. A Pod running with `runAsUser: 1000` gets `Permission denied` writing to a PVC mount whose root directory is owned by root with mode 0755 (assume the provisioner made it so). Which field can fix it and what does the kubelet do?
8. Why does `fsGroup` not help for a `hostPath` volume, and what do you use instead?
9. What does `usermod -G devs alice` do compared with `usermod -aG devs alice`?
10. What does `getcap` show and what is `CAP_NET_BIND_SERVICE` for?

<details><summary>Answers</summary>

1. `id`. The kernel checks only numbers (UID and GID). Names are labels from `/etc/passwd` and `/etc/group`, which is why a container can run as UID 1000 with no name at all.
2. 750. Owner `rwx` (7), group `r-x` (5), other `---` (0). The owner can read, write and run, the group can read and run, others nothing.
3. 0022 (666 minus 022 = 644, 777 minus 022 = 755).
4. Everyone needs to write in `/tmp`, but without more protection anyone could delete anyone's files. The sticky bit (`t`, the leading `1`) allows deletion only by the file owner, the directory owner or root.
5. `mkdir -p $HOME/.kube`, `sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config`, `sudo chown $(id -u):$(id -g) $HOME/.kube/config`. `$(id -u)` and `$(id -g)` expand in your shell before `sudo` runs, so they are your numbers.
6. `sudo` uses `secure_path`, not your `PATH`, so a binary found only through your `PATH` is not found. Fixes: `sudo -i` (root's login shell) or the full path to the binary. Also check the kubeconfig under root's `HOME`.
7. `fsGroup` at Pod level, if the volume type supports ownership management. The kubelet changes the volume's group to that GID, sets setgid and group read/write, and adds the GID to the process's supplementary groups, so the group bits allow the write. (An `emptyDir` is already 0777, so it never needs this for a denial.)
8. The kubelet does not change ownership of host directories for `hostPath`. Use an init container running as UID 0 that runs `chown`, or fix the directory on the node.
9. Without `-a`, `-G` replaces the whole supplementary group list (you can lose `sudo`). With `-aG`, the group is appended.
10. `getcap` lists the capabilities attached to a file. `CAP_NET_BIND_SERVICE` allows binding ports below 1024 without being root.

</details>
