## 1. Why this matters

Every Kubernetes object is a tree of maps, lists and scalars. You write it as YAML, `kubectl` turns it into JSON, and the API server answers in JSON. If you cannot read that tree and pull one field out of it, you cannot answer "which node is this Pod on", "what is the Ready condition", or "write all node IPs to a file" without scrolling through 80 lines of `-o yaml` by eye.

In real life the same skills prevent the quiet failures: a Helm values file where `enabled: yes` becomes a boolean and the chart breaks, a ConfigMap value `0644` that turns into the wrong number, or a `kubectl apply` that dies with `did not find expected key` because one line is indented by three spaces. In the exam, tasks often say "write the result to a file", and the file is checked exactly. `yq` is on the exam hosts ([tips page](https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad)), so editing YAML from the command line is a fair and fast option, but only if you know its traps (for example, one wrong `yq -i` can delete every other document in a multi-document file).

## 2. Concepts

### 2.1 Why two formats

YAML and JSON describe the same data model: **maps** (key to value), **lists** (ordered values) and **scalars** (strings, numbers, booleans, null). YAML is made for people: no braces, comments allowed, indentation shows structure. JSON is made for programs: strict, no comments, every string quoted.

What actually happens when you run `k apply -f pod.yaml`:

1. `kubectl` reads the YAML and converts it to JSON. It sends JSON to the API server. (In the captured request headers below, `Content-Type: application/json`.)
2. The API server decodes the JSON into the Go type for that kind (`Pod`, `Deployment`, ...). The Go type decides what is legal: `replicas` is an integer, `env[].value` is a string.
3. The server validates, stores the object, and later returns it as JSON (or YAML if `kubectl` converts it for you).

This is why most "YAML problems" are really type problems. The YAML parser does not know that `value` must be a string. It sees `true`, makes a boolean, and the server rejects it in step 2.

```text
$ k apply -f app.yaml -v=8 2>&1 | grep -E 'Content-Type|PATCH|POST' | head -3
	Content-Type: text/plain; charset=utf-8
	Content-Type: application/json
	Content-Type: application/json
```

REAL OUTPUT (kind v0.33.0, v1.37.0). The first `text/plain` line belongs to a request that I did not identify (see section 11); the lines after it are JSON.

Plain `k get pods` is different: the same `-v=8` trick shows the request header `Accept: application/json;as=Table;v=v1;g=meta.k8s.io,...`. The server builds the printed table (NAME, READY, STATUS) and `kubectl` only prints it. That is why you cannot reach fields such as `.status.podIP` from the normal table: the table only has the columns the server chose. Output formats `-o yaml`, `-o json`, `-o jsonpath` and `-o custom-columns` give you access to the full object.

### 2.2 YAML syntax: maps, lists, scalars, indentation, documents

| Structure | Block style (what you write) | Flow style (inline, same meaning) |
|---|---|---|
| Map | `name: solo` on its own line, nested keys indented below | `{name: solo, tier: backend}` |
| List | one `- item` per line | `[sleep, "3600"]` |
| Scalar | `image: busybox:1.36` | same |
| Comment | `# text` to end of line | same (JSON has no comments) |

Rules that cause most errors:

- **Indentation is spaces only.** A tab character is illegal as indentation. The parser stops with `found character that cannot start any token`.
- **Siblings must line up exactly.** Keys of one map must start in the same column. One extra space makes the parser think the line is a continuation of the line above.
- **A list item can sit at the same indent as its parent key or be indented further.** Both are legal and equal:

```yaml
containers:
- name: a        # list item at the same column as "containers"
containers:
  - name: a      # list item indented two spaces (the style used in this lesson)
```

- **`key: value` needs a space after the colon.** `image:nginx` is one scalar string, not a pair.
- **Multi-document files.** A line with only `---` starts a new document. `kubectl apply -f file.yaml` applies every document in order. Keep related objects (Deployment + Service + ConfigMap) in one file when you want to apply them together.
- **Quotes.** `"double"` quotes understand escapes such as `\n`. `'single'` quotes take everything literally; a literal single quote is written twice (`'didn''t'`). Both produce a string.

Real example of a tab error (the file `tabbed.yaml` has tab characters before `containers:`):

```text
$ k create -f tabbed.yaml --dry-run=client
error: error parsing tabbed.yaml: error converting YAML to JSON: yaml: line 6: found character that cannot start any token

$ yq '.' tabbed.yaml
Error: bad file 'tabbed.yaml': go-yaml load error in scanner (while scanning for the next token) at L6.C1: found character that cannot start any token
```

REAL OUTPUT (host). Both tools name line 6, the first tab. `yq` also gives the column (`C1`), which `kubectl` does not.

### 2.3 Quoting pitfalls: booleans, numbers, strings and octal-looking values

**The problem.** In YAML a plain (unquoted) scalar is not always a string. The parser guesses the type from the characters. Kubernetes API fields have fixed types. When the guess and the field disagree, the server says `cannot unmarshal bool into Go struct field ... of type string`.

**Which words are guessed as booleans or numbers?** I tested each plain value as `data.k` of a ConfigMap (a field whose values must be strings) with `k apply -f t.yaml --dry-run=server`:

| Plain value you typed | What `kubectl` made of it | Result for a string field |
|---|---|---|
| `yes`, `Yes`, `YES`, `no`, `No`, `NO` | boolean | rejected: `cannot unmarshal bool` |
| `on`, `On`, `ON`, `off`, `Off`, `OFF` | boolean | rejected |
| `y`, `Y`, `n`, `N` | boolean | rejected |
| `true`, `True`, `TRUE`, `false`, `False`, `FALSE` | boolean | rejected |
| `0644`, `0o644`, `08`, `1_000`, `1e3`, `0x1F` | number | rejected: `cannot unmarshal number` |
| `1.10`, `.5` | number | rejected |
| `null`, `Null`, `~` | null | accepted; the value is empty |
| `12:30`, `1:30:00`, `2026-10-27` | string | accepted |
| `"yes"`, `'0644'` (quoted) | string | accepted |

REAL OUTPUT (kind v0.33.0, v1.37.0): this is a summary of 37 separate server dry-runs (one more, an explicit `!!str true`, also came back as the string `true`). The famous "Norway problem" is the `NO` row: a country code `NO` becomes the boolean `false`.

**Rule 1: if the API field is a string, quote anything that is not obviously text.** The common string fields: `env[].value`, ConfigMap `data` values, Secret `stringData` values, label and annotation values, image tags such as `"1.20"`.

**Rule 2: if the API field is an integer, do not quote it.** `replicas: "2"` and `containerPort: "80"` are rejected the other way round (`cannot unmarshal string into ... of type int32`).

**How do you know the field type?** Ask the API, do not guess:

```text
$ k explain deploy.spec.replicas
GROUP:      apps
KIND:       Deployment
VERSION:    v1

FIELD: replicas <integer>

DESCRIPTION:
    Number of desired pods. This is a pointer to distinguish between explicit
    zero and not specified. Defaults to 1.
```

REAL OUTPUT (kind v0.33.0, v1.37.0), trimmed. `<integer>` means no quotes. `<string>` means quote it if it could be read as something else.

**Octal-looking values.** File modes such as `defaultMode: 0644` are integer fields. `kubectl`'s YAML reader treats a leading `0` as octal, so `0644` is stored as the decimal number 420. Writing `644` is a different number (decimal 644), and the server rejects it because the maximum is octal 0777:

```text
$ k apply -f octal.yaml --dry-run=server -o yaml | grep -n defaultMode      # file has defaultMode: 0644
50:      defaultMode: 420
55:      defaultMode: 420

$ sed 's/0644/644/' octal.yaml | k apply -f - --dry-run=server -o yaml | grep -n defaultMode
The Pod "octal-demo" is invalid: 
* spec.volumes[0].configMap.defaultMode: Invalid value: 644: must be a number between 0 and 0777 (octal), both inclusive
* spec.containers[0].volumeMounts[0].name: Not found: "cfg"
```

REAL OUTPUT (kind v0.33.0, v1.37.0). The two `defaultMode: 420` lines are the Pod's own service-account volume (line 50) and the volume from the file (line 55); both are 420. The second error line is a side effect of the first (the volume is invalid, so the mount cannot find it). In the opposite direction, a ConfigMap data value like `mode: 0644` must be quoted (`"0644"`), because there it is a string field and the number would lose its leading zero.

**YAML 1.1 versus 1.2 (why tools disagree).** `kubectl` reads YAML with the older YAML 1.1 rules (where `yes`, `no`, `on`, `off` are booleans and `0644` is octal). `yq` follows YAML 1.2 for plain scalars. Same file, different answers:

```text
$ yq '.data' -o json cm.yaml          # cm.yaml: flag: yes / mode: 0755 / port: 8080
{
  "flag": "yes",
  "mode": 755,
  "port": 8080
}

$ k create -f cm.yaml --dry-run=server
Error from server (BadRequest): error when creating "cm.yaml": ConfigMap in version "v1" cannot be handled as a ConfigMap: json: cannot unmarshal bool into Go struct field ConfigMap.data of type string
```

REAL OUTPUT (kind v0.33.0, v1.37.0). `yq` shows `yes` as a string and `0755` as 755, so `yq` will never warn you about a value that `kubectl` rejects. Treat `kubectl apply --dry-run=server` as the judge, not `yq`. There is a second consequence: when you set a string with `yq` (for example `.value = "on"`), `yq` writes `on` without quotes, because in YAML 1.2 that is a string. `kubectl` then reads it as a boolean. Section 2.7 shows the fix (`style="double"`).

### 2.4 Block scalars `|` and `>` (multi-line ConfigMap data)

A **block scalar** is a multi-line string. You use it for config files inside a ConfigMap. The indicator is the last thing on the key line; the text below is indented consistently.

| Indicator | Meaning | Example result |
|---|---|---|
| `\|` (literal) | Keep every newline exactly | `"line one\nline two\n"` |
| `>` (folded) | Single newlines become spaces; a blank line becomes one newline | `"one two\nthree\n"` |
| `\|-` / `>-` (strip) | Same, but remove the final newline | `"line one\nline two"` / `"one two"` |
| `\|+` (keep) | Keep all trailing blank lines | Rarely needed |

The rule for the trailing newline: no sign (clip) keeps exactly one final newline; `-` strips it; `+` keeps all.

```text
$ cat bs.yaml
data:
  keep: |
    line one
    line two
  strip: |-
    line one
    line two
  fold: >
    one
    two

    three
  foldstrip: >-
    one
    two

$ yq -o json '.data' bs.yaml | jq -c .
{"keep":"line one\nline two\n","strip":"line one\nline two","fold":"one two\nthree\n","foldstrip":"one two"}
```

REAL OUTPUT (host). A ConfigMap that holds a file such as `nginx.conf` needs `|` so that the line breaks survive. `kubectl` shows the stored value back in the same style:

```text
$ k get cm shop-config -o yaml
apiVersion: v1
data:
  motd: |
    Welcome.
    Second line.
  summary: |
    This text is folded into one line.
kind: ConfigMap
...
```

REAL OUTPUT (kind v0.33.0, v1.37.0), trimmed. The `summary` key was written with `>` but is shown with `|`, because the stored string is a single line that ends with one newline. Both indicators produce the same string, and `kubectl` picks its own display style.

### 2.5 YAML and JSON are equivalent; `-o json`, `-o yaml` and `-o kyaml`

Any JSON document is also valid YAML, so every object can be shown in either form with no loss. These are the output formats you need:

| `-o` value | What you get | Use it for |
|---|---|---|
| `yaml` | Block-style YAML | Reading, editing, saving a manifest |
| `json` | Pretty JSON | Piping into `jq`; seeing the exact field names |
| `kyaml` | KYAML: a strict, always-quoted flow style of YAML | Unambiguous output; awareness for v1.37 |
| `name` | `pod/solo` | Scripting with `xargs`; `k delete $(k get ... -o name)` |
| `wide` | Table with extra columns | Quick look at IP and node |
| `jsonpath='...'` | Text built by a JSONPath template | Section 2.8 |
| `custom-columns=...` | Your own table | Section 2.9 |
| `go-template='...'` | Go template text | Also works, but JSONPath is the documented exam tool |

**KYAML.** KYAML is "a safer and less ambiguous subset of YAML designed specifically for Kubernetes, not a replacement for it". Every KYAML file is valid YAML, so any `kubectl` can read it as input. It graduated to **Stable in Kubernetes v1.37**, and `kubectl get -o kyaml` is Stable (v1.37 release blog: <https://kubernetes.io/blog/2026/08/26/kubernetes-v1-37-release/>; explainer: <https://kubernetes.io/blog/2026/08/11/how-to-pretty-print-kubernetes-yaml-as-kyaml/>). I confirmed that `-o kyaml` is accepted by `kubectl` v1.37.1 (the flag help lists `json|yaml|kyaml|name|...`).

What KYAML changes, from the captured output below: keys are not quoted, but every string value is double-quoted; every map uses `{}` and every list `[]`; entries end with a trailing comma; the document starts with a `---` line; indentation no longer carries meaning. That removes the two classic traps (whitespace and silent type changes). The blog says there are no plans to make it the default output; the exam tasks do not require it, so this is awareness only.

```text
$ k get pod solo -o kyaml | head -24
---
{
  apiVersion: "v1",
  kind: "Pod",
  metadata: {
    creationTimestamp: "2026-10-27T07:31:52Z",
    generation: 1,
    labels: {
      tier: "backend",
    },
    name: "solo",
    namespace: "lab-t113",
    resourceVersion: "...",
    uid: "...",
  },
  spec: {
    containers: [{
      command: [
        "sleep",
        "3600",
      ],
      image: "busybox:1.36",
      imagePullPolicy: "IfNotPresent",
      name: "solo",
```

REAL OUTPUT (kind v0.33.0, v1.37.0), trimmed (`...` replaces values that differ per cluster). A multi-line string appears as a quoted string with `\n` and backslash line continuations:

```text
$ k get cm shop-config -o kyaml
---
{
  apiVersion: "v1",
  data: {
    motd: "\
       Welcome.\n\
       Second line.\n\
      ",
    summary: "\
       This text is folded into one line.\n\
      ",
  },
  kind: "ConfigMap",
  ...
```

REAL OUTPUT (kind v0.33.0, v1.37.0), trimmed. `kubectl create cm demo --from-literal=a=b --dry-run=client -o kyaml` also works (real output: `kind: "ConfigMap"`, `apiVersion: "v1"`, ... in KYAML form), so you can generate a manifest in KYAML. I fed such a file to `yq` and it parsed as ordinary YAML.

### 2.6 jq: the JSON query tool

`jq` reads JSON on stdin and applies a **filter**. You build filters from small pieces joined with `|` (pipe, same idea as the shell pipe).

| Piece | Meaning | Example on `k get pods -o json` |
|---|---|---|
| `.` | The whole input | `jq .` pretty-prints |
| `.items[]` | Every element of the `items` list, one by one | `jq '.items[]'` |
| `.metadata.name` | Field access (dots) | `jq '.items[].metadata.name'` |
| `select(cond)` | Keep the input only if the condition is true | `.items[] \| select(.status.phase=="Running")` |
| `map(f)` | Apply `f` to every list element, collect into a list | `.items \| map(.metadata.name)` |
| `length` | Count of list items, map keys or string length | `.items \| length` |
| `keys` | Sorted list of a map's keys | `.metadata \| keys` |
| `to_entries` | Turn a map into a list of `{key, value}` | `.metadata.labels \| to_entries[]` |
| `-r` | Raw output: print strings without the JSON quotes | `jq -r '.items[0].metadata.name'` |
| `-c` | Compact one-line JSON | `jq -c '.items[0].metadata'` |
| `//` | Default when the left side is null | `.spec.nodeName // "-"` |
| `@tsv` | Format a list as tab-separated text | `[.a, .b] \| @tsv` |
| `--arg n v` | Pass a shell value in as `$n` | `jq --arg n solo '... == $n'` |
| `[ ... ]` | Collect results into a list | `[.items[] \| .metadata.name]` |

Real runs on the lab cluster (Pods `solo`, `stuck`, and three `web-*`):

```text
$ k get pods -o json | jq -r '.items[].metadata.name'
solo
stuck
web-69c6f74b8b-59trs
web-69c6f74b8b-cqnfp
web-69c6f74b8b-dvq4n

$ k get pods -o json | jq -r '.items[]|select(.status.phase!="Running")|.metadata.name'
stuck

$ k get pods -o json | jq '.items | length'
5

$ k get pod solo -o json | jq '.metadata | keys'
[
  "creationTimestamp",
  "generation",
  "labels",
  "name",
  "namespace",
  "resourceVersion",
  "uid"
]

$ k get pod solo -o json | jq -r '.metadata.labels | to_entries[] | "\(.key)=\(.value)"'
tier=backend

$ k get pods -o json | jq '.items | map(.metadata.name)'
[
  "solo",
  "stuck",
  "web-69c6f74b8b-59trs",
  "web-69c6f74b8b-cqnfp",
  "web-69c6f74b8b-dvq4n"
]

$ k get pods -o json | jq -r '.items[] | [.metadata.name, (.spec.nodeName // "-"), .status.phase] | @tsv'
solo	k-t113-worker	Running
stuck	-	Pending
web-69c6f74b8b-59trs	k-t113-worker	Running
web-69c6f74b8b-cqnfp	k-t113-worker2	Running
web-69c6f74b8b-dvq4n	k-t113-worker2	Running
```

REAL OUTPUT (kind v0.33.0, v1.37.0). Two things to notice. First, `k get pods -o json` returns a **List** object (`"kind": "List"`), so Pods are under `.items`. `k get pod solo -o json` returns the **single object**, with no `.items`. Second, without `-r`, `jq` prints strings with quotes (`"api-8dcbf848-2lcld"`) and with `-r` it does not. For files and shell variables you almost always want `-r`.

### 2.7 yq v4: YAML in, YAML out

`yq` (mikefarah, v4) uses a jq-like expression language but works on YAML directly. It keeps comments and key order. It handles **multi-document** files by running your expression once per document.

| Task | Command | Notes |
|---|---|---|
| Read a field | `yq '.spec.replicas' f.yaml` | Prints one result per document |
| Same, explicit sub-command | `yq e '.spec.replicas' f.yaml` | `e` is short for `eval`, the default sub-command. Old tutorials use it; `yq '...'` is the same |
| Edit in place | `yq -i '.spec.replicas = 3' f.yaml` | `-i` rewrites the file. Keep a copy first (`cp f.yaml f.bak`) |
| Select documents | `yq e 'select(.kind == "Service")' multi.yaml` | Prints only matching documents |
| Choose by position | `yq 'select(documentIndex == 1)' multi.yaml` | `documentIndex` starts at 0 |
| Convert to JSON | `yq -o json '.spec.selector' f.yaml` | Also `-o=json` |
| Drop the `---` lines | `yq -N '.kind' multi.yaml` | `-N` is `--no-doc` |
| Work across all documents at once | `yq ea '...' multi.yaml` | `ea` is `eval-all`; needed to merge or compare documents |
| Delete | `yq -i 'del(.metadata.labels)' f.yaml` | Applies to every document unless you `select` |
| Append to a list | `yq -i '.spec.template.spec.containers[0].env += [{"name":"A","value":"b"}]' f.yaml` | |
| Force quotes on a scalar | `yq -i '.path.to.value style="double"' f.yaml` | Required for strings that YAML 1.1 reads as bool/number |
| Show a node's type | `yq '.data.flag \| tag' f.yaml` | Prints `!!str`, `!!bool`, `!!int` or `!!float` (YAML 1.2 type) |

Real runs:

```text
$ k get deploy web -o yaml | yq '.spec.replicas'
3
$ k get deploy web -o yaml | yq '.spec.template.spec.containers[0].image'
nginx:1.27
$ k get deploy web -o yaml | yq -o json '.spec.selector'
{
  "matchLabels": {
    "app": "web"
  }
}
$ yq '.spec.replicas' app.yaml            # a 3-document file: Deployment, Service, ConfigMap
2
---
null
---
null
$ yq -N '.kind' app.yaml
Deployment
Service
ConfigMap
$ yq 'select(.kind == "Service") | .spec.ports[0].port' app.yaml
80
$ yq --version
yq (https://github.com/mikefarah/yq/) version v4.54.1
```

REAL OUTPUT (kind v0.33.0, v1.37.0) for the `k get ... | yq` lines, REAL OUTPUT (host) for the rest. Note that `yq '.spec.replicas' app.yaml` prints `null` for the Service and the ConfigMap, because they have no `.spec.replicas`. Filter with `select(...)` to avoid the noise.

**The big trap: `select` with assignment in a multi-document file.** Two expressions that look the same behave very differently:

```text
$ cp app.yaml work.yaml; yq -i 'select(.kind == "Deployment") | .spec.replicas = 4' work.yaml; cat work.yaml
apiVersion: apps/v1
kind: Deployment
...
spec:
  replicas: 4
...
          ports:
            - containerPort: 80
```

REAL OUTPUT (host), trimmed. The file now contains only the Deployment. The Service and the ConfigMap are gone, because `select(...) | ...` as the whole expression means "output only the selected documents", and `-i` writes that output back. The correct form puts the `select` and the path in parentheses on the left of the assignment:

```text
$ cp app.yaml work.yaml; yq -i '(select(.kind == "Deployment") | .spec.replicas) = 4' work.yaml; diff app.yaml work.yaml
8c8
<   replicas: 2
---
>   replicas: 4
45,46c45,46
<     This text is folded
<     into one line.
---
>     This text is folded into one line.
> 
```

REAL OUTPUT (host). Now all three documents remain and only the Deployment's replicas changed. The extra `diff` lines at the end show that `yq` re-wrapped the folded (`>`) block scalar in the ConfigMap. The meaning of the string is unchanged, but the text moved. Always `diff` after `yq -i` (or work on a copy) before you apply.

Other verified edits on a 3-document `app.yaml` (all with the parenthesised form):

```bash
# Image of the Deployment only
yq -i '(select(.kind == "Deployment") | .spec.template.spec.containers[0].image) = "nginx:1.27"' app.yaml
# Port of the Service only
yq -i '(select(.kind == "Service") | .spec.ports[0].port) = 8080' app.yaml
# A label on EVERY document (no select on purpose)
yq -i '.metadata.labels.env = "lab"' app.yaml
# Replace the whole env list of the container, then force the value to a quoted string
yq -i '(select(.kind == "Deployment") | .spec.template.spec.containers[0].env) = [{"name":"MODE","value":"on"}]' app.yaml
yq -i '(select(.kind == "Deployment") | .spec.template.spec.containers[0].env[0].value) style="double"' app.yaml
```

**Quoting with `yq`.** After the `env` assignment the file contains `value: on` (no quotes). The server then rejects it. Real error when the objects already exist (the usual case in the exam):

```text
$ k apply -f lab/app.yaml --dry-run=server
service/shop configured (server dry run)
configmap/shop-config configured (server dry run)
The request is invalid: patch: Invalid value: "map[metadata:map[annotations:map[kubectl.kubernetes.io/last-applied-configuration:{...\"env\":[{\"name\":\"MODE\",\"value\":true}]...}\n] labels:map[env:lab]] spec:map[replicas:4 template:map[spec:map[]]]]": unrecognized type: string
```

REAL OUTPUT (kind v0.33.0, v1.37.0), long middle part replaced with `...`. This message is hard to read, but one clue is visible: `"value":true`. `kubectl` turned your `on` into `true` before computing the patch. The `grep -n 'value:' file` shows `value: on`, and `style="double"` fixes it (`value: "on"`). When the object does not exist yet, the clean error appears instead (see section 6).

### 2.8 kubectl JSONPath

**JSONPath** is a small path language for JSON. `kubectl` has its own implementation, documented at <https://kubernetes.io/docs/reference/kubectl/jsonpath/>. You use it as `-o jsonpath='<template>'`. A template is plain text mixed with `{ expression }` parts.

| Element | Meaning | Verified example |
|---|---|---|
| `{.a.b}` | Field path from the root object | `{.status.podIP}` |
| `{.items[*].metadata.name}` | `[*]` means every list element; results are joined by spaces | all Pod names on one line |
| `{.items[0]}`, `{.items[-1:]}` | Index; a negative slice takes from the end | first / last Pod |
| `{..image}` | `..` means recursive descent (find the key at any depth) | see warning below |
| `{range .items[*]}...{end}` | Loop: repeat the text between `range` and `end` per element | one line per Pod |
| `[?(@.type=="Ready")]` | Filter: keep list elements where the test is true (`@` is the current element) | `{.status.conditions[?(@.type=="Ready")].status}` |
| `{"\n"}` and `{"\t"}` | A literal string; this is how you print a newline or tab | between fields |
| `\.` | Backslash escapes a dot inside a key name | `{.metadata.labels.kubernetes\.io/hostname}` |

**Quoting.** Put the whole template in single quotes in Bash so that the shell does not touch `{`, `$`, `"` or `\`. Inside the template, strings and filter values use double quotes. A template without spaces also works unquoted (`-o jsonpath={.items[0].metadata.name}`), but do not rely on that.

**Output has no trailing newline unless you print one.** `{.status.podIP}` prints the IP and then nothing. When you redirect to a file or use two commands in a row, end the template with `{"\n"}`.

Real runs:

```text
$ k get pod solo -o jsonpath='{.status.podIP}{"\n"}'
10.244.1.7
$ k get pod solo -o jsonpath='{.metadata.labels}{"\n"}'
{"tier":"backend"}
$ k get pod solo -o jsonpath='{.metadata.labels.tier}{"\n"}'
backend
$ k get pod solo -o jsonpath='{.status.conditions[*].type}{"\n"}'
PodReadyToStartContainers Initialized Ready ContainersReady PodScheduled
$ k get pod solo -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}{"\n"}'
True
$ k get pods -o jsonpath='{.items[*].metadata.name}{"\n"}'
solo stuck web-69c6f74b8b-59trs web-69c6f74b8b-cqnfp web-69c6f74b8b-dvq4n
$ k get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.nodeName}{"\t"}{.status.podIP}{"\n"}{end}'
solo	k-t113-worker	10.244.1.7
stuck		
web-69c6f74b8b-59trs	k-t113-worker	10.244.1.6
web-69c6f74b8b-cqnfp	k-t113-worker2	10.244.2.3
web-69c6f74b8b-dvq4n	k-t113-worker2	10.244.2.4
$ k get pods -o jsonpath='{.items[-1:].metadata.name}{"\n"}'
web-69c6f74b8b-dvq4n
$ k get pods -o jsonpath-as-json='{.items[*].metadata.name}'
[
    "solo",
    "stuck",
    "web-69c6f74b8b-59trs",
    "web-69c6f74b8b-cqnfp",
    "web-69c6f74b8b-dvq4n"
]
```

REAL OUTPUT (kind v0.33.0, v1.37.0). `jsonpath-as-json` prints the result as a JSON list, which is handy for seeing how many values matched. The `stuck` Pod has no node and no IP yet, so its two fields are empty; JSONPath prints nothing for missing fields.

**The node InternalIP command from the entry**, per node and as a bare list:

```text
$ k get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.addresses[?(@.type=="InternalIP")].address}{"\n"}{end}'
k-t113-control-plane	192.168.147.2
k-t113-worker	192.168.147.6
k-t113-worker2	192.168.147.5

$ k get nodes -o jsonpath='{range .items[*]}{.status.addresses[?(@.type=="InternalIP")].address}{"\n"}{end}' > ips.txt; cat ips.txt

192.168.147.6
192.168.147.5
```

REAL OUTPUT (kind v0.33.0, v1.37.0). A node has several entries in `.status.addresses` (`InternalIP`, `Hostname`, ...). The filter keeps only the `InternalIP` element. The `range` loop runs once per node and `{"\n"}` puts each IP on its own line.

**Escaping dots in keys.** Label and annotation keys often contain dots and slashes. Without the backslash, JSONPath reads the dot as a path separator and finds nothing:

```text
$ k get node k-t113-worker -o jsonpath='{.metadata.labels.kubernetes\.io/hostname}{"\n"}'
k-t113-worker
$ k get node k-t113-worker -o jsonpath='{.metadata.labels.kubernetes.io/hostname}{"\n"}'

$ k get deploy web -o jsonpath='{.metadata.annotations.deployment\.kubernetes\.io/revision}{"\n"}'
1
```

REAL OUTPUT (kind v0.33.0, v1.37.0). The middle command printed an empty line and exit code 0. No error.

**Missing keys print nothing, by default.** That is why a typo gives an empty result instead of an error. Turn the error on while debugging:

```text
$ k get pod solo -o jsonpath='{.status.podip}{"\n"}'

$ k get pod solo -o jsonpath='{.status.podip}' --allow-missing-template-keys=false
error: error executing jsonpath "{.status.podip}": Error executing template: podip is not found. Printing more information for debugging the template:
	template was:
		{.status.podip}
	object given to jsonpath engine was:
		map[string]interface {}{"apiVersion":"v1", "kind":"Pod", ... "status":map[string]interface {}{... "podIP":"10.244.1.7", ...}}
```

REAL OUTPUT (kind v0.33.0, v1.37.0), the dump of the object trimmed to `...` (the real one is a few thousand characters on one line). The object dump is useful: it shows the exact key spelling (`podIP`).

**`..` finds too much.** `{..image}` matches every key called `image` at any depth, including `status.containerStatuses[].image`:

```text
$ k get pods -o jsonpath='{..image}{"\n"}'
busybox:1.36 docker.io/library/busybox:1.36 nginx:1.27 nginx:1.27 docker.io/library/nginx:1.27 ...
```

REAL OUTPUT (kind v0.33.0, v1.37.0), trimmed. Each Pod contributes two values: the spec image and the longer resolved name from status. Use the explicit path `{.items[*].spec.containers[*].image}` when you need only the spec.

### 2.9 custom-columns and `--sort-by`

**`-o custom-columns`** builds your own table: `HEADER:path` pairs separated by commas. The path is a JSONPath **without** the curly braces. The path is applied to every object in the list. An empty or missing value prints `<none>`.

```text
$ k get pods -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName,IP:.status.podIP,PHASE:.status.phase,IMAGE:.spec.containers[0].image
NAME                   NODE             IP           PHASE     IMAGE
solo                   k-t113-worker    10.244.1.7   Running   busybox:1.36
stuck                  <none>           <none>       Pending   nginx:1.27
web-69c6f74b8b-59trs   k-t113-worker    10.244.1.6   Running   nginx:1.27
web-69c6f74b8b-cqnfp   k-t113-worker2   10.244.2.3   Running   nginx:1.27
web-69c6f74b8b-dvq4n   k-t113-worker2   10.244.2.4   Running   nginx:1.27
```

REAL OUTPUT (kind v0.33.0, v1.37.0). More forms, all verified:

| Need | Command |
|---|---|
| Hide the header row | `k get nodes --no-headers -o custom-columns=:.metadata.name` (an empty header before the colon is fine) |
| A filter inside a column | `-o custom-columns='NAME:.metadata.name,READY:.status.conditions[?(@.type=="Ready")].status'` |
| A key with dots | `-o custom-columns='NAME:.metadata.name,HOST:.metadata.labels.kubernetes\.io/hostname'` |
| Columns kept in a file | `-o custom-columns-file=cols.txt` where line 1 is the headers and line 2 the paths (see below) |

```text
$ k get pods -o custom-columns='NAME:.metadata.name,READY:.status.conditions[?(@.type=="Ready")].status'

solo                    True
stuck                   <none>
web-69c6f74b8b-59trs    True

stuck                  <none>           <none>
...
```

REAL OUTPUT (kind v0.33.0, v1.37.0), trimmed (the READY output was captured while two more Pods of the `shop` Deployment also existed).

**`--sort-by`** sorts the list by one JSONPath (no braces) before printing. It combines with every output format:

```text
$ k get pods --sort-by=.metadata.creationTimestamp
NAME                   READY   STATUS    RESTARTS   AGE
solo                   1/1     Running   0          34s
web-69c6f74b8b-59trs   1/1     Running   0          34s
web-69c6f74b8b-cqnfp   1/1     Running   0          34s
web-69c6f74b8b-dvq4n   1/1     Running   0          34s
stuck                  0/1     Pending   0          8s

$ k get pods --sort-by=.metadata.creationTimestamp -o name

pod/web-69c6f74b8b-59trs
pod/web-69c6f74b8b-cqnfp
pod/web-69c6f74b8b-dvq4n
```

REAL OUTPUT (kind v0.33.0, v1.37.0). Oldest first, newest last. `creationTimestamp` has a resolution of one second, so Pods created in the same second tie, and the order among ties is not something to rely on. For a list of names in creation order, use `-o name` or a `range` loop with `--sort-by`.

### 2.10 Field discovery with `kubectl explain`

`k explain` prints the API schema of the cluster you are connected to, so it always matches the server version. It needs no internet and is not a web page. In the exam it is the quickest way to check a field name, its spelling (`podIP` versus `podIp`), its type and its default.

| Command | What you learn |
|---|---|
| `k explain pod.spec.containers` | One level: description and the field list of a container |
| `k explain pod.spec.containers --recursive` | The full tree below that field, types and `-required-` markers, no descriptions |
| `k explain pod.status.podIP` | The exact spelling, type (`<string>`) and meaning of one field |
| `k explain deploy.spec.replicas` | Type `<integer>` and default (1) |
| `k explain pod.spec.terminationGracePeriodSeconds` | Type `<integer>`, default 30 |

```text
$ k explain pod.spec.containers --recursive | head -24
KIND:       Pod
VERSION:    v1

FIELD: containers <[]Container>


DESCRIPTION:
    List of containers belonging to the pod. Containers cannot currently be
    added or removed. There must be at least one container in a Pod. Cannot be
    updated.
    A single application container that you want to run within a pod.
    
FIELDS:
  args	<[]string>
  command	<[]string>
  env	<[]EnvVar>
    name	<string> -required-
    value	<string>
    valueFrom	<EnvVarSource>
      configMapKeyRef	<ConfigMapKeySelector>
        key	<string> -required-
        name	<string>
        optional	<boolean>
```

REAL OUTPUT (kind v0.33.0, v1.37.0), trimmed. How to read the types: `<[]Container>` is a list of `Container` maps; `<string>` is a scalar string (quote lookalikes); `<integer>` is a number (never quote); `<map[string]string>` is a map of strings (label values are strings); `-required-` means the API rejects the object without it. ### 2.11 Validating manifests: `--dry-run=client` and `--dry-run=server`

| Command | Where it runs | What it catches | What it misses |
|---|---|---|---|
| `k create ... --dry-run=client -o yaml` | Client only | Nothing is validated against the cluster. It builds the object from your flags and prints it. This is the generator you save into a file | Everything about the cluster |
| `k apply -f f.yaml --dry-run=client` | Client | YAML syntax | In my runs: misspelled field names and a missing namespace were NOT caught (see below) |
| `k apply -f f.yaml --dry-run=server` | The API server runs the whole request (decode, strict field check, defaulting, admission) and then stores nothing | Type errors, unknown fields, missing namespace, invalid values | Whether Pods will actually start |

Two real differences, same file:

```text

$ k apply -f app.yaml -n nosuchns --dry-run=client

$ k apply -f app.yaml -n nosuchns --dry-run=server

Error from server (NotFound): error when creating "app.yaml": namespaces "nosuchns" not found
Error from server (NotFound): error when creating "app.yaml": namespaces "nosuchns" not found
```

REAL OUTPUT (kind v0.33.0, v1.37.0). The client dry-run said "created" for both bad cases. A typo like `replica` would silently disappear and the Deployment would run with the default of one replica. Use `--dry-run=server` as your final check before and after every `yq -i`.

### 2.12 Common field paths

| Path | Object | Type | Notes |
|---|---|---|---|
| `.metadata.name`, `.metadata.namespace` | any | string | Name and namespace |
| `.metadata.labels` | any | map of strings | Keys may contain dots and slashes: escape with `\.` |
| `.metadata.creationTimestamp` | any | string (time) | Used by `--sort-by` |
| `.metadata.annotations` | any | map of strings | Same escaping rule |
| `.spec.nodeName` | Pod | string | Empty until the scheduler picks a node |
| `.spec.containers[*].image` | Pod | string | `[0]` for the first container |
| `.status.podIP` | Pod | string | Capital `IP`. Empty while the Pod is Pending |
| `.status.hostIP` | Pod | string | Node IP where the Pod runs |
| `.status.phase` | Pod | string | `Pending`, `Running`, `Succeeded`, `Failed` |
| `.status.conditions` | Pod, Node, Deployment | list of `{type, status, ...}` | Filter by `type` with `[?(@.type=="Ready")]` |
| `.status.addresses` | Node | list of `{type, address}` | `InternalIP`, `Hostname` |
| `.status.nodeInfo.kubeletVersion` | Node | string | Verified: `v1.37.0` |
| `.spec.replicas` | Deployment | integer | Desired count |
| `.status.readyReplicas` | Deployment | integer | Left out of the object when it is zero (not captured, see section 11), so the key may be missing; `jq` prints `null`, JSONPath prints nothing |

Why conditions are a list and not a map: each condition has several fields (`type`, `status`, `reason`, `message`, `lastTransitionTime`), and the order in the list is not guaranteed, so you filter by `type` rather than by position.

```text
$ k get pod stuck -o jsonpath='{.status.conditions[?(@.type=="PodScheduled")].reason}{"\n"}'
Unschedulable
$ k get pod stuck -o jsonpath='{.status.conditions[?(@.type=="PodScheduled")].message}{"\n"}'
0/3 nodes are available: 1 node(s) had untolerated taint(s), 2 node(s) didn't match Pod's node affinity/selector. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.
```

REAL OUTPUT (kind v0.33.0, v1.37.0). This is the fastest way to see why a Pod is `Pending` without reading `describe`.

### 2.13 Under the hood and related-but-different

**Under the hood.** The API server stores each object as one document made of `metadata`, `spec` (what you want) and `status` (what is true now). Controllers and the kubelet write `status`, you write `spec`. Fields at their zero value are often left out of the response (an unset `nodeName`, `readyReplicas: 0`). That is why the same path can print a value for one Pod and nothing for another, and why the three tools show a missing value differently:

```text
$ k get pod stuck -o json | jq '.status.podIP, .spec.nodeName'
null
null
$ k get pod stuck -o jsonpath='[{.status.podIP}] [{.spec.nodeName}]{"\n"}'
[] []
$ k get pod stuck -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName,IP:.status.podIP
NAME    NODE     IP
stuck   <none>   <none>
```

REAL OUTPUT (kind v0.33.0, v1.37.0). `jq` prints `null`, JSONPath prints empty text and `custom-columns` prints `<none>`. If a task needs "identical" results from different tools, restrict the objects (`--field-selector=status.phase=Running`) or give `jq` a default with `//`.

**Related but different.**

- `-l key=value` (label selector) and `--field-selector=status.phase=Running` filter on the **server** before output. `jq select` and JSONPath `[?()]` filter on the **client** after the full list arrives. Server-side filters are shorter to type but only work for a small list of fields (`status.phase`, `metadata.name`, `spec.nodeName`, ...).
- `kubectl patch --type=json` uses JSON Patch paths such as `/spec/replicas`. That is not JSONPath, and the syntax is different.
- `jq` filters and `kubectl` JSONPath look alike but are different languages. In `jq`, you write `.items[].metadata.name`; in JSONPath, `{.items[*].metadata.name}`.
- `yq` and `jq` do not share files: `yq` works on YAML and keeps it as YAML; `jq` needs JSON (`k get ... -o json` or `yq -o json`).

## 3. How it works (diagram)

The same Pod (trimmed to the fields we use) in YAML and in JSON, with the `kubectl` JSONPath template that selects each field. The jq equivalent is the same path with dots only (`.status.conditions[] | select(.type=="Ready") | .status`).

```text
YAML (what you write)       JSON (what kubectl sends)               JSONPath (kubectl -o jsonpath)
------------------------------------------------------------------------------------------------------------------
                            {
apiVersion: v1                "apiVersion": "v1",                   {.apiVersion}
kind: Pod                     "kind": "Pod",                        {.kind}
metadata:                     "metadata": {                         {.metadata}
  name: solo                    "name": "solo",                     {.metadata.name}
  labels:                       "labels": {                         {.metadata.labels}
    tier: backend                 "tier": "backend"                 {.metadata.labels.tier}
                                }
                              },
spec:                         "spec": {                             {.spec}
  nodeName: k-t113-worker       "nodeName": "k-t113-worker",        {.spec.nodeName}
  containers:                   "containers": [                     {.spec.containers[*]}
                                  {                                 {.spec.containers[0]}
  - name: solo                      "name": "solo",                 {.spec.containers[0].name}
    image: busybox:1.36             "image": "busybox:1.36"         {.spec.containers[0].image}
                                  }
                                ]
                              },
status:                       "status": {                           {.status}
  podIP: 10.244.1.7             "podIP": "10.244.1.7",              {.status.podIP}
  conditions:                   "conditions": [                     {.status.conditions[*]}
                                  {
  - type: Ready                     "type": "Ready",                {.status.conditions[?(@.type=="Ready")]}
    status: "True"                  "status": "True"                {.status.conditions[?(@.type=="Ready")].status}
                                  }
                                ]
                              }
                            }
```

Walkthrough:

1. Each YAML key is a JSON key and each YAML indent level is a JSON `{ }`. A YAML `- ` line is one element of a JSON `[ ]`.
2. A JSONPath is the list of keys from the top to the value, each key written with a dot: `.metadata.labels.tier`.
3. A list is entered with `[*]` (all elements), `[0]` (one by position) or `[?(@.type=="Ready")]` (the elements that pass a test). Use the filter for `conditions` and `addresses`, because their order is not fixed.
4. Look at `status: "True"`: it is quoted because `True` unquoted would be a boolean. Kubernetes uses the strings `"True"`, `"False"`, `"Unknown"` for condition status.
5. If a path matches nothing, JSONPath prints an empty string and `jq` prints `null`. Neither is an error.

## 4. Commands and YAML you must produce fast

### 4.1 Imperative shortcuts

```bash
# Generate a manifest, never type one from scratch
k create deploy web --image=nginx:1.27 --replicas=3 $do > web.yaml
# Generator + yq: change one field without opening an editor
k create deploy x --image=nginx:1.27 $do | yq '.spec.replicas = 3' > x.yaml
# Edit a field of a saved manifest in place (the entry's example)
yq -i '.spec.template.spec.containers[0].image="nginx:1.27"' d.yaml
# Write all node InternalIPs, one per line, to a file (exam-style path /opt/ips.txt; use any path you can write)
k get nodes -o jsonpath='{range .items[*]}{.status.addresses[?(@.type=="InternalIP")].address}{"\n"}{end}' > /opt/ips.txt
# Node name + InternalIP on one line each (the entry's key command)
k get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.addresses[?(@.type=="InternalIP")].address}{"\n"}{end}'
# Names of Pods that are not Running (jq, lab tool)
k get pods -o json | jq -r '.items[]|select(.status.phase!="Running")|.metadata.name'
# Same without jq (works on the exam hosts)
k get pods --field-selector=status.phase!=Running -o name
# Pods in creation order
k get pods --sort-by=.metadata.creationTimestamp
# Validate before applying
k apply -f app.yaml --dry-run=server
```

| Command | What it does | Check |
|---|---|---|
| `k create deploy ... $do > f.yaml` | Builds the YAML on the client, nothing is created | `yq . f.yaml` parses without error |
| `yq -i 'EXPR' f.yaml` | Edits the file in place | `diff f.bak f.yaml`, then `--dry-run=server` |
| `... > /opt/ips.txt` | Redirect writes (or replaces) the file | `cat /opt/ips.txt`; one IP per line, no empty last line |
| `--field-selector=status.phase!=Running -o name` | Server-side filter, prints `pod/<name>` | Output starts with `pod/` |

Real output of the yq edit, with a generated Deployment:

```text
$ k create deploy d --image=nginx:1.26 --replicas=2 $do > d.yaml
$ yq -i '.spec.template.spec.containers[0].image="nginx:1.27"' d.yaml
$ yq '.spec.template.spec.containers[0].image' d.yaml
nginx:1.27
```

REAL OUTPUT (host). `yq` re-indented the list under `containers:` by two spaces, which is still valid YAML.

### 4.2 The declarative YAML: a three-document file

This is the manifest used in the worked example and in the Medium lab. It applies cleanly with `k apply -f app.yaml` (a namespace is set by the context or by `-n`).

```yaml
# app.yaml: three documents separated by "---"
apiVersion: apps/v1          # API group/version for Deployments. A wrong value is rejected by the server
kind: Deployment             # Object type. Case matters
metadata:
  name: shop                 # Required. DNS-1123 name: lowercase letters, digits, "-" and "."
  labels:
    app: shop                # Labels on the Deployment object itself (values are strings: quote lookalikes such as "1.20")
spec:
  replicas: 2                # INTEGER. Default 1. "2" (quoted) is rejected; negative values are invalid
  selector:
    matchLabels:
      app: shop              # Must match template.metadata.labels. Immutable after creation
  template:
    metadata:
      labels:
        app: shop            # Labels the Pods get; the selector above finds them by this
    spec:
      containers:
        - name: nginx        # Required, unique in the Pod
          image: nginx:1.26  # Required. Always a pinned tag, never :latest
          ports:
            - containerPort: 80   # INTEGER 1-65535. Informational; does not open or close anything
---
apiVersion: v1
kind: Service
metadata:
  name: shop
  labels:
    app: shop
spec:
  selector:
    app: shop                # Pods with this label receive the traffic. A typo gives a Service with no endpoints
  ports:
    - port: 80               # Port the Service listens on (integer)
      targetPort: 80         # Container port to forward to. Defaults to "port" when omitted
  # type is not set: default is ClusterIP (reachable only inside the cluster)
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: shop-config
data:                        # All values are STRINGS. A bare yes/on/123 here is rejected
  motd: |                    # literal block: newlines are kept, one final newline
    Welcome.
    Second line.
  summary: >                 # folded block: single newlines become spaces
    This text is folded
    into one line.
```

Check it before use: `yq -N '.kind' app.yaml` prints `Deployment`, `Service`, `ConfigMap`, and `k apply -f app.yaml --dry-run=server` prints three `(server dry run)` lines.

## 6. Common mistakes and how to fix them

| Symptom | What you will see (exact text) | Cause | Fix |
|---|---|---|---|
| Indentation broken | `error: error parsing bad3.yaml: error converting YAML to JSON: yaml: line 6: did not find expected key` (variants: `did not find expected '-' indicator`, `mapping values are not allowed in this context`) | A line is indented by a different number of spaces than its siblings | `yq . file` to get line and column; fix the spaces; re-run `k apply --dry-run=server` |
| Tab in indentation | `yaml: line 6: found character that cannot start any token` | A tab character | Replace each tab with spaces in your editor; configure the editor to insert spaces when you press Tab |
| Env value `true` rejected | `Error from server (BadRequest): error when creating "bf.yaml": Deployment in version "v1" cannot be handled as a Deployment: json: cannot unmarshal bool into Go struct field EnvVar.spec.template.spec.containers.env.value of type string` | `value: true` (or `yes`, `on`) is a boolean; `value` is a string | Quote it: `value: "true"` |
| Number where a string is needed | `unable to decode "bf.yaml": json: cannot unmarshal number into Go struct field ObjectMeta.metadata.labels of type string` and `... into Go struct field ConfigMap.data of type string` | `version: 1.20` (label), `release: 1.10` and `mode: 0644` (data) are numbers | Quote them: `"1.20"`, `"1.10"`, `"0644"` |
| String where an integer is needed | `... json: cannot unmarshal string into Go struct field DeploymentSpec.spec.replicas of type int32` and `... into Go struct field ContainerPort.spec.template.spec.containers.ports.containerPort of type int32` | `replicas: "2"`, `containerPort: "80"` | Remove the quotes |
| Same error on an existing object is unreadable | `The request is invalid: patch: Invalid value: "map[...]": unrecognized type: string` | The wrong type is in an object that already exists; `kubectl` builds a patch first | `grep -n` the changed lines, look for `"value":true` or similar inside the message, quote the value |
| JSONPath prints nothing | an empty line, exit code 0 | Wrong case (`.status.podip` for `.status.podIP`), wrong level, or an unescaped dot in a key | See the ladder below |
| `jq` prints `null` | `null` | A List used as one object: `.metadata.name` on `k get pods -o json` reads the List's own metadata | Use `.items[].metadata.name` |
| `jq` index error | `jq: error (at <stdin>:926): Cannot index array with string ("metadata")` | `.items.metadata.name` without `[]`: `.items` is an array | `.items[].metadata.name` |
| `jq` iterate error | `jq: error (at <stdin>:195): Cannot iterate over null (null)` | `.items[]` on a single object (`k get pod solo -o json`) | Drop `.items[]` for a single object |
| `yq -i` deleted documents | The file now holds one document | `yq -i 'select(...) \| ... = x'` outputs only the selected document | `yq -i '(select(...) \| .path) = x' f.yaml`; restore from your copy |
| `yq` wrote `value: on` | `grep` shows an unquoted `on`; apply fails as above | `yq` follows YAML 1.2 and sees a string; `kubectl` reads YAML 1.1 | `... style="double"` on that node |
| `defaultMode: 644` rejected | `spec.volumes[0].configMap.defaultMode: Invalid value: 644: must be a number between 0 and 0777 (octal), both inclusive` | 644 is a decimal number | Write `0644` (stored as 420) |
| Typo field accepted by `--dry-run=client` | client prints `created (dry run)`; server prints `strict decoding error: unknown field "spec.replica"` | Client dry-run does not check field names against the schema | Always use `--dry-run=server` |
| Output glued together | `solo stuck web-...` on one line; last line of a file has no newline | `[*]` joins with spaces; JSONPath adds no newline | Use `{range ...}{...}{"\n"}{end}` |
| `{..image}` shows extra names | `busybox:1.36 docker.io/library/busybox:1.36 ...` | `..` also matches `status.containerStatuses[].image` | Use `{.items[*].spec.containers[*].image}` |


REAL OUTPUT (host). `kubectl` says `line 6`, the last good line of the map, while `yq` gives the range `L4.C3-L7.C4`, which starts at the `metadata` map and ends at the bad line 7. Look at the reported line and the line below it. Other shifts give the sibling messages in the table, both reproduced with a Pod whose container is `- name: app` followed by `image:` and `ports:` keys: a key one column too far to the left of `name:` gives `did not find expected '-' indicator`, and a key one column too far to the right gives `mapping values are not allowed in this context`.

**Troubleshooting ladder for "JSONPath prints nothing"** (run in this order):

1. Print the object and look at the real keys: `k get pod solo -o json | head -60` (or `-o yaml`). Compare your path letter by letter. Case matters: `podIP`, not `podIp` and not `podip`.
2. Count the levels. A list command (`k get pods`) returns `.items[*]...`; a named object (`k get pod solo`) returns the fields at the top. Mixing them gives nothing.
3. Check for dots in keys (`kubernetes.io/hostname`, `deployment.kubernetes.io/revision`) and escape each dot with `\.`.
4. Re-run with `--allow-missing-template-keys=false`. The error names the key that was not found and dumps the object.
5. Ask the schema: `k explain pod.status.podIP` prints the exact spelling and type.
6. If the value should exist but does not, the field may be empty on purpose (for example, a Pod that is still Pending has no `podIP`). Check `.status.phase` first.

**Reading an apply error** (the same path for every type error):

1. Read the type name at the end: `of type string` means a string field got a non-string; `of type int32` means an integer field got a string.
2. Read the Go field path: `EnvVar...value` is an env var; `ConfigMap.data` is a ConfigMap entry; `ObjectMeta.metadata.labels` is a label.
3. List candidates in the file: `grep -nEi ':[[:space:]]+(y|n|yes|no|on|off|true|false|[0-9][0-9._]*)[[:space:]]*$' file.yaml` finds unquoted bool/number-like values. Check integer fields separately: `grep -nE '(replicas|containerPort|port|targetPort|nodePort): "' file.yaml`.
4. Fix, then validate everything again with `k apply -f file.yaml --dry-run=server`. The server reports the first error per object, so after each fix a different error may show up. Repeat until it passes.

**Setup**

```bash

k wait --for=condition=Available deploy/web --timeout=120s
```

**Task**

In namespace `lab-t113`, for every Pod whose phase is `Running`, produce one line with these five values separated by single spaces, in this order: Pod name, node name, Pod IP, phase, image of the first container.

Create the same content three times, once per tool:

- `~/lab/t113/jp.txt` with `kubectl -o jsonpath`
- `~/lab/t113/jq.txt` with `jq`
- `~/lab/t113/cc.txt` with `kubectl -o custom-columns` (no header line)

The Pod that is not Running must not appear. The three files must hold the same answers (column spacing in `cc.txt` may be wider).

<details>
<summary>Hint 1</summary>

`--field-selector=status.phase=Running` removes the Pending Pod on the server, before any tool sees it.
</details>

<details>
<summary>Hint 2</summary>

For JSONPath you need `{range .items[*]}` ... `{end}` and `{"\n"}` after the last field. For `jq`, build a list of five values and `join(" ")` it, with `-r`.
</details>

<details>
<summary>Hint 3</summary>

`custom-columns` takes `HEADER:path` pairs and does not use braces. `--no-headers` hides the header row.
</details>

<details>
<summary>Solution</summary>

```bash
cd ~/lab/t113
# JSONPath: range loops over the list; one line per Pod; {"\n"} ends each line
k get pods --field-selector=status.phase=Running \
  -o jsonpath='{range .items[*]}{.metadata.name} {.spec.nodeName} {.status.podIP} {.status.phase} {.spec.containers[0].image}{"\n"}{end}' > jp.txt
# jq: build a 5-element array per Pod and join it; -r removes the quotes
k get pods --field-selector=status.phase=Running -o json \
  | jq -r '.items[] | [.metadata.name,.spec.nodeName,.status.podIP,.status.phase,.spec.containers[0].image] | join(" ")' > jq.txt
# custom-columns: five NAME:path pairs, no header
k get pods --field-selector=status.phase=Running --no-headers \
  -o custom-columns=N:.metadata.name,NODE:.spec.nodeName,IP:.status.podIP,PH:.status.phase,IMG:.spec.containers[0].image > cc.txt
cat jp.txt jq.txt cc.txt
```

Why each step: the field selector keeps the Pending Pod out, so no tool has to print a missing node or IP (JSONPath would print nothing, `jq` would print `null`, custom-columns would print `<none>`). The redirect `>` writes each result to its file. `{"\n"}` is needed in JSONPath because it adds no newline by itself. `join(" ")` makes `jq` use the same single-space separator as the JSONPath template. Custom-columns pads columns, which is why the check below squeezes spaces.

```text
...
```

REAL OUTPUT (kind v0.33.0, v1.37.0), trimmed.
</details>

**Verification** (each command can fail; `PASS` prints only if everything holds)


<details>
<summary>Answers</summary>

1. `k get nodes -o jsonpath='{range .items[*]}{.status.addresses[?(@.type=="InternalIP")].address}{"\n"}{end}' > file`. The filter picks the `InternalIP` entry from the `addresses` list; the `range` and `{"\n"}` give one line per node.

3. (a) Compare the spelling with the real object: the key is `podIP`. (b) Re-run with `--allow-missing-template-keys=false` to get an error that names the missing key. (c) `k explain pod.status.podIP` to confirm path and type. Also check whether the Pod is still Pending (no IP yet).
4. In YAML, `true` is a boolean, but `EnvVar.value` is a string. The server answers `cannot unmarshal bool into Go struct field EnvVar...value of type string`. Quote it: `value: "true"`.
5. Client dry-run only builds and prints the object locally; server dry-run sends the request through decoding, strict field checks, defaulting and admission, and stores nothing. Server dry-run catches the typo with `strict decoding error: unknown field "spec.replica"`. Client dry-run prints `created (dry run)`.
6. `k get deploy NAME -o jsonpath='{.metadata.annotations.deployment\.kubernetes\.io/revision}{"\n"}'`. Each dot inside the key is escaped.
7. `k get pods -o json` returns a List; `.metadata` is the List's own metadata and has no `name`. Use `.items[].metadata.name`.
8. A schema view of every field below `containers` with its type and `-required-` markers, from the live API. `describe` shows the state of one object, not the schema.
9. `yq` follows YAML 1.2, where `yes` is a plain string. `kubectl` reads YAML 1.1, where `yes/no/on/off/y/n` are booleans. The server therefore receives `true`. Judge with `kubectl apply --dry-run=server`, not with `yq`.
10. `|` keeps newlines (literal); `>` folds single newlines into spaces (a blank line becomes one newline). `|-` and `>-` also strip the final newline.

</details>
