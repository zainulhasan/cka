## 1. Why this matters

Kubernetes promises that every Pod can reach every other Pod by its IP address, on any node, with no address translation. The CNI plugin makes that promise true. When it breaks, you see Pods that work alone but cannot talk to each other, Services that time out for only some clients, or a web page that loads but a large download stalls.

If you do not know the packet path, you guess. If you know it (Pod, veth, node routing table, tunnel or route, other node, other veth, other Pod), you test one hop at a time and find the break in minutes. This competency sits in the CKA domain "Servicing and Networking" (20% of the curriculum). It is the base that Services, DNS, NetworkPolicy and Ingress all stand on. What exact tasks the exam asks for is UNVERIFIED; prepare to read and repair the path, not to memorize a recipe.

## 2. Concepts

### 2.1 The Kubernetes network model

**What it is.** A short set of rules that every cluster network must satisfy. The rules are in the official page "Cluster Networking" ([link](https://kubernetes.io/docs/concepts/cluster-administration/networking/)). In plain words:

1. **Every Pod gets its own unique IP address.** All containers in one Pod share that IP and its network namespace (they talk over `localhost`).
2. **A Pod can reach every other Pod using that IP, on any node, without NAT.** NAT (network address translation) means a router rewrites the source or destination address. "Without NAT" means the Pod that receives the packet sees the real IP of the Pod that sent it.
3. **Agents on a node (kubelet, system daemons) can reach all Pods on that node.** This is "nodes to Pods". The kubelet needs it for health probes.
4. **Pods on the host network** (`hostNetwork: true`, section 2.7) use the node's IP and can still reach all Pods on all nodes.

**The problem it solves.** On plain Docker, a container sits behind a private bridge and is NATed out. To let two containers on different hosts talk you had to map ports on the host and remember which host port belonged to which app. Kubernetes removes that: a Pod IP is the real address of the Pod, so an app can be configured with `10.x.y.z:5432` and it just works, and port numbers mean the same thing everywhere.

**What breaks without it.** Kubernetes itself does not build this network. It only defines the rule and calls a plugin (the CNI plugin, see [T4.03](../part4-cka/T4.03-understand-extension-interfaces-cni-csi-cri.md)). With no CNI the Node is `NotReady`. With a broken CNI on one node, Pods on that node get an IP but are cut off from the rest.

**What the model does NOT promise.** It does not promise that traffic is *allowed*: a NetworkPolicy can still drop it (section 2.8). It does not promise Service IPs: those are virtual and are handled by kube-proxy (section 2.12).

### 2.2 The packet path: same node and across nodes

Every Pod lives in its own **network namespace** (a private copy of interfaces, routes and firewall state, see [T1.07](../part1-linux/T1.07-linux-networking-i-interfaces-ips-routes.md)). The CNI plugin connects that namespace to the node with a **veth pair**: two virtual interfaces joined like a cable. One end is `eth0` inside the Pod. The other end stays in the node's namespace (Calico names it `cali<hash>`).

**Same node.** There are two designs:

| Design | How the node forwards between two local Pods | Used by |
|---|---|---|
| Bridge | All host-side veth ends are plugged into one Linux bridge (for example `cni0`). The bridge switches frames at layer 2. | The reference `bridge` plugin, Flannel, kindnet |
| Routed (no bridge) | Each host-side veth has its own `/32` route in the node routing table. The node routes at layer 3. | Calico, Cilium (in its own way) |

Under Calico the Pod's default route is `default via 169.254.1.1 dev eth0`. That address does not exist anywhere. The host-side veth has **proxy ARP** turned on, so it answers the Pod's ARP question "who has 169.254.1.1?" with its own MAC address, and from then on the Pod sends every packet to the node. The node looks up the destination in its routing table (`192.168.140.6 dev cali... scope link`) and hands the packet to the right veth. This is why the same-node path needs no bridge.

**Different nodes.** The packet must cross the node network. Two families of design:

| Model | How it works | What the physical network sees | Needs from the network | Examples |
|---|---|---|---|---|
| **Overlay: IPIP** | The whole Pod packet is wrapped in a new IP packet from node to node (IP protocol number 4). | Node IP to node IP, protocol 4. Pod IPs are hidden inside. | The network must pass **IP protocol 4** (it is not TCP or UDP, so port-based firewall rules miss it). | Calico IPIP |
| **Overlay: VXLAN** | The Pod's Ethernet frame is wrapped in a UDP packet, port 4789, with a 24-bit VXLAN network ID (VNI). | UDP from node to node. | **UDP 4789** open between nodes. | Calico VXLAN, Flannel (default backend), Cilium |
| **Routed (underlay, BGP)** | No wrapping. Each node announces "I own block 192.168.198.64/26, send it to me" and the others add that as a route. | Pod IPs appear on the node network, routed to the owning node. | Nodes on the same L2 network, or routers that learn the routes. BGP uses **TCP 179**. | Calico with `Never` encapsulation; cloud VPC route tables |
| **Hybrid: CrossSubnet** | Send plain (routed) when the other node is in the same subnet; wrap only when the path crosses a router. | Mixed. | Both of the above, depending on node placement. | Calico `CrossSubnet` modes |

Why overlays exist: the node network does not know the Pod CIDR, so it would drop packets whose source or destination is a Pod IP (or never route them). Wrapping hides the Pod IPs. The price is 20 to 50 bytes of overhead per packet, which lowers the usable MTU (section 2.9), and a little CPU.

### 2.3 Pod CIDR allocation

Pod IPs come from a range. Three components are involved and they are easy to confuse.

| Layer | Setting | Who reads it | Effect |
|---|---|---|---|
| kubeadm | `--pod-network-cidr=192.168.0.0/16`, or `networking.podSubnet` in the config file | kubeadm | Passes the value to kube-controller-manager as `--cluster-cidr`, and to kube-proxy as `clusterCIDR`. |
| kube-controller-manager | `--cluster-cidr`, `--allocate-node-cidrs=true`, `--node-cidr-mask-size` (default 24 for IPv4, 64 for IPv6) | The node IPAM controller | Cuts one slice per node and writes it to **`node.spec.podCIDR`** (single) and **`node.spec.podCIDRs`** (list, used for dual-stack). |
| CNI IPAM | Plugin-specific. `calico-ipam` uses the **IPPool** objects. `host-local` uses a range from its config or from `podCIDR`. | The CNI plugin, when a Pod starts | Chooses the actual Pod IP. |

**The key fact for Calico.** Calico's IPAM does **not** use `node.spec.podCIDR` by default. It has its own scheme: the IPPool (a cluster CIDR) is cut into small **blocks** (default `/26`, 64 addresses), and a node claims a block when it first needs addresses ("block affinity"). So on a kubeadm + Calico cluster:

- `k get nodes -o jsonpath='{.items[*].spec.podCIDR}'` still prints one `/24` per node (kubeadm turned on `--allocate-node-cidrs`).
- The Pods on that node usually have IPs from a *different* range: the node's Calico `/26` block.
- Both ranges sit inside the pool `192.168.0.0/16`, but the Pod IP is **not** required to be inside that node's `podCIDR`.

Do not treat a Pod IP outside `podCIDR` as a bug on Calico. It is only a bug on CNIs that read `podCIDR` (Flannel, kindnet, the `bridge` plugin with `host-local`). On those, a node without `podCIDR` stays `NotReady` or its Pods fail to start. (Calico can also be configured to use `host-local` with `usePodCidr: true`; that is not the default in the manifest.)

To see the three layers, run on `cp1`:

```bash
k get nodes -o custom-columns=NODE:.metadata.name,PODCIDR:.spec.podCIDR,PODCIDRS:.spec.podCIDRs
grep -E 'cluster-cidr|allocate-node-cidrs|service-cluster-ip-range|node-cidr-mask' /etc/kubernetes/manifests/kube-controller-manager.yaml
k -n kube-system get cm kube-proxy -o yaml | grep clusterCIDR
k get ippools.crd.projectcalico.org default-ipv4-ippool -o jsonpath='{.spec.cidr} {.spec.blockSize}{"\n"}'
```

### 2.4 Service CIDR vs Pod CIDR vs node network

There are three address spaces in a cluster. They must not overlap.

| Space | Example | What lives in it | Is it routable on the wire? |
|---|---|---|---|
| Node network | `10.10.0.0/24` | Node IPs (the API server address, kubelet) | Yes, it is the real network |
| Pod CIDR | `192.168.0.0/16` | Pod IPs | Inside the cluster. Real on the wire with routed designs; hidden inside the tunnel with overlays |
| Service CIDR | `10.96.0.0/12` | ClusterIP addresses | **No.** No interface owns these. kube-proxy rewrites them to a Pod IP inside the node, before the packet leaves |

**Why overlap is a problem.** If two spaces share addresses, a routing table cannot tell which one a packet means. Concretely: a Pod IP that equals a node or LAN host IP makes that host unreachable from the Pod (the packet is delivered to the Pod instead, or goes to the wrong place). A Service CIDR that includes the node network, or the API server address, makes the API server unreachable from Pods (a classic: Multipass or home networks that use `192.168.x.x` collide with a Pod CIDR of `192.168.0.0/16`, and `10.96.0.0/12` covers `10.96.0.0` to `10.111.255.255`, which some VM networks use).

**Rule.** Pick the Pod CIDR and Service CIDR before `kubeadm init`, check them against `ip -4 addr` and `ip route` on every node, and against any LAN the Pods must reach (a database, a VPN). You cannot change them later without a rebuild or a careful migration (the Calico pool `cidr` is immutable: the CRD rejects a change with "CIDR cannot be changed; follow IP pool migration guide to avoid corruption"). See failure 2 in section 6.

### 2.5 Calico specifics for the labs

**What Calico is.** A CNI plugin plus a network-policy engine. Its parts, as they appear in the v3.33.0 `calico.yaml`:

| Part | Kind / name | Role |
|---|---|---|
| `calico-node` | DaemonSet, `kube-system`, label `k8s-app=calico-node` | One Pod per node, host network, privileged. Runs **Felix** (programs routes, firewall rules and tunnel devices) and **BIRD** (BGP daemon, announces and learns routes). Also creates the default IPPool on first start. |
| CNI plugin + IPAM | Binaries `calico` and `calico-ipam` copied to `/opt/cni/bin`, config `/etc/cni/net.d/10-calico.conflist` | Called by containerd for each new Pod: create the veth, pick an IP from the node's block. |
| `calico-kube-controllers` | Deployment, `kube-system` | Cleans up Calico data when Nodes or Pods disappear. |
| IPPool | CRD `ippools.crd.projectcalico.org` (kind `IPPool`, cluster scoped) | The cluster CIDR plus its encapsulation settings. |
| IPAM data | CRDs `ipamblocks`, `blockaffinities`, `ipamhandles` (same group) | Which node owns which block, and which IP is used. |
| `calico-config` | ConfigMap, `kube-system` | `calico_backend: "bird"`, `typha_service_name: "none"`, `veth_mtu: "0"` (0 = auto-detect). |

**Namespace depends on the install method.** The plain manifest puts everything in `kube-system`: `k -n kube-system get pods -l k8s-app=calico-node`. The **operator** install (`tigera-operator.yaml` + `custom-resources.yaml`) puts the Pods in `calico-system`: `k -n calico-system get pods`. The lab here uses the plain manifest. If a cluster you meet uses the other method, use the other namespace. Find out with `k get pods -A | grep calico`.

**The IPPool and encapsulation mode.** The fields that matter (all from the CRD in `calico.yaml` v3.33.0):

| Field | Meaning | Values | Default in the CRD | Risky value |
|---|---|---|---|---|
| `spec.cidr` | The pool range | a CIDR | required, **immutable** | one that overlaps the node network |
| `spec.blockSize` | Size of the per-node block | `20` to `32` for IPv4 | 26 | immutable |
| `spec.ipipMode` | IP-in-IP tunnelling | `Never`, `Always`, `CrossSubnet` | `Never` | `Always` with a network that drops protocol 4 |
| `spec.vxlanMode` | VXLAN tunnelling | `Never`, `Always`, `CrossSubnet` | `Never` | `Always` with UDP 4789 blocked |
| `spec.natOutgoing` | Masquerade traffic that leaves the pool | bool | false in CRD, `true` in the default pool | off when Pods must reach the internet |
| `spec.nodeSelector` | Which nodes may use this pool | Calico selector | `all()` | one that matches no node |

`ipipMode` and `vxlanMode` **cannot both be enabled** on one pool: the CRD has a validation rule "ipipMode and vxlanMode cannot both be enabled". To switch from IPIP to VXLAN you set both in one patch (done in Lab B).

**What v3.33.0 gives you by default.** I read these from the manifests:

| Install method | Default pool | Result |
|---|---|---|
| Plain `calico.yaml` | `calico-node` env `CALICO_IPV4POOL_IPIP=Always`, `CALICO_IPV4POOL_VXLAN=Never`; `CALICO_IPV4POOL_CIDR` is commented out (the pool CIDR then defaults to `192.168.0.0/16`) | **IPIP, always**, even between nodes in the same subnet. Tunnel device `tunl0`. BGP (BIRD) distributes the routes. |
| Operator `custom-resources.yaml` | `cidr: 192.168.0.0/16`, `blockSize: 26`, `encapsulation: VXLANCrossSubnet`, `natOutgoing: Enabled` | **VXLAN only between different subnets**; nodes in the same subnet talk unencapsulated. |

### 2.6 Testing connectivity

Test from the outside in. Do not guess.

1. **Which Pods are on which node, and what IPs do they have?** `k get pods -o wide`. Add `-A` for all namespaces.
2. **Same node first, then cross node.** Same-node success with cross-node failure points at the inter-node path (tunnel, route, firewall, `calico-node`). Both failing points at the Pod itself, a NetworkPolicy, or the node's local CNI.
3. **Use two protocols.** `ping` tests ICMP. `wget -qO- -T 3 http://<ip>` tests TCP and a real application. NetworkPolicy and MTU problems can break one and not the other.
4. **Look at the node.** `ip route` on each node shows how it reaches each other node's block.

Pin two Pods on different nodes with `nodeName` (the exact YAML is in section 4) and run:

```bash
k -n lab-t417 get pods -o wide
k -n lab-t417 exec a -- ping -c2 192.168.198.67            # Pod on w1 -> Pod on w2
k -n lab-t417 exec a -- wget -qO- -T 3 http://192.168.198.67 | head -4
```

### 2.7 hostNetwork Pods and port conflicts

**What it is.** `spec.hostNetwork: true` puts the Pod in the **node's** network namespace instead of a new one. The Pod has no veth, no CNI-assigned IP. Its IP is the node IP, and its listening ports are the node's ports.

| Field | Meaning | Default | Risk |
|---|---|---|---|
| `spec.hostNetwork` | Use the node's network namespace | `false` | The Pod can bind any node port, see node-local services, and is not isolated. Often needs privilege to be useful. |
| `spec.dnsPolicy` | How DNS is configured | `ClusterFirst` | With `hostNetwork: true`, `ClusterFirst` is treated as `Default` (the node's `/etc/resolv.conf`), so cluster names (`web.ns.svc`) do not resolve. Set **`ClusterFirstWithHostNet`** to keep cluster DNS. |
| `containers[].ports[].hostPort` | Also open a port on the node | none | For a `hostNetwork` Pod the API server sets `hostPort` equal to `containerPort` for you. |

**Port conflicts.** A node has one set of ports. Two `hostNetwork` Pods that both listen on port 80 cannot run on the same node, and neither can one of them with a host service (such as `sshd` on 22). Two outcomes:

- The Pod declares `containerPort: 80`. The scheduler sees the (defaulted) `hostPort`, and a node that already has it in use is filtered out. A Pod that fits no node stays `Pending`, with the event `... node(s) didn't have free ports for the requested pod ports`.
- The Pod does **not** declare the port. The scheduler cannot see it. The Pod starts, the process fails to bind, and the container crashes with the application's own "address already in use" error (`CrashLoopBackOff`).

Always declare `containerPort` on `hostNetwork` Pods so the scheduler can protect you. A `hostNetwork` Pod is also what the control plane static Pods and `calico-node` are: `k -n kube-system get pods -o wide` shows their IP equal to the node IP.

**For connectivity.** A `hostNetwork` Pod is reached at the node IP and port, not at a Pod-CIDR address. NetworkPolicy support for these Pods is unspecified in the Kubernetes API: many plugins treat the traffic as node traffic and do not apply Pod policies to it.

### 2.8 NetworkPolicy effects on connectivity

By default Pods accept traffic from everywhere (**non-isolated**). As soon as one NetworkPolicy selects a Pod for a direction (ingress or egress), that Pod is **isolated** for that direction: only traffic that some policy allows gets through. Policies are enforced by the CNI plugin, not by the API server: Calico enforces them; a plugin without policy support (Flannel on its own) accepts the objects and ignores them. NetworkPolicy has its own lesson: [T4.20](../part4-cka/T4.20-define-and-enforce-network-policies.md).

How to tell a policy block from a dataplane break, in one test:

| Observation | Likely cause |
|---|---|
| Same-node **and** cross-node both fail, and `k get netpol -A` shows a policy selecting the target Pod | NetworkPolicy |
| Only cross-node fails, no policies | Dataplane: tunnel, route, forwarding, firewall, `calico-node` |
| Ping fails but `wget` to an allowed TCP port works | Policy that allows TCP only. The Kubernetes API defines TCP, UDP and SCTP rules, and says nothing about ICMP: what happens to ping depends on the plugin. Test with TCP too. |

Quick check: `k get netpol -A` and `k -n <ns> describe netpol <name>` (the `PodSelector` line says which Pods it isolates).

### 2.9 MTU and encapsulation issues

**MTU** (maximum transmission unit) is the largest packet an interface sends without splitting it. A normal Ethernet link is 1500 bytes. An overlay adds a header, so a Pod packet that was 1500 bytes no longer fits in one node-to-node packet. The Pod interface MTU must therefore be **smaller** than the node NIC MTU, by the size of the overhead.

| Encapsulation | Extra bytes (IPv4) | Pod MTU when node MTU is 1500 |
|---|---|---|
| None (routed/BGP) | 0 | 1500 |
| IPIP | 20 | 1480 |
| VXLAN | 50 | 1450 |
| WireGuard (Calico) | 60 | 1440 |

If the Pod MTU is too large, big packets with the "don't fragment" bit set are dropped, and the sender must be told with an ICMP "fragmentation needed" message. When that message is lost (a firewall that blocks ICMP, a cloud network that does not send it), the connection **hangs**. The pattern is distinctive: small requests work (ping, a short HTTP header, the TCP handshake), large payloads stall (a TLS handshake with big certificates, a big response, `scp`). It is intermittent from the user's point of view because it depends on payload size.

In the Calico manifest, `veth_mtu: "0"` in the `calico-config` ConfigMap means "detect the MTU from the node NIC and subtract the encapsulation overhead". Set a number there to override (after, restart `calico-node` with `k -n kube-system rollout restart ds/calico-node`; **existing Pods keep their old MTU until they are recreated**). On the operator install, set `spec.calicoNetwork.mtu` in the `Installation` resource.

Measure from a node with real `ping` (iputils; the busybox ping has no don't-fragment option): the payload is MTU minus 28 (20 IP + 8 ICMP).

```bash
# on w1, target = Pod b on w2. 1450 - 28 = 1422 fits a VXLAN Pod MTU; 1423 does not
ping -c2 -M do -s 1422 192.168.198.67
ping -c2 -M do -s 1423 192.168.198.67
ip -o link show | grep -E 'tunl0|vxlan.calico|cali|enp'   # MTU of every interface on the path
k exec a -- ip link show eth0                               # MTU inside the Pod (run on cp1)
```

EXPECTED OUTPUT (not captured), VXLAN pool, node MTU 1500:

```text
2 packets transmitted, 2 received, 0% packet loss
ping: local error: message too long, mtu=1450
```

### 2.10 Dual-stack awareness

**Dual-stack** means every Pod (and Service) can have one IPv4 and one IPv6 address at the same time. It is stable (GA since Kubernetes 1.23). What changes for connectivity:

- `node.spec.podCIDRs` has two entries (one per family), and `pod.status.podIPs` lists two addresses (`pod.status.podIP` still shows the first).
- kubeadm: give two comma-separated values in the cluster config. The IPv6 node mask defaults to `/64`. Controller-manager flags are `--cluster-cidr=192.168.0.0/16,fd00:10:244::/56` and (optional) `--node-cidr-mask-size-ipv4`, `--node-cidr-mask-size-ipv6`.
- The CNI must be dual-stack too. For the plain Calico manifest that means a second (IPv6) IPPool and turning IPv6 on in `calico-node` (the manifest sets `FELIX_IPV6SUPPORT=false` and the IPv6 pool is not created). IPIP does not support IPv6 pools.
- A Service picks its families with `spec.ipFamilyPolicy` (`SingleStack` default, `PreferDualStack`, `RequireDualStack`) and `spec.ipFamilies` (see [T4.18](../part4-cka/T4.18-use-clusterip-nodeport-loadbalancer-service-types.md)).

A kubeadm config file for a dual-stack cluster (use with `kubeadm init --config`, **not** `kubectl apply`):

```yaml
apiVersion: kubeadm.k8s.io/v1beta4
kind: ClusterConfiguration
kubernetesVersion: v1.37.1
networking:
  podSubnet: 192.168.0.0/16,fd00:10:244::/56      # one IPv4 range + one IPv6 range; becomes --cluster-cidr
  serviceSubnet: 10.96.0.0/12,fd00:10:96::/112    # IPv6 service range must be /108 or longer
```

Check on a running cluster: `k get pod a -o jsonpath='{.status.podIPs}'` prints a list; one address on a single-stack cluster. This lesson's lab cluster is single-stack IPv4. For exam tasks, dual-stack is mostly "read the fields"; building one is a cluster-rebuild job.

### 2.11 Debug tools: `kubectl debug`, `nsenter`, `tcpdump`

You debug in three places: inside the Pod, on the node, and on the wire.

| Where | Tool | Use |
|---|---|---|
| Inside the Pod's network namespace | `k exec <pod> -- <cmd>`; or `k debug -it <pod> --image=busybox:1.36 --target=<container>` | Run `ip addr`, `ip route`, `ping`, `wget`. The `k debug` ephemeral container joins the Pod's network namespace, so it works even when the Pod image has no shell. |
| On the node | `ssh <node>`, `sudo -i`; or `k debug node/<node> -it --image=busybox:1.36 --profile=sysadmin` | `k debug node` starts a Pod on that node with the host's network, PID and IPC namespaces, and the node's root file system mounted at `/host`. Run `chroot /host` to use the node's own `ip`, `crictl`, `tcpdump`. It leaves a Pod called `node-debugger-<node>-<random>` behind: delete it. |
| The Pod's namespace from the node | `nsenter -t <pid> -n <cmd>` or `ip netns exec <name> <cmd>` | Run a node tool (like `tcpdump`) inside the Pod's network namespace, even if the Pod image has no such tool. |
| On the wire | `tcpdump -ni <iface> <filter>` | See the packets: whether they leave one node and arrive at the other. |

**Find the Pod's veth on the node (no PID needed).** Inside the Pod, `eth0@if12` means "my peer interface is number 12 on the node".

```bash
k -n lab-t417 exec a -- ip -o link show eth0          # on cp1: note the number after @if
# on w1 (the Pod's node):
ip -o link | grep '^12:'                              # that is the host side, cali<hash>
```

EXPECTED OUTPUT (not captured):

```text
3: eth0@if12: <BROADCAST,MULTICAST,UP,LOWER_UP,M-DOWN> mtu 1480 qdisc noqueue ...
12: cali3f2a1b9c7d1@if3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1480 qdisc noqueue ...
```

**Enter the Pod's network namespace from the node.** containerd + the CNI plugin create a named namespace for each Pod under `/var/run/netns` (names start with `cni-`), or you can use the PID of the Pod's process:

```bash
# on w1, as root
CID=$(crictl ps --name '^a$' -q)                                      # container ID of container "a"
PID=$(crictl inspect --output go-template --template '{{.info.pid}}' "$CID")
nsenter -t "$PID" -n ip addr show eth0                                # the Pod's eth0, seen from the node
nsenter -t "$PID" -n tcpdump -ni eth0 icmp                            # capture inside the Pod's namespace
ip netns list                                                         # alternative: named namespaces cni-<uuid>
```

`nsenter -n` switches only the network namespace, so the node's `tcpdump` binary runs against the Pod's `eth0`. That is the trick for distroless Pods. `crictl` is introduced in [T4.03](../part4-cka/T4.03-understand-extension-interfaces-cni-csi-cri.md).

**Where to put the capture** (cross-node ping, IPIP pool, from Pod `a` on `w1` to Pod `b` on `w2`):

| Capture point | Command | What you see |
|---|---|---|
| Pod `eth0` (w1) | `nsenter -t $PID -n tcpdump -ni eth0 icmp` | Request and reply with Pod IPs. |
| Host veth (w1) | `tcpdump -ni cali3f2a1b9c7d1 icmp` | Same packets, still Pod IPs. |
| Tunnel device (w1) | `tcpdump -ni tunl0 icmp` (IPIP) or `-ni vxlan.calico icmp` (VXLAN) | Same inner packets, just before wrapping or just after unwrapping. |
| Node NIC (w1) | `tcpdump -ni enp0s1 'ip proto 4'` (IPIP) or `'udp port 4789'` (VXLAN) | The **wrapped** packets: node IP to node IP. |
| Node NIC (w2) | the same filter | Packets arrive. If they show on w1 but not on w2, the network between them dropped them. If they show on w2 but no reply leaves, w2 dropped them (forwarding, firewall, no route). |

The rule: find the last place the packet is visible and the first place it is not. The break is between them. `tcpdump` is not on every host: on Ubuntu `apt-get install -y tcpdump` installs it, which needs the node to reach a package mirror (UNVERIFIED for exam hosts). Find the NIC name with `ip -4 route show default` (the word after `dev`).

### 2.12 Under the hood and related but different

**Under the hood: one Pod starting.** (1) The scheduler binds the Pod to a node. (2) The kubelet asks containerd to create the Pod sandbox (the `pause` container that owns the network namespace). (3) containerd runs the CNI plugin from `/etc/cni/net.d` with `ADD`. (4) `calico` creates the veth pair, moves one end into the namespace as `eth0`, asks `calico-ipam` for an address from the node's block, sets the default route via `169.254.1.1`, and creates the workload record. (5) Felix, running in `calico-node`, sees the new endpoint and programs the `/32` route and the firewall rules on the node. (6) BIRD already announced the node's block to the other nodes. Only after (5) and (6) can other nodes reach the new Pod.

**Related but different.**

| Looks the same | Difference |
|---|---|
| Pod-to-Pod vs Pod-to-Service | Pod-to-Pod uses the destination Pod IP directly: this lesson. Pod-to-Service uses a ClusterIP that kube-proxy rewrites (DNAT) to a Pod IP, then the same path as here. If Pod-to-Pod is broken, every Service that leaves the node is broken too. See [T4.18](../part4-cka/T4.18-use-clusterip-nodeport-loadbalancer-service-types.md). |
| CNI vs kube-proxy | CNI builds Pod addressing and Pod-to-Pod reachability. kube-proxy builds Service virtual IPs. They are separate components. |
| `podCIDR` vs IPPool | `podCIDR` is a Node API field set by the controller-manager. IPPool is a Calico object that Calico IPAM really uses. |
| Pod IP vs node IP | A normal Pod has its own IP. A `hostNetwork` Pod shares the node IP. |

## 3. How it works (diagram)

Two nodes, the default Calico IPIP pool from the v3.33.0 manifest. Addresses are the example values from the table at the top (Pod CIDR `192.168.0.0/16`, node network `10.10.0.0/24`, Service CIDR `10.96.0.0/12` is not on this path).

```text
 cluster Pod CIDR (Calico IPPool)  192.168.0.0/16    block size /26    encapsulation: IPIP (tunl0)
 Service CIDR 10.96.0.0/12 (virtual, never on the wire)       node network 10.10.0.0/24

   NODE w1  10.10.0.11                                       NODE w2  10.10.0.12
   Calico block 192.168.140.0/26                             Calico block 192.168.198.64/26
   (node.spec.podCIDR 192.168.1.0/24, not used by Calico)    (node.spec.podCIDR 192.168.2.0/24)

   +-------------------------+                               +--------------------------+
   | Pod a  192.168.140.5    |                               | Pod b  192.168.198.67    |
   | eth0  mtu 1480          |                               | eth0  mtu 1480           |
   | default via 169.254.1.1 |                               |                          |
   +------------|------------+                               +------------|-------------+
                | (1) veth pair                                           ^ (6) veth pair
   +------------v------------+                               +------------|-------------+
   | cali3f2a1b9c7d1         |                               | cali9e8d7c6b5a4          |
   | host end, proxy ARP on  |                               | route: 192.168.198.67    |
   +------------|------------+                               |   dev cali9e8d.. link    |
                | (2) node routing table                     +------------^-------------+
   +------------v------------+                                            | (5) forward (ip_forward=1)
   | 192.168.198.64/26       |                               +------------|-------------+
   |   via 10.10.0.12        |                               | routing table w2         |
   |   dev tunl0 (proto bird)|                               | + tunl0 unwraps          |
   +------------|------------+                               +------------^-------------+
                | (3) IPIP wrap                                           | (4) arrives on NIC
   +------------v------------+      outer: 10.10.0.11 -> 10.10.0.12      +------------|-------------+
   | tunl0  mtu 1480         |      IP protocol 4, inner = Pod packet     | enp0s1  mtu 1500         |
   | enp0s1 mtu 1500 --------+--------------------------------------------> (must pass protocol 4) |
   +-------------------------+      (VXLAN pool instead: UDP 4789,         +--------------------------+
                                     tunnel vxlan.calico, Pod MTU 1450)
```

Walkthrough:

1. Pod `a` sends to `192.168.198.67`. Its only route is the default via `169.254.1.1`, which the host veth answers by proxy ARP, so the packet goes to the node (1).
2. `w1` looks at its routing table (2). The block `192.168.198.64/26` is reached via `10.10.0.12` on `tunl0`. That line was put there by Felix/BIRD after `w2` announced its block.
3. `tunl0` wraps the whole Pod packet in a new IP packet from `10.10.0.11` to `10.10.0.12`, protocol 4 (3). With a VXLAN pool the wrapper is UDP 4789 on `vxlan.calico`.
4. The packet crosses the node network (4). The network only sees node IPs. If protocol 4 (or UDP 4789) is blocked, the packet dies here.
5. `w2` unwraps it, finds the inner destination in its routing table (`192.168.198.67 dev cali9e8d... scope link`) and forwards it (5). Forwarding must be enabled (`net.ipv4.ip_forward=1`) or it is dropped.
6. The packet leaves through the veth into Pod `b` (6). The reply takes the same path reversed.

## 6. Common mistakes and how to fix them

Quotes of messages are the parts I am sure of; `...` marks wording that may differ in your build.

| # | Symptom | What you will see | Cause | Fix (command) |
|---|---|---|---|---|
| 1 | Same-node Pod ping works, cross-node fails | `k exec a -- ping -c2 <ip-on-other-node>` prints `2 packets transmitted, 0 packets received, 100% packet loss`; `wget: download timed out` | CNI broken on one node (`calico-node` not Running or not Ready), or the encapsulation traffic (IP protocol 4, UDP 4789, TCP 179) is blocked | `k -n kube-system get pods -l k8s-app=calico-node -o wide`; `k -n kube-system logs <calico-node-pod> -c calico-node --tail=30`; on the node `ip route`; open the firewall or security group between nodes |
| 2 | Pod IPs overlap the node LAN | `k get pods -A -o wide` shows Pod IPs in the same range as `k get nodes -o wide` INTERNAL-IP; Pods cannot reach some nodes or LAN hosts; two routes cover the same range in `ip route` | `podSubnet` collides with the node network (for example a `192.168.0.0/16` Pod CIDR on a `192.168.1.0/24` LAN) | Rebuild with a Pod CIDR that does not overlap: `kubeadm reset -f` on every node, then `kubeadm init --pod-network-cidr=10.244.0.0/16` and set the same CIDR in the Calico manifest before `k create -f` |
| 3 | Intermittent large-payload failures | Ping works, small HTTP works, a big response or a TLS handshake hangs. `ping -M do -s 1472 <podIP>` prints `message too long, mtu=...` or `Frag needed and DF set` | MTU: Pod/tunnel MTU larger than the path allows, and the ICMP "fragmentation needed" message is lost | Set the CNI MTU: `k -n kube-system patch cm calico-config --type=merge -p '{"data":{"veth_mtu":"1450"}}'`, then `k -n kube-system rollout restart ds/calico-node`, then recreate the Pods |
| 4 | Cross-node fails after a node was changed or rebooted | `sysctl net.ipv4.ip_forward` prints `0` on a node; `ip route` looks complete; a capture shows packets arriving on that node's NIC and no reply leaving | IP forwarding is off on the receiving or sending node: the node accepts the packet but will not route it to the Pod | `sysctl -w net.ipv4.ip_forward=1` and remove the persistent override: `grep -r ip_forward /etc/sysctl.d /etc/sysctl.conf`, then `sysctl --system` |
| 5 | BGP never comes up, only some node pairs work | `k -n kube-system describe pod <calico-node>` shows readiness events such as `... BGP not established with <ip> ...` | `calico-node` autodetected the wrong NIC or IP (VMs with more than one interface), so BIRD peers with an address the other nodes cannot reach | `k -n kube-system set env ds/calico-node IP_AUTODETECTION_METHOD=interface=enp0s1` (use your NIC name); watch the rollout |
| 6 | New `hostNetwork` Pod stuck `Pending` | `k describe pod` shows `FailedScheduling ... node(s) didn't have free ports for the requested pod ports` | Another Pod (or host service) on every node already uses that host port | Change the port, reduce replicas, or use a normal Pod plus a Service. `k get pods -A -o wide` plus `ss -ltnp` on the node finds the owner |
| 7 | Everything between two Pods fails, same node too | Ping and `wget` fail even to a Pod on the same node; `k get netpol -A` lists a policy | A NetworkPolicy isolates the target (or source) Pod | `k -n <ns> describe netpol`; add an allow rule or delete the test policy ([T4.20](../part4-cka/T4.20-define-and-enforce-network-policies.md)) |

**How to work each failure, step by step.**

*Failure 1: cross-node fails, same node works.* Run in this order and stop at the first thing that is wrong.

1. `k get pods -o wide` on both Pods: are they `Running`, on different nodes, with IPs in a Calico block? A Pod with no IP is a different problem (CNI add failed; read `k describe pod`).
2. `k -n kube-system get pods -l k8s-app=calico-node -o wide`: one per node, all `1/1 Running`. A `0/1` Pod on the failing node (the readiness probe checks Felix and BIRD) means that node does not run its dataplane. Read `k -n kube-system logs <pod> -c calico-node --tail=30`.
3. On both nodes `ip route`: is there a `via ... dev tunl0` (or `vxlan.calico`, or the NIC) line for the **other** node's block? No line = routes are not being learned (BGP down, wrong NIC, firewall on TCP 179).
4. `sysctl net.ipv4.ip_forward` on both nodes: must print `1` (failure 4).
5. `tcpdump` on the sender and receiver NICs with the filter for your mode (`'ip proto 4'`, `'udp port 4789'`, or plain `icmp` for unencapsulated): packets leave the sender but never arrive = the network or a firewall dropped them (`iptables -S` / `ufw status` on nodes; security group in a cloud). Packets arrive but no reply leaves = the receiver dropped them (forwarding, policy, no route).

The fix is whatever the failing step names. Restarting `calico-node` (`k -n kube-system rollout restart ds/calico-node`) helps only after the cause is removed.

*Failure 2: overlapping CIDRs.* Compare three lists: `k get nodes -o wide` (INTERNAL-IP), `k get pods -A -o wide` (IP of normal Pods), and `ip -4 addr` / `ip route` on a node. If a Pod IP lies inside the node LAN range, or the LAN range lies inside the pool, you have the problem. Why you cannot patch it: the pool `cidr` is immutable and `--cluster-cidr` is baked into the static Pod manifest and into kube-proxy; every running Pod already has an address from the old range. The safe fix in a lab is a rebuild: `kubeadm reset -f` and the cleanup steps on every node ([T4.02](../part4-cka/T4.02-create-and-manage-kubernetes-clusters-using.md)), then:

```bash
# on cp1: edit the manifest BEFORE creating it, so the pool uses the new range
curl -LO https://raw.githubusercontent.com/projectcalico/calico/v3.33.0/manifests/calico.yaml
sed -i -e 's|# - name: CALICO_IPV4POOL_CIDR|- name: CALICO_IPV4POOL_CIDR|' \
       -e 's|#   value: "192.168.0.0/16"|  value: "10.244.0.0/16"|' calico.yaml
kubeadm init --pod-network-cidr=10.244.0.0/16 --kubernetes-version=v1.37.1   # plus any other flags you used in T4.02
k create -f calico.yaml
```

Also check the Service CIDR (`10.96.0.0/12` by default) against the node network the same way. A different Service CIDR is set with `--service-cidr` on `kubeadm init`.

*Failure 3: MTU.* (1) Confirm small packets work: `k exec a -- ping -c2 <ip>`. (2) On a node, send packets of growing size with the don't-fragment bit: `ping -c2 -M do -s 1400 <podIP>`, then 1422, 1452, 1472. Find the largest size that works, add 28, and you have the path MTU. (3) Compare with `ip -o link` MTUs: node NIC, `tunl0` or `vxlan.calico`, `cali...`, and the Pod's `eth0` (`k exec a -- ip link show eth0`). The Pod MTU must be at most the path MTU minus the overhead (section 2.9). (4) Fix the configured value, restart `calico-node` so the tunnel device and the CNI config change, then **delete and recreate** the Pods: the MTU of an existing Pod's `eth0` does not change.

### Lab A (Easy): map the Pod IPs and CIDRs per node, and test every pair

**Setup** (T-cp1):

```bash
mkdir -p ~/lab/t417 && k create ns lab-t417
cat > ~/lab/t417/probe.yaml <<'EOT'

  name: probe

      labels: {app: probe}

      - {name: probe, image: "busybox:1.36", command: ["sleep", "3600"]}

```

**Task.** In namespace `lab-t417`, create the DaemonSet from `~/lab/t417/probe.yaml` so that one Pod runs on each of the three nodes. Then write these files (all under `~/lab/t417/`):

1. `map.txt`: one line per Pod, `<node> <podIP>`, sorted by node name.
2. `cidrs.txt`: one line per node, `<node> <spec.podCIDR>`.
3. `pool.txt`: one line, `<cidr> <blockSize>` of the Calico pool `default-ipv4-ippool`.
4. `matrix.txt`: one line for every ordered pair of **different** nodes, `<src-node> -> <dst-node> OK` or `FAIL`, decided by `ping -c2` from the Pod on the source node to the Pod IP on the destination node. Three nodes give six lines.

<details><summary>Hints</summary>

1. `k -n lab-t417 get pods -l app=probe -o jsonpath='{range .items[*]}...{end}'` can print node name, Pod IP and Pod name on one line each. Keep the Pod name in a scratch file: you need it for `k exec`.
2. A `while read sn sip sp; do while read dn dip dp; do ... done < f; done < f` loop gives you all pairs. Skip the pair when the two node names are equal. Redirect the `k exec` input with `</dev/null`.
3. `jsonpath` with `{.spec.podCIDR}` on `k get nodes` gives the CIDRs; the pool is a Calico object (`ippools.crd.projectcalico.org`).

</details>

<details><summary>Solution</summary>

```bash
k apply -n lab-t417 -f ~/lab/t417/probe.yaml
k -n lab-t417 rollout status ds/probe --timeout=120s        # wait until 3/3 Pods are Ready

# Scratch file: node, IP, Pod name. map.txt keeps only the first two columns.
k -n lab-t417 get pods -l app=probe \
  -o jsonpath='{range .items[*]}{.spec.nodeName} {.status.podIP} {.metadata.name}{"\n"}{end}' \
  | sort > ~/lab/t417/pods-raw.txt
cut -d' ' -f1,2 ~/lab/t417/pods-raw.txt > ~/lab/t417/map.txt

k get nodes -o jsonpath='{range .items[*]}{.metadata.name} {.spec.podCIDR}{"\n"}{end}' > ~/lab/t417/cidrs.txt
k get ippools.crd.projectcalico.org default-ipv4-ippool -o jsonpath='{.spec.cidr} {.spec.blockSize}{"\n"}' > ~/lab/t417/pool.txt

: > ~/lab/t417/matrix.txt
while read sn sip sp; do
  while read dn dip dp; do
    [ "$sn" = "$dn" ] && continue                           # same node: not part of the matrix
    if k -n lab-t417 exec "$sp" -- ping -c2 -W2 "$dip" </dev/null >/dev/null 2>&1; then r=OK; else r=FAIL; fi
    echo "$sn -> $dn $r" >> ~/lab/t417/matrix.txt
  done < ~/lab/t417/pods-raw.txt
done < ~/lab/t417/pods-raw.txt
cat ~/lab/t417/map.txt ~/lab/t417/cidrs.txt ~/lab/t417/pool.txt ~/lab/t417/matrix.txt
```

Why each step. The DaemonSet guarantees exactly one Pod per node, so you test one Pod per node without `nodeName`. The toleration is needed for `cp1`, which has the `NoSchedule` taint. The outer loop picks the source Pod, the inner loop the destination, and the `continue` drops same-node pairs. `ping -c2 -W2` waits at most 2 seconds per reply, so a broken pair fails in a few seconds instead of hanging. `</dev/null` stops `kubectl exec` from eating the loop's input.

</details>

T-cp1:

```bash
k -n lab-t417 exec a -- ping -c2 -W2 $BIP               # 100% packet loss: the fault is real
k -n lab-t417 get pods -o wide                          # both Running, on w1 and w2: not a Pod problem
k -n kube-system get ds calico-node                     # DESIRED 2, not 3: one node has no calico-node
k -n kube-system get pods -l k8s-app=calico-node -o wide   # none on w2
k -n kube-system get ds calico-node -o jsonpath='{.spec.template.spec.affinity}{"\n"}'   # the NotIn w2 rule
```

T-w2 (root):

```bash
ip route | grep -E 'tunl0|cali'                         # routes may look fine
sysctl net.ipv4.ip_forward                              # 0: the node will not route to its Pods
grep -r ip_forward /etc/sysctl.d /etc/sysctl.conf       # k8s.conf says 1, zz-lab.conf says 0
NIC=$(ip -4 route show default | awk '{print $5; exit}')
timeout 20 tcpdump -nli $NIC -c 2 'ip proto 4'          # while T-cp1 pings: requests ARRIVE, no reply leaves
```

How to read it. Fault 1: the DaemonSet has a node affinity that excludes `w2`, so `w2` has no Felix/BIRD: it neither learns routes nor programs the firewall and routes for new Pods. Fault 2: `net.ipv4.ip_forward=0` on `w2`: the packet arrives on the NIC or tunnel, the kernel must **forward** it to the Pod's veth, and with forwarding off it drops it. The capture shows requests arriving and no reply: the receiver dropped them. The sysctl file `zz-lab.conf` sorts after `k8s.conf`, so it wins when `sysctl --system` runs at boot. ```bash


T-w2 (root):

```bash
rm /etc/sysctl.d/zz-lab.conf
sysctl --system | grep ip_forward                        # last line: net.ipv4.ip_forward = 1
sysctl -n net.ipv4.ip_forward                            # 1
```

Why each step: removing the affinity lets the DaemonSet controller schedule `calico-node` on `w2` again; `rollout status` waits until it is Ready. Deleting the override file and re-running `sysctl --system` applies the remaining files (`k8s.conf` has `net.ipv4.ip_forward=1`) now and at every boot.

</details>

## 9. Quick review

1. What are the rules of the Kubernetes network model? <details><summary>Answer</summary>Every Pod has its own unique IP; any Pod can reach any other Pod on any node by that IP without NAT; agents on a node (kubelet) can reach all Pods on that node; `hostNetwork` Pods use the node IP and can reach all Pods. The CNI plugin implements it; it does not decide what is allowed (NetworkPolicy does).</details>
2. Which command shows on which node each Pod runs and its IP? <details><summary>Answer</summary>`k get pods -o wide` (add `-A` for all namespaces). For scripts, `k get pod b -o jsonpath='{.status.podIP}'`.</details>
3. On a kubeadm + Calico cluster, why is a Pod IP not inside its node's `spec.podCIDR`? <details><summary>Answer</summary>kubeadm turns on `--allocate-node-cidrs`, so the controller-manager fills `podCIDR` (a `/24` per node). Calico IPAM ignores that field: it cuts its own `/26` blocks out of the IPPool and assigns them to nodes. Both ranges are inside the pool, but they are independent.</details>
4. What must the node network allow for IPIP, VXLAN and BGP? <details><summary>Answer</summary>IPIP: IP protocol 4 (not a port). VXLAN: UDP 4789. BGP (BIRD): TCP 179. Missing any of these between all nodes breaks cross-node traffic for the matching mode.</details>
5. Same-node Pod ping works and cross-node fails. What do you check first, second and third? <details><summary>Answer</summary>1) `calico-node` Pods: one per node, all Ready (`k -n kube-system get pods -l k8s-app=calico-node -o wide`, logs of the failing node). 2) `ip route` on both nodes: a line for the other node's block via the tunnel or NIC; plus `sysctl net.ipv4.ip_forward` = 1. 3) `tcpdump` on both NICs with the filter for the mode: where do the packets stop; then firewall or security group.</details>
6. How do you find the encapsulation mode of the pool? <details><summary>Answer</summary>`k get ippools.crd.projectcalico.org default-ipv4-ippool -o jsonpath='{.spec.ipipMode} {.spec.vxlanMode}'`. The v3.33.0 plain manifest gives `Always Never` (IPIP); the operator default is `VXLANCrossSubnet`. The two modes cannot both be enabled on one pool.</details>
7. Small requests work, large downloads hang. Cause, test and fix? <details><summary>Answer</summary>MTU. The Pod or tunnel MTU is larger than the path allows (IPIP costs 20 bytes, VXLAN 50) and the "fragmentation needed" ICMP is lost. Test from a node with `ping -M do -s <size> <podIP>`; the largest working size plus 28 is the path MTU. Fix: set `veth_mtu` in `calico-config` (or `spec.calicoNetwork.mtu` with the operator), restart `calico-node`, recreate the Pods.</details>
8. Why does a second `hostNetwork` Pod on port 80 stay `Pending`, and what if the port is not declared? <details><summary>Answer</summary>A `hostNetwork` Pod shares the node's ports; the API server defaults `hostPort` to `containerPort`, so the scheduler filters out nodes where the port is in use (`didn't have free ports for the requested pod ports`). If the port is not declared the scheduler cannot see the clash; the Pod starts and the process fails to bind (`CrashLoopBackOff`).</details>
9. How do you find the host-side veth of a Pod without a PID? <details><summary>Answer</summary>Inside the Pod, `ip -o link show eth0` prints `eth0@ifN`. On the node, `ip -o link | grep '^N:'` shows the `cali...` interface with that index.</details>
10. Why must the Pod CIDR, Service CIDR and node network not overlap, and how do you fix it? <details><summary>Answer</summary>A routing table cannot tell which space an address belongs to, so packets go to the wrong place or the host becomes unreachable. The Pod CIDR (`--pod-network-cidr`) and the pool cidr are fixed at install (the pool `cidr` is immutable), so the fix is a rebuild with a non-overlapping range, setting the same range in the Calico manifest before `k create -f`.</details>
11. How do you run `tcpdump` inside a Pod's network namespace when the Pod image has no `tcpdump`? <details><summary>Answer</summary>On the Pod's node, as root: get the container PID with `crictl inspect` and run `nsenter -t <pid> -n tcpdump -ni eth0`. Or add an ephemeral container: `k debug -it <pod> --image=busybox:1.36 --target=<container>`, which shares the Pod's network namespace (use an image that has the tool you need).</details>
12. Which three views of a ping do you get with a VXLAN pool, and what does each show? <details><summary>Answer</summary>Pod `eth0` or the host veth: Pod to Pod addresses. `vxlan.calico`: still Pod to Pod (unwrapped or about to be wrapped). Node NIC filtered on `udp port 4789`: node to node, with `vni 4096`, the Pod packet inside.</details>
