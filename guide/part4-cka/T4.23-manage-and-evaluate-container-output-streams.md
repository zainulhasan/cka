## 1. Why this matters

When an app or a control-plane component fails, the text it printed on stdout and stderr is the evidence. `kubectl logs` reads it through the API server, so it stops working exactly when the API server is the broken part. If you also know the node-level paths (`crictl logs`, files under `/var/log/pods`, `journalctl`), you can still find the crash reason, save it to a file, and fix the fault. This lesson also teaches the reading skill: find the first error, spot a panic or an out-of-memory kill, and save only the lines a task asks for.

Prerequisites: the `kubectl logs` basics are in [T3.22](../part3-ckad/T3.22-utilize-container-logs.md). The `journalctl` basics are in [T1.06](../part1-linux/T1.06-systemd-and-journalctl.md). Here we only recap them.

## 2. Concepts

### 2.1 What "container output" is

A container is a Linux process. Every process has three standard streams:

| Stream | File descriptor | Normal use |
|---|---|---|
| stdin | 0 | input (usually nothing in a Pod) |
| stdout | 1 | normal messages |
| stderr | 2 | errors and diagnostics |

Kubernetes has no log API of its own for apps. It only captures what the main process of each container writes to stdout and stderr. If an app writes to a file inside the container (for example `/var/log/app/app.log`), `kubectl logs` shows nothing. You then need a sidecar or an agent (section 2.9).

**Under the hood.** The container runtime starts the process with stdout and stderr connected to pipes. The runtime reads those pipes and writes every line to a file on the node, adding a prefix. The kubelet (the node agent) tells the runtime where to put the file. That file is the single source for `kubectl logs`, for `crictl logs`, and for any log agent that reads the node. Section 3 draws it.

### 2.2 `kubectl logs` recap (see [T3.22](../part3-ckad/T3.22-utilize-container-logs.md))

| Flag | What it does | Default / note |
|---|---|---|
| `-c <name>` | pick a container in a multi-container Pod | without it, kubectl picks the Pod's default container and prints `Defaulted container "x" out of: x, y` |
| `-p` / `--previous` | logs of the previous (terminated) instance of the container | error if there was no previous instance |
| `--all-containers` | logs of every container in the Pod (init containers too) | |
| `-l key=value` | all Pods matching a label selector | with `-l` the default `--tail` becomes 10, otherwise -1 (all lines) |
| `--since=5m` | only lines newer than a duration | `--since-time=<RFC3339>` takes an absolute time |
| `--tail=N` | only the last N lines | -1 means all |
| `-f` | follow (stream) new lines | Ctrl+C to stop |
| `--timestamps` | prefix each line with the timestamp | the kubelet takes the timestamp from the node file when you ask for it |
| `--prefix` | prefix each line with `[pod/<name>/<container>]` | useful with `-l` |
| `--max-log-requests=N` | how many Pods are read at once with `-l` or `-f` | default 5 |
| `--limit-bytes=N` | stop after N bytes | |

Under the hood, `kubectl logs` is a chain: kubectl asks the **API server**; the API server calls the **kubelet** of the node that runs the Pod (port 10250, path `/containerLogs/<ns>/<pod>/<container>`); the kubelet reads the log file on its node, **strips the CRI prefix** (section 2.3), and streams the text back. Three consequences:

1. If the API server is down, `kubectl logs` fails even though the log file is fine.
2. If the kubelet on that node is down or unreachable, `kubectl logs` fails for Pods on that node.
3. The stream tag (stdout or stderr) is removed on the way. `kubectl logs` shows both streams mixed in file order, and you cannot filter by stream with it.

### 2.3 Node-level log files and the CRI log format

The kubelet creates this layout under `/var/log/pods`:

```
/var/log/pods/<namespace>_<pod-name>_<pod-uid>/<container-name>/<restart-count>.log
```

- `<pod-uid>` is the Pod's `metadata.uid`. A re-created Pod with the same name has a new UID, so the directory name changes. Use a glob (`lab-t423_streams_*`).
- `<restart-count>` starts at 0 and goes up by one each time the container restarts. `0.log` is the first run, `1.log` the second run, and so on. The highest number is the newest run.
- For a **static Pod** (a control-plane Pod started from `/etc/kubernetes/manifests`), the Pod name ends with the node name (`kube-apiserver-cp1`) and the UID part is a hash of the manifest. Change the manifest and the UID changes, so the directory changes too.

There is a second, flat view for log agents:

```
/var/log/containers/<pod-name>_<namespace>_<container-name>-<container-id>.log
```

Each entry is a symbolic link to the real file under `/var/log/pods`. Use it when you know the Pod name and want one `ls | grep`.

Inside the file, every line uses the **CRI logging format** (CRI is the Container Runtime Interface, the API between kubelet and runtime):

```
<timestamp> <stream> <tag> <content>
```

| Field | Example | Meaning |
|---|---|---|
| timestamp | `2026-10-28T10:15:04.404040404Z` | RFC 3339 time with nanoseconds, UTC (`Z`), added by the runtime when it read the line |
| stream | `stdout` or `stderr` | which pipe the line came from |
| tag | `F` or `P` | `F` = full line. `P` = partial: the runtime split a very long line into chunks, and the next chunk continues it. The CRI spec allows extra tags after a colon (`P:xyz`). |
| content | `ERROR db connect failed` | the original text, without the newline |

The runtime splits very long lines at a fixed buffer size (about 16 KiB in containerd; see section 11). If you grep a file that contains `P` lines, a word may sit across two chunks.

### 2.4 stdout versus stderr

Programs choose the stream. The rule of thumb: results go to stdout, problems go to stderr. Kubernetes components written in Go use the `klog` library, which writes to **stderr** by default. So the log file of `kube-apiserver`, `kube-scheduler` and `kube-controller-manager` contains mostly `stderr` lines, even for plain `I` (info) messages. `etcd` is not a klog component: it also writes to stderr, but with its own logger (zap), by default as one JSON object per line, so it has no `I`/`E` severity letter (section 11). Do not assume "stderr" means "error".

The klog line starts with a severity letter and a date:

```
E1028 10:21:04.512345       1 file.go:123] "message" key="value"
```

`I` info, `W` warning, `E` error, `F` fatal (the process exits right after). In a CRI file you see this after the prefix: `2026-10-28T10:21:04.512345678Z stderr F E1028 10:21:04.512345 ...`.

To filter by stream you must read the node file or `crictl logs`:

```bash
# exact stream match on field 2 (safe)
awk '$2=="stderr"' 0.log
# sloppy match: also hits a stdout line whose TEXT contains " stderr " (unsafe)
grep ' stderr ' 0.log
```

**REAL OUTPUT (Docker, busybox:1.36).** These commands ran against a hand-made sample file in CRI format, not a file captured from a node. The file:

```bash
cat > 0.log <<'EOF'
2026-10-28T10:15:01.101010101Z stdout F INFO starting worker pool size=4
2026-10-28T10:15:02.202020202Z stdout F INFO listening on :8080
2026-10-28T10:15:03.303030303Z stderr F WARN cache cold, falling back to disk
2026-10-28T10:15:04.404040404Z stderr F ERROR db connect failed: dial tcp 10.0.0.9:5432: connect: connection refused
2026-10-28T10:15:05.505050505Z stdout F INFO retry 1 of 3
2026-10-28T10:15:06.606060606Z stderr F panic: runtime error: invalid memory address or nil pointer dereference
2026-10-28T10:15:06.606060607Z stderr F goroutine 1 [running]:
2026-10-28T10:15:06.606060608Z stdout F error: this is a stdout line that mentions stderr in its text
EOF
awk '$2=="stderr"' 0.log | wc -l        # 4  (exact)
grep -c ' stderr ' 0.log                 # 5  (one false hit: the last line)
awk '$2=="stderr"' 0.log | cut -d' ' -f4-
```

```text
4
5
WARN cache cold, falling back to disk
ERROR db connect failed: dial tcp 10.0.0.9:5432: connect: connection refused
panic: runtime error: invalid memory address or nil pointer dereference
goroutine 1 [running]:
```

`cut -d' ' -f4-` removes the three prefix fields and leaves the original text. This is the answer to the "only stderr matters but stdout was saved" mistake (section 6).

### 2.5 `crictl`: the runtime's own view

`crictl` is a command-line client for any CRI runtime (here containerd). It talks to the runtime socket, not to the API server, so it works when the API server is down. It needs root and the socket path. If it complains about endpoints, create `/etc/crictl.yaml`:

```yaml
runtime-endpoint: unix:///run/containerd/containerd.sock
```

| Command | Use |
|---|---|
| `crictl pods` | list Pod sandboxes (one per Pod) |
| `crictl ps` | list **running** containers |
| `crictl ps -a` | list **all** containers, including Exited ones. Newest first (check the CREATED column). |
| `crictl ps -a --name kube-apiserver` | filter by container name (regex) |
| `crictl ps -a -q` | print only IDs |
| `crictl logs <id>` | print the container's output |
| `crictl logs --tail=20 <id>` | last 20 lines |
| `crictl logs --since=5m <id>` | only recent lines |
| `crictl logs -t <id>` | with timestamps |
| `crictl logs -f <id>` | follow |
| `crictl inspect <id>` | full status as JSON (state, exit code, reason) |

Three facts to remember:

1. **`crictl ps` (without `-a`) hides crashed containers.** A control-plane container that crashed is in state `Exited` and only `crictl ps -a` lists it. This is the classic first step when the API server will not start.
2. **`crictl logs` writes the container's stdout to its own stdout and the container's stderr to its own stderr.** That is why the standard recipe is `crictl logs <id> 2>&1 | ...`. Without `2>&1`, the stderr part skips the pipe and goes straight to your terminal. Klog components write to stderr, so for them this matters a lot.
3. **`crictl logs` reads the same node file as the other paths.** crictl asks containerd, over the socket, for the container's status, which includes the path of its log file. Then crictl opens that file itself and strips the prefix. That is why it needs root on the node. It skips the API server and the kubelet, but not the file: if the file is gone (rotated away, Pod deleted), `crictl logs` fails too (section 11).

### 2.6 Control-plane static Pod logs without kubectl

The control-plane components run as static Pods. Their containers are normal containers in containerd, so `crictl` sees them. Recipe when `kubectl` is unavailable:

```bash
sudo -i
crictl ps -a --name kube-apiserver        # find the newest container, read STATE
crictl logs --tail=50 <id> 2>&1           # read why it stopped
```

If `crictl` cannot show the logs either (for example the runtime is unhealthy), read the file directly:

```bash
ls -dt /var/log/pods/kube-system_kube-apiserver-cp1_* | head -1     # newest directory
tail -n 50 /var/log/pods/kube-system_kube-apiserver-cp1_*/kube-apiserver/*.log
```

`crictl inspect <id>` adds two more clues: the exit code and the reason. See section 2.10 for how to read them.

### 2.7 kubelet and containerd logs with `journalctl` (see [T1.06](../part1-linux/T1.06-systemd-and-journalctl.md))

The kubelet and containerd are **systemd services on the node**, not containers. Their output goes to the systemd journal, not to `/var/log/pods`. When a static Pod does not even start, the kubelet's journal says why (bad manifest, image pull error, sandbox error).

```bash
journalctl -u kubelet --since '5 min ago' --no-pager       # last 5 minutes
journalctl -u kubelet -f                                   # follow
journalctl -u kubelet -p err --no-pager -n 50              # only priority err and worse, last 50
journalctl -u containerd --since '10 min ago' --no-pager   # the runtime
journalctl -k | grep -i 'out of memory'                    # kernel messages (OOM kills)
```

`--no-pager` prints straight to the terminal (so you can pipe or redirect it). `-p err` filters by syslog priority, which only helps if the program sets priorities; klog writes to stderr, which journald stores as priority `info`, so `-p err` may hide real errors. When in doubt, drop `-p` and use `grep -i`.

### 2.8 Log rotation and where old logs go

Without limits a chatty container would fill the node disk. The kubelet rotates the files. Two settings in the kubelet configuration (`/var/lib/kubelet/config.yaml` on a kubeadm node):

```yaml
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
containerLogMaxSize: 10Mi     # rotate when a file reaches this size
containerLogMaxFiles: 5       # keep at most this many files per container (current + rotated)
```

| Field | Default | Meaning | Risky or invalid values |
|---|---|---|---|
| `containerLogMaxSize` | `10Mi` | file size that triggers rotation | write it as a quantity with a unit (`10Mi`); a very small value rotates constantly and loses history quickly |
| `containerLogMaxFiles` | `5` | max log files kept per container, counting the current one | must be at least 2; `1` is rejected |

The defaults are the documented ones; confirm them on your 1.37 node (section 11). Apply a change by editing the file and running `sudo systemctl restart kubelet`. On a kubeadm cluster, `kubeadm upgrade` rewrites the node file from the `kubelet-config` ConfigMap, so a manual edit is not permanent across upgrades. The older flags `--container-log-max-size` and `--container-log-max-files` are deprecated in favour of this file.

How rotation looks on disk. The block below is an illustration of the naming pattern:

EXPECTED OUTPUT (not captured):

```text
/var/log/pods/lab-t423_streams_<uid>/main/0.log                       <- current file, still being written
/var/log/pods/lab-t423_streams_<uid>/main/0.log.20261028-101500       <- rotated, timestamp in the name
/var/log/pods/lab-t423_streams_<uid>/main/0.log.20261028-094000.gz     <- older rotated files are compressed
```

The kubelet checks files on a timer (about every 10 seconds), so a file can slightly exceed the limit. `kubectl logs` reads only the **current** `<n>.log`. Older rotated files stay on the node until they are pushed out by `containerLogMaxFiles`.

**Why your old logs are missing.** Check these causes in order:

| Cause | How to recognise it | What to do |
|---|---|---|
| Rotated away | `ls` shows `0.log.<timestamp>` files | read the rotated files with `zcat`/`cat` |
| Container restarted | a new `1.log` exists; the old run is in `0.log` | `kubectl logs -p`, or read `0.log` |
| Old container garbage-collected | only the latest run's file exists | nothing; the kubelet keeps few dead containers |
| Pod deleted | the whole `/var/log/pods/<ns>_<pod>_<uid>` directory is gone | nothing on the node. **A Pod's logs are deleted with the Pod.** Use a cluster-level agent (2.9) if you need them to outlive Pods. |
| Node replaced | the Pod ran on another node | read logs on the node that ran it (`k get pod -o wide`) |

### 2.9 Cluster-level logging architectures (awareness)

Kubernetes itself does not store logs after the Pod is gone. A real cluster adds a logging layer. The docs describe these patterns (https://kubernetes.io/docs/concepts/cluster-administration/logging/):

| Pattern | How it works | Good for | Cost |
|---|---|---|---|
| **Node-level agent (DaemonSet)** | one agent Pod per node mounts `/var/log` from the host and ships `/var/log/pods` or `/var/log/containers` files to a backend | apps that already log to stdout/stderr (the normal case) | one agent per node; agent needs host path access |
| **Sidecar that streams** | the app writes a file on a shared volume; a sidecar container runs `tail -F` on it and prints to its own stdout, so the normal pipeline picks it up | apps that cannot be changed to log to stdout, or that write several log files | doubles the data (file plus stdout copy); the file itself is not rotated by the kubelet |
| **Sidecar agent** | a log shipper runs as a sidecar and sends the file straight to the backend | per-app custom parsing | one shipper per Pod: more CPU and memory |
| **App pushes directly** | the app sends logs to a backend itself | special cases | the app carries the logging code; `kubectl logs` shows nothing |

A toy node-agent shape (not a production agent, not run in the labs). It shows the two things every node agent needs: a `hostPath` volume on `/var/log` and the same path inside the container, because `/var/log/containers/*` are symlinks to absolute `/var/log/pods/...` paths.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-agent-demo
  namespace: lab-t423
spec:
  selector:
    matchLabels:
      app: node-agent-demo
  template:
    metadata:
      labels:
        app: node-agent-demo
    spec:
      containers:
      - name: agent
        image: busybox:1.36
        command: ["sh", "-c", "tail -q -n0 -F /var/log/containers/*.log"]
        volumeMounts:
        - name: varlog
          mountPath: /var/log      # same path as on the host so the symlinks resolve
          readOnly: true
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
          type: Directory
```

A sidecar example that you can run is in section 4.

### 2.10 Saving, filtering and evaluating

**Saving.** Tasks ask for evidence in a file. Redirect with `>` (overwrite) or `>>` (append). Check the file afterwards, because an empty file is a silent failure.

```bash
k -n kube-system logs kube-apiserver-cp1 | grep -i error > /opt/errors.txt
k logs web --since=10m --timestamps > /opt/web-recent.txt
```

**Filtering.** `grep -i` ignores case. `grep -E 'error|fatal|panic'` matches several words. `grep -B2 -A5` adds context lines. `tail -n 20` keeps the last 20. Order matters: filter first, then `tail`, if the task says "last 20 error lines".

**Evaluating (reading the output).** Use this routine:

1. **Find the first error, not the loudest.** One root fault makes many follow-up errors. Find the earliest: `grep -n -i -m1 -E 'error|fatal|panic' file`. Then read the 5 lines around it (`sed -n '1,12p'` or `grep -B3 -A3`).
2. **Read the process exit.** `crictl inspect <id>` or `k describe pod` shows the exit code:

| Exit code | Meaning |
|---|---|
| 0 | clean exit |
| 1 | the app reported an error and quit (read the log) |
| 2 | wrong usage, often a bad flag or config |
| 126 / 127 | command found but not executable / command not found |
| 137 | killed by SIGKILL (128+9). Often OOM, see below. |
| 143 | stopped by SIGTERM (128+15), normal during shutdown |

3. **Panic stack.** A Go panic prints `panic: <reason>` then `goroutine 1 [running]:` and a list of frames. The reason is the first line. Read the first frame that names your own package, not the bottom of the stack.
4. **OOM (out-of-memory) kill.** When a container exceeds its memory limit the **kernel** kills it with SIGKILL. The process gets no chance to log, so the container log just **stops** without an error line. Evidence is elsewhere: `k describe pod` shows `Last State: Terminated`, `Reason: OOMKilled`, `Exit Code: 137`; the node's kernel log shows the kill (`journalctl -k | grep -i 'out of memory'`). An app-level message such as a Java `OutOfMemoryError` is different: the runtime printed it, so it is in the log.
5. **Crash loops.** The kubelet typically waits longer and longer between restarts (starting at about 10 s and doubling, up to a cap of about 5 min; the exact numbers depend on the kubelet version, section 11). Use `-p` (or the previous `<n>.log`) to read the run that died.

### 2.11 Related but different

| Looks similar | Difference |
|---|---|
| `kubectl logs` vs `kubectl get events` | logs are the app's output; events are messages from the cluster (scheduling, pulling, killing). Use both. |
| `kubectl logs` vs `kubectl exec ... cat file` | `logs` reads only stdout/stderr, `exec` reads files inside the container |
| `/var/log/pods` vs `/var/log/containers` | the first holds the real files; the second holds symlinks to them |
| Docker's `json-file` logs vs CRI logs | the Docker format is JSON per line (`{"log":...,"stream":...}`); Kubernetes nodes with containerd use the plain CRI text format above |
| `journalctl -u kubelet` vs the kubelet's container logs | the kubelet has no container; its output is in the journal |

There is also an alpha feature to ask the API for one stream only (feature gate `PodLogsQuerySplitStreams`, KEP-3288) and a node-log query endpoint for kubelet/journal logs through the API. Neither is on by default, and their state in 1.37 is UNVERIFIED (section 11). Do not rely on them; the node-file and `crictl` methods work everywhere.

## 3. How it works (diagram)

```
                       NODE (w1 or cp1)
  +--------------------------------------------------------------------------+
  |                                                                          |
  |   container process                                                      |
  |     fd 1 (stdout) ----+                                                  |
  |     fd 2 (stderr) ----+---> pipes held by the containerd-shim            |
  |                                  |                                       |
  |                                  v                                       |
  |                         containerd (CRI plugin)                          |
  |                         adds:  <timestamp> <stream> <F|P> <text>         |
  |                                  |                                       |
  |                                  v                                       |
  |   /var/log/pods/<ns>_<pod>_<uid>/<container>/<n>.log     <-- the truth    |
  |        ^        ^                               ^                        |
  |        |        |  symlink                      | rotated by kubelet     |
  |        |        +-- /var/log/containers/...     | (containerLogMaxSize / |
  |        |                                        |  containerLogMaxFiles) |
  |        |                                                                 |
  |   PATH A: crictl logs <id> --socket--> containerd: "LogPath of <id>?"    |
  |           then crictl reads + strips the SAME file, as root              |
  |           (no API server needed; fails if the file is gone)             |
  |        |                                                                 |
  |   PATH B: kubelet :10250 /containerLogs  (strips prefix) --------+       |
  |   PATH C: you read the file yourself: tail / awk / grep          |       |
  +------------------------------------------------------------------|-------+
                                                                      |
                                              kube-apiserver  <-------+
                                                    ^
                                                    |
                                             kubectl logs   (PATH B only works
                                                              while the API server is up)
```

Walkthrough:

1. The container writes to stdout and stderr. The shim keeps the pipe ends and containerd's CRI plugin reads them line by line.
2. The plugin writes one CRI line per output line into `/var/log/pods/<ns>_<pod>_<uid>/<container>/<n>.log`. `/var/log/containers` only holds symlinks to these files.
3. **Path B (`kubectl logs`)**: kubectl calls the API server, which calls the kubelet; the kubelet reads the file and removes the prefix. Needs the API server and the kubelet.
4. **Path A (`crictl logs`)**: crictl asks containerd, over the socket, for the container's log path, then reads and strips that same file itself (so it needs root). Works with the API server down; does not work if the file is gone.
5. **Path C (the file)**: always works if you have root on the node. It is the only path that keeps the stream tag and the timestamps without extra flags.
6. The kubelet rotates the file by size; Pod deletion removes the whole directory.

## 4. Commands and YAML you must produce fast

### Imperative commands

```bash
# Through the API (needs the API server)
k logs web                                   # one container Pod
k logs web -c sidecar                        # pick a container
k logs web -p                                # previous run (crash loop)
k logs -l app=web --all-containers --prefix  # all Pods with the label, every container
k logs web --since=10m --tail=50 --timestamps
k -n kube-system logs kube-apiserver-cp1     # a control-plane static Pod (mirror Pod)

# Without the API server (on the node, as root)
crictl ps -a --name kube-apiserver           # find the container, check STATE
crictl logs --tail=20 <id> 2>&1              # 2>&1: stderr must go into the pipe too
crictl inspect <id> | grep -E '"(state|exitCode|reason)"'
tail -f /var/log/pods/kube-system_etcd-cp1_*/etcd/0.log   # follow the file; glob = any UID (etcd lines are JSON, not klog)
awk '$2=="stderr"' /var/log/pods/<ns>_<pod>_*/<container>/0.log  # only stderr lines

# Services
journalctl -u kubelet --since '5 min ago' --no-pager
journalctl -u containerd --since '10 min ago' --no-pager
```

**The headline task: find and save the last 20 error lines of a crashed kube-apiserver using only crictl (no kubectl).** Run as root on `cp1`:

```bash
mkdir -p /opt/t423
ID=$(crictl ps -a --name kube-apiserver -q | head -1)    # newest container first
crictl logs "$ID" 2>&1 | grep -iE 'error|fatal|panic' | tail -n 20 > /opt/t423/apiserver-errors.txt
wc -l /opt/t423/apiserver-errors.txt
```

How it reads: `crictl ps -a -q` lists the IDs of all containers named like `kube-apiserver` (running or exited) with the newest first. `head -1` takes it. `2>&1` merges the two streams. `grep` keeps the error-like lines, `tail -n 20` keeps the last 20 of those, `>` saves them. If the first row of `crictl ps -a` is not the newest by the CREATED column in your version, pick the ID by eye instead.

### Declarative YAML: a log-streaming sidecar

An app that writes a file, plus a sidecar that turns the file into stdout. This uses a **native sidecar**: an init container with `restartPolicy: Always`. It starts before the app, keeps running next to it, and stops after it. Apply it with `k apply -f` in namespace `lab-t423` (create it first with `k create ns lab-t423`).

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-sidecar
  namespace: lab-t423
spec:
  volumes:
  - name: applog                 # shared scratch space; lives and dies with the Pod
    emptyDir: {}                 # default medium = node disk. Add sizeLimit if the file can grow without bound
  initContainers:
  - name: logger                 # the sidecar; its stdout is what `kubectl logs -c logger` shows
    image: busybox:1.36
    restartPolicy: Always        # makes this init container a sidecar; "Always" is the only valid value
    command: ["sh", "-c", "tail -n+1 -F /var/log/app/app.log"]
                                 # -n+1 : start at line 1 (not just the last 10)
                                 # -F   : follow by NAME and retry if the file is missing or replaced
                                 #        (-f follows the file descriptor and misses a re-created file)
    volumeMounts:
    - name: applog               # MUST be the same volume name the app uses
      mountPath: /var/log/app    # MUST be the path the app writes to
      readOnly: true             # the sidecar only reads
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "i=0; while true; do echo \"$(date +%T) INFO request $i\" >> /var/log/app/app.log; i=$((i+1)); sleep 2; done"]
    volumeMounts:
    - name: applog
      mountPath: /var/log/app    # a different path here means the app writes into the container filesystem and the sidecar sees nothing
```

Commands to check it:

```bash
k -n lab-t423 get pod app-with-sidecar
k -n lab-t423 logs app-with-sidecar -c logger --tail=3
```

Risks: the app's own file `app.log` is not rotated by the kubelet (only the sidecar's stdout copy is), so a busy app can fill the volume. If the Pod has no `-c`, `k logs` defaults to the main container, which is silent here.

**REAL OUTPUT (Docker, busybox:1.36).** The same two commands run as two containers sharing a Docker volume (this tests the `tail -F` pattern only, not Kubernetes). The reader container printed the app's lines from the shared file:

```text
06:18:21 INFO request 41
06:18:22 INFO request 42
...
```

A reader that mounts a different volume, so the file does not exist, prints this once and then waits silently:

```text
tail: can't open '/var/log/app/app.log': No such file or directory
```

## 5. Worked example

Goal: read the same control-plane log through three paths, then break the API server, find the reason without kubectl, save the evidence, and repair it.

Environment: **vms**, as root on `cp1` (`ssh cp1`, then `sudo -i`). The kubectl in this walkthrough needs a kubeconfig; on a kubeadm control-plane node run `export KUBECONFIG=/etc/kubernetes/admin.conf` if `k get nodes` fails with a permission or missing-config error. Lines show `...` where the content varies per cluster.

All blocks in this section are **EXPECTED OUTPUT (not captured)** because the machine that wrote this lesson has no VMs. Shapes come from the klog and CRI formats described above; placeholders are in angle brackets.

**Step 1. The same scheduler log through three paths.**

Path B, through the API server:

```bash
k -n kube-system logs kube-scheduler-cp1 --tail=2
```

EXPECTED OUTPUT (not captured):

```text
I1028 HH:MM:SS.uuuuuu       1 <file>.go:<line>] <message>
I1028 HH:MM:SS.uuuuuu       1 <file>.go:<line>] <message>
```

Path A, through the runtime:

```bash
ID=$(crictl ps --name kube-scheduler -q)
crictl logs --tail=2 "$ID" 2>&1
```

EXPECTED OUTPUT (not captured): the same two lines as above, no prefix.

Path C, the node file:

```bash
ls -d /var/log/pods/kube-system_kube-scheduler-cp1_*
tail -n 2 /var/log/pods/kube-system_kube-scheduler-cp1_*/kube-scheduler/*.log
ls -l /var/log/containers | grep kube-scheduler
```

EXPECTED OUTPUT (not captured):

```text
/var/log/pods/kube-system_kube-scheduler-cp1_<hash>
<timestamp> stderr F I1028 HH:MM:SS.uuuuuu       1 <file>.go:<line>] <message>
<timestamp> stderr F I1028 HH:MM:SS.uuuuuu       1 <file>.go:<line>] <message>
kube-scheduler-cp1_kube-system_kube-scheduler-<container-id>.log -> /var/log/pods/kube-system_kube-scheduler-cp1_<hash>/kube-scheduler/0.log
```

What to look for: the **message text is identical** in all three. Only the prefix differs. Path C has `<timestamp> stderr F` in front. That `stderr` is the tag you cannot see through `kubectl logs`. The symlink under `/var/log/containers` points at the file under `/var/log/pods`.

**Step 2. Break the API server and prepare a backup.**

Put the backup outside the manifests directory. The kubelet treats every file in `/etc/kubernetes/manifests` as a manifest, so a backup left there would start a second API server.

```bash
mkdir -p /root/t423-backup /opt/t423
cp /etc/kubernetes/manifests/kube-apiserver.yaml /root/t423-backup/
sed -i '/^    - kube-apiserver$/a\    - --audit-log-maxbackups-total=3' /etc/kubernetes/manifests/kube-apiserver.yaml
grep -n 'audit-log-maxbackups-total' /etc/kubernetes/manifests/kube-apiserver.yaml
```

The `sed` line adds a flag that `kube-apiserver` does not have, directly after `- kube-apiserver` in the `command` list. (The sed edit was tested on a sample file in Docker. The effect on a real API server is expected, not captured.)

**Step 3. Notice the symptom.** After 20-60 seconds:

```bash
k get nodes
```

EXPECTED OUTPUT (not captured):

```text
The connection to the server <address>:6443 was refused - did you specify the right host or port?
```

`kubectl logs` would fail the same way. Do not keep retrying kubectl. Go to the node.

**Step 4. Find the container.**

```bash
crictl ps -a --name kube-apiserver
```

Columns can differ by crictl version.

EXPECTED OUTPUT (not captured):

```text
CONTAINER      IMAGE         CREATED          STATE    NAME            ATTEMPT   POD ID       POD
<id-newest>    <image-id>    <n> seconds ago  Exited   kube-apiserver  <k>       <pod-id>     kube-apiserver-cp1
<id-older>     <image-id>    <n> minutes ago  Exited   kube-apiserver  0         <old-pod-id> kube-apiserver-cp1
```

Read this: a plain `crictl ps` would have shown nothing for `kube-apiserver`. The newest row is `Exited`. ATTEMPT is 0 for the first try of a container in a Pod sandbox and rises by one on each restart inside the same sandbox. The edit made the kubelet create a new sandbox, so the newest row can still show 0 (and a later row can show 1, 2, ...). Tell old from new by the CREATED column and the POD ID, not by ATTEMPT. The older row is the healthy run from before the edit.

**Step 5. Read the reason.**

```bash
ID=$(crictl ps -a --name kube-apiserver -q | head -1)
crictl logs --tail=20 "$ID" 2>&1
```

The exact wording of the first line is expected from the command-line library, not checked (section 11).

EXPECTED OUTPUT (not captured):

```text
Error: unknown flag: --audit-log-maxbackups-total
...
```

Read this: the first line names the exact flag. There is no stack trace because the process most likely exited while parsing its command line, before it started anything. The exit code (next command) confirms a non-zero exit (section 2.10).

```bash
crictl inspect "$ID" | grep -E '"(state|exitCode|reason)"'
```

EXPECTED OUTPUT (not captured):

```text
    "state": "CONTAINER_EXITED",
    "exitCode": <non-zero>,
    "reason": "Error",
```

**Step 6. Same evidence from the node file, and from the kubelet.**

```bash
D=$(ls -dt /var/log/pods/kube-system_kube-apiserver-cp1_* | head -1)
ls "$D/kube-apiserver"
tail -n 3 "$D/kube-apiserver"/*.log
journalctl -u kubelet --since '5 min ago' --no-pager | grep -i apiserver | tail -n 3
```

EXPECTED OUTPUT (not captured):

```text
0.log   1.log   ...
<timestamp> stderr F Error: unknown flag: --audit-log-maxbackups-total
... kubelet: "Error syncing pod, skipping" ... "CrashLoopBackOff" ... kube-apiserver-cp1 ...
```

`ls -dt` sorts by modification time, newest first, because the directory name (with the manifest-hash UID) changed when you edited the manifest. The kubelet journal confirms the container is being restarted with back-off.

**Step 7. Save the evidence (the headline task) and repair.**

```bash
crictl logs "$ID" 2>&1 | grep -iE 'error|fatal|panic' | tail -n 20 > /opt/t423/apiserver-errors.txt
cat /opt/t423/apiserver-errors.txt
cp /root/t423-backup/kube-apiserver.yaml /etc/kubernetes/manifests/kube-apiserver.yaml
```

A changed manifest makes the kubelet create a new Pod immediately, so you do not wait for a long crash back-off. The API server still needs 30-90 seconds to answer, so poll until it does:

```bash
until k get nodes >/dev/null 2>&1; do sleep 5; done
k get nodes
```

EXPECTED OUTPUT (not captured): a table with `cp1`, `w1`, `w2` and STATUS `Ready`.

Cleanup: `diff /root/t423-backup/kube-apiserver.yaml /etc/kubernetes/manifests/kube-apiserver.yaml && rm -rf /root/t423-backup /opt/t423`. No output from `diff` means the manifest is back to baseline.

## 6. Common mistakes and how to fix them

| Symptom | What you will see (exact error or event text) | Cause | Fix (command) |
|---|---|---|---|
| `kubectl logs` unavailable because the API server is down | `The connection to the server <address>:6443 was refused - did you specify the right host or port?` | `kubectl logs` goes kubectl, API server, kubelet; the first hop is dead | on the node as root: `crictl ps -a --name kube-apiserver`, `crictl logs <id> 2>&1 \| tail`, or `tail /var/log/pods/kube-system_kube-apiserver-*/kube-apiserver/*.log` |
| Old container logs missing | `Error from server (BadRequest): previous terminated container "x" in pod "y" not found`, or the node file is gone | the file was rotated, the old container was garbage-collected, or the Pod was deleted (its log directory goes with it) | `ls /var/log/pods/<ns>_<pod>_*/<container>/` for `0.log.<timestamp>` files; for the future run a node-level log agent (2.9) |
| Only stderr matters, but stdout was saved | the saved file has the right words but also unrelated `info` lines; or a `grep ' stderr '` file has extra lines | `kubectl logs` mixes both streams and drops the tag; `grep ' stderr '` matches text, not the tag | read the node file or `crictl logs`, and filter on field 2: `awk '$2=="stderr"' 0.log` |
| `crictl ps` shows no `kube-apiserver` | empty list | crashed containers are `Exited`, and `crictl ps` lists only running ones | `crictl ps -a --name kube-apiserver` |
| Only half the output is in the pipe | the error text prints on screen but `grep` and the file miss it | `crictl logs` sends container stderr to its own stderr | add `2>&1` before the pipe: `crictl logs <id> 2>&1 \| grep -i error` |
| Logs of a Pod that has not started | `Error from server (BadRequest): container "x" in pod "y" is waiting to start: ContainerCreating` | no container has run yet, so there is no output | `k describe pod y` and read Events |
| Multi-container Pod, wrong container | `Defaulted container "app" out of: app, logger (init)` (and the log is silent) | `kubectl logs` chose the default container | `k logs y -c logger` |
| `crictl` fails | an error that mentions the runtime endpoint, `permission denied` or `connection error` | not root, or no runtime endpoint configured | `sudo -i`; create `/etc/crictl.yaml` with `runtime-endpoint: unix:///run/containerd/containerd.sock` |
| Container dies with no error in its log | log stops mid-flow; Pod `RESTARTS` goes up | the kernel OOM-killed it (SIGKILL), the app could not log | `k describe pod y \| grep -A4 'Last State'` shows `OOMKilled` and `137`; `journalctl -k \| grep -i 'out of memory'` on the node |
| Sidecar prints nothing | `tail: can't open '/var/log/app/app.log': No such file or directory` | sidecar and app do not share the volume or path | `k exec y -c app -- ls /var/log/app` versus `k exec y -c logger -- ls /var/log/app` |

**Troubleshooting path: "kubectl logs does not work".** Follow it in order:

1. Run `k get nodes`. If it fails with "connection refused", the API server is the problem. Go to step 4.
2. If `k get nodes` works but `k logs` says `Error from server: Get "https://<node-ip>:10250/containerLogs/...": dial tcp ... i/o timeout` (or similar), the kubelet or the network to it is the problem. SSH to the node and check `systemctl status kubelet`.
3. If the error says the container is waiting to start, there are no logs yet. Read Events.
4. On the node as root: `crictl ps -a --name <component>`. Read the STATE column. If `Running`, `crictl logs --tail=50 <id> 2>&1`. If `Exited`, read the same and then `crictl inspect <id> | grep -E '"(exitCode|reason)"'`.
5. If there is no container at all for a static Pod, the kubelet never created one. Read `journalctl -u kubelet --since '10 min ago' --no-pager | grep -i <component>` (a bad manifest, a failed image pull or a sandbox error).

**Troubleshooting path: "my old logs are gone".** Run `k get pod -o wide` to see the node. On that node: `ls -l /var/log/pods/<ns>_<pod>_*/<container>/`. Many files named `0.log.<timestamp>` mean rotation (read them, they are plain text or `.gz`). A higher `<n>.log` than you expected means restarts (read the lower numbers). No directory at all means the Pod is gone: its logs left with it.

**Troubleshooting path: "wrong stream saved".** Look at one raw line from the node file. Field 2 is the stream. Re-run with `awk '$2=="stderr"'` (or `crictl logs <id> 2>&1 >/dev/null` to keep only stderr, see the easy lab). Compare line counts to prove the difference.

### Lab 1 (Easy): collect app logs through three paths and compare formats

**Terminals.** Open two terminals on your host. Do not run `ssh w1` from inside the `cp1` session.

| Terminal | How you get it | Used for |
|---|---|---|
| T1 | `ssh cp1` (normal user; `k` works here) | setup, kubectl steps, kubectl verification, final cleanup |
| T2 | `ssh w1`, then `sudo -i` (root on `w1`) | node-file and `crictl` steps, their verification and cleanup |

**Environment and setup** (in T1, on `cp1`):

```bash
mkdir -p ~/lab/t423 && cd ~/lab/t423
sudo mkdir -p /opt/t423 && sudo chown "$USER" /opt/t423
k create ns lab-t423
cat > streams.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: streams
  namespace: lab-t423
spec:
  nodeSelector:
    kubernetes.io/hostname: w1
  containers:
  - name: main
    image: busybox:1.36
    command: ["sh", "-c", "i=0; while true; do echo out $i; echo err $i >&2; i=$((i+1)); sleep 1; done"]
```

**Task.** Pod `streams` (container `main`) in namespace `lab-t423` runs on node `w1`.

1. In T1 (`cp1`): with kubectl, save its last 6 log lines to `/opt/t423/kubectl.txt`.
2. In T2 (`w1`, root): save the absolute path of the Pod's current node log file to `/opt/t423/path.txt` (create `/opt/t423` on `w1` first).
3. In T2: save only the **stderr** lines of that node file, with their CRI prefix kept, to `/opt/t423/node-file.txt`.
4. In T2: with `crictl`, save only the container's **stderr** output to `/opt/t423/crictl-stderr.txt`.

**Hints** (collapsed):

<details><summary>Hint 1</summary>

The directory is `/var/log/pods/lab-t423_streams_<uid>/main/`. A glob replaces the UID. This Pod never restarted, so the file is `0.log`.

</details>

<details><summary>Hint 2</summary>

A CRI line is `<timestamp> <stream> <tag> <text>`. The stream is the second field. `awk '$2=="stderr"'` tests it exactly.

</details>

<details><summary>Hint 3</summary>

`crictl logs` writes container stderr to its own stderr. Redirect only file descriptor 2 to the file and throw stdout away: `2>file >/dev/null`. Find the ID with `crictl ps --name main -q`.

</details>

<details><summary>Solution</summary>

In T1 (`cp1`):

```bash
k -n lab-t423 logs streams --tail=6 > /opt/t423/kubectl.txt
head -3 /opt/t423/kubectl.txt
```

Why: `--tail=6` keeps the last 6 lines. kubectl prints plain text without the prefix. Look at the output: `out N` and `err N` lines are mixed and you cannot tell which stream is which.

In T2 (root on `w1`; open it now with `ssh w1` then `sudo -i` if you have not):

```bash
mkdir -p /opt/t423
ls /var/log/pods/lab-t423_streams_*/main/0.log > /opt/t423/path.txt
cat /opt/t423/path.txt
head -4 "$(cat /opt/t423/path.txt)"
awk '$2=="stderr"' "$(cat /opt/t423/path.txt)" > /opt/t423/node-file.txt
crictl logs "$(crictl ps --name main -q)" 2>/opt/t423/crictl-stderr.txt >/dev/null
head -3 /opt/t423/crictl-stderr.txt
```

Why each step: `ls` with a glob finds the unknown UID, and saving the result proves you found the path. The file's first lines show the format `<timestamp> stdout F out 0` and `<timestamp> stderr F err 0`. `awk` keeps lines whose second field is `stderr`. In the `crictl` line, `2>file` sends the container's stderr stream to the file and `>/dev/null` drops its stdout stream.

Compare the three formats in your head: kubectl shows `err 12`; crictl shows `err 12`; the node file shows `2026-...Z stderr F err 12`. Only the node file carries the timestamp and the stream.

Keep T2 open for the verification.

</details>

**Verification.** In T1 (`cp1`):

```bash
test "$(wc -l < /opt/t423/kubectl.txt)" -eq 6 && ! grep -qE '^[0-9]{4}-' /opt/t423/kubectl.txt && echo PASS-kubectl || echo FAIL-kubectl
```

In T2 (root on `w1`):

```bash
test -f "$(cat /opt/t423/path.txt)" && grep -q 'lab-t423_streams_' /opt/t423/path.txt && echo PASS-path || echo FAIL-path
test "$(wc -l < /opt/t423/node-file.txt)" -ge 5 && test "$(awk '$2!="stderr"' /opt/t423/node-file.txt | wc -l)" -eq 0 && echo PASS-node-file || echo FAIL-node-file
grep -qE '^err [0-9]+$' /opt/t423/crictl-stderr.txt && ! grep -q '^out' /opt/t423/crictl-stderr.txt && echo PASS-crictl || echo FAIL-crictl
```

Each line prints `PASS-...` only when its file has the right shape. An empty file, a file with stdout lines, or a missing prefix prints `FAIL-...`.

### Lab 2 (Medium): read the crash reason of a broken kube-apiserver without kubectl

**Environment and setup.** As root on `cp1` only (`ssh cp1`, `sudo -i`). This lab stops the API server for a few minutes. Do not run other labs at the same time.

**Hints** (collapsed):

<details><summary>Hint 1</summary>

`crictl ps` without `-a` shows nothing for a crashed container. Use `-a`, and `-q` for IDs only.

</details>

<details><summary>Hint 2</summary>

The component writes to stderr. Put `2>&1` before the first pipe, then `grep -i`, then `tail -n 20`.

</details>

<details><summary>Hint 3</summary>

</details>

<details><summary>Solution</summary>

```bash

cat /opt/t423/apiserver-errors.txt /opt/t423/exit-code.txt
```

Why: `-a` lists exited containers; the newest is first. `2>&1` is needed because the error goes to stderr. `grep -i` is case-insensitive so `Error` and `error` both match; `tail -n 20` comes after `grep` so you get the last 20 matches, not the matches inside the last 20 lines. `crictl inspect` prints JSON; `grep -m1` takes the first `exitCode` field. Read `apiserver-errors.txt`: it names the flag `--audit-log-maxbackups-total`, which the API server does not have.

Repair: remove the bad flag by restoring the backup.

```bash
cp /root/t423-backup/kube-apiserver.yaml /etc/kubernetes/manifests/kube-apiserver.yaml
until k get nodes >/dev/null 2>&1; do sleep 5; done
k get nodes
```

Why restore instead of editing: it returns the file to a known-good state. You could also delete the one line with `sed -i '/audit-log-maxbackups-total/d'`. Waiting is needed: the kubelet sees the file change, stops the broken Pod and creates a new one; the API server needs 30-90 seconds to become ready, and the `until` loop retries `k get nodes` every 5 seconds until it answers. The nodes can show `NotReady` for a few seconds after the API server returns; the verification below can be re-run.

</details>

**Verification** (as root on `cp1`, after the repair):

```bash
grep -q . /opt/t423/id.txt && echo PASS-id || echo FAIL-id
grep -q 'audit-log-maxbackups-total' /opt/t423/apiserver-errors.txt && test "$(wc -l < /opt/t423/apiserver-errors.txt)" -le 20 && echo PASS-errors || echo FAIL-errors
grep -qE 'exitCode"?: *[1-9]' /opt/t423/exit-code.txt && echo PASS-exit || echo FAIL-exit
! grep -q 'audit-log-maxbackups-total' /etc/kubernetes/manifests/kube-apiserver.yaml && echo PASS-manifest || echo FAIL-manifest
test "$(k get nodes --no-headers | awk '$2=="Ready"' | wc -l)" -eq 3 && echo PASS-nodes || echo FAIL-nodes
```

If the API server is still starting, the last line can print `FAIL-nodes` for a moment even after a correct fix: wait a few seconds and run it again.

**Cleanup.**

```bash
diff /root/t423-backup/kube-apiserver.yaml /etc/kubernetes/manifests/kube-apiserver.yaml && echo BASELINE-OK
rm -rf /opt/t423 /root/t423-backup
```

`diff` prints nothing and the shell prints `BASELINE-OK` when the manifest is identical to the baseline. If `diff` prints lines, copy the backup back before you delete it.

### Lab 3 (Break-fix): a sidecar that loses the logs

**Environment and setup** (on `cp1`, not as root; you need a working `k`):

```bash
mkdir -p ~/lab/t423 && cd ~/lab/t423
sudo mkdir -p /opt/t423 && sudo chown "$USER" /opt/t423
k create ns lab-t423
```

`break.sh` (save it as a file and run it with `bash break.sh`; it uses `kubectl`, because the alias `k` does not exist inside a script):

```bash
#!/bin/bash
cd ~/lab/t423
cat > weblog.yaml <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: weblog
  namespace: lab-t423
spec:
  volumes:
  - name: applog
    emptyDir: {}
  - name: scratch
    emptyDir: {}
  initContainers:
  - name: logger
    image: busybox:1.36
    restartPolicy: Always
    command: ["sh", "-c", "tail -n+1 -F /var/log/app/app.log"]
    volumeMounts:
    - name: scratch
      mountPath: /var/log/app
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "i=0; while true; do echo \"$(date +%T) INFO request $i\" >> /var/log/app/app.log; i=$((i+1)); sleep 2; done"]
    volumeMounts:
    - name: applog
      mountPath: /var/log/app
EOF
kubectl apply -f weblog.yaml
kubectl -n lab-t423 wait --for=condition=Ready pod/weblog --timeout=90s
sleep 10
```

**Task.** Pod `weblog` in namespace `lab-t423` has an `app` container that writes its access log to `/var/log/app/app.log`, and a native sidecar `logger` that should print that file to its own stdout. `k -n lab-t423 logs weblog -c logger` does not show the app's lines. Fix it so the sidecar prints them. Do not change the `app` container. When it works, save the last 3 lines of the `logger` output to `/opt/t423/weblog.txt`.

**Hints** (collapsed):

<details><summary>Hint 1</summary>

Compare what the two containers see: `k -n lab-t423 exec weblog -c app -- ls -l /var/log/app` and the same with `-c logger`.

</details>

<details><summary>Hint 2</summary>

Both containers mount a volume at the same path. Check whether it is the **same volume** (the `name:` field in each `volumeMounts` entry).

</details>

<details><summary>Hint 3</summary>

A running Pod's `volumeMounts` cannot be edited. Change the YAML and re-create the Pod with `k replace --force -f`.

</details>

<details><summary>Solution</summary>

Diagnosis, in order:

```bash
k -n lab-t423 logs weblog -c logger                      # shows: tail: can't open '/var/log/app/app.log': No such file or directory
k -n lab-t423 exec weblog -c app -- ls /var/log/app       # app.log is there
k -n lab-t423 exec weblog -c logger -- ls /var/log/app    # empty
k -n lab-t423 get pod weblog -o jsonpath='{range .spec.initContainers[*].volumeMounts[*]}{.name}{"\n"}{end}'   # scratch
```

Reading it: the app writes the file, the sidecar's directory is empty, so the two containers do not share a volume. The sidecar mounts `scratch` while the app uses `applog`. `tail -F` waits silently for a file that will never appear.

Fix: in `weblog.yaml` change the sidecar mount from `scratch` to `applog` (and add `readOnly: true`), then re-create the Pod:

Edit `~/lab/t423/weblog.yaml` by hand (the `logger` block is the one with `scratch`). The sidecar block must read:

```yaml
    volumeMounts:
    - name: applog
      mountPath: /var/log/app
      readOnly: true
```

Then:

```bash
cd ~/lab/t423
k replace --force -f weblog.yaml
k -n lab-t423 wait --for=condition=Ready pod/weblog --timeout=90s
sleep 10
k -n lab-t423 logs weblog -c logger --tail=3 > /opt/t423/weblog.txt
cat /opt/t423/weblog.txt
```

Why `replace --force`: Pod volume mounts are immutable, so the Pod must be deleted and created again. The unused `scratch` volume can stay; an unused volume is harmless.

</details>

**Verification:**

```bash
test "$(wc -l < /opt/t423/weblog.txt)" -eq 3 && grep -q 'INFO request' /opt/t423/weblog.txt && ! grep -q "can't open" /opt/t423/weblog.txt && echo PASS-file || echo FAIL-file
k -n lab-t423 logs weblog -c logger --tail=1 | grep -q 'INFO request' && echo PASS-live || echo FAIL-live
test "$(k -n lab-t423 get pod weblog -o jsonpath='{.spec.initContainers[0].volumeMounts[0].name}')" = applog && echo PASS-mount || echo FAIL-mount
```

**Cleanup.**

```bash
k delete ns lab-t423
rm -rf /opt/t423 ~/lab/t423
```

## 8. Exam tips

- **Read the task for the file path first, then pick the path to the log.** If kubectl works, `k logs ... | grep -i error > /path` is fastest. If `k get nodes` hangs or is refused, do not wait: `ssh <node>`, `sudo -i`, `crictl ps -a`.
- **Always `crictl ps -a` for crashed containers, and always `2>&1` on `crictl logs`.** These two habits cover the most common dead ends. Check the saved file with `wc -l` and `head` before you move on.
- **Use globs, not UIDs.** `/var/log/pods/kube-system_kube-apiserver-cp1_*/kube-apiserver/*.log`. The UID changes with the manifest.
- **Filter on the stream tag with `awk '$2=="stderr"'`**, not `grep stderr`. Tools on the exam SSH hosts are kubectl, yq, curl, wget and man (summary E9, https://docs.linuxfoundation.org/tc-docs/certification/tips-cka-and-ckad). `grep`, `awk` and `sed` are normal Linux tools on the nodes; their presence on the exam hosts is UNVERIFIED, so also know the pure-kubectl and `crictl` routes. This lesson does not use `jq`.
- **Docs pages to open:** https://kubernetes.io/docs/concepts/cluster-administration/logging/ (log locations, rotation, architectures), https://kubernetes.io/docs/tasks/debug/debug-cluster/ (control-plane troubleshooting list), https://kubernetes.io/docs/tasks/debug/debug-cluster/crictl/ (crictl commands). They are on the allowed list (summary E13, https://docs.linuxfoundation.org/tc-docs/certification/certification-resources-allowed).
- **Before moving on:** was the first error saved, or only the last? Did you save stderr and not only stdout? If you edited a static Pod manifest, is your backup outside `/etc/kubernetes/manifests`? Do not leave the cluster broken.

## 9. Quick review

1. Which command lists a crashed `kube-apiserver` container when kubectl does not work?
2. Why do you write `crictl logs <id> 2>&1 | grep ...` and not just `| grep ...`?
3. What are the four fields of a CRI log line, and which one does `kubectl logs` remove?
4. A Pod named `web` in `prod` has UID `abc`. What is the path of the log file of its container `app` after the second restart?
5. Which kubelet configuration fields control log rotation, and what are the defaults?
6. A container log ends abruptly with no error, and `RESTARTS` goes up. What is the likely cause, and which two commands prove it?
7. What is the difference between `/var/log/pods` and `/var/log/containers`?
8. How do you read the kubelet's own logs, and why can they not be read with `kubectl logs`?
9. Name two cluster-level logging patterns and one downside of each.
10. You must save "the last 20 error lines" of a log. In which order do you put `grep` and `tail`, and why?

<details><summary>Answers</summary>

1. `crictl ps -a --name kube-apiserver` as root on the control-plane node. `-a` includes Exited containers.
2. `crictl logs` sends the container's stderr to its own stderr, so it bypasses the pipe. `2>&1` merges them. Klog components write to stderr, so without it you miss most of the output.
3. Timestamp, stream (`stdout` or `stderr`), tag (`F` full or `P` partial), content. `kubectl logs` (via the kubelet) removes the prefix, so the timestamp and the stream are gone unless you use `--timestamps` (timestamp only).
4. `/var/log/pods/prod_web_abc/app/2.log`. Restart count 0 is the first run; after two restarts the current run is number 2.
5. `containerLogMaxSize` (default `10Mi`) and `containerLogMaxFiles` (default `5`) in the `KubeletConfiguration`, normally `/var/lib/kubelet/config.yaml`. Confirm the defaults on your version.
6. An OOM kill (SIGKILL from the kernel). `k describe pod web` shows `Reason: OOMKilled` and `Exit Code: 137`; on the node `journalctl -k | grep -i 'out of memory'` shows the kernel message.
7. `/var/log/pods/<ns>_<pod>_<uid>/<container>/<n>.log` holds the real files. `/var/log/containers/` holds symlinks named `<pod>_<ns>_<container>-<id>.log` that point at them.
8. `journalctl -u kubelet` on the node. The kubelet is a systemd service, not a container, so it has no Pod and no log file under `/var/log/pods`.
9. Node-level agent (DaemonSet): needs host path access and one Pod per node. Sidecar streaming: duplicates the data and the file is not rotated by the kubelet. Sidecar agent: one shipper per Pod costs CPU and memory. App pushes directly: `kubectl logs` shows nothing.
10. `grep` first, then `tail -n 20`. Then you keep the last 20 matching lines. With `tail` first you would keep the last 20 lines and then filter, which can return fewer than 20 error lines.

</details>
