## 2-5. Findings

| Severity | Section | Problem | Fix |
|---|---|---|---|
| minor | 2.4 podFailurePolicy example, line `podReplacementPolicy: Failed   # required value when podFailurePolicy is set` | Not required. If omitted, the API server defaults it to `Failed` when `podFailurePolicy` is set (the lesson's own table says so in 2.3). Only `TerminatingOrFailed` is rejected. | Change the comment to "optional: this is also the default when podFailurePolicy is set; TerminatingOrFailed is rejected". |
| minor | 2.4 successPolicy example and its expected output ("within seconds the Job gets `SuccessCriteriaMet`, then `Complete`") | The sleeping Pods run `sh -c` as PID 1, which ignores SIGTERM, so they end only after the 30 s grace period. `SuccessCriteriaMet` appears at once, but `Complete` arrives only after the Pods are gone. | Say `SuccessCriteriaMet` appears within seconds and `Complete` after the Pods terminate (up to about 30 s), or add `terminationGracePeriodSeconds: 5`. |
| minor | 7 Lab 3 verification, last line (`owned Job OK`) and Hint 1 | Hint 1 creates Job `t` with `--from=cronjob/report`, which carries an ownerReference to `report`. The `owned Job OK` check therefore passes without the schedule ever firing. (`fired OK` still guards this, but the last check is weak.) | Match on the scheduled Job name, e.g. `k get jobs -n lab-t302 -o name \| grep -q '^job.batch/report-[0-9]'`, or tell the learner to delete `t` before verifying. |
