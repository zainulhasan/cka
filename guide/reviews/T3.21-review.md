## 2-5. Findings

| Severity | Section | Problem | Fix |
|---|---|---|---|
| major | 4.1 (`k autoscale deploy web --min=2 --max=5 --cpu-percent=50 $do`) | In `kubectl` 1.37.1, `--cpu-percent` is itself deprecated. Running it prints `Flag --cpu-percent has been deprecated, Use --cpu with percentage or resource quantity format (e.g., '70%' ...)`. A lesson on deprecations teaches a deprecated flag, and it is the one imperative shortcut for the HPA. The command also contacts the API server (I got `connection refused`). The line comment "works; see note" and the note do not say it needs a reachable cluster and an existing Deployment `web` (the 4.1 snippet runs before any Deployment exists). | Use `k autoscale deploy web --min=2 --max=5 --cpu=50% $do > hpa.yaml`. State that it needs a cluster and the target Deployment, and that it is a shortcut for a v1-style CPU target only. Mention the flag deprecation as a live example of a CLI deprecation (ties to 2.14). |
| major | 5 Step 7 and 2.12 ("The gauge is `1` because a deprecated API was just requested", `apiserver_requested_deprecated_apis{...resource="endpoints"...} 1`) | The lesson states a mechanism it cannot confirm (conventions §10). The Endpoints warning is a resource-level warning (the Endpoints API is not a deprecated API version). `apiserver_requested_deprecated_apis` is populated from API versions marked deprecated, and a v1.37 cluster serves essentially none. The learner will likely get empty output from the `grep`, so the step cannot pass as written. Section 11 item 6 admits the label set and `removed_release` value are unknown, but the step still presents the series as the expected result. | Either remove Step 7 and keep the metric as awareness text only (2.12). Or rewrite the step so the expected result is "likely no series on a v1.37 kind cluster". Explain that a series appears only when a request hits a deprecated *version*, and that Endpoints warns through a different path. Mark the Endpoints claim `UNVERIFIED` until captured. |
| minor | 1 ("In the CKAD you get an old manifest and must spot the dead apiVersion...") | An exam statement with no summary §2 source (conventions §5 and §10). It comes from the topic entry, not from an exam fact. | Rewrite as advice: "A task may give you an old manifest; practise spotting the dead apiVersion and converting it", or mark it UNVERIFIED. |
| minor | Output labels (several blocks: "EXPECTED OUTPUT (not captured) - first block text is from...", "- label order and extra labels may differ", "- the loop prints ...", "- the exact prefix ... may differ") | Conventions §7 require the label to be exactly `EXPECTED OUTPUT (not captured)`. The suffixes make these blocks not an exact match for the accepted-limitation wording. | Keep the label exact on the first line and move the explanation to a sentence under the block. |
| minor | 4.6 cleanup, 5 cleanup, Labs A, B and C setup/cleanup (`k delete ns lab-t321 --wait=false`, then `k create ns lab-t321 2>/dev/null`) | The next lab or worked example usually starts while the namespace is still `Terminating`. The `2>/dev/null` hides the create failure, and the following `k apply -n lab-t321` fails with "being terminated" or "not found". This contradicts "any order works" (§10). | Drop `--wait=false`, or add `k wait --for=delete ns/lab-t321 --timeout=60s` after the delete. Remove `2>/dev/null` from the create, or replace it with `k get ns lab-t321 \|\| k create ns lab-t321`. |
| minor | Lab A verification and task | The verification block writes `expected.txt` in plain view, so it gives away every answer before the learner has tried (the Solution is collapsed, the verification is not). The line `grep -q ... m1.yaml && echo "m1 unchanged"` cannot fail the check. The task says "only ... kubectl read commands" but Hint 2 and the Solution use `k apply --dry-run=server`. | Compare against a hash or a collapsed `<details>` block. Make the m1 check exit non-zero (`grep -q ... m1.yaml \|\| echo FAIL`). Reword the task to allow `--dry-run=server`. |
| minor | Lab B verification | The task requires installing `kubectl-convert` into `~/bin` with the checksum verified and `~/bin` on `PATH`. The verification only greps the output files and the cluster state, so a learner who hand-migrated passes without installing the plugin. | Add `command -v kubectl-convert` (or `test -x ~/bin/kubectl-convert`) to the verification. |
| minor | 6 row 5 vs 4.6 setup | The row shows the decode error for `old-hpa.yaml` with version `autoscaling/v2beta2`, but the `old-hpa.yaml` created in the 4.6 setup (and the example in 4.4) uses `autoscaling/v2beta1`. I reproduced the error with `v2beta1`, and the text only differs in the version string. | Use `autoscaling/v2beta1` in the quoted error, or say the version in the message is whatever the file contains. |
| minor | 7 Lab C ("`break.sh` ... Run it") | `break.sh` uses the alias `k`. Aliases are not expanded when the file is run as a script (`bash break.sh`). `k create ns` then fails silently under `2>/dev/null` and the later steps break. | Say "paste this block into your shell, or source it" (or use `kubectl` inside the script). |
| minor | 5 Step 8, 6 row 3, 11 item 7 | For a Deployment with no selector, the API server normally returns the `spec.selector: Required value` line and also a second line, `spec.template.metadata.labels: Invalid value ... selector does not match template labels`. The lesson shows only the first line, and row 4 later presents the second as a separate case. A learner who sees both lines may think the Deployment has two separate problems. | Note that both lines can appear together, and that adding `selector.matchLabels` fixes both. |
