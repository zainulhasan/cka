| major | 6 (ErrImagePull row), 2.15, 4.4 drill 4 | The fix for a Pod stuck in `ErrImagePull` says to patch the ServiceAccount "or add `spec.imagePullSecrets` and re-apply", implying the existing Pod recovers. It does not. ServiceAccount `imagePullSecrets` are copied into a Pod only at creation (admission), so an existing Pod never inherits them. `spec.imagePullSecrets` is also immutable on a live Pod, so `k apply` of a changed bare Pod is rejected ("pod updates may not change fields other than ..."). Only a changed Secret with the same name is picked up on retry. Section 2.15 says "every Pod using that account inherits it" without the creation-time caveat. | State that for a bare Pod the fix is: create the Secret, then delete and recreate the Pod (`k delete pod POD $now; k apply -f pod.yaml`). The lesson captured only the Docker case with a forced sysctl. Section 11 admits the Pod case is unconfirmed. Containerd 2.x (used by `kindest/node:v1.37.0`) has CRI `enable_unprivileged_ports` default true since 2.0, so a non-root Pod on a current kind node may bind port 80 fine. This breaks conventions section 10 ("never state a mechanism you cannot confirm"). The entry's mistake may not reproduce on kind. | Rewrite as conditional: "whether a non-root Pod can bind port 80 depends on the runtime's `net.ipv4.ip_unprivileged_port_start`; containerd 2.x and Docker default it to 0, older runtimes and some hardened clusters leave 1024.
